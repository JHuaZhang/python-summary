## 1. 介绍

### 1.1 什么是方法重写

在面向对象编程中，子类继承父类后，会自动拥有父类定义的方法。但父类的行为并不总是适合子类：一个 `Shape` 父类的 `area()` 不知道该返回什么面积，一个 `Employee` 父类的汇报方式可能不适合 `Manager` 子类。这时，子类可以定义一个与父类**同名**的方法，用自己的实现替换掉从父类继承来的版本——这个动作就叫**方法重写（method overriding）**。

重写是" vertically override one_load 父类方法"的机制：沿继承链自上而下，子类的方法定义会"覆盖"父类的同名方法。注意它和"重载（overload）"是两个概念——重载指同名方法靠不同参数列表区分（如 Java 里的 `print(int)` / `print(String)`），Python 没有原生重载，二者容易混淆，后文会专门区分。

重写的核心价值在于**特化（specialization）**与**多态（polymorphism）**：

- **特化**：子类保留父类接口（方法名、参数约定），但把行为改成适合自己的版本。父类定"做什么"，子类定"怎么做"。
- **多态**：调用方只需要对着父类接口写代码，运行时根据实例的实际类型，自动调用对应子类的实现。同一个 `shape.area()` 调用，`Circle` 走圆面积公式，`Rectangle` 走矩形公式——这就是动态分发。

最小示例：

```python
class Animal:
    def speak(self):
        return "某种声音"

class Dog(Animal):
    def speak(self):          # 重写父类 speak
        return "汪汪"

class Cat(Animal):
    def speak(self):          # 重写父类 speak
        return "喵喵"

for a in (Dog(), Cat(), Animal()):
    print(a.speak())          # 同一个调用，不同行为
# 输出：
# 汪汪
# 喵喵
# 某种声音
```

`Dog` 和 `Cat` 都重写了 `speak`。循环里 `a` 的静态类型都是 `Animal`，但 `a.speak()` 在运行时按 `a` 的实际类型（`Dog` / `Cat` / `Animal`）分别找到了对应的实现——这就是重写带来的多态效果。

### 1.2 重写的基本语法与判定规则

Python 没有 `@Override` 注解，重写是**隐式**的：只要子类定义了与父类同名的方法，就算重写，不需要任何关键字声明。判定规则很简单——**名字相同即重写**，Python 不会因为参数签名不同而报错或区分。

```python
class Base:
    def greet(self, name):
        return f"Hello, {name}"

class Sub(Base):
    def greet(self, name, title=None):   # 重写，参数可以和父类不同
        if title:
            return f"Hello, {title} {name}"
        return f"Hi, {name}"

print(Sub().greet("Alice"))              # 调子类版本
# 输出：Hi, Alice
print(Sub().greet("Alice", title="Dr."))
# 输出：Hello, Dr. Alice
```

几个要点：

- **名字相同即重写**，不关心参数个数、默认值是否一致。Python 是动态语言，方法签名不做强约束。这意味着你可以"放宽"参数（给默认值），但调用方要小心兼容性（见第 3 章最佳实践里 LSP 的讨论）。
- **没有显式重写声明**。有些团队会用 `@override`（PEP 646 系列 / typing 模块的 `@override` 装饰器，3.12+ 正式可用）来让静态检查器帮你确认"父类确实有这个方法可重写"，但这只是静态检查辅助，运行时无任何影响。
- **属性重写在查找规则下和普通方法重写一致**。子类的同名属性同样会遮蔽父类属性，机制与本章讨论的方法重写同源（见第 4 章原理）。
- **私有方法（`__double_leading_underscore`）不会被重写**。因为名称重整（name mangling）会给私有方法加上 `_ClassName` 前缀，子类和父类的 `__private` 实际是两个不同名字的方法，互不遮蔽——这点关联第 10 篇笔记，后文会展开。

## 2. 核心内容

### 2.1 最基本的方法重写：特化父类行为

**作用**：父类提供一个通用实现，子类把它替换成更具体的实现。

**何时用**：当子类的行为逻辑和父类"同名但不同内容"时。父类的实现要么是通用的占位，要么是子类需要在它基础上做调整的场景。

**典型模式**：子类完全重写方法体，不再调用父类版本。

```python
class Shape:
    """所有形状的基类，定义接口但无具体实现。"""
    def area(self):
        raise NotImplementedError("子类必须实现 area()")

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):                       # 重写：圆面积
        return 3.14159 * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):                       # 重写：矩形面积
        return self.width * self.height

shapes = [Circle(3), Rectangle(4, 5), Circle(1)]
for s in shapes:
    print(f"{type(s).__name__} 面积 = {s.area():.2f}")
# 输出：
# Circle 面积 = 28.27
# Rectangle 面积 = 20.00
# Circle 面积 = 3.14
```

**运行结果说明**：`Shape.area()` 抛 `NotImplementedError` 是常见做法——父类把方法定义为"抽象接口"，强制子类重写。循环里三件事都调 `s.area()`，但运行时各自找到子类的实现，行为不同——多态直接体现。

这里父类 `Shape` 本身没有重写也可以，甚至可以给个返回 0 的默认实现。但用 `NotImplementedError` 的好处是：如果有人忘了重写，调用时立刻报错，问题暴露在使用点而不是埋到业务深处。更严格的做法是用 `abc.abstractmethod`（抽象基类），它会在实例化未重写的子类时直接报错，把检查时机提前到类创建时。

### 2.2 重写后调用父类版本：增强而非替换

很多场景下子类不是要"全盘替换"父类行为，而是要**在父类行为基础上增强**：先做父类该做的事，再加自己的补充。这时需要在子类方法里显式调用父类的同名方法，工具就是 `super()`。

`super()` 的详细用法参见第 15 篇笔记，这里只讲它在重写场景下的标准模式：

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("存款金额必须为正")
        self.balance += amount
        return self.balance

class LoggedAccount(BankAccount):
    def __init__(self, owner, balance=0, log=None):
        super().__init__(owner, balance)   # 重写 __init__，先调父类初始化
        self.log = log or []

    def deposit(self, amount):             # 重写 deposit
        result = super().deposit(amount)   # 先让父类做核心逻辑
        self.log.append(f"存入 {amount}，余额 {result}")  # 再补充日志
        return result

acc = LoggedAccount("张三")
acc.deposit(100)
acc.deposit(50)
print("余额：", acc.balance)
print("日志：")
for entry in acc.log:
    print(" ", entry)
# 输出：
# 余额： 150
# 日志：
#   存入 100，余额 100
#   存入 50，余额 150
```

**运行结果说明**：`LoggedAccount.deposit` 没有自己重复"加余额 + 校验"的逻辑，而是 `super().deposit(amount)` 让父类去做，自己只负责记日志。这样校验逻辑只在父类写一次，子类行为增强而不重复——这正是"增强而非替换"的精髓。如果哪天校验规则要改（比如禁止超过 1 万的单笔存款），只需改 `BankAccount.deposit` 一处，所有子类自动继承新规则。

**模式总结**：

```
子类方法:
    [前置增强]          # 可选：子类特有的预处理
    super().method(...)  # 调用父类核心逻辑
    [后置增强]          # 可选：子类特有的补充
    return ...
```

这个"前置 / super / 后置"三段式是重写配合 `super()` 最常用的结构。前置适合做参数转换、权限校验；后置适合做结果加工、日志、缓存等。

### 2.3 重写 `__init__`：子类构造必须衔接父类

`__init__` 也是方法，同样可以被重写。但重写 `__init__` 有一个"必须做"的事——**显式调用父类的 `__init__`**。因为 Python 不会自动调父类构造器，子类如果完全重写 `__init__` 又不 `super().__init__(...)`，父类定义的实例属性就不会被初始化。

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

class Employee(Person):
    def __init__(self, name, age, emp_id, department):
        super().__init__(name, age)        # 必须显式调父类 __init__
        self.emp_id = emp_id
        self.department = department

e = Employee("李四", 30, "E1024", "研发")
print(e.name, e.age, e.emp_id, e.department)
# 输出：李四 30 E1024 研发
```

**反例：忘了调父类 `__init__`**

```python
class BadEmployee(Person):
    def __init__(self, name, age, emp_id):
        # 忘了 super().__init__(name, age)
        self.emp_id = emp_id

e = BadEmployee("王五", 28, "E2048")
print(e.emp_id)
# 输出：E2048
print(e.name)
# 输出：AttributeError: 'BadEmployee' object has no attribute 'name'
```

父类的 `name`、`age` 初始化逻辑被跳过，实例上根本没有这两个属性，访问时报 `AttributeError`。这是初学 OOP 时最常见的坑之一。

**何时可以不调父类 `__init__`**：只有当子类确实要**完全替代**父类的初始化方式（父类那套属性子类都不需要，或子类用完全不同的方式管理状态）时，才可以省略。但即便如此，也要确认父类的 `__init__` 里没有"子类也需要的关键副作用"（比如注册到某个全局表、打开资源等）。多继承场景下 `super().__init__(...)` 的协作调用更复杂，参见第 15、16 篇。

### 2.4 重写 `__str__` 等魔术方法：定制对象的"表现"

Python 的魔术方法（dunder methods）是对象和语言协议交互的钩子：`__str__` 控制被 `print` / `str()` 时的字符串表现，`__repr__` 控制 `repr()` 和交互式回显，`__len__` 控制被 `len()` 调用时的返回，`__eq__` 控制相等比较……这些方法都定义在 `object` 基类里（或内置类型里），子类重写它们就能定制对象在语言层面的"表现"。

**`__str__` 重写示例**：让 `Employee` 被 `print` 时输出友好格式。

```python
class Employee:
    def __init__(self, name, title, salary):
        self.name = name
        self.title = title
        self.salary = salary

    def __str__(self):                      # 重写 object.__str__
        return f"<员工 {self.name}，岗位 {self.title}，月薪 {self.salary}>"

    def __repr__(self):
        return f"Employee(name={self.name!r}, title={self.title!r}, salary={self.salary})"

emp = Employee("赵六", "后端工程师", 25000)
print(emp)            # 触发 __str__
# 输出：<员工 赵六，岗位 后端工程师，月薪 25000>
print(repr(emp))      # 触发 __repr__
# 输出：Employee(name='赵六', title='后端工程师', salary=25000)
emp                    # 在交互式解释器里回显，也触发 __repr__
```

**运行结果说明**：`print(emp)` 期望给"人"看，所以走 `__str__`；`repr(emp)` 期望给"开发者"看、尽量能用来重建对象，所以走 `__repr__`。两者职责不同，一般 `__str__` 友好简短，`__repr__` 明确无歧义。如果只重写一个，建议优先 `__repr__`——因为当 `__str__` 未定义时，Python 会回退用 `__repr__` 作为 `str()` 的结果；反过来不行。

`__str__` 与 `__repr__` 的完整对比与更多细节参见第 18 篇笔记，这里只强调一点：**重写魔术方法本质和重写普通方法完全一样**，都是名字遮蔽在 MRO 下的体现，只不过魔术方法的调用方是 Python 语言本身（`print`、`len`、`==` 等会在内部去调对应 dunder）。

**其他常见可重写魔术方法速览**：

| 魔术方法 | 触发场景 | 重写典型目的 |
|---|---|---|
| `__str__` | `print(obj)` / `str(obj)` | 用户友好的字符串 |
| `__repr__` | `repr(obj)` / 交互式回显 | 开发者可读、可重建 |
| `__len__` | `len(obj)` | 自定义"长度"语义 |
| `__getitem__` | `obj[key]` | 支持下标访问 |
| `__iter__` / `__next__` | `for x in obj` | 支持迭代 |
| `__eq__` / `__hash__` | `obj == other` / dict 键 | 自定义相等与哈希 |
| `__call__` | `obj(...)` | 让实例像函数一样可调用 |
| `__enter__` / `__exit__` | `with obj as x` | 支持上下文管理器 |
| `__lt__` 等 | `obj < other` / `sorted` | 支持比较运算 |

### 2.5 重写与多态：运行时动态分发

重写本身只是"子类写了同名方法"，它真正发挥作用要靠**动态多态**：调用 `obj.method()` 时，Python 不是看 `obj` 变量的静态声明类型（Python 也没有静态类型），而是看 `obj` 当前指向实例的**实际类型**，沿着该类型的 MRO 查找 `method`——找到的第一个就是被调用的版本。因为子类的方法排在 MRO 前面，所以"子类重写的方法优先于父类"被调用。

**多态示例**：写一个对任意 `Shape` 都能工作的"总面积计算器"，完全不用关心具体子类。

```python
class Shape:
    def area(self):
        raise NotImplementedError

class Circle(Shape):
    def __init__(self, r):
        self.r = r
    def area(self):
        return 3.14159 * self.r ** 2

class Rectangle(Shape):
    def __init__(self, w, h):
        self.w = w
        self.h = h
    def area(self):
        return self.w * self.h

class Triangle(Shape):
    def __init__(self, base, height):
        self.base = base
        self.height = height
    def area(self):
        return 0.5 * self.base * self.height

def total_area(shapes):
    """对任意 Shape 集合求面积，不关心具体类型。"""
    return sum(s.area() for s in shapes)   # s.area() 动态分发

shapes = [Circle(2), Rectangle(3, 4), Triangle(6, 8)]
print(f"总面积 = {total_area(shapes):.2f}")
# 输出：总面积 = 54.57
```

**运行结果说明**：`total_area` 里写的 `s.area()` 是一句"对着父类接口"写的代码，但它实际调用了三种不同的子类实现——`Circle.area`、`Rectangle.area`、`Triangle.area`。如果将来新增 `Square` 或 `Ellipse`，只要它们也是 `Shape` 子类并重写了 `area`，`total_area` 一个字都不用改就能工作。这就是多态带来的**开闭原则**：对扩展开放（加新形状），对修改关闭（旧代码不动）。

动态分发的关键：分发的依据是 `type(obj)` 的 MRO，而不是变量名或赋值历史。同一个变量先后指向不同子类的实例，调用结果会随之变化：

```python
s = Circle(2)
print(type(s), s.area())
# 输出：<class '...Circle'> 12.56636
s = Rectangle(3, 4)
print(type(s), s.area())
# 输出：<class '...Rectangle'> 12
```

### 2.6 重写 vs 重载：两个常被混淆的概念

**重载（overload）** 指"同一个作用域内，同名方法靠不同参数列表区分"，典型如 Java：

```java
// Java 风格，Python 不支持
void print(int x)      { ... }
void print(String s)   { ... }
void print(int x, int y) { ... }
```

调用 `print(3)` 走第一个，`print("hi")` 走第二个，编译器根据参数类型和个数静态绑定。这是**静态分发的重载**，和重写的动态分发是两套机制。

**Python 没有原生重载**。Python 函数定义是"后定义覆盖前定义"——同名函数（或方法）后写的会直接替换先写的，不会并存：

```python
class Demo:
    def f(self, x):
        return x + 1

    def f(self, x, y):       # 这个 f 直接覆盖上一个 f，不是"重载"
        return x + y

d = Demo()
print(d.f(1))
# 输出：TypeError: f() missing 1 required positional argument: 'y'
# 类里只剩第二个 f，第一个被完全替换
```

Python 的函数参数本身就是动态的：默认值、`*args`、`**kwargs`、类型不约束，一个函数就能处理多种调用形态，根本不需要重载：

```python
class Demo:
    def f(self, x, y=None):
        if y is None:
            return x + 1
        return x + y

print(Demo().f(1))         # 一个参数
# 输出：2
print(Demo().f(1, 2))      # 两个参数
# 输出：3
```

需要"按类型分派"的复杂场景，Python 用 `functools.singledispatch`（单分派泛函数）或第三方的多重分派库（如 `multipledispatch`）来实现，但这些都是函数级装饰器机制，和面向对象里的"方法重写"是不同的东西。

**一句话区分**：

- **重写（override）**：子类 vs 父类，同名方法，运行时按实际类型动态选一个调用——Python 原生支持，本章主题。
- **重载（overload）**：同类同名不同参，编译时按参数静态选一个调用——Python 无原生支持，靠默认参数/`*args`/`singledispatch` 模拟。

### 2.7 协变返回与参数签名一致性：里氏替换原则

重写在语法上"名字相同即可"，但在工程设计上有一个更软的约束——**里氏替换原则（LSP, Liskov Substitution Principle）**：子类对象应该能无副作用地替换父类对象，而不破坏程序正确性。落到重写上，这意味着子类重写的方法在"契约"上要和父类兼容：

- **参数**：子类方法应该接受父类方法能接受的所有参数（**逆变参数**，或至少不收窄）。如果父类 `f(self, x: Animal)`，子类重写为 `f(self, x: Dog)`，那原来传 `Cat` 的调用在子类上就失败了——违反 LSP。
- **返回值**：子类方法返回的应该能当作父类方法返回值的子类型使用（**协变返回**）。父类 `f() -> Animal`，子类 `f() -> Dog` 是 OK 的（Dog 也是一种 Animal），但子类 `f() -> str` 就违反了。
- **异常**：子类方法抛出的异常应该是父类声明异常的子类（或更窄），不能抛出全新的、调用方没预期的异常类型。
- **前置/后置条件**：子类不能比父类要求更强的前置条件（更严的参数校验），也不能保证比父类更弱的后置条件。

**协变返回示例**：

```python
class Animal:
    pass

class Dog(Animal):
    pass

class AnimalFactory:
    def create(self):
        return Animal()

class DogFactory(AnimalFactory):
    def create(self):                # 重写，返回 Dog（Animal 的子类）
        return Dog()

def use_factory(factory: AnimalFactory):
    obj = factory.create()           # 拿到的是 Animal 或其子类
    print(type(obj).__name__)

use_factory(AnimalFactory())
# 输出：Animal
use_factory(DogFactory())            # 子类工厂替换父类工厂，调用方无感
# 输出：Dog
```

**反例：违反 LSP 的参数收窄**

```python
class Base:
    def process(self, data):
        print("处理", data)

class Sub(Base):
    def process(self, data):
        # 子类拒绝父类能接受的输入 → 违反 LSP
        if not isinstance(data, str):
            raise TypeError("只接受 str")
        print("处理 str", data)

def run(b: Base):
    b.process(123)        # 调用方按 Base 契约传 int，本应能工作

run(Base())
# 输出：处理 123
run(Sub())
# 输出：TypeError: 只接受 str
```

`run` 对着 `Base` 的契约写代码，本应能接受任何 `Base` 子类，但 `Sub` 把参数收窄到只接受 `str`，替换进去就崩了——这是典型的 LSP 违反。Python 不会在运行时强制 LSP（它是设计原则不是语法规则），但违反它会让代码在"看似能多态"的地方突然出错，排查极难。静态类型检查器 mypy / pyright 能对协变返回、参数兼容性做检查，工程上建议开启。

### 2.8 私有方法与重写的隔离：`__name` mangling

以两个下划线开头、至多一个下划线结尾的方法名（如 `__private`）会触发**名称重整（name mangling）**：Python 解释器在类定义时把它改写成 `_ClassName__private`。父类的 `__private` 变成 `_Base__private`，子类的 `__private` 变成 `_Sub__private`——二者名字不同，所以**子类的"同名"私有方法并不会重写父类的私有方法**，它们是两个独立的方法。

```python
class Base:
    def __private(self):
        print("Base.__private")

    def run(self):
        self.__private()           # 实际调用 self._Base__private

class Sub(Base):
    def __private(self):            # 实际定义的是 _Sub__private
        print("Sub.__private")

Sub().run()
# 输出：Base.__private
```

**运行结果说明**：`Sub` 以为自己重写了 `__private`，但 `Base.run` 里 `self.__private()` 在 `Base` 类体里写，被改写成 `self._Base__private()`，所以无论 `self` 是 `Base` 还是 `Sub`，调用的都是 `_Base__private`——子类定义的 `_Sub__private` 根本没被触达。这就是"私有方法不能被重写"：父类内部的私有方法调用是"绑定到父类自己"的，子类无法介入。

这点和第 10 篇笔记（名称重整）紧密关联。工程上的推论：**如果你想提供"子类可重写的钩子"，就不要用 `__double_underscore`，改用 `_single_underscore`（约定保护但可重写）或显式定义一个普通的"钩子方法"**。`__double_underscore` 私有的语义就是"这是类的内部实现细节，不希望被外部（含子类）触碰"。

### 2.9 避免误重写父类魔术方法

魔术方法多且语义复杂，重写它们时容易踩两类坑：

**坑一：误以为"定义了同名方法就是重写"，但父类根本没有公开这个方法。**

比如你想给子类加个 `__bool__`，但没在意父类已经通过 `__len__` 间接定义了布尔语义。Python 的规则是：`bool(obj)` 优先找 `__bool__`，找不到再退而求其次找 `__len__`（返回 0 即 False）。子类加一个 `__bool__` 就会"覆盖"掉父类靠 `__len__` 提供的布尔行为：

```python
class Container:
    def __init__(self, items):
        self.items = items
    def __len__(self):
        return len(self.items)

class FancyContainer(Container):
    def __bool__(self):              # 重写：定义新的布尔语义
        return len(self.items) > 2   # 只有 >2 个才算"有内容"

c = FancyContainer([1])
print(bool(c))
# 输出：False
print(len(c))                        # len 行为不变，仍是 1
# 输出：1
```

本例是有意为之，但如果是无意重写，会导致原来 `if container:` 的判断语义悄悄变化，很难排查。

**坑二：重写魔术方法时漏调父类版本，破坏内部协议。**

`__init__`、`__enter__`、`__del__` 这类方法重写时如果不调 `super()`，父类负责的初始化/清理就不会执行，可能导致资源泄漏或属性缺失（见 2.3 节）。更隐蔽的是 `__eq__` 和 `__hash__`：Python 规定"重写 `__eq__` 会把 `__hash__` 隐式设为 `None`"——如果你只重写 `__eq__` 不重写 `__hash__`，对象就变得不可哈希，不能当 dict 键、不能放进 set：

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):          # 重写 __eq__
        if not isinstance(other, Point):
            return NotImplemented
        return self.x == other.x and self.y == other.y
    # 没重写 __hash__ → __hash__ 被设为 None

p = Point(1, 2)
print(p.__hash__)
# 输出：None
s = {p}
# 输出：TypeError: unhashable type: 'Point'
```

修正方式：重写 `__eq__` 时一并重写 `__hash__`：

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented
        return self.x == other.x and self.y == other.y

    def __hash__(self):
        return hash((self.x, self.y))

p = Point(1, 2)
s = {p}
print(len(s))
# 输出：1
```

**经验法则**：重写魔术方法前先确认"父类（含 `object`）有没有提供默认行为、这个默认行为被打破后有没有副作用、需不需要配合重写相关方法（如 `__eq__`/`__hash__` 成对、`__lt__` 等四则比较成组、`__enter__`/`__exit__` 成对）"。能不重写就不重写，必须重写时把"协议成对的方法"一起处理。

### 2.10 用 `@override` 做静态检查（3.12+）

从 Python 3.12 起，`typing` 模块提供了 `@override` 装饰器（PEP 698），让静态检查器（如 mypy、pyright）能确认"这个方法确实重写了父类或某个祖先类的同名方法"。它对运行时**完全没有影响**，只是给工具看的标记。

```python
from typing import override

class Base:
    def greet(self, name):
        return f"Hello, {name}"

class Sub(Base):
    @override
    def greet(self, name):            # 静态检查器会确认 Base 有 greet 可重写
        return f"Hi, {name}"

    @override
    def great(self, name):            # 拼错名字，Base 没有 great
        return f"Hey, {name}"
    # mypy / pyright 报错：Method 'great' is marked as override but does not override any base method
```

`@override` 解决的是"重写是隐式的，容易写错方法名 / 父类后来改名了却没人发现"这类问题。大项目里推荐用——把"我以为我重写了"变成"工具帮我确认我重写了"。

## 3. 最佳实践

**3.1 重写前问自己：是"特化"还是"替代"**

重写不该是随手的动作。动笔前先判断意图：

- **特化**：子类保留父类接口语义，只换实现细节 → 合理重写。
- **替代**：子类想要完全不同的行为，只是恰好名字撞了 → 大概率是设计问题。换个方法名、或把"想要的行为"放到新方法里，比硬重写更健康。强行重写会让调用方对着父类接口写代码，却得到完全不同的结果，违反 LSP。

**判断标准**：如果你重写后，调用方"对着父类写、传子类实例"的代码行为会变得不可预期或报错，这个重写很可能是不该做的——要么改设计，要么别重写、另起方法名。

**3.2 重写 `__init__` 必调父类 `__init__`**

这条没有例外——除非你 100% 确定父类 `__init__` 的事子类都不需要、且父类没有任何关键副作用。即便如此，在多继承下省略 `super().__init__()` 会破坏协作式多继承的 MRO 链（见第 15、16 篇），代价远大于收益。养成"子类 `__init__` 第一行就 `super().__init__(...)`"的肌肉记忆。

```python
# 推荐写法
class Sub(Base):
    def __init__(self, x, y):
        super().__init__(x)        # 先衔接父类
        self.y = y                 # 再做子类自己的初始化

# 不推荐：跳过父类初始化
class BadSub(Base):
    def __init__(self, x, y):
        # 忘了 super().__init__(x)
        self.y = y
```

**3.3 重写魔术方法成对处理**

- `__eq__` 和 `__hash__` 必须成对：重写 `__eq__` 后如果不重写 `__hash__`，对象不可哈希。
- `__lt__` / `__le__` / `__gt__` / `__ge__` / `__eq__` 建议"要么全用 `functools.total_ordering` + 一两个基础方法，要么成组重写"，否则 `sorted` / `>` / `<` 行为不一致。
- `__enter__` / `__exit__` 成对：只写一个 `with` 用不上。
- `__iter__` / `__next__`：迭代器协议要两个都到位（或 `__iter__` 返回一个独立的迭代器对象）。

**3.4 维持 LSP：不收窄参数、不放宽前置条件**

- 子类方法至少要能接受父类方法能接受的所有参数形态。给参数加默认值（放宽）OK，去掉参数（收窄）通常不 OK。
- 子类的前置校验不能比父类更严，比如父类接受任意 `int`，子类重写后只接受正数——违反 LSP。
- 子类抛的异常应该是父类异常的子类，不能抛父类调用方没预期的全新异常。
- 子类返回值应该是父类返回值的子类型（协变），不能换成无关类型。

```python
# 推荐写法：协变返回、不收窄参数
class BaseRepo:
    def find(self, id: int) -> "BaseModel | None":
        ...

class SubRepo(BaseRepo):
    def find(self, id: int) -> "SubModel | None":   # 返回子类型 OK
        ...

# 不推荐：收窄参数类型
class BadRepo(BaseRepo):
    def find(self, id: str) -> "BaseModel | None":   # 参数类型变了，违反 LSP
        ...
```

**3.5 谨慎重写 `__eq__`，并总是同时重写 `__hash__`**

只要对象有可能进 set / 当 dict 键，就别只重写 `__eq__`。即便暂时不当键，未来某天别人把你的对象塞进 set，bug 就埋下了。习惯性"`__eq__` 和 `__hash__` 成对写"。

**3.6 不要为了"少写代码"而重写**

有时重写是为了复用父类逻辑，但更干净的方式是**组合（composition）**而非继承。如果子类重写父类方法后，绝大部分逻辑都在替换父类行为、几乎没复用，说明继承关系本身可疑。经典的"组合优于继承"原则在这里同样适用——把父类对象作为子类的属性持有，子类调它的方法，比重写更灵活、耦合更低。

**3.7 用 `@override` 让重写可被静态检查**

大型项目里，父类改名、方法签名变化时，子类的重写会悄悄失效（变成"子类定义了一个新方法，父类方法没被覆盖"）。加 `@override`（3.12+，或 `typing_extensions` 向后兼容）让工具帮你盯住这层关系：

```python
from typing import override

class Sub(Base):
    @override
    def greet(self, name):
        ...
```

老项目没条件上 3.12 的，至少在 CI 里跑 mypy / pyright，加 `--strict` 或开启 `reportIncompatibleMethodOverride` 类规则。

**3.8 私有方法不要当"可重写钩子"用**

`__double_underscore` 私有方法不会被重写（见 2.8），父类内部调用也绑定到父类自己。如果你想给子类留"可重写的内部钩子"，用 `_single_underscore`（约定受保护、可重写）或留一个明确的普通方法作钩子。反过来，如果你**不希望**子类碰某个内部方法，用 `__double_underscore` 能有效隔离——这是它被设计的初衷之一。

**3.9 重写不要改变方法的公开语义**

`deposit` 在父类里是"存钱使余额增加"，子类重写后不能变成"取钱使余额减少"——语义反了，调用方按父类契约写代码必崩。重写改的是"怎么做"，不是"做什么"。语义变了就换方法名，别顶着同名方法干相反的事。

## 4. 原理

本章是重写机制的核心原理。理解它需要先明确一个事实：**Python 的"方法"本质上不是像 Java 那样的独立实体，而是"类对象里的一个函数属性 + 实例绑定"**。所谓"重写"，归根结底是"属性查找"在继承链（MRO）上的一次"名字遮蔽"。下面把它拆开讲清楚。

### 4.1 属性查找与 MRO：重写在查找规则下的体现

Python 访问 `obj.method` 时，发生的事比表面复杂。简化后的核心流程是：

1. 看 `type(obj)`（实例的类），沿它的 `__mro__`（方法解析顺序）从前往后查找名为 `method` 的属性。
2. 在 MRO 的某个类里找到了 `method`（它是一个普通函数对象），把 `obj` 作为第一个参数绑给它，得到一个**绑定方法（bound method）**。
3. 调用这个绑定方法时，`obj` 就成了 `self`。

`__mro__` 是一个元组，定义了"查找顺序"。对单继承 `class Sub(Base)`，`Sub.__mro__` 是 `(Sub, Base, object)`——**子类在前，父类在后**。所以当 `Sub` 和 `Base` 都有 `method` 时，查找会先在 `Sub` 里命中，`Base` 的版本被"遮蔽"——这就是重写的全部机制。

```python
class Base:
    def who(self):
        return "Base"

class Sub(Base):
    def who(self):
        return "Sub"

print(Sub.__mro__)
# 输出：(<class '__main__.Sub'>, <class '__main__.Base'>, <class 'object'>)

s = Sub()
print(s.who())
# 输出：Sub
```

**为什么子类版本优先**：因为查找从 MRO 第一个（`Sub`）开始，`Sub.who` 命中就停止往下找，`Base.who` 根本没机会被看到。重写本质是"名字遮蔽在 MRO 顺序下"的结果——没有专门的"覆盖表"，就是查找顺序使然。

这也解释了为什么"父类后加的同名方法不会自动被子类重写"——因为子类的属性已经在 MRO 的更前面命中，查找永远到不了父类。反过来，如果子类删除了自己的 `who`，`Base.who` 立刻"显现"出来：

```python
del Sub.who        # 删掉子类的重写
print(s.who())
# 输出：Base
```

"删掉子类方法就回到父类实现"这个现象，正是"重写 = MRO 上的遮蔽"的最直接证据——遮蔽物被移走，被遮蔽的自然就露出来了。

### 4.2 动态多态的分发机制：`type(obj)` 决定查找起点

为什么 `obj.method()` 能"按实际类型"调用对应的重写版本？关键在于**查找的起点是 `type(obj)`，而不是变量声明或赋值历史**。

`obj.method()` 在 Python 字节码层面大致等价于 `type(obj).method(obj, ...)`——注意第一步就是 `type(obj)`，它拿到的是 `obj` 当前指向的实例的真实类。所以：

- `obj` 指向 `Circle` 实例 → `type(obj)` 是 `Circle` → 查 `Circle.__mro__` → 命中 `Circle.area`
- `obj` 指向 `Rectangle` 实例 → `type(obj)` 是 `Rectangle` → 查 `Rectangle.__mro__` → 命中 `Rectangle.area`

这就是动态分发（dynamic dispatch），且**每次调用都重新按 `type(obj)` 查找**，不是编译期绑定。所以同一个变量先后指向不同子类的实例，调用结果会动态变化（2.5 节示例）。这也是 Python 没有"静态类型"但仍有多态的原因——多态不依赖静态类型声明，只依赖"运行时实际类型 + MRO 查找"。

**绑定的细节**：类里的 `method` 是一个普通函数（`function` 对象），通过描述符协议在实例访问时被绑定。`obj.method` 拿到的是一个 `bound method`，它内部记住了"哪个函数 + 哪个实例"，调用时自动把实例作为 `self` 传入。这部分机制关联"描述符协议"，此处不展开，只需记住：`obj.method(x)` 等价于 `type(obj).method(obj, x)`，`type(obj)` 即分发依据。

下面这个例子直观展示了"查找随 `type(obj)` 变化"：

```python
class A:
    def f(self):
        return "A.f"

class B(A):
    def f(self):
        return "B.f"

obj = B()
print(obj.f())          # type(obj) 是 B → 走 B.f
# 输出：B.f

# 把 obj 的 __class__ 改回 A（仅为演示机制，生产代码不要这么做）
obj.__class__ = A
print(obj.f())          # type(obj) 现在是 A → 走 A.f
# 输出：A.f
```

修改 `__class__` 是极端手段，仅用于说明机制。它直接证明了：调用哪个版本，完全由 `type(obj)` 当前的 MRO 决定，与对象原本怎么创建无关。

### 4.3 `super().method()` 如何沿 MRO 找到父类版本

`super()` 看似简单，其实机制微妙。关键事实：**`super()` 不是"找父类"，而是"沿当前类的 MRO 往后找"**——"当前类"指的不是 `self` 的实际类型，而是 `super()` 所在的那个类（在方法里通常是定义该方法的类）。

`super()` 的无参形式在方法体里使用时，Python 通过两个隐式变量确定起点：

- `__class__`：当前方法所在的类（词法上的类，例如 `Sub`）。
- `self`：当前实例。

`super().method()` 的查找过程是：取 `type(self).__mro__`，在这个元组里找到 `__class__`（即 `Sub`）的位置，然后从它的**下一个**位置开始往后找 `method`，找到的第一个就是要调用的版本。

```python
class Base:
    def f(self):
        return "Base.f"

class Sub(Base):
    def f(self):
        result = super().f()       # 沿 MRO 找 Sub 之后的 f
        return f"Sub.f → {result}"

s = Sub()
print(Sub.__mro__)
# 输出：(<class '__main__.Sub'>, <class '__main__.Base'>, <class 'object'>)
print(s.f())
# 输出：Sub.f → Base.f
```

**`type(self).__mro__` 里 `Sub` 之后是 `Base`**，所以 `super().f()` 命中 `Base.f`。这就是"重写后调用父类版本"的底层实现。

**微妙之处：`super()` 找的是"实例类型 MRO"上的下一个，不是"定义类的直接父类"**。在多继承下这非常关键——`super()` 跳到的是 MRO 下一个类，未必是你在 `class Sub(Base)` 里写的那个直接父类。这也是为什么多继承下要靠 C3 线性化算 MRO，以及为什么"协作式多继承"要求每个类都用 `super()` 而不是显式调父类名。详见第 15、16、17 篇。

下面用多继承场景演示 `super()` 沿 MRO 跳转：

```python
class A:
    def f(self):
        print("A.f")

class B(A):
    def f(self):
        print("B.f → super")
        super().f()

class C(A):
    def f(self):
        print("C.f → super")
        super().f()

class D(B, C):
    def f(self):
        print("D.f → super")
        super().f()

print(D.__mro__)
# 输出：(<class '__main__.D'>, <class '__main__.B'>, <class '__main__.C'>, <class '__main__.A'>, <class 'object'>)
D().f()
# 输出：
# D.f → super
# B.f → super
# C.f → super
# A.f
```

`D` 的实例调 `f`，沿 MRO 依次走 `D.f → B.f → C.f → A.f`。每一步 `super().f()` 都跳到 MRO 里"当前类之后"的下一个，而不是各自的直接父类（`B` 的直接父类是 `A`，但 `super()` 跳到的是 `C`，而不是 `A`）。这就是 `super()` 与 MRO 协作的全部玄机，也是"重写配合 super"在多继承下能正确协作的基础。

### 4.4 重写与属性遮蔽的统一视角

理解了前面的机制，可以看出"方法重写"和"属性同名遮蔽"在 Python 里是同一件事。类体里定义的所有东西——方法、类变量、甚至嵌套类——都是类的属性，都遵循同样的 MRO 查找规则：

```python
class Base:
    value = 100
    def show(self):
        return f"Base value = {self.value}"

class Sub(Base):
    value = 200          # "重写"父类的类属性
    def show(self):      # "重写"父类的方法
        return f"Sub value = {self.value}"

print(Sub().show())
# 输出：Sub value = 200
print(Sub().value)
# 输出：200
```

`Sub.value` 遮蔽 `Base.value`，机制和 `Sub.show` 遮蔽 `Base.show` 完全相同——都是 MRO 查找顺序使然。Python 不区分"方法重写"和"属性遮蔽"，对解释器来说它们是同一回事。这也解释了为什么 PrivateStub 之类的"函数对象"和"数据属性"在重写机制上没有差异。

### 4.5 私有方法的隔离原理：name mangling 与查找

2.8 节讲了私有方法不能被重写，这里补上原理。类体编译时，Python 对形如 `__name`（至少两个前导下划线、至多一个尾部下划线）的标识符做名称重整：改写成 `_ClassName__name`，其中 `ClassName` 是当前类名。这个改写发生在"类体被解析"时，对所有 `__name` 的**定义**和**引用**都生效。

```python
class Base:
    def __private(self):
        return "Base.__private"

    def call_private(self):
        return self.__private()      # 编译期改写为 self._Base__private()

print([n for n in dir(Base) if "private" in n])
# 输出：['_Base__private']

class Sub(Base):
    def __private(self):
        return "Sub.__private"

print([n for n in dir(Sub) if "private" in n])
# 输出：['_Base__private', '_Sub__private']    # 两个不同的方法

Sub().call_private()
# 输出：'Base.__private'
```

`Base.call_private` 里的 `self.__private()` 被改写成 `self._Base__private()`——无论 `self` 是 `Base` 还是 `Sub`，找的都是 `_Base__private` 这个名字，子类的 `_Sub__private` 永远不会被这条调用触达。这就是"父类内部调用私有方法绑定到父类自己"的底层原因，也是"私有方法不可被重写"的实现细节。

如果想显式调用子类版本，唯一办法是用重整后的全名 `obj._Sub__private()`——但这等于在调用方写死类名，违背了私有约定，不推荐。设计上需要"可重写钩子"时改用 `_single_underscore`。

### 4.6 `@override` 装饰器的运行时行为

`@override`（`typing.override`，3.12+）在运行时是什么？它本质上是一个**返回原函数不变的装饰器**，对运行时行为零影响——它只是在该函数对象的 `__override__` 属性上打个标记，供静态检查器读取：

```python
from typing import override

class Base:
    def f(self): ...

class Sub(Base):
    @override
    def f(self): ...

print(Sub.f.__override__)     # 仅作标记，运行时可查但不影响调用
# 输出：True
```

`@override` 提供的保障完全发生在静态检查阶段：mypy / pyright 在类型检查时确认"被标记的方法在父类（或祖先类）里有同名可重写方法"，没有就报错。运行时即便没装检查器、即便重写关系其实是错的，程序照样跑——这也是为什么它叫"装饰器"但实际是"静态注解"的缘故。

### 4.7 重写与 `__dict__` 查找的性能点缀

每次 `obj.method()` 调用都要走一次 MRO 查找，看起来有开销，但 CPython 对此做了优化：常用路径上，类对象的 `__dict__` 会被缓存为一组"属性描述符表"，属性查找在 C 层面是 O(1) 的哈希表访问；MRO 查找在最坏情况下是 O(MRO 长度)，但实际查找会先命中子类（MRO 前段），且深度继承链极少，开销通常可忽略。再加上绑定方法对象会被复用、方法调用栈帧在 CPython 3.11+ 有专门优化，重写带来的分发开销在实际项目中几乎不是瓶颈——除非你在一个极热路径上每秒数百万次调用，否则不必为"重写会拖慢"担心。

## 5. 总结

**本文内容要点**：

- 方法重写是子类定义与父类同名方法、靠 MRO 查找顺序"遮蔽"父类版本的机制，Python 中名字相同即重写，无需关键字。
- 重写服务于"特化"和"多态"：子类换实现、调用方对父类接口写代码、运行时按实例实际类型动态分发。
- 重写后常通过 `super().method()` 调用父类版本，实现"增强而非替换"，标准模式是"前置增强 / super / 后置增强"三段式。
- 重写 `__init__` 必须显式调父类 `__init__`，否则父类属性不会初始化，是初学 OOP 最常见的坑。
- 重写 `__str__` / `__repr__` 等魔术方法可定制对象在语言层面的表现，注意 `__eq__` 与 `__hash__` 成对、`__enter__` 与 `__exit__` 成对等协议约束。
- 重写 vs 重载：重写是子类对父类、运行时动态分发；重载是同类同名不同参、编译时静态分发，Python 无原生重载，靠默认参数 / `*args` / `singledispatch` 模拟。
- 里氏替换原则（LSP）要求重写的方法参数不收窄、返回值协变、异常不扩展、不收紧前置条件，工程上靠 mypy / pyright 静态检查托底。
- 私有方法（`__double_underscore`）因名称重整不可被重写，需要"可重写钩子"应改用 `_single_underscore`。
- `@override`（3.12+）让重写关系可被静态检查器确认，大项目推荐启用，把"以为重写了"变成"工具确认重写了"。
- 原理层面：重写 = 名字遮蔽在 MRO 下的体现；`obj.method()` 的分发依据是 `type(obj).__mro__`；`super().method()` 沿 `type(self).__mro__` 从当前类之后查找；私有隔离源于 `__name` 被改写为 `_ClassName__name`。

**读完本文你应能掌握**：

- 能说出"重写"和"重载"的区别，并解释为什么 Python 没有原生重载、该用什么替代。
- 能正确重写父类方法，并按"前置 / super / 后置"三段式在父类行为基础上增强，而不是全盘替换。
- 能正确重写 `__init__`，不遗漏 `super().__init__(...)`，并解释遗漏会导致什么后果。
- 能重写 `__str__` / `__repr__` 定制对象表现，并知道 `__eq__` 与 `__hash__` 必须成对重写、`__bool__` 与 `__len__` 的优先级关系。
- 能用 Shape / Circle / Rectangle 这类例子说明动态多态：调用方对父类接口写代码，运行时按 `type(obj)` 的 MRO 分发到子类实现。
- 能说出 LSP 对重写的约束（参数不收窄、返回协变、异常不扩展），在代码里识别违反 LSP 的重写。
- 能解释私有方法为什么不能被重写（name mangling 改名），并知道用什么方式给子类留"可重写钩子"。
- 能从原理上解释 `obj.method()` 的查找过程、`super().method()` 如何沿 MRO 找到父类版本，并用 `__mro__` 验证查找顺序。
- 能使用 `@override`（3.12+）让重写关系被静态检查器托底，并在 CI 里启用相关规则。
