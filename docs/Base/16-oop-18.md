## 1. 介绍

### 1.1 什么是对象的字符串表示

在 Python 中，任何一个对象都可以被"变成字符串"——不管是用 `print(obj)` 打印到屏幕，还是在交互式解释器里直接敲一个变量名回车看到它的模样，又或者用 `f"{obj}"` 把它塞进一段格式化文本里。这些看似不同的场景，背后都指向同一个问题：**对象该如何把自己表达成一段文字？**

Python 把这个"对象 → 字符串"的转换交给两个特殊的实例方法来管理：

- `__str__`：面向"终端用户"的可读表示。当你在生产环境里 `print()` 一个对象、或者用 `str(obj)` 显式转换时，Python 会调用它。它的目标是让人一眼看懂这个对象"是什么"，强调可读性，不追求精确还原。
- `__repr__`：面向"开发者/调试者"的准确表示。当你在交互式解释器里直接回显一个对象、用 `repr(obj)` 显式转换、或者在日志和调试器中查看对象时，Python 会调用它。它的目标是"准确、无歧义"，理想情况下这段字符串应该能被 `eval()` 还原成一个等价的对象。

理解这两个方法的区别，是写出"调试友好"代码的第一步。一个没实现任何字符串表示的自定义类，打印出来永远是类似 `<__main__.Point object at 0x10a3f4d60>` 这种对调试毫无帮助的地址串；而一旦你花几分钟实现好 `__repr__`，调试、日志、错误堆栈里立刻就能看到 `Point(x=1, y=2)` 这样有信息量的内容。

### 1.2 两个方法的最基本形式

两个方法都遵循同一个签名约定：**无参数（只接收 `self`），返回一个字符串**。Python 会在内部自动调用它们，绝大多数情况下你不需要手动调用。

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    # 面向用户：好看、易读
    def __str__(self):
        return f"({self.x}, {self.y})"

    # 面向开发者：准确、可还原
    def __repr__(self):
        return f"Point(x={self.x!r}, y={self.y!r})"
```

定义好之后，它们会被不同入口自动触发：

```python
p = Point(3, 4)

print(p)        # 触发 __str__：面向用户
# 输出：(3, 4)

print(str(p))   # 显式调用 str()，同样触发 __str__
# 输出：(3, 4)

print(repr(p))  # 显式调用 repr()，触发 __repr__
# 输出：Point(x=3, y=4)

p                # 在交互式解释器里直接回显，触发 __repr__
# 输出：Point(x=3, y=4)
```

注意上面 `__repr__` 里用了 `{self.x!r}` 这种写法——这里的 `!r` 是 f-string 的转换标志，表示对 `self.x` 强制走 `repr()` 而不是默认的 `str()`。这在实现 `__repr__` 时非常常见，后面会详细讲。

### 1.3 一个直觉式的记忆口诀

如果你觉得两个方法容易混淆，记住这一句就够了：

> **`__str__` 是给用户看的，`__repr__` 是给程序员看的。**

更具体一点：

| 维度 | `__str__` | `__repr__` |
|------|-----------|------------|
| 受众 | 终端用户 | 开发者/调试者 |
| 触发方式 | `print(obj)`、`str(obj)`、`f"{obj}"` | `repr(obj)`、交互式直接回显、容器元素打印 |
| 目标 | 可读 | 准确、无歧义、尽量可还原 |
| 理想形态 | 简洁自然的一句话 | `ClassName(attr1=..., attr2=...)` 形如合法 Python 表达式 |
| 回退关系 | 未定义时自动回退到 `__repr__` | 不回退（最终回退到 `object.__repr__` 的地址串） |

后面几章会把这些要点逐一展开——先看清楚两个方法各自的触发场景和典型用法（第 2 章），再给出工程上的取舍建议（第 3 章），接着深入到 Python 内部到底是按什么顺序查找这两个方法的（第 4 章原理），最后总结全文（第 5 章）。

## 2. 核心内容

### 2.1 __str__：面向用户的可读表示

`__str__` 的责任是把对象转成"对用户友好"的字符串。所谓"对用户友好"，指的是这段字符串将被展示给最终使用者：可能是命令行程序的一行输出，可能是 Web 页面上的一行文本，可能是日志里要给人看的一段描述。它不需要保证能被程序还原回对象，只需要让人看得明白。

**触发场景**：

- `print(obj)`：`print` 内部对每个参数调用 `str()`，最终输出的是 `__str__` 的结果。
- `str(obj)`：显式构造字符串时调用。
- `f"{obj}"`、`"{}".format(obj)`、`"%s" % obj`：f-string 和 `format` 默认对每个值用 `str()`，`%s` 同理。

**设计原则**：

- 返回值必须是 `str` 类型，不能返回 `None` 或其他类型，否则会抛 `TypeError`。
- 内容应简洁、自然，像一个"标题"或"摘要"，不一定要包含全部信息。
- 如果对象本身就是一个"字符串载体"（比如某个模型的显示名），`__str__` 可以直接返回那个名字。

来看一个有场景感的例子：一个表示"温度"的类，`__str__` 给出自然的中文描述，面向最终用户。

```python
class Temperature:
    def __init__(self, value, unit="C"):
        self.value = value
        self.unit = unit

    def __str__(self):
        unit_name = {"C": "摄氏度", "F": "华氏度"}[self.unit]
        return f"{self.value}{unit_name}"

t = Temperature(26)
print(t)            # print 内部调 str(t) → __str__
# 输出：26摄氏度

print(f"当前室温：{t}")   # f-string 默认走 str()
# 输出：当前室温：26摄氏度

print(str(t))       # 显式 str()，也是 __str__
# 输出：26摄氏度
```

这里 `__str__` 选择了"26摄氏度"这种贴近自然语言的表达，而不是 `Temperature(26, 'C')`。因为这段文字是给普通用户看的——如果是给开发者调试看，就应该用 `__repr__` 输出后者。

**对比：只定义 `__str__` 时，调试输出会怎样？**

很多人会只实现 `__str__` 而忘了 `__repr__`，结果在调试时是这样：

```python
class OnlyStr:
    def __init__(self, name):
        self.name = name
    def __str__(self):
        return f"[{self.name}]"

obj = OnlyStr("settings")

print(obj)
# 输出：[settings]

# 但在交互式解释器里直接回显，或 repr(obj)：
print(repr(obj))
# 输出：<__main__.OnlyStr object at 0x...>
```

`print(obj)` 看起来很正常，可一旦你把它放进列表、丢进日志、在 REPL 里敲 `obj` 回车，就立刻退化为毫无信息量的地址串。这就是为什么"至少实现 `__repr__`"是一条比"实现 `__str__`"更重要的原则——稍后第 3 章会展开。

### 2.2 __repr__：面向开发者的准确表示

`__repr__` 的责任和 `__str__` 截然不同：它要给出"对程序员有意义、准确、无歧义"的表示。Python 官方文档里对 `__repr__` 的期望是——如果可能，这段字符串应该看起来像一个合法的 Python 表达式，能被 `eval()` 还原成一个"值相等"的对象。

**触发场景**：

- `repr(obj)`：显式调用。
- 交互式解释器（REPL）里直接输入变量名回车：解释器显示对象时用的是 `repr()`，不是 `str()`。
- 调试器、`pprint`、错误堆栈中展示对象时。
- **容器元素打印**：当你 `print([obj])` 或 `print({"key": obj})` 时，容器内部的元素用 `repr()` 而不是 `str()` 表示——这一点非常关键，后面 2.4 节专门讲。

**设计原则**：

- 返回值必须是 `str`。
- 应当包含类名和足以区分对象状态的关键属性，格式尽量形如 `ClassName(arg1=value1, arg2=value2)`。
- 如果属性本身是字符串，在 `__repr__` 里应当带引号（用 `!r` 或手动加引号），否则还原时语义会错。例如 `Person(name=alice)` 就比 `Person(name='alice')` 含糊——前者看着像 `alice` 是个变量。
- 理想情况下 `eval(repr(obj)) == obj`，但如果做不到（例如对象持有文件句柄、网络连接等不可还原资源），退而求其次，给出一个 `<...>` 形式的、信息量足够的描述即可。内置的 `datetime` 等都能 eval 还原。

再看温度的例子，这次把 `__repr__` 加上：

```python
class Temperature:
    def __init__(self, value, unit="C"):
        self.value = value
        self.unit = unit

    def __str__(self):
        unit_name = {"C": "摄氏度", "F": "华氏度"}[self.unit]
        return f"{self.value}{unit_name}"

    def __repr__(self):
        return f"Temperature(value={self.value!r}, unit={self.unit!r})"

t = Temperature(26)

# 用户视角
print(t)
# 输出：26摄氏度

# 开发者视角
print(repr(t))
# 输出：Temperature(value=26, unit='C')

# REPL 回显也是 __repr__
t
# 输出：Temperature(value=26, unit='C')

# 理想情况：能 eval 还原
import ast
eval(repr(t))          # 会构造出一个新的 Temperature(26, 'C')
# 输出：Temperature(value=26, unit='C')
```

注意 `__repr__` 里 `unit='C'` 的引号——这是因为用了 `!r`，对字符串属性强制走 `repr()`，于是 `unit` 这个字符串自带了引号。如果写成 `{self.unit}` 得到 `Temperature(value=26, unit=C)`，`C` 看着像变量名，eval 不了。这是实现 `__repr__` 时最常踩的细节。

**对象不可还原时的处理**

并非所有对象都能 `eval(repr(...))` 还原。比如一个持有数据库连接的对象：

```python
class DbSession:
    def __init__(self, dsn, conn):
        self.dsn = dsn
        self._conn = conn   # 内部连接对象，无法用字面量还原

    def __repr__(self):
        # 无法还原，就给一个信息量足够的 <...> 描述
        return f"<DbSession dsn={self.dsn!r} connected={self._conn is not None}>"
```

这种 `<...>` 形式是 Python 官方认可的"无法 eval 时的得体降级"——内置 `open()` 返回的文件对象、`socket` 对象等都是这个风格：

```python
f = open("tmp.txt", "w")
repr(f)
# 输出："<_io.TextIOWrapper name='tmp.txt' mode='w' encoding='UTF-8'>"
```

### 2.3 回退关系：为什么"只实现 __repr__ 就够"

`__str__` 和 `__repr__` 之间有一条不对称的回退关系，这也是整篇笔记最重要的一条规则：

> 如果一个类只定义了 `__repr__` 而没有定义 `__str__`，那么 `str(obj)`、`print(obj)`、`f"{obj}"` 等所有"面向用户"的调用都会**自动回退到 `__repr__`**。
>
> 反过来不成立：只定义 `__str__` 时，`repr(obj)` 和 REPL 回显**不会**回退到 `__str__`，而是退到 `object.__repr__` 给出地址串。

这条规则直接决定了一个工程上的最佳实践：**当你只想写一个方法时，写 `__repr__`**。因为写了 `__repr__`，等于同时覆盖了"开发者视角"和"用户视角"（后者通过回退）；而只写 `__str__`，开发者视角仍然是地址串。

来看一个最小对比：

```python
class OnlyRepr:
    def __init__(self, n):
        self.n = n
    def __repr__(self):
        return f"OnlyRepr(n={self.n})"

class OnlyStr:
    def __init__(self, n):
        self.n = n
    def __str__(self):
        return f"<{self.n}>"

a = OnlyRepr(5)
b = OnlyStr(5)

# ---- 面向用户：print / str ----
print(a)            # 没有 __str__，回退到 __repr__
# 输出：OnlyRepr(n=5)

print(b)            # 有 __str__
# 输出：<5>

# ---- 面向开发者：repr / REPL ----
print(repr(a))
# 输出：OnlyRepr(n=5)

print(repr(b))      # 没有 __repr__，退到 object.__repr__ 的地址串
# 输出：<__main__.OnlyStr object at 0x...>
```

`OnlyRepr` 一个方法搞定两个视角；`OnlyStr` 只管了用户视角，开发者一调试就抓瞎。

回退的具体机制在第 4 章原理部分会展开：简而言之，`object.__str__` 的默认实现就是 `return repr(self)`，所以没覆盖 `__str__` 时，自然就走到 `__repr__`；而 `object.__repr__` 不会反过来调用 `__str__`，它直接给出 `<ClassName object at 0x...>`。

### 2.4 容器打印：为什么列表元素走 __repr__

这是一个非常经典、也最容易让新手困惑的现象：

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y
    def __str__(self):
        return f"({self.x}, {self.y})"
    def __repr__(self):
        return f"Point({self.x}, {self.y})"

p = Point(1, 2)

print(p)            # __str__
# 输出：(1, 2)

print([p, p])       # 猜猜看：元素会用 __str__ 还是 __repr__？
# 输出：[Point(1, 2), Point(1, 2)]
```

明明 `print(p)` 输出 `(1, 2)`，可一旦把 `p` 放进列表再打印，每个元素就变成了 `Point(1, 2)`——走的是 `__repr__` 而不是 `__str__`。字典、元组、集合等所有内置容器都一样：

```python
print({"p": p})
# 输出：{'p': Point(1, 2)}

print((p,))
# 输出：(Point(1, 2),)

print({p})
# 输出：{Point(1, 2)}
```

**为什么会这样？**

原因在于容器的 `__repr__` 实现。以 `list` 为例，`list.__repr__` 要把自己表达成 `[elem0, elem1, ...]` 的形式，它对每一个元素调用的是 `repr(elem)` 而不是 `str(elem)`。这是 Python 容器设计的统一约定。

这个设计是合理的：设想一个 `Point` 的 `__str__` 是 `(1, 2)`，如果容器元素走 `__str__`，那么 `print([p1, p2])` 就会输出 `[(1, 2), (3, 4)]`——这和"一个包含两个元组的列表"完全无法区分，调试时根本看不出元素类型是 `Point` 还是 `tuple`。而走 `__repr__` 输出 `[Point(1, 2), Point(3, 4)]`，元素类型一目了然。

这也是"一定要实现 `__repr__`"的另一个强理由：只要你的对象有可能被放进容器、日志、堆栈里打印，`__repr__` 就一定会被用到。`__str__` 救不了这种场景——容器压根不看 `__str__`。

**强制容器元素走 __str__ 的折中办法**

如果你确实想让容器按"可读"形式输出，得自己动手：

```python
points = [Point(1, 2), Point(3, 4)]

# 方法一：手动 join，每个元素显式走 str()
print(", ".join(str(p) for p in points))
# 输出：(1, 2), (3, 4)

# 方法二：自定义容器类的 __str__，内部对元素用 str()
class PointList(list):
    def __str__(self):
        return "[" + ", ".join(str(p) for p in self) + "]"

pl = PointList([Point(1, 2), Point(3, 4)])
print(pl)
# 输出：[(1, 2), (3, 4)]
```

但在大多数场景下，接受"容器元素走 `__repr__`"这个默认行为、把 `__repr__` 写好，是更省事也更一致的做法。

### 2.5 f-string 中的 !s 与 !r 转换标志

f-string（以及 `format()` / `%` 格式化）默认对插入的值调用 `str()`。但你可以用转换标志（conversion）强制改走哪个方法：

- `{value!s}`：强制走 `str(value)`，即 `__str__`（这也是默认行为，写出来只是为了显式）。
- `{value!r}`：强制走 `repr(value)`，即 `__repr__`。
- `{value!a}`：强制走 `ascii(value)`，返回纯 ASCII 表示（非 ASCII 字符会被转义），较少用。

`!r` 在两个场景下特别高频：

**场景一：实现 `__repr__` 时对字符串属性加引号。** 这正是前面温度类里 `unit={self.unit!r}` 的用法——保证字符串属性带引号，让输出可 eval。

**场景二：调试日志里想看到"带引号"的值。** 比如对比 `name="alice"` 时：

```python
name = "alice"
age = 30

print(f"name={name}, age={age}")       # 默认 str()
# 输出：name=alice, age=30

print(f"name={name!r}, age={age!r}")   # 强制 repr()
# 输出：name='alice', age=30
```

第一行的 `name=alice` 看不出 `name` 的值到底是字符串 `"alice"` 还是变量名，第二行 `name='alice'` 一眼能看出类型和值。所以 `!r` 在调试、日志、错误信息里几乎是标配。

看一个带场景的例子：一个校验函数在失败时打印"收到的是什么"。

```python
def require_positive(x):
    if not isinstance(x, int) or x <= 0:
        raise ValueError(f"需要一个正整数，但收到 {x!r}")
    return x

require_positive("5")
# 抛出：ValueError: 需要一个正整数，但收到 '5'
```

如果不用 `!r`，错误信息会变成 `需要一个正整数，但收到 5`——用户根本分不清传进去的是字符串 `"5"` 还是整数 `5`，排查方向都会错。`!r` 让类型信息立刻可见。

**!s / !r / 默认 的对比表**

| 写法 | 实际调用 | 典型用途 |
|------|---------|---------|
| `f"{obj}"` | `str(obj)` → `__str__`（回退 `__repr__`） | 面向用户输出 |
| `f"{obj!s}"` | `str(obj)` → `__str__`（同上，显式写法） | 同上，强调意图 |
| `f"{obj!r}"` | `repr(obj)` → `__repr__` | 调试、日志、实现 `__repr__` 时给字符串属性加引号 |
| `f"{obj!a}"` | `ascii(obj)` | 需要纯 ASCII 输出（如老式日志系统） |

### 2.6 @dataclass 自动生成 __repr__

从 Python 3.7 起，`dataclasses.dataclass` 装饰器会自动为你生成 `__repr__`，生成的格式恰好就是推荐的 `ClassName(field1=value1, field2=value2)` 形式。这极大减少了样板代码。

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p = Point(3, 4)

print(p)            # dataclass 默认只生成 __repr__，__str__ 回退到它
# 输出：Point(x=3, y=4)

print(repr(p))
# 输出：Point(x=3, y=4)

p                   # REPL 回显
# 输出：Point(x=3, y=4)
```

注意：dataclass 默认**只生成 `__repr__`，不生成 `__str__`**——但因为前面讲的回退机制，`print(p)` 会自然回退到自动生成的 `__repr__`，所以两者输出一致。如果你想要不同的用户视角，可以显式定义 `__str__`，它不会和自动生成的 `__repr__` 冲突：

```python
@dataclass
class Point:
    x: int
    y: int

    def __str__(self):
        return f"点({self.x}, {self.y})"

p = Point(3, 4)
print(p)
# 输出：点(3, 4)

print(repr(p))
# 输出：Point(x=3, y=4)
```

**控制 repr 的生成**

`@dataclass` 的参数 `repr=False` 可以关掉自动生成，让你完全手写（或干脆不写）：

```python
@dataclass(repr=False)
class Secret:
    token: str

s = Secret("abc123")
print(repr(s))
# 输出：<__main__.Secret object at 0x...>   退回 object.__repr__
```

**字段排除：`field(repr=False)`**

某些字段（密码、内部 ID、大块数据）不希望出现在 repr 里，可以用 `field(repr=False)` 把它排除：

```python
from dataclasses import dataclass, field

@dataclass
class User:
    name: str
    password: str = field(repr=False)

u = User("alice", "s3cret")
print(repr(u))
# 输出：User(name='alice')
```

`password` 不会出现在任何 `repr()` 调用、REPL 回显或容器打印中——这对安全敏感字段尤为重要。

### 2.7 __repr__ 应包含类名与关键属性

无论是手写还是用 dataclass，一条不变的设计准则是：**`__repr__` 必须包含类名，且包含足以辨识对象状态的关键属性**。

类名是为了在一堆日志/调试输出里立刻认出"这是哪一类对象"；关键属性是为了在同类的多个实例之间区分"这是哪一个实例"。缺了类名，你看不出类型；缺了属性，所有实例看起来都一样。

**正面例子**

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def __repr__(self):
        return f"Rectangle(width={self.width!r}, height={self.height!r})"

Rectangle(3, 4)
# 输出：Rectangle(width=3, height=4)
```

一眼看出：是 `Rectangle`，宽 3 高 4。

**反面例子一：只有类名没有属性**

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height
    def __repr__(self):
        return "Rectangle()"      # 看不出尺寸

Rectangle(3, 4)
# 输出：Rectangle()
Rectangle(10, 20)
# 输出：Rectangle()    # 两个不同实例 repr 完全一样，无法区分
```

**反面例子二：只有属性没有类名**

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height
    def __repr__(self):
        return f"({self.width}, {self.height})"   # 看不出类型

Rectangle(3, 4)
# 输出：(3, 4)    # 和一个 tuple 怎么区分？
```

**反面例子三：信息过多**

```python
class HttpRequest:
    def __init__(self, method, url, headers, body):
        ...
    def __repr__(self):
        return f"HttpRequest(method={self.method!r}, url={self.url!r}, headers={self.headers!r}, body={self.body[:1000]!r})"
```

把整个请求体一千字节都塞进 repr 会让日志变得无法阅读。对"大字段"应截断或用 `field(repr=False)` 排除，只保留定位用的关键信息（`method`、`url` 等）。

### 2.8 __format__ 简提

与 `__str__`、`__repr__` 同族的还有 `__format__`。当你用格式化字符串指定了格式说明符（`{obj:spec}` 中的 `spec`）时，Python 调用 `__format__(self, format_spec)`。

- `f"{obj}"`（无说明符）→ 走 `__str__`。
- `f"{obj:spec}"`（有说明符）→ 走 `__format__(self, "spec")`。
- `format(obj, spec)` → 同上。

```python
from datetime import datetime, date

d = date(2026, 7, 23)

print(f"{d}")           # 无说明符 → __str__
# 输出：2026-07-23

print(f"{d:%Y年%m月%d日}")  # 有说明符 → __format__
# 输出：2026年07月23日
```

自定义类可以接管 `__format__` 来支持自己的格式语法，例如让 `Temperature` 支持 `{t:.1f}` 表示保留一位小数：

```python
class Temperature:
    def __init__(self, value, unit="C"):
        self.value = value
        self.unit = unit

    def __str__(self):
        return f"{self.value}{self.unit}"

    def __repr__(self):
        return f"Temperature({self.value!r}, {self.unit!r})"

    def __format__(self, spec):
        # spec 为空就等价于 __str__
        if spec == "":
            return str(self)
        # 否则把 spec 当作对 value 的数值格式
        return f"{self.value:{spec}}{self.unit}"

t = Temperature(26.37, "C")
print(f"{t}")
# 输出：26.37C

print(f"{t:.1f}")
# 输出：26.4C
```

`__format__` 不是本篇的主角，但需要知道它和 `__str__`/`__repr__` 的分界：说明符为空时 `f"{obj}"` 调用的是 `__format__` 还是 `__str__`，实际上 CPython 里为空说明符走的路径会回退到 `__str__`（通过 `object.__format__` 转调 `str`），所以多数情况下你只需关心 `__str__` 和 `__repr__`，需要自定义格式语法时再去覆盖 `__format__`。

## 3. 最佳实践

### 3.1 永远至少实现 __repr__

这是反复强调过的一条总原则，值得单独列出来。理由汇总：

1. **调试场景全覆盖**：REPL 回显、`repr(obj)`、错误堆栈、`pprint`、`logging` 的 `%r`、`pdb` 调试器——全都依赖 `__repr__`。
2. **容器打印的刚需**：`print([obj])`、`print({"k": obj})` 中元素走 `__repr__`，`__str__` 救不了。
3. **回退机制兜底用户视角**：没有 `__str__` 时，`print(obj)`/`str(obj)` 自动回退到 `__repr__`，用户视角也不至于出错。
4. **唯一不写 `__repr__` 的代价**：所有调试输出退化为 `<ClassName object at 0x...>`，看不出任何状态。

所以当时间只够写一个方法时，写 `__repr__`，而不是 `__str__`。

**推荐写法**

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point(x={self.x!r}, y={self.y!r})"
```

仅此一个方法，`print`、`str`、`repr`、REPL、容器全都能用：

```python
p = Point(1, 2)
print(p)          # 输出：Point(x=1, y=2)
print([p])        # 输出：[Point(x=1, y=2)]
p                 # 输出：Point(x=1, y=2)
```

**不推荐写法（只写 __str__ 不写 __repr__）**

```python
class Point:      # 不推荐
    def __init__(self, x, y):
        self.x = x
        self.y = y
    def __str__(self):
        return f"({self.x}, {self.y})"

p = Point(1, 2)
print(p)          # 输出：(1, 2)        ——看着还行
print([p])        # 输出：[<__main__.Point object at 0x...>]  ——暴露问题
```

### 3.2 __repr__ 的格式约定

写 `__repr__` 时遵循这条约定能让调试输出统一、可读、可还原：

- 以类名开头，后跟括号包裹的 `字段=值` 列表，形如 `ClassName(field1=value1, field2=value2)`。
- 字符串字段用 `!r` 加引号；数字、布尔等基本类型直接写值即可（用 `!r` 也无害）。
- 选择"足以区分实例"的关键字段，不必把全部属性都塞进去；大字段用 `repr=False` 或截断。
- 若对象不可还原（持有连接、句柄等），用 `<ClassName key=... state=...>` 形式降级。

**推荐 vs 不推荐**

```python
# 推荐：类名 + 关键字段 + 字符串带引号
def __repr__(self):
    return f"User(id={self.id!r}, name={self.name!r})"
# 输出：User(id=42, name='alice')

# 不推荐：缺类名
def __repr__(self):
    return f"id={self.id}, name={self.name}"
# 输出：id=42, name=alice   ——看不出类型，name 也像变量

# 不推荐：缺属性
def __repr__(self):
    return "User()"
# 输出：User()   ——所有实例都长一样

# 不推荐：无脑全字段（含密码）
def __repr__(self):
    return f"User(id={self.id}, name={self.name}, password={self.password})"
# 输出：User(id=42, name=alice, password=s3cret)   ——密码泄露到日志
```

### 3.3 实现 __str__ 的时机

"至少实现 `__repr__`" 不等于"永远只实现 `__repr__`"。当"用户视角"和"开发者视角"确实需要不同表达时，就额外定义 `__str__`：

- `__str__` 更短、更自然、更本地化（比如中文描述），适合展示给最终用户。
- `__repr__` 更技术、更精确、可还原，适合调试和日志。

典型例子：`datetime.date`

```python
import datetime
d = datetime.date(2026, 7, 23)

str(d)     # '2026-07-23'        ——用户友好
repr(d)    # 'datetime.date(2026, 7, 23)'   ——可 eval 还原

eval(repr(d)) == d     # True
```

如果你的类只有一种"合理表示"（比如一个纯数据值对象），那 `__str__` 就不必要，让回退机制处理即可。多写一个和 `__repr__` 一模一样的 `__str__` 是无意义的重复。

### 3.4 让 __repr__ 可 eval 还原

当你的类能用"构造参数"完整描述状态时，尽量让 `__repr__` 输出一个合法的构造表达式，使 `eval(repr(obj))` 能还原等价对象。好处：

- 调试时可以直接把 repr 输出复制成代码重新构造对象。
- 文档、测试、bug report 里都能"所见即所得"地复现状态。

```python
class Color:
    def __init__(self, r, g, b):
        self.r, self.g, self.b = r, g, b

    def __repr__(self):
        return f"Color({self.r}, {self.g}, {self.b})"

    def __eq__(self, other):
        return (self.r, self.g, self.b) == (other.r, other.g, other.b)

c = Color(255, 128, 0)
eval(repr(c)) == c     # True
```

做不到时（对象持有线程、文件、连接等不可序列化资源），老老实实降级到 `<...>` 形式，不要硬拼一个 eval 会报错的字符串。

### 3.5 安全：敏感字段不要进 repr

repr 会被写进日志、错误堆栈、调试输出，甚至被采集到监控系统。密码、token、身份证号、手机号等敏感字段绝不能出现在 repr 里。

```python
from dataclasses import dataclass, field

@dataclass
class ApiKey:
    owner: str
    secret: str = field(repr=False)   # 不进 repr
    # 手写时同理：
    # def __repr__(self):
    #     return f"ApiKey(owner={self.owner!r}, secret=***)"

k = ApiKey("alice", "sk-xxxxxxxxxxxx")
print(repr(k))
# 输出：ApiKey(owner='alice')

print(k)
# 输出：ApiKey(owner='alice')
```

手写实现时，对敏感字段要么用 `"***"` 占位，要么直接不写进去。

### 3.6 性能：避免 __repr__ 做重活

`__repr__` 在调试、日志、异常处理中被频繁调用，如果实现里做重活（查数据库、递归遍历大对象、大字符串拼接），会导致"随便 print 一下"都卡顿，甚至让调试器变慢。

```python
# 不推荐：__repr__ 里触发网络请求
class LazyUser:
    def __repr__(self):
        detail = self._fetch_from_api()   # 网络调用！
        return f"LazyUser({detail!r})"
```

`__repr__` 应该只读取对象自身已有的属性，不要触发副作用或耗时操作。需要耗时构造的"详细视图"应该提供一个单独的方法（如 `to_dict()` / `details()`）按需调用。

### 3.7 循环引用与递归保护

对象间互相引用时，`__repr__` 如果递归下去会无限循环。CPython 的 `reprlib` 对容器有内置的递归保护（会输出 `...`），但自定义类没有自动保护。

```python
class Node:
    def __init__(self, name):
        self.name = name
        self.peer = None
    def __repr__(self):
        return f"Node(name={self.name!r}, peer={self.peer!r})"

a = Node("A"); b = Node("B")
a.peer = b; b.peer = a

# repr(a)   # 会无限递归 → 最终 RecursionError
```

处理方式之一是在 repr 里对"已访问"的引用降级，或用 `reprlib` 的 `Repr` 控制深度。简单场景里，对可能成环的字段只显示其 `id` 或名字：

```python
def __repr__(self):
    peer = f"Node(name={self.peer.name!r})" if self.peer else "None"
    return f"Node(name={self.name!r}, peer={peer})"
```

### 3.8 与 logging 的配合

`logging` 模块的 `%r` 占位符走 `repr()`，`%s` 走 `str()`。调试日志推荐用 `%r`，这样类型信息保留：

```python
import logging

logging.basicConfig(level=logging.DEBUG)
log = logging.getLogger(__name__)

name = "alice"; count = 0
log.debug("处理用户 %r，当前计数 %r", name, count)
# 输出：DEBUG:__main__:处理用户 'alice'，当前计数 0
```

注意是 `%r` 不是 `%s`——后者会丢掉字符串的引号，`name` 变成 `alice` 而不是 `'alice'`。新式 f-string 写法对应 `f"... {name!r}"`。

## 4. 原理

这一章深入 Python 内部，把几个关键现象的"为什么"讲透：`str()`/`print()` 到底怎么触发 `__str__`，`__str__` 未定义时怎么回退到 `__repr__`，容器元素打印为什么走 `repr()`，以及 `object.__repr__` 的默认实现。

### 4.1 str() 与 print() 的调用链

当你调用 `str(obj)` 时，CPython 做的事情远不止"找 obj 上有没有 `__str__` 方法"那么简单。准确的过程是：

> `str(obj)` 会去查找 `type(obj).__str__`，而不是 `obj.__str__`。

这句话的意思是：查找发生在**对象的类型**上，沿类型的 MRO（方法解析顺序）向上查找，而不是在实例自身的 `__dict__` 里找。这也是为什么特殊方法（dunder methods）通常应该定义在类上，而不是实例上——实例上挂的 `__str__` 不会被隐式调用。

更完整的描述：

1. `str(obj)` 实际调用的是 `type(obj).__str__(obj)`。
2. Python 沿 `type(obj)` 的 MRO 查找 `__str__` 这个槽位。
3. 如果在某个类（包括 `object`）里找到了，就调用它；`type` 类型本身（以及 `object`）提供了默认实现。
4. `object.__str__` 的默认实现是：**`return repr(self)`**——这就是回退的源头。

所以当一个类没有覆盖 `__str__` 时，`type(obj).__str__` 解析到的是 `object.__str__`，而它内部转调 `repr(self)`，继而走 `type(obj).__repr__`。这条"回退链"完全由 `object.__str__` 的这一行实现。

可以验证 `object.__str__` 的行为：

```python
class NoStr:           # 既不定义 __str__ 也不定义 __repr__
    pass

obj = NoStr()

# object.__str__ 转调 repr，object.__repr__ 给地址串
str(obj) == repr(obj) == object.__repr__(obj)
# 结果：True

print(str(obj))
# 输出：<__main__.NoStr object at 0x...>
```

`print(obj)` 之所以也触发 `__str__`，是因为 `print` 对每个参数执行 `str(arg)`，然后写到 `sys.stdout`。所以 `print(obj)` 等价于 `sys.stdout.write(str(obj) + end)`，最终走到的还是 `type(obj).__str__`。

### 4.2 repr() 与 REPL 回显的调用链

`repr(obj)` 的机制和 `str(obj)` 对称：

> `repr(obj)` 实际调用 `type(obj).__repr__(obj)`。

沿 MRO 查找 `__repr__`。关键区别在于：`object.__repr__` **不会**转调 `__str__`。它的默认实现是返回一个形如 `<ClassName object at 0x...>` 的字符串，包含模块名、类名和 `id(obj)`（十六进制地址）。

`object.__repr__` 在 CPython 中的等价 Python 描述大致是：

```python
def __repr__(self):
    return f"<{type(self).__module__}.{type(self).__qualname__} object at 0x{id(self):x}>"
```

所以只定义 `__str__` 不定义 `__repr__` 时，`repr(obj)` 直接落到 `object.__repr__` 给出地址串——没有"回退到 `__str__`"这条路径，因为 `object.__repr__` 压根不调用 `__str__`。

这就是回退关系不对称的本质原因：

- `object.__str__` → 调 `repr(self)` → 有 `__repr__` 就走它，没有就再落到 `object.__repr__` 的地址串。
- `object.__repr__` → 直接给地址串，不回头找 `__str__`。

**REPL 回显为什么用 repr**

在交互式解释器里直接敲 `obj` 回车，CPython 的交互循环（`sys.displayhook`）会把对象的 `repr()` 写到 `sys.stdout`，而不是 `str()`。这是为了让开发者准确看到对象状态，而不是面向用户的友好文案。可以用 `sys.displayhook` 验证：

```python
import sys

class Demo:
    def __str__(self):
        return "我是 str"
    def __repr__(self):
        return "我是 repr"

d = Demo()
sys.displayhook(d)      # 模拟 REPL 回显
# 输出：我是 repr
```

`sys.displayhook(obj)` 的默认实现简化为：

```python
def displayhook(obj):
    if obj is None:
        return
    text = repr(obj)
    sys.stdout.write(text + "\n")
    builtins._ = obj
```

注意它用的是 `repr(obj)` 而不是 `str(obj)`。所以在普通 `print` 里看到的"友好文案"，和 REPL 里看到的"准确描述"会不一样——这正是两个方法分工的体现。

### 4.3 容器元素为何走 repr：list.__repr__ 的实现

前面 2.4 节展示过 `print([p])` 走 `__repr__` 的现象。原理在于：Python 内置容器（`list`、`tuple`、`dict`、`set`、`frozenset` 等）的 `__repr__` 在拼装字符串时，对每个元素（或键值）调用的是 `repr()` 而不是 `str()`。

`list.__repr__` 的等价描述大致是：

```python
def __repr__(self):
    items = ", ".join(repr(item) for item in self)
    return f"[{items}]"
```

证据：无论你怎么定义元素的 `__str__`，`list` 打印时都只看 `__repr__`：

```python
class Tag:
    def __init__(self, text):
        self.text = text
    def __str__(self):
        return f"<{self.text}>"
    def __repr__(self):
        return f"Tag({self.text!r})"

tags = [Tag("a"), Tag("b")]
print(tags)            # list.__repr__ 对每个元素调 repr
# 输出：[Tag('a'), Tag('b')]

# 想"强制走 str"得自己拼
print("[" + ", ".join(str(t) for t in tags) + "]")
# 输出：[<a>, <b>]
```

`dict.__repr__` 同理：键和值都走 `repr()`：

```python
print({"name": Tag("x"), Tag("y"): 1})
# 输出：{'name': Tag('x'), Tag('y'): 1}
```

注意 dict 的键 `Tag('y')` 也是走 `repr`，所以它能要求和值用同一种"准确"表示，保证整个字典的 repr 看起来像一个能 eval 还原的表达式。

这个设计让"容器嵌套对象"的调试输出天然一致：每一层都是 repr，类型信息层层保留，不会因为某一层的 `__str__` 更花哨而丢信息。代价就是：如果你的类没实现 `__repr__`，容器里立刻出现一串地址。

### 4.4 object 默认 __repr__ 的内容

最后看一下最底兜底的 `object.__repr__` 到底输出什么。前面给过等价描述，这里再用实验确认它确实包含三样东西：模块名、类名、`id()`。

```python
class Something:
    pass

s = Something()
r = repr(s)
print(r)
# 输出：<__main__.Something object at 0x...>

# 解析出三个部分
import re
m = re.match(r"<(\S+)\.(\S+) object at 0x([0-9a-f]+)>", r)
print(m.group(1), m.group(2), int(m.group(3), 16))
# 输出：__main__ Something <某个整数，等于 id(s)>

int(m.group(3), 16) == id(s)
# 输出：True
```

可以看到地址部分的十六进制值恰好等于 `id(s)`。所以说默认 repr "不是随机的地址串"，而是"模块名 + 类名 + 对象 id"，其中对象 id 在对象生命周期内是确定的。

当你的类定义在某个包里，`type(self).__module__` 会是包名，`type(self).__qualname__` 会包含嵌套路径（比如 `Outer.Inner`），所以 repr 里能准确看到"这是哪个包、哪个嵌套类的对象"——这对排查线上问题非常有价值。

### 4.5 回退关系与 MRO 的综合示意

把前几节的机制合起来，用一个图式化的小例子完整走一遍。假设继承关系如下：

```python
class Base:
    def __repr__(self):
        return "Base.repr"

class Mid(Base):       # 只定义 __str__
    def __str__(self):
        return "Mid.str"

class Leaf(Mid):       # 啥都不定义
    pass

leaf = Leaf()
```

MRO 是 `Leaf → Mid → Base → object`。

2. `print(leaf)`：`str(leaf)` → 找 `type(leaf).__str__`，沿 MRO 在 `Mid` 找到 `__str__` → 输出 `Mid.str`。

3. `repr(leaf)`：找 `type(leaf).__repr__`，沿 MRO 在 `Base` 找到 `__repr__` → 输出 `Base.repr`。

4. `[leaf]` 打印：`list.__repr__` 对 `leaf` 调 `repr` → 同上 → 输出 `[Base.repr]`。

5. 把 `Mid.__str__` 删掉再 `print(leaf)`：找 `__str__` 沿 MRO 一直找到 `object.__str__`，它转调 `repr(self)` → 找到 `Base.__repr__` → 输出 `Base.repr`。这就是"没 `__str__` 时回退"的完整路径。

6. 把 `Base.__repr__` 也删掉再 `repr(leaf)`：找到 `object.__repr__` → 输出 `<__main__.Leaf object at 0x...>`。没有回退到（已删的）`__str__`。

```python
print(leaf)
# 输出：Mid.str

print(repr(leaf))
# 输出：Base.repr

print([leaf])
# 输出：[Base.repr]
```

这个例子同时展示了：MRO 查找、`__str__` 回退到 `__repr__`、`__repr__` 不回退、容器走 `__repr__`——四条规则一次看全。

### 4.6 type 上的 __str__ 与 __repr__

还有一个容易忽视的点：`__str__` 和 `__repr__` 的查找发生在 `type(obj)` 上，而"类型对象本身"也是一个对象（`type` 的实例）。当你 `print(SomeClass)` 时，走的是 `type.__repr__`（对类）或 `type.__str__`（对类，Python 3 中 `type` 没单独的 `__str__`，会回退）。

```python
class Foo:
    pass

print(Foo)       # type.__str__(Foo) → 通常是 "<class '__main__.Foo'>"
# 输出：<class '__main__.Foo'>

repr(Foo)
# 输出：<class '__main__.Foo'>

# 给类自己定义 __repr__（通过 metaclass）可以改写它
class Meta(type):
    def __repr__(cls):
        return f"<Class {cls.__name__}>"

class Bar(metaclass=Meta):
    pass

print(Bar)
# 输出：<Class Bar>
```

日常业务代码几乎不用动 metaclass，这里只是为了说明"`type(obj).__str__`"这条规则对"类型对象本身"同样成立：`type(Foo)` 是 `type`，所以走 `type.__str__` / `type.__repr__`。

### 4.7 小结：一图概括的调用图

把全章机制压缩成一张文字图：

```
print(obj)  ──> str(obj) ──> type(obj).__str__(obj)
                                  │
            ┌─────────────────────┴──────────────────────┐
            │ 找到自定义 __str__?  ──> 调用它，结束。
            │ 否则落到 object.__str__(obj)
            │       └──> return repr(obj)
            │                   └──> type(obj).__repr__(obj)
            │                          │
            │                 ┌────────┴─────────────┐
            │                 │ 找到自定义 __repr__? │
            │                 │   ──> 调用它，结束。  │
            │                 │ 否则 object.__repr__ │
            │                 │   ──> "<Cls at 0x..>"│
            │                 └──────────────────────┘
            └──────────────────────────────────────────┘

repr(obj)  ──> type(obj).__repr__(obj)   （同上右半支，无 __str__ 回退）

REPL 回显  ──> sys.displayhook(obj) ──> repr(obj) ──> 同上

print([obj]) ──> list.__repr__ ──> repr(obj) for each ──> 同上
```

这张图集中了五条规则：`str` 查 `type().__str__`、`object.__str__` 转调 `repr`、`repr` 不回退、REPL 用 `repr`、容器对元素用 `repr`。理解了这张图，本篇所有现象都能自己推导。

## 5. 总结

### 5.1 本文内容要点

- Python 用 `__str__` 和 `__repr__` 两个特殊方法管理"对象 → 字符串"的转换，分别面向用户和开发者。
- `__str__` 由 `print()`、`str()`、`f"{obj}"` 等触发，目标是可读；`__repr__` 由 `repr()`、REPL 回显、调试器、`logging %r` 等触发，目标是准确无歧义、理想可 eval 还原。
- 两者之间存在不对称回退：未定义 `__str__` 时通过 `object.__str__` 自动回退到 `__repr__`；未定义 `__repr__` 时不回退，退到 `object.__repr__` 给出 `<ClassName object at 0x...>` 地址串。
- 正因如此，**永远至少实现 `__repr__`**——它能同时覆盖调试视角和（通过回退）用户视角；只写 `__str__` 救不了调试和容器场景。
- 容器（`list`、`dict`、`tuple`、`set` 等）的 `__repr__` 对元素/键值一律调用 `repr()`，所以 `print([obj])` 走的是元素的 `__repr__` 而非 `__str__`——这是"必须实现 `__repr__`"的强理由之一。
- f-string 默认走 `__str__`；`!r` 强制走 `__repr__`，在实现 `__repr__` 给字符串属性加引号、以及在调试/日志里保留类型信息时高频使用；`!s` 是显式的默认。
- `@dataclass` 自动生成符合规范的 `__repr__`（只生成 `__repr__`，`__str__` 由回退处理）；`field(repr=False)` 可把敏感/大字段排除出 repr。
- `__repr__` 应包含类名与关键属性，格式形如 `ClassName(field=value, ...)`；不可还原的对象用 `<ClassName ...>` 降级；敏感字段不进 repr；避免在 `__repr__` 里做重活或触发副作用。
- `__format__` 在带格式说明符（`{obj:spec}`）时接管，空说明符回退到 `__str__`，需要自定义格式语法时再覆盖。

### 5.2 读完应能掌握的能力

- 能说明 `__str__` 与 `__repr__` 各自的受众、触发入口和设计目标，并能根据场景选择实现哪一个。
- 能解释"只定义 `__repr__` 时 `print(obj)` 为什么也能工作"——即 `object.__str__` 转调 `repr` 的回退链。
- 能解释"只定义 `__str__` 时 `repr(obj)` 为什么仍是地址串"——即 `object.__repr__` 不回退到 `__str__`。
- 能解释 `print([obj])` 中元素为什么走 `__repr__`——即容器 `__repr__` 对元素调 `repr()`。
- 能写出符合规范的 `__repr__`（类名 + 关键属性 + 字符串带引号 + 可 eval 还原或 `<...>` 降级）。
- 能用 `!r` 在 f-string 里强制 repr，并理解它在实现 `__repr__` 和调试日志里的作用。
- 能用 `@dataclass` 自动生成 `__repr__`，并用 `field(repr=False)` 排除敏感字段。
- 能描述 `str(obj)`/`repr(obj)` 沿 `type(obj)` 的 MRO 查找的过程，以及 `object.__str__`/`object.__repr__` 的默认实现各做什么。
