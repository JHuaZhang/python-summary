## 1. 介绍

### 1.1 什么是"同步阻塞"

在绝大多数 Python 入门教程里，我们写的代码都是"同步"的：一行执行完才执行下一行，前一个调用没返回，后面的语句就只能干等。这种"写起来像流水账"的编程模型，就是同步编程（synchronous programming）。

所谓"阻塞"（blocking），指的是当程序执行到一个耗时的 I/O 操作时——比如发起一次网络请求、读写一个文件、查询一次数据库、调用 `time.sleep()`——当前线程会被操作系统挂起，把这个 CPU 时间片让出去，直到这个操作完成才能继续往下跑。在这段等待的时间里，线程什么都不干，CPU 也无法用它去做别的有用的事（从应用代码的视角看，就是"空等"）。

同步阻塞并不是一个"bug"，它是大多数系统调用默认的工作方式，也是人类最直观的思考顺序："先拿数据，再处理数据，最后输出结果"。问题在于：当程序需要同时处理大量 I/O 时——比如一个 Web 服务要同时响应几百个用户的请求，每个请求都要去查一次数据库、调一次第三方接口——同步阻塞模型会让 CPU 在大量的"等待"中白白浪费掉，吞吐量上不去。

本篇要做的，就是把"同步代码遇到 I/O 会怎样"这件事拆开讲透：先看同步串行执行多个 I/O 时耗时如何累加，再看用多线程绕过阻塞要付出什么代价，最后引出协程这个"在单线程内用事件循环切任务"的思路，作为异步系列的开篇动机。

### 1.2 "同步"到底同步在哪里

很多人对"同步"这个词只有模糊感受，这里把它钉死。在编程语境里，"同步"指的是**调用方和被调方在时间上被绑在一起**：调用方发起调用后，必须原地等被调方把结果准备好并返回，才能继续往下走；被调方没返回之前，调用方什么也做不了。所谓"同步"，就是"你和我，在同一时间线上，一个做完另一个才能开始"。

它和"异步"的对照是：异步调用下，调用方发起调用后**不原地等**，而是先去干别的活；被调方准备好结果后，通过回调、事件、Future 等方式通知调用方"我好了"。两者的时间线是解耦的。

理解这一层，就能明白为什么同步代码"直观但低效"：把时间线绑死的好处是推理简单——每一行执行时，上一行的结果一定已经到位；坏处是只要有一行在等 I/O，整条时间线就卡在那里，CPU 不能借这个空档去推别的时间线（别的任务）。

### 1.3 同步代码的最小样貌

在展开痛点之前，先用一段最朴素的同步代码把"阻塞"具象化。这段代码没有依赖任何外部服务，只是用 `time.sleep` 模拟一次 I/O 等待（真实场景里，它可能是一次 `requests.get`、一次 `db.query`、一次 `f.read()`）。

```python
import time

def fetch_data(name: str, seconds: float) -> str:
    # 模拟一次耗时 I/O：网络请求 / 数据库查询 / 文件读取都长这样
    print(f"[{name}] 开始请求 ...")
    time.sleep(seconds)          # 阻塞当前线程 seconds 秒
    print(f"[{name}] 请求完成")
    return f"{name} 的数据"

start = time.perf_counter()

# 三个任务串行执行，前一个不完成后一个不开始
r1 = fetch_data("接口A", 1.0)
r2 = fetch_data("接口B", 1.0)
r3 = fetch_data("接口C", 1.0)

elapsed = time.perf_counter() - start
print(f"总耗时: {elapsed:.2f}s")
# 输出：
# [接口A] 开始请求 ...
# [接口A] 请求完成
# [接口B] 开始请求 ...
# [接口B] 请求完成
# [接口C] 开始请求 ...
# [接口C] 请求完成
# 总耗时: 3.00s
```

三个各耗时 1 秒的 I/O 任务串行跑完，总耗时就是 3 秒——它们是"一个等一个"的。这并不奇怪，因为 `time.sleep` 把当前线程挂起了整整 1 秒，这段时间里第二个 `fetch_data` 根本没机会开始。

这就是同步阻塞最直接的痛点：**I/O 等待时间被线性累加，CPU 在等待期间无法服务其它任务**。后面我们会看到，为了不白白等这 3 秒，人们先是想到多线程，再是发现多线程有它自己的代价，最后才走到协程。

### 1.4 常见的阻塞调用清单

为了把"阻塞"从抽象概念变成可识别的具体点，列一份 Python 里最常见的阻塞调用清单。看到这些调用，大脑就该响起"这里会卡住线程"的警报：

| 类别 | 典型调用 | 阻塞原因 |
|------|---------|---------|
| 网络 | `socket.recv` / `requests.get` / `urllib.request.urlopen` | 等待对端数据到达 |
| 文件 | `f.read()` / `f.write()` / `open()`（某些情况） | 等待磁盘 I/O 完成 |
| 数据库 | `cursor.execute()` / `cursor.fetchall()` | 等待数据库返回结果 |
| 进程 | `subprocess.run()` / `subprocess.Popen.wait()` | 等待子进程结束 |
| 时间 | `time.sleep(n)` | 等待 n 秒定时器到期 |
| 同步原语 | `lock.acquire()` / `queue.Queue.get()` | 等待锁释放 / 队列有数据 |
| 线程 | `thread.join()` | 等待目标线程结束 |

这张表的本质是：**任何"等待某个外部事件"的调用，默认都是阻塞的**。阻塞并不可耻，它是默认行为；但当一段代码里这样的调用密集出现时，同步模型就会显出疲态。协程后面要做的事，就是把这些调用一一替换成"非阻塞 + 事件通知"的等价物（`aiohttp`、`aiomysql`、`asyncio.sleep` 等）。

## 2. 核心内容

### 2.1 痛点一：串行执行下 I/O 耗时线性累加

真实业务里，一次接口调用很少只依赖一个外部服务。一个典型的订单详情页可能要并行调用：用户信息接口、订单主表接口、物流信息接口、优惠券接口。如果这些接口各耗时 200ms，同步串行地一个个调，总耗时就是 800ms；而它们彼此并没有依赖关系，完全可以同时去拿，理论上 200ms 就能全部回来。

先看串行版本的样子。下面用 `requests` 库模拟调用三个 HTTP 接口（如果你没有 `requests`，把它脑补成任何会阻塞的网络调用即可，`urllib.request.urlopen` 也是一样的阻塞行为）。

```python
import time
import requests   # pip install requests

def fetch(url: str) -> str:
    # requests.get 是阻塞调用：在响应返回前，当前线程一直挂起
    resp = requests.get(url, timeout=5)
    return resp.text

start = time.perf_counter()

# 三个接口要的数据相互独立，但因为是同步代码，只能一个一个调
data_a = fetch("https://httpbin.org/delay/1")   # 服务端故意延迟 1 秒
data_b = fetch("https://httpbin.org/delay/1")
data_c = fetch("https://httpbin.org/delay/1")

elapsed = time.perf_counter() - start
print(f"三个接口串行总耗时: {elapsed:.2f}s")
# 输出：
# 三个接口串行总耗时: 3.02s
```

`httpbin.org/delay/1` 是一个测试服务，收到请求后会等 1 秒再返回。三个请求串行打过去，总耗时 ≈ 3 秒。这里的关键不在于"网络慢"，而在于：**第二个请求在第一个请求等待的那 1 秒里，本可以同时发出去，但同步代码做不到**。

把这个放大到生产规模：如果一个网关服务每秒要处理 1000 个请求，每个请求内部要调 3 个下游接口、各 50ms。串行的话每个请求要花 150ms，单线程一秒最多处理约 6 个请求；如果能让这 3 个调用并行，每个请求只要 50ms，单线程一秒就能处理约 20 个请求——同样的一台机器，吞吐差 3 倍以上。这就是"耗时线性累加"在规模化场景下的代价。

**为什么 Python 的 I/O 调用会阻塞线程**

`requests.get`、`urllib.request.urlopen`、`socket.recv`、`time.sleep`、`f.read()` 这些看起来毫不相关的调用，底层都会走到操作系统的"阻塞式系统调用"（blocking syscall）。比如读网络数据最终会调用类似 `recv(fd, ...)` 的系统调用，操作系统发现这个 socket 上还没数据到达，就把当前线程标记为"不可运行"（睡眠状态），从 CPU 上拿下来，去调度别的进程运行；等数据到了网卡、内核把数据准备好，再把线程唤醒。在"睡着"到"被唤醒"这段时间里，这个线程对 Python 层来说就是"卡在那一行不动"——这就是阻塞的本意。

所以"阻塞"不是 Python 的发明，而是系统调用默认的工作方式。Python 只是忠实地继承了它。

### 2.2 痛点二：阻塞期间 CPU 无法服务其它任务

线性累加耗时还不是最伤的，更伤的是：线程被挂起的那段时间，CPU 这块资源本来可以拿去算别的东西，但同步代码里它就是空闲了。

用一个对比来感受。假设有两个任务：一个是 CPU 计算（算斐波那契），一个是 I/O 等待（`sleep`）。先看同步串行执行。

```python
import time

def cpu_work(n: int) -> int:
    # 纯 CPU 计算，不涉及 I/O
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

def io_work(seconds: float) -> None:
    # 模拟一次 I/O 等待
    time.sleep(seconds)

start = time.perf_counter()
io_work(1.0)            # 先等 1 秒：这段时间 CPU 是空的
result = cpu_work(200000)   # 再算一会儿
elapsed = time.perf_counter() - start
print(f"串行总耗时: {elapsed:.3f}s, fib={result % 100000}")
# 输出：
# 串行总耗时: 1.045s
```

在 `io_work` 等待的那 1 秒里，`cpu_work` 本可以同时把活干完，但同步代码做不到——它只能让 CPU 空等那 1 秒。总耗时 ≈ "I/O 等待 + CPU 计算"。

这就是第二个痛点的典型表现：**I/O 等待和 CPU 计算无法重叠，CPU 资源在 I/O 阻塞期间被浪费**。在单线程同步代码里，这是无解的——你只能让 CPU 陪着一根网线一起等。

**理想情况应当是什么样**

如果有一种机制能让 CPU 在"第一个任务等 I/O"的那 1 秒里，去跑"第二个任务的 CPU 计算"，那总耗时就能从 1.045s 降到 max(1.0s, 0.045s) ≈ 1.0s——CPU 不再陪 I/O 一起空等。这正是后面要讲的多线程能做的事，也是协程能做得更好的事。本节只是先把"理想"立起来，方便后面衡量各种方案的得失。

### 2.3 痛点三：sleep 阻塞会"冻住"整个线程

`time.sleep` 是最容易让人低估的阻塞源。它看起来"无害"，只是让程序停一下，但它会把这个线程整个冻住——在 sleep 期间，这个线程做不了任何事，连后面的 print 都发不出来，更别说处理别的事件。

```python
import time

start = time.perf_counter()
print("准备 sleep 2 秒 ...", flush=True)
time.sleep(2)   # 这 2 秒里，线程完全冻结，什么都做不了
print("醒来", flush=True)
print(f"距开始已过: {time.perf_counter() - start:.2f}s")
# 输出：
# 准备 sleep 2 秒 ...
# 醒来
# 距开始已过: 2.00s
```

如果把这段代码放进一个 CLI 工具里，用户在这 2 秒里按 Ctrl+C 是能中断的（因为 `sleep` 会被信号打断），但如果你想在这 2 秒里"顺便"刷新一下进度条、响应一下另一个网络消息，单线程同步代码做不到。

这个痛点在很多场景里都很扎眼：

- **定时任务**里 `time.sleep(60)` 等待下一轮，这 60 秒线程没法处理任何别的逻辑。
- **轮询接口**时 `while True: data = fetch(); if data: break; time.sleep(1)`，每次 sleep 都冻住线程。
- **GUI / 游戏主循环**里如果用 `sleep`，整个界面会卡死——因为 UI 线程被冻住了，没法响应鼠标和重绘。

`time.sleep` 就是阻塞式系统调用的一个直观缩影：它把"我想等一会儿"翻译成了"把当前线程从 CPU 上拿下来，过一会儿再放回来"。在等待期间，线程就是一个不能动的植物人。后面我们在协程里会见到的 `asyncio.sleep`，干的是完全不同的另一件事——它不冻结线程，只是把当前协程挂起、把控制权还给事件循环，让别的协程趁机跑。

### 2.4 用多线程绕过阻塞：把"同时等"变成可能

面对"3 个接口串行要 3 秒"的痛点，最常见的本能反应是：开 3 个线程同时去等，总耗时就能压到 1 秒。这正是多线程在做的事——每个线程各自阻塞各自的，但它们在"同时"阻塞，从外面看就是并发地完成了 3 次 I/O。

```python
import time
import threading

def fetch(name: str, seconds: float) -> str:
    print(f"[{name}] 开始", flush=True)
    time.sleep(seconds)   # 每个线程各自阻塞，互不影响
    print(f"[{name}] 完成", flush=True)
    return f"{name} 的数据"

start = time.perf_counter()

results = [None, None, None]
def worker(idx: int, name: str, seconds: float):
    results[idx] = fetch(name, seconds)

threads = [
    threading.Thread(target=worker, args=(0, "接口A", 1.0)),
    threading.Thread(target=worker, args=(1, "接口B", 1.0)),
    threading.Thread(target=worker, args=(2, "接口C", 1.0)),
]
for t in threads:
    t.start()
for t in threads:
    t.join()   # 主线程等所有子线程结束

elapsed = time.perf_counter() - start
print(f"三线程并发总耗时: {elapsed:.2f}s, 结果: {results}")
# 输出：
# [接口A] 开始
# [接口B] 开始
# [接口C] 开始
# [接口A] 完成
# [接口B] 完成
# [接口C] 完成
# 三线程并发总耗时: 1.00s, 结果: ['接口A 的数据', '接口B 的数据', '接口C 的数据']
```

3 个线程各自 sleep 1 秒，总耗时从 3 秒降到了 1 秒——I/O 等待被"并发"掉了。这正是多线程在 I/O 密集场景下的价值：**它让多个阻塞操作在同一时间段内并行等待，从而把线性累加的耗时压到单次最长的那个**。

看起来问题解决了？并没有。多线程只是把痛转移了——它带来了一系列新的代价，下面逐一拆。

### 2.5 多线程的代价一：线程切换的内核开销

线程并不是"免费的"。每个线程要有一个独立的栈空间（默认可以到几 MB），创建和销毁线程要走系统调用（Linux 上是 `clone`/`futex` 一类），线程之间切换时要从内核态把当前线程的寄存器、栈指针、程序计数器保存下来，再恢复另一个线程的上下文——这个动作叫"上下文切换"（context switch），全部由操作系统内核完成，开销不低。

下面这段代码用两种方式对比：用线程池不断提交小任务 vs 直接在主线程里同步循环。重点看线程切换带来的额外耗时。

```python
import time
from concurrent.futures import ThreadPoolExecutor

def tiny_io(i: int) -> int:
    # 一个极轻的"I/O"：只 sleep 极短时间，让线程会被挂起/唤醒
    time.sleep(0.0001)
    return i

N = 2000

# 方式一：同步串行
start = time.perf_counter()
for i in range(N):
    tiny_io(i)
serial = time.perf_counter() - start

# 方式二：线程池并发，但任务极小，开销主要来自线程调度
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=50) as pool:
    list(pool.map(tiny_io, range(N)))
pooled = time.perf_counter() - start

print(f"同步串行 {N} 次: {serial:.3f}s")
print(f"50 线程池 {N} 次: {pooled:.3f}s")
# 输出（一次实测）：
# 同步串行 2000 次: 0.24s
# 50 线程池 2000 次: 0.31s
```

注意看：在这个任务极轻的场景下，多线程反而比同步串行更慢——因为每个任务的有效工作量只有 0.1ms，而线程的创建/调度/切换开销把它本身那点收益吃掉了。这说明：**线程并发对 I/O 密集且单次 I/O 较重的场景收益明显，但对"海量小任务"反而可能因切换开销变慢**。

一次上下文切换在主流操作系统上大致是微秒级到几十微秒，看起来很小，但当线程数拉到几百上千、且任务本身又轻时，切换开销的累积就不可忽略。线程数越多，调度器要管理的就绪队列越长，切换越频繁，CPU 花在"切线程"而不是"干活"上的时间就越多。

**进一步：观察线程切换的实际代价**

Python 标准库并没有直接暴露"线程切换次数"的便捷 API，但可以用 `time` + 高频任务的对比看出量级差别。下面对比"同样量的 I/O，单线程串行 vs 线程池并发"，这次把单次任务调重一点（50ms），让并发收益能盖过切换开销。

```python
import time
from concurrent.futures import ThreadPoolExecutor

def real_io(i: int) -> int:
    time.sleep(0.05)   # 50ms，更接近真实一次网络 I/O
    return i

N = 100

start = time.perf_counter()
for i in range(N):
    real_io(i)
serial = time.perf_counter() - start   # 串行：5s 左右

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=20) as pool:
    list(pool.map(real_io, range(N)))  # 并发：5 批，每批 0.05s
parallel = time.perf_counter() - start

print(f"串行 {N} 次: {serial:.3f}s")
print(f"20 线程并发 {N} 次: {parallel:.3f}s")
# 输出（一次实测）：
# 串行 100 次: 5.05s
# 20 线程并发 100 次: 0.27s
```

任务变重后，多线程优势立刻就出来了——5 秒压到 0.27 秒。这说明线程并发的收益曲线和"单次 I/O 耗时 vs 切换开销"比例强相关：单次 I/O 越重，越值得开线程去并发；单次 I/O 越轻（上节 0.1ms），越不值得。这给协程留出了定位空间：协程的切换开销远小于线程，所以在"海量但单次不重"的 I/O 场景里优势更明显。

### 2.6 多线程的代价二：GIL 限制 CPU 并发

GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器的一个实现细节，但对多线程的并发能力影响极大。它的含义是：**在任意时刻，只有一个线程在执行 Python 字节码**。也就是说，即便你开了 8 个线程跑在一台 8 核机器上，这 8 个线程也只能轮流用一个核心来执行 Python 代码，不能真正并行地算。

对于 I/O 密集任务，GIL 的影响相对小——因为线程在等待 I/O 时会主动释放 GIL（阻塞式系统调用前夕 CPython 会释放 GIL，I/O 完成后再重新获取），其它线程可以趁机跑。这就是为什么上面 3 线程并发能把 3 次 sleep 压到 1 秒：I/O 等待期间 GIL 被让出，其它线程能进入系统调用。

但对于 CPU 密集任务，GIL 几乎是致命的。下面对比单线程串行 vs 多线程并发做纯 CPU 计算。

```python
import time
import threading

def cpu_work(n: int) -> int:
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

N = 120000
WORKERS = 4

# 单线程：跑 4 次计算
start = time.perf_counter()
for _ in range(WORKERS):
    cpu_work(N)
serial = time.perf_counter() - start

# 多线程：4 个线程各跑一次
start = time.perf_counter()
threads = [threading.Thread(target=cpu_work, args=(N,)) for _ in range(WORKERS)]
for t in threads: t.start()
for t in threads: t.join()
parallel = time.perf_counter() - start

print(f"单线程跑 {WORKERS} 次 CPU 计算: {serial:.2f}s")
print(f"{WORKERS} 线程并发跑 {WORKERS} 次 CPU 计算: {parallel:.2f}s")
# 输出（一次实测，8 核机器）：
# 单线程跑 4 次 CPU 计算: 4.10s
# 4 线程并发跑 4 次 CPU 计算: 4.18s
```

4 线程并发的耗时和单线程几乎一样——并没有因为多了 3 个线程就快 3 倍。这就是 GIL：CPU 工作时 GIL 被持有，其它线程只能干等着轮到自己，4 个线程其实是串行跑的，只是轮着跑而已。

**对照：用多进程绕开 GIL**

同样这段 CPU 计算，换个 `ProcessPoolExecutor`（多进程，每个进程有自己的 GIL），就能真正并行起来。

```python
import time
from concurrent.futures import ProcessPoolExecutor

def cpu_work(n: int) -> int:
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

N = 120000
WORKERS = 4

if __name__ == "__main__":
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=WORKERS) as pool:
        list(pool.map(cpu_work, [N] * WORKERS))
    parallel = time.perf_counter() - start

    print(f"4 进程并行跑 4 次 CPU 计算: {parallel:.2f}s")
    # 输出（一次实测，8 核机器）：
    # 4 进程并行跑 4 次 CPU 计算: 1.12s
```

4 进程并行 ≈ 1.1s，相比单线程 4.1s 拿到了接近 4 倍加速——这才是真正的 CPU 并行。代价是进程比线程重得多（独立内存空间、独立 Python 解释器实例），进程间通信要 IPC、不能直接共享对象。

这意味着：**多线程只对 I/O 密集有效，对 CPU 密集无效**（CPU 密集要并行得用 `multiprocessing` 多进程，各进程有独立 GIL）。这是后面协程定位"只解决 I/O 并发，不解决 CPU 并发"的重要背景。

### 2.7 多线程的代价三：线程数过多带来资源占用

每个线程要占内存（栈空间），线程数过多会吃满内存；线程数过多也会让调度器不堪重负。下面给一个直观感受：开 10000 个线程看看内存占用和启动时间。

```python
import time
import threading
import resource

def noop():
    time.sleep(1)   # 每个线程都睡 1 秒，活着但不干活

start = time.perf_counter()
threads = [threading.Thread(target=noop) for _ in range(10000)]
for t in threads:
    t.start()
for t in threads:
    t.join()
elapsed = time.perf_counter() - start

# 读取当前进程最大驻留内存（Linux/macOS，单位 KB）
mem_kb = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
print(f"10000 线程启动+运行耗时: {elapsed:.2f}s")
print(f"进程峰值内存: {mem_kb / 1024:.0f} MB")
# 输出（一次实测）：
# 10000 线程启动+运行耗时: 3.2s
# 进程峰值内存: 540 MB
```

10000 个什么活都不干的线程，光栈就要吃掉几百 MB。这在异步场景里是个很现实的问题：一个要同时 hold 住几万个长连接的服务（比如 IM 网关、股票行情推送），如果每个连接一个线程，光是线程栈就能把内存吃光，CPU 调度开销更是雪上加霜。

**栈空间为什么这么大**

Python 线程在 C 实现上就是操作系统的原生线程，所以它的栈按 OS 线程栈管理。Linux 默认线程栈是 8MB（可调小），macOS 通常 512KB~8MB。即便栈还没真的写满 8MB，操作系统也会按需逐步分配实际物理页，但虚拟地址空间是预留的。一个进程能开多少线程，基本上受"虚拟地址空间 / 栈大小"和 `ulimit -u` 的限制——32 位机器上开几千个就顶天了，64 位机器地址空间够、但物理内存和调度开销还是会顶住。

相比之下，协程的"任务"本质是用户态的对象，栈空间极小（几 KB 量级，甚至可以按需增长），一个进程 hold 住十万级协程是常态。这就是异步在"海量并发"场景下压倒多线程的根本原因之一。

### 2.8 多线程的代价四：竞态条件需要加锁

多线程访问共享数据时会出现竞态条件（race condition），必须靠锁来保护。锁用得对能保证正确性，但用得不对就是死锁、性能下降、代码难维护。

```python
import threading

counter = 0
lock = threading.Lock()

def bump_without_lock():
    global counter
    for _ in range(100000):
        counter += 1   # 非原子操作：读-改-写，多线程下会丢更新

def bump_with_lock():
    global counter
    for _ in range(100000):
        with lock:     # 加锁保护共享变量
            counter += 1

# 不加锁的对比
counter = 0
ts = [threading.Thread(target=bump_without_lock) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print(f"不加锁, 期望 500000, 实际: {counter}")
# 输出：
# 不加锁, 期望 500000, 实际: 241317   # 每次运行都不同，且远小于期望

# 加锁的对比
counter = 0
ts = [threading.Thread(target=bump_with_lock) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print(f"加锁,   期望 500000, 实际: {counter}")
# 输出：
# 加锁,   期望 500000, 实际: 500000
```

不加锁的结果是 24 万多而不是 50 万——因为 `counter += 1` 不是原子操作，它分"读 counter → 加 1 → 写回 counter"三步，多个线程交错执行时会丢掉大量更新。加锁后结果对，但代价是：

- **性能下降**：锁是串行化点，同一时刻只有一个线程能进临界区，并发度被压低。
- **写代码心智负担大**：每一处共享数据访问都要想"要不要加锁""锁的粒度多大""会不会死锁"。
- **死锁风险**：两把锁交叉持有，线程互相等对方释放，程序卡死。

**死锁的最小复现**

下面这个例子就是为了让你看到死锁是怎么长出来的：两个线程各拿一把锁、又去要对方的锁，结果谁也不松手。

```python
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()

def t1_work():
    with lock_a:
        time.sleep(0.1)   # 制造时序，让对方有机会拿 lock_b
        with lock_b:
            print("t1 拿到两把锁")

def t2_work():
    with lock_b:
        time.sleep(0.1)
        with lock_a:
            print("t2 拿到两把锁")

# 启动后两个线程会互相卡死，程序永远不退出
t1 = threading.Thread(target=t1_work)
t2 = threading.Thread(target=t2_work)
t1.start(); t2.start()
t1.join(timeout=1); t2.join(timeout=1)
print("主线程退出（子线程还在死锁中）")
# 输出：
# 主线程退出（子线程还在死锁中）
#   # 没有 "t1 拿到两把锁" / "t2 拿到两把锁" 打印——都在死等
```

死锁是并发编程里最阴险的 bug 之一，因为它不报错、不抛异常，只是程序"卡住不动"。要避免死锁得遵守"锁的顺序"——所有线程都按相同顺序获取多把锁——但这需要全局视角、靠人维护，规模一大就难。这正是多线程代码难写难维护的核心原因之一。

协程天然规避了大部分这类问题：**协程的切换发生在用户态、由事件循环在确定的点调度，不存在"两条字节码被真正同时执行"的情况**（单线程内的协程其实是协作式调度），所以协程之间的共享数据通常不需要加锁。这又是协程相对多线程的一个结构性优势。

### 2.9 阻塞式 vs 事件驱动：两种思路的对比

把上面所有痛点综合起来，就能看出两种 I/O 模型的根本分歧。

**阻塞式（同步 / 多线程）模型**：每个任务一个执行流（线程），执行流在 I/O 时阻塞。要并发就开多个执行流，让它们各自阻塞各自。代价是执行流本身有资源成本和切换成本，且执行流数量受内存和调度器能力限制。

**事件驱动（异步 / 协程）模型**：一个执行流（线程）跑一个事件循环（event loop），同时"关注"成千上万个 I/O 操作。当某个 I/O 可以读/写了，事件循环就通知对应的回调或协程去处理；处理过程中又遇到 I/O，就把控制权交回事件循环，去处理别的就绪任务。执行流只有一个，没有线程切换，没有 GIL 在并发上的牵制（因为就不需要多个执行流），共享数据也不需要锁。

用一个生活类比：阻塞式模型像是"一个人排队买一张票"——要买 10 张票就派 10 个人去排队；事件驱动模型像是"一个人同时对 10 个窗口说'到我了喊我'"，然后自己坐在中央处理任何一个窗口的叫号。后者只用一个人，但要求"叫号机制"足够高效。

**两种模型的代码长相对比**

阻塞式（线程池版本）：

```python
# 每个并发单元是一条独立的 OS 线程
def fetch(url):
    return requests.get(url).text   # 阻塞这一条线程

with ThreadPoolExecutor(max_workers=3) as pool:
    results = list(pool.map(fetch, urls))
```

事件驱动（协程版本，仅形式预览，细节后续讲）：

```python
import asyncio
import aiohttp   # 异步 HTTP 库

async def fetch(session, url):
    async with session.get(url) as resp:   # 遇 I/O 让出 CPU，不阻塞线程
        return await resp.text()

async def main(urls):
    async with aiohttp.ClientSession() as session:
        results = await asyncio.gather(
            *[fetch(session, u) for u in urls]
        )
    return results

# asyncio.run(main(urls))  # 单线程内并发所有请求
```

两者的差别不在"功能"——都是把 N 个请求并发起来；差别在"代价"——线程池要付线程开销、受 GIL 牵制（但 I/O 场景影响小）、并发数受线程数限制；协程全在单线程内跑，无切换开销、无锁、可 hold 住海量并发单元。

协程就是 Python 对事件驱动模型的语言级支持：用 `async def` 定义能在 I/O 处"让出 CPU"的函数，用事件循环在单线程内调度这些协程。这正是后续笔记要展开的内容。本篇作为动机篇，先讲清"为什么需要它"。

### 2.10 一图胜千言：三种方案的并发模型对照

把前面三种 I/O 处理思路的对照表放这里，方便一眼看清差异：

| 维度 | 同步串行 | 多线程并发 | 协程并发（后续） |
|------|---------|-----------|-----------------|
| 并发单元 | 无（一条主线） | OS 线程 | 协程（用户态） |
| I/O 时行为 | 线程挂起、CPU 空等 | 线程挂起、但多线程并发等待 | 协程让出 CPU、事件循环跑别协程 |
| 切换开销 | 无切换 | 内核态切换，微秒~几十微秒 | 用户态切换，纳秒~微秒级 |
| 内存占用 | 仅主线程栈 | 每线程 MB 级栈 | 每协程 KB 级 |
| GIL 影响 | 单线程无所谓 | I/O 场景可释放、CPU 场景受限 | 单线程、无 GIL 牵制 |
| 共享数据加锁 | 不需要 | 通常需要 | 通常不需要 |
| 适合场景 | 简单脚本、低并发 | 中等 I/O 并发、CPU 密集要换多进程 | 高并发 I/O、海量连接 |

这张表是本篇所有要点的浓缩。异步系列的后续笔记会深入到协程的每一栏细节，本篇的任务是把"为什么要从第 1 列走到第 3 列"讲透。

### 2.11 一句话总结同步代码的根本矛盾

把它压缩成一句话：**同步代码"写起来直观、推理容易"，但"I/O 并发效率低"；用多线程能并发，但代价是线程开销、GIL 限制、内存占用、加锁复杂度**。

这个矛盾在"高并发 I/O"场景里被放大到不可忽视：
- 网关 / 代理服务动辄同时 hold 住几万连接。
- 爬虫要同时抓几百个页面。
- 实时数据推送要 maintain 大量长轮询。

这些场景下，同步 + 多线程的路子要么资源扛不住、要么代码复杂度扛不住。于是就有了协程——**单线程 + 事件循环 + I/O 处让出 CPU**，既保留了"单线程推理简单、不用加锁"的好处，又拿到了"I/O 并发能力"。下一篇我们就正式进入协程。

## 3. 最佳实践

**不要在 I/O 密集的同步代码里硬扛**

如果一个函数内部要调 3 个相互独立的下游接口，别一个个串行调——这是同步代码里最常见的低效。起码用 `concurrent.futures.ThreadPoolExecutor` 把它们并发起来，把总耗时从"三次累加"压到"最长一次"。这是"在同步框架内"能做的最小改进。

```python
# 不推荐：三个独立接口串行调，耗时累加
def get_order_slow(order_id):
    user = requests.get(f"{API}/users/{order_id}").json()
    order = requests.get(f"{API}/orders/{order_id}").json()
    logistics = requests.get(f"{API}/logistics/{order_id}").json()
    return {**user, **order, **logistics}

# 推荐（同步框架内的最小改进）：用线程池并发三个独立调用
from concurrent.futures import ThreadPoolExecutor

def get_order_faster(order_id):
    with ThreadPoolExecutor(max_workers=3) as pool:
        f_user = pool.submit(requests.get, f"{API}/users/{order_id}")
        f_order = pool.submit(requests.get, f"{API}/orders/{order_id}")
        f_logi = pool.submit(requests.get, f"{API}/logistics/{order_id}")
        user = f_user.result().json()
        order = f_order.result().json()
        logistics = f_logi.result().json()
    return {**user, **order, **logistics}
```

理由：三个调用相互独立，没有数据依赖，没有并发就纯属浪费。`ThreadPoolExecutor` 的写法改动量很小，但能把耗时从 3 倍压到 1 倍。如果后续要更进一步，就上协程。

**线程池不是越大越好**

`max_workers` 不是越大越快。线程数过多会带来切换开销和内存占用。经验值：**I/O 密集任务，线程数大致设为"并发 I/O 数"的上界即可，常见 10~200**；不要再往上堆，堆到几千就得考虑协程了。CPU 密集任务用 `ProcessPoolExecutor`，进程数 ≈ CPU 核心数。

```python
# 不推荐：盲目开大线程池
with ThreadPoolExecutor(max_workers=1000) as pool:
    ...

# 推荐：按实际并发 I/O 数设
with ThreadPoolExecutor(max_workers=20) as pool:
    ...
```

**CPU 密集别用多线程，用多进程**

一旦任务的瓶颈是算而不是等，多线程因为 GIL 几乎拿不到加速。这时候要么用 `multiprocessing` / `ProcessPoolExecutor`，要么老老实实单线程 + 优化算法。把多线程寄希望于"CPU 也能并行"是 GIL 下最常见的误判。

```python
# 不推荐：CPU 密集用多线程，GIL 下不并行
threads = [threading.Thread(target=heavy_compute) for _ in range(8)]

# 推荐：CPU 密集用多进程，绕开 GIL
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(max_workers=8) as pool:
    ...
```

**别在主线程里 `time.sleep` 等长期事件**

`time.sleep` 是阻塞调用，在主线程（尤其是有 UI、有事件循环需要驱动的场景）里 long-sleep 会"冻住"整个程序。如果要"过一会儿做某事"，用定时器或事件循环提供的非阻塞等待；在异步代码里用 `asyncio.sleep`，它不会阻塞线程。

**共享数据访问必须想清楚要不要加锁**

多线程下但凡有共享可变状态，就要问一句"两个线程会不会同时碰它"。会碰就要加锁，而且锁的粒度要恰当：太粗会压并发，太细会死锁。如果可以用 `queue.Queue`、`threading.local` 这类"天然线程安全"的封装，优先用它们，少自己 `Lock`。

```python
# 推荐：用线程安全队列在线程间传数据，少自己加锁
import queue
q: queue.Queue = queue.Queue()
# 生产者 q.put(item)；消费者 q.get()——内部已加锁
```

**识别"阻塞点"是迈向异步的第一步**

学会在看代码时本能地标注阻塞点：每个 `requests.get`、`urllib.urlopen`、`f.read()`、`time.sleep`、`db.query`、`subprocess.run` 都是潜在阻塞点。这是后面理解协程"在阻塞点让出 CPU"的基础——协程无非是把这些阻塞点换成"非阻塞 + 事件通知"。

**给后续迁移留余地**

如果一个同步模块大概率以后要改异步，提前做两件事能少很多坑：一是把 I/O 调用集中封装在一层"数据访问"函数里，业务逻辑只调这层、不直接碰 `requests`；二是确保每个阻塞点都配了超时参数（`timeout=`），不要让一次卡死的下游把整个线程永久占住。迁移到协程时，只要替换这一"数据访问层"的实现（同步版 → 异步版），业务逻辑几乎不动。

**常见误区：多线程能"加速一切"**

很多人把多线程当成万能加速器，但它只在 I/O 密集场景有效。记住两个反例：
- CPU 密集任务用多线程，因为 GIL，并不会快，甚至因为切换开销变慢。
- 单次 I/O 极轻（微秒级）的任务用线程池，切换开销会吃掉并发收益。

判断标准很简单：任务的主要时间是"等"还是"算"——等的就适合并发（多线程或协程），算的就要么多进程、要么优化算法。

## 4. 原理

### 4.1 阻塞式系统调用如何让线程进入内核等待态

要从根上理解"阻塞"，得看到一次阻塞调用在操作系统层面发生了什么。以一次网络读 `socket.recv` 为例：

1. Python 调用 `sock.recv(bufsize)`，最终走到 C 层的 `recv(fd, buf, len, flags)` 系统调用，触发用户态 → 内核态切换。
2. 内核检查这个 socket 的接收缓冲区：如果没有数据可读（且 socket 是阻塞模式），内核不会让系统调用立刻返回，而是把当前线程的状态从"运行态"改成"睡眠态"（TASK_INTERRUPTIBLE），并把它挂到这个 socket 的等待队列上。
3. 调度器从 CPU 上撤下这个线程，去运行下一个就绪线程。被撤下的线程在操作系统看来就是"不可运行"，不占用 CPU 时间片。
4. 过了若干毫秒，网卡收到对端发来的数据包，触发了硬件中断；内核在中断处理里把数据拷进 socket 的接收缓冲区，并唤醒"挂在这个 socket 等待队列上的所有线程"——即把上面那个线程重新标记为"就绪态"。
5. 调度器在下一轮调度时把这个线程重新放回 CPU，`recv` 系统调用返回，Python 层拿到数据，继续往下执行。

这就是"阻塞"的完整路径：**线程睡着，CPU 去干别的，数据到了再被唤醒**。`time.sleep` 的原理类似——内核用定时器（高精度定时器 / hrtimer）把线程挂起，定时器到期后再唤醒。文件读 `f.read()` 在阻塞模式下也是这套逻辑（磁盘 I/O 完成后由磁盘控制器中断唤醒）。

关键点：在这段"睡眠"时间里，**线程虽然不占 CPU，但它作为执行流还占着内存（栈）、还占着线程表项、还在调度器视野里**。这就是为什么"线程被阻塞"并不等于"线程没有成本"——它是一个躺着的资源。

**阻塞 vs 非阻塞 vs 同步 vs 异步**

这四个词经常被混用，钉死它们的含义：

- **阻塞 / 非阻塞**：描述的是**系统调用**的行为——调用方是否会原地等。"阻塞"= 调用方原地等结果；"非阻塞"= 调用方不等，立刻返回（没数据也返回，通常返回 EAGAIN）。
- **同步 / 异步**：描述的是**调用方与被调方的时间线耦合关系**。"同步"= 调用方等被调方做完、主动取结果；"异步"= 调用方不等，被调方做完后通过回调/事件/Future 通知。

常说的"同步阻塞"= 调用方原地等 + 系统调用会阻塞。常说的"异步非阻塞"= 调用方不等 + 系统调用立刻返回、由事件机制通知完成。组合还有"同步非阻塞"（轮询非阻塞 socket）和"异步阻塞"（少见），但工程里常用的就是前两种。

### 4.2 CPU 时间片空转与浪费

从 CPU 视角看同步阻塞的痛：CPU 的时间是被调度器切成一片一片分给各线程的（时间片，典型几毫秒到几十毫秒）。当一个线程的时间片还没用完，它就执行了一个阻塞调用被挂起，CPU 只能立刻切到下一个线程；如果下一个线程也很快阻塞、再下一个也阻塞……在最坏情况下，CPU 把时间片切来切去，但每个线程都在等 I/O，没有谁在真正"算东西"。这时候 CPU 的利用率看起来低，但实际上调度器很忙——忙着在"等 I/O 的线程"之间来回切换。

更极端的同步场景是单线程：线程阻塞了，整个 CPU 核心就闲着（或在跑别的进程）。我们前文看到的"3 个接口要 3 秒"就是这样：单线程里第一个请求阻塞 1 秒，这 1 秒这个 CPU 核心没有为这个进程做任何有用的工作；第二个请求阻塞的第 2 秒、第三个的第 3 秒，同理。**从应用代码的视角，这 2 秒就是纯浪费**。

事件驱动模型之所以能"榨干"这 2 秒，靠的就是：**在第一个请求阻塞的那 1 秒里，事件循环不是睡死，而是去看其它关注中的 I/O 是否就绪了**——如果第二个请求的 socket 已经可以发数据了，事件循环就让"协程B"去发；写到一半又要等响应，协程B 把控制权交回事件循环，再去跑协程C……于是在同一个 1 秒里，三个请求都被推到了"等待响应"的阶段，最终一起被唤醒。这就是协程"榨干 I/O 等待时间"的本质。

**量化"浪费"的大小**

一个直观的量化：假设一个 I/O 任务 95% 的时间在等、5% 的时间在算，那理论极限加速比是 1/(1-0.95) = 20 倍。同步串行跑这种任务，CPU 利用率只有 5%；并发跑（线程或协程）能把利用率顶到接近 100%。反过来说，如果任务 95% 在算、5% 在等，理论极限加速比就只有 1.05 倍，并发收益很有限——这也是"Amdahl 定律"的一个直觉化应用：并发能力受限于任务中"必须串行"部分的比例。I/O 密集任务之所以适合并发，正是因为它的"必须串行 CPU"部分占比极小。

### 4.3 线程切换的内核态开销

线程切换（context switch）是阻塞模型绕不开的成本。一次切换大致做这些事：

1. **用户态 → 内核态**：线程被时钟中断或阻塞调用带入内核态，CPU 模式从用户态切到内核态，切换页表基地址（用户进程页表 vs 内核页表，部分架构可共享）。
2. **保存当前线程上下文**：把当前线程的全部寄存器（通用寄存器、栈指针、程序计数器、状态寄存器、浮点寄存器等）保存到它的内核栈或线程控制块里。
3. **调度器决策**：调度器从就绪队列里挑下一个要跑的线程（CFS 等算法）。
4. **恢复下一个线程上下文**：把下一个线程之前保存的寄存器值恢复回 CPU。
5. **可能的 TLB 刷新 / cache 失效**：如果切换的是不同进程的线程，页表变了，TLB 要刷；即便同进程，L1/L2 cache 里缓存的数据也可能因新线程访问不同内存而失效。
6. **内核态 → 用户态**：返回用户态继续执行新线程。

这一整套流程都是内核在干，开销在微秒级到几十微秒。看起来很小，但量大了就累加：一个有 1000 个线程的进程，如果每个线程都在频繁阻塞/唤醒，每秒可能产生上万次切换，CPU 的一个核心就会被切走相当一部分时间。

**协程切换为什么便宜得多**

**协程的切换完全是另一回事**：协程的切换不进内核，全在用户态——事件循环只是把当前协程的寄存器/栈状态保存到一个数据结构里，恢复另一个协程的状态，然后跳过去执行。没有系统调用、没有模式切换、没有 TLB 刷新。一次协程切换在几十纳秒到微秒级，比线程切换快一到两个数量级。这是协程在高并发下开销低的根本来源。

具体一点：Python 协程的切换点是 `await`，CPython 在这里把当前协程"挂起"，状态保存在协程对象（一个 Python 对象）里，然后把控制权交给事件循环（`asyncio` 的 `Task` 调度）；事件循环挑下一个就绪协程恢复执行，整个过程没有系统调用、没有内核参与。对比"OS 线程挂起→内核睡眠→中断唤醒→内核恢复"这条重链路，协程的切换链路是"对象状态保存→函数跳转"，轻量得多。

### 4.4 CPython GIL 对多线程 CPU 并发的限制

GIL 是 CPython 解释器为了简化内存管理而引入的一把进程级互斥锁。它的规则：**任意时刻只有一个操作系统线程能持有 GIL，从而只有一个线程能执行 Python 字节码**。

**为什么要有 GIL**

CPython 的内存管理（引用计数）不是线程安全的，如果没有 GIL，多个线程同时修改对象的引用计数就会出竞态。CPython 选择了"一把大锁保平安"的实现路线——所有线程共享一把 GIL，谁跑字节码谁拿它。这也让 C 扩展的集成简单很多。

**GIL 对 I/O 的处理**

CPython 在调用阻塞式 I/O 系统调用前会释放 GIL（`Py_BEGIN_ALLOW_THREADS` 宏），I/O 完成后再重新获取。所以 I/O 等待期间其它线程能跑——上面 3 线程 sleep 能压到 1 秒就是这个机制。

**GIL 对 CPU 的处理**

纯 CPU 工作时不释放 GIL，CPython 以 `sys.setswitchinterval`（默认 5ms）为周期强制让线程释放 GIL 给其它线程。但即便放了，也只是"轮流跑"，不是"并行跑"——任意时刻仍然只有一个线程在执行字节码。所以多线程跑 CPU 密集任务拿不到多核加速，要并行只能多进程。

**GIL 的释放时机细节**

GIL 释放主要在三处：
1. **I/O 阻塞前**：通过 `Py_BEGIN_ALLOW_THREADS` 主动释放，让其它线程在 I/O 等待期间能跑。
2. **定时强制释放**：`sys.setswitchinterval` 设定的间隔到期后，持有 GIL 的线程会检查"有没有别的线程在等 GIL"，有就释放、给别的线程机会。
3. **C 扩展里**：写得规范的 C 扩展在执行耗时纯 C 计算前应释放 GIL，否则会卡住其它线程。

这解释了一个现象：为什么有些 C 扩展（如 NumPy 的部分 BLAS 调用、 Pillow 的图像编解码）能在多线程下跑出并行加速？因为它们在 C 层释放了 GIL，多个线程能在 C 代码段里真正并行。但这要求扩展作者自觉遵守规范，不是 Python 语言保证的。

**对协程的意义**

协程跑在单线程内，根本不存在"多线程争用 GIL"的问题——因为只有一个线程，GIL 只是它自己持有的，不影响并发能力。协程的并发能力来自"事件循环切任务"而不是"多线程并行"。所以协程在 I/O 密集场景里完美绕开了 GIL 的限制。

**为什么是 CPython 才有 GIL**

GIL 不是 Python 语言的固有特性，而是 CPython 实现的选择。PyPy 也有 GIL（实现策略类似）。Jython、IronPython 没有 GIL，因为它们跑在 JVM / CLR 上、用的是各自平台的内存管理和线程模型。目前主流使用的是 CPython，所以 GIL 是 Python 开发者必须了解的现实。PEP 703 提案正在尝试给 CPython 引入"无 GIL"的可选模式（free-threaded），Python 3.13 起作为实验特性提供。即便无 GIL 版本成熟，多线程在 I/O 并发上的"栈开销大、切换开销大、加锁复杂"等结构性问题依然存在——所以协程在 I/O 并发场景的优势不会因为 GIL 消失而被推翻。

### 4.5 I/O 密集场景下线程数与切换开销的权衡

在 I/O 密集场景下，线程数要选得"刚好够并发覆盖 I/O 等待"，而不是"越多越好"。权衡逻辑大致这样：

- 如果并发 I/O 数为 N、每次 I/O 平均等待 W 秒、平均 CPU 处理 C 秒。要让"CPU 不闲着、I/O 不排队"，理想线程数 ≈ N（每个 I/O 配一个线程去等）。
- 但线程数太大会让切换开销爆炸。设每秒切 K 次、每次切换开销 s 秒，则 CPU 被切换吃掉的比例是 K×s。线程数越多、K 越大，切到点 s 也可能因 cache 失效而变大，最终可能"切的开销比干活还多"。
- 内存也限制了线程数：每线程栈 8MB（默认）、加线程控制块，1 万线程 ≈ 几十到几百 MB。

所以工程上 I/O 密集多线程的线程池通常在十~几百级别，靠排队应对瞬时高峰；再大就只能往异步走了。

**Little's Law 的直觉**

排队论里的 Little's Law：驻留系统的并发单元数 = 到达速率 × 平均逗留时间。把它套在 I/O 服务上：如果每秒来 1000 个请求、每个请求逗留 0.1 秒（其中 0.08 秒在等 I/O），那稳态下同时有 100 个请求"在路上"。用多线程要 hold 住这个并发度，需要 ~100 个线程；用协程只需要 ~100 个协程对象，内存和切换开销差两三个数量级。这就是协程"能 hold 住更高 QPS"的理论支撑——不是因为协程"算得快"，而是它"每个并发单元的成本低"。

**协程如何绕开这个权衡**

协程绕开线程权衡的方式：协程的"切换"在用户态微秒以下，栈几 KB、可复用，所以单线程 hold 住几万到几十万协程是常态。这是在"高并发 I/O"场景下协程结构性地优于多线程的原因——不是"协程更聪明"，而是"协程把每个并发单元的成本压到了线程的千分之一量级"。

### 4.6 为何协程能在单线程用事件循环避免这些开销

把上面几节串起来，协程能"单线程高并发 I/O"的机制就清楚了：

1. **I/O 非阻塞化**：协程把阻塞式系统调用换成"非阻塞 I/O + 事件通知"（epoll/kqueue/IOCP）。发起 I/O 时不睡死，而是把"谁来收尾"登记到事件循环，然后函数主动让出 CPU。
2. **协作式调度**：协程跑在单线程里，事件循环是唯一的调度者。当一个协程遇到 I/O 让出时，事件循环挑另一个"已就绪"的协程接着跑——这个切换在用户态、无系统调用、无锁。
3. **无 GIL 牵制**：I/O 并发不需要多个线程并行执行字节码，单线程一个时刻跑一个协程就够了，GIL 不构成限制。
4. **无锁并发**：同一时刻只有一个协程在跑字节码，协程之间的共享数据访问天然互斥（协作式调度），大部分情况下不需要加锁。
5. **栈可压缩**：协程不是操作系统线程，它的"栈"由 Python 运行时管理、可按需增长，单个协程内存占用几 KB；而线程栈是 OS 分配的、通常 MB 级。

这五点合起来，就是协程"用单线程扛住高并发 I/O、且开销远低于多线程"的全部秘密。代价是：代码要写成"协程风格"（`async def`、`await`），I/O 库要选异步版本（`aiohttp` 而非 `requests`、`aiomysql` 而非 `pymysql`），调用栈不再像同步代码那样线性——这些是后续笔记要展开的内容。

**事件循环在 OS 层靠什么**

事件循环的底层是操作系统提供的"I/O 多路复用"系统调用：Linux 的 `epoll`、macOS/BSD 的 `kqueue`、Windows 的 `IOCP`。它们的共同特点是**能在一个系统调用里同时盯住上千个文件描述符，返回"哪些已经就绪"**——这是单线程能"同时关注"海量 I/O 的根本。一个线程调用一次 `epoll_wait`，内核一次性告诉它"这 50 个 socket 有数据可读了、那 3 个可写了"，事件循环就分别去唤醒对应的协程。这一步是进内核的系统调用，但一次调用能批量处理多个事件，远比"一个 I/O 配一个线程、各自阻塞各自"高效。

`asyncio` 在 Python 层做了抽象：把"协程的让出/恢复" + "事件循环的调度" + "底层 epoll/kqueue 的封装"组合起来，让开发者用 `async/await` 的语法写起来像同步代码、底层却能拿到事件驱动的并发能力。这正是"异步代码读起来像同步、跑起来像事件驱动"的根本。

## 5. 总结

- **同步阻塞**是系统调用默认行为：I/O 时线程被内核挂起、CPU 空等，从单线程视角"时光静止"。
- **同步/异步 vs 阻塞/非阻塞**：前者描述调用方与被调方时间线是否耦合，后者描述系统调用是否原地等；常说的"同步阻塞"和"异步非阻塞"是两对正交概念在工程上的两种常见组合。
- **串行 I/O 耗时线性累加**：N 个各 1 秒的独立请求串行 = N 秒，哪怕它们彼此无依赖。
- **阻塞期间 CPU 闲着**：I/O 等待和 CPU 计算无法重叠，单线程白白浪费等待时间。
- **`time.sleep` 冻住线程**：不是"程序停一下"，是"执行流整个被挂起"，期间什么都做不了；`asyncio.sleep` 是另一回事——它让出 CPU，不冻线程。
- **多线程能绕过 I/O 阻塞**：让多个线程各自阻塞，从而并发等待多个 I/O，把累加耗时压到最长那次。
- **多线程代价一：线程切换开销**——上下文切换全在内核态，微秒到几十微秒，海量小任务下会被切到比干活还慢。
- **多线程代价二：GIL 限制 CPU 并发**——任意时刻只有一个线程跑字节码，CPU 密集任务拿不到多核加速；CPU 密集要并行得用多进程。
- **多线程代价三：资源占用**——每线程栈 MB 级，上万线程吃掉几百 MB，调度器不堪重负。
- **多线程代价四：竞态要加锁**——共享数据要锁，锁带来性能下降、死锁风险、心智负担；死锁不报错只卡死，最阴险。
- **阻塞式 vs 事件驱动**：前者每个任务一个执行流、I/O 时阻塞；后者一个执行流关注多 I/O、就绪时处理，开销低且无锁；事件循环底层依赖 epoll/kqueue/IOCP 一次批量返回就绪事件。
- **根本矛盾**：同步代码"写起来直观但 I/O 并发效率低"，多线程能并发但代价高。高并发 I/O 场景下这个矛盾不可忽视。
- **协程是更优解**：单线程 + 事件循环 + I/O 处让出 CPU，既绕开线程开销与 GIL 牵制，又拿到 I/O 并发能力，且大部分场景无需加锁，单进程可 hold 住十万级并发单元。

读完本篇你应能：

- 说清楚"阻塞"在系统调用层面发生了什么：线程为何被挂起、CPU 为何空等、唤醒由谁触发。
- 区分"同步/异步"和"阻塞/非阻塞"两对概念，不再混用。
- 解释 N 个各 1 秒的同步 I/O 为什么总耗时是 N 秒，以及为什么多线程能把它压到 1 秒。
