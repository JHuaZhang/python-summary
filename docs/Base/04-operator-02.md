## 1. 介绍

### 1.1 为什么单独讲除法与整除

在《算术运算符》里已经介绍过 `/` 与 `//` 的基本规则,但这两个运算符的差异远不止"一个出小数、一个出整数"那么简单——它们在**返回类型、负数行为、精度表现、与 `%` 的耦合、对索引和累加的影响**上各有陷阱,是新手从 C/Java 迁来后最容易写错的一组运算符。把它单独拎出来深入对比,是因为除法是数值计算里出现频率最高、出错代价最大的运算:分页算偏移、统计求均值、时间换算、坐标取整,几乎处处是除法,而 `/` 与 `//` 用错一处,轻则结果带个 `.0` 导致后续 `TypeError`,重则负数取整方向反了,分页越界、区间算偏。

Python 把"取精确商"(`/`)与"取整数商"(`//`)拆成两个独立运算符,这是它相对 C/Java 的一个关键设计决策。C/Java 只有一个 `/`,它的行为随操作数类型漂移(整数相除截断、含浮点则真除),本是"语义重载陷阱"的来源。Python 3 通过 PEP 238 让 `/` 语义单一(永远真除、永远 float),把"取整数商"彻底交给 `//`。这篇的目标,就是把这条设计带来的全部后果——以及两者在每个维度上的具体差异——讲透,让你在任何场景都能毫不含糊地选对运算符。

```python
print(7 / 2)      # 3.5   真除:精确小数商
print(7 // 2)     # 3     整除:整数商(向下取整)
print(-7 / 2)     # -3.5
print(-7 // 2)    # -4    整除对负数"更负",不是 -3!
print(8 / 2)      # 4.0   真除即便整除也是 float
print(8 // 2)     # 4     整除全 int 返回 int
```

先看这张"一句代码见差异"的对比:同样是 `7` 和 `2`,`/` 给 `3.5`、`//` 给 `3`;同样的 `8` 和 `2`,`/` 给 `4.0`、`//` 给 `4`——多出的那个 `.0` 不是小事,它意味着类型从 `int` 变成了 `float`,而 `float` 不能做列表索引、不能参与精确的整数逻辑。这就是为什么必须分清两者。

### 1.2 一句话区分

先用最简练的方式锚定两者的本质:

- **`/`(真除,true division)**:执行数学上精确的除法,返回**完整的商**(含小数部分),结果**永远是 `float`**。它回答的是"除完到底等于多少"。
- **`//`(整除,floor division)**:执行除法后取**整数部分**,向**负无穷**地板取整,结果类型"全 int 返回 int、有 float 返回 float"。它回答的是"能完整分成几份"。

```python
# / 回答"等于多少"——精确商
print(17 / 5)     # 3.4   —— 5 份分 17,每份 3.4

# // 回答"能分成几整份"——整数商
print(17 // 5)    # 3     —— 17 里能凑出 3 个完整的 5(余 2)
```

记忆要点:`/` 是"求值",`//` 是"求份数"。需要小数精度用 `/`,需要整数计数用 `//`。这两个心智模型分清,大半的误用就避免了。

### 1.3 两者差异总览表

下面这张表是本篇的总纲,后续每一节围绕表的每一行展开。先建立全局对照。

| 维度 | `/` 真除 | `//` 整除 |
|------|----------|-----------|
| 结果值 | 精确商(含小数) | 整数商(向负无穷取整) |
| 返回类型 | 永远 `float` | 全 int→`int`,有 float→`float` |
| `8 / 2` / `8 // 2` | `4.0` | `4` |
| `-7 / 2` / `-7 // 2` | `-3.5` | `-4`(向负无穷,不是 -3) |
| 能否做列表索引 | ❌ `float` 不能 | ✅ `int` 可以(全 int 操作数时) |
| 与 `%` 的关系 | 无直接等式约束 | 满足 `a == (a//b)*b + a%b` |
| float 精度影响 | 直接表现误差 | 取整前先真除,误差可能让结果偏一格 |
| 除以零 | `ZeroDivisionError` | `ZeroDivisionError` |
| 典型场景 | 均值、比例、概率 | 分页、取整计数、时间换算 |

这张表把两者的全部差异维度列齐了。其中**返回类型**和**负数取整方向**是两个最容易踩坑的维度——前者决定结果能不能用,后者决定负数下结果对不对。后续章节逐一深入。

## 2. 核心内容

本章逐维度对比 `/` 与 `//`,每节遵循"规则 → demo → 陷阱 → 场景"展开。重点是返回类型规则、负数取整方向、float 精度叠加、与 `%`/`divmod` 的配合,因为它们最易在生产代码出问题。

### 2.1 返回类型的根本差异

这是 `/` 与 `//` 最本质、也最容易被忽略的差异:**`/` 的返回类型是固定的 `float`,与操作数无关;`//` 的返回类型跟随操作数**。

```python
# / 永远 float,无论操作数是什么
print(type(7 / 2))      # <class 'float'>
print(type(8 / 2))      # <class 'float'> —— 整除也 float!
print(type(8.0 / 2))    # <class 'float'>
print(type(8 / 2.0))    # <class 'float'>

# // 跟随操作数:全 int 返回 int,有 float 返回 float
print(type(7 // 2))     # <class 'int'>     —— 全 int → int
print(type(8 // 2))     # <class 'int'>
print(type(7.0 // 2))   # <class 'float'>   —— 有 float → float
print(type(7 // 2.0))   # <class 'float'>
print(type(7.0 // 2.0)) # <class 'float'>
```

关键认知:`8 / 2` 是 `4.0`(`float`),`8 // 2` 是 `4`(`int`)。看起来只差一个 `.0`,但类型不同,行为就不同——`float` 不能做列表索引、不能做 `dict` 的逻辑键判断、`isinstance(x, int)` 为 `False`。这条"多出来的 `.0`"是从 C 迁来的开发者最常忽视的:在 C 里整数除法 `8/2` 得 `int 4`,而在 Python 用 `/` 会得 `float 4.0`。

⚠️ **高频陷阱:`/` 的结果不能做索引**

```python
data = [10, 20, 30, 40]
mid = 4 / 2              # 2.0 —— float!
# data[mid]              # TypeError: list indices must be integers, not float
mid = 4 // 2            # 2 —— 用 // 得 int
print(data[mid])        # 30 —— 正常
```

任何"算完位置去取元素"的场景(二分查找、分页取中点、切片边界),必须用 `//` 得到 `int`,用 `/` 得到 `float` 会直接 `TypeError`。这是 `/` vs `//` 最典型的运行时错误。

⚠️ **`//` 含 float 时返回 float,值是整数但类型不是**

```python
x = 7.0 // 2            # 3.0 —— 值是整数,但类型是 float
print(x, type(x))       # 3.0 <class 'float'>
# data[x]               # 同样 TypeError!float 不能做索引,即便值是 3.0
```

`//` 只有在**两个操作数都是 int** 时才返回 int;只要有一个 float,结果就是 float——即便值恰好是整数,类型仍是 float,照样不能做索引。需要 int 索引时,要么保证操作数全 int,要么对结果 `int()` 显式转换:`int(7.0 // 2)`。

**记忆口诀**:`/` 一定 float,`//` 看"有没有 float 掺和"。

### 2.2 取整方向的差异:真除不分方向,整除向负无穷

这是两者在**负数**下分道扬镳的地方,也是从 C/Java 迁来者最易写错的核心。

`/` 没有取整动作,它给出精确商,所以负数下没有方向问题——商是几就是几:

```python
print(-7 / 2)     # -3.5   —— 精确,无方向
print(7 / -2)     # -3.5
print(-8 / 2)     # -4.0   —— 恰好整除,但仍是 float
print(7 / -3)     # -2.333...
```

`//` 要取整,而它取整的方向是**向负无穷(floor)**,不是向零截断。这是 Python 与 C/Java 整数除法的根本分歧:

```python
print(7 // 2)     # 3    —— 3.5 向负无穷 = 3(正数,与 C 相同)
print(-7 // 2)    # -4   —— -3.5 向负无穷 = -4(C/Java 是 -3,向零截断!)
print(7 // -2)    # -4   —— -3.5 向负无穷 = -4
print(-7 // -2)   # 3    —— 3.5 向负无穷 = 3
```

理解这条规则:`-7 // 2` 的精确商是 `-3.5`,向负无穷取整要找"不大于 -3.5 的最大整数",也就是 `-4`(因为 `-4 < -3.5 < -3`)。而 C/Java 的整数除法是向零截断,直接丢掉小数部分得 `-3`。两者差 1。

**用一张图直观对照**(以 `-7 ÷ 2` 为例):

```
数轴:   ... -5   -4   -3   -2   -1    0    1 ...
                    ↑    ↑
                    │    └─ 截断(C/Java):-3.5 丢小数 → -3
                    └────── 地板(Python //):-3.5 向负无穷 → -4
```

`-3.5` 落在 `-4` 和 `-3` 之间。C 的截断"往零的方向走"(向右)到 `-3`;Python 的地板"往负无穷走"(向左)到 `-4`。这就是 `-7 // 2 == -4` 的几何含义。

⚠️ **负数整除陷阱实例:分页向下取整 vs 向上取整**

```python
# 计算第 n 个元素落在第几页(每页 size 个)
def page_of(index, size):
    return index // size       # 地板除,负数下"更负"

# 正常:第 7 个元素,页大小 5 → 第 1 页(0 起算)
print(page_of(7, 5))           # 1

# 负索引场景(如从末尾倒数):倒数第 3 个元素
print(page_of(-3, 5))          # -1 —— 地板到 -1,不是 0!
# 若期望"负索引也归到第 0 页",这里就错了,需另行处理
```

负数下 `//` 的"向负无穷"会把本该归到某一页的边界值推到更小的页号。处理含负数的区间/分页时,务必先用具体负数测一遍 `//` 结果,确认方向符合业务预期。

**记忆要点**:`/` 无方向(精确),`//` 永远往负无穷方向拉(负数时比截断再小 1)。

### 2.3 整除与取余的耦合:`a == (a//b)*b + a%b`

`//` 与 `%` 是一对,它们共同满足一条严格的数学不变量:**对任意 `a, b`(b≠0),`a == (a // b) * b + (a % b)` 恒成立**。`/` 没有这条约束(它不取整,无余数概念)。理解这条等式,就理解了 `//` 在负数下的全部行为——它的取整方向决定了 `%` 的余数符号。

```python
# 验证等式(正数)
a, b = 17, 5
print(a // b, a % b)                      # 3 2
print(a == (a // b) * b + a % b)          # True —— 17 == 3*5 + 2

# 验证等式(负数,关键!)
a, b = -17, 5
print(a // b, a % b)                      # -4 3
print(a == (a // b) * b + a % b)          # True —— -17 == (-4)*5 + 3
```

`-17 // 5` 为何是 `-4` 而非 `-3`?因为精确商 `-3.4` 向负无穷取整是 `-4`;相应地,要让等式成立,余数必须是 `3`(`(-4)*5 + 3 = -17`)。所以 `%` 在负数下的余数与**除数**同号,这是 `//` 地板取整的数学推论——两者是绑定的,改不了其中一个而不改另一个。

⚠️ 对比 C/Java:C 的整数除法向零截断(`-17 / 5 = -3`),相应的余数与**被除数**同号(`-17 % 5 = -2`,因为 `-3*5 + (-2) = -17`)。从 C 迁来的人常以为 Python 的 `-17 % 5` 也该是 `-2`,实际是 `3`——这就是 `//` 取整方向不同带来的连锁差异。

**用 `divmod` 一次拿到商和余**:`divmod(a, b)` 返回 `(a // b, a % b)` 元组,内部一次算完,符合上述等式,负数也遵循 Python 地板规则:

```python
print(divmod(17, 5))      # (3, 2)
print(divmod(-17, 5))     # (-4, 3) —— 与 //、% 单独算一致
print(divmod(17, -5))     # (-4, -3)
print(divmod(-17, -5))    # (3, -2)
```

`divmod` 适合"同时需要商和余"的场景(分页+偏移、时间换算、进制转换),比 `//` 和 `%` 各算一次更清晰、且底层不重复计算。`/` 不参与这条等式,也没有 `divmod` 式的配套(真除无余数)。

### 2.4 float 精度对两者的不同影响

这是 `/` 与 `//` 在浮点场景下差异最隐蔽的一环:`/` 直接暴露精度误差(意料之中),而 `//` 会先做真除、再取整,中间的浮点误差可能让取整结果**偏离直觉一位**。

**`/` 的精度表现(直接误差)**:

```python
print(0.1 + 0.2)        # 0.30000000000000004 —— / 不取整,误差直接可见
print(1 / 3)            # 0.3333333333333333 —— 有限的近似
print(0.7 / 0.1)        # 6.999999999999999 —— 精度误差(本该是 7)
```

`/` 是"纯真除",误差如实呈现,开发者通常有心理预期。

**`//` 的精度陷阱(误差 + 取整叠加,更隐蔽)**:

```python
print(0.7 // 0.1)       # 6.0 —— 直觉是 7!实际 6
print(0.7 / 0.1)        # 6.999999999999999 —— 真相:0.7/0.1 受误差≈6.999...
# 取整:6.999... 向负无穷 = 6.0
```

`0.7 // 0.1` 得 `6.0` 而非 `7.0`,因为 `0.7 / 0.1` 在 float 里受精度影响是 `6.999...`,`//` 取整后变 `6`。这种"误差 + 取整"的复合陷阱比单纯 `/` 的误差更危险——因为它会让"本该是 7 的整数商"静悄悄变成 6,且没有显眼的 `0.30000000000000004` 提示。

⚠️ **`//` 取整偏一格的更多实例**:

```python
print(1.0 % 0.1)        # 0.09999999999999995 —— 直觉是 0(1.0 是 0.1 的 10 倍)
# 因为 1.0 / 0.1 ≈ 9.999...,// 得 9,余 0.0999...
print(1.0 // 0.1)       # 9.0 —— 不是 10!

print(2.3 // 0.1)       # 22.0 —— 直觉 23,实际 22(2.3/0.1≈22.999...)
print(0.3 // 0.1)       # 2.0 —— 直觉 3,实际 2(0.3/0.1≈2.999...)
```

凡是"用 float 除数做 `//`",都可能因 `0.1`、`0.7` 这类二进制无法精确表示的小数而偏一格。

**规避方案**:

```python
# 方案一:放大成整数单位,用 int 操作数的 //
print(7 // 1)           # 7 —— 把 0.7、0.1 放大 10 倍成 7, 1
scale = 10
print((int(0.7 * scale)) // (int(0.1 * scale)))  # 7 —— 但 int(0.7*10)=7, int(0.1*10)=1
# 注意 0.7*10 本身可能是 7.000000000000001,需先 round
print(round(0.7 * 10) // round(0.1 * 10))        # 7 —— round 后再 //

# 方案二:用 Decimal 精确十进制
from decimal import Decimal
print(Decimal('0.7') // Decimal('0.1'))   # 7 —— 精确!无偏移
print(Decimal('0.7') % Decimal('0.1'))    # Decimal('0.0') —— 余数也精确
```

需要"精确的整数商"时,**绝不要直接对 float 用 `//`**:要么放大成 int 单位(配合 `round` 消除乘法误差),要么用 `decimal.Decimal`(须字符串构造)。`/` 的误差至少可见,`//` 的偏移却会伪装成正确的整数,更具欺骗性。

### 2.5 `//` 与 `math.floor` 的关系

`//` 的"向负无穷取整"本质就是 `math.floor`,但两者在使用形式与返回类型上有差别,值得厘清。

```python
import math
# 全 int 操作数:// 等价于 floor,但 // 返回 int,floor 也返回 int
print(7 // 2)            # 3
print(math.floor(7 / 2)) # 3 —— 先 / 得 3.5,再 floor 得 3

# 负数完全一致
print(-7 // 2)           # -4
print(math.floor(-7 / 2))# -4 —— floor(-3.5) = -4
```

`a // b`(全 int)与 `math.floor(a / b)` 在**值**上完全等价——都向负无穷取整。差别在:

- **形式**:`//` 是运算符,直接作用于两数;`math.floor` 是函数,接受一个值(通常先 `/`)。
- **类型**:`//` 全 int 返回 int;`math.floor` 接受 float 返回 int(3.x 起 `floor` 返回 int,2.x 返回 float)。
- **float 行为**:`x // y`(含 float)是"先真除再 floor",而 `math.floor(x / y)` 也是"先真除再 floor",两者一致——都会受 float 精度影响偏一格。

```python
print(0.7 // 0.1)             # 6.0 —— // 受误差
print(math.floor(0.7 / 0.1))  # 6   —— floor 同样受误差(先 / 再 floor)
```

所以 `//` 在含 float 时与 `math.floor(a/b)` **行为一致**(都偏),换 `math.floor` 不能解决 float 误差问题。要精确还得用 int 单位或 Decimal。

⚠️ 还有一组相关的取整函数,与 `//` 的"向负无穷"不同:

```python
import math
print(math.floor(-3.5))   # -4 —— 向负无穷(与 // 一致)
print(math.trunc(-3.5))   # -3 —— 向零截断(与 C 整数除法一致)
print(int(-3.5))          # -3 —— int() 也是向零截断
print(math.ceil(-3.5))    # -3 —— 向正无穷(天花板)
```

当你**想要 C 风格的截断整数商**(向零,而非 Python `//` 的向负无穷),可以组合 `int(a / b)` 或 `math.trunc(a / b)`:

```python
print(int(-7 / 2))        # -3 —— 截断,等价 C 的 -7/2
print(-7 // 2)            # -4 —— Python 地板,不同!
print(math.trunc(-7 / 2)) # -3 —— 截断
```

`int(-7 / 2)` = `-3`(先真除得 -3.5,再向零截断),这正是 C 整数除法的行为。所以"想要 C 风格整数商"的写法是 `int(a / b)`,而非 `a // b`。这条对应关系对从 C 迁代码、或需要"截断语义"的算法(如某些数值算法)很关键。

### 2.5.1 各取整函数的正负数完整对照

把四种取整函数在正负数下的差异一次性列清,这是从 C 迁代码、写数值算法时最常要查的对照表。关键看**正数时是否一致**、**负数时分不分歧**:

| 表达式 | `//`<br>floor | `int()`<br>trunc | `math.floor` | `math.trunc` | `math.ceil` | `round` |
|--------|---|---|---|---|---|---|
| `3.5` | 3 | 3 | 3 | 3 | 4 | 4 |
| `-3.5` | -4 | -3 | -4 | -3 | -3 | -4 |
| `2.5` | 2 | 2 | 2 | 2 | 3 | **2**(银行家) |
| `-2.5` | -3 | -2 | -3 | -2 | -2 | **-2**(银行家) |

```python
import math
# 正数:floor 和 trunc 表现一致
print(3.5 // 1, int(3.5), math.floor(3.5), math.trunc(3.5))  # 3 3 3 3

# 负数:floor 向负无穷(-4),trunc/int 向零(-3) —— 这里分歧!
print(-3.5 // 1, int(-3.5), math.floor(-3.5), math.trunc(-3.5))  # -4 -3 -4 -3

# .5 边界:round 银行家(向偶数),其余按各自方向
print(round(2.5), round(-2.5))   # 2 -2 —— 都向偶数(注意不是 3/-3)
```

从表里读出三个要点:① 正数下 `floor` 与 `trunc` 一致,所以正数场景 `//` 和 `int(a/b)` 不会出错;② 负数下两者分歧,这是 C 迁移的核心坑点;③ `round` 的 `.5` 行为与所有取整函数都不同(银行家),且 `.5` 时受 float 精度干扰不可靠,不能当"四舍五入"用。

⚠️ 还有个细节:`math.floor` 和 `math.trunc` 在 3.x 都返回 `int`(2.x floor 返回 float),与 `int()` 一致;而 `a // b` 的返回类型仍跟随操作数(全 int → int,有 float → float)。所以"要 int 结果"时,`math.floor(a/b)` 比 `a // b`(含 float)更稳——前者一定 int,后者可能 float。

### 2.6 四种"取整除法"对照:floor / trunc / ceil / round

把视野放大,Python 里"除法后取整"其实有多种约定,`//` 只是其中一种(floor)。理解全谱,才能在不同需求下选对。

```python
import math
a, b = -7, 2
print(f"真除      {a}/{b} = {a/b}")            # -3.5
print(f"地板 //   {a}//{b} = {a//b}")          # -4   向负无穷
print(f"截断 int  int({a}/{b}) = {int(a/b)}")   # -3   向零
print(f"天花板    ceil({a}/{b}) = {math.ceil(a/b)}")  # -3  向正无穷
print(f"四舍五入  round({a}/{b}) = {round(a/b)}")     # -2  最近的整数(注意银行家)
```

完整对照(以 `-7 / 2 = -3.5` 为例):

| 约定 | 函数 | 结果 | 方向 |
|------|------|------|------|
| 地板 | `a // b` / `math.floor(a/b)` | -4 | 向负无穷 |
| 截断 | `int(a/b)` / `math.trunc(a/b)` | -3 | 向零 |
| 天花板 | `math.ceil(a/b)` | -3 | 向正无穷 |
| 四舍五入 | `round(a/b)` | -2 | 最近整数(银行家,逢5向偶数) |

注意 `round` 是**银行家舍入**(逢 5 向最近的偶数),`round(2.5)=2`、`round(3.5)=4`,且受 float 精度干扰,详见《float 类型与精度问题》。`round(a/b)` **不是** "四舍五入到整数商"的可靠方式。

**选型指南**:

| 需求 | 用什么 |
|------|--------|
| 精确小数商 | `/` |
| 整数商,向负无穷(分页、份数、Python 惯例) | `//` |
| 整数商,向零截断(C 风格、对称取整) | `int(a/b)` |
| 整数商,向上取整(至少几份) | `-(-a // b)` 或 `math.ceil(a/b)` |
| 整数四舍五入(传统,非银行家) | `Decimal` + `ROUND_HALF_UP` |

**向上取整的技巧**:`//` 是向下(向负无穷),没有现成的"向上取整除法"运算符,但可用负号翻转技巧 `-(-a // b)`(全 int 时):

```python
# 向上取整:每页 size,共 total 个,需要几页
total, size = 17, 5
pages_floor = total // size                 # 3 —— 向下,不够装
pages_ceil = -(-total // size)             # 4 —— 向上,确保装下
print(pages_floor, pages_ceil)             # 3 4
import math
print(math.ceil(total / size))             # 4 —— 或用 ceil(但先 / 得 float)
```

`-(-total // size)` 是纯 int 运算(不引入 float),是"向上取整除法"的经典 idiom;`math.ceil(total / size)` 更直观但会经 float。负数下两者语义需单独验证。分页"总页数"必用向上取整,否则会漏装最后一页。

### 2.7 大整数除法:int 任意精度下的精确性

Python 的 `int` 是任意精度的,这条特性让 `//` 在大整数下保持**精确**,而 `math.floor(a/b)` 这种"先 `/` 得 float 再 floor"的写法会因 float 精度上限而**失真**。这是 `/`-based 取整相对 `//` 的一个硬伤。

```python
big = 10 ** 30
# // 直接对 int 运算,精确
print(big // (10 ** 20))               # 10000000000 —— 准确(10^30 / 10^20 = 10^10)

# 先 / 得 float,大整数精度丢失!
print(int(big / (10 ** 20)))           # 9999999488 —— 错!float 只有 ~15 位有效数字
print(math.floor(big / (10 ** 20)))    # 9999999488 —— 同样错
```

`big` 是 10^30(31 位十进制),远超 float 的 ~15~17 位有效数字。`big / 1e20` 时,`big` 被转成 float 会丢失低位精度,得到 `9.999999488e9` 之类的近似值,再取整就错了。而 `big // 1e20`(全 int)在任意精度 int 上精确算出 `10^10`。

⚠️ 这个陷阱在大数据计数、时间戳(纳秒级)、加密大数运算中很现实:**大整数的整数商必须用 `//`(全 int),绝不用 `int(a/b)` 或 `math.floor(a/b)`**(它们会先把 int 转成 float 丢精度)。

```python
# 推荐:大整数用 //
result = big // divisor               # 精确,任意精度

# 危险:大整数用 int(a/b) 或 floor(a/b)
result_bad = int(big / divisor)       # float 中间值丢精度!
```

这也是为什么 `//` 不能简单地理解为"`math.floor(a/b)` 的简写"——在大整数场景它俩行为完全不同,`//` 才是精确的。理解这一点,就理解了 `//` 作为"运算符直接作用于 int"相对"函数作用于 float 商"的本质优势。

### 2.8 综合示例:`/` 与 `//` 全维度对比

下面这个片段集中演示两者在每个维度的差异,阅读时对照每段的行为:

```python
import math
from decimal import Decimal

print("=== 返回类型 ===")

print(f"7.0//2 = {7.0//2} ({type(7.0//2).__name__})") # 3.0 float

# 9. 除零
print("=== 除零 ===")
```

跑一遍这段示例,对照输出:返回类型与索引可用性、负数取整方向、商余等式、float 精度偏移与 Decimal 修正、四种取整约定对照、向上取整分页、大整数精度差异、除零一致报错——`/` 与 `//` 的完整差异图景就清晰了。核心结论:**要精确小数用 `/`,要整数用 `//`(全 int 精确、负数向负无穷);float 上 `//` 会偏移用 int/Decimal 修正;大整数商必须 `//`;取整方向不对时按需选 int()截断 / ceil 向上 / Decimal 四舍五入**。

## 3. 最佳实践

### 3.1 需要索引用 `//`,需要均值用 `/`,绝不混用

```python
# 推荐:语义匹配
mid = (low + high) // 2          # 二分查找中点,要 int 索引
avg = total / count              # 均值,要小数精度
page = offset // page_size       # 分页页号,要 int

# 不推荐:误用 / 取索引
mid = (low + high) / 2           # float!
data[mid]                        # TypeError: list indices must be integers
```

`/` 永远 float 不能做索引,`//`(全 int)返回 int 可以。任何"算出来的值要当位置/下标/计数"的场景必用 `//`;要小数精确值(均值、比例、概率)用 `/`。把这两个心智模型焊死,能消掉大半除法 bug。

### 3.2 负数除法先测后用,记住"// 向负无穷"

```python
# Python: // 向负无穷,% 余数与除数同号
print(-7 // 2)    # -4 (C 是 -3)
print(-7 % 2)     # 1  (与除数同号)

# 需要 C 风格截断商:用 int(a/b)
print(int(-7 / 2))  # -3
```

写涉及负数的除法/取模前,用具体负数跑一遍 `//` 和 `%`,确认与预期一致。Python `//` 向负无穷、`%` 余数与除数同号,都与 C 不同。需要 C 风格截断语义(向零)用 `int(a / b)`。分页、坐标、时间区间含负数时尤其要测。

### 3.3 float 上的 `//` 会偏一格,改用 int 单位或 Decimal

```python
# 危险:float 精度让 // 偏移
print(0.7 // 0.1)     # 6.0 (直觉 7)

# 推荐:int 单位(配合 round 消除乘法误差)
print(round(0.7 * 10) // round(0.1 * 10))  # 7

# 或用 Decimal(字符串构造)
from decimal import Decimal
print(Decimal('0.7') // Decimal('0.1'))    # 7 精确
```

float 的 `1/0.1 ≈ 9.999...` 让 `//` 取整后偏一格,且伪装成正确整数。需要精确整数商时,放大成 int 单位(先 `round` 消除 `0.7*10=7.000...1` 的误差)或用 `Decimal`(字符串构造)。绝不要对 float 直接 `//` 后与"理论整数"比较。

### 3.4 大整数整数商用 `//`,不用 `int(a/b)` / `math.floor(a/b)`

```python
big = 10 ** 30
divisor = 10 ** 20

# 推荐:全 int //,任意精度精确
result = big // divisor            # 10000000000

# 危险:先 / 得 float,大整数丢精度
result_bad = int(big / divisor)    # 9999999488 错!
result_bad2 = math.floor(big / divisor)  # 同样错
```

`int(a/b)` 和 `math.floor(a/b)` 会先把 int 转成 float(只 ~15 位有效数字),大整数丢精度。`//` 直接在任意精度 int 上运算,精确。大数计数、纳秒时间戳、加密大数运算的整数商,必须用 `//`。这也是 `//` 不能视为 `floor(a/b)` 简写的关键原因。

### 3.5 向上取整分页用 `-(-a // b)`,别漏装最后一页

```python
total, size = 17, 5
# 推荐:向上取整(纯 int,不引入 float)
pages = -(-total // size)         # 4 —— 装下全部
# 或更直观(但经 float)
import math
pages = math.ceil(total / size)   # 4

# 错误:用 // 向下取整会漏页
pages_bad = total // size         # 3 —— 漏装最后 2 个
```

分页"总页数"、装箱"总箱数"等"至少需要几份"的场景必须向上取整。纯 int 用 `-(-a // b)` 技巧(避免 float),或 `math.ceil(a / b)`(更直观但经 float,大数下失真)。负数下两者语义需单独验证。

### 3.6 同时需要商和余用 `divmod`,别分开算

```python
# 推荐:divmod 一次算完
q, r = divmod(17, 5)             # (3, 2)

# 不推荐:// 和 % 各算,底层重复计算
q = 17 // 5
r = 17 % 5
```

`divmod(a, b)` 返回 `(a // b, a % b)` 元组,一次算出商余,符合等式 `a == q*b + r`,负数遵循 Python 地板规则。分页(页号+偏移)、时间换算(时分秒)、进制转换(商+余数)同时需要商余时首选 `divmod`,清晰且不重复运算。

### 3.7 除零必须显式处理,`/` 和 `//` 都会抛错

```python
# 推荐:校验或捕获
if count != 0:
    avg = total / count
else:
    avg = 0

try:
    ratio = a // b
except ZeroDivisionError:
    ratio = 0
```

`/`、`//` 除以零都抛 `ZeroDivisionError`(Python 不像 JS 返回 `Infinity`)。来自用户输入、配置、统计的除数可能为零,必须显式校验或 `try/except`,别假设非零。`b == 0` 和 `b == 0.0` 都会触发。

### 3.8 想要"截断整数商"(C 风格)用 `int(a/b)`,但大数下慎用

```python
# C 风格:向零截断
print(int(-7 / 2))     # -3 —— 截断
print(-7 // 2)         # -4 —— Python 地板

# 大数下 int(a/b) 失真,改用 int(a/b) 的替代
# 若需大数截断商:用 divmod 配合符号修正,或 Decimal
```

算法迁移自 C、或需要对称截断语义(正负数都向零)时,用 `int(a/b)` 得截断商。但注意它经 float,大整数下丢精度——大数截断需用 `Decimal` 或手动按符号处理 `//`。日常小数 `int(a/b)` 够用,大数必须换方案。

### 3.9 `//` 含 float 返回 float,需 int 索引时显式转换

```python
x = 7.0 // 2     # 3.0 (float,值是整数但类型 float)
# data[x]        # TypeError

# 推荐:保证全 int,或显式转
idx = 7 // 2          # 3 int(操作数全 int)
idx = int(7.0 // 2)   # 3 int(显式转换)
```

`//` 只要有一个 float 操作数就返回 float,即便值是整数也不能做索引。需要 int 索引时,要么确保两操作数都是 int,要么对结果 `int()` 显式转换。别被"值是 3.0 看起来像整数"迷惑。

### 3.10 均值/比例类计算用 `/`,接受 float 精度;金额类用 Decimal

```python
# 科学/统计:用 /,float 精度足够
avg = sum(data) / len(data)         # 均值,float
ratio = hits / total                # 命中率,float

# 金额:绝不用 / 或 //,用 Decimal(或 int 存分)
from decimal import Decimal
price = Decimal('49.99')
avg_price = price / 3               # Decimal 精确除法(按上下文精度)
```

`/` 在 float 上有精度误差,科学计算、统计、比例场景通常可接受(精度远超需求)。但金额、利率等精度敏感场景,绝不用 float 的 `/` 或 `//`,改用 `Decimal`(精确十进制)或 `int` 存最小单位。详见《float 类型与精度问题》。

### 3.11 `round(a/b)` 不是可靠的整数舍入,慎用

```python
# round 是银行家舍入(逢5向偶数),且受 float 精度干扰
print(round(2.5))        # 2 (不是 3!)
print(round(0.7 / 0.1))  # 7 (恰好蒙对,但不稳定)

# 需传统四舍五入用 Decimal
from decimal import Decimal, ROUND_HALF_UP
print(Decimal('2.5').quantize(Decimal('1'), rounding=ROUND_HALF_UP))  # 3
```

`round` 是银行家舍入(逢 5 向最近偶数),且受 float 精度干扰,不适合"精确的整数四舍五入"。需要传统四舍五入(逢 5 进 1)用 `Decimal` + `ROUND_HALF_UP`。别把 `round(a/b)` 当作 `//` 的"四舍五入版"用,行为不可预测。

### 3.12 除法运算链式书写要注意返回类型传递

```python
# // 链式:类型会"传染"——一旦中间冒出 float,后续 // 也变 float
print(100 // 5 // 2)         # 10 —— 全 int,链式 // 仍 int
print(100 // 5.0 // 2)       # 10.0 —— 中间 100//5.0=20.0 是 float,后续全 float

# / 与 // 混链:/ 一旦出现就 float,/ / / / 最终 float
print(100 / 5 // 2)          # 10.0 —— 100/5=20.0 float,后续 // 也是 float(值 10.0)
print(100 // 5 / 2)          # 10.0 —— 100//5=20 int,但 /2 得 10.0 float
```

链式除法里,返回类型按"最宽规则"传递:`/` 出现就 float,`//` 含 float 就 float。这会让"本以为是 int 的链式结果"悄悄变 float。需要保证 int 的链式除法,确保全程用 `//` 且操作数全 int;一旦混入 `/` 或 float,结果类型就变了。复杂除法链最好分步写并显式断言类型,别依赖隐式传递。

### 3.13 分页/分桶计算的完整模板

除法在分页、分桶、分块场景用得最多,这里给一个完整可靠的模板,综合 `//`、`%`、`divmod`、向上取整:

```python
def paginate(total, page_size):
    """分页:总页数、最后一页元素数、给定元素所在页与偏移"""
    if page_size <= 0:
        raise ValueError("页大小必须为正")
    if total == 0:
        return 0, 0
    # 总页数:向上取整(确保最后一页不满也计数)
    num_pages = -(-total // page_size)      # 17 // 5 向上 = 4
    # 最后一页元素数:余数为 0 则满页,否则取余
    last_page_count = page_size if total % page_size == 0 else total % page_size
    return num_pages, last_page_count

def locate(index, page_size):
    """第 index 个元素(0 起算)落在第几页、页内偏移"""
    page, offset = divmod(index, page_size) # 一次取商余
    return page, offset

print(paginate(17, 5))   # (4, 2) —— 4 页,最后一页 2 个
print(locate(7, 5))      # (1, 2) —— 第 7 个在第 1 页偏移 2
print(paginate(20, 5))   # (4, 5) —— 恰好整除,最后一页满 5
```

这套模板用 `//` 向上取整算总页数、`%` 算最后一页余量、`divmod` 算元素定位,全程 int 精确无 float。注意 `page_size <= 0` 要显式校验(否则向上取整和取余行为异常),`total == 0` 要单独处理(否则 `-(-0//size)` = 0 但语义"1 页空页"可能不符预期)。这是分页算法的标准范式,记住它可避免绝大多数分页边界 bug。

本章讲清 `/` 与 `//` 行为差异背后的机制:Python 3 真除法决议(PEP 238)为何让 `/` 永远 float、地板除向负无穷的数学一致性、`//` 与 `%` 等式约束的来源、float 精度叠加取整的成因、`//` 相对 `math.floor(a/b)` 在大整数下的精度优势。这些是"两者为何如此不同"的根基。

### 4.1 PEP 238:真除法决议,为何 `/` 永远返回 float

Python 2 时代,`/` 的行为随操作数类型漂移:两个 int 相除做**整数除法**(`7/2` 得 `3`),含 float 才做真除。这让同一运算符有两种语义,是经典的"语义重载陷阱"——本想要小数商,写 `7/2` 却得 `3`,悄悄丢精度;且 `7/2` 的类型不可预测(取决于操作数),违反"运算符语义单一"原则。

PEP 238(Python 3)做了决断:

- **`/` 一律真除,永远返回 float**,语义单一稳定——"要精确商就用 `/`"。
- **`//` 专司整数商(floor division)**,把"取整数商"的职责从 `/` 剥离——"要整数商就用 `//`"。

```python
# Python 2:  7/2 = 3 (int)   7.0/2 = 3.5 (float)   —— 语义漂移
# Python 3:  7/2 = 3.5 (float)   7//2 = 3 (int)   —— 语义单一
```

这个改变消除了"`/` 行为随类型漂移"的陷阱,代价是迁移:Python 2 依赖整数 `/` 的代码在 Python 3 会变 float,可能破坏索引、`isinstance` 等逻辑。为此 Python 2.2+ 提供 `from __future__ import division` 提前切换,3.x 强制执行。

理解这条历史,就理解了"`/` 永远 float"不是随意设计,而是为消除语义重载做的深思熟虑——一致性优先于"看起来更整洁"。这也解释了为何 `8/2` 是 `4.0` 而非 `4`:为了 `/` 语义的绝对单一,宁可整除时也返回 float。

### 4.2 地板除向负无穷:`//` 与 `%` 的数学一致性

`//` 向负无穷取整(而非 C 的向零截断)不是拍脑袋,而是遵循一条严格的数学不变量:**对任意 `a, b`(b≠0),`a == (a // b) * b + (a % b)` 恒成立,且 `a % b` 与 `b` 同号,`0 <= |a % b| < |b|`**。

关键是"余数与除数同号"这个选择(Voorhees 选择)。数学上有两种合理的取整约定:

- **地板取整(floor)**:`//` 向负无穷,余数与**除数**同号(Python 选择)。
- **截断取整(trunc)**:向零截断,余数与**被除数**同号(C/Java 选择)。

以 `-7 / 2 = -3.5` 为例:

| 约定 | 商 `//` | 余 `%` | 验证 `商*2 + 余` |
|------|--------|--------|------------------|
| 地板(Python) | -4(向负无穷) | 1(与除数2同号) | -4*2+1 = -7 ✓ |
| 截断(C/Java) | -3(向零) | -1(与被除数同号) | -3*2+(-1) = -7 ✓ |

两种约定都满足等式,区别在"商往哪取整、相应余数补多少"。Python 选地板的理由:`%` 结果符号只取决于除数,不取决于被除数,这让"周期/环形"运算自然——`i % n`(n>0)恒在 `[0, n)` 范围,无论 `i` 正负。而 C 截断约定下 `-1 % 5` 是 `-1`,做环形索引前要加 `n` 修正,啰嗦易错。

```python
# Python 地板约定的红利:环形索引负数也自然
n = 5
for i in [-6, -1, 0, 6]:
    print(i % n, end=' ')   # 4 4 0 1 —— 全在 [0,5),无需修负数
```

`//` 的"向负无穷"与 `%` 的"余数与除数同号"是同一枚硬币的两面,由等式 `a == (a//b)*b + a%b` 绑定。理解这条原理,就理解了 Python 整除看似反直觉的负数行为实为"周期语义优化",数学上完全自洽。需要截断语义时用 `int(a/b)` 或 `math.fmod` 显式切换。

### 4.3 为何 `//` 在 float 上会"偏一格"

`//` 含 float 时的实现逻辑是:**先做真除(`/`)得到 float 商,再对该 float 商取 `math.floor`**。问题在于,第一步的真除已经引入了 float 精度误差,第二步的 floor 在"误差边界"上会把结果推向错误的一侧。

```python
# 0.7 // 0.1 的内部过程
quotient = 0.7 / 0.1           # 6.999999999999999 —— 真除,误差(本该 7.0)
result = math.floor(quotient)  # 6 —— floor(6.999...) = 6,偏了!
print(result)                  # 6 (// 直接给 6.0)
```

`0.7 / 0.1` 在 float 里是 `6.999...`(因 `0.1`、`0.7` 二进制无法精确表示,真除结果略小于 7),`floor` 把它取到 `6`。这就是"偏一格"的成因:**真除的微小负误差,经 floor 放大为整数差 1**。

这个机制解释了几个现象:

- **正数偏小**:`0.7 // 0.1 = 6`(真除略小于 7,floor 偏小)。
- **负数偏更负**:`-0.7 // 0.1` 同理,floor 让它更负。
- **`math.floor(a/b)` 同样偏**:`//` 在含 float 时与 `math.floor(a/b)` 行为一致(都先真除再 floor),换 `math.floor` 不能解决误差。

**为何 int 操作数的 `//` 不偏**:全 int 时,`//` 不经过 float——它在任意精度 int 上直接算"地板商",精确无误差。只有当操作数含 float,`//` 才走"真除→floor"路径,引入误差。

```python
print(7 // 1)               # 7 —— 全 int,精确(不走 float)
print(0.7 // 0.1)           # 6.0 —— 含 float,走 float 真除,偏
```

**解决之道**:既然误差源于"float 真除",规避就是"不经过 float 真除"——用 int 单位(放大成整数,在 int 上 `//`)或 `Decimal`(十进制精确,`0.7/0.1` 真的就是 7)。这是 §2.4、§3.3 规避方案的原理依据。

### 4.4 `//` 相对 `math.floor(a/b)` 的大整数精度优势

`//` 与 `math.floor(a/b)` 在小整数、正数上等价,但在**大整数**上行为根本不同——这源于"是否经过 float"。

- **`a // b`(全 int)**:Python `int` 任意精度,`//` 在 CPython 层直接调用大数除法(`long_div`),结果精确,无大小上限。
- **`math.floor(a / b)`**:先执行 `a / b`,这步把 `a`、`b` 转成 float(若它们是 int)。float 只有 ~15~17 位十进制有效数字,**大 int 转 float 时低位被舍入丢失**,得到的"商"已是近似的,再 floor 自然错了。

```python
big = 10 ** 30            # 31 位十进制,float 装不下
# // 全 int,直接大数除法,精确
print(big // (10**20))         # 10000000000

# a/b 把 big 转 float,丢精度
print(big / (10**20))          # 1e+30 / 1e+20,但 big 转 float 时丢低位
print(int(big / (10**20)))     # 9999999488 —— 错
```

`big`(10^30)转 float 时,因 float 尾数只有 52 位(约 15~17 位十进制),`10^30` 的低位无法表示,被舍成最接近的可表示值(约 `9.999999488e29`),除以 `1e20` 得 `9.999999488e9`,取整 `9999999488`,与真值 `10^10 = 10000000000` 差了很多。

这是 `//` 作为"运算符直接作用于 int"相对"函数作用于 float 商"的本质优势:**它绕开了 float 的精度上限,在任意精度 int 上精确运算**。理解这点,就理解了"大整数整数商必须用 `//`,不能用 `int(a/b)` 或 `math.floor(a/b)`"的原理——后两者都会把 int 塞进 float 的精度笼子,而 `//` 不会。

### 4.5 `/`、`//` 的协议方法:真正除与地板除的分派

Python 的 `/` 与 `//` 在对象模型上是两个独立的协议方法,这也是它们能被精确区分、且能被不同类型重载的底层原因:

| 运算符 | 正向方法 | 反向方法 |
|--------|---------|----------|
| `/` | `__truediv__` | `__rtruediv__` |
| `//` | `__floordiv__` | `__rfloordiv__` |

`a / b` 执行 `a.__truediv__(b)`(失败回退 `b.__rtruediv__(a)`);`a // b` 执行 `a.__floordiv__(b)`(回退 `b.__rfloordiv__(a)`)。两者分属不同协议,互不干扰——这也是为何 `Decimal` 能让 `/` 返回精确十进制商、`//` 返回精确十进制地板商,各自独立精确。

```python
from decimal import Decimal
print(Decimal('7') / Decimal('2'))     # 3.5 —— __truediv__,Decimal 精确十进制
print(Decimal('7') // Decimal('2'))    # 3   —— __floordiv__,Decimal 地板
print(Decimal('0.7') // Decimal('0.1'))# 7   —— Decimal 不走 float,不偏!
```

`Decimal` 重载了 `__truediv__`/`__floordiv__`,在其十进制表示上运算,绕开了 float 二进制误差——这是 §3.3 用 `Decimal` 修正 `//` 偏移的原理:换一个不基于二进制 float 的类型,误差源头就消失了。

`int`、`float` 的这两个方法由 C 层实现:`int.__floordiv__` 走大数地板除(精确),`float.__floordiv__` 走"真除→floor"(含误差)。同一个 `//` 运算符,因操作数类型不同,分派到不同实现,行为(精度)也不同。理解协议方法分派,就理解了"`//` 在 int 上精确、在 float 上偏移"的实现根源——不是 `//` 本身有精度问题,而是它分派到的 `float.__floordiv__` 走了 float 真除。运算符重载详见《面向对象 OOP 全套》。

## 5. 总结

### 5.1 本文内容回顾

- **为何单独讲**:除法是数值计算最高频、出错代价最大的运算;Python 把"精确商 `/`"与"整数商 `//`"拆成两个独立运算符(PEP 238),消除了 C 里 `/` 语义随类型漂移的陷阱。
- **一句话区分**:`/` 求精确值(永远 float),`//` 求份数(整数商,向负无穷)。差异总览表覆盖返回类型、负数方向、索引可用、与 `%` 耦合、float 精度、除零、典型场景。
- **返回类型**:`/` 永远 float(无论是否整除);`//` 全 int→int、有 float→float。多出的 `.0` 意味 float 不能做索引(`data[4/2]` TypeError),`//` 含 float 即便值是整数也不能做索引。
- **取整方向**:`/` 无方向(精确);`//` 向负无穷(`-7//2=-4`,C 是 -3)。数轴直观对照:地板往负无穷拉,截断往零走。
- **与 `%` 耦合**:`//` 与 `%` 满足 `a==(a//b)*b+a%b`,余数与除数同号;`divmod(a,b)` 一次返回 `(a//b, a%b)`,负数遵循 Python 地板规则。`/` 无此约束。
- **float 精度**:`/` 直接暴露误差;`//` 含 float 时"先真除再 floor",误差让结果偏一格(`0.7//0.1=6`、`1.0%0.1≈0.099`),修正用 int 单位(配 round)或 Decimal。
- **四种取整约定**:floor(`//`/`math.floor`)向负无穷、trunc(`int(a/b)`/`math.trunc`)向零、ceil 向正无穷、round 银行家舍入;向上取整除法用 `-(-a//b)` 或 `math.ceil(a/b)`。
- **`//` vs `math.floor(a/b)`**:值上等价(正数),但大整数下 `math.floor(a/b)` 经 float 丢精度,`//` 全 int 任意精度精确——大整数整数商必须用 `//`。
- **最佳实践**:索引用 `//` 均值用 `/`、负数先测记忆"向负无穷"、float 上 `//` 用 int/Decimal 修正、大数商用 `//`、向上分页 `-(-a//b)`、商余用 `divmod`、除零显式处理、C 风格截断用 `int(a/b)`(大数慎用)、`//` 含 float 转 int 索引、金额用 Decimal、`round(a/b)` 不可靠。
- **原理**:PEP 238 真除决议让 `/` 单一语义;地板约定满足商余等式并让周期运算自然(Voorhees 选择);`//` 在 float 上"先真除再 floor"导致偏移,int 上不经 float 精确;`//` 相对 `floor(a/b)` 的大整数精度优势源于不经过 float;`/`、`//` 分属 `__truediv__`/`__floordiv__` 独立协议,分派到不同类型实现决定精度。
