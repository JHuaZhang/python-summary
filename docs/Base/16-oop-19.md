## 1. 介绍

### 1.1 什么是 __call__

在 Python 里，函数是一等公民——可以把函数赋值给变量、当作参数传递、从函数里返回。而 Python 是一门"消息传递 + 协议"式的面向对象语言：任何操作背后都对应一个或一组特殊方法（魔法方法）。函数之所以能被"调用"，并不是因为它是函数这个语法类别，而是因为它的类型上存在 `__call__` 方法。

`__call__` 是 Python 面向对象协议中负责"调用语义"的特殊方法。当我们在一个类里定义 `__call__(self, *args, **kwargs)` 后，该类的实例对象就不再是"只能访问属性、只能调用方法"的静态数据容器，而是自身可以被当作函数那样"加括号调用"——即 `obj(args)` 这种语法会变得合法。

换句话说：定义了 `__call__` 的类的实例，行为上就像一个函数。你既可以用 `obj(...)` 去触发它，也可以用内置函数 `callable(obj)` 去检测它（返回 `True`）。更重要的是，由于它本质上还是实例，因此仍然可以携带自己的属性、状态、配置——这是"函数对象"区别于普通函数的关键。

这一机制让 Python 中"函数"与"对象"的界限变得模糊：一个带状态的可执行实体，既可以用类 + `__call__` 实现，也可以用闭包 + 嵌套函数实现，二者在调用层面完全等价。理解 `__call__` 不仅能让你写出更灵活的代码，也是理解类装饰器、`functools.partial`、`__init_subclass__`、回调系统等高级用法的底层钥匙。

### 1.2 基本语法与最小用法

`__call__` 的签名与普通方法一致，第一个参数永远是 `self`（因为是实例方法），之后可以接任意位置参数和关键字参数：

```python
class Greeter:
    def __init__(self, name: str):
        self.name = name

    def __call__(self, greeting: str = "Hello") -> str:
        # 定义了 __call__ 后，实例本身可以被"加括号调用"
        return f"{greeting}, {self.name}!"


g = Greeter("Alice")
print(g("Hi"))      # 实例加括号 = 调用 __call__
# 输出：Hi, Alice!
print(g())          # 使用默认参数
# 输出：Hello, Alice!
print(callable(g))  # 实例定义了 __call__，故 callable 返回 True
# 输出：True
```

上面就是一个最小闭环：

- `Greeter("Alice")` 创建实例，`__init__` 初始化 `self.name`；
- `g("Hi")` 看起来像函数调用，实际触发的是 `Greeter.__call__(g, "Hi")`；
- `print` 将 `__call__` 的返回值打印出来；
- `callable(g)` 为 `True`，说明 `g` 已具备"可调用"的能力。

下面我们围绕这一协议，展开其完整用法、调用链原理与工程实践。

## 2. 核心内容

### 2.1 __call__ 的签名与参数约定

`__call__` 是一个普通的实例方法，只不过被 Python 赋予了特殊语义。它的形式一般是：

```python
def __call__(self, *args, **kwargs):
    ...
```

- `self`：调用时由 Python 自动绑定为"被调用的那个实例"。`obj(x)` 会被翻译成 `type(obj).__call__(obj, x)`，其中第一个 `obj` 就是这里的 `self`。
- `*args / **kwargs`：因为 `__call__` 要模拟"任意函数"，所以大部分情况下用万能参数签名，以保证传进来的任意参数都能被接收并在内部转发。
- 返回值：`__call__` 可以返回任意值，也可以不返回（隐式 `None`），与普通函数完全一致。调用方拿到的就是 `__call__` 的返回值。

签名也可以是固定参数，例如 `def __call__(self, x, y): ...`，这取决于你希望这个"函数对象"暴露什么样的调用接口。固定参数的好处是调用者能借助签名提示正确传参，坏处是失去了万能转发的灵活性。

```python
import math

class Vector2D:
    """一个固定参数签名的可调用对象：把实例当函数用，输入缩放因子。"""
    def __init__(self, x: float, y: float):
        self.x, self.y = x, y

    def __call__(self, scale: float) -> float:
        # 返回向量按 scale 缩放后的模长
        return math.hypot(self.x * scale, self.y * scale)


v = Vector2D(3, 4)
print(v(2))     # 2*(3,4) 的模长 = 2*5
# 输出：10.0
```

**何时用固定参数，何时用万能参数**

- 如果这个可调用对象对外是一个明确函数（如 `predict(x)`、`scale(k)`），用固定参数更清晰，调用方有提示。
- 如果它是一个"转发器""代理""装饰器内部对象"，需要把任意参数原样转给底层函数，用 `*args, **kwargs`。

### 2.2 实例加括号调用 obj(args) 的基本形态

定义 `__call__` 之后，实例对象的调用语法和函数完全一致：可以传位置参数、关键字参数、默认参数，甚至用 `*` 解包。

```python
class Transformer:
    def __init__(self, prefix: str = ">>"):
        self.prefix = prefix

    def __call__(self, *tokens, sep: str = " ", upper: bool = False):
        text = sep.join(tokens)
        if upper:
            text = text.upper()
        return f"{self.prefix} {text}"


t = Transformer(prefix="[LOG]")
print(t("hello", "world"))
# 输出：[LOG] hello world
print(t("hello", "world", sep="-", upper=True))
# 输出：[LOG] HELLO-WORLD

args = ("a", "b", "c")
print(t(*args, sep="|"))
# 输出：[LOG] a|b|c
```

可以看到：

- 位置参数正常传入；
- 关键字参数 `sep` / `upper` 正常工作；
- `*args` 解包也和普通函数调用一致。

对调用方来说，`t(...)` 与一个普通函数 `f(...)` 在语法层面没有任何区别，这正是"实例当函数用"的精髓。

### 2.3 callable() 判断对象是否可调用

Python 内置函数 `callable(obj)` 返回一个布尔值，表示对象是否可调用。对自定义类的实例，`callable(obj)` 是否为 `True`，取决于实例所属的**类型**上是否定义了 `__call__`——如果定义了则为 `True`，否则为 `False`。

```python
class A:
    pass

class B:
    def __call__(self, x):
        return x * 2


a = A()
b = B()
print(callable(a))   # 没有 __call__
# 输出：False
print(callable(b))   # 有 __call__
# 输出：True
print(callable(print))   # 函数类型本身有 __call__
# 输出：True
print(callable(42))      # int 没有 __call__，故不可调用
# 输出：False
```

**callable 的实际意义**

`callable` 常用在两类场景：

1. 在框架或通用工具里，先判断"这个东西能不能被调用"再做分发，避免直接 `obj()` 触发 `TypeError`。
2. 在做策略注入、回调注册时，用 `callable` 做入参校验，确保传入的是函数或可调用对象。

```python
def run_if_callable(fn, *args, **kwargs):
    """仅当 fn 可调用时执行，否则静默跳过。"""
    if not callable(fn):
        print(f"[skip] {fn!r} 不可调用")
        return None
    return fn(*args, **kwargs)


class Counter:
    def __init__(self):
        self.n = 0

    def __call__(self):
        self.n += 1
        return self.n


c = Counter()
run_if_callable(c)         # 可调用实例，执行
run_if_callable(c)
run_if_callable(42)        # 不可调用，跳过
print(c.n)
# 输出：
# 1
# 2
# [skip] 42 不可调用
# 2
```

注意：`callable` 只判断"能不能调用"，不判断"调用后会不会成功"。一个有 `__call__` 但参数不匹配的实例，`callable` 仍返回 `True`，真正调用时会抛 `TypeError`。

### 2.4 与普通函数、Lambda 的对比

普通函数、`lambda`、定义了 `__call__` 的实例，三者都可以被"加括号调用"，但在状态管理、可扩展性上有显著差异。

```python
# 普通函数：无状态（除非借助闭包或全局变量）
def make_counter_func():
    n = 0
    def counter():
        nonlocal n
        n += 1
        return n
    return counter


f = make_counter_func()
print(f(), f(), f())
# 输出：1 2 3

# 可调用对象：状态保存在实例属性里，更直观，也便于扩展
class Counter:
    def __init__(self, start: int = 0):
        self.n = start

    def __call__(self, step: int = 1):
        self.n += step
        return self.n

    def reset(self):
        self.n = 0


c = Counter()
print(c(), c(), c(10))
# 输出：1 2 12
c.reset()
print(c())
# 输出：1
```

| 维度 | 普通函数 / lambda | 定义 `__call__` 的实例 |
|---|---|---|
| 可调用 (`callable`) | True | True |
| 内部状态 | 需借助闭包 / globals | 直接存实例属性 |
| 方法扩展 | 不便（只能加嵌套函数） | 可加任意方法（如 `reset`、`config`） |
| 调试 (`repr`) | 函数名 | 可自定义 `__repr__` |
| 可继承 | 否 | 是，可在子类复用/重写 |
| 作为装饰器/上下文管理器组合 | 麻烦 | 天然支持（可同时定义 `__call__` 与 `__enter__` 等） |

一句话：**普通函数适合"无状态计算"**；**可调用对象适合"带状态、可配置、可扩展的可执行实体"**。

### 2.5 场景一：函数对象保持状态——计数器

计数器是 `__call__` 的经典场景：既要"加括号就计数"，又不希望把计数状态暴露成全局变量或闭包。用一个带 `__call__` 的对象，状态天然放在 `self` 上。

```python
class Counter:
    """可调用计数器：每调用一次加一，可随时读取/重置。"""

    def __init__(self, name: str = "counter"):
        self.name = name
        self.count = 0

    def __call__(self, step: int = 1) -> int:
        if step < 0:
            raise ValueError("Counter 只能递增，step 必须 >= 0")
        self.count += step
        return self.count

    def reset(self):
        self.count = 0

    def __repr__(self):
        return f"<Counter {self.name!r} count={self.count}>"


hits = Counter("hits")
clicks = Counter("clicks")

# 模拟事件流
hits()
hits()
hits()
clicks()
clicks()

print(hits)
# 输出：<Counter 'hits' count=3>
print(clicks)
# 输出：<Counter 'clicks' count=2>

print(hits())
# 输出：4
```

这样的计数器相比闭包的优势：

- 可以用 `hits.count` 直接读取计数，无需借助 `nonlocal`；
- 可以用 `hits.reset()` 重置，闭包要暴露重置得再写一个嵌套函数并返回；
- 可以有多个独立实例，互不干扰。

### 2.6 场景二：Multiplier 工厂实例当函数

工厂对象意味着：实例本身就是一个可重复调用的"加工函数"，但配置在 `__init__` 时固化。Multiplier 是一个最直观的例子——拿到一个乘上固定系数的"函数"。

```python
class Multiplier:
    """一个乘法器函数对象：系数在构造时确定，之后多次调用。"""

    def __init__(self, factor: float):
        self.factor = factor

    def __call__(self, x: float) -> float:
        return x * self.factor

    def __repr__(self):
        return f"Multiplier(factor={self.factor})"


double = Multiplier(2)
triple = Multiplier(3)
print(double(5), triple(5))
# 输出：10 15

# 当作函数传给 map / sorted 的 key 不在话下
nums = [1, 2, 3, 4]
print(list(map(double, nums)))
# 输出：[2, 4, 6, 8]
```

**为什么不用一个返回函数的闭包？**

确实可以：`def multiplier(f): return lambda x: x * f`。两者调用层面等价。但用类的好处是：

- 间隔一段时间想"修改系数"时，可以加 `factor` setter 或方法，闭包做不到（系数被捕获锁定）；
- 在调试器里看到 `Multiplier(factor=2)`，比看到 `<function multiplier.<locals>.<lambda>>` 更清晰；
- 可继承做变体，比如 `Discount(Multiplier)` 复用 `__call__` 逻辑。

### 2.7 场景三：带缓存的可调用对象（Memoize）

把纯函数的结果缓存下来，是 `__call__` 的另一类高频用法。用闭包也能做，但用可调用对象能更自然地把缓存字典、命中计数等暴露成属性。

```python
class Memoize:
    """对一个纯函数做结果缓存的可调用包装器。"""

    def __init__(self, func):
        self.func = func
        self.cache = {}
        self.hits = 0
        self.misses = 0

    def __call__(self, *args, **kwargs):
        # 简化：仅对可哈希的 args 做缓存；kwargs 不参与缓存键以保持简洁
        key = args
        if args not in self.cache:
            self.misses += 1
            self.cache[key] = self.func(*args, **kwargs)
        else:
            self.hits += 1
        return self.cache[key]

    def clear(self):
        self.cache.clear()
        self.hits = 0
        self.misses = 0


import math

@Memoize
def slow_sqr(n: int) -> int:
    print(f"  [compute] {n}^2")
    return n * n


print(slow_sqr(3))
# 输出：
#   [compute] 3^2
# 9
print(slow_sqr(3))
# 输出：9   ← 命中缓存，不再打印 compute
print(slow_sqr.hits, slow_sqr.misses)
# 输出：1 1
```

上面把 `@Memoize` 当类装饰器用——这正是"类装饰器常用 `__call__`"的含义：装饰器本身是可调用对象，装饰后返回的 `slow_sqr` 实例又能被调用。本篇聚焦协议本身，类装饰器的更完整讨论放在装饰器章；这里只需理解：**装饰器要"返回的东西可调用"，最自然的方式就是返回一个有 `__call__` 的实例**。

### 2.8 场景四：策略对象，实例当可配置函数

策略模式的目标是"把一组可切换的算法封装成相同接口的对象"。Python 里策略对象天然适合用 `__call__`：策略实例本身就是那个"被调用的算法"，调用时传不同参数得到不同结果，切换策略就是换一个实例。

```python
class DiscountPolicy:
    """折扣策略：实例即折扣函数。"""
    def __call__(self, price: float) -> float:
        raise NotImplementedError


class NoDiscount(DiscountPolicy):
    def __call__(self, price: float) -> float:
        return price


class PercentageDiscount(DiscountPolicy):
    def __init__(self, rate: float):
        assert 0 <= rate <= 1
        self.rate = rate

    def __call__(self, price: float) -> float:
        return price * (1 - self.rate)


class FullReduction(DiscountPolicy):
    """满减：满 base 减 reduce。"""
    def __init__(self, base: float, reduce: float):
        self.base, self.reduce = base, reduce

    def __call__(self, price: float) -> float:
        if price >= self.base:
            return price - self.reduce
        return price


def final_price(price: float, policy: DiscountPolicy) -> float:
    if not callable(policy):
        raise TypeError("policy 必须是可调用折扣策略")
    return policy(price)


print(final_price(100, NoDiscount()))
# 输出：100.0
print(final_price(100, PercentageDiscount(0.2)))
# 输出：80.0
print(final_price(100, FullReduction(base=80, reduce=20)))
# 输出：80.0
```

策略实例 `NoDiscount() / PercentageDiscount(0.2) / FullReduction(...)` 在 `final_price` 看来就是"一个函数"——`final_price` 只关心 `policy(price)` 能不能成立，不关心策略内部长什么样。这种解耦让追加策略变得简单，只要新策略实现了 `__call__` 即可。

### 2.9 场景五：机器学习模型 predict

在机器学习 / 数据科学的工程化代码里，`predict` 这种"用一个新样本求输出"的调用常常被建模成可调用实例。好处是：模型自身持有权重、归一化参数等状态，调用时只需要 `model(x)` 而不是 `model.predict(x)`，语法更函数化；同时模型实例仍是一个对象，可以挂 `fit`、`save`、`load` 等方法。

这里用一个最简单的线性回归演示这个用法：

```python
class LinearRegression:
    """最小化线性回归：fit 后可调用 predict。"""

    def __init__(self):
        self.w = None      # 权重向量
        self.b = 0.0       # 偏置
        self._fitted = False

    def fit(self, X, y):
        n = len(X)
        dim = len(X[0])
        self.w = [0.0] * dim
        # 仅用极简梯度下降演示，不追求精度
        lr = 0.01
        for _ in range(200):
            grad_w = [0.0] * dim
            grad_b = 0.0
            for xi, yi in zip(X, y):
                pred = sum(wi * xij for wi, xij in zip(self.w, xi)) + self.b
                err = pred - yi
                for j in range(dim):
                    grad_w[j] += err * xi[j]
                grad_b += err
            self.w = [w - lr * gw / n for w, gw in zip(self.w, grad_w)]
            self.b -= lr * grad_b / n
        self._fitted = True
        return self

    def __call__(self, x):
        """实例加括号 = predict。"""
        if not self._fitted:
            raise RuntimeError("模型未 fit，调用前请先训练")
        return sum(wi * xij for wi, xij in zip(self.w, x)) + self.b


X_train = [[1.0], [2.0], [3.0], [4.0]]
y_train = [2.0, 4.0, 6.0, 8.0]      # 目标关系 y = 2x, b=0

m = LinearRegression().fit(X_train, y_train)
print(m([5.0]))      # 等价于 m.predict([5.0]) 加括号调用
# 输出：约 10.0（取决于迭代次数与学习率）
print(callable(m))   # 模型实例本身就是可调用对象
# 输出：True
```

`(m([5.0]))` 这种写法对应在工程库里非常常见：scikit-learn 的某些 Pipeline、TensorFlow 的某些 Keras 子类化模型、PyTorch 的 `nn.Module`（`forward` 经由 `__call__` 暴露）都把"实例即函数"作为对外调用接口。这种设计让模型的调用语法与普通函数无差异，使用方无需关心内部到底是网络还是公式。

在生产里常见一种组合：模型对象同时是可调用对象和上下文管理器（`__enter__` 用于加载权重、`__exit__` 用于释放显存），这正是"实例可调用但仍保留完整对象能力"的体现。

### 2.10 场景六：回调对象

回调（callback）是把"以后要做的事"打包传出去，等时机到了由对方触发。普通函数作为回调只有一个被调用入口，而用可调用对象作为回调天然能携带状态。

```python
class LogCallback:
    """回调对象：被调用时记录一行日志并累计次数。"""

    def __init__(self, tag: str):
        self.tag = tag
        self.fired = 0

    def __call__(self, payload):
        self.fired += 1
        print(f"[{self.tag}#{self.fired}] payload={payload}")


class EventEmitter:
    """最简事件源：注册回调，触发时依次调用。"""

    def __init__(self):
        self._callbacks = []

    def on(self, cb):
        if not callable(cb):
            raise TypeError("回调必须是可调用对象")
        self._callbacks.append(cb)

    def emit(self, payload):
        for cb in self._callbacks:
            cb(payload)


emitter = EventEmitter()
lc = LogCallback("DATA")

emitter.on(lc)              # 注册可调用对象作为回调
emitter.emit({"id": 1})
emitter.emit({"id": 2})
print(lc.fired)
# 输出：
# [DATA#1] payload={'id': 1}
# [DATA#2] payload={'id': 2}
# 2
```

注意 `lc.fired` 在 `emit` 之后变成了 `2`——回调对象自己维护触发次数，事件源完全不知道这个状态的存在。这就是"有状态的回调"相比"无状态函数回调"的价值所在。

### 2.11 结合 functools.partial 的类比

`functools.partial(func, *args, **kwargs)` 返回一个"部分应用"后的可调用对象，它把一部分参数固定下来，剩下的参数留给后续调用。`partial` 返回的对象类型 `functools.partial` 内部正是基于类似 `__call__` 的机制——它本身是一个 C 实现的可调用类型，但在语义上等价于下面这个纯 Python 版本：

```python
class MyPartial:
    """手工实现的 partial：固定前置参数，后续调用补齐剩余参数。"""

    def __init__(self, func, *args, **kwargs):
        self.func = func
        self.args = args
        self.kwargs = kwargs

    def __call__(self, *more_args, **more_kwargs):
        # 合并固化参数与新增参数
        merged_kw = {**self.kwargs, **more_kwargs}
        return self.func(*self.args, *more_args, **merged_kw)


def build_url(scheme, host, path, port=80):
    return f"{scheme}://{host}:{port}{path}"


# 固定 scheme 和 host，后续调用只补 path / port
github_url = MyPartial(build_url, "https", "github.com", port=443)
print(github_url("/orgs"))
# 输出：https://github.com:443/orgs
print(github_url("/users/octocat"))
# 输出：https://github.com:443/users/octocat
```

这个 `MyPartial` 与标准库 `functools.partial` 在调用层面完全等价：都是一个"已经保存了部分状态、对外可加括号调用"的对象。这印证了一个观点：**凡是需要"保存一些上下文，等之后带着剩余参数再调用"的场合，本质都是一个带 `__call__` 的可调用对象**。

### 2.12 __call__ 让"函数"与"对象"界限模糊

把前面几个场景串起来可以感受到：在 Python 中，"函数"并不是一类语法特权，而是一种行为契约——只要某个对象能被"加括号调用"，它就是函数。这带来两种等价的实现选择：

```python
# 方式 A：函数 + 闭包，保存状态
def make_adder(delta):
    def adder(x):
        return x + delta
    return adder

# 方式 B：类 + __call__，保存状态
class Adder:
    def __init__(self, delta):
        self.delta = delta
    def __call__(self, x):
        return x + self.delta


add5_a = make_adder(5)
add5_b = Adder(5)
print(add5_a(10), add5_b(10))
# 输出：15 15
print(callable(add5_a), callable(add5_b))
# 输出：True True
```

对调用方而言两者无差别，但在工程取舍上：

- **A（闭包）**：更"函数式"，代码更短，无 `self`；适合状态简单、生命周期清晰的场合。
- **B（可调用对象）**：更"对象式"，状态字段可命名、可观测、可修改；适合状态复杂、需要辅助方法、需要被调试和扩展的场合。

业界经验是：状态只有一两个变量、且短期内即用即抛，用闭包更轻；状态多、或需要附加方法（`reset`、`save`、`stats`）、或可能被继承改写，用可调用对象更合适。

### 2.13 实例可调用但仍是完整对象

定义 `__call__` 并不会让实例"退化成函数"——它仍然是完整的对象，可以拥有任意属性、方法，可以充当上下文管理器、迭代器、描述符等。`__call__` 只是给它的能力清单多加了一项。

```python
class SmartFn:
    """同时是：可调用对象 + 上下文管理器 + 带配置方法。"""

    def __init__(self):
        self.calls = 0

    def __call__(self, x):
        self.calls += 1
        return x + 1

    def config(self, label):
        self.label = label
        return self

    def __enter__(self):
        self.calls = 0
        print(f"[enter] label={getattr(self, 'label', None)}")
        return self

    def __exit__(self, exc_type, exc, tb):
        print(f"[exit] calls={self.calls}")


fn = SmartFn().config("demo")
print(fn(1), fn(2))
# 输出：2 3
print(fn.calls)
# 输出：2

with SmartFn().config("ctx") as f:
    f(10)
    f(20)
# 输出：
# [enter] label=ctx
# [exit] calls=2
```

`fn` 既是函数（`fn(1)`）、又带方法（`config`）、还能进 `with`，这种"角色叠加"正是 Python 协议式设计的魅力：对象的能力由它实现了哪些特殊方法决定，彼此正交。定义 `__call__` 只是叠加其中一条协议。

### 2.14 被继承的 __call__

`__call__` 作为普通实例方法，遵循正常的方法解析顺序（MRO）：子类可以继承、覆盖、扩展父类的 `__call__`。

```python
class BaseHandler:
    def __call__(self, request):
        raise NotImplementedError

    def log(self, request):
        print(f"[{type(self).__name__}] {request}")


class EchoHandler(BaseHandler):
    def __call__(self, request):
        self.log(request)
        return request


class UpperHandler(BaseHandler):
    def __call__(self, request):
        self.log(request)
        return request.upper()


handlers = [EchoHandler(), UpperHandler()]
for h in handlers:
    print("->", h("ping"))
# 输出：
# [EchoHandler] ping
# -> ping
# [UpperHandler] ping
# -> PING
```

这段代码把 `Handler` 这一抽象作为"可被调用的东西"，不同子类提供不同 `__call__`，调度方只管 `h(request)`。这相当于把"继承"和"函数调用接口"结合在一起，构成了一种常见的请求处理结构（在 Web 框架的中间件、WSGI/ASGI 应用里都能看到它的影子）。

## 3. 最佳实践

### 3.1 __call__ 应聚焦于单一调用语义

`__call__` 把实例变成"函数"，调用方对 `obj(...)` 的期望是"它做这件事并返回结果"。把 `__call__` 写成一个什么都干的万能方法（一会儿做计算、一会儿做 I/O、一会儿改状态），会让调用方很难预期行为。

**推荐**：`__call__` 只负责这一个类型的对外调用语义（如 `predict`、`transform`、`discount`、`apply`），其他能力拆成命名方法。

**不推荐**：`obj()` 内部顺便刷新缓存、写日志、发请求、改属性——这在多人协作时极易踩坑。

```python
# 不推荐：obj() 内部混入多种语义
class BadCall:
    def __call__(self, x):
        self.last = x          # 改状态
        self.cache_dirty = True
        open("log.txt", "a").write(str(x) + "\n")
        return x * 2


# 推荐：__call__ 只做核心转换，副作用由显式方法承载
class GoodCall:
    def __init__(self):
        self.last = None

    def __call__(self, x):
        self.last = x           # 与调用语义直接相关的轻量状态，保留
        return x * 2

    def flush_log(self):
        ...
```

### 3.2 用 __call__ 做有状态、有方法的可调用实体时优先于闭包

判断要不要用 `__call__` 而不是闭包，有几个工程信号：

- 需要 `reset`、`save`、`load`、`stats` 等命名方法 → 用可调用对象；
- 需要在调试器里看到清晰的 `repr` → 用可调用对象（搭配 `__repr__`）；
- 需要被继承/扩展 → 用可调用对象；
- 需要在多处创建多个独立实例且可配置不同参数 → 用可调用对象；
- 状态只有 1~2 个标量、生命周期短、不暴露辅助方法 → 闭包更简洁。

### 3.3 保持 __call__ 的参数语义清晰

如果你的可调用对象对外是一个函数接口，那么 `__call__` 的参数语义最好稳定、有名字、有默认值，避免用 `*args, **kwargs` 兜底所有变化——调用方在 IDE 里看不到提示，传错参数只能在运行时炸。

```python
# 不推荐：调用方完全不知道该传什么
class Vague:
    def __call__(self, *args, **kwargs):
        ...

# 推荐：固定签名 + 类型注解
class Scaler:
    def __call__(self, x: float, y: float) -> float:
        return x * y
```

只有当对象本质是"转发器/代理/装饰器内部对象"时，用万能参数才是合理选择。

### 3.4 在库的回调入口用 callable 校验

如果你的库接收用户传进来的"策略/模型/回调"，在入参处用 `callable()` 做一次校验，能在调用前就给出清晰错误，而不是到 `obj()` 那一刻才抛出难以追溯的 `TypeError`。

```python
def register_callback(cb):
    if not callable(cb):
        raise TypeError(f"callback 必须可调用，得到 {type(cb).__name__}")
    ...
```

### 3.5 避免把 __call__ 与普通方法混淆命名

类里同时存在 `__call__` 和名字相近的普通方法（如 `predict` 与 `__call__` 都做预测）时，要明确二者关系：

- 是同一个语义（`predict` 就是 `__call__` 的对外别名），约定 `predict = __call__` 或互相转发，并写清注释；
- 是不同语义，名字要区分清楚，避免"到底调用哪个"产生歧义。

```python
class Model:
    def predict(self, x):
        return self._forward(x)

    # 把 predict 与 __call__ 统一：实例加括号 == predict
    __call__ = predict
```

### 3.6 可调用对象参与鸭子类型时要提供友好 repr

可调用对象常作为"函数"被传给 `map`、`filter`、`sorted`、第三方框架。出错时栈里会出现这个对象的 `repr`，若默认显示 `<Model object at 0x...>` 不利于排查。建议给可调用对象写 `__repr__`，至少把类型与关键状态打出来。

### 3.7 注意性能：热路径上的 __call__ 比普通函数略慢

`__call__` 走的是 `type(obj).__call__` 这层协议分发（见第 4 章），相比直接调用一个普通函数多一次属性查找与方法绑定开销。在每秒调用上百万次的热路径里，这个差异可能被放大。若发现热点是可调用对象，可改写成裸函数 + 原生局部变量来比较。日常业务代码无需为此纠结，先把可读性、可维护性考虑清楚。

## 4. 原理

### 4.1 语法糖：obj(args) 等价于 type(obj).__call__(obj, args)

理解 `__call__` 的核心在于一句话：**"加括号"这个语法是 Python 解释器的一个协议分发点**。当解释器在字节码层面执行 `CALL`（对某对象加括号）时，它并不是直接去对象身上找 `__call__` 属性，而是去**对象的类型**上找 `__call__`，找到后以"被调用的实例"作为第一个参数传入。

也就是说：

```python
obj(args)
# 会被解释器翻译为（概念上的等价形式）
type(obj).__call__(obj, args)
```

注意第一个关键点：`__call__` 查找走的是**类型**（`type(obj)`），而不是**实例本身**。这一点和普通方法的查找机制一致——普通方法的 `obj.method(x)` 也是先在 `type(obj)` 上找到函数对象再绑定 `obj` 作为 `self`。区别在于，普通方法需要你显式写 `.method` 去取，而 `(...)` 这个语法隐式触发的就是 `__call__` 这一个特殊方法。

可以用下面这段实验来加深印象：

```python
class Demo:
    def __call__(self):
        return "called"


d = Demo()
print(d())                 # 正常调用
# 输出：called
print(type(d).__call__(d)) # 手动按协议等价形式调用
# 输出：called

# 在实例本身上挂一个同名属性，不影响 ( ) 的行为
d.__call__ = lambda: "fake on instance"
print(d.__call__())        # 显式访问实例属性，命中新挂的
# 输出：fake on instance
print(d())                 # 语法层调用仍走 type(d).__call__
# 输出：called
```

最后两行的反差非常关键：`d.__call__` 显式访问时拿到的是实例属性（后被覆盖的那个 `lambda`），但 `d()` 这种"加括号语法"根本不看实例属性，只看 `type(d)` 上的 `__call__`。这就是协议查找"走类型不走实例"的直观证据。

### 4.2 callable() 检查的是类型上的 __call__

`callable(obj)` 的判断规则同样遵循"看类型不看实例"：它返回 `True` 当且仅当 `type(obj)` 上存在 `__call__`。实例身上挂什么属性都不影响 `callable` 的判断。

```python
class K:
    pass


k = K()
print(callable(k))           # 类型上没有 __call__
# 输出：False
k.__call__ = lambda: "anything"   # 在实例上挂
print(callable(k))           # callable 仍然看类型，不看实例属性
# 输出：False
```

这也解释了为什么 `callable(42)` 是 `False`——`int` 类型没有 `__call__`；而 `callable(print)` 是 `True`——函数对象的类型 `function` 上有 `__call__`（见下一节）。

### 4.3 函数本身就是可调用对象

Python 的函数并不是"语法特权一类"，它也是对象。`def f(): ...` 执行后，`f` 是 `function` 类型的一个实例：

```python
def f(x):
    return x + 1

print(type(f))
# 输出：<class 'function'>
print(callable(f))
# 输出：True
```

从协议角度，当写 `f(1)` 时，解释器做的事情和 `obj(1)` 完全一致——去 `type(f)` 即 `function` 类型上找 `__call__`，然后以 `f, 1` 为参数调用它。`function` 类型在 C 层实现，其 `__call__` 槽位指向的 C 函数负责真正去执行 `f` 的字节码（并把 `f` 的代码对象、globals 等拿出来运行）。

所以可以做一个很直接的类比：

```python
obj(args)   # -> type(obj).__call__(obj, args)    （obj 是 Demo 实例，__call__ 是实例方法）
f(args)     # -> type(f).__call__(f, args)        （f 是 function 实例，__call__ 是 function 类型的 C 槽）
```

二者在协议层面完全同构，差别只在 `function` 类型的 `__call__` 是 C 实现的、负责跑函数字节码；自定义类 `Demo` 的 `__call__` 是 Python 实现的、由你在方法里写逻辑。这正是"Python 里一切可调用对象在调用协议上是统一"的真正含义。

### 4.4 内置类型上的 __call__：以类调用为例

我们早已熟悉 `list()`、`dict()`、`int()` 这种类调用，本质上它们同样是 `type(obj).__call__(...)` 模式的体现——只不过这里的 `obj` 是 `list` / `dict` / `int` 本身，而它们的类型是 `type`（元类）。

```python
print(type(list))
# 输出：<class 'type'>
print(type(dict))
# 输出：<class 'type'>
```

所以 `list("abc")` 在协议层面相当于 `type(list).__call__(list, "abc")`，即 `type.__call__(list, "abc")`。`type.__call__` 这个元类上的 `__call__` 负责的是"创建并初始化一个新实例"——它会先调用 `list.__new__(list, ...)` 得到新对象，再调用 `list.__init__(new_obj, ...)` 进行初始化，最后把新对象返回。

把"实例加括号调用自定义 `__call__`"与"类加括号创建实例"放在一起对比，就能看到完整图景：

- `obj(...)`：其中 `obj` 是自定义类的实例，语法触发 `type(obj).__call__(obj, ...)`，即在 `Demo` 类里定义的 `__call__` 实例方法；
- `Cls(...)`：其中 `Cls` 是一个类，语法触发 `type(Cls).__call__(Cls, ...)`，即元类 `type` 上的 `__call__`，它负责 `__new__` + `__init__` 的组合调用。

二者是同一个协议在不同层级上的应用。这也是为什么说"`__call__` 是 Python 调用语义的总入口"——无论可调用的是实例还是类，最终都归约到"在被调用对象的类型上找 `__call__`"。

### 4.5 自定义元类与 __call__：控制实例创建

顺着上一节，如果你自定义一个元类并覆盖其 `__call__`，就能介入"类被加括号创建实例"的过程。这是一个少见但能非常直接验证"类调用走元类的 `__call__`"的机制。

```python
class SingletonMeta(type):
    """元类：让被它创建的类变成单例。"""
    def __call__(cls, *args, **kwargs):
        if not hasattr(cls, "_instance"):
            cls._instance = super().__call__(*args, **kwargs)
        return cls._instance


class Service(metaclass=SingletonMeta):
    def __init__(self):
        print("  Service.__init__ 被调用")


s1 = Service()
s2 = Service()
print(s1 is s2)
# 输出：
#   Service.__init__ 被调用
#   Service.__init__ 被调用       ← 注意：__init__ 仍被调
# True
```

这里 `Service()` 触发的不是 `Service` 上某个 `__call__`，而是 `type(Service).__call__`，而 `type(Service)` 正是 `SingletonMeta`。`SingletonMeta.__call__` 决定了"类被加括号时到底怎么造一个实例"，通过 `super().__call__` 委托回原始元类 `type` 的 `__call__` 完成 `__new__` / `__init__` 的组合。

这个例子再次印证："加括号调用"统一走"被调用对象的类型上的 `__call__`"——对实例来说就是它所属的类，对类来说就是它的元类，对函数来说就是 `function` 类型。一条规则，三层应用。

### 4.6 自定义类实例上 __call__ 的完整调用链

把前面几节综合起来，我们描述 `demo(...)`（`demo` 为 `Demo` 类的实例且 `Demo` 定义了 `__call__`）被调用时，解释器的完整动作链：

1. 解释器在字节码中遇到 `CALL`，被调用对象为 `demo`；
2. 解释器取 `demo` 的类型 `type(demo)`，得到 `Demo`；
3. 解释器在 `Demo` 上查找 `__call__` 特殊方法（沿 MRO 查找；若 `Demo` 自身未定义，看父类是否定义）；
4. 找到后，解释器以 `demo` 以及后续实参为参数，调用 `Demo.__call__(demo, ...)`；
5. `Demo.__call__` 函数体执行，其 `self` 绑定为第 4 步里第一个传入的 `demo`；
6. `__call__` 返回值成为整个 `demo(...)` 表达式的值。

其中第 3 步如果没找到 `__call__`，Python 会立刻抛出 `TypeError: 'Demo' object is not callable`——这就是为什么没定义 `__call__` 的实例不能加括号调用。

而 `callable(demo)` 的逻辑等价于"在第 3 步里能否找到 `__call__`"，能找到就 `True`，否则 `False`，并不会真正执行方法体。

### 4.7 __call__ 与函数调用在字节码层面的统一性

在 Python 3.11+ 的字节码中，函数调用与可调用对象调用都经由 `CALL` 指令处理（旧版本里是 `CALL_FUNCTION` 等）。解释器并不在源码层面区分"这是一个函数还是一个实例"——它只关心"被调用对象的类型上是否有可执行的 `__call__` 槽"。可以这样理解：

```
f(args)            # CALL：目标是 function 类型实例，type(f)=function，调用 function.__call__
obj(args)          # CALL：目标是 Demo 类型实例，type(obj)=Demo，  调用 Demo.__call__
SomeClass(args)    # CALL：目标是 Demo 类，     type(Demo)=type，   调用 type.__call__
```

三者在字节码层面是同一种操作，这就是"Python 的调用协议是统一的"在实现层面的落实。理解了这一点，也就明白了为什么 `callable()` 不区分函数和实例——它只是检查"类型上有没有 `__call__`"，对所有对象一视同仁。

### 4.8 __call__ 为什么必须走类型而非实例

可能会有人疑惑：为什么 `obj(args)` 不直接访问 `obj.__call__` 而要绕到 `type(obj)` 上？这是 Python 针对所有特殊方法（dunder methods）的统一设计——特殊方法的查找走类型，不走实例字典。这样做有两个理由：

1. **隐式调用点必须明确**：`obj()`、`len(obj)`、`obj + other` 这些语法都是解释器在背后帮忙查特殊方法。如果允许实例字典覆盖，那么代码里任何给实例属性赋值的操作都可能隐式改变这些语法的语义，造成难以发现的 bug。
2. **类型上的方法共享一份实现**：所有 `Demo` 实例共享 `Demo.__call__` 这一份函数对象，调用时绑定不同的 `self` 即可。若走实例字典，等于每个实例要各自存一份调用逻辑，违背了"类是行为模板"的模型。

因此 `__call__` 能不能被调用，永远由类决定，不由实例字典决定。这也提示我们：若想让"某个实例有不同的调用行为"，正确做法是建不同的子类或用不同类型的实例，而不是试图给单个实例挂 `__call__`。

### 4.9 类装饰器里 __call__ 的位置

回到前面 `Memoize` 的例子，一个类装饰器结构通常是：

```python
class DecoratorClass:
    def __init__(self, func):
        self.func = func        # 拦截被装饰函数

    def __call__(self, *args, **kwargs):
        # 增强/替代被装饰函数的调用行为
        return self.func(*args, **kwargs)
```

装饰器语法 `@DecoratorClass` 在概念上等价于 `fn = DecoratorClass(fn)`，于是 `fn` 由原来的 `function` 实例变成了 `DecoratorClass` 实例。之后所有 `fn(...)` 调用，解释器都会去 `type(fn)` 即 `DecoratorClass` 上找 `__call__`——这就是"类装饰器要靠 `__call__` 才能保持函数可被调用"的本质。如果没有 `__call__`，被装饰后的 `fn` 就只剩属性、不能加括号调用，自然也就不再是"函数"了。

这一机制在装饰器章会专题展开，这里从 `__call__` 协议的角度只需记住：**类装饰器的核心契约就是——被装饰后的对象必须仍然 `callable`**。

### 4.10 与其它"协议方法"的一致性

把 `__call__` 放在更大的图景里看，它是 Python 一系列隐式协议方法中的一员，查找规则与它们完全一致：

| 语法 / 内置 | 触发的特殊方法 | 查找位置 |
|---|---|---|
| `obj()` | `__call__` | `type(obj)` |
| `len(obj)` | `__len__` | `type(obj)` |
| `obj[key]` | `__getitem__` | `type(obj)` |
| `for x in obj` | `__iter__` / `__getitem__` | `type(obj)` |
| `with obj` | `__enter__` / `__exit__` | `type(obj)` |
| `obj + other` | `__add__` | `type(obj)` |

它们都遵循同一套规则：**语法触发 → 去类型上找对应的特殊方法 → 以实例为第一个参数调用**。`__call__` 只是这条规则在"调用"语义上的具体体现。理解一条规则，就理解了一整族协议方法的工作方式。

## 5. 总结

### 5.1 本文内容要点

- `__call__(self, *args, **kwargs)` 是定义"实例可调用"语义的特殊方法。定义后，实例可像函数一样加括号调用，语法 `obj(args)` 等价于 `type(obj).__call__(obj, args)`。
- `callable(obj)` 根据 `type(obj)` 是否具有 `__call__` 来判断对象是否可调用，与实例字典无关。
- 函数本身也是对象，其类型 `function` 上有 `__call__`，故函数可调用。类加括号创建实例则走元类 `type` 的 `__call__`。三层调用（实例、函数、类）在协议上统一。
- 典型应用：计数器、Multiplier 工厂、带缓存的 Memoize、折扣策略对象、机器学习模型 predict、有状态回调对象。它们共同特征是"需要带状态且对外暴露为函数"。
- `functools.partial` 返回的部分应用对象在语义上等价于一个保存前置参数的可调用对象，是 `__call__` 协议的库级体现。
- 可调用对象相比闭包：状态可命名、可观测、可扩展、可继承；相比普通函数：携带状态且可叠加其它协议（上下文管理器、迭代器等）。
- 自定义元类的 `__call__` 控制"类加括号"的实例创建过程，可用于单例等模式，进一步印证"调用走类型"的协议统一性。

### 5.2 读完应能掌握

- 能定义 `__call__` 并写出实例可直接加括号调用的类，正确处理 `self` 与任意参数；
- 能用 `callable()` 做入参校验，并说明它检查的是类型而非实例；
- 能讲清 `obj(args)` 触发 `type(obj).__call__(obj, args)` 这一调用链，并解释为何特殊方法走类型不走实例；
- 能在计数器、策略对象、模型 predict、回调等场景里选用可调用对象替代闭包，并说明取舍理由；
- 能识别类装饰器为何必须定义 `__call__`，以及它与"实例可调用协议"的关联；
- 能将 `__call__` 与其它特殊方法（`__len__`、`__getitem__`、`__enter__` 等）归并到同一套协议查找规则下统一理解。
