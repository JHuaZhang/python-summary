# 集合的哈希机制与元素要求

## 1. 介绍

### 1.1 要理解什么

集合（`set`）是 Python 中基于哈希表（Hash Table）实现的数据结构。哈希机制是集合一切能力的根基——去重、快速查找、成员判断，全部依赖哈希表在背后运作。

理解集合的哈希机制，核心要搞清楚三个问题：

- **为什么集合能 O(1) 判断元素是否存在**——哈希表如何将"遍历查找"变成"直接定位"
- **什么样的对象能放入集合**——"可哈希"到底意味着什么，为什么列表不行而元组可以
- **集合如何判断两个元素是否"相同"**——`__hash__` 和 `__eq__` 的协作机制

集合对元素有一个硬性要求：**元素必须是可哈希的（hashable）**。这个要求不是可选的，而是哈希表数据结构本身的固有约束。

### 1.2 为什么需要理解它

如果你只写 `s = {1, 2, 3}`，哈希机制对你隐形。但以下场景都会"撞墙"：

```python
# 场景一：想把列表放进集合去重
s = {[1, 2], [3, 4]}  # TypeError: unhashable type: 'list'

# 场景二：自定义对象放入集合后"去重"失败
class User:
    def __init__(self, name):
        self.name = name

users = {User("Alice"), User("Alice")}
print(len(users))  # 2，本应为 1

# 场景三：元素入集合后修改了属性，"丢了"
p = User("Bob")
s = {p}
p.name = "Charlie"
print(p in s)  # False，对象还在集合里但找不到了
```

这些问题的根源都指向哈希机制。不理解哈希，遇到这些错误就只能搜索答案；理解了哈希，你就能从根本上避免它们。

### 1.3 在 Python 集合知识体系中的定位

哈希机制属于集合的**底层原理**层面，它支撑着集合的所有上层行为：

```text
集合知识层次
├── 使用层（怎么用）
│   ├── 创建集合、增删改查
│   ├── 集合运算（并集、交集、差集）
│   └── 集合方法（issubset、isdisjoint 等）
├── 规则层（什么能放、什么不能放）
│   ├── 可哈希性要求           ← 本篇核心
│   └── 元素相等性判断
└── 原理层（底层怎么运作）
    ├── 哈希表结构             ← 本篇核心
    ├── 哈希函数 hash()
    └── __hash__ / __eq__ 协议  ← 本篇核心
```

## 2. 整体架构

### 2.1 哈希表的工作原理

集合的核心是一个**哈希表**——一种用"键"直接定位"位置"的数据结构。整体工作流程如下：

```text
  元素入集合的完整流程
  ┌──────────────────────────────────────────────────────┐
  │                                                      │
  │  1. 元素 → hash() 函数                                │
  │     │                                                │
  │     ▼                                                │
  │  2. 得到哈希值（一个大整数）                          │
  │     │                                                │
  │     ▼                                                │
  │  3. 哈希值 % 表大小 → 桶编号（bucket index）          │
  │     │                                                │
  │     ▼                                                │
  │  4. 到对应桶中检查：                                   │
  │     ├── 桶为空 → 直接插入                              │
  │     ├── 桶中已有"相同"元素 → 跳过（去重）              │
  │     └── 桶中已有"不同"元素 → 哈希碰撞，找下一个空桶    │
  │                                                      │
  └──────────────────────────────────────────────────────┘
```

### 2.2 哈希表 vs 列表：为什么是 O(1)

列表查找元素需要从头遍历到尾，最坏情况下要检查每一个元素：O(n)。哈希表不需要遍历，它通过哈希函数直接算出元素的"位置"：

```text
  列表查找：                    集合（哈希表）查找：

  [A, B, C, D, E, F]          [_, _, _, _, _, _]
   ↑                           hash('C') % 6 = 2
   逐个比较...                      ↑
   找到 C（第 3 次比较）            直接跳到位置 2 → 找到 C

  时间复杂度：O(n)             时间复杂度：O(1)
```

这就是集合成员判断 `in` 为 O(1) 的根本原因——不需要"找"，只需要"算"。

### 2.3 集合判断元素是否存在的完整流程

当你在集合中查找一个元素时（`x in s` 或 `s.add(x)`），Python 的执行步骤如下：

```text
  查找元素 x：
  ┌─────────────────────────────────────────────┐
  │ 步骤 1: 计算 h = hash(x)                    │
  │           ↓                                 │
  │ 步骤 2: 根据哈希值定位到桶 bucket            │
  │           ↓                                 │
  │ 步骤 3: 桶为空？                             │
  │           ├── 是 → x 不在集合中，返回 False  │
  │           └── 否 → 进入步骤 4               │
  │           ↓                                 │
  │ 步骤 4: 桶中已有元素 y，比较 x == y          │
  │           ├── True  → x 在集合中，返回 True  │
  │           └── False → 哈希碰撞               │
  │           ↓                                 │
  │ 步骤 5: 用探测策略检查下一个桶，回到步骤 3   │
  └─────────────────────────────────────────────┘
```

这个流程揭示了一个关键点：集合判断"两个元素是否相同"需要两个步骤——**先比哈希值（快速定位），再比值相等（确认身份）**。这涉及 `__hash__` 和 `__eq__` 两个方法的协作。

## 3. 关键机制拆解

### 3.1 哈希函数 hash()

#### 3.1.1 hash() 的基本行为

Python 内置的 `hash()` 函数接收一个对象，返回一个整数（哈希值）。哈希值是对象在哈希表中的"地址映射依据"。

```python
# 不同类型对象的哈希值
print(hash(42))           # 整数：通常 hash(n) == n
print(hash(3.14))         # 浮点数：一个大整数
print(hash("hello"))      # 字符串：一个大整数（可正可负）
print(hash((1, 2)))       # 元组：基于元素的哈希组合
print(hash(True))         # 布尔：True 的哈希等于 1
print(hash(False))        # 布尔：False 的哈希等于 0
print(hash(None))         # None：一个固定值
```

**运行结果**：

```text
42
322818021289917443
-5761971367476251095
-3550055125485641917
1
0
4238894112
```

哈希值有以下特性：

| 特性 | 说明 | 类比 |
|------|------|------|
| 确定性 | 同一对象在同一次运行中哈希值不变 | 同一身份证号永远对应同一个人 |
| 可正可负 | 哈希值可以是任意整数，范围很大 | 不保证是正数 |
| 紧凑性 | 不同对象的哈希值尽量分散 | 不同身份证号尽量不重复 |
| 映射性 | 哈希值用于定位存储位置 | 身份证号用于查找个人档案 |

#### 3.1.2 整数与浮点数的哈希一致性

Python 中一个重要规则：**值相等的数字有相同的哈希值**。

```python
print(hash(1))          # 1
print(hash(1.0))        # 1
print(hash(1) == hash(1.0))  # True
print(len({1, 1.0}))    # 1，集合中 1 和 1.0 被视为重复
```

**运行结果**：

```text
1
1
True
1
```

不仅如此，`True` 的哈希值也等于 `1`，`False` 等于 `0`：

```python
print(hash(True) == hash(1))    # True
print(hash(False) == hash(0))   # True
print(len({True, 1}))     # 1
print(len({False, 0}))    # 1
```

这意味着在集合中，`1`、`1.0`、`True` 被视为同一个元素，`0`、`0.0`、`False` 也被视为同一个元素。这是因为它们值相等（`1 == 1.0 == True`），而哈希一致性和相等性是集合并存的两个条件。

#### 3.1.3 字符串哈希的随机化

整数和浮点数的哈希值在所有 Python 进程中是固定的，但**字符串和字节的哈希值在不同进程之间可能不同**。这是 Python 3 中的安全机制（`PYTHONHASHSEED`）：

```python
# 在同一个进程中，同一字符串的哈希值稳定
print(hash("hello"))  # 每次输出相同
print(hash("hello"))  # 同上
```

```text
# 但在两个独立的 Python 进程中，hash("hello") 的结果可能不同：
进程 1: hash("hello") = -5761971367476251095
进程 2: hash("hello") = 1955240880021843687
```

这个机制是为了防止哈希碰撞攻击——攻击者故意构造大量哈希值相同的字符串，让哈希表退化为链表，拖慢服务。通过随机化种子，每次运行时哈希值分布不同，攻击者无法预测。

**实际影响**：不要把哈希值用于跨进程的数据存储（比如存到文件或数据库），同一次运行内使用是安全的。

### 3.2 可哈希性：什么样的对象能放入集合

#### 3.2.1 可哈希的定义

一个对象是**可哈希的（hashable）**，需要满足两个条件：

1. **有 `__hash__` 方法**，调用它返回一个不变的整数（在对象生命周期内）
2. **有 `__eq__` 方法**，可以与同类型对象比较是否相等

简化为一句话：**不可变对象通常可哈希，可变对象通常不可哈希**。

```text
  可哈希性判断规则

  ┌─────────────────────────────────────┐
  │      对象是否可哈希？                 │
  │                                     │
  │  对象是内置不可变类型？               │
  │     ├── 是 → 可哈希                  │
  │     │   (int, float, str, tuple,     │
  │     │    bool, None, frozenset)      │
  │     │                                │
  │     └── 否 → 不可哈希                │
  │         (list, dict, set, bytearray) │
  │                                     │
  │  对象是自定义类实例？                  │
  │     ├── 未定义 __eq__ → 可哈希        │
  │     │   (默认按 id 哈希)              │
  │     ├── 定义了 __eq__ 但              │
  │     │   也定义了 __hash__ → 可哈希    │
  │     └── 定义了 __eq__ 但              │
  │         __hash__ = None → 不可哈希   │
  └─────────────────────────────────────┘
```

#### 3.2.2 可哈希类型一览

以下内置类型是可哈希的，可以直接放入集合：

```python
# 所有这些都是可哈希的
s = {
    42,                    # int
    3.14,                  # float
    True,                  # bool
    "hello",               # str
    (1, 2, 3),             # tuple
    None,                  # NoneType
    frozenset([1, 2]),     # frozenset
    b"data",              # bytes
    range(5),             # range 对象
}
print(len(s))  # 9
```

**运行结果**：

```text
9
```

#### 3.2.3 不可哈希类型一览

以下内置类型是可变的，因此不可哈希，不能放入集合：

```python
# 尝试将可变类型放入集合
try:
    {1, [2, 3]}  # list
except TypeError as e:
    print(f"list: {e}")

try:
    {{"a": 1}}  # dict
except TypeError as e:
    print(f"dict: {e}")

try:
    {{1, 2}}  # set
except TypeError as e:
    print(f"set: {e}")

try:
    {bytearray(b"hi")}  # bytearray
except TypeError as e:
    print(f"bytearray: {e}")
```

**运行结果**：

```text
list: unhashable type: 'list'
dict: unhashable type: 'dict'
set: unhashable type: 'set'
bytearray: unhashable type: 'bytearray'
```

#### 3.2.4 元组的特殊规则

元组本身是不可变的，但元组可哈希的前提是**它的所有元素也必须可哈希**。如果元组中嵌套了可变类型，整个元组就变得不可哈希：

```python
# 纯不可变元素的元组 → 可哈希
print(hash((1, 2, 3)))        # 正常返回哈希值
print(hash((1, "a", None)))   # 正常返回哈希值
print(hash((1, (2, 3))))      # 嵌套元组也可以

# 含可变元素的元组 → 不可哈希
try:
    hash((1, [2, 3]))         # 元组中嵌套了 list
except TypeError as e:
    print(f"hash((1, [2, 3])): {e}")

try:
    hash((1, {"a": 1}))       # 元组中嵌套了 dict
except TypeError as e:
    print(f"hash((1, {{'a': 1}})): {e}")
```

**运行结果**：

```text
hash((1, [2, 3])): unhashable type: 'list'
hash((1, {'a': 1})): unhashable type: 'dict'
```

原因在于元组的 `__hash__` 方法会递归地对所有元素调用 `hash()`，如果任何一个元素不可哈希，整个元组的哈希就失败了。这也解释了"不可变 ≠ 可哈希"——元组不可变，但它包含的对象可能是可变的。

#### 3.2.5 为什么可变对象不可哈希

理解这个限制的关键在于哈希表的存储原理：元素入集合时，哈希值决定了它在表中的位置。如果对象可变，修改对象后哈希值会变化，但对象在表中的位置不会自动更新——它就"丢"了。

```text
  假设 list 可哈希会怎样？

  1. 创建列表 lst = [1, 2]，假设 hash([1, 2]) = 100
     放入集合后存储在桶 100 % 8 = 4

  2. 修改列表 lst.append(3)，现在 lst = [1, 2, 3]
     hash([1, 2, 3]) = 200（哈希值变了）

  3. 查找 lst in 集合 → 用 hash=200 定位到桶 200 % 8 = 0
     但桶 0 是空的 → 返回 False

  4. 实际上 lst 还在桶 4 里，但找不到了 → 数据丢失！
```

因此 Python 直接禁止可变对象哈希，从源头上杜绝这个问题。

#### 3.2.6 判断可哈希性

可以用 `hash()` 函数来测试一个对象是否可哈希：

```python
def is_hashable(obj):
    """判断对象是否可哈希"""
    try:
        hash(obj)
        return True
    except TypeError:
        return False

# 测试各种类型
candidates = [42, 3.14, "hello", (1, 2), [1, 2], {"a": 1}, {1, 2}, None, True]
for c in candidates:
    print(f"  {str(c):20s} -> hashable={is_hashable(c)}")
```

**运行结果**：

```text
  42                   -> hashable=True
  3.14                 -> hashable=True
  hello                -> hashable=True
  (1, 2)               -> hashable=True
  [1, 2]               -> hashable=False
  {'a': 1}             -> hashable=False
  {1, 2}               -> hashable=False
  None                 -> hashable=True
  True                 -> hashable=True
```

### 3.3 哈希碰撞

#### 3.3.1 什么是哈希碰撞

哈希碰撞（Hash Collision）是指**两个不同的对象计算出了相同的哈希值**。由于哈希值是一个固定大小的整数，而对象的取值空间是无限的，根据鸽笼原理，碰撞不可避免。

```python
# 1 和 1.0 的哈希值相同
print(hash(1))      # 1
print(hash(1.0))    # 1
print(hash(1) == hash(1.0))  # True

# True 和 1 的哈希值也相同
print(hash(True))   # 1
print(hash(True) == hash(1))  # True
```

上例中 `1` 和 `1.0` 是不同类型的对象，但哈希值相同，这是一种"自然碰撞"。它们值也相等，所以集合将它们视为同一元素——这不是问题。

#### 3.3.2 哈希相同但值不同：集合如何处理

更关键的问题是：两个**值不同但哈希值相同**的对象放入集合时，集合如何区分？答案是：先用哈希值定位到桶，再用 `__eq__` 逐一比较。

```python
class BadHash:
    """所有实例返回相同哈希值"""

    def __init__(self, val):
        self.val = val

    def __hash__(self):
        return 42  # 固定哈希值

    def __eq__(self, other):
        return isinstance(other, BadHash) and self.val == other.val

    def __repr__(self):
        return f"BadHash({self.val})"

a = BadHash(1)
b = BadHash(2)
c = BadHash(1)  # 内容和 a 相同

print(f"hash(a) == hash(b): {hash(a) == hash(b)}")  # True，哈希相同
print(f"a == b: {a == b}")  # False，值不同
print(f"a == c: {a == c}")  # True，值相同

s = {a, b, c}
print(f"集合: {s}")
print(f"集合大小: {len(s)}")  # 2，a 和 c 被去重
```

**运行结果**：

```text
hash(a) == hash(b): True
a == b: False
a == c: True
集合: {BadHash(1), BadHash(2)}
集合大小: 2
```

集合的处理方式：

```text
  插入 a (BadHash(1)):  hash=42 → 桶位置计算 → 桶为空 → 插入
  插入 b (BadHash(2)):  hash=42 → 相同桶位置 → 桶中已有 a
                        → 比较 a == b? False → 哈希碰撞 → 探测下一桶 → 插入
  插入 c (BadHash(1)):  hash=42 → 相同桶位置 → 桶中有 a
                        → 比较 a == c? True → 重复，跳过
```

#### 3.3.3 没有 __eq__ 时默认按 id 比较

如果一个类只定义了 `__hash__` 没有定义 `__eq__`，`__eq__` 默认按对象身份（id）比较。此时即使内容相同，不同实例也不被视为重复：

```python
class OnlyHash:
    def __init__(self, val):
        self.val = val

    def __hash__(self):
        return 999  # 固定哈希值

    def __repr__(self):
        return f"OnlyHash({self.val})"

x = OnlyHash(1)
y = OnlyHash(1)  # 内容相同，但不同对象
z = OnlyHash(1)
s = {x, y, z}
print(f"集合大小: {len(s)}")  # 3，按 id 区分，三个不同对象
```

**运行结果**：

```text
集合大小: 3
```

这说明哈希值相同不等于"被视为同一元素"——最终决定权在 `__eq__`。

#### 3.3.4 哈希碰撞对性能的影响

正常情况下哈希碰撞很少，集合查找是 O(1)。但如果所有元素的哈希值都相同，哈希表退化为链表，查找变为 O(n)：

```python
class AlwaysSame:
    def __init__(self, value):
        self.value = value

    def __hash__(self):
        return 0  # 所有元素哈希相同

    def __eq__(self, other):
        return isinstance(other, AlwaysSame) and self.value == other.value

import time

# 正常情况
normal_set = set(range(100000))
start = time.perf_counter()
for _ in range(10000):
    55555 in normal_set
t1 = time.perf_counter() - start

# 全碰撞情况
collision_set = {AlwaysSame(i) for i in range(100)}
test = AlwaysSame(101)  # 不在集合中
start = time.perf_counter()
for _ in range(10000):
    test in collision_set
t2 = time.perf_counter() - start

print(f"正常集合: {t1:.6f}s")
print(f"全碰撞集合: {t2:.6f}s")
print(f"慢了约 {t2/t1:.0f} 倍")
```

**运行结果**：

```text
正常集合: 0.000302s
全碰撞集合: 0.049393s
慢了约 163 倍
```

这就是 `PYTHONHASHSEED` 随机化的意义——防止攻击者故意触发全碰撞。

### 3.4 __hash__ 与 __eq__ 协议

#### 3.4.1 协议的契约关系

`__hash__` 和 `__eq__` 之间存在一个严格的契约：**如果 `a == b` 为 `True`，则 `hash(a)` 必须等于 `hash(b)`**。

```text
  契约关系
  ┌────────────────────────────────────┐
  │   a == b 为 True                   │
  │      ↓                             │
  │   hash(a) == hash(b) 必须为 True   │
  │                                    │
  │   反过来不要求：                     │
  │   hash(a) == hash(b) 不代表 a == b │
  │   （这叫哈希碰撞，由 __eq__ 解决）  │
  └────────────────────────────────────┘
```

用代码验证集合判断元素的完整流程：

```python
class Tracer:
    """追踪 hash 和 eq 的调用次数"""
    _hash_count = 0
    _eq_count = 0

    @classmethod
    def reset(cls):
        cls._hash_count = 0
        cls._eq_count = 0

    def __init__(self, val):
        self.val = val

    def __hash__(self):
        Tracer._hash_count += 1
        return hash(self.val)

    def __eq__(self, other):
        Tracer._eq_count += 1
        return isinstance(other, Tracer) and self.val == other.val

    def __repr__(self):
        return f"Tracer({self.val})"

# 构建集合
Tracer.reset()
s = {Tracer(i) for i in range(5)}
print(f"构建集合: hash调用={Tracer._hash_count}次, eq调用={Tracer._eq_count}次")

# 查找存在的元素
Tracer.reset()
Tracer(0) in s
print(f"查找存在的: hash调用={Tracer._hash_count}次, eq调用={Tracer._eq_count}次")

# 查找不存在的元素
Tracer.reset()
Tracer(99) in s
print(f"查找不存在的: hash调用={Tracer._hash_count}次, eq调用={Tracer._eq_count}次")
```

**运行结果**：

```text
构建集合: hash调用=5次, eq调用=0次
查找存在的: hash调用=1次, eq调用=1次
查找存在的: hash调用=1次, eq调用=0次
```

可以看到：查找时先调用 `hash()`（定位桶），再调用 `__eq__`（确认值）。不存在同一桶中的元素时 `__eq__` 不会被调用。

#### 3.4.2 只定义 __eq__ 不定义 __hash__

Python 的一个重要规则：**一旦在类中定义了 `__eq__`，Python 会自动将 `__hash__` 设为 `None`**，使该类变为不可哈希。

```python
class OnlyEq:
    def __init__(self, val):
        self.val = val

    def __eq__(self, other):
        return isinstance(other, OnlyEq) and self.val == other.val

try:
    hash(OnlyEq(1))
except TypeError as e:
    print(f"TypeError: {e}")
```

**运行结果**：

```text
TypeError: unhashable type: 'OnlyEq'
```

这个设计的原因是：定义了 `__eq__` 后，默认的按 id 比较被覆盖了，如果继续用默认的按 id 哈希，就违反了"相等对象必须哈希相同"的契约。Python 选择宁可不可哈希，也不允许违反契约。

#### 3.4.3 显式声明不可哈希

通过设置 `__hash__ = None` 可以显式声明一个类不可哈希：

```python
class Unhashable:
    __hash__ = None  # 显式不可哈希

    def __init__(self, val):
        self.val = val

try:
    hash(Unhashable(1))
except TypeError as e:
    print(f"TypeError: {e}")
```

**运行结果**：

```text
TypeError: unhashable type: 'Unhashable'
```

#### 3.4.4 违反契约的后果

如果 `__eq__` 返回 `True` 但 `__hash__` 返回不同值，集合的去重就会失败：

```python
class Buggy:
    """__eq__ 基于 name，__hash__ 基于 val，不一致"""

    def __init__(self, name, val):
        self.name = name
        self.val = val

    def __eq__(self, other):
        return isinstance(other, Buggy) and self.name == other.name

    def __hash__(self):
        return hash(self.val)  # 基于不同的属性！

    def __repr__(self):
        return f"Buggy({self.name!r}, {self.val})"

x = Buggy("Alice", 1)
y = Buggy("Alice", 2)

print(f"x == y: {x == y}")  # True，name 相同
print(f"hash(x) == hash(y): {hash(x) == hash(y)}")  # False，val 不同
print(f"集合去重: len({{x, y}}) = {len({x, y})}")  # 2，本应为 1
```

**运行结果**：

```text
x == y: True
hash(x) == hash(y): False
集合去重: len({x, y}) = 2
```

集合根据哈希值将 x 和 y 放到了不同的桶里，从此两者不会被比较 `__eq__`，去重失败。这就是违反契约的后果：集合中存在"相等"的元素。

### 3.5 自定义类的可哈希性

#### 3.5.1 默认行为：按对象 id

自定义类如果不定义 `__eq__` 和 `__hash__`，默认按对象身份（id）处理：

```python
class Default:
    def __init__(self, name):
        self.name = name

    def __repr__(self):
        return f"Default({self.name!r})"

p1 = Default("Alice")
p2 = Default("Alice")
print(f"p1 == p2: {p1 == p2}")  # False，默认按 id 比较
print(f"len({{p1, p2}}): {len({p1, p2})}")  # 2，视为不同对象
```

**运行结果**：

```text
p1 == p2: False
len({p1, p2}): 2
```

#### 3.5.2 自定义 __hash__ 和 __eq__：按内容去重

要让内容相同的对象在集合中被视为同一元素，需要同时定义 `__eq__` 和 `__hash__`：

```python
class ContentBased:
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, ContentBased) and self.name == other.name

    def __hash__(self):
        return hash(self.name)

    def __repr__(self):
        return f"ContentBased({self.name!r})"

q1 = ContentBased("Alice")
q2 = ContentBased("Alice")
print(f"q1 == q2: {q1 == q2}")  # True
print(f"len({{q1, q2}}): {len({q1, q2})}")  # 1，按内容去重
```

**运行结果**：

```text
q1 == q2: True
len({q1, q2}): 1
```

规则口诀：**`__eq__` 比较什么属性，`__hash__` 就基于什么属性计算哈希值**。

#### 3.5.3 多属性参与哈希和相等判断

当对象有多个属性时，通常把所有参与相等判断的属性放在一起计算哈希，最常见的方式是打包成元组：

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):
        return isinstance(other, Point) and self.x == other.x and self.y == other.y

    def __hash__(self):
        return hash((self.x, self.y))  # 元组打包

    def __repr__(self):
        return f"Point({self.x}, {self.y})"

points = [Point(1, 2), Point(3, 4), Point(1, 2), Point(5, 6)]
unique = set(points)
print(f"去重后: {unique}  len={len(unique)}")  # 3
```

**运行结果**：

```text
去重后: {Point(1, 2), Point(3, 4), Point(5, 6)}  len=3
```

#### 3.5.4 对象入集合后修改属性：危险操作

如果自定义类基于可变属性计算哈希值，对象入集合后修改该属性会导致"丢失"：

```python
class MutableHash:
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, MutableHash) and self.name == other.name

    def __hash__(self):
        return hash(self.name)

    def __repr__(self):
        return f"MutableHash({self.name!r})"

m = MutableHash("Alice")
s = {m}
print(f"入集合后: {s}")

m.name = "Bob"  # 修改了影响哈希值的属性
print(f"修改后: {s}")
print(f"m in s: {m in s}")  # False！哈希值变了，找不到了
```

**运行结果**：

```text
入集合后: {MutableHash('Alice')}
修改后: {MutableHash('Bob')}
m in s: False
```

集合中的对象还在（repr 显示 Bob），但用 `in` 查找时算的是新哈希值，定位到了错误的桶，找不到。这是 Python 集合中最隐蔽的陷阱之一。

**最佳实践**：作为集合元素的自定义对象应该是**逻辑上不可变**的——即用于 `__hash__` 和 `__eq__` 的属性在对象生命周期内不应被修改。可以通过属性只读、`__slots__` 或约定来实现。

### 3.6 frozenset：让集合本身可哈希

#### 3.6.1 set 不能作为 set 元素

`set` 本身是可变的，所以不可哈希，不能作为另一个集合的元素：

```python
try:
    s = {{1, 2}, {3, 4}}
except TypeError as e:
    print(f"TypeError: {e}")
```

**运行结果**：

```text
TypeError: unhashable type: 'set'
```

#### 3.6.2 frozenset 是可哈希的集合

`frozenset` 是 `set` 的不可变版本——创建后不能添加、删除元素，因此可哈希，可以作为集合元素：

```python
fs1 = frozenset({1, 2})
fs2 = frozenset({3, 4})
fs3 = frozenset({1, 2})  # 和 fs1 内容相同

s = {fs1, fs2, fs3}
print(f"集合: {s}")
print(f"大小: {len(s)}")  # 2，fs1 和 fs3 去重
```

**运行结果**：

```text
集合: {frozenset({1, 2}), frozenset({3, 4})}
大小: 2
```

#### 3.6.3 frozenset 的哈希值基于元素

```python
# 元素相同但顺序不同的 frozenset 哈希值相同
print(hash(frozenset({1, 2})))   # -1826646154956904602
print(hash(frozenset({2, 1})))   # -1826646154956904602
print(f"相同: {hash(frozenset({1, 2})) == hash(frozenset({2, 1}))}")  # True
```

**运行结果**：

```text
-1826646154956904602
-1826646154956904602
True: True
```

frozenset 的 `__hash__` 基于其所有元素计算，与元素顺序无关，这符合集合的无序特性。

#### 3.6.4 实际应用：标签组合去重

```python
tag_sets = [
    {"python", "集合"},
    {"java", "集合"},
    {"python", "集合"},  # 重复
    {"python", "装饰器"},
]

# 用 frozenset 包裹后放入集合，自动对标签组合去重
unique_tag_sets = {frozenset(ts) for ts in tag_sets}
print(f"原始标签组合数: {len(tag_sets)}")  # 4
print(f"去重后组合数: {len(unique_tag_sets)}")  # 3
for ts in unique_tag_sets:
    print(f"  {set(ts)}")
```

**运行结果**：

```text
原始标签组合数: 4
去重后组合数: 3
  {'集合', 'python'}
  {'集合', 'java'}
  {'装饰器', 'python'}
```

## 4. 设计决策与权衡

### 4.1 为什么集合要求元素可哈希

| 维度 | 要求可哈希（当前方案） | 不要求可哈希（假设方案） |
|------|----------------------|----------------------|
| 查找性能 | O(1) | O(n)，退化为列表 |
| 去重机制 | hash + eq，高效 | 需逐个比较，O(n) |
| 实现复杂度 | 依赖哈希表 | 退化为线性结构 |
| 适用范围 | 仅限不可变对象 | 更广（但牺牲性能） |
| 安全性 | PYTHONHASHSEED 防碰撞攻击 | 无法防护 |

集合的核心价值就是 O(1) 的查找和去重，如果放弃可哈希要求，集合就失去了意义。Python 的设计选择是"宁可在类型上有限制，也要保证性能"。

### 4.2 为什么用哈希表而非其他数据结构

| 数据结构 | 查找复杂度 | 去重能力 | 顺序保持 |
|---------|----------|---------|---------|
| 列表 | O(n) | 需逐个比较 | 保留插入顺序 |
| 哈希表（set） | O(1) | hash + eq 自动去重 | 无序 |
| 二叉搜索树 | O(log n) | 需自定义比较 | 可排序遍历 |

Python 选择哈希表的核心理由是 O(1) 查找——这是集合区别于列表的本质优势。代价是元素必须可哈希、且不保留插入顺序（`dict` 在 3.7+ 保留了顺序，但 `set` 至今不保证顺序）。

### 4.3 为什么定义 __eq__ 会自动禁用 __hash__

| 情形 | __eq__ | __hash__ | 可哈希？ | 原因 |
|------|--------|----------|---------|------|
| 都不定义 | 默认按 id | 默认按 id | 是 | 默认行为一致 |
| 只定义 __eq__ | 自定义 | 被设为 None | 否 | 防止 `__eq__` 与默认 `__hash__` 不一致 |
| 定义了 __eq__ 且手动定义 __hash__ | 自定义 | 自定义 | 是 | 开发者保证一致性 |
| 设置 __hash__ = None | 任意 | None | 否 | 显式不可哈希 |

这个自动禁用的设计体现了 Python 的防御性哲学：与其让开发者不小心写出违反契约的代码，不如直接报错。如果你确实需要自定义类可哈希，你需要同时定义 `__eq__` 和 `__hash__`——这迫使你思考两者是否一致。

### 4.4 PYTHONHASHSEED 的安全考量

Python 3 默认开启字符串哈希随机化，每次进程启动时使用不同的随机种子计算字符串和字节的哈希值。这个决策的背景是 2012 年前后 Python、PHP、Ruby 等语言都遭受了"哈希碰撞 DoS 攻击"：

```text
  攻击原理：
  攻击者构造大量哈希值相同的字符串 → 集合中全部碰撞 → 哈希表退化为链表
  → 单次查找从 O(1) 变为 O(n) → 大量请求耗尽 CPU

  防护方案：
  PYTHONHASHSEED 随机化 → 每次运行哈希种子不同 → 攻击者无法预测哈希分布
```

开启方式：`PYTHONHASHSEED=random`（默认），关闭方式：`PYTHONHASHSEED=0`（固定种子，仅调试用）。

**代价**：字符串哈希值在不同进程间不固定，不能用于跨进程持久化场景。

### 4.5 当前方案的局限性

- **可变对象不能放入集合**：`list`、`dict`、`set` 无法直接去重，需要先转为 `tuple`、`frozenset`
- **集合不保留顺序**：如果需要按顺序去重，需要用 `dict` 或额外的有序结构
- **内存开销**：哈希表的装载因子通常不超过 2/3，空间利用率低于列表
- **哈希冲突可被利用**：即使有随机化防护，在同一进程内恶意构造碰撞仍有影响

## 5. 总结

本文围绕集合的哈希机制与元素要求展开，主要介绍了以下内容：

- 哈希表是集合的底层数据结构，通过 `hash()` 函数将元素映射到存储位置，实现 O(1) 的查找和去重
- `hash()` 函数返回对象的哈希值：整数、浮点数等值相等的数字哈希相同，字符串哈希在进程间随机化
- 可哈希性是元素能放入集合的硬性条件：不可变内置类型（int、float、str、tuple、frozenset 等）可哈希，可变类型（list、dict、set 等）不可哈希
- 元组可哈希的前提是其所有元素也可哈希；不可变不等于可哈希，关键是"生命周期内哈希值不变"
- 哈希碰撞是不同对象哈希值相同的现象，集合通过 `__eq__` 进一步区分值不同的碰撞元素
- `__hash__` 和 `__eq__` 存在严格契约：相等对象必须哈希相同；定义 `__eq__` 会自动禁用 `__hash__`，需手动恢复
- 自定义类的可哈希性：默认按 id 区分，同时定义 `__eq__` 和 `__hash__` 可按内容去重，元素入集合后不应修改影响哈希值的属性
- `frozenset` 是 `set` 的不可变版本，可哈希，可作为集合元素实现嵌套集合
- 设计决策包括要求可哈希（保证 O(1)）、选择哈希表（性能优先）、`__eq__` 自动禁用 `__hash__`（防御性设计）、`PYTHONHASHSEED` 随机化（防碰撞攻击）
