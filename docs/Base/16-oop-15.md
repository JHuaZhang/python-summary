## 1. 介绍

### 1.1 什么是 super

在面向对象编程中，子类经常需要在重写（override）父类方法时，先调用父类原有的实现，再补充自己的逻辑。`super()` 就是 Python 提供的"调用父类方法"的内置函数——更准确地说，它返回一个**代理对象（proxy object）**，通过这个代理对象去访问**按 MRO 顺序的下一个类**的方法。

很多初学者对 `super` 有一个根深蒂固的误解：认为 `super` 就是"父类"的别名，`super().__init__()` 就是"调用父类的构造函数"。这个理解在单继承下基本成立，但在多继承下是错误的——这也是本篇要反复强调的核心点：

> `super` 调用的并非"父类"，而是 MRO（方法解析顺序）中当前类之后的下一个类。在多继承 / 菱形继承下，这个"下一个类"未必是直接父类。

`super` 在 Python 的 OOP 体系里地位非常重要，它直接关系到：

- 子类 `__init__` 中如何正确初始化父类部分。
- 重写方法时如何复用父类逻辑而不破坏继承链。
- 多继承下如何通过"协作式调用"确保每个类的 `__init__`（或被重写方法）恰好执行一次。
- 框架 / Mixin 设计中方法沿 MRO 链条传递的机制。

### 1.2 基本语法与最小用法

Python 3 中 `super` 最常见的用法是**零参形式**，直接在方法体内写 `super()`：

```python
class Animal:
    def __init__(self, name):
        self.name = name
        print(f"Animal.__init__({name})")

class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)      # 调用父类 __init__，初始化 name
        self.breed = breed          # 再初始化子类自己的属性
        print(f"Dog.__init__({name}, {breed})")

d = Dog("旺财", "柴犬")
# 输出：
# Animal.__init__(旺财)
# Dog.__init__(旺财, 柴犬)
```

上面这段代码体现了 `super` 最典型的使用场景：子类的 `__init__` 先用 `super().__init__(...)` 把"父类负责的那部分属性"初始化好，再初始化自己独有的属性。如果不调用 `super().__init__`，父类的初始化逻辑就被跳过了，`self.name` 不会被设置。

除了 `__init__`，重写普通方法时同样常用 `super()`：

```python
class Shape:
    def area(self):
        return 0

class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        base = super().area()   # 先拿父类的"基础面积"（0）
        return base + 3.14 * self.r ** 2   # 再加上圆的面积

print(Circle(2).area())
# 输出：12.56
```

这里 `super().area()` 调用了父类的 `area`，拿到基础值后再叠加子类计算。虽然在这个简单例子里 `base` 就是 0、看似没意义，但它展示了"重写时复用父类逻辑"的标准模式——在更复杂场景下父类方法可能做了缓存、日志、预处理等工作，`super` 让你不必复制这些逻辑。

### 1.3 两种调用形式

`super` 有两种主要形式：

```python
# 形式一：Python 3 零参形式（推荐）
super().__init__(...)
super().method(...)

# 形式二：显式两参形式（Python 2 风格，Python 3 仍支持）
super(Dog, self).__init__(...)
super(Dog, self).method(...)
```

零参形式之所以能工作，是因为 Python 3 的编译器会在定义类的函数体里自动注入一个隐式的 `__class__` 引用（详见第 4 章原理）。在绝大多数情况下，零参形式就够用了；显式形式主要用于一些特殊场景（如脱离类体定义的函数中、元类编程、需要跳过某个类的场景），第 2 章会详细对比。

## 2. 核心内容

### 2.1 super().__init__(...)：初始化父类部分

子类定义了 `__init__` 后，会**完全覆盖**父类的 `__init__`——Python 不会自动调用父类构造器。这意味着如果父类的 `__init__` 负责设置某些属性，而子类 `__init__` 里没调用 `super().__init__`，那些属性就不会被初始化。

**为什么需要手动调用**

来看一个反例：

```python
class Animal:
    def __init__(self, name):
        self.name = name

class Dog(Animal):
    def __init__(self, breed):
        # 忘记调用 super().__init__(name)
        self.breed = breed

d = Dog("柴犬")
print(d.breed)   # 输出：柴犬
print(d.name)    # 抛出 AttributeError: 'Dog' object has no attribute 'name'
# 输出：(上面已抛异常，不会执行到这里)
```

`Dog.__init__` 接收的是品种而非名字，并且没有调用父类的 `__init__`，结果 `self.name` 根本不存在。这说明：**子类一旦重写 `__init__`，就必须主动负责父类那部分的初始化**，而承担这份责任的工具就是 `super().__init__`。

**正确的多层初始化**

下面是一个三层继承的例子，展示 `super().__init__` 如何一层层把初始化责任传递下去：

```python
class Vehicle:
    def __init__(self, wheels):
        self.wheels = wheels
        print(f"  Vehicle.__init__: wheels={wheels}")

class Car(Vehicle):
    def __init__(self, wheels, brand):
        super().__init__(wheels)        # 先让父类初始化 wheels
        self.brand = brand              # 再初始化自己的 brand
        print(f"  Car.__init__: brand={brand}")

class SportsCar(Car):
    def __init__(self, wheels, brand, top_speed):
        super().__init__(wheels, brand) # 让父类去初始化 wheels 和 brand
        self.top_speed = top_speed
        print(f"  SportsCar.__init__: top_speed={top_speed}")

print("创建一辆跑车：")
sc = SportsCar(4, "保时捷", 330)
# 输出：
# 创建一辆跑车：
#   Vehicle.__init__: wheels=4
#   Car.__init__: brand=保时捷
#   SportsCar.__init__: top_speed=330

print(f"轮子={sc.wheels}, 品牌={sc.brand}, 极速={sc.top_speed}")
# 输出：轮子=4, 品牌=保时捷, 极速=330
```

注意执行顺序：`SportsCar.__init__` 最先被调用，但它通过 `super().__init__` 先把控制权交给 `Car`，`Car` 又通过 `super().__init__` 交给 `Vehicle`。所以**初始化是自顶向下（父类先执行）**，而调用链是**自底向上（子类先被调用，再通过 super 往上传）**。这是 `super` 在 `__init__` 中的核心范式：每一层只负责自己引入的属性，其余交给上一层。

**参数传递的配合**

调用 `super().__init__(...)` 时传什么参数，取决于父类 `__init__` 的签名。一个常见模式是子类接收比父类更多的参数：子类用自己需要的参数初始化自己的属性，把其余参数"上交"给父类。

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

class Student(Person):
    def __init__(self, name, age, student_id):
        super().__init__(name, age)   # name、age 交给父类
        self.student_id = student_id # student_id 是子类独有的

s = Student("张三", 18, "S001")
print(s.name, s.age, s.student_id)
# 输出：张三 18 S001
```

**何时调用**

`super().__init__` 通常放在子类 `__init__` 的**开头**——先把父类部分初始化好，再设置子类属性。这样能避免子类属性被父类 `__init__` 意外覆盖（如果父类恰好也设置了同名属性）。不过这不是死规定，当父类 `__init__` 依赖某些子类属性时，也可能需要先设置子类属性再调 `super`，但这属于较少见的设计。

### 2.2 super().method()：重写中调用原方法

除了 `__init__`，`super` 另一大用途是在**重写普通方法**时调用父类的同名方法。这种"先调父类、再加料"的模式让你能在复用父类逻辑的基础上扩展行为，而不必把父类代码复制一遍。

**基本模式：先调原方法，再加修饰**

```python
class Shape:
    def describe(self):
        return "这是一个形状"

class Circle(Shape):
    def describe(self):
        parent_desc = super().describe()       # 拿到父类的描述
        return parent_desc + "（具体来说是圆形）"

print(Circle().describe())
# 输出：这是一个形状（具体来说是圆形）
```

父类 `describe` 给出通用描述，子类 `Circle` 重写后先用 `super().describe()` 取到通用描述，再拼上自己的细化信息。好处是：如果以后父类修改了通用描述的措辞，所有子类自动跟上，无需逐个改。

**带计算的扩展：area 加修饰**

下面用一个更接近真实场景的例子：父类 `Rectangle` 有 `area` 方法，子类 `ColoredRectangle` 重写 `area`，在父类算出的面积基础上乘以一个"颜色系数"（假设不同颜色有不同定价系数）。

```python
class Rectangle:
    def __init__(self, w, h):
        self.w = w
        self.h = h

    def area(self):
        return self.w * self.h

class ColoredRectangle(Rectangle):
    def __init__(self, w, h, color_factor):
        super().__init__(w, h)          # 初始化宽高（父类职责）
        self.color_factor = color_factor

    def area(self):
        base = super().area()           # 父类算出的原始面积
        return base * self.color_factor # 乘以颜色系数

r = ColoredRectangle(10, 5, 1.2)
print(f"定价面积 = {r.area()}")
# 输出：定价面积 = 60.0
```

这里 `super().area()` 复用了父类的面积计算逻辑（宽×高），避免在子类里再写一遍 `self.w * self.h`。如果后续父类把面积算法改成更复杂的形式（比如减去圆角面积），子类无需改动就能继承这个变化。

**链式重写：多层 super 调用**

当继承层级多于两层时，`super().method()` 会沿 MRO 一层层把调用传上去，每一层都可以在父类结果基础上再加工：

```python
class Base:
    def build(self):
        return "地基"

class Wall(Base):
    def build(self):
        return super().build() + " → 墙体"

class Roof(Wall):
    def build(self):
        return super().build() + " → 屋顶"

house = Roof()
print(house.build())
# 输出：地基 → 墙体 → 屋顶
```

`Roof.build` 调 `super().build`，由于单继承 MRO 是 `Roof → Wall → Base`，`super()` 在 `Roof` 里指向 `Wall`，`Wall.build` 再调 `super().build` 指向 `Base`，每一层都把自己的部分拼接到父类结果后面。最终 `build` 自下而上把整条链串了起来。

**前处理与后处理**

`super().method()` 不一定要放在方法开头。你可以先做子类自己的预处理，再调父类，再做后处理：

```python
class Logger:
    def save(self, msg):
        print(f"  写入日志: {msg}")

class TimestampedLogger(Logger):
    def save(self, msg):
        import time
        stamped = f"[{time.strftime('%H:%M:%S')}] {msg}"  # 前处理：加时间戳
        super().save(stamped)                              # 再交给父类写入
        print("  （已完成带时间戳的写入）")                # 后处理

TimestampedLogger().save("系统启动")
# 输出（时间会变化）：
#   写入日志: [14:30:21] 系统启动
#   （已完成带时间戳的写入）
```

这里 `super().save` 在方法中间被调用，子类先改写了消息内容、再让父类去写入、最后做了自己的收尾打印。这比单纯"前调"或"后调"更灵活。

### 2.3 super 并非单纯"父类"——MRO 决定下一个类

这是本篇最关键的概念。`super` 这个名字具有误导性，它并不会去调用"当前类的父类"，而是根据 `type(self).__mro__`（实例类型的 MRO）找到**当前类之后的下一个类**。

**单继承下的直觉成立**

单继承时 MRO 就是一条直线，"下一个类"恰好就是直接父类，所以直觉上 `super = 父类` 没问题：

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(B):
    def who(self):
        return super().who()   # 期望调 B.who

print(C().who())
# 输出：B
```

MRO 是 `C → B → A → object`，`super()` 在 `C.who` 里指向 `B`，符合预期。

**菱形继承下"下一个类"未必是直接父类**

看这个菱形继承的例子：

```python
class A:
    def greet(self):
        return "A.greet"

class B(A):
    def greet(self):
        return "B.greet"

class C(A):
    def greet(self):
        return "C.greet"

class D(B, C):
    def greet(self):
        return super().greet()

print(D().greet())
# 输出：B.greet

print(D.__mro__)
# 输出：(<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>)
```

`D` 继承自 `B` 和 `C`，MRO 是 `D → B → C → A → object`。`D.greet` 里 `super()` 指向的是紧随 `D` 之后的 `B`，直接父类也就是 `B`，这里也是对的。但关键看下一个例子——在 `B.greet` 里如果再调 `super()`，它会指向谁？

```python
class A:
    def greet(self):
        return "A.greet"

class B(A):
    def greet(self):
        return "B.greet → " + super().greet()

class C(A):
    def greet(self):
        return "C.greet → " + super().greet()

class D(B, C):
    def greet(self):
        return super().greet()

print(D().greet())
# 输出：B.greet → C.greet → A.greet
```

意外吗？`B.greet` 里的 `super().greet()` 没有调用 `A.greet`（`B` 的直接父类），而是调用了 `C.greet`！原因就在于：`super` 查找的依据不是"当前类的父类"，而是**实例的 MRO 中、当前类之后的下一个类**。`D` 的 MRO 是 `D → B → C → A`，当 `D.greet` 调 `super().greet` 进入 `B.greet` 后，`super()` 仍然依据同一个 MRO，找到 `B` 之后的是 `C`，而不是 `A`。

> **核心结论**：`super` 查找的目标完全由 `type(self).__mro__` 决定，与"当前类的直接父类"无关。这就是为什么说 `super` 是"MRO 上的下一个类"，而非"父类"。

这也是为什么说：在设计用于多继承的类时，每个重写方法里都应该用 `super()`（而非直接写父类名）来传递调用，这样调用才能沿 MRO 正确流动。我们会在 2.4 节看到为什么这一点至关重要。

### 2.4 协作式多继承：super 链确保每个 __init__ 被调用一次

在多继承（尤其是菱形继承）下，如果每个类的 `__init__` 都正常使用 `super().__init__()`，那么无论继承结构多复杂，每个类的 `__init__` 都会**恰好被调用一次**，不会重复也不会遗漏。这叫"协作式多继承"（cooperative multiple inheritance）。

先看菱形继承会出什么问题。菱形继承指：一个类最终由两条路径继承自同一个基类，形成菱形结构。

```
        A
       / \
      B   C
       \ /
        D
```

如果每个类的 `__init__` 都用 `super().__init__()`，`super` 会沿 MRO 把调用串成一条链，每个类恰好执行一次：

```python
class A:
    def __init__(self):
        print("  A.__init__")

class B(A):
    def __init__(self):
        print("  B.__init__ 开始")
        super().__init__()    # 沿 MRO 传给下一个
        print("  B.__init__ 结束")

class C(A):
    def __init__(self):
        print("  C.__init__ 开始")
        super().__init__()    # 沿 MRO 传给下一个
        print("  C.__init__ 结束")

class D(B, C):
    def __init__(self):
        print("  D.__init__ 开始")
        super().__init__()    # 沿 MRO 传给下一个
        print("  D.__init__ 结束")

print("创建 D：")
D()
# 输出：
# 创建 D：
#   D.__init__ 开始
#   B.__init__ 开始
#   C.__init__ 开始
#   A.__init__
#   C.__init__ 结束
#   B.__init__ 结束
#   D.__init__ 结束
```

注意 `A.__init__` 只被调用了一次。这是因为 MRO 是 `D → B → C → A`，`super` 沿这条线性链把调用一次传下去，不会因为 `B` 和 `C` 都继承自 `A` 就把 `A.__init__` 调两次。

**如果不使用 super 会怎样**

对比一下"显式调用父类名"的写法在菱形继承下的灾难：

```python
class A:
    def __init__(self):
        print("  A.__init__")

class B(A):
    def __init__(self):
        print("  B.__init__ 开始")
        A.__init__(self)      # 显式直接调 A，绕过 MRO
        print("  B.__init__ 结束")

class C(A):
    def __init__(self):
        print("  C.__init__ 开始")
        A.__init__(self)      # 显式直接调 A，绕过 MRO
        print("  C.__init__ 结束")

class D(B, C):
    def __init__(self):
        print("  D.__init__ 开始")
        B.__init__(self)      # 显式调 B
        C.__init__(self)      # 显式调 C
        print("  D.__init__ 结束")

print("创建 D：")
D()
# 输出：
# 创建 D：
#   D.__init__ 开始
#   B.__init__ 开始
#   A.__init__
#   B.__init__ 结束
#   C.__init__ 开始
#   A.__init__
#   C.__init__ 结束
#   D.__init__ 结束
```

`A.__init__` 被调用了两次！因为 `B` 和 `C` 都直接显式调 `A.__init__`，完全绕过了 MRO 协调。如果 `A.__init__` 做了打开文件、分配资源等操作，重复调用会导致资源泄漏或状态错乱。这就是 `super` 存在的核心理由之一：**让多继承下的初始化调用链可预测、无重复**。

**协作式调用的前提：参数要兼容**

要让协作式多继承正常工作，各参与类的 `__init__` 签名需要能互相配合。一种常见做法是用 `**kwargs` 接收并传递自己不需要的参数，让参数沿 super 链流动：

```python
class Base:
    def __init__(self, **kwargs):
        print("  Base.__init__")

class MixinLog:
    def __init__(self, log_level="INFO", **kwargs):
        self.log_level = log_level
        print(f"  MixinLog.__init__: log_level={log_level}")
        super().__init__(**kwargs)   # 把其余参数继续往下传

class MixinCache:
    def __init__(self, cache_size=100, **kwargs):
        self.cache_size = cache_size
        print(f"  MixinCache.__init__: cache_size={cache_size}")
        super().__init__(**kwargs)   # 把其余参数继续往下传

class Service(MixinLog, MixinCache, Base):
    def __init__(self, **kwargs):
        print("  Service.__init__ 开始")
        super().__init__(**kwargs)   # 一个 super 调用启动整条链
        print("  Service.__init__ 结束")

Service(log_level="DEBUG", cache_size=200)
# 输出：
#   Service.__init__ 开始
#   MixinLog.__init__: log_level=DEBUG
#   MixinCache.__init__: cache_size=200
#   Base.__init__
#   Service.__init__ 结束
```

这里 `MixinLog` 取走自己关心的 `log_level`，把其余参数通过 `**kwargs` 继续沿 `super` 链传给下一个类；`MixinCache` 同理取走 `cache_size` 再往下传；最后 `Base` 接收剩余参数。每个 Mixin 只"摘取"自己关心的参数、其余透传，是协作式多继承的标准参数处理模式。

### 2.5 super(Class, self) 显式形式

Python 3 仍支持显式两参形式 `super(Class, instance)`。它的语义是：在 `type(instance).__mro__` 中找到 `Class` 之后的下一个类，返回指向它的代理。

```python
class A:
    def hi(self):
        return "A.hi"

class B(A):
    def hi(self):
        return "B.hi"

class C(B):
    def hi(self):
        return super(C, self).hi()   # 显式指定当前类为 C

print(C().hi())
# 输出：B.hi
```

`super(C, self)` 等价于零参的 `super()`（在 `C.hi` 内）。但在某些场景下显式形式更灵活：

**用途一：跳过中间类**

你可以指定一个**不是当前类**的类作为第一个参数，从而改变 super 查找的起点：

```python
class A:
    def hi(self):
        return "A.hi"

class B(A):
    def hi(self):
        return "B.hi"

class C(B):
    def hi(self):
        return "C.hi"

c = C()
# 正常调用
print(c.hi())
# 输出：C.hi

# 用显式 super 跳过 C，直接从 B 往下找下一个（即 A）
print(super(C, c).hi())
# 输出：B.hi

# 再跳过 B，直接指向 A
print(super(B, c).hi())
# 输出：A.hi
```

这种"指定起点"的能力让 `super` 可以被用来在类外部手动控制方法解析，常见于框架内部、调试、或在某些设计中需要"跳过某个中间类"时。注意这种用法会破坏正常的 MRO 协作，普通业务代码很少需要。

**用途二：在脱离类体定义的函数中使用**

零参 `super()` 依赖编译器注入的 `__class__`，而这只在"类体中定义的函数"里有效。如果你在一个独立的、定义在类体之外的函数中想用 `super`，就必须用显式形式：

```python
class A:
    def greet(self):
        return "A.greet"

class B(A):
    pass

# 这个函数定义在类体之外，没有 __class__ 上下文
def external_greet(self):
    return super(B, self).greet()   # 只能用显式形式

B.greet = external_greet
print(B().greet())
# 输出：A.greet
```

如果在 `external_greet` 里写零参 `super()`，会报 `RuntimeError: super(): no arguments`，因为这个函数没有 `__class__` 上下文。

**第二个参数也可以是类本身**

`super` 的第二个参数不仅可以是实例，还可以是类。当传入类时，返回的是"未绑定"的代理，调用方法时需要手动传 `self`：

```python
class A:
    @classmethod
    def create(cls):
        return f"A.create({cls.__name__})"

class B(A):
    @classmethod
    def create(cls):
        return super(B, cls).create()   # 第二个参数传 cls，用于类方法

print(B.create())
# 输出：A.create(B)
```

类方法里用 `super()` 时，零参形式同样有效（`super()` 会自动绑定当前类）。显式形式 `super(B, cls)` 等价。

### 2.6 super 与显式 Parent.method(self) 的区别

除了 `super`，还可以用另一种方式调用父类方法：直接写父类名，手动传 `self`——`Parent.method(self)`。这种写法在某些简单情况下效果和 `super` 一样，但本质完全不同。

**核心区别一：硬编码绑定 vs MRO 动态解析**

```python
class A:
    def show(self):
        return "A.show"

class B(A):
    def show(self):
        # return super().show()       # MRO 方式：沿 MRO 找下一个
        return A.show(self)            # 硬编码方式：直接指定 A

class C(A):
    def show(self):
        return "C.show"

class D(B, C):
    def show(self):
        return super().show()          # 沿 MRO：D → B，进入 B.show

d = D()
print(d.show())
# 假设 B.show 用 A.show(self)：输出 A.show（跳过了 C）
# 假设 B.show 用 super().show()：    会进入 C.show，输出 C.show（MRO 是 D→B→C→A）
```

这个对比非常关键：当 `D.show` 调 `super().show()` 进入 `B.show` 后，`B.show` 内部如果用 `A.show(self)`，就会**直接跳到 A**，完全跳过 `C`；而如果用 `super().show()`，会按 MRO 进入 `C.show`。

```python
# 完整对比演示
class A:
    def show(self):
        return "A.show"

class B(A):
    def show(self):
        return "B.show → " + A.show(self)   # 硬编码 A

class C(A):
    def show(self):
        return "C.show"

class D(B, C):
    def show(self):
        return super().show()

# B 的 MRO 单独看是 B → A，但 d 的 MRO 是 D → B → C → A
# B.show 里硬编码 A.show(self)，直接跳到 A，跳过了 C
print(D().show())
# 输出：B.show → A.show
```

```python
# 对比：用 super 的版本
class A2:
    def show(self):
        return "A2.show"

class B2(A2):
    def show(self):
        return "B2.show → " + super().show()   # 沿 MRO

class C2(A2):
    def show(self):
        return "C2.show"

class D2(B2, C2):
    def show(self):
        return super().show()

print(D2().show())
# 输出：B2.show → C2.show
# B2.show 里的 super().show() 按照整体 MRO 进入 C2，而不是 A2
```

可以看到：硬编码 `A.show(self)` 破坏了 MRO 协作，导致 `C` 被跳过；而 `super().show()` 让调用正确地流经 `C`。

**核心区别二：菱形继承下的重复调用**

正如 2.4 节演示的，显式 `Parent.__init__(self)` 会导致菱形顶端 `A.__init__` 被调多次，而 `super().__init__()` 保证只调一次。这是 `super` 在多继承下不可替代的原因。

**核心区别三：耦合度**

显式写父类名意味着把"父类是谁"硬编码进了方法。如果以后修改继承关系（比如插入一个中间类、改用另一个基类），所有硬编码的地方都要改。而 `super` 是动态按 MRO 解析的，继承结构调整后调用链自动适应。

**何时可以接受显式调用**

- 单继承、且结构稳定、不会演变成多继承时。
- 有意识地要绕过 MRO、直接调用某个特定类时（少数框架场景）。
- 调用的方法不在 MRO 关心的链上（比如调用一个 `@staticmethod` 工具方法）。

除这些情况外，重写方法中调用父类逻辑应当统一使用 `super()`。

**对比速查表**

| 维度 | `super().method()` | `Parent.method(self)` |
|------|--------------------|-----------------------|
| 解析依据 | 实例的 MRO，动态解析 | 硬编码的类名，静态绑定 |
| 多继承下 | 沿 MRO 流转，不跳类 | 直接跳到指定类，可能跳过中间类 |
| 菱形继承 | 每个 `__init__` 恰好一次 | 顶端 `__init__` 可能被多次调用 |
| 继承关系变更 | 自动适应 | 需手动改所有硬编码处 |
| 类外函数中 | 需显式 `super(Class, self)` | 可直接用 |
| 推荐度 | 默认推荐 | 仅特殊场景 |

## 3. 最佳实践

### 3.1 重写 __init__ 时务必调用 super().__init__

除非你有意要完全替换父类的初始化逻辑（这很少见，且通常是设计信号），否则子类 `__init__` 的第一件事就应当是 `super().__init__(...)`。忘记调用是最常见的 OOP bug 之一：父类属性未初始化，程序在稍后访问时才报 `AttributeError`，排查成本高。

```python
# 推荐
class Child(Parent):
    def __init__(self, x, y):
        super().__init__(x)   # 先初始化父类部分
        self.y = y            # 再初始化自己的

# 不推荐（除非有意为之）
class Child(Parent):
    def __init__(self, y):
        self.y = y
        # 忘记 super().__init__，父类属性丢失
```

### 3.2 多继承下的 __init__ 签名要保持协作友好

让参与多继承的各基类 `__init__` 能互相配合：要么签名一致，要么用 `**kwargs` 接收并透传自己不需要的参数。避免各基类用不同的固定位置参数，那样在组合时不得不逐个对照调用，无法用统一的 `super().__init__(**kwargs)` 流转参数。

```python
# 推荐：用 **kwargs 透传
class MixinA:
    def __init__(self, *, foo="a", **kwargs):
        self.foo = foo
        super().__init__(**kwargs)

class MixinB:
    def __init__(self, *, bar="b", **kwargs):
        self.bar = bar
        super().__init__(**kwargs)

class Combined(MixinA, MixinB):
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

c = Combined(foo="A", bar="B")
print(c.foo, c.bar)
# 输出：A B
```

```python
# 不推荐：固定位置参数，组合时难协作
class MixinA:
    def __init__(self, foo):      # 固定位置参数
        self.foo = foo

class MixinB:
    def __init__(self, bar):      # 固定位置参数，和 MixinA 签名不同
        self.bar = bar

# 组合时难处理：super().__init__ 该传什么？
```

### 3.3 重写方法里统一用 super，不要混用显式父类名调用

在一个会被多继承涉及的方法里，不要混用 `super().method()` 与 `Parent.method(self)`。混用会破坏 MRO 协作链，导致某些类被跳过或重复执行。统一用 `super()` 是最安全的默认策略。

### 3.4 不要在 __new__ 之外的普通方法里用 super 创建实例

`super` 是用来查找并调用方法的代理，不是用来"实例化父类"的。有人会误写 `super().__new__(cls)` 或类似用法，这在普通方法中没有意义。`super` 的对象只是方法查找代理，不参与实例创建语义。

### 3.5 注意 super 链中的参数,避免意外丢失

`super().__init__(**kwargs)` 会把 `kwargs` 传给 MRO 的下一个类。如果下一个类不认识其中某个参数又没有 `**kwargs` 接收，就会报 `TypeError`。协作式多继承要求每个类的 `__init__` 都"吃掉"自己需要的参数、透传其余参数，链尾的类通常以 `**kwargs` 兜底忽略剩余。

```python
# 链尾用 **kwargs 兜底，避免因剩余参数报错
class Root:
    def __init__(self, **kwargs):
        # 不再 super（object.__init__ 不接受自定义参数）
        pass
```

### 3.6 super 与 property 的配合

在 property 的 getter/setter 中也可以用 `super()` 调用父类对应的 property，但写法略有不同：要用 `super().attr`（属性访问）而非 `super().attr()`，因为 property 是描述符。

```python
class Base:
    @property
    def value(self):
        return 10

class Derived(Base):
    @property
    def value(self):
        return super().value + 5   # 通过 super 访问父类 property

print(Derived().value)
# 输出：15
```

### 3.7 不要假设 super 一定调到"父类"

记住核心结论：`super` 调的是 MRO 中的下一个类。在阅读他人代码或设计多继承体系时，不要凭"父类是谁"推断 `super` 调到哪——应查看该实例类型的实际 MRO。

```python
# 查看 MRO 是理解 super 行为的第一步
print(SomeClass.__mro__)
```

### 3.8 适度使用 Mixin,保持 MRO 清晰

协作式多继承虽好用，但过深的 MRO 链条会让调试变难。Mixin 设计应保持每个 Mixin 职责单一、参数协作友好，避免 MRO 过长。如果发现 MRO 深度超过 5-6 层，可能需要重新审视架构。

## 4. 原理

### 4.1 super 对象的本质

`super` 是一个内置类型（不是函数）。调用 `super()` 返回的是一个 `super` 类型的**代理对象（proxy object）**，它不是父类的实例，也不是父类本身，而是一个"方法查找代理"。

`super` 对象内部有两个关键字段：

- `_self_`：绑定的实例（即调用时的 `self`，用于实际方法调用时传入）。
- `_type_`：绑定的类（即"查找起点"，通常是 `__class__`，即在 MRO 中排在其后的下一个类才是查找目标）。

当你写 `super().method()` 时，Python 做的并不是"去父类找 method"，而是：

1. 取 `type(self).__mro__`（实例类型的 MRO）。
2. 在这个 MRO 中找到 `_type_`（当前类）的位置。
3. 取 MRO 中 `_type_` 之后的下一个类作为查找起点。
4. 从这个下一个类开始，按 MRO 顺序查找名为 `method` 的方法。
5. 找到后，用 `_self_`（绑定的实例）作为 `self` 调用该方法。

**关键区分**：`_type_` 是"查找的起点类"，而非"目标类"——真正的查找目标是从 MRO 中该类之后开始的下一个类。`_self_` 是实际接收方法调用的实例，确保方法里拿到的 `self` 是原始的、最底层的那个实例（而非中间代理）。

用代码验证这两个内部字段：

```python
class A:
    pass

class B(A):
    def f(self):
        s = super()              # 创建 super 代理对象
        print(f"  _self_ is self? {s.__self__ is self}")    # True
        print(f"  _type_ == B?   {s.__selfclass__ is B}")   # True

class C(B):
    pass

C().f()
# 输出：
#   _self_ is self? True
#   _type_ == B?   True
```

（注：Python 内部字段名为 `_self_` / `_type_`，对外暴露的属性名为 `__self__` / `__selfclass__`。）

注意 `_type_` 是 `B`，因为 `super()` 是在 `B.f` 里调用的，编译器注入的 `__class__` 就是 `B`。而 `self` 实际是 `C` 的实例。所以查找目标会是 `type(self).__mro__`（即 `C.__mro__`）中 `B` 之后的那一项——也就是 `A`。虽然 `B` 的直接父类也恰好是 `A`，但在多继承下"直接父类"和"MRO 中的下一个"可能不同，`super` 用的是后者。

### 4.2 零参 super 的编译器魔法：__class__ 隐闭包

零参形式 `super()` 不需要你传任何参数就能知道"当前类是谁"，这并非靠运行时探测，而是靠 **CPython 编译器在编译期注入的隐式 `__class__` 闭包变量**。

当编译器处理一个 `class` 定义时，会做一件特别的事：在类体内定义的任何函数中，只要用到了 `super` 或 `__class__`，编译器就会在该函数的 `__code__.co_cellvars` 里加入 `__class__`，使其成为一个闭包变量，并在类定义完成时把刚创建的类对象绑定到这个闭包变量上。

这意味着：

- `super()` 在类体内定义的方法中能"自动知道"当前类，是因为编译器偷偷给它传了 `__class__`。
- 这个 `__class__` 是**词法层面**绑定的——它指向方法被定义所在的那个类，而非运行时 `self` 所属的类。

验证 `__class__` 的存在：

```python
class A:
    def f(self):
        return __class__     # 编译器注入的隐闭包变量

print(A().f())               # 输出：<class '__main__.A'>
print(A.f.__code__.co_cellvars)  # 输出：('__class__',)
```

`A.f` 虽然没有显式定义 `__class__`，但只要函数体里出现了 `__class__` 或 `super`，编译器就会把它加入 `co_cellvars`，使其成为闭包变量，并在类创建后绑定。

`super()` 的实际等价形式可以这样理解：

```python
# 你写的零参形式
super().method(args)

# 编译器等价展开为
super(__class__, self).method(args)
#     ^^^^^^^^^  ← 编译器注入的隐闭包变量，指向方法定义所在的类
```

所以零参 `super()` 本质上还是两参 `super(__class__, self)`，只是参数由编译器自动填入。这也解释了为什么"在类体之外定义的函数中零参 super 不工作"——那种函数没有 `__class__` 闭包变量可填。

验证：当方法体没有任何 `super` 或 `__class__` 出现时，编译器不会注入：

```python
class B:
    def no_super(self):
        return 1

print(B.no_super.__code__.co_cellvars)
# 输出：()    # 没有 __class__，因为这个方法用不到 super
```

### 4.3 MRO 与 super 的查找算法

理解 `super` 必须理解 MRO（Method Resolution Order，方法解析顺序）。Python 3 使用 **C3 线性化**算法计算 MRO，保证：

- 子类在父类之前。
- 多个父类的相对顺序按声明顺序保持。
- 每个类只出现一次。

对一个实例 `obj`，`type(obj).__mro__` 是一个元组，从 `obj` 的实际类开始，依次列出查找方法时要访问的类，直到 `object`。

`super` 的查找规则（设 `super()` 在类 `K` 的方法中被调用，绑定实例 `obj`）：

1. 取 `MRO = type(obj).__mro__`。
2. 在 `MRO` 中定位 `K` 的位置 `i`。
3. 从 `MRO[i+1]` 开始，依次查找请求的方法名，直到找到或到末尾。
4. 用 `obj` 作为 `self` 调用找到的方法。

**为什么是 type(self).__mro__ 而非 K.__mro__**

这是一个微妙但关键的设计。用 `type(self).__mro__` 而不是"当前类 `K` 的 MRO"，是为了在多继承下让 `super` 查找能正确地沿着**实例真实类型**的线性化链流动。

回顾 2.3 节的菱形继承示例：

```python
class A:
    def greet(self):
        return "A.greet → end"

class B(A):
    def greet(self):
        return "B.greet → " + super().greet()

class C(A):
    def greet(self):
        return "C.greet → " + super().greet()

class D(B, C):
    def greet(self):
        return super().greet()
```

`D` 的实例调用 `greet` 时：

1. `D.greet` 调 `super().greet()`。`super()` 在 `D` 中创建，`_type_=D`，`_self_=d`。查找起点 = `type(d).__mro__` 中 `D` 之后 = `B`，进入 `B.greet`。
2. `B.greet` 调 `super().greet()`。`super()` 在 `B` 中创建，`_type_=B`，`_self_=d`。查找起点 = `type(d).__mro__` 中 `B` 之后 = `C`（而非 `A`！），进入 `C.greet`。
3. `C.greet` 调 `super().greet()`。`super()` 在 `C` 中创建，`_type_=C`，`_self_=d`。查找起点 = `type(d).__mro__` 中 `C` 之后 = `A`，进入 `A.greet`。
4. `A.greet` 返回 `"A.greet → end"`，逐层拼接，最终得 `B.greet → C.greet → A.greet → end`。

整条链串起来，关键在于每一步的 `super()` 都依据**同一个 `type(d).__mro__`**（即 `D → B → C → A`），只是起点 `_type_` 各不相同。如果某一步用"当前类的 MRO"（如 `B.__mro__ = B → A`），那一步就会跳到 `A`，跳过 `C`，破坏协作。

这就是为什么 `super` 必须用 `type(self).__mro__`：它让整条协作链始终对齐同一个线性化序列，每个类各被访问一次。

### 4.4 协作式 __init__ 为何每个类恰好执行一次

在 2.4 节的菱形继承示例中，所有基类的 `__init__` 都用 `super().__init__()`，结果每个 `__init__` 恰好执行一次。原因正是 4.3 描述的 MRO 线性流动。

MRO 是一条**线性序列**（`D → B → C → A → object`），没有分支。`super().__init__` 沿这条线一步步往下传，每个类在这条线上只出现一次，所以每个 `__init__` 只被调一次。菱形的两条"边"（`B→A` 和 `C→A`）在 C3 线性化后合并成一条线，`A` 只出现一次，因此 `A.__init__` 只执行一次。

对比显式 `Parent.__init__(self)`：它不参考 MRO，直接跳到指定的父类，于是 `B` 调 `A.__init__`、`C` 也调 `A.__init__`，`A` 就被调两次。`super` 的线性流动天然避免了这种重复，这是它作为多继承初始化机制的核心价值。

### 4.5 super 在静态方法、类方法中的行为

`super` 不仅适用于实例方法，对类方法和静态方法也适用，但绑定方式不同：

- **实例方法**：`super()` 等价于 `super(__class__, self)`，`_self_` 是实例。
- **类方法**：`super()` 等价于 `super(__class__, cls)`，`_self_` 是当前类（作为 `cls` 传入）。
- **静态方法**：`super()` 无法自动获取实例或类，因为静态方法没有 `self`/`cls` 参数，需要显式 `super(__class__, some_class_or_instance)`。

```python
class Base:
    @classmethod
    def who(cls):
        return f"Base.who({cls.__name__})"

class Derived(Base):
    @classmethod
    def who(cls):
        return super().who()   # 类方法里 super 自动绑定 cls

print(Derived.who())
# 输出：Base.who(Derived)
```

类方法中的 `super()` 把 `_self_` 设为当前类 `Derived`，`_type_` 为 `Derived`。查找 MRO（`Derived → Base`）中 `Derived` 之后即 `Base`，调用 `Base.who(Derived)`，`cls` 拿到的是 `Derived` 而非 `Base`——这符合"方法属于哪个类被调用的"语义。

### 4.6 super 对象不支持属性赋值与实例化

`super` 对象是只读代理，不能给它赋值属性，也不能用它来实例化类。它只支持方法查找调用（`super().method(...)`）和属性读取（`super().attr`，走描述符协议）。尝试 `super().x = 1` 会抛 `AttributeError`。

```python
class P:
    x = 10

class Q(P):
    def f(self):
        # super().x = 20  # 会报错：super 对象不支持属性赋值
        return super().x   # 读属性可以

print(Q().f())
# 输出：10
```

这是因为 `super` 对象的 `__setattr__` 被设计为禁止赋值，以避免有人误以为"通过 super 修改父类属性"——super 只用于查找并调用，不用于修改继承结构。

## 5. 总结

### 5.1 本文内容要点

- `super()` 返回一个代理对象，用于调用按 MRO 顺序的"下一个类"的方法，而非简单的"父类"。
- `super().__init__(...)` 在子类构造器中初始化父类负责的那部分属性；子类一旦重写 `__init__`，父类构造器不会被自动调用，必须手动 `super().__init__`。
- `super().method()` 在重写方法中复用父类逻辑，支持先调原方法再加修饰、前处理/后处理等多种模式。
- `super` 查找目标的依据是 `type(self).__mro__` 中当前类之后的下一个类——在多继承下未必是直接父类。这是 `super` 与"父类"概念的关键差异。
- 显式形式 `super(Class, self)` 用于跳过指定类、在类体外函数中使用、或在类方法中需要时手动指定起点。
- 协作式多继承：当所有参与类都使用 `super().__init__(**kwargs)` 时，调用沿 MRO 线性流动，每个类的 `__init__` 恰好执行一次，菱形继承顶端不会被重复调用。
- `super().method()` 与 `Parent.method(self)` 的本质区别：前者按 MRO 动态解析、支持多继承协作，后者硬编码绑定、绕过 MRO、多继承下会重复或跳类。
- `super` 对象内部维护 `_self_`（绑定的实例）与 `_type_`（查找起点类），查找目标为 `type(self).__mro__` 中 `_type_` 之后的下一个类。
- 零参 `super()` 由 CPython 编译器在编译期注入 `__class__` 隐闭包变量，等价于 `super(__class__, self)`；这是它能"自动知道当前类"的根本机制。

### 5.2 读完应能掌握

- 能正确在子类 `__init__` 中用 `super().__init__(...)` 初始化父类部分，并合理传递参数。
- 能在重写方法中用 `super().method()` 复用父类逻辑，区分前处理与后处理。
- 能解释 `super` 调用的并非"父类"而是 MRO 中下一个类，并会用 `__mro__` 预测多继承下 `super` 的实际目标。
- 能说明协作式多继承中每个 `__init__` 恰好执行一次的原因，并能用 `**kwargs` 透传模式设计参数协作友好的 Mixin。
- 能区分 `super().method()` 与 `Parent.method(self)` 在多继承下的行为差异，并说明为何默认应使用 `super`。
- 能用 `super(Class, self)` 显式形式在需要的特殊场景（类体外函数、跳过中间类、类方法）中正确调用。
- 能说明零参 `super()` 的编译器 `__class__` 隐闭包原理，解释为何类体外函数中零参 `super` 失效。
