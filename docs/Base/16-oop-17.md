## 1. 介绍

### 1.1 什么是 MRO 与 __mro__

在面向对象编程中，一个子类可以从多个父类继承行为。当我们在实例上调用一个方法、访问一个属性时，Python 需要一条确定的顺序去搜索"这个方法到底定义在哪个类里"——这条顺序就叫 **MRO（Method Resolution Order，方法解析顺序）**。

MRO 本质上是一张"类继承的线性查找表"。它把一棵可能复杂的继承图（包含多重继承、菱形继承）压扁成一条单链表，查找方法时只需要沿着这条链从头到尾走一遍，第一个命中的类即为结果。有了 MRO，Python 不必在运行时对继承图做图搜索，也不用担心同样一个父类被重复访问——继承图在类创建时就已经被线性化好了。

Python 把这张查找表存放在每个类的 `__mro__` 属性上。`__mro__` 是一个只读的元组，元素是类对象，顺序就是查找顺序。与之配套的 `mro()` 方法返回的是同一份顺序的列表（`list`，而非元组），可以用于在运行时以可变形式查阅。

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(A):
    def who(self):
        return "C"

class D(B, C):
    pass

print(D.__mro__)
# 输出：(<class '__main__.D'>, <class '__main__.B'>, <class '__main__.C'>, <class '__main__.A'>, <class 'object'>)

print(D.mro())
# 输出：[<class '__main__.D'>, <class '__main__.B'>, <class '__main__.C'>, <class '__main__.A'>, <class 'object'>]
```

从输出可以看到，`D` 自身排在最前面，然后是 `B`、`C`、`A`、`object`。当 `D` 实例调用 `who()` 时，Python 会沿着这条顺序先看 `D`（没有定义 `who`）、再看 `B`（命中），于是返回 `"B"`。`C` 和 `A` 里虽然也定义了 `who`，但它们排在 `B` 之后，不会被命中。

**为什么需要专门的算法来算 MRO**

如果继承结构只是一条单链（`A → B → C`），查找顺序天然就是 `C → B → A`，没什么好算的。真正复杂的是多继承：当 `D` 同时继承 `B` 和 `C`，而 `B` 和 `C` 又都继承 `A` 时，就形成了"菱形继承"。此时 `A` 在查找链里应该排在什么位置？是放在 `B` 之后（深度优先）、还是放在所有子类之后？如果父类列表里某个类的顺序和它自身 MRO 里的顺序冲突了怎么办？

Python 3 用 **C3 线性化算法**（C3 linearization）来回答这些问题。C3 是一种单调线性化算法，由 1996 年 Dylan 语言的开发者提出，Python 从 2.3 起对新式类统一采用。它能保证：子类永远在父类之前出现、继承列表中父类的相对顺序被保持、且不会让任何类被重复访问。当继承图的结构无法满足这些约束时，C3 不会勉强生成一个混乱的顺序，而是直接在类定义时报 `TypeError: Cannot create a consistent method resolution order`，把问题暴露在开发期而不是留到运行时产生难以排查的方法覆盖 bug。

### 1.2 基本语法与最小用法

查看一个类的 MRO 有两种方式：

```python
# 方式一：直接读 __mro__ 属性，得到元组
print(SomeClass.__mro__)

# 方式二：调用 mro() 方法，得到列表
print(SomeClass.mro())
```

`__mro__` 是属性（注意两边都有双下划线），`mro()` 是方法（需要加括号调用）。两者返回的顺序完全一致，区别只在于类型：`__mro__` 是不可变的元组，`mro()` 返回可变列表。实际上 `mro()` 这个方法的存在主要是给元类（metaclass）一个可重写的钩子——如果你自定义元类并覆盖 `mro()`，就可以干预类的 MRO 计算（极其少用，且稍有不慎就会导致不一致）。日常开发中，**只读不写**：把 `__mro__` 当作一个只读快照来查看顺序即可，绝不要尝试去修改它。

一个最小可用场景：当你不确定某个方法最终被哪个父类提供时，打印 MRO 就能一眼看出：

```python
class Base:
    def greet(self):
        return "Base.greet"

class MixinX(Base):
    def greet(self):
        return "MixinX.greet"

class MixinY(Base):
    pass  # 不覆盖 greet，继续向上查找

class Service(MixinY, MixinX):
    pass

# 想知道 Service().greet() 会调用谁？看 __mro__ 即可
for cls in Service.__mro__:
    if "greet" in cls.__dict__:
        print(f"greet 实际由 {cls.__name__} 提供")
        break
# 输出：greet 实际由 MixinX 提供
```

这段代码模拟了 Python 内部的方法查找过程：沿着 `__mro__` 逐个类检查 `__dict__`，第一个拥有该方法名的类就是命中者。可见 `MixinY` 虽然排在 `MixinX` 前面（因为继承列表写的是 `MixinY, MixinX`），但它没定义 `greet`，查找继续走到 `MixinX` 才命中。这说明 MRO 决定的是"查找顺序"，而不是"谁覆盖谁"——真正决定覆盖关系的是"谁先在 MRO 里定义了该方法"。

## 2. 核心内容

### 2.1 __mro__ 属性详解

`__mro__` 是每个类（注意是类对象，不是实例）都有的内置属性，存储该类的方法解析顺序。它的几个关键特征需要逐一讲清。

**只读元组，类创建时冻结**

`__mro__` 在类对象创建（`class` 语句执行）的那一刻就被 C3 算法算好并冻结。之后你无法对它做任何修改——元组本身不可变，且即便你绕过去给类重新赋一个 `__mro__`，CPython 内部也不会用你给的值做方法查找，查找走的是 C 层缓存的另一份顺序。所以试图通过改 `__mro__` 来"动态调整继承顺序"是无效的：

```python
class P:
    pass

class Q(P):
    pass

# 试图强行改写 __mro__，对方法查找毫无影响
try:
    Q.__mro__ = (Q, object)
except AttributeError as e:
    print(e)
# 输出：attribute '__mro__' of 'type' objects is not writable
```

直接就是 `not writable`——`__mro__` 在 C 层被声明为只读 descriptor。

**开头永远是自身，结尾永远是 object（新式类）**

在 Python 3 中，所有类都是新式类，隐式继承 `object`。因此任何类的 `__mro__` 一定以自己开头、以 `object` 结尾，中间是其各级基类。这条性质是 C3 算法自然推出的结论，也是 `object` 作为"终极基类"的体现：

```python
class Solo:
    pass

print(Solo.__mro__)
# 输出：(<class '__main__.Solo'>, <class 'object'>)
```

即便你没写任何父类，`object` 也会出现在末尾。这解释了为什么任何对象都有 `__init__`、`__repr__`、`__str__` 等方法——它们都来自 `object`，处于 MRO 的最后一站。

**实例无 __mro__，类才有**

`__mro__` 是挂在类（`type` 的实例）上的，不是挂在你业务实例上的。实例要做方法查找时，是通过 `type(self).__mro__` 间接拿到类的 MRO：

```python
s = Solo()
# print(s.__mro__)  # AttributeError: 'Solo' object has no attribute '__mro__'
print(type(s).__mro__)
# 输出：(<class '__main__.Solo'>, <class 'object'>)
```

这也意味着，如果某个实例的 `type(self)` 不是你以为的类（比如被某个元类替换、或者用了 `__class__` 属性的 tricks），方法查找顺序会跟着变。但这是极特殊场景，普通业务代码无需关心。

### 2.2 mro() 方法详解

`mro()` 是 `type` 上的一个方法，返回一个和 `__mro__` 同序的 `list`。它和 `__mro__` 的关系可以这样理解：`__mro__` 是"计算结果缓存"，`mro()` 是"计算入口"。

**默认行为**

`type.mro(cls)` 调用 C3 线性化算法计算顺序，返回列表。Python 在创建类时内部调用的就是这个方法，然后把结果转成元组存进 `__mro__`：

```python
class K:
    pass

print(type.mro(K) is K.mro())  # mro() 内部就是调 type.mro
# 输出：False （每次返回的是新 list，不是同一个对象）

print(K.mro() == list(K.__mro__))
# 输出：True  （顺序完全一致）
```

注意 `mro()` 每次调用都会返回一个新的列表对象，所以对它做 `.append` / `.sort` 不会影响任何东西，只是改了一个临时副本。

**元类可覆盖 mro() 改变计算逻辑**

这是 `mro()` 作为方法存在的真正原因。自定义元类如果覆盖 `mro()`，就能在 C3 之外塞进特殊的顺序。但这是一个高风险操作——C3 的约束一旦被打破，`super()`、方法覆盖、菱形继承都可能产生反直觉的行为，绝大多数项目永远用不到这个钩子。一个非常简化的示意（仅演示钩子存在，不代表推荐用法）：

```python
class ReorderMeta(type):
    def mro(cls):
        # 故意把 object 提前，制造一个非标准顺序（仅演示）
        default = super().mro()  # 先拿到 C3 的标准结果
        default.remove(object)
        default.append(default.pop(0))  # 把 cls 自己挪到最后
        return default

# 这样的元类会导致 super() 行为极度反直觉，实际项目不要这么做
# 这里只说明：mro() 确实是可被元类覆盖的钩子
print("ReorderMeta 存在，mro() 可被覆盖")
# 输出：ReorderMeta 存在，mro() 可被覆盖
```

除非你正在写框架级的对象系统（比如 ORM、DI 容器）且完全清楚后果，否则把这个钩子当作"不存在"即可。

### 2.3 查看 __mro__ 的实战场景

实际开发中，查看 `__mro__` 通常发生在以下几种场景。每种场景都值得用一个 demo 展示"为什么看 MRO 能解决问题"。

**场景一：排查方法被谁覆盖**

当一个类混合了多个 Mixin，调用某个方法时出来的行为和你预期的不一样，最快的排查方式就是打印 `__mro__`，看第一个定义该方法的类是谁：

```python
class JsonSerializable:
    def to_dict(self):
        return {"_from": "JsonSerializable"}

class LogMixin:
    def to_dict(self):
        return {"_from": "LogMixin"}

class Model(JsonSerializable, LogMixin):
    pass

m = Model()
print(m.to_dict())
# 输出：{'_from': 'JsonSerializable'}

# 期望明明是 LogMixin 的版本？看 MRO 就知道为什么
print([c.__name__ for c in Model.__mro__])
# 输出：['Model', 'JsonSerializable', 'LogMixin', 'dict', 'object']
```

`JsonSerializable` 排在 `LogMixin` 之前（因为继承列表写的是 `JsonSerializable, LogSerializable, LogMixin`），所以它的 `to_dict` 先被命中。想换成 `LogMixin` 的版本，要么改继承列表顺序，要么在 `Model` 里显式覆盖。MRO 让这个"谁覆盖谁"的问题一目了然。

**场景二：理解 Django/Flask 等框架的基类组合**

框架的基类往往用多层 Mixin 组合出最终视图类。比如一个简化版的类 Django View 结构：

```python
class View:
    def dispatch(self):
        return "View.dispatch"

class GetMixin:
    def dispatch(self):
        return "GetMixin.dispatch"

class PostMixin:
    pass

class ApiView(GetMixin, PostMixin, View):
    pass

print(ApiView().dispatch())
# 输出：GetMixin.dispatch

print([c.__name__ for c in ApiView.__mro__])
# 输出：['ApiView', 'GetMixin', 'PostMixin', 'View', 'object']
```

看到 MRO 后，你就知道：`ApiView` 自身没定义 `dispatch`，先查 `GetMixin`（命中）。如果以后你给 `PostMixin` 加了 `dispatch`，它也不会生效，因为 `GetMixin` 在前。这种"加了个方法但没被调用"的困惑，看一眼 MRO 就解开。

**场景三：确认 Mixin 不会意外遮蔽业务方法**

写 Mixin 时经常会担心：我这个 Mixin 里定义的 `save` 方法，会不会在和别的类组合时反而覆盖了业务基类里更重要的 `save`？把组合后的 MRO 打出来即可确认：

```python
class BaseModel:
    def save(self):
        return "BaseModel.save（真实落库）"

class AuditMixin:
    def save(self):
        return "AuditMixin.save（只记日志，不落库）"

class User(AuditMixin, BaseModel):
    pass

u = User()
print(u.save())
# 输出：AuditMixin.save（只记日志，不落库）

# 这显然是个 bug：AuditMixin 应该在 BaseModel.save 之上加日志，
# 而不是替换掉它。MRO 一看就发现 AuditMixin 排在 BaseModel 前面
print([c.__name__ for c in User.__mro__])
# 输出：['User', 'AuditMixin', 'BaseModel', 'object']
```

这种问题在代码评审时就可以靠"看 MRO"提前发现。正确写法是 `AuditMixin.save` 内部用 `super().save()` 转给下一个类（参见 2.5 节）。

### 2.4 手算多继承 MRO 的例子（菱形继承）

C3 算法的价值在菱形继承下体现得最明显。我们来手算一个经典例子，看看 Python 3 的顺序到底是怎么算出来的，并对照运行结果。

**菱形继承结构**

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(A):
    def who(self):
        return "C"

class D(B, C):
    def who(self):
        return "D"
```

继承图是一个菱形：`D → B → A`、`D → C → A`，`A` 在顶部。直觉上，`D` 的方法查找应该先查 `D` 自己，再按继承列表顺序查 `B`、`C`，最后查 `A`。但具体顺序需要 C3 来确定。

**逐步推演（C3 合并算法）**

C3 的核心公式是（详细推导见第 4 章原理）：

```
L[D] = D + merge(L[B], L[C], [B, C])
```

其中 `+` 是列表拼接，`merge` 是 C3 的合并操作。先把各基类的线性化列出来：

- `L[object] = [object]`
- `L[A] = [A] + merge(L[object], [object]) = [A, object]`
- `L[B] = [B] + merge(L[A], [A]) = [B, A, object]`
- `L[C] = [C] + merge(L[A], [A]) = [C, A, object]`

现在算 `L[D]`：

```
L[D] = [D] + merge(L[B], L[C], [B, C])
     = [D] + merge([B, A, object], [C, A, object], [B, C])
```

`merge` 的规则是：扫描每个参与合并的列表，取其"头"（第一个元素），如果这个头不在任何其他列表的"尾"（除第一个之外的位置）中出现，就把它选出来；否则跳过这个列表，看下一个列表的头。

第 1 步：候选列表 `[B, A, object]`、`[C, A, object]`、`[B, C]`。看第一个列表的头 `B`：检查 `B` 是否出现在其它列表的非头位置——`[C, A, object]` 里没有 `B`、`[B, C]` 里 `B` 是头（不算）。所以 `B` 不在任何列表的尾部，取 `B`。从所有含 `B` 的列表里移除 `B`。

```
剩余：merge([A, object], [C, A, object], [C])
已选：D, B
```

第 2 步：第一个列表的头是 `A`。检查 `A` 是否在其它列表的尾部——`[C, A, object]` 里 `A` 处于非头位置（它是第二个元素，属于"尾"）。所以 `A` 不能取，跳过第一个列表。看第二个列表的头 `C`：检查 `C` 是否在其它列表的尾部——`[A, object]` 没有 `C`、`[C]` 里 `C` 是头（不算）。`C` 不在任何列表尾部，取 `C`。

```
剩余：merge([A, object], [A, object], [])
已选：D, B, C
```

第 3 步：第一个列表的头 `A`。检查 `A` 是否在其它列表的尾部——第二个列表 `[A, object]` 里 `A` 是头，不算尾部。空列表不算。`A` 不在任何列表尾部，取 `A`。

```
剩余：merge([object], [object], [])
已选：D, B, C, A
```

第 4 步：取 `object`。

```
最终：L[D] = [D, B, C, A, object]
```

**对照运行结果验证**

```python
print([c.__name__ for c in D.__mro__])
# 输出：['D', 'B', 'C', 'A', 'object']
```

和手算完全一致。关键观察是：`A` 虽然在 `L[B]` 里紧跟 `B`，但在最终顺序里被推到了 `C` 之后。这是因为 C3 必须保证 `C` 在 `A` 之前（`C` 是 `A` 的子类），同时也要保持继承列表 `[B, C]` 中 `B` 在 `C` 之前。深度优先的旧式算法会把 `A` 排在 `C` 之前（因为先沿 `B` 走到底），从而违背"`C` 是 `A` 的子类、应排在 `A` 前"这一单调性——这正是 Python 3 改用 C3 的核心动机。

**再看一个稍复杂的例子**

```python
class O:
    pass

class F(O):
    pass

class E(O):
    pass

class D(O):
    pass

class C(D, F):
    pass

class B(D, E):
    pass

class A(B, C):
    pass
```

先算各基类：

- `L[O] = [O, object]`
- `L[F] = [F, O, object]`
- `L[E] = [E, O, object]`
- `L[D] = [D, O, object]`

`L[C] = [C] + merge(L[D], L[F], [D, F]) = [C] + merge([D, O, object], [F, O, object], [D, F])`

- 取 `D`（不在任何尾）：`[C, D]`，剩余 `merge([O, object], [F, O, object], [F])`
- 头 `O`？在第二个列表尾部（`[F, O, object]` 里 `O` 非头），跳过。看第二列表头 `F`：不在任何尾，取 `F`：`[C, D, F]`，剩余 `merge([O, object], [O, object], [])`
- 取 `O`、再 `object`。

`L[C] = [C, D, F, O, object]`

`L[B] = [B] + merge(L[D], L[E], [D, E]) = [B] + merge([D, O, object], [E, O, object], [D, E])`

- 取 `D`：`[B, D]`，剩余 `merge([O, object], [E, O, object], [E])`
- 头 `O` 在第二列表尾，跳过。看 `E`：不在任何尾，取 `E`：`[B, D, E]`，剩余 `merge([O, object], [O, object], [])`
- 取 `O`、`object`。

`L[B] = [B, D, E, O, object]`

现在算 `L[A] = [A] + merge(L[B], L[C], [B, C]) = [A] + merge([B, D, E, O, object], [C, D, F, O, object], [B, C])`

- 取 `B`（不在任何尾）：`[A, B]`，剩余 `merge([D, E, O, object], [C, D, F, O, object], [C])`
- 头 `D` 在第二列表（`[C, D, F, O, object]`）的非头位置，跳过。看第二列表头 `C`：不在任何尾，取 `C`：`[A, B, C]`，剩余 `merge([D, E, O, object], [D, F, O, object], [])`
- 取 `D`：`[A, B, C, D]`，剩余 `merge([E, O, object], [F, O, object], [])`
- 头 `E`：不在任何尾，取 `E`：`[A, B, C, D, E]`，剩余 `merge([O, object], [F, O, object], [])`
- 头 `O` 在第二列表尾，跳过。看第二列表头 `F`：不在任何尾，取 `F`：`[A, B, C, D, E, F]`，剩余 `merge([O, object], [O, object], [])`
- 取 `O`、`object`。

最终 `L[A] = [A, B, C, D, E, F, O, object]`。

对照运行：

```python
print([c.__name__ for c in A.__mro__])
# 输出：['A', 'B', 'C', 'D', 'E', 'F', 'O', 'object']
```

一致。这个例子更能看出 C3 的精妙之处：`D` 在 `B` 和 `C` 的 MRO 里都紧随其后，但最终顺序里 `D` 排在 `B`、`C` 之后、`E`、`F` 之前——因为它必须等到"直接继承它的子类 `B`、`C`"都排完，才轮到自己，同时还要保持 `B` 在 `C` 之前、`E` 在 `F` 之前（继承列表顺序）。

### 2.5 super() 依赖 __mro__ 决定"下一个"

`super()` 是 Python 多继承协作的关键机制。很多人对 `super()` 的误解是"调用父类的方法"——这在新式类里并不准确。准确的描述是：**`super()` 调用的是 `__mro__` 中"当前类之后"的下一个类**。

这个"下一个"完全由 `__mro__` 决定，而不是由你在源码里写的"父类名字"决定。这就是为什么在多继承里，`super()` 能让多个 Mixin 协作地依次执行：每个 Mixin 调 `super()` 时，跳到的是 MRO 里的下一个类，而不是它自己声明继承的那个父类。

```python
class Base:
    def __init__(self):
        print("Base.__init__")

class MixinA(Base):
    def __init__(self):
        print("MixinA.__init__ 进入")
        super().__init__()  # 下一个是谁？看 MRO
        print("MixinA.__init__ 退出")

class MixinB(Base):
    def __init__(self):
        print("MixinB.__init__ 进入")
        super().__init__()
        print("MixinB.__init__ 退出")

class Composed(MixinA, MixinB):
    def __init__(self):
        print("Composed.__init__ 进入")
        super().__init__()
        print("Composed.__init__ 退出")

print("--- MRO ---")
print([c.__name__ for c in Composed.__mro__])
# 输出：['Composed', 'MixinA', 'MixinB', 'Base', 'object']

print("--- 实例化 ---")
Composed()
# 输出：
# Composed.__init__ 进入
# MixinA.__init__ 进入
# MixinB.__init__ 进入
# Base.__init__
# MixinB.__init__ 退出
# MixinA.__init__ 退出
# Composed.__init__ 退出
```

关键点：`MixinA.__init__` 里写的 `super().__init__()` 调用的并不是 `Base.__init__`（虽然 `MixinA` 源码里继承的是 `Base`），而是 `MixinB.__init__`！因为 `Composed` 的 MRO 是 `[Composed, MixinA, MixinB, Base, object]`，当执行到 `MixinA.__init__` 时，"当前类"是 `MixinA`，`super()` 找的是 MRO 里 `MixinA` 之后的那一个——也就是 `MixinB`，而不是源码里写的 `Base`。

这就是"super 走 MRO 而不走源码继承名"的核心。它带来的好处是：多个 Mixin 可以通过各自调用 `super()` 串成一条完整的初始化链，每个 Mixin 都能参与，不会因为某个 Mixin 直接继承 `Base` 而跳过其它兄弟。

**super 的两参数形式可以脱离实例使用**

`super()` 不传参时，靠的是隐式从当前方法栈拿到"当前类"和"实例"（`__class__` 隐式闭包变量 + 第一个参数 `self`/`cls`）。两参数形式 `super(当前类, 实例)` 让你显式指定起点，常用于元类方法、类方法里手动控制 `super` 的起点：

```python
class Logger:
    def __init__(self):
        print("Logger.__init__")

class Auth:
    def __init__(self):
        print("Auth.__init__")

class Service(Logger, Auth):
    def __init__(self):
        print("Service.__init__")
        # 显式从 Logger 的下一站开始找，跳过 Logger 本身
        super(Logger, self).__init__()  # 直接走 Auth.__init__
        print("Service.__init__ done")

# 解读：Service 的 MRO 是 [Service, Logger, Auth, object]
# super(Logger, self) 起点设为 Logger，"下一个"就是 Auth
Service()
# 输出：
# Service.__init__
# Auth.__init__
# Service.__init__ done
```

注意 `Logger.__init__` 没被调用——因为 `super(Logger, self)` 把起点设到了 `Logger`，下一个直接是 `Auth`。这种写法很少用，但理解它能让"super 走 MRO"的机制更扎实。

### 2.6 构造一个无法线性化的继承（TypeError）

C3 算法不是万能的：当继承结构存在不可调和的顺序冲突时，算法会失败，Python 会在 `class` 语句执行时直接抛 `TypeError`。这是一个非常良性的设计——让冲突在开发期就炸出来，而不是留到运行时产生方法覆盖 bug。

**经典冲突案例**

```python
class X:
    pass

class Y:
    pass

class A(X, Y):
    pass

# 试图让 B 的继承顺序和 A 相反
class B(Y, X):
    pass

# 再让 C 同时继承 A 和 B —— 这时 A 期望 X 在 Y 之前，B 期望 Y 在 X 之前
# 任何线性顺序都无法同时满足，C3 失败
try:
    class C(A, B):
        pass
except TypeError as e:
    print(e)
# 输出：Cannot create a consistent method resolution
# order for bases X, Y
```

**为什么会失败**

`A` 的 MRO 里 `X` 必须在 `Y` 之前（因为 `A` 的继承列表是 `X, Y`）。`B` 的 MRO 里 `Y` 必须在 `X` 之前（因为 `B` 的继承列表是 `Y, X`）。现在 `C` 同时继承 `A` 和 `B`，C3 要把 `L[A]` 和 `L[B]` 合并成一条链。但 `L[A]` 要求 `X` 在 `Y` 前，`L[B]` 要求 `Y` 在 `X` 前——这两条约束相互矛盾，没有任何一个线性顺序能同时满足。于是 `merge` 在尝试取 `X` 时发现它在某条尾部（`L[B]` 的尾部），尝试取 `Y` 时发现它在某条尾部（`L[A]` 的尾部），所有候选都被卡住，算法宣布失败。

逐步看一眼失败过程：

```
L[X] = [X, object]
L[Y] = [Y, object]
L[A] = [A, X, Y, object]
L[B] = [B, Y, X, object]

L[C] = [C] + merge(L[A], L[B], [A, B])
     = [C] + merge([A, X, Y, object], [B, Y, X, object], [A, B])

第 1 步：取 A（不在任何尾），接着取 B（不在任何尾）。
剩余：merge([X, Y, object], [Y, X, object], [])
已选：C, A, B

第 2 步：候选头 X。检查 X 是否在其它列表尾部——
  [Y, X, object] 中 X 处于非头位置，属于尾部。X 不能取。
候选头 Y。检查 Y 是否在其它列表尾部——
  [X, Y, object] 中 Y 处于非头位置，属于尾部。Y 不能取。
所有列表的头都无法选取，merge 失败 → TypeError。
```

这种"无法线性化"的根本原因是继承结构里存在循环约束。实务上避免的方法很简单：**多继承时，所有分支对同一组基类的继承顺序必须一致**。比如多个类都继承 `X, Y`，那就都按 `X, Y` 这个顺序写，不要有的写 `X, Y`、有的写 `Y, X`，否则一旦它们被某个类共同继承，就会触发 TypeError。

### 2.7 C3 与旧式类深度优先的差异

Python 2 时代存在"旧式类"（不继承 `object`）和"新式类"（继承 `object`）两种类，它们的 MRO 算法不同：旧式用"深度优先、从左到右"，新式用 C3。Python 3 统一为新式类，全部走 C3。理解这个差异有助于理解为什么 C3 必须被发明出来。

**旧式深度优先的问题**

用菱形继承举例：

```python
# 伪代码，描述旧式类的深度优先行为（Python 3 无法真正复现旧式类，
# 这里用 C3 的结果做对照说明差异）
#
# 旧式深度优先 MRO（假设）：
#   D → B → A → C → A  （A 被访问两次，且 C 排在 A 之后）
#
# C3 真实 MRO：
#   D → B → C → A
```

深度优先会先沿 `B` 走到底：`D → B → A`，然后再回来走 `C` 这一支：`C → A`。问题是：

1. `A` 被访问了两次，方法查找被 `A` 第一次出现截断，`C` 的方法永远轮不到——`C` 本应排在 `A` 之前（`C` 是 `A` 的子类），却排在了 `A` 之后，破坏了"子类优先"的单调性。
2. 同一个类在查找链里出现多次，浪费且语义混乱。

C3 通过合并算法把 `A` 推到所有子类之后，让 `A` 只出现一次，同时保证 `B` 在 `C` 之前（继承列表顺序）和 `C` 在 `A` 之前（子类优先）。来看 Python 3 里的真实表现：

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(A):
    def who(self):
        return "C"

class D(B, C):
    pass

# 旧式深度优先会给出 D-B-A-C-A（A 重复且 C 排在 A 后）
# C3 给出 D-B-C-A（A 不重复，C 在 A 前）
print([c.__name__ for c in D.__mro__])
# 输出：['D', 'B', 'C', 'A', 'object']

print(D().who())
# 输出：B
```

`D().who()` 命中 `B`，和旧式深度优先看似一样。差异体现在 `C` 的方法能否被 `D` 的兄弟链路过——比如如果 `B` 不定义 `who`，C3 会找 `C`（因为 `C` 在 `A` 之前），而旧式深度优先会跳过 `C` 直接找 `A`：

```python
class A2:
    def who(self):
        return "A2"

class B2(A2):
    pass  # 不覆盖 who

class C2(A2):
    def who(self):
        return "C2"

class D2(B2, C2):
    pass

print(D2().who())
# C3 下：B2 没 who，下一个是 C2，命中 → "C2"
# 旧式深度优先下会是 A2（直接沿 B2 走到 A2）

# 输出：C2
```

`C2` 的 `who` 被正确命中，因为 C3 保证了 `C2` 在 `A2` 之前。旧式深度优先会错成 `A2`，把 `C2` 的覆盖能力丢掉。这就是为什么 Python 3 必须用 C3——它让多继承的覆盖语义变得可预测。

### 2.8 __mro__ 与 isinstance / issubclass 的关系

`isinstance` 和 `issubclass` 在判断继承关系时，依据的也是 `__mro__`（更准确地说是依据继承图，但结果和 MRO 一致）。理解这一点可以解释一些边界行为。

```python
class Animal:
    pass

class Dog(Animal):
    pass

class Puppy(Dog):
    pass

print(isinstance(Puppy(), Animal))   # True
print(issubclass(Puppy, Animal))     # True
print(Animal in Puppy.__mro__)       # True
```

`Animal` 在 `Puppy.__mro__` 里，所以 `isinstance` 返回 `True`。反过来，如果你有一个不在 MRO 里、但通过某些 trick 混进来的"假继承"关系，`isinstance` 是不会认的。抽象基类（ABC）是个特殊例外：`abc.ABCMeta` 通过 `__subclasshook__` 让 `isinstance` 在没有真实继承关系时也能返回 `True`，但这走的是另一套机制，不影响 `__mro__` 的内容。

```python
from abc import ABC, abstractmethod

class Drawable(ABC):
    @classmethod
    def __subclasshook__(cls, subclass):
        # 只要子类有 draw 方法就认为是 Drawable 的子类
        return hasattr(subclass, "draw")

class Circle:
    def draw(self):
        pass

print(isinstance(Circle(), Drawable))  # True —— ABC 钩子
print(Circle in Drawable.__mro__)      # False —— 实际 MRO 里没有
# 输出：
# True
# False
```

这个例子提醒：`isinstance` 和 `__mro__` 在普通继承下一致，但在 ABC 钩子下可能分离。不能只凭 `isinstance` 为 `True` 就断言两个类有真实继承关系。

## 3. 最佳实践

**优先用组合而非复杂多继承**

C3 算法虽然能处理任意可线性化的继承图，但继承层次越深、Mixin 越多，MRO 就越难一眼读懂，方法覆盖的走向也越难预测。当一个类的 `__mro__` 超过 5~6 个自定义类时，就该警惕：是不是该把某些行为拆成独立对象、用组合（持有引用）而不是继承来复用？组合不会引入额外的查找链，行为也更可控。

```python
# 不推荐：继承层数过深、Mixin 过多，MRO 难读
class ValidatorMixin: ...
class SerializerMixin: ...
class AuditableMixin: ...
class SoftDeleteMixin: ...
class BaseModel: ...
class User(ValidatorMixin, SerializerMixin, AuditableMixin, SoftDeleteMixin, BaseModel): ...

# 推荐：把横切关注点拆成独立组件，组合使用
class User:
    def __init__(self):
        self.validator = Validator()
        self.serializer = Serializer()
        self.audit = Auditor()
```

**多继承时保持基类顺序一致**

如 2.6 节所示，多个类对同一组基类的继承顺序不一致，一旦被共同继承就会触发 `TypeError`。团队约定一条规则：当多个 Mixin/基类一起出现时，统一按某个固定顺序写（比如"日志、序列化、业务基类"），不要随意颠倒。

```python
# 不推荐：A 里 X,Y；B 里 Y,X —— 共同继承会 TypeError
class A(X, Y): ...
class B(Y, X): ...
class C(A, B): ...  # 炸

# 推荐：统一顺序
class A(X, Y): ...
class B(X, Y): ...
class C(A, B): ...  # 安全
```

**Mixin 的方法必要时要 super()，不要只覆盖**

一个合格的 Mixin 在覆盖某个方法时，应当用 `super()` 把调用传递给 MRO 的下一站，而不是直接"截断"覆盖。否则它会破坏协作链，让排在 MRO 后面的 Mixin 永远拿不到调用：

```python
# 不推荐：AuditMixin 截断了 BaseModel.save
class BaseModel:
    def save(self):
        print("落库")

class AuditMixin:
    def save(self):
        print("记日志")  # 没调 super，BaseModel.save 永远不执行

class User(AuditMixin, BaseModel): pass
User().save()
# 输出：记日志（只记了日志，没落库）

# 推荐：AuditMixin 用 super() 传递
class AuditMixinGood:
    def save(self):
        print("记日志")
        super().save()  # 转给 MRO 下一站

class UserGood(AuditMixinGood, BaseModel): pass
UserGood().save()
# 输出：
# 记日志
# 落库
```

**不要依赖 __mro__ 里的具体下标**

查找顺序应该作为"概念上的链"来理解，不要在业务代码里写死 `cls.__mro__[3]` 这种下标引用——继承结构一调整，下标就变了，代码会悄悄出错。需要按顺序处理时，遍历 `__mro__` 并按条件判断：

```python
# 不推荐
next_cls = SomeClass.__mro__[2]

# 推荐
for cls in type(self).__mro__:
    if hasattr(cls, "_special_marker"):
        next_cls = cls
        break
```

**遇到 TypeError 先画继承图再改**

当 Python 报 `Cannot create a consistent method resolution order` 时，不要急着用 try/except 吃掉或颠倒顺序硬试。把继承图画出来，找出哪两个类对同一组基类的顺序冲突了，然后统一顺序。这种错误的根本解法永远是"理顺继承结构"，而不是绕过 C3。

## 4. 原理

C3 线性化算法是理解 `__mro__` 的关键。本节详细推导算法本身、它保证的性质、失败条件，以及 `super` 沿 MRO 查找的内部依据。

### 4.1 线性化的目标与约束

给定一个类 `C` 继承自 `B1, B2, ..., Bn`（基类列表），线性化的目标是产生一个序列 `L[C]`，满足三条约束：

1. **自身在前**：`C` 出现在序列开头。
2. **子类在父类前（单调性）**：如果 `Bi` 是 `C` 的直接基类，则 `Bi` 在 `L[C]` 中出现在 `C` 之后；更一般地，若类 `X` 是类 `Y` 的子类（不论隔着多少层），则 `X` 在 `L[C]` 中排在 `Y` 之前——只要它们都出现在 `L[C]` 里。
3. **基类列表顺序保持**：若 `i < j`，则 `Bi` 在 `L[C]` 中出现在 `Bj` 之前（除非被约束 2 否决）。这条约束让继承列表的书写顺序具有语义意义。

这三条约束合在一起就是一个偏序关系。C3 的任务是把偏序扩展成全序（线性序列）。当偏序里存在矛盾（比如 `X` 既要在 `Y` 前、又要在 `Y` 后）时，就无法扩展，算法报错。

### 4.2 递归合并算法

C3 用递归定义每个类的线性化：

```
L[C] = C + merge(L[B1], L[B2], ..., L[Bn], [B1, B2, ..., Bn])
```

- `+` 是列表拼接：`[C]` 拼上 `merge(...)` 的结果。
- `merge` 接收若干个列表（前 n 个是各基类自己的线性化 `L[Bi]`，最后一个是 `C` 的直接基类列表 `[B1, ..., Bn]`），输出一个合并后的列表。

**merge 的取头规则**

`merge` 重复执行以下步骤直到所有列表都空：

1. 取第一个非空列表的"头"（第一个元素），记为 `h`。
2. 检查 `h` 是否出现在任何其它列表的"尾"（除第一个元素外的部分）中。
   - 如果不在任何其它列表的尾中：把 `h` 选入结果，并从所有含 `h` 的列表里移除 `h`（从头移除）。回到步骤 1。
   - 如果在某个其它列表的尾中：跳过当前列表，看下一个非空列表的头，重复步骤 2。
3. 如果所有非空列表的头都"在某个其它列表的尾中"（即没有任何头可取），`merge` 失败，算法报 `TypeError`。

这条"头不能在任何其它列表尾部出现"的规则，本质上是约束 2（子类在父类前）的操作化体现：如果一个类 `h` 出现在某个列表的尾部，意味着存在另一个类（那个列表的头）是 `h` 的子类（它把 `h` 排在自己之后），所以 `h` 不能在结果里排在那个子类之前——必须等那个子类先被选出。

### 4.3 算法保证的性质

C3 被设计为保证以下性质，这些性质让方法解析的语义可预测：

**单调性（Monotonicity）**

若类 `X` 在类 `Y` 的线性化 `L[Y]` 中排在 `Z` 之前，且 `X` 也出现在 `Z` 的子类 `W` 的线性化 `L[W]` 里，则 `X` 在 `L[W]` 中仍排在 `Z` 之前。简言之：子类的线性化不会"颠倒"父类线性化里既有的顺序。这条性质保证了：当你把一个 Mixin 加到不同基类上时，它在不同组合里的相对顺序不会自相矛盾。

**一致性（Consistency / 基类列表顺序保持）**

直接基类列表 `[B1, B2, ..., Bn]` 的顺序在 `L[C]` 中被保持（除了被单调性否决的情况）。这条让继承列表的书写顺序成为可依赖的语义。

**无重复**

`L[C]` 中每个类只出现一次。菱形继承下，共享的顶层基类（如 `object`）只会排在所有子类之后、出现一次，不会被分支各自带出来。

**object 永远在末尾**

因为所有类的最终基类都是 `object`，单调性要求 `object` 排在所有其它类之后，所以 `L[C]` 的末尾恒为 `object`。

### 4.4 失败条件与 TypeError 的产生

`merge` 失败的条件是：所有非空候选列表的头都"卡在某个其它列表的尾部"。这等价于偏序里存在无法同时满足的约束——典型的形态是两个基类的线性化里对同一对类的顺序有相反要求。

更形式化地：若存在类 `X` 和 `Y`，使得在某条基类线性化 `L[Bi]` 里 `X` 在 `Y` 之前，而在另一条 `L[Bj]` 里 `Y` 在 `X` 之前，且 `X`、`Y` 都必须出现在最终结果里，那么任何线性顺序都无法同时满足，C3 失败。Python 在 `class` 语句执行、调用 `type.__new__` 计算 MRO 时捕获这一失败并抛出：

```
TypeError: Cannot create a consistent method resolution
order for bases X, Y
```

错误信息里列出的"bases"就是冲突的那对类。这是一种"早失败"设计——把继承结构的不可调和矛盾暴露在类定义时，而不是留到方法调用时产生一个反直觉的命中结果。

### 4.5 super 沿 __mro__ 找下一类的依据

`super()` 的实现在 C 层（CPython 的 `Objects/typeobject.c` 里的 `super` 类型）。其核心逻辑可以概括为：

1. 确定"当前类"（`super()` 无参时通过隐式闭包变量 `__class__` 拿到定义该方法的类；两参数形式 `super(start, obj)` 显式指定）。
2. 拿到实例的类型：`type(obj)`（对于类方法则是 `obj` 本身）。
3. 在 `type(obj).__mro__` 里查找"当前类"的位置，取它之后第一个类作为 `super` 代理的目标。
4. 后续属性访问会在这个目标类的 `__dict__` 及其 `__mro__` 后续位置里查找。

这个机制解释了 2.5 节的关键现象：`super()` 跳到的是 `__mro__` 里的下一个类，而不是源码里写的父类。因为查找起点是"当前类在 `__mro__` 里的位置"，而 `__mro__` 是 C3 算出来的合并线性化，可能和源码继承名不一致（在多继承下几乎总是不一致）。

这也解释了为什么 `super()` 必须在方法内部使用、且依赖隐式 `__class__`——它需要知道"当前正在执行的方法属于哪个类"，才能在 MRO 里定位。脱离方法上下文（比如在模块顶层调 `super()`）会报错，因为没有"当前类"的概念。

### 4.6 C3 算法的伪代码

把算法写成伪代码，便于在脑中模拟：

```
function linearize(C):
    # C 的直接基类列表
    bases = C.__bases__  # [B1, B2, ..., Bn]
    # 各基类的线性化（递归已有结果）
    partial = [linearize(B) for B in bases]
    # 加上基类列表本身
    partial.append(list(bases))
    # 合并
    merged = merge(partial)
    return [C] + merged

function merge(lists):
    result = []
    lists = [l for l in lists if len(l) > 0]  # 过滤空列表
    while lists:
        head = None
        for l in lists:
            h = l[0]
            # 检查 h 是否在任何其它列表的尾部
            in_tail = any(h in other[1:] for other in lists if other is not l)
            if not in_tail:
                head = h
                break
        if head is None:
            raise TypeError("Cannot create a consistent MRO")
        result.append(head)
        # 从所有列表头部移除 head
        for l in lists:
            if l[0] == head:
                l.pop(0)
        lists = [l for l in lists if len(l) > 0]
    return result
```

用任何具体例子套这段伪代码，都能复现 Python 的真实 `__mro__`。理解这段伪代码后，面对任何继承图都能手算 MRO，而不必靠运行 Python 试试看。

### 4.7 与旧式深度优先的机制对比

旧式类的深度优先算法（Python 2 旧式类使用）没有 `merge` 步骤，它只是简单地"从左到右深度优先遍历继承树"，遇到访问过的类就跳过。这种做法的问题在于它不维护单调性：

- 深度优先会先沿最左分支走到底，把那条分支上的所有祖先（包括共享的顶层基类）都排进去，然后再走下一分支。共享基类被第一次访问后就跳过，导致后续分支里的中间类（它们是共享基类的子类、本应排在共享基类之前）被排到共享基类之后。
- 这破坏了"子类在父类前"的约束，让中间类的方法永远无法覆盖共享基类的方法。

C3 通过 `merge` 把"各分支的线性化"合并，而不是简单拼接，并在取头时检查"是否在其它列表尾部"，从机制上杜绝了这种破坏。共享基类必须等所有分支里它的所有子类都已入选后才能入选，从而保证子类在前。

Python 2.2 引入新式类时先用了一种"广度优先"的过渡算法（仍不满足单调性），2.3 起改为 C3。Python 3 直接只保留新式类，C3 成为唯一的方法解析算法。这也意味着 Python 3 的开发者完全不必担心"旧式 vs 新式"的差异——一切继承都走 C3，行为统一可预测。

## 5. 总结

本文围绕 Python 3 的方法解析顺序（MRO）展开，核心要点如下：

- **MRO 是什么**：方法解析顺序，一个类的方法查找线性表，存在 `__mro__` 属性（只读元组）和 `mro()` 方法（返回列表）两种查阅形式。
- **C3 线性化**：Python 3 用 C3 算法计算 MRO。算法递归定义为 `L[C] = C + merge(L[B1], ..., L[Bn], [B1, ..., Bn])`，`merge` 按"取头、检查头不在任何其它列表尾部"的规则逐步合并。
- **保证的性质**：子类在父类前（单调性）、直接基类列表顺序保持（一致性）、每个类只出现一次（无重复）、`object` 永远末尾。
- **失败条件**：当继承结构里存在对同一对类的相反顺序约束（如 `A` 里 `X` 在 `Y` 前、`B` 里 `Y` 在 `X` 前，再被共同继承）时，`merge` 无头可取，Python 在类定义时抛 `TypeError: Cannot create a consistent method resolution order`。
- **super 与 MRO 的关系**：`super()` 调用的是 `__mro__` 中"当前类之后"的下一个类，不是源码继承名。这让多 Mixin 能通过各自的 `super()` 串成协作链。
- **与旧式深度优先的差异**：深度优先会破坏单调性（共享基类被提前访问、中间类排到共享基类之后），C3 的 `merge` 从机制上避免这一问题。
- **实战要点**：排查方法覆盖看 `__mro__`；Mixin 覆盖方法时务必 `super()` 传递；多继承对同一组基类的顺序保持一致以避免 TypeError；继承过深时优先用组合。

读完本文你应能掌握：

- 能准确解释 `__mro__` 与 `mro()` 的区别和只读性质，并在代码中正确查阅。
- 能手算一个多继承（含菱形）类的 C3 线性化结果，并用 `print(cls.__mro__)` 验证。
- 能判断给定的继承结构是否会触发 `TypeError`，并解释失败原因（偏序矛盾）。
- 能说明 `super()` 为何在 `MixinA` 里调用却跳到 `MixinB`（MRO 下一个，而非源码父类），并写出协作式 Mixin 的正确 `super()` 模式。
- 能在遇到 `Cannot create a consistent MRO` 时，通过画继承图、对比各基类继承顺序定位冲突并修正。
