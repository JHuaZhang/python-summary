# 字典的哈希机制与键要求

## 1. 介绍

### 1.1 要理解什么

字典是 Python 中最高频使用的数据结构之一。你可能已经知道字典由"键值对"组成，通过 `d[key]` 可以快速取出对应的值——但你有没有想过以下几个问题：

- 为什么字典的键可以是整数、字符串、元组，却不能是列表、字典、集合？
- 为什么字典查找速度比列表快那么多？
- 为什么 `True` 和 `1` 在字典里会被当作同一个键？
- 为什么修改了作为键的对象之后，字典里就找不到它了？

这些问题的答案都指向同一个底层机制：**哈希表（Hash Table）**。

字典的本质是一张哈希表。理解哈希机制，你就能判断什么类型的对象可以做键、为什么字典查找是 O(1)、自定义类作为键时要遵守什么规则，以及如何避开"修改键对象导致查找失败"这类隐蔽 bug。

### 1.2 为什么需要理解它

如果你只把字典当作"键值对容器"来用，不考虑键的类型约束，写代码时迟早会踩到这些坑：

- 拿列表当字典键，绞尽脑汁想不通为什么报 `TypeError: unhashable type: 'list'`
- 自定义类做了字典键，修改对象属性后发现字典里找不到那个键了
- 定义了 `__eq__` 却没定义 `__hash__`，导致对象突然不能做键了
- 用 `True` 和 `1` 做不同含义的键，结果它们被当成同一个键互相覆盖

理解哈希机制后，这些问题都能从原理层面解释和避免，你也能在需要时正确实现自定义类作为字典键的逻辑。

## 2. 整体架构

### 2.1 哈希表的核心思想

字典底层是一张**哈希表**——一种通过"哈希函数"将键映射到存储位置的数据结构。核心思想可以类比为图书馆找书：

- 每本书有一个编号（哈希值）
- 编号通过一定规则映射到书架位置（数组下标）
- 直接走到对应书架取书，不需要逐本翻找

与传统数组的对比：

| 维度 | 数组/列表 | 哈希表（字典） |
|------|----------|--------------|
| 查找方式 | 从头到尾逐个比较 | 算出位置直接跳过去 |
| 查找复杂度 | O(n) | O(1)（平均） |
| 插入方式 | 追加或插入到指定位置 | 算出位置直接放入 |
| 键类型要求 | 整数索引 | 任意可哈希对象 |
| 最坏情况 | O(n) | O(n)（所有键冲突时退化） |

### 2.2 哈希表的工作流程

字典的一次查找操作（`d[key]`）经历以下步骤：

```text
查找 d[key]
    │
    ▼
┌─────────────────┐
│  1. 计算 hash(key)  │  ← 调用 key.__hash__() 得到哈希值
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. 定位数组下标    │  ← hash(key) % table_size 得到初始位置
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  3. 检查该位置     │  ← 位置为空 → 键不存在，返回 KeyError
│    是否有键值对    │  ← 位置有键值对 → 进入比较
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 4. 比较 key 是否   │  ← 调用 key.__eq__(stored_key)
│    等于存储的键    │  ← 相等 → 返回对应的 value
└────────┬────────┘  ← 不相等 → 哈希冲突，走冲突解决
         │
         ▼
┌─────────────────┐
│ 5. 冲突解决        │  ← 开放寻址法：向后探测下一个位置
│    （开放寻址）    │  ← 重复步骤 3-4，直到找到或确认不存在
└─────────────────┘
```

这个流程揭示了哈希表查找高效的原因：不需要遍历所有键，而是通过哈希函数直接跳到目标位置附近。

### 2.3 Python 字典的内部结构

CPython 3.6+ 的字典采用**紧凑字典（compact dict）**实现，由两个数组组成：

```text
┌──────────────────────────────────────────────────────┐
│                    PyDictObject                       │
│                                                       │
│  ┌─────────────────┐    ┌─────────────────────────┐  │
│  │  稀疏数组        │    │  紧凑数组                 │  │
│  │  (dk_indices)   │    │  (dk_entries)            │  │
│  │                  │    │                          │  │
│  │  索引数组         │    │  实际键值对               │  │
│  │  较大、稀疏       │    │  较小、紧凑               │  │
│  │                  │    │                          │  │
│  │ [3] → 指向 entry │    │  entry 0: hash, key, val │  │
│  │ [ ] → 空         │    │  entry 1: hash, key, val │  │
│  │ [1] → 指向 entry │    │  entry 2: hash, key, val │  │
│  │ [0] → 指向 entry │    │  entry 3: hash, key, val │  │
│  │ [ ] → 空         │    │                          │  │
│  │ ...              │    │  无空洞，插入顺序存储      │  │
│  └─────────────────┘    └─────────────────────────┘  │
│                                                       │
│  定位流程:                                             │
│  hash(key) → index = hash % indices_size             │
│  → dk_indices[index] → entry_index                    │
│  → dk_entries[entry_index] → {hash, key, value}       │
└──────────────────────────────────────────────────────┘
```

这种"稀疏索引 + 紧凑条目"的设计有两个好处：

1. **内存节省**：稀疏数组只存整数索引（指向紧凑数组中的位置），实际键值对紧凑排列无空洞
2. **保持插入顺序**：紧凑数组按插入顺序追加，因此 Python 3.7+ 保证字典保留键的插入顺序

## 3. 关键机制拆解

### 3.1 哈希函数：hash() 的作用

哈希函数是哈希表的基石。Python 内置的 `hash()` 函数接收一个对象，返回一个整数——这个整数就是对象的"哈希值"。

**哈希函数的三个核心性质**：

| 性质 | 说明 | 示例 |
|------|------|------|
| 确定性 | 同一对象在同一进程内哈希值不变 | `hash(42)` 多次调用结果相同 |
| 快速计算 | 哈希值计算应高效 | `hash("hello")` 瞬间得到 |
| 均匀分布 | 不同对象应尽量产生不同哈希值 | 减少冲突概率 |

用代码观察不同类型对象的哈希值：

```python
# 整数的哈希值就是它自身（小整数）
print(f"hash(42)  = {hash(42)}")
print(f"hash(0)    = {hash(0)}")
print(f"hash(-1)   = {hash(-1)}")

# 浮点数的哈希经过特殊处理
print(f"hash(3.14) = {hash(3.14)}")
print(f"hash(1.0)  = {hash(1.0)}")

# 字符串的哈希经过复杂计算
print(f"hash('hello') = {hash('hello')}")

# 元组的哈希递归组合元素
print(f"hash((1, 2, 3)) = {hash((1, 2, 3))}")
```

运行结果：

```text
hash(42)  = 42
hash(0)    = 0
hash(-1)   = -2
hash(3.14) = 322818021289917443
hash(1.0)  = 1
hash('hello') = -4791436340740924009
hash((1, 2, 3)) = 529344067295497451
```

**一个关键观察**：`hash(1)` 和 `hash(1.0)` 结果相同。这是因为 Python 规定：**两个相等的对象必须有相同的哈希值**。`1 == 1.0` 为 `True`，所以它们的哈希值也必须相等。这个规则在后面理解 `True` 和 `1` 的冲突时非常重要。

`hash(-1)` 返回 `-2` 而不是 `-1`，因为 CPython 在 C 层面用 `-1` 表示错误，所以 Python 层面 `-1` 的哈希值被特殊处理为 `-2`。

### 3.2 可哈希与不可哈希：键类型约束

字典的键必须是**可哈希对象**。一个对象可哈希意味着它满足两个条件：

1. **实现了 `__hash__` 方法**：调用 `hash()` 能返回一个整数
2. **实现了 `__eq__` 方法**：能与另一个对象比较是否相等
3. **哈希值在生命周期内不变**：对象的哈希值一旦确定就不应再改变

Python 内置类型的可哈希性如下：

| 类型 | 可哈希 | 能否做键 | 原因 |
|------|--------|---------|------|
| `int` | 是 | 可以 | 不可变，`__hash__` 返回自身值 |
| `float` | 是 | 可以 | 不可变，`__hash__` 基于 IEEE 754 位模式 |
| `bool` | 是 | 可以 | `True` 哈希为 1，`False` 哈希为 0 |
| `str` | 是 | 可以 | 不可变，`__hash__` 基于内容计算 |
| `tuple` | 看情况 | 元素均可哈希时可以 | 不可变，`__hash__` 递归调用元素的 `hash` |
| `frozenset` | 是 | 可以 | 不可变，`__hash__` 基于元素集合计算 |
| `None` | 是 | 可以 | `hash(None)` 返回 0 |
| `list` | 否 | 不可以 | 可变，无 `__hash__` |
| `dict` | 否 | 不可以 | 可变，无 `__hash__` |
| `set` | 否 | 不可以 | 可变，无 `__hash__` |
| `bytearray` | 否 | 不可以 | 可变，无 `__hash__` |

用代码验证不可哈希类型：

```python
# 列表不可哈希
try:
    hash([1, 2, 3])
except TypeError as e:
    print(f"hash([1, 2, 3]) → TypeError: {e}")

# 字典不可哈希
try:
    hash({1: 2})
except TypeError as e:
    print(f"hash({{1: 2}}) → TypeError: {e}")

# 集合不可哈希
try:
    hash({1, 2, 3})
except TypeError as e:
    print(f"hash({{1, 2, 3}}) → TypeError: {e}")
```

运行结果：

```text
hash([1, 2, 3]) → TypeError: unhashable type: 'list'
hash({1: 2}) → TypeError: unhashable type: 'dict'
hash({1, 2, 3}) → TypeError: unhashable type: 'set'
```

**元组的特殊性**：元组本身不可变，但只有当它的所有元素都可哈希时，元组才是可哈希的。如果元组包含了列表等不可哈希元素，整个元组也变成不可哈希。

```python
# 元素均可哈希 → 元组可哈希
print(f"hash((1, 2, 3)) = {hash((1, 2, 3))}")

# 包含列表 → 元组不可哈希
try:
    hash((1, [2, 3], 4))
except TypeError as e:
    print(f"hash((1, [2, 3], 4)) → TypeError: {e}")
```

运行结果：

```text
hash((1, 2, 3)) = 529344067295497451
hash((1, [2, 3], 4)) → TypeError: unhashable type: 'list'
```

**为什么可变对象不可哈希？** 因为可变对象的内容可以改变，如果允许它做键，添加到字典后再修改内容，哈希值就变了，字典就无法再找到这个键。为了避免这种逻辑漏洞，Python 直接禁止可变类型实现 `__hash__`。

### 3.3 哈希冲突：当两个键映射到同一位置

哈希函数的输出空间是无限的（任意大的整数），而哈希表的数组大小是有限的。因此，不同的键可能计算出相同的数组下标——这就是**哈希冲突（Hash Collision）**。

需要区分两种"冲突"：

| 概念 | 含义 | 后果 |
|------|------|------|
| 哈希值相同 | `hash(a) == hash(b)` 但 `a != b` | 需要冲突解决策略 |
| 键完全相同 | `a == b`（哈希值也必然相同） | 后者覆盖前者的值 |

**Python 字典使用开放寻址法（Open Addressing）** 解决冲突：当目标位置已被占用时，按一定规则探测下一个位置，直到找到空位或匹配的键。

```text
插入 key1（hash=5, table_size=8）
  → index = 5 % 8 = 5 → 位置 5 为空 → 存入位置 5

插入 key2（hash=13, table_size=8）
  → index = 13 % 8 = 5 → 位置 5 已被 key1 占用 → 哈希冲突！
  → 开放寻址：探测位置 6 → 位置 6 为空 → 存入位置 6

查找 key2
  → index = 13 % 8 = 5 → 位置 5 是 key1 ≠ key2
  → 探测位置 6 → 位置 6 是 key2 == key2 → 找到！
```

哈希冲突本身不影响正确性——字典仍能准确存取。但冲突越多，查找需要的探测次数就越多，性能就越差。极端情况下，如果所有键的哈希值都相同，字典退化为链表，查找从 O(1) 退化为 O(n)。

用代码验证哈希冲突的性能影响：人为让所有对象的 `__hash__` 返回相同值。

```python
import time


class BadHash:
    """所有对象哈希值相同，人为制造冲突"""
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, BadHash) and self.name == other.name

    def __hash__(self):
        return 42  # 固定哈希值


class GoodHash:
    """正常哈希"""
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, GoodHash) and self.name == other.name

    def __hash__(self):
        return hash(self.name)  # 不同 name 产生不同哈希

    def __repr__(self):
        return f"GoodHash('{self.name}')"


N = 1000
bad_keys = [BadHash(f"key_{i}") for i in range(N)]
good_keys = [GoodHash(f"key_{i}") for i in range(N)]

bad_dict = {k: i for i, k in enumerate(bad_keys)}
good_dict = {k: i for i, k in enumerate(good_keys)}

# 测试查找最后一个键的时间
start = time.perf_counter()
for _ in range(10000):
    _ = bad_dict[bad_keys[-1]]
bad_time = time.perf_counter() - start

start = time.perf_counter()
for _ in range(10000):
    _ = good_dict[good_keys[-1]]
good_time = time.perf_counter() - start

print(f"BadHash 字典查找 10000 次: {bad_time:.6f}s")
print(f"GoodHash 字典查找 10000 次: {good_time:.6f}s")
print(f"冲突字典慢了 {bad_time / good_time:.1f} 倍")
```

运行结果：

```text
BadHash 字典查找 10000 次: 0.603981s
GoodHash 字典查找 10000 次: 0.001373s
冲突字典慢了 439.8 倍
```

439 倍的差距清楚地展示了哈希冲突对性能的影响。正常情况下 Python 内置类型的哈希函数分布均匀，不会出现这种极端退化。

### 3.4 哈希一致性规则：相等的对象必须哈希相同

Python 的哈希机制有一条铁律：**如果 `a == b` 为 `True`，那么 `hash(a)` 必须等于 `hash(b)`**。反过来说不成立——`hash(a) == hash(b)` 不意味着 `a == b`（这是哈希冲突正常存在的原因）。

这条规则解释了一组反直觉的行为：

**整数与浮点数的"合并"**：

```python
d = {1: "int", 1.0: "float"}
print(f"len(d) = {len(d)}")
print(f"d[1]   = {d[1]}")
print(f"d[1.0] = {d[1.0]}")
```

运行结果：

```text
len(d) = 1
d[1]   = float
d[1.0] = float
```

`1 == 1.0` 为 `True`，且 `hash(1) == hash(1.0)` 也为 `True`，字典把它们当作同一个键，第二个赋值 `1.0: "float"` 覆盖了第一个 `1: "int"`。

**布尔值与整数的"合并"**：

```python
d2 = {1: "one", True: "boolean_true"}
print(f"len(d2)   = {len(d2)}")
print(f"d2[1]     = {d2[1]}")
print(f"d2[True]  = {d2[True]}")
```

运行结果：

```text
len(d2)   = 1
d2[1]     = boolean_true
d2[True]  = boolean_true
```

`True == 1` 为 `True`，`hash(True) == hash(1)` 为 `True`（`True` 的哈希值就是 1），因此 `True` 和 `1` 被视为同一键。这是一个容易踩的坑——如果你用 `0` 和 `False`、`1` 和 `True` 做不同含义的键，它们会互相覆盖。

**实际编程中应避免用布尔值做键**，因为 `True`/`False` 只有两个值，且会和 `1`/`0` 冲突。如果需要二值状态映射，用字符串 `"yes"`/`"no"` 更安全。

### 3.5 自定义类作为键：__eq__ 与 __hash__ 的协作

当你定义一个类并希望它的实例能作为字典键时，必须同时实现 `__eq__` 和 `__hash__`，并且保持两者的一致性。

**默认行为**：如果不定义 `__eq__` 和 `__hash__`，对象默认基于 `id()`（内存地址）做比较和哈希——两个不同对象即使内容相同也不相等，不能互相查找。

```python
class Default:
    def __init__(self, name):
        self.name = name

d1 = Default("a")
d2 = Default("a")
print(f"d1 == d2: {d1 == d2}")               # False
print(f"hash(d1) == hash(d2): {hash(d1) == hash(d2)}")  # False

d = {d1: 100}
print(f"d[d1] = {d[d1]}")                   # 100
# d[d2] → KeyError，因为 d2 和 d1 不是"同一个键"
```

**只定义 `__eq__` 的陷阱**：如果只定义了 `__eq__` 没定义 `__hash__`，Python 会**自动将 `__hash__` 设为 `None`**，使对象变为不可哈希。

```python
class EqOnly:
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, EqOnly) and self.name == other.name

obj = EqOnly("test")
print(f"EqOnly.__hash__ = {EqOnly.__hash__}")  # None

try:
    hash(obj)
except TypeError as e:
    print(f"hash(obj) → TypeError: {e}")
```

运行结果：

```text
EqOnly.__hash__ = None
hash(obj) → TypeError: unhashable type: 'EqOnly'
```

这是 Python 的安全机制：定义了 `__eq__` 意味着你希望按内容比较对象，但默认的 `__hash__`（基于 `id()`）与按内容比较的 `__eq__` 不一致，违反了"相等对象必须哈希相同"的规则。Python 宁可让你显式定义 `__hash__`，也不默默使用不一致的默认实现。

**正确做法**：同时实现 `__eq__` 和 `__hash__`，确保相等的对象有相同的哈希值。

```python
class Student:
    def __init__(self, student_id, name):
        self.student_id = student_id
        self.name = name

    def __eq__(self, other):
        if not isinstance(other, Student):
            return NotImplemented
        return self.student_id == other.student_id

    def __hash__(self):
        return hash(self.student_id)  # 基于学号计算哈希

s1 = Student(1001, "张三")
s2 = Student(1001, "张三")
print(f"s1 == s2: {s1 == s2}")                    # True
print(f"hash(s1) == hash(s2): {hash(s1) == hash(s2)}")  # True

score_map = {s1: 95}
print(f"score_map[s2] = {score_map[s2]}")         # 95
```

### 3.6 __hash__ 应基于不可变属性

定义 `__hash__` 时有一个关键原则：**哈希值只能基于对象的不可变属性计算**。如果基于可变属性计算哈希，修改属性后哈希值改变，字典就无法再找到这个键。

**反面示例——基于可变属性**：

```python
class MutableKey:
    def __init__(self, val):
        self.val = val  # 可变属性

    def __eq__(self, other):
        return isinstance(other, MutableKey) and self.val == other.val

    def __hash__(self):
        return hash(self.val)  # 基于可变属性 → 有隐患


mk = MutableKey(10)
d = {mk: "value_10"}
print(f"d[mk] = {d[mk]}")  # 正常找到

# 修改属性值
mk.val = 99
print(f"hash(mk) = {hash(mk)}")  # 哈希值变成 99

try:
    print(f"d[mk] = {d[mk]}")
except KeyError as e:
    print(f"d[mk] → KeyError: {e}")
```

运行结果：

```text
d[mk] = value_10
hash(mk) = 99
d[mk] → KeyError: MutableKey(99)
```

修改 `mk.val` 后，`hash(mk)` 从 10 变成 99，字典再去查找时用新的哈希值定位到一个空位置（或无关位置），找不到原来的键了。而且原来的键还"卡"在旧哈希值对应的位置上，成了无法访问的"孤儿"。

**正面示例——基于不可变属性**：

```python
class Product:
    def __init__(self, sku, name, price):
        self.sku = sku          # 不可变标识
        self.name = name        # 可变
        self.price = price      # 可变

    def __eq__(self, other):
        return isinstance(other, Product) and self.sku == other.sku

    def __hash__(self):
        return hash(self.sku)   # 只基于不可变的 sku

p1 = Product("A001", "手机", 2999)
p2 = Product("A001", "手机Pro", 3999)  # 名称价格不同
print(f"p1 == p2: {p1 == p2}")                    # True
print(f"hash(p1) == hash(p2): {hash(p1) == hash(p2)}")  # True

product_stock = {p1: 100}
print(f"product_stock[p2] = {product_stock[p2]}")  # 100
```

`__hash__` 只基于 `sku`，即使 `name` 和 `price` 变了，哈希值不变，查找不受影响。

**最佳实践——使用 frozen dataclass**：如果你不想手写 `__eq__` 和 `__hash__`，可以用 `@dataclass(frozen=True)` 让 Python 自动生成一行代码不可变的类：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Point:
    x: float
    y: float


pt1 = Point(1.0, 2.0)
pt2 = Point(1.0, 2.0)
print(f"pt1 == pt2: {pt1 == pt2}")                    # True
print(f"hash(pt1) == hash(pt2): {hash(pt1) == hash(pt2)}")  # True

d = {pt1: "origin"}
print(f"d[pt2] = {d[pt2]}")                           # origin

# 尝试修改 → 报错
try:
    pt1.x = 99
except Exception as e:
    print(f"pt1.x = 99 → {type(e).__name__}: {e}")
```

运行结果：

```text
pt1 == pt2: True
hash(pt1) == hash(pt2): True
d[pt2] = origin
pt1.x = 99 → FrozenInstanceError: cannot assign to field 'x'
```

`frozen=True` 使对象不可变，自动实现了 `__eq__` 和 `__hash__`，且从机制上杜绝了"修改属性导致哈希值改变"的问题。这是自定义类作为字典键最安全、最省心的方式。

### 3.7 哈希随机化：PYTHONHASHSEED

如果你多次运行 Python 程序，会发现字符串的哈希值每次都不一样：

```python
print(f"hash('hello') = {hash('hello')}")
```

第一次运行可能输出 `hash('hello') = -4791436340740924009`，第二次运行输出 `hash('hello') = -3761099879366823174`。

这是因为 Python 3.3+ 默认启用了**哈希随机化**——每次启动 Python 进程时，用随机种子初始化字符串/字节串的哈希函数。这个机制的安全目的是防止恶意构造的输入引发大量哈希冲突（哈希冲突 DoS 攻击）。

**数值类型不受影响**：整数、浮点数、布尔值的哈希值是固定的，不受哈希随机化影响。

| 类型 | 哈希值是否随进程变化 | 原因 |
|------|-------------------|------|
| `int` / `float` / `bool` | 不变 | 哈希值由值的数学性质决定 |
| `str` / `bytes` | 变化 | 哈希随机化，每次进程用不同种子 |
| `tuple`（含 str 元素） | 变化 | 递归调用元素哈希，受 str 元素影响 |
| `tuple`（纯 int 元素） | 不变 | 递归调用元素哈希，int 不受影响 |
| `frozenset` | 看元素 | 取决于元素类型 |
| `datetime` | 变化 | datetime 也参与了哈希随机化 |

如果你想禁用随机化（比如调试时需要可复现的哈希值），可以设环境变量 `PYTHONHASHSEED=0`：

```bash
PYTHONHASHSEED=0 python3 -c "print(hash('hello'))"
# 每次运行结果相同
```

对一个字典来说，哈希随机化不影响使用——同一个字典内的键仍然能正确查找。它只影响跨进程的哈希值比较，而正常编程不需要跨进程比较哈希值。

### 3.8 字典扩容：负载因子与容量增长

哈希表的存储数组大小是有限的。当存入的键值对数量超过一定比例（**负载因子，Load Factor**）时，字典会自动扩容——分配更大的数组，将所有键值对重新哈希到新数组中。

Python 字典的扩容策略：

- **触发条件**：当已用条目数超过数组容量的 2/3 时触发扩容
- **增长方式**：新容量近似翻倍（取大于 2 倍的 2 的幂次或素数）
- **重新哈希**：所有键值对重新计算在新数组中的位置

用 `sys.getsizeof()` 观察字典扩容时的大小跳变：

```python
import sys

d = {}
prev_size = sys.getsizeof(d)
expansions = []

for i in range(50):
    d[str(i)] = i
    current_size = sys.getsizeof(d)
    if current_size != prev_size:
        expansions.append((i, prev_size, current_size, len(d)))
    prev_size = current_size

print(f"{'添加次数':>8} | {'扩容前':>8} | {'扩容后':>8} | {'键数':>4}")
for step, old, new, count in expansions:
    print(f"{step:>8} | {old:>8} | {new:>8} | {count:>4}")
```

运行结果：

```text
添加次数 | 扩容前 | 扩容后 | 键数
       0 |       64 |      184 |    1
       5 |      184 |      272 |    6
      10 |      272 |      464 |   11
      21 |      464 |      832 |   22
      42 |      832 |     1584 |   43
```

可以看到字典大小在特定的键数量处有跳变，每次跳变后容量大约翻倍。扩容是自动的、对使用者透明的，但了解这个机制有助于理解以下现象：

- **预分配比逐步添加快**：字典推导式 `{i: i for i in range(N)}` 一次性创建，避免了多次扩容的不必要开销，比逐步添加更快

```python
import time

# 逐步添加（多次扩容）
start = time.perf_counter()
d1 = {}
for i in range(100000):
    d1[i] = i * 2
step_time = time.perf_counter() - start

# 字典推导式（一次性创建，内部优化扩容）
start = time.perf_counter()
d2 = {i: i * 2 for i in range(100000)}
comp_time = time.perf_counter() - start

print(f"逐步添加 100000 个键值对: {step_time:.4f}s")
print(f"字典推导式创建 100000 个键值对: {comp_time:.4f}s")
print(f"推导式快 {step_time / comp_time:.2f} 倍")
```

运行结果：

```text
逐步添加 100000 个键值对: 0.0088s
字典推导式创建 100000 个键值对: 0.0035s
推导式快 2.53 倍
```

## 4. 设计决策与权衡

### 4.1 为什么字典键要求可哈希而不是可比较

有人会问：列表也能用 `==` 比较，为什么不让列表做字典键？只要在比较时遍历元素不就行了？

| 维度 | 可哈希要求 | 仅可比较 |
|------|----------|---------|
| 查找效率 | O(1)：一次哈希定位 | O(n)：必须遍历比较 |
| 正确性保证 | 不可变 → 哈希值稳定 | 可变 → 修改后哈希值变化，查找失败 |
| 内存开销 | 需额外存储哈希值 | 无额外存储 |
| 适用场景 | 键值映射、去重 | 有序集合、序列查找 |

字典选择"可哈希"作为键的核心约束，本质是用一点点额外计算和存储，换取 O(1) 的查找效率。如果改用"仅可比较"，每次查找都要线性遍历所有键，字典就退化成列表了。

可哈希要求与不可变性的绑定也是合理的设计：不可变对象的哈希值在其生命周期内稳定不变，字典可以安全地缓存哈希值。可变对象的哈希值会随内容变化，字典无法维持索引的有效性。

### 4.2 开放寻址 vs 链地址法

哈希冲突有两大解决流派，Python 字典选择了开放寻址法：

| 维度 | 开放寻址法（Python 选择） | 链地址法（Java HashMap 选择） |
|------|----------------------|--------------------------|
| 冲突处理 | 冲突时探测下一个数组位置 | 每个位置维护一个链表 |
| 内存局部性 | 好（数据连续存储在数组中） | 差（链表节点分散在堆上） |
| 缓存友好性 | 高（CPU 缓存预取有效） | 低（链表节点指针跳跃） |
| 实现复杂度 | 中（需处理探测序列） | 低（链表操作简单） |
| 最坏情况 | 探测序列过长，退化为 O(n) | 所有键冲突到一个链表，退化为 O(n) |

Python 选择开放寻址法的主要原因是**内存局部性和缓存友好性**。Python 字典是使用频率最高的内置类型之一，缓存性能的微小提升在大规模使用时收益显著。CPython 的开放寻址实现还做了大量优化——包括探测序列的设计、伪随机探测等，使其在实际负载下性能优于链地址法。

### 4.3 紧凑字典设计：Python 3.6+ 的内存优化

Python 3.6 之前，字典内部只有一个稀疏数组，每个数组元素直接存储哈希值、键和值。由于数组稀疏（负载因子 ~2/3），内存中有大量空洞，浪费严重。

Python 3.6+ 引入**紧凑字典**设计，将存储拆分为两部分：

| 维度 | 旧方案（3.5 及以前） | 新方案（3.6+） |
|------|-------------------|--------------|
| 存储结构 | 单一稀疏数组 | 稀疏索引数组 + 紧凑条目数组 |
| 内存浪费 | ~1/3 数组位置空洞 | 索引数组小（存 int），条目数组紧凑 |
| 内存节省 | 基准 | 约 20%~25% |
| 插入顺序 | 不保证 | 保留（条目按插入顺序追加） |
| 遍历顺序 | 不可预测 | 插入顺序（3.7+ 正式保证） |

这个设计是一个"一举两得"的决策——既节省了内存，又顺带解决了"字典不保序"这个长期被用户吐槽的问题。

### 4.4 __hash__ 返回值的约束

`__hash__` 方法必须返回一个**整数**。返回非整数会报 `TypeError`：

```python
class BadReturnHash:
    def __hash__(self):
        return "not_an_integer"  # 返回字符串

try:
    hash(BadReturnHash())
except TypeError as e:
    print(f"__hash__ 返回字符串 → TypeError: {e}")
```

运行结果：

```text
__hash__ 返回字符串 → TypeError: __hash__ method should return an integer
```

Python 内部会将 `__hash__` 的返回值裁剪为机器字长的整数（64 位机器上截取 64 位），因此返回超大的整数也不会出错——只是高位会被丢弃。实际编程中，`hash()` 返回的整数范围在 `[-2^63, 2^63 - 1]`。

### 4.5 布尔值做键的设计妥协

`bool` 是 `int` 的子类，`True` 和 `False` 分别等于 `1` 和 `0`。如果要求布尔值用独立的哈希值，就会违反"相等对象哈希相同"的规则（因为 `True == 1` 为 `True`）。

Python 选择了保持一致性——`hash(True) == hash(1) == 1`，代价是 `True` 和 `1` 不能同时作为一个字典的键。这在实践中极少造成问题（布尔值只有两个，很少用作键），偶尔遇到时应改用字符串或其他类型。

| 取舍 | 选择 | 代价 |
|------|------|------|
| 布尔值哈希独立 | 未选 | 违反相等性 → 哈希一致性规则 |
| 布尔值继承 int 哈希 | 已选 | `True`/`1`、`False`/`0` 会冲突 |

## 5. 总结

本文深入讲解了字典底层的哈希机制与键类型约束：

- 字典本质是哈希表，通过 `hash(key)` 计算键的存储位置，实现 O(1) 查找
- 键必须是可哈希对象——实现了 `__hash__` 和 `__eq__`，且哈希值在生命周期内不变
- 不可变类型（int、str、tuple 等）可哈希，可变类型（list、dict、set）不可哈希
- 哈希冲突是正常现象，Python 用开放寻址法解决，冲突过多会退化为 O(n)
- "相等的对象必须哈希相同"是铁律，解释了 `1` 和 `1.0`、`True` 和 `1` 被视为同一键的原因
- 自定义类作为键时，必须同时实现 `__eq__` 和 `__hash__`，且 `__hash__` 应基于不可变属性
- `@dataclass(frozen=True)` 是实现不可变可哈希类的最简方案
- 哈希随机化（PYTHONHASHSEED）使字符串的哈希值每次进程启动时不同，防止哈希冲突 DoS 攻击
- 字典在负载因子超过 2/3 时自动扩容，预分配比逐步添加更快
