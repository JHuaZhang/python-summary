## 1. 介绍

### 1.1 什么是 index 与 count

`index` 和 `count` 是列表(`list`)的两个**查询型**方法,它们不修改列表,只从列表中"找信息":

- **`index(x[, start[, stop]])`**:查找值 `x` 在列表中**首次出现的位置**(索引),找不到抛 `ValueError`。可选 `start`/`stop` 限定查找范围。
- **`count(x)`**:统计值 `x` 在列表中出现的**次数**,找不到返回 `0`(不报错)。

```python
nums = [1, 2, 3, 2, 4, 2, 5]

# index:找首次出现位置
print(nums.index(2))         # 1 —— 第一个 2 在位置 1

# count:统计出现次数
print(nums.count(2))         # 3 —— 共有 3 个 2
```

二者底层都是**线性扫描**——从头到尾逐个比较,复杂度 O(n)。这与字典 `dict` 的 O(1) 查找形成对比:列表没有哈希索引,只能老实地挨个看。理解这点,就知道为何"在列表上反复查找"会成为性能瓶颈,以及何时该换 `set`/`dict`。

二者的另一个关键差异是**找不到时的行为**:`index` 抛错(`ValueError`),`count` 返回 0。这是高频混淆点,也是后续安全用法(先 `in` 判断、`try/except`)的来源。本篇系统讲解 `index`、`count` 的参数语义、返回值、边界、与 `in`/`set`/`dict` 的协作,以及性能选型。

### 1.2 基本语法与最小用法

**`index` 的签名**:`list.index(x[, start[, stop]])` —— 在 `[start, stop)` 范围内找首个 `== x` 的索引。

```python
fruits = ["apple", "banana", "cherry", "banana", "date"]

print(fruits.index("cherry"))      # 2
print(fruits.index("banana"))      # 1 —— 只返回首次出现
print(fruits.index("banana", 2))   # 3 —— 从位置 2 起,跳过第一个 banana
print(fruits.index("banana", 1, 3))# 1 —— 在 [1,3) 内找,得到位置 1

# 找不到抛 ValueError
try:
    fruits.index("grape")
except ValueError as e:
    print(e)                       # 'grape' is not in list
```

**`count` 的签名**:`list.count(x)` —— 统计 `== x` 的元素个数。

```python
nums = [1, 2, 3, 2, 4, 2, 5]
print(nums.count(2))               # 3
print(nums.count(99))              # 0 —— 找不到返回 0,不报错
print(nums.count(1))               # 1
```

**速查表**:

| 方法 | 签名 | 返回值 | 找不到时 | 复杂度 | 是否限定范围 |
|------|------|--------|---------|--------|------------|
| `index` | `index(x[, start[, stop]])` | 首个匹配的索引(int) | `ValueError` | O(n) | 是(`start`/`stop`) |
| `count` | `count(x)` | 出现次数(int) | 返回 `0` | O(n) | 否 |

"index 返回索引、count 返回次数;index 找不到抛错、count 找不到给 0"——这两条对比记牢,能挡住大半误用。

### 1.3 为什么 index 和 count 都是 O(n)

列表在内存中是连续的引用数组,元素与元素之间没有按值建立的索引。查找一个值时,Python 没有任何"捷径",只能从 `ob_item[0]` 开始,逐个比较 `ob_item[i] == x`,直到命中或扫完:

```python
# index 的概念性实现
def list_index(lst, x):
    for i in range(len(lst)):
        if lst[i] == x:
            return i
    raise ValueError
```

最坏情况下要扫完整个列表(目标在末尾或不存在),故 O(n)。`count` 更是铁定要扫完整个列表才能数清次数,总是 O(n)。

对比基于哈希的结构:

```python
# set/dict 查找是 O(1)
s = {1, 2, 3}
print(2 in s)                      # True,O(1)

d = {"a": 1, "b": 2}
print("a" in d)                    # True,O(1)
```

`set`/`dict` 用哈希表,通过哈希值直接定位桶,无需线性扫描。所以"频繁按值查找"场景下,把列表转 `set`/`dict` 是性能关键。本篇 2.6/4.2 节会展开这条选型。

### 1.4 index/count 与 in、remove 的关系

`index`、`count`、`in` 三个"按值查询"操作共享同一套线性扫描底层,语义上互相补充:

```python
nums = [1, 2, 3, 2]

# in:是否存在(O(n),找到即停,比 count 快)
print(2 in nums)                   # True

# index:首次位置(找不到抛错)
print(nums.index(2))               # 1

# count:总数(O(n),必扫完全部)
print(nums.count(2))               # 2
```

| 查询需求 | 用谁 | 找不到时 |
|---------|------|---------|
| 判断是否存在 | `x in lst` | `False`(不报错) |
| 拿首次位置 | `lst.index(x)` | `ValueError` |
| 数出现次数 | `lst.count(x)` | `0` |
| 按值删第一个 | `lst.remove(x)` | `ValueError` |

`remove` 上一篇讲过,它内部其实就是"先 `index` 找位置、再 `pop` 那个位置",所以 `remove` 与 `index` 找不到时都抛 `ValueError`、复杂度都是 O(n)——同源同行为。理解这层关系,`remove` 的边界行为就无需单独记忆。

## 2. 核心内容

本章逐一详解 `index`、`count` 的参数与范围控制、返回值、边界行为、与 `in`/`enumerate` 的协作,以及性能选型。每节遵循"文字详解 → demo → 运行结果说明 → 陷阱"。

### 2.1 `index(x)`:查找首次出现位置

`index` 在**全列表**范围内从左到右找首个 `== x` 的元素,返回其索引。找到立即返回(不继续往后找),找不到扫完全部后抛 `ValueError`。

```python
tags = ["python", "java", "python", "go"]

print(tags.index("python"))        # 0 —— 首次出现
print(tags.index("go"))            # 3
print(tags.index("go", 2))         # 3 —— 从位置 2 起找
```

**只返回首次**:`index` 永远只给第一个匹配的位置。要找后续出现的位置,得配合范围参数,见 2.2 节。

```python
# 想找第二个 "python" 的位置
pos1 = tags.index("python")                 # 0
pos2 = tags.index("python", pos1 + 1)       # 2 —— 从 pos1+1 起再找
print(pos1, pos2)                           # 0 2
```

这种"找到首个 → 从其后一位再找"的链式调用是定位第 N 次出现的标准套路,但每找一次都是一次 O(n),找全部出现位置需循环,共 O(n²)。要一次拿全部位置,改用 `enumerate` + 推导式(见 2.5)。

**返回的是索引,不是元素**:

```python
nums = [10, 20, 30]
pos = nums.index(20)               # 1 —— 返回位置
# 配合索引访问拿元素
print(nums[pos])                   # 20(转了一圈,因为本来就知道值是 20)
```

`index` 适合"我知道值、不知道位置"的场景。若已经知道值,再用 `index` 拿位置往往是为了后续按位置操作(`pop`、`del`、切片)。

**找不到抛 `ValueError`**:

```python
nums = [1, 2, 3]
try:
    nums.index(99)
except ValueError:
    print("不存在")                  # 不存在
```

`ValueError`(不是 `IndexError`!)——因为 `index` 是按值找,找不到是"值不存在",与 `pop`/索引访问的"位置越界"(`IndexError`)不同。报错类型与定位方式绑定,这条规律在上一篇已确立。

### 2.2 `index` 的范围参数 start / stop

`index` 可接收两个可选参数 `start` 和 `stop`,把查找范围限定在 `[start, stop)`。这在"从某个位置之后找""只在某段内找"时很有用,避免每次都从头扫。

```python
logs = ["INFO", "ERROR", "INFO", "ERROR", "INFO", "WARN"]

# 全局找首个 ERROR
print(logs.index("ERROR"))                   # 1

# 从位置 2 起找下次 ERROR
print(logs.index("ERROR", 2))                # 3

# 在 [2, 5) 范围内找 ERROR
print(logs.index("ERROR", 2, 5))             # 3

# 在 [4, 6) 范围内找 ERROR —— 这个范围里没有 ERROR
try:
    logs.index("ERROR", 4, 6)
except ValueError:
    print("范围内无 ERROR")                    # 范围内无 ERROR
```

**范围参数是半开区间**:`[start, stop)`,与切片语义一致。`stop` 省略时默认到列表尾。只给一个参数时它被当作 `start`,`stop` 默认 `len`。

**找第 N 次出现**:

```python
nums = [2, 0, 2, 0, 2]
# 找第 3 个 2
pos = nums.index(2)               # 0
pos = nums.index(2, pos + 1)      # 2
pos = nums.index(2, pos + 1)      # 4
print(pos)                        # 4 —— 第三个 2 在位置 4
```

每次用"上次位置 + 1"作 `start` 递进,找到所有出现。但注意这是 O(n × k)(k 为出现次数),要找一遍全部出现位置,2.5 节的 `enumerate` 写法是 O(n)。

**start/stop 支持负索引**:

```python
nums = [1, 2, 3, 4, 5]
print(nums.index(3, -3))          # 2 —— 从倒数第三个(位置 2)起找
print(nums.index(5, -2))          # 4
```

负索引在 `index` 内部转成正索引后,继续按半开区间扫描。若 `start >= len` 或 `start >= stop`,扫描范围为空,直接抛 `ValueError`(目标不可能在该空范围)。

**范围越界行为**:与切片类似,`start`/`stop` 超出范围会被截到合法区间,而非报"索引越界":

```python
nums = [1, 2, 3]
print(nums.index(3, 0, 100))      # 2 —— stop=100 被截到 len=3,正常找到
try:
    nums.index(3, 100)            # start=100 超出,扫描范围为空
except ValueError:
    print("start 越界 → 范围空")   # start 越界 → 范围空
```

`start` 越界使范围退化为空,`index` 自然找不到,抛 `ValueError`(找不到的错,而非越界的 `IndexError`)。

### 2.3 `count(x)`:统计出现次数

`count` 从头到尾扫完整个列表,数出 `== x` 的元素个数,返回整数。总是 O(n),无论结果多少。

```python
inventory = ["sword", "shield", "potion", "sword", "shield", "sword"]

print(inventory.count("sword"))    # 3
print(inventory.count("shield"))   # 2
print(inventory.count("potion"))   # 1
print(inventory.count("bow"))      # 0 —— 不存在返回 0
```

**`count` 不报错**:与 `index` 不同,`count` 找不到时返回 `0`,不抛异常。这让 `count` 适合"直接问有多少个,不在乎有没有"的场景,无需 `try/except`。

**`count` 必扫完全部**:`index` 命中即停,`count` 必须扫完整个列表才能确认总数。所以在"只想知道是否存在"时,`in` 比 `count` 快(`in` 命中即停,`count` 必扫完):

```python
nums = [1] * 1_000_000 + [2]       # 100 万个 1 加一个 2
# 判断 2 是否存在
"2"                                # 用 in:命中即停,理论快(虽然 2 在末尾,这里都得扫完)
# 用 count: 必扫完全部
print(nums.count(2))               # 1,但扫了 100 万次
print(2 in nums)                   # True,也是扫 100 万次才命中(2 在末尾)
```

上例因目标在末尾,`in` 与 `count` 都扫完了。但若目标在开头,`in` 立即返回 `True`,`count` 仍要扫完全部。所以**判断存在性永远用 `in`,不用 `count(x) > 0`**。

**`count` 返回布尔语境的误用**:

```python
# ❌ 用 count 判断存在,慢且语义模糊
if nums.count(2):                  # count 扫完全部
    print("有 2")

# ✅ 用 in 判断存在
if 2 in nums:                      # 命中即停
    print("有 2")
```

`count` 的语义是"数个数",不是"判断有没有"。把"有没有"的需求交给 `in`。

### 2.4 用 count 统计全部元素的频次

`count` 只能一次数一个值。要统计列表中**每个不同值**的出现次数(频次表),直接对每个值都 `count` 一遍是 O(n × m)(m 为不同值数),很慢。标准做法是用 `collections.Counter`:

```python
from collections import Counter

logs = ["INFO", "ERROR", "INFO", "WARN", "ERROR", "INFO"]

# ✅ Counter:一次扫描 O(n),得到全部频次
freq = Counter(logs)
print(freq)                        # Counter({'INFO': 3, 'ERROR': 2, 'WARN': 1})
print(freq["INFO"])                # 3
print(freq.most_common(2))         # [('INFO', 3), ('ERROR', 2)] —— 前两高频

# ❌ 对每个值 count 一遍:O(n × m)
unique = set(logs)
freq = {v: logs.count(v) for v in unique}   # 每个 count 都 O(n),总共 O(n×m)
```

`Counter` 内部一次扫描建哈希表,O(n) 拿到所有频次,且支持 `most_common`、算术运算等。**批量频次统计永远优先 `Counter`,不要循环 `count`**。`list.count` 的定位是"查单个值的次数",不是做频次表。

**`count` 与 `Counter` 的取舍**:

| 需求 | 推荐 | 复杂度 |
|------|------|--------|
| 单个值出现几次 | `lst.count(x)` | O(n) |
| 是否存在 | `x in lst` | O(n) 命中即停 |
| 全部值的频次表 | `Counter(lst)` | O(n) |
| 前 N 高频 | `Counter(lst).most_common(N)` | O(n + k log k) |

单查用 `count`、批量用 `Counter`,这是清晰分工。详见《标准库精讲》`collections.Counter` 章节。

### 2.5 找全部出现位置:enumerate + 推导式

`index` 只给首个位置。要一次拿到某值的**全部出现位置**(O(n)),用 `enumerate` 配合列表推导式:

```python
nums = [1, 2, 3, 2, 4, 2, 5]

# 一次扫描,O(n),拿全部 2 的位置
positions = [i for i, v in enumerate(nums) if v == 2]
print(positions)                  # [1, 3, 5]
```

`enumerate(nums)` 同时产出"索引 + 元素",推导式过滤 `v == 2` 的索引,一次过。对比用 `index` 链式找:

```python
# ❌ 用 index 链式找全部:O(n × k),且写法笨重
positions = []
start = 0
while True:
    try:
        pos = nums.index(2, start)
        positions.append(pos)
        start = pos + 1
    except ValueError:
        break
print(positions)                  # [1, 3, 5]
```

虽然功能相同,但 `enumerate` 写法一行、O(n)、无异常控制流,明显更优。`index` 循环找全部只在"只关心前几个、找到就停"时才有性价比优势(如只要第二个出现位置)。

**用 `enumerate` 同时取位置和值**:

```python
for i, v in enumerate(nums):
    if v == 2:
        print(f"位置 {i} 是 2")
# 位置 1 是 2
# 位置 3 是 2
# 位置 5 是 2
```

`enumerate` 是 Python 遍历带索引的标准工具,既可统计位置,也可在循环里按位置操作。详见《流程控制》`enumerate` 章节。

### 2.6 性能选型:何时该换 set / dict

`index`、`count`、`in` 对列表都是 O(n)。当"按值查找"频繁发生(如循环里反复查),O(n) 单次 × 频繁次数 = 平方级,会拖垮性能。此时把列表转 `set`(只要存在/去重)或 `dict`(要映射),把单次查找降到 O(1):

```python
# 场景:判断 10000 个候选值是否在 10 万条数据里
data = list(range(100_000))        # 10 万条
candidates = list(range(50_000, 150_000))   # 1 万个候选

# ❌ 用 in 列表:每次 O(n),总共 O(n × m) = 10 亿级
hits = [c for c in candidates if c in data]   # 极慢

# ✅ 先转 set:O(n) 建表 + O(m) 查询
data_set = set(data)               # O(n) 一次性
hits = [c for c in candidates if c in data_set]   # 每次 O(1),总共 O(m)
```

**timeit 实测**(示意量级):

```python
import timeit

setup = 'data=list(range(100000)); s=set(data); cands=list(range(50000,150000))'

# in 列表
print(timeit.timeit('[c for c in cands if c in data]', setup=setup, number=1))
# 数秒级

# in 集合
print(timeit.timeit('[c for c in cands if c in s]', setup=setup, number=1))
# 毫秒级
```

集合版本快数千倍。**频繁查找时,数据结构选对胜过算法优化**。

**set/dict 的代价**:

- 建 `set`/`dict` 需 O(n) 一次性成本,且占用更多内存(哈希表)。
- 元素必须是**可哈希**的(因此列表、字典等可变对象不能放进 `set`)。
- `set` **丢失顺序**(无序,Python 3.7+ 字典保序但集合不保证)。若需要顺序+去重,得另想办法(`dict.fromkeys` 保序去重)。

所以权衡:**查一两次 → 直接 `in`/`index` 列表无所谓;查很多次 → 值得建 `set`/`dict` 摊销建表成本**。详见《集合与冻结集合》《字典深度剖析》。

**界限的口算判断**:查找次数 × 列表长度,若乘积在百万级以下,直接 `in` 通常够快;百万级以上或循环里反复,优先建 `set`。

### 2.7 index / count 的相等判定:== 而非 is

`index` 和 `count` 在比较元素时用的是 `==`(值相等),不是 `is`(身份相同)。这对自定义对象、NaN、字符串驻留等场景有影响。

```python
# 自定义对象:由 __eq__ 决定相等
class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __eq__(self, o): return isinstance(o, Point) and (self.x, self.y) == (o.x, o.y)

pts = [Point(1, 2), Point(3, 4)]
print(pts.index(Point(1, 2)))      # 0 —— __eq__ 判定为相等,找到
print(pts.count(Point(3, 4)))      # 1
```

只要 `__eq__` 返回 `True`,`index`/`count` 就认。所以"逻辑上相等"的自定义对象也能被找到,即便不是同一个对象。

**NaN 的特殊情况**:

```python
nan = float("nan")
nums = [1.0, nan, 2.0, nan]
print(nums.count(nan))             # 0 —— 因为 nan != nan(自己都不等于自己)!
try:
    nums.index(nan)                # ValueError
except ValueError:
    print("nan 用 index 找不到")
```

`float('nan')` 的特性是 `nan != nan`(IEEE 754 规定),所以 `count` 用 `==` 比较时,连自己都匹配不上,结果 0、`index` 抛错。要统计/定位 NaN,得用 `math.isnan` 显式判断:

```python
import math
nan_count = sum(1 for v in nums if math.isnan(v))   # 2
nan_pos = [i for i, v in enumerate(nums) if math.isnan(v)]  # [1, 3]
```

**字符串小整数驻留**:`is` 与 `==` 在字符串上偶尔表现不同(CPython 的字符串驻留优化让某些字符串 `is` 相等),但 `index`/`count` 用 `==`,所以不受驻留影响,行为总是基于值相等,可放心使用。

## 3. 最佳实践

### 3.1 判断存在性用 `in`,不要用 `count > 0` 或 `index` + try

```python
# ✅ 最直接、命中即停
if x in lst:
    ...

# ❌ count 必扫完全部,慢
if lst.count(x) > 0:
    ...

# ❌ 绕一大圈,笨重
try:
    lst.index(x)
    exists = True
except ValueError:
    exists = False
```

`in` 语义最清晰、命中即停,是判断存在性的正解。`count`/`index` 的"存在性"是它们的副产品,不该用于主用途。

### 3.2 拿位置前先确认存在,或用 try/except

```python
# 写法一:先 in 再 index(两次扫描,但可读性好)
if x in lst:
    pos = lst.index(x)

# 写法二:EAFP,一次扫描
try:
    pos = lst.index(x)
except ValueError:
    pos = -1   # 或 None,表示不存在
```

若"不存在"是常见情况、`index` 会频繁抛错,写法一(先 `in`)更省(避免异常开销);若"几乎总存在",写法二更简洁。两种都安全,选贴合语义的。

### 3.3 找全部位置用 enumerate,不要循环 index

```python
# ✅ 一次 O(n)
positions = [i for i, v in enumerate(lst) if v == target]

# ❌ O(n × k),且 try/except 控制流笨重
positions = []
start = 0
while True:
    try:
        p = lst.index(target, start)
        positions.append(p)
        start = p + 1
    except ValueError:
        break
```

`index` 设计用于"找首个",找全部是 `enumerate` 的领域。代码更短、更快、无异常流。

### 3.4 频次统计用 Counter,不要循环 count

```python
from collections import Counter

# ✅ 一次 O(n)
freq = Counter(lst)

# ❌ O(n × m),每个不同值都扫一遍
freq = {v: lst.count(v) for v in set(lst)}
```

`Counter` 专为频次表设计,还附赠 `most_common`、算术运算。循环 `count` 是 O(n × m),数据稍大就慢到不可用。单查一个值的次数才用 `lst.count(x)`。

### 3.5 频繁查找先转 set,把 O(n) 降到 O(1)

```python
# ❌ 循环里反复 in 列表
data = load_large_list()
for q in queries:
    if q in data:          # 每次 O(n)
        ...

# ✅ 先建集合,O(n) 建表后查询 O(1)
data_set = set(data)
for q in queries:
    if q in data_set:      # 每次 O(1)
        ...
```

建表有 O(n) + 内存成本,但查找次数一多就被摊销回来。判断标准:查找次数 × 列表长度在百万级以上,或查询在循环内,就考虑建 `set`。注意元素须可哈希。

### 3.6 用 index 配合范围参数避免重复扫描

```python
# ❌ 每次从头找,重复扫描已查过的部分
first = lst.index(x)
second = lst.index(x)         # 又从头扫,前面那段白扫

# ✅ 用 start 跳过已查部分
first = lst.index(x)
second = lst.index(x, first + 1)
```

找第 N 次出现时,把"上次位置 + 1"作 `start`,避免重复扫描前缀。这条优化在查找稀疏出现的目标时尤其有效。

### 3.7 count 对 NaN 返回 0,统计 NaN 用 math.isnan

```python
import math

vals = [1.0, float("nan"), 2.0, float("nan")]
# ❌ count 因 nan != nan 而失效
vals.count(float("nan"))      # 0

# ✅ 显式用 isnan
nan_num = sum(math.isnan(v) for v in vals)   # 2
```

`NaN` 是 `==` 比较的特例。数据可能含 NaN 时(浮点计算、CSV 导入),别用 `count` 统计它,改用 `math.isnan`。同理 `index` 也找不到 NaN。

### 3.8 范围 index 时记得 start/stop 是半开区间,容易 off-by-one

```python
nums = [1, 2, 3, 2, 4]
# 想在 [1, 4) 找 2:位置 1 和 3 是 2,首个是 1
print(nums.index(2, 1, 4))    # 1

# 误把 stop 当闭区间
print(nums.index(2, 1, 3))    # 1,但如果 2 只在位置 3 就会 ValueError
```

`index(x, start, stop)` 的范围是 `[start, stop)`,与切片一致。写 `stop` 时想"要查到的最后一个位置 + 1",不易错。跨过这层心智,范围查找就不会误删/漏查。

### 3.9 自定义对象的 index/count 依赖 __eq__,留意其行为

```python
class User:
    def __init__(self, name): self.name = name
    # 没有 __eq__,默认按身份(is)比较
    # 同名不同对象算"不同"

users = [User("a")]
print(users.count(User("a")))   # 0 —— 没 __eq__,新对象身份不同
print(users.index(users[0]))    # 0 —— 同一对象 identity 相同
```

`index`/`count` 用 `==`,若你的类没定义 `__eq__`,`==` 退化为 `is`(身份比较),同值的两个对象会被判"不等"。想让"逻辑上相等"的对象能被找到,实现 `__eq__`(通常还要 `__hash__` 配套)。

### 3.10 别用 index 模拟队列/栈的定位删除,有更直接的

```python
# ❌ 先 index 再 pop/insert,两步
pos = lst.index(x)
lst.pop(pos)

# ✅ 直接 remove(x),一步到位(内部即 index + pop)
lst.remove(x)
```

"按值定位删除"用 `remove`(见上篇),它内部走 `index`+`pop`。手写两步既慢又易错(两步之间列表若被改,index 结果就过时)。`index` 适合"只要位置"的需求,真要删就该用 `remove`。

## 4. 原理

### 4.1 线性扫描:index 与 count 的内部实现

`index` 和 `count` 都基于线性扫描,内部是一个 C 层的 for 循环逐个比较。`index` 的核心(CPython 简化示意):

```c
// list_index 简化逻辑
Py_ssize_t list_index(lst, x, start, stop) {
    // 规范化 start/stop:负索引转正,越界截断
    normalize(start, stop, len);

    for (i = start; i < stop; i++) {
        int cmp = PyObject_RichCompareBool(lst->ob_item[i], x, Py_EQ);
        if (cmp > 0)          // == 成立
            return i;          // 命中即返回
        if (cmp < 0) goto error;
    }
    // 扫完未命中
    raise ValueError("x not in list");
}
```

关键点:

1. **逐个用 `==` 比较**:`PyObject_RichCompareBool(..., Py_EQ)` 即调用对象的 `__eq__`。所以 `index`/`count` 的相等判定完全由元素类型的 `__eq__` 决定(详见 2.7)。
2. **命中即停**:`index` 找到第一个就返回,不扫剩余。所以目标越靠前越快,最坏(目标在末尾或不存在)才扫完全部。
3. **找不到抛 ValueError**:扫完 `[start, stop)` 任未命中,`raise ValueError`。这是"按值找而值不存在"的标准报错。

`count` 的核心类似,但不"命中即停":

```c
Py_ssize_t list_count(lst, x) {
    Py_ssize_t n = 0;
    for (i = 0; i < ob_size; i++) {
        if (PyObject_RichCompareBool(lst->ob_item[i], x, Py_EQ) > 0)
            n++;                 // 命中则计数 +1,继续扫
    }
    return n;                    // 总是扫完全部,返回计数
}
```

`count` 必须**扫完全部**才能确认总数,所以总是 O(n),无论结果 0 还是 100。这也解释了为何 `count` 不像 `in`/`index` 那样能"命中即停"——它要的不是"有没有"而是"有几个"。

### 4.2 为什么列表查询是 O(n),而 set/dict 是 O(1)

列表是**连续引用数组**,元素按下标连续存放,元素之间没有按值建立的任何辅助结构。要找一个值,唯一的办法是挨个比较——因为"值"和"位置之间"没有任何映射关系。

`set`/`dict` 之所以 O(1),是因为它们在**元素/键**和**存储位置**之间用**哈希函数**建立了映射:

```python
# set 查找的概念流程
def set_contains(s, x):
    h = hash(x)                    # 算哈希值
    bucket = h % table_size        # 定位到桶
    # 只在桶内(通常 1~2 个元素)线性比较
    for item in s.table[bucket]:
        if item == x:
            return True
    return False
```

`hash(x)` 把值映射到一个桶的位置,查询时只在该桶内做少量比较,与总规模无关,故平均 O(1)(最坏哈希冲突退化为 O(n),但良好哈希下罕见)。

建表成本:把 n 个元素塞进 `set` 要算 n 次哈希、写入 n 个桶,O(n)。但建一次后,后续所有查询都 O(1),查询次数足够多时,总成本 = O(n) + O(m)(m 次查询);而用列表则是 O(n × m)。当 m 较大时,集合完胜。**数据结构决定查询复杂度**,这是选型时最该想清楚的一点。

代价:`set`/`dict` 元素须可哈希(列表、字典等可变对象不行),且 `set` 不保序、占内存更大(哈希表有装载因子空位)。这些是 O(1) 查询的必要妥协。

### 4.3 index 的范围参数如何规范化

`index(x, start, stop)` 的 `start`/`stop` 规范化逻辑与切片相似但用于控制扫描范围:

```c
void normalize_index_range(start, stop, len) {
    // 负索引转正
    if (start < 0) start += len;
    if (stop  < 0) stop  += len;
    // 越界截断
    if (start < 0) start = 0;
    if (stop  > len) stop = len;
    if (start > len) start = len;   // start 超出 → 范围空
}
// 之后在 [start, stop) 内扫描
```

规范化后,若 `start >= stop` 或 `start >= len`,扫描范围为空,循环体不执行,直接走到"未命中"分支抛 `ValueError`。所以"范围越界"在 `index` 里表现为"范围空 → 找不到 → ValueError",而非索引访问那种"越界 → IndexError"。再次印证:**按值找的越界归为"值不存在"(`ValueError`),按位置找的越界归为"位置非法"(`IndexError`)**。

半开区间 `[start, stop)` 的选择与切片一致:这样 `index(x, a, b)` 与"切片 `lst[a:b]` 里找 x"心智统一,且边界计算(长度 = stop - start)自然。

### 4.4 in、index、count、remove 的同源关系

`in`、`index`、`count`、`remove` 四个"按值操作"共享同一套线性扫描 + `==` 比较底层,差异只在"命中后做什么":

```c
// 共同的扫描循环骨架
for (i = start; i < stop; i++) {
    if (lst[i] == x) {
        /* 命中处理,各操作不同 */
    }
}
```

| 操作 | 命中后做什么 | 找不到时 | 是否继续搜 |
|------|------------|---------|----------|
| `x in lst` | 返回 `True` | 返回 `False` | 否(命中即停) |
| `lst.index(x)` | 返回 `i` | `ValueError` | 否(命中即停) |
| `lst.count(x)` | 计数 +1 | 返回 `0` | 是(必扫完) |
| `lst.remove(x)` | 左移删除 `lst[i]`,返回 | `ValueError` | 否(只删首个) |

`remove` 实际是"`index` 找位置 + `pop` 那个位置"的组合,所以它与 `index` 行为完全同源:同样的 `==` 比较、同样的"首个"、同样的 `ValueError`。理解了这四个是同一扫描骨架的不同变体,它们的边界行为就无需分别记忆——找值的都是 O(n)、都是 `==` 比较、找不到都走 `ValueError`(除了 `in`/`count` 用返回值表达"无")。

### 4.5 Counter 如何一次扫描得到频次表

`collections.Counter` 用字典(哈希表)在**一次扫描**内建成频次表,复杂度 O(n):

```python
# Counter 的概念实现
def counter(iterable):
    table = {}
    for item in iterable:
        table[item] = table.get(item, 0) + 1   # 哈希查找 + 更新,每项 O(1)
    return table
```

每个元素一次 `dict` 操作(均摊 O(1)),n 个元素共 O(n)。对比"对每个不同值 `count` 一遍":

```python
# 错误做法的概念复杂度
freq = {}
for v in set(lst):          # m 个不同值
    freq[v] = lst.count(v)  # 每次 count 是 O(n)
# 总计 O(m × n)
```

`set(lst)` 有 O(n) 建表成本,然后对 m 个不同值各 `count` 一次 O(n),合计 O(n + m·n)。当 m 与 n 同阶时退化为 O(n²)。`Counter` 一次扫描搞定,差距悬殊。

`Counter` 还提供 `most_common(k)`,用堆(或排序)取出前 k 高频,O(n + k log k) 量级,比"排序全部取前 k"更省。所以做频次分析,`Counter` 是从复杂度到功能都碾压 `count` 循环的选择。详见《标准库精讲》`collections` 章节。

### 4.6 == 比较与 NaN:为什么指数/count 失效

`index`/`count` 用 `PyObject_RichCompareBool(..., Py_EQ)` 比较,即调用元素的 `__eq__`。对 `float` 而言,`__eq__` 遵循 IEEE 754,而 IEEE 754 规定 `NaN != NaN`:

```c
// float 的相等比较(简化)
int float_eq(a, b) {
    if (isNaN(a) || isNaN(b)) return 0;   // 任何含 NaN 的比较都返回"不等"
    return a.bits == b.bits;
}
```

所以 `float("nan") == float("nan")` 为 `False`,即使两个 NaN 的位模式相同。`index`/`count` 扫到 NaN 时,`__eq__` 返回"不等",于是"跳过"它,既不计入 `count` 也不被 `index` 命中。这是为什么 `nums.count(nan) == 0`、`nums.index(nan)` 抛 `ValueError`——不是 `count`/`index` 的 bug,而是浮点 NaN 的语义使然。

要处理 NaN,必须绕过 `==`,用 `math.isnan` 显式判断(它直接查位模式,不经过 `==`)。这是数值数据处理中的常备知识。同理,任何"自定义 `__eq__` 行为特殊"的类型(如某些 ORM 对象、代理对象),其 `index`/`count` 行为都由该 `__eq__` 决定,使用时要了然于胸。

## 5. 总结

### 5.1 本文内容回顾

- **核心定位**:`index(x[, start[, stop]])` 返回首个 `== x` 的索引,找不到抛 `ValueError`;`count(x)` 返回 `== x` 的元素个数,找不到返回 0。两者都是只读查询,不修改列表。

- **线性扫描 O(n)**:列表是连续引用数组,无按值的索引,只能挨个 `==` 比较。`index`/`in` 命中即停(最坏 O(n)),`count` 必扫完全部(恒 O(n))。`set`/`dict` 用哈希表实现 O(1) 查找,是频繁查找的替代方案。

- **index 的范围参数**:`start`/`stop` 限定 `[start, stop)` 半开区间,支持负索引、越界截断。找第 N 次出现用"`index` + start 递进",但找全部出现位置用 `enumerate` 更优(O(n))。

- **count 的定位**:查单个值的次数用 `count`;判断存在性用 `in`(命中即停,优于 `count > 0`);统计全部元素频次表用 `Counter`(O(n),优于循环 `count` 的 O(n×m))。

- **相等判定用 `==`**:`index`/`count` 调用元素 `__eq__`,逻辑相等的自定义对象可被找到;但 NaN 因 `!=` 自身而使 `count` 返回 0、`index` 抛错,需 `math.isnan` 显式处理。

- **同源关系**:`in`、`index`、`count`、`remove` 共享线性扫描 + `==` 比较底层,差异只在命中后动作(返回存在/位置/计数/删除)。找不到时 `in`→`False`、`count`→`0`、`index`/`remove`→`ValueError`。

- **性能选型**:查一两次直接 `in`/`index` 列表无所谓;循环内频繁查 → 先建 `set`/`dict` 把 O(n) 降 O(1);频次表 → `Counter`;找全部位置 → `enumerate`。判断阈值:查找次数 × 列表长度在百万级以上,优先建索引结构。

- **原理**:线性扫描+`==` 比较是 O(n) 根源;哈希表通过 `hash(x)` 映射到桶实现 O(1);`index` 范围规范化(负索引转正、越界截断、空范围→ValueError);Counter 一次扫描建哈希表 O(n);NaN 的 `!=` 自身导致 `==` 失效。

### 5.2 读完本文你应能掌握

- 一句话讲清 `index` 与 `count` 的返回值与"找不到"行为差异,并据此选对方法、写出安全调用(先 `in` 或 `try/except`)。

- 解释为什么列表的 `index`/`count`/`in` 都是 O(n),以及为何 `set`/`dict` 能做到 O(1),并知道何时把列表转集合来摊销建表成本。

- 正确使用 `index` 的 `start`/`stop` 范围参数(半开区间、负索引、越界截断)定位第 N 次出现,并知道找全部位置应改用 `enumerate` 推导式。

- 区分"查单个次数用 `count`""判断存在用 `in`""做频次表用 `Counter`"三种需求的方法选择,避免循环 `count` 退化为 O(n×m)。

- 说明 `index`/`count` 的相等判定基于 `==`/`__eq__`,据此解释自定义对象的查找行为,以及为何 `count(nan)` 返回 0、需用 `math.isnan` 处理 NaN。

- 阐述 `in`、`index`、`count`、`remove` 的同源关系(共享扫描骨架 + `==` 比较),并据此推断它们的边界行为与复杂度。

- 在"频繁查找"场景下做出正确性能选型:直接列表查询 vs 建 `set`/`dict`,并说明 `set`/`dict` 的代价(可哈希、不保序、内存)。
