## 1. 介绍

### 1.1 什么是单继承

继承是面向对象编程（OOP）的核心机制之一。它允许我们定义一个新类（子类），从已有的类（父类）那里"继承"属性与方法，从而在复用已有代码的基础上扩展出新的能力。所谓"单继承"，就是指一个子类只继承一个直接父类——这是 Python 中最基础、最常用的继承形式。

现实里有一类天然的层次关系：狗是动物，猫也是动物；经理是员工，员工是人。当我们把这些关系映射到代码时，"动物"可以作为一个父类，封装"吃""睡"等所有动物共有的行为；"狗"作为子类继承"动物"，就自动拥有了 `eat()` 方法，无需再写一遍，同时还能新增狗独有的 `bark()` 方法。这就是继承解决的核心问题：**在不复制粘贴的前提下，实现行为的复用与扩展**。

Python 的继承语法非常直接：

```python
class Parent:
    ...

class Child(Parent):
    ...
```

`class Child(Parent):` 中的括号里写父类名，就完成了继承声明。如果一个子类只写了一个父类，就是单继承；写了多个父类（逗号分隔）则是多重继承——多重继承的语义、MRO、`super()` 行为都更复杂，留到本系列第 16 篇专门讲，本篇只聚焦单继承这一最常见形态。

需要注意的是，Python 3 里所有类都隐式继承自 `object`，即便你写 `class Parent:` 不带括号，`Parent` 同样是 `object` 的子类。`object` 是整个类体系的根基，提供了 `__init__`、`__str__`、`__repr__`、`__eq__` 等一整套"出厂默认"方法。我们后文会在原理章详细看到这条继承链如何发挥作用。

### 1.2 基础语法与最小用法

单继承的最小示例只需三步：定义父类、定义子类、用子类创建实例并调用继承来的方法。

```python
class Animal:
    """所有动物的父类，封装共有的'吃'行为。"""

    def eat(self):
        print("这个动物正在进食。")


class Dog(Animal):
    """狗继承自动物，自动获得 eat()，同时新增 bark()。"""

    def bark(self):
        print("汪汪！")


# 用子类创建实例
dog = Dog()

# 子类实例可以直接调用从父类继承来的方法
dog.eat()     # 输出：这个动物正在进食。

# 子类实例也能调用自己新增的方法
dog.bark()    # 输出：汪汪！
```

上面这段代码体现了单继承最核心的两件事：

1. **复用**：`Dog` 并没有自己写 `eat()`，但因为继承了 `Animal`，`dog.eat()` 能正常工作——父类的实例方法自动对子类实例可见。
2. **扩展**：`Dog` 在继承的基础上新增了 `bark()`，这是父类没有的行为。

从语法上看，声明继承只多了一个括号和父类名；但从语义上看，这一步建立了"狗是一个动物"（is-a）的关系，使得后续所有针对 `Animal` 写的代码，理论上都能接纳 `Dog` 的实例——这就是继承带来的"多态契约"基础。

下面再看一个贴近工程场景的最小例子：`Employee` 继承 `Person`，复用姓名与年龄的初始化逻辑。

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def introduce(self):
        print(f"我叫{self.name}，今年{self.age}岁。")


class Employee(Person):
    def work(self):
        print(f"{self.name}正在上班。")


emp = Employee("张三", 28)
emp.introduce()   # 输出：我叫张三，今年28岁。
emp.work()        # 输出：张三正在上班。
```

这里 `Employee` 继承了 `Person`，所以 `emp.introduce()` 可以直接用，`self.name` / `self.age` 也由父类的 `__init__` 完成赋值。需要特别留意的是：`Employee` 没有定义自己的 `__init__`，因此创建实例时 `Employee("张三", 28)` 的参数会原样传给 `Person.__init__`。一旦子类自己定义了 `__init__`，父类的 `__init__` 就不会被自动调用，需要手动用 `super()` 触发——这是本篇 2.5 节和原理章会重点讲的内容，更完整的 `super()` 用法留到第 15 篇。

## 2. 核心内容

### 2.1 子类获得父类的属性与方法

继承最直接的效果，是子类"免费"获得父类定义的所有属性和方法。这里的"所有"包括：实例方法、类方法、静态方法、实例属性（经由父类 `__init__` 设置）、类属性。理解这一点，关键在于弄清子类到底"拿到了什么"以及"怎么拿到的"。

**实例方法与实例属性**

父类在方法体里通过 `self.xxx = ...` 设置的实例属性，会在父类 `__init__`（或其他方法）被调用时，写入到具体实例的 `__dict__` 中。由于子类实例本质上就是一个完整的实例对象，只要父类的 `__init__` 被执行过，这些属性就真真切切地存在于这个子类实例上。

```python
class Vehicle:
    def __init__(self, brand):
        self.brand = brand          # 父类初始化的实例属性

    def start(self):
        print(f"{self.brand} 启动了。")


class Car(Vehicle):
    def honk(self):
        print(f"{self.brand} 嘀嘀！")   # 子类方法里直接用父类设置的 self.brand


car = Car("比亚迪")
print(car.brand)        # 输出：比亚迪   —— 父类设置的属性，子类实例直接可见
car.start()             # 输出：比亚迪 启动了。
car.honk()              # 输出：比亚迪 嘀嘀！
```

`Car` 自己的 `__init__` 没写，因此 `Car("比亚迪")` 调用的是继承来的 `Vehicle.__init__`，`self.brand = "比亚迪"` 被执行，属性就挂在了 `car` 这个实例上。`Car.honk` 里用 `self.brand` 完全合法，因为属性查找发生在实例层面，只要实例上有就找得到。

**类属性**

类属性同样会被继承。父类定义在类体里、与方法平级的变量，子类可以直接通过 `SubClass.attr` 或 `self.attr` 访问。

```python
class Shape:
    dimension = "二维"     # 父类的类属性

    def describe(self):
        print(f"我是一个{self.dimension}图形。")


class Circle(Shape):
    pi = 3.14159           # 子类自己的类属性


print(Circle.dimension)   # 输出：二维   —— 继承自父类
print(Circle.pi)          # 输出：3.14159

c = Circle()
c.describe()              # 输出：我是一个二维图形。
```

这里有个容易踩的坑：如果子类自己又定义了同名类属性 `dimension = "三维"`，那么 `Circle.dimension` 取到的是子类的值，父类的原值会被"遮蔽"（但不影响父类本身）。这其实就是"属性查找顺序"在起作用——后面原理章会看到，查找永远从子类开始向父类走。

**类方法与静态方法**

`@classmethod` 和 `@staticmethod` 也会被子类继承，但有一个微妙之处：类方法接收的第一个参数 `cls` 在被子类调用时，会是子类本身，而不是定义该方法的父类。

```python
class Logger:
    prefix = "[LOG]"

    @classmethod
    def format(cls, message):
        return f"{cls.prefix} {message}"   # cls.prefix 会查到调用类的 prefix

    @staticmethod
    def timestamp():
        return "2026-07-23"


class ErrorLogger(Logger):
    prefix = "[ERR]"


print(Logger.format("启动完成"))        # 输出：[LOG] 启动完成
print(ErrorLogger.format("磁盘满了"))   # 输出：[ERR] 磁盘满了
print(ErrorLogger.timestamp())        # 输出：2026-07-23
```

`ErrorLogger` 继承了 `format` 这个类方法，但调用 `ErrorLogger.format(...)` 时，`cls` 是 `ErrorLogger`，所以 `cls.prefix` 查到的是子类的 `"[ERR]"`。这正是类方法配合继承时强大的地方——一个在父类里写的方法，能自动适配到子类的类属性。

**不会被子类继承的东西**

有几点需要明确：

- 构造函数 `__init__` 也是方法，会被继承，但只要子类自己定义了 `__init__`，父类的就会被覆盖（不会自动调用）。
- 模块级别的函数、全局变量与类无关，不存在继承。
- 实例属性不会"凭空"存在——只有父类的 `__init__`（或其它会设置 `self.xxx` 的方法）被实际调用后，子类实例才拥有这些属性；否则访问会抛 `AttributeError`。

```python
class Base:
    def __init__(self):
        self.base_attr = "来自父类"


class Sub(Base):
    def __init__(self):
        # 子类自己定义了 __init__，但没有调用父类的 __init__
        self.sub_attr = "来自子类"


s = Sub()
print(s.sub_attr)      # 输出：来自子类
# print(s.base_attr)   # AttributeError: 'Sub' object has no attribute 'base_attr'
```

这个例子很关键：它说明继承不是"把父类的属性复制到子类"，而是"子类有机会去触发父类的初始化逻辑"。一旦子类覆盖了 `__init__` 又不显式调用父类的 `__init__`，父类本该设置的属性就不会出现。这也是为什么编写子类时，`__init__` 里通常需要 `super().__init__(...)`。

### 2.2 子类新增自己的成员

继承不是只能"原样接收"父类的东西，子类完全可以新增父类没有的属性和方法，这也是继承有价值的根本原因——复用一部分，扩展另一部分。新增的成员只对子类及其下级的"孙子类"可见，对父类不可见。

**新增方法**

最常见的新增就是添加父子类没有的行为。下面的 `Animal → Dog` 例子中，`Dog` 在继承 `eat` 的基础上，新增了 `bark` 和 `fetch`（捡球）两个方法。

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def eat(self, food):
        print(f"{self.name} 正在吃 {food}。")


class Dog(Animal):
    def bark(self):
        print(f"{self.name}：汪汪！")

    def fetch(self, item):
        print(f"{self.name} 捡回了 {item}！")


dog = Dog("旺财")
dog.eat("骨头")      # 输出：旺财 正在吃 骨头。   —— 继承自 Animal
dog.bark()           # 输出：旺财：汪汪！        —— Dog 新增
dog.fetch("飞盘")    # 输出：旺财 捡回了 飞盘！  —— Dog 新增

# 父类实例并没有这些新方法
animal = Animal("某动物")
# animal.bark()      # AttributeError: 'Animal' object has no attribute 'bark'
```

**新增类属性**

子类同样可以定义自己独有的类属性，用于表达子类层面的常量配置。

```python
class Animal:
    kingdom = "动物界"


class Dog(Animal):
    species = "犬科"     # 子类新增类属性

    legs = 4             # 子类新增类属性


print(Dog.kingdom)    # 输出：动物界  —— 继承自父类
print(Dog.species)    # 输出：犬科    —— 子类新增
print(Dog.legs)       # 输出：4
```

**新增实例属性**

子类如果自己定义了 `__init__`，通常会在调用父类 `__init__` 设置共性属性之后，再设置子类特有的实例属性。

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age


class Employee(Person):
    def __init__(self, name, age, employee_id, department):
        super().__init__(name, age)          # 先让父类初始化 name/age
        self.employee_id = employee_id        # 子类新增的实例属性
        self.department = department          # 子类新增的实例属性

    def show_badge(self):
        print(f"工号 {self.employee_id}（{self.department}）：{self.name}")


emp = Employee("李四", 30, "E-1024", "研发部")
print(emp.name)          # 输出：李四    —— 由父类 __init__ 设置
print(emp.employee_id)   # 输出：E-1024 —— 子类新增
emp.show_badge()         # 输出：工号 E-1024（研发部）：李四
```

这里 `super().__init__(name, age)` 的作用是：以子类实例 `self` 为目标，调用父类 `Person.__init__`，从而让 `emp` 同时拥有父类设置的 `name`/`age` 和子类自己设置的 `employee_id`/`department`。`super()` 的完整形态（包括在多重继承下的 MRO 协作）会在第 15 篇深入。

**新增与覆盖的区别**

新增是"子类有、父类没有"；覆盖（override）是"子类有、父类也有同名"。本节聚焦新增，覆盖属于另一个话题，本篇 2.6 节会顺带提到方法覆盖与 `super()` 协作的典型写法，更完整的覆盖与多态留到第 14 篇。

### 2.3 isinstance 与 issubclass 判断

有了继承，实例与类、类与类之间就形成了层级。Python 提供两个内置函数来检查这种层级关系：`isinstance` 判断"对象是不是某个类（或其子类）的实例"，`issubclass` 判断"一个类是不是另一个类（或其父类）的子类"。这两个函数在类型守卫、权限校验、序列化前的类型检查等场景非常常用。

**isinstance(obj, classinfo)**

`isinstance` 返回布尔值。当 `obj` 是 `classinfo` 或其（任意层级）子类的实例时返回 `True`。`classinfo` 可以是单个类，也可以是类的元组——传元组时只要满足其中任意一个即返回 `True`。

```python
class Animal:
    pass


class Dog(Animal):
    pass


class Cat(Animal):
    pass


dog = Dog()

# dog 既是 Dog 的实例，也是 Animal 的实例（因为 Dog 继承自 Animal）
print(isinstance(dog, Dog))       # 输出：True
print(isinstance(dog, Animal))    # 输出：True
print(isinstance(dog, Cat))       # 输出：False

# 元组形式：只要属于其中之一即真
print(isinstance(dog, (Cat, Dog)))  # 输出：True
print(isinstance(dog, (Cat, str)))  # 输出：False

# 所有实例都是 object 的实例
print(isinstance(dog, object))    # 输出：True
```

注意第二条：`isinstance(dog, Animal)` 为 `True`，正是"狗是一个动物"在类型系统里的体现。这一点在写"接收 Animal 的函数"时非常有用——可以放心地把 `Dog` 实例传进去。

**issubclass(cls, classinfo)**

`issubclass` 检查的是"类与类"之间的关系，不涉及实例。`issubclass(Dog, Animal)` 为 `True`，因为 `Dog` 确实在 `Animal` 的下级。同样支持元组形式的 `classinfo`。

```python
print(issubclass(Dog, Animal))       # 输出：True
print(issubclass(Animal, Dog))       # 输出：False  —— 反过来不成立
print(issubclass(Dog, Dog))          # 输出：True   —— 一个类视为自身的子类
print(issubclass(Dog, object))       # 输出：True   —— 所有类都是 object 的子类
print(issubclass(Dog, (Cat, str)))   # 输出：False
print(issubclass(Dog, (Animal, str)))# 输出：True   —— 满足 Animal 即真
```

**一个完整的类型校验场景**

下面的例子模拟一段处理"可支付对象"的代码：函数接收任意对象，但只有当它是 `Payment` 或其子类的实例时才执行扣款，否则给出明确提示。

```python
class Payment:
    def pay(self, amount):
        print(f"支付 {amount} 元。")


class WeChatPay(Payment):
    def pay(self, amount):
        print(f"微信支付 {amount} 元。")


class Alipay(Payment):
    def pay(self, amount):
        print(f"支付宝支付 {amount} 元。")


class Order:
    pass   # 订单类，不支持支付方法


def process_payment(obj, amount):
    # 用 isinstance 做类型守卫：只要是 Payment 体系内的对象，就都有 pay 方法
    if not isinstance(obj, Payment):
        print(f"类型校验失败：{type(obj).__name__} 不支持支付。")
        return
    obj.pay(amount)


process_payment(WeChatPay(), 100)   # 输出：微信支付 100 元。
process_payment(Alipay(), 50)       # 输出：支付宝支付 50 元。
process_payment(Order(), 200)       # 输出：类型校验失败：Order 不支持支付。
process_payment("不是支付对象", 10) # 输出：类型校验失败：str 不支持支付。
```

这里 `isinstance(obj, Payment)` 是一道"宽口径"的检查——它不关心 `obj` 具体是 `WeChatPay` 还是 `Alipay`，只关心它"是不是一个 `Payment`"。只要通过这道检查，就可以放心调用 `obj.pay(amount)`，因为继承保证了 `Payment` 体系内一定有 `pay` 方法（要么从父类继承，要么被子类覆盖）。这就是"继承 + isinstance"配合实现的多态式编程。

**isinstance 与 type() 的区别**

一个常见误区是用 `type(obj) == SomeClass` 来判断类型。`type()` 只返回实例的直接类，不认继承关系，而 `isinstance` 会沿继承链向上判断。

```python
print(type(dog) is Dog)        # 输出：True
print(type(dog) is Animal)     # 输出：False  —— type 不认父类
print(isinstance(dog, Animal)) # 输出：True   —— isinstance 认继承链
```

绝大多数情况下应优先用 `isinstance`：它尊重继承、更贴合"是一个"的语义，也不会在引入子类时无故失效。`type()` 精确比较只在极少数"就是要严格匹配直接类型"的场景下使用，例如某些序列化框架要区分"到底是哪个具体子类"。

### 2.4 方法解析从子类到父类

当一个方法或属性被访问时，Python 需要确定"到底用哪个类的定义"。这个过程叫方法解析（method resolution）。在单继承下，规则非常直观：**从子类开始，沿继承链向上查找，直到找到第一个匹配的定义为止**；如果一路找到 `object` 都没有，就抛 `AttributeError`。

**查找顺序演示**

下面的例子刻意制造一个"父子类同名方法"的场景，观察调用时用的是哪一个。

```python
class Animal:
    def speak(self):
        print("动物发出了声音。")


class Dog(Animal):
    # Dog 自己定义了 speak，会"遮蔽"父类的同名方法
    def speak(self):
        print("汪汪！")


dog = Dog()
dog.speak()   # 输出：汪汪！   —— 找到 Dog.speak，不再向上

# 如果删掉 Dog.speak，调用就会落到 Animal.speak
del Dog.speak
dog.speak()   # 输出：动物发出了声音。
```

第一次调用时，查找从 `Dog` 开始，发现 `Dog` 有 `speak`，就用它，不再继续找父类。用 `del Dog.speak` 把这个方法删掉后，再次调用 `dog.speak()` 时，`Dog` 里找不到了，于是向上到 `Animal`，找到 `Animal.speak` 并执行。

**属性查找同理**

不仅是方法，普通属性也遵循同样的从子类到父类的查找顺序。实例属性在实例自己的 `__dict__` 里；类属性在类（及其父类）的 `__dict__` 里。

```python
class Base:
    value = "父类的 value"


class Sub(Base):
    value = "子类的 value"   # 同名类属性，遮蔽父类


s = Sub()
print(s.value)     # 输出：子类的 value

del Sub.value
print(s.value)     # 输出：父类的 value

# 还可以给实例单独设置同名属性，遮蔽类属性
s.value = "实例的 value"
print(s.value)     # 输出：实例的 value
```

查找的完整顺序是：**实例的 `__dict__` → 子类的 `__dict__` → 父类的 `__dict__` → …… → `object` 的 `__dict__`**。这个顺序在单继承下是一条直线，非常容易理解；多重继承时顺序会变成一棵树的遍历（C3 线性化），那是第 16 篇的话题。

**未找到时的行为**

```python
class A:
    pass


class B(A):
    pass


b = B()
# b.no_such_thing()   # AttributeError: 'B' object has no attribute 'no_such_thing'
```

一路找不到匹配定义时，属性访问会触发 `AttributeError`。如果类定义了 `__getattr__` 钩子，还可以在"找不到"时动态兜底——这属于属性访问协议的进阶内容，这里不展开。

### 2.5 子类 __init__ 通常需调用父类 __init__

这是编写子类时最容易踩的坑之一。前面 2.1 节已经提到：**子类一旦定义了自己的 `__init__`，父类的 `__init__` 不会被自动调用**。这意味着父类本该完成的初始化（设置公共属性、建立不变式）会"丢失"，导致子类实例缺少预期属性，甚至破坏对象的一致性。

**反例：忘记调用父类 __init__**

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age
        print(f"Person.__init__ 完成：{self.name}")

    def greet(self):
        print(f"你好，我是{self.name}。")


class Student(Person):
    def __init__(self, school):
        self.school = school
        # 忘记调用 super().__init__(...)，name/age 没有被设置
        print(f"Student.__init__ 完成：{self.school}")


stu = Student("清华")
print(stu.school)   # 输出：清华
# stu.greet()        # AttributeError: 'Student' object has no attribute 'name'
print(hasattr(stu, "name"))   # 输出：False
```

`stu.greet()` 会失败，因为 `greet` 里用到 `self.name`，而 `Person.__init__` 从未被执行，`name` 根本不存在。`hasattr(stu, "name")` 返回 `False` 也印证了这一点。这就是典型的"子类覆盖 `__init__` 却忘了调用父类"导致的一致性破坏。

**正例：用 super() 调用父类 __init__**

修复方式是在子类 `__init__` 里，通过 `super().__init__(...)` 先把父类的初始化工作做了，再做子类自己的初始化。

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age
        print(f"Person.__init__ 完成：{self.name}")


class Student(Person):
    def __init__(self, name, age, school):
        super().__init__(name, age)      # 先调用父类 __init__，设置 name/age
        self.school = school             # 再做子类自己的初始化
        print(f"Student.__init__ 完成：{self.school}")


stu = Student("王五", 20, "清华")
# 输出：
# Person.__init__ 完成：王五
# Student.__init__ 完成：清华

print(stu.name)     # 输出：王五   —— 父类初始化的属性已就位
print(stu.age)      # 输出：20
print(stu.school)   # 输出：清华
stu.greet()         # 输出：你好，我是王五。  —— 父类方法可用
```

从输出顺序可以看到：`super().__init__(...)` 这一行先执行了父类的初始化逻辑（打印 "Person.__init__ 完成"），随后才执行子类自己的初始化（打印 "Student.__init__ 完成"）。这是一条推荐的工作流：**在子类 `__init__` 中，先用 `super()` 完成父类的初始化，保证父类的不变式已经建立，再做子类专属的扩展**。

**参数对齐的两种常见风格**

子类 `__init__` 的参数通常需要"兼容"父类——至少覆盖父类 `__init__` 需要的参数，再看是否额外增收子类特有的参数。

风格一：子类参数是父类参数的超集。这是最常见的，如上面的 `Student(name, age, school)`，`name`、`age` 原样转交父类，`school` 是子类新增。

风格二：子类的参数与父类部分重叠，但语义有差异，需要在子类里做转换后再传给父类。

```python
class Animal:
    def __init__(self, legs):
        self.legs = legs


class Snake(Animal):
    def __init__(self):
        # 蛇没有腿：子类用固定值调用父类的初始化
        super().__init__(legs=0)


s = Snake()
print(s.legs)   # 输出：0
```

不管哪种风格，原则都是：**父类 `__init__` 期望的参数，子类要有办法提供**——要么从自己的参数里透传，要么用合理默认值补上。

**什么时候可以不调用 super().__init__？**

有两种情况可以不调用：

1. 子类完全不需要父类 `__init__` 建立的属性，且不会调用任何依赖这些属性的父类方法。例如一些"标记类"只是为了被 `isinstance` 识别，不依赖父类状态。
2. 子类用 `__new__` 或其它机制完全接管了实例的构造，明确知道自己在做什么。

但这些都是特例。**默认情况下，只要子类写了 `__init__`，就应当在其中调用 `super().__init__(...)`**，这是最安全的习惯。

更复杂的 `super()` 用法——比如在多重继承下沿 MRO 链调用、在非 `__init__` 的方法里用 `super()` 实现协作式多态——会在第 15 篇专题讲解。本篇只要求读者掌握"子类 `__init__` 里通过 `super().__init__(...)` 初始化父类部分"这一基本写法。

### 2.6 子类访问父类成员与简单覆盖

子类虽然能自动获得父类成员，但有时我们希望在"覆盖"父类方法的同时，仍然复用父类的那份逻辑。这时需要在子类方法里显式访问父类的成员。Python 提供两种主要写法：`super()` 和直接通过类名访问。

**用 super() 在覆盖中复用父类逻辑**

下面的 `Cat` 覆盖了 `Animal.speak`，但在覆盖版本里先用 `super().speak()` 调用父类版本，再做扩展。

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        print(f"{self.name} 发出了声音。")


class Cat(Animal):
    def speak(self):
        super().speak()        # 先调用父类版本
        print(f"{self.name}：喵～")   # 再做子类特有的补充


cat = Cat("咪咪")
cat.speak()
# 输出：
# 咪咪 发出了声音。
# 咪咪：喵～
```

输出顺序说明了执行流：先跑父类 `Animal.speak` 的全部逻辑，再跑 `Cat.speak` 里 `super().speak()` 之后的扩展部分。这种"先调父类再扩展"的写法，是覆盖时复用父类代码的标准模式。

**通过类名直接访问父类成员**

也可以不写 `super()`，而是用"父类名.方法(self, ...)"的形式。这在 Python 2 时代是主流写法，现在仍可见到。

```python
class Cat(Animal):
    def speak(self):
        Animal.speak(self)       # 显式传入 self
        print(f"{self.name}：喵～")
```

效果与 `super().speak()` 一样，但有两个区别：

1. 语义上 `super()` 更"面向未来"——它沿 MRO 查找，而不是硬编码父类名，在多重继承下表现更合理（第 15、16 篇会展开）。
2. 用类名直接调用时必须手动传 `self`，写起来更啰嗦，且类名一旦改名要同步修改。

**推荐写法**：在单继承下，两种写法功能等价，但 `super()` 更通用、可读性更好，应作为默认选择；仅在需要绕过 MRO、明确调用某个特定父类时（例如调试或特殊协作模式），才用"父类名.方法(self)"的形式。

**访问父类的类属性**

父类的类属性同样可以通过 `super()` 或类名访问。但因为属性查找本来就沿着继承链向上，父类的类属性可以直接通过 `self.xxx` 或 `cls.xxx` 读到——只有当子类也定义了同名属性、需要"绕过遮蔽读到父类原值"时，才需要显式用 `super()` 或类名。

```python
class Base:
    threshold = 100


class Sub(Base):
    threshold = 50    # 子类覆盖了类属性

    def show(self):
        print("子类 threshold:", self.threshold)
        print("父类 threshold:", super().threshold)


Sub().show()
# 输出：
# 子类 threshold: 50
# 父类 threshold: 100
```

### 2.7 object 是所有类的根基

Python 3 中，无论你是否显式写 `(object)`，所有类最终都继承自 `object`。`object` 提供了一整套"出厂默认"的 dunder 方法，是所有 Python 对象行为的最低保障。理解 `object` 的存在，有助于解释为什么即使你什么都没写，实例也有一堆"天生"的方法。

```python
class Empty:
    pass


e = Empty()

# 这些方法都不是 Empty 定义的，而是从 object 继承来的
print(e.__str__())    # 输出：<__main__.Empty object at 0x...>
print(e.__repr__())   # 输出：<__main__.Empty object at 0x...>
print(e.__hash__())   # 输出：某个整数
print(e.__class__)    # 输出：<class '__main__.Empty'>
print(e == e)         # 输出：True（object.__eq__ 默认比较身份）
```

`object` 提供的关键默认行为包括：

| 方法 | 默认行为 |
|------|---------|
| `__init__` | 什么都不做（空实现） |
| `__str__` | 返回 `<模块名.类名 object at 0x...>` |
| `__repr__` | 同 `__str__` 的默认形式 |
| `__eq__` | 比较两个对象是否是同一个对象（身份比较，等价于 `is`） |
| `__hash__` | 基于对象身份返回哈希值 |
| `__hash__` 与 `__eq__` 的关系 | 默认可哈希，因为 `__eq__` 基于身份 |

这就是为什么你在自己的类里覆盖 `__eq__` 而不覆盖 `__hash__` 时，Python 会把对象标记为不可哈希——因为 `object.__hash__` 基于身份的语义与你的"值相等"语义不兼容，Python 保守地禁用哈希以保证正确性。这种"默认行为 + 覆盖时的连锁反应"，正是源于所有类共享 `object` 这一根基。

**显式继承 object 与隐式继承等价**

```python
class A:
    pass

class B(object):
    pass

print(A.__bases__)   # 输出：(object,)
print(B.__bases__)   # 输出：(object,)
print(issubclass(A, B))   # 输出：False —— A 和 B 是平级，都直接继承 object
print(issubclass(A, object))  # 输出：True
```

`A` 和 `B` 在 Python 3 里完全等价——`__bases__` 都是 `(object,)`。历史上 Python 2 有"经典类"与"新式类"之分，写 `(object)` 是为了声明新式类；在 Python 3 这一区分已不复存在，所有类都是新式类，都继承 `object`。所以现代代码里写不写 `(object)` 只是风格问题，没有功能差异。

### 2.8 继承表达"是一个(is-a)"关系

面向对象里有两种基本的对象关系：**"是一个"（is-a）** 和 **"有一个"（has-a）**。继承表达的是 is-a：子类是父类的一种特化。组合表达的是 has-a：一个对象内部包含另一个对象作为组成部分。判断该用继承还是组合，先要看清两者在语义上的差异。

**is-a 就该用继承**

经典的 is-a 关系："狗是一个动物""经理是一个员工""圆形是一个形状"。这种关系下，子类的实例"无条件地"就是父类的实例——`isinstance(dog, Animal)` 永远成立。这是继承的正当理由。

```python
class Animal:
    def eat(self):
        print("动物在进食。")


class Dog(Animal):       # 狗"是一个"动物 —— 继承合理
    def bark(self):
        print("汪汪！")


def feed(animal: Animal):
    # 只要"是一个动物"，就能喂
    animal.eat()


feed(Dog())    # 输出：动物在进食。   —— Dog 是 Animal，可传入
```

`feed` 函数的形参标注为 `Animal`，而 `Dog` 实例可以传进去，正是因为"狗是一个动物"。继承让这种"用父类类型接纳子类实例"的多态成为可能。

**has-a 就该用组合，而不是继承**

反面例子：为了让"汽车"拥有"引擎"的启动能力，有的人会让 `Car` 继承 `Engine`。这是错的——汽车不是引擎，汽车"有一个"引擎。正确的做法是组合：把 `Engine` 作为 `Car` 的一个属性。

```python
# 不推荐：Car 继承 Engine —— 语义错误，汽车"不是"引擎
class Engine:
    def start(self):
        print("引擎启动。")


# class Car(Engine):    # 语义错位：Car 不应该 is-a Engine
#     pass


# 推荐：Car 组合 Engine —— 汽车有一个引擎
class Car:
    def __init__(self):
        self.engine = Engine()    # 组合：Car 内部持有一个 Engine

    def start(self):
        self.engine.start()       # 委托给内部组件
        print("汽车出发。")


Car().start()
# 输出：
# 引擎启动。
# 汽车出发。
```

**继承 vs 组合的取舍（简提）**

一个实用的判断标准是问自己："如果别人问 X 是不是 Y，我会自然地回答'是'吗？"

- "狗是动物吗？"——是，用继承。
- "汽车是引擎吗？"——不是，汽车有引擎，用组合。
- "学生是人吗？"——是，用继承。
- "订单是支付方式吗？"——不是，订单有支付方式，用组合。

设计模式社区有句老话叫"组合优先于继承"（favor composition over inheritance），意思是：当拿不准时，优先用组合，因为继承把子类与父类的实现细节深度耦合（父类内部实现一变，所有子类都可能受影响），而组合的耦合更松、更灵活。但这不意味着继承不好——在真正的 is-a 关系下，继承仍然是表达多态和复用代码的最佳工具。

本篇只简要提这个取舍，更深入的设计权衡留到后续 OOP 设计相关的篇章。多重继承则完全留到第 16 篇。

## 3. 最佳实践

**优先用 isinstance，而不是 type() 精确比较**

在绝大多数类型判断场景下，`isinstance(obj, cls)` 比 `type(obj) is cls` 更合适。`isinstance` 尊重继承链，能正确接纳子类实例；`type()` 精确比较会在引入子类时无故失效，破坏多态。

```python
# 推荐：尊重继承，接纳子类
def is_animal(obj):
    return isinstance(obj, Animal)

# 不推荐：只认直接类型，子类会被误判为"不是动物"
def is_animal_strict(obj):
    return type(obj) is Animal
```

前者对 `Dog()` 返回 `True`，后者对 `Dog()` 返回 `False`——后者几乎肯定不是你期望的语义。只有在你确实要区分"到底是哪个直接类"、排除子类时，才考虑 `type()`。

**子类 __init__ 默认要调用 super().__init__**

这是最稳的习惯。只要你替父类覆盖了 `__init__`，就应在子类 `__init__` 的开头调用 `super().__init__(...)`，保证父类的不变式先行建立，再做子类扩展。

```python
# 推荐
class Student(Person):
    def __init__(self, name, age, school):
        super().__init__(name, age)
        self.school = school
```

```python
# 不推荐：父类的 name/age 不会被设置，后续调用 greet() 会崩
class Student(Person):
    def __init__(self, school):
        self.school = school
```

**不要为了"复用一点点代码"而强行继承**

如果两个类之间没有真正的 is-a 关系，仅仅因为想复用某个方法就让一个继承另一个，往往会导致继承层级畸形、子类背上它并不需要的方法。这种情况下提取一个公共父类或用组合更合理。

```python
# 不推荐：为了让 Order 复用 pay，让 Order 继承 Payment —— 订单不是一种支付
class Order(Payment):
    pass

# 推荐：Order 组合一个 Payment，或让两者都依赖某个抽象
class Order:
    def __init__(self):
        self.payment = WeChatPay()
```

**继承层次不要太深**

每多一层继承，方法解析链就长一截，可读性和可维护性都会下降。一般建议继承层级控制在 2~3 层以内。当发现层次过深时，通常是设计出现了问题，应考虑用组合或拆分类来重构。一个经验法则：如果你要追三代以上才能看清一个方法来自哪里，这棵继承树就太深了。

**覆盖父类方法时保持签名兼容**

子类覆盖父类方法时，应尽量保持与父类相同的参数签名（或至少是兼容的超集）。原因是：父类定义了一套调用契约，调用方按父类签名传参；如果子类改了签名，原来针对父类写的代码传入子类实例时就会报错。

```python
class Animal:
    def eat(self, food):
        ...


# 推荐：签名一致，只是行为不同
class Dog(Animal):
    def eat(self, food):
        if food == "巧克力":
            print("狗不能吃巧克力！")
        else:
            super().eat(food)


# 不推荐：子类私自改变了签名，破坏父类契约
class Cat(Animal):
    def eat(self, food, times):   # 多了个必选参数，原调用方会崩
        ...
```

**用 issubclass 做类级别的校验，用 isinstance 做实例级别的校验**

两者不要混用。`issubclass` 接收的是类对象，`isinstance` 接收的是实例。写校验代码时先想清楚你要检查的是"这个对象是不是某体系的实例"还是"这个类是不是某体系的子类"。

```python
def register_handler(handler_cls):
    # 类级别校验：用 issubclass
    if not issubclass(handler_cls, Handler):
        raise TypeError("handler_cls 必须是 Handler 的子类")
    ...

def invoke(handler):
    # 实例级别校验：用 isinstance
    if not isinstance(handler, Handler):
        raise TypeError("handler 必须是 Handler 实例")
    ...
```

**暴露继承关系，而不是隐藏**

定义子类时，父类的名字写在括号里本身就是一种文档——它明确告诉读者"这个类与谁有 is-a 关系"。不要为了让某个方法"恰好能用"而把继承藏在深层基类里制造意外依赖。如果子类真的依赖父类的某个方法，要么在父类里把它标注为"可被子类覆盖的协议方法"（命名上加以区分，例如 `_*` 或在文档中声明），要么把它定义成抽象方法（配合 `abc` 模块）。

## 4. 原理

本章深入单继承在 Python 对象模型里的实现机制。理解这些机制，能让你在面对"为什么这样写能生效""为什么调用的是这个方法而不是那个"时有清晰的答案，而不是凭感觉。

### 4.1 __bases__ 指向父类元组

每个类对象都有一个特殊属性 `__bases__`，它是一个元组，按声明顺序存放该类的直接父类。单继承下这个元组只有一个元素。这个属性是 Python 表达"继承关系"的数据结构基础——解释器通过它知道一个类的直接父类是谁，从而在方法解析时向上查找。

```python
class Animal:
    pass


class Dog(Animal):
    pass


print(Animal.__bases__)   # 输出：(object,)   —— Animal 直接继承 object
print(Dog.__bases__)      # 输出：(Animal,)   —— Dog 直接继承 Animal
print(Dog.__bases__[0])   # 输出：<class '__main__.Animal'>
print(Dog.__bases__[0] is Animal)   # 输出：True
```

从输出可以看到：

- `Animal` 虽然声明时没写父类，但它的 `__bases__` 是 `(object,)`——Python 3 自动把 `object` 作为所有类的根基父类。
- `Dog` 的 `__bases__` 是 `(Animal,)`，单继承所以只有一个元素。
- 元组里的元素就是父类对象本身（`is` 比较为 `True`），不是字符串也不是副本。

**__bases__ 是可变的（但谨慎修改）**

`__bases__` 理论上可以在运行时修改，这会动态改变继承关系，但这是非常深水区的操作，几乎只在元编程/框架内部使用，绝不应在普通业务代码里做。

```python
class A:
    def hello(self):
        print("A.hello")


class B:
    def hello(self):
        print("B.hello")


class C(A):
    pass


C().hello()        # 输出：A.hello
C.__bases__ = (B,)
C().hello()        # 输出：B.hello   —— 运行时换了父类，方法解析随之改变
```

这种``换父类''的操作之所以能生效，正是因为方法解析依赖的就是 `__bases__`（以及由它构建的 MRO）。改了 `__bases__`，MRO 也会重新计算，后续方法查找就走新链路。

### 4.2 __mro__：方法解析顺序

`__bases__` 只给出直接父类，但一个类可以有祖父类、曾祖父类……直到 `object`。方法解析需要一条"线性"的查找路径，这条路径就是 **MRO（Method Resolution Order，方法解析顺序）**。Python 3 用 C3 线性化算法计算 MRO，并把它存在类的 `__mro__` 属性里——这是一个元组，按查找顺序排列。

**单继承下的 __mro__ 就是一条直线**

单继承下 MRO 非常简单：从子类开始，沿 `__bases__` 一步步向上，直到 `object`。

```python
class Animal:
    pass


class Dog(Animal):
    pass


print(Dog.__mro__)
# 输出：(<class '__main__.Dog'>, <class '__main__.Animal'>, <class 'object'>)
```

`Dog.__mro__` 是 `(Dog, Animal, object)`。这意味着：

1. 访问 `dog.xxx` 时，Python 先在 `Dog` 的 `__dict__` 里找；
2. 找不到就到 `Animal` 的 `__dict__` 里找；
3. 再找不到就到 `object` 的 `__dict__` 里找；
4. 最终找不到才抛 `AttributeError`。

这条线性顺序决定了前面 2.4 节看到的"从子类到父类"的查找行为。可以对照 `__mro__` 来理解：为什么子类同名方法会"遮蔽"父类——因为子类排在 MRO 的前面，先被找到。

**多层单继承的 MRO**

```python
class A:
    pass


class B(A):
    pass


class C(B):
    pass


print(C.__mro__)
# 输出：(<class '__main__.C'>, <class '__main__.B'>, <class '__main__.A'>, <class 'object'>)
```

`C → B → A → object`，三层单继承形成一条直线，MRO 就是这条直线本身。这个简单性是单继承相对于多重继承的一个好处——在多重继承下，MRO 是 C3 算法对一棵"父类图"的线性化，会出现一些反直觉的顺序，那是第 16 篇的内容。

**MRO 决定了 super() 的下一个目标**

`super()` 在单继承下看起来只是"调父类"，但它实际上是基于 MRO 工作的：`super()` 返回一个代理对象，它会沿着 MRO 找到"当前类之后的下一个类"，并在那个类的 `__dict__` 里查找方法。这就是为什么前面 2.6 节用 `super().speak()` 能调用到 `Animal.speak`——`Dog` 的 MRO 是 `(Dog, Animal, object)`，`super()` 在 `Dog` 内部指向的就是 `Animal`。

```python
class Animal:
    def who(self):
        return "Animal"


class Dog(Animal):
    def who(self):
        # super() 在 Dog 内部，沿 Dog.__mro__ 找下一个，即 Animal
        return "Dog → " + super().who()


print(Dog().who())   # 输出：Dog → Animal
```

如果 `Dog` 没有定义 `who`，那么 `Dog().who()` 会沿 MRO 直接命中 `Animal.who`，返回 `"Animal"`。`Dog` 定义了 `who` 后，就用 `Dog.who`，在它内部 `super().who()` 又复用父类逻辑——这就是覆盖与复用的协作。

### 4.3 isinstance 与 issubclass 沿继承链判断

理解了 `__bases__` 和 `__mro__`，`isinstance` 与 `issubclass` 的实现原理就清楚了：它们都是沿着继承链（实际上就是 MRO 这条链）向上判断的。

**issubclass(cls, base) 的判断逻辑**

`issubclass(cls, base)` 本质上是检查 `base` 是否出现在 `cls` 的 MRO 里（或者 `cls` 就是 `base` 本身）。

```python
class Animal:
    pass


class Dog(Animal):
    pass


# Dog 的 MRO 是 (Dog, Animal, object)
# Animal 在其中，所以 True
print(issubclass(Dog, Animal))    # 输出：True

# Dog 在 Dog 的 MRO 中（首元素），视为自身的子类
print(issubclass(Dog, Dog))       # 输出：True

# object 在 Dog 的 MRO 中，所以所有类都是 object 的子类
print(issubclass(Dog, object))    # 输出：True

# Animal 的 MRO 是 (Animal, object)，Cat 不在其中，所以 False
print(issubclass(Animal, Dog))    # 输出：False
```

**isinstance(obj, cls) 的判断逻辑**

`isinstance(obj, cls)` 等价于：先取 `type(obj)`（对象的直接类），再检查这个类是否是 `cls` 的子类——也就是判断 `type(obj)` 的 MRO 里是否包含 `cls`。当 `classinfo` 是元组时，只要其中任意一个类满足即返回 `True`。

```python
dog = Dog()

# type(dog) 是 Dog，Dog 的 MRO 含 Animal，所以 isinstance(dog, Animal) 为 True
print(isinstance(dog, Animal))   # 输出：True

# 这等价于下面的 issubclass 检查
print(issubclass(type(dog), Animal))   # 输出：True

# 反过来不成立：Animal 的实例不是 Dog 的实例
animal = Animal()
print(isinstance(animal, Dog))   # 输出：False
# 因为 type(animal) 是 Animal，Animal 不是 Dog 的子类
print(issubclass(type(animal), Dog))   # 输出：False
```

这也解释了为什么 `isinstance(dog, object)` 永远为 `True`——任何对象的 `type` 的 MRO 最终都包含 `object`，因为 `object` 是所有类的根基。

**与 type() 的根本差异**

`type(obj)` 只返回"直接类型"，不含继承信息；`isinstance` 则沿 MRO 判断。所以：

```python
dog = Dog()
print(type(dog) is Animal)       # False —— 直接类型不是 Animal
print(isinstance(dog, Animal))   # True  —— 沿 MRO 判断，Animal 在链上
```

`type()` 的比较不认 MRO，因此无法识别"是一个"的子类关系；`isinstance` 识别 MRO，所以尊重继承。这也是最佳实践里反复强调"优先用 isinstance"的原理依据。

### 4.4 单继承下 __mro__ 即 [Child, Parent, object]

把前面的机制串起来，单继承下的方法解析模型可以总结成一句话：**MRO 是 `[Child, Parent, object]`（多层则是 `[Child, ..., Parent, ..., object]` 的一条直线），所有属性查找都沿这条直线从左到右进行**。

下面用一个综合例子，把 `__bases__`、`__mro__`、方法查找、`isinstance`/`issubclass` 串联起来。

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def breathe(self):
        print(f"{self.name} 在呼吸。")


class Dog(Animal):
    def bark(self):
        print(f"{self.name}：汪汪！")


# 1) __bases__：直接父类
print(Dog.__bases__)           # 输出：(Animal,)
print(Animal.__bases__)        # 输出：(object,)

# 2) __mro__：完整查找路径
print(Dog.__mro__)
# 输出：(<class 'Dog'>, <class 'Animal'>, <class 'object'>)

# 3) 方法解析：bark 在 Dog 找到
dog = Dog("旺财")
dog.bark()      # 输出：旺财：汪汪！   —— 命中 Dog.bark
# breathe 不在 Dog，沿 MRO 向上到 Animal，命中 Animal.breathe
dog.breathe()   # 输出：旺财 在呼吸。

# 4) __init__ 解析：Dog 没有 __init__，沿 MRO 向上到 Animal，命中 Animal.__init__
#    所以 Dog("旺财") 实际调用的是 Animal.__init__(self, "旺财")
print(Dog.__init__ is Animal.__init__)   # 输出：True

# 5) isinstance / issubclass：沿 MRO 判断
print(isinstance(dog, Animal))    # 输出：True  —— Animal 在 type(dog).__mro__ 中
print(isinstance(dog, object))    # 输出：True
print(issubclass(Dog, Animal))    # 输出：True
print(issubclass(Dog, object))    # 输出：True
```

注意第 4 条：`Dog.__init__ is Animal.__init__` 为 `True`，说明 `Dog` 自己没有 `__init__`，访问 `Dog.__init__` 时沿 MRO 找到了 `Animal.__init__`。这就解释了 2.1 节"子类不写 `__init__` 就自动用父类 `__init__`"的原理——不是"复制"，而是查找时向上命中。

**查找的完整顺序再回顾**

对于 `dog.breathe()` 这一次调用：

1. Python 先查 `dog.__dict__`（实例自有属性），没有 `breathe`。
2. 再查 `type(dog)` 即 `Dog.__dict__`，没有 `breathe`。
3. 沿 `Dog.__mro__` 向上到 `Animal.__dict__`，找到 `breathe`，执行。
4. 如果 `Animal` 也没有，就到 `object.__dict__`——`object` 没有 `breathe`，抛 `AttributeError`。

这条"实例 dict → 类 dict（沿 MRO）"的查找路径，是 Python 属性访问的底层规则，单继承下尤其简单直观。

### 4.5 继承的"是一个"与组合的"有一个"语义差异

从对象模型的层面看，"继承"和"组合"对应着完全不同的结构关系，理解这种结构性差异有助于在设计时做出正确选择。

**继承：子类的实例本身就是父类的实例**

继承在类型系统里建立的是 `is-a` 关系：子类的实例通过 `isinstance` 判定时，对父类返回 `True`。这是因为在 MRO 上，父类就在子类的查找链中——子类的实例"是一个"父类的实例。这种关系是"身份层面"的：`Dog` 实例同时是 `Dog`、`Animal`、`object` 的实例。

```python
class Animal:
    pass


class Dog(Animal):
    pass


dog = Dog()
print(isinstance(dog, Dog))      # True —— 它是 Dog
print(isinstance(dog, Animal))   # True —— 它也是 Animal
print(isinstance(dog, object))   # True —— 它也是 object
```

**组合：一个对象的属性里持有另一个对象**

组合在结构上是 `has-a` 关系：一个对象在自己的 `__dict__` 里持有另一个对象作为属性。后者不是前者的"父"，前者的实例也不是后者的实例——`isinstance` 判断不成立。

```python
class Engine:
    def start(self):
        print("引擎启动。")


class Car:
    def __init__(self):
        self.engine = Engine()    # Car 的 __dict__ 里有 engine 属性


car = Car()
print(isinstance(car, Engine))    # False —— 汽车"不是"引擎
print(hasattr(car, "engine"))     # True  —— 汽车"有一个"引擎
print(type(car.engine))           # <class 'Engine'>
```

**结构差异的对照**

| 维度 | 继承（is-a） | 组合（has-a） |
|------|------------|--------------|
| 关系语义 | 子类是父类的一种特化 | 一个对象内部包含另一个对象 |
| 类型判断 | `isinstance(sub, Parent)` 为真 | `isinstance(outer, Inner)` 为假 |
| 成员获得方式 | 通过 MRO 查找自动获得父类成员 | 通过属性访问委托给内部对象 |
| 耦合度 | 强耦合：父类实现变动影响所有子类 | 较松耦合：内部对象可替换 |
| 运行时灵活度 | 继承关系在类定义时固定（改 `__bases__` 是黑魔法） | 组合对象可在运行时替换 |

这张表从原理层面说明了"组合优先于继承"的技术依据：继承通过 MRO 把父类和子类的成员查找深度绑在一起，父类内部实现一旦变化，所有子类的方法解析都可能受影响；而组合只是"持有一个引用"，内部对象甚至可以在运行时换成另一个实现，耦合更松。但反过来，在真正的 is-a 场景下，继承带来的多态（`isinstance` 判定、方法分发）是组合难以等价替代的。

**组合 + 接口可以模拟多态**

如果只是想要"不同的类都有同名方法"这种多态效果，不一定非得继承——可以用组合 + 约定接口（或抽象基类、Protocol）来实现。这也是为什么"组合优先"在实践中被反复强调：很多原本被写成继承的代码，其实只想要多态，并不真的有 is-a 关系，用组合更合适。但这一话题属于更进阶的设计内容，本篇点到为止。

## 5. 总结

### 5.1 本文内容要点

- **单继承语法**：`class Child(Parent):` 声明子类继承父类，子类自动获得父类的属性与方法，并可新增自己的成员。
- **子类获得父类成员**：实例方法、类方法、静态方法、类属性都会被继承；实例属性需要在父类 `__init__` 实际执行后才存在于子类实例上。
- **子类新增成员**：可新增方法、类属性、实例属性；新增只对子类及更下级可见，父类不可见。
- **isinstance / issubclass**：`isinstance(obj, cls)` 沿继承链判断实例与类的关系，`issubclass(cls, base)` 判断类与类的关系，都尊重继承；区别于 `type()` 的精确比较。
- **方法解析顺序**：从子类到父类到 `object`，沿 MRO 线性查找；单继承下 MRO 是一条直线 `[Child, Parent, object]`。
- **子类 __init__**：子类一旦定义 `__init__`，父类的 `__init__` 不再自动调用，通常需用 `super().__init__(...)` 手动触发，以保证父类的不变式先行建立。
- **访问父类成员 / 覆盖**：用 `super()` 在覆盖中复用父类逻辑，是默认写法；也可用"父类名.方法(self)"形式显式调用。
- **object 是根基**：所有类都隐式继承 `object`，获得一整套默认 dunder 方法；`object` 是 MRO 的终点。
- **is-a 与 has-a**：继承表达"是一个"，组合表达"有一个"；真正的 is-a 用继承，否则优先组合。
- **原理**：`__bases__` 存直接父类元组，`__mro__` 存完整查找顺序；`isinstance`/`issubclass` 沿 MRO 判断；继承建立身份层面的 is-a，组合建立持有层面的 has-a。

- 能正确写出 `class Child(Parent):` 形式的单继承声明，并说明子类获得了父类的哪些成员、通过什么机制获得。
- 能在子类中新增方法、类属性、实例属性，并解释"新增只对子类可见"的查找原因。
- 能正确使用 `isinstance` 与 `issubclass`（含元组形式）进行类型判断，并说明它们与 `type()` 精确比较的区别与各自的适用场景。
- 能说出方法解析从子类到父类到 `object` 的查找顺序，并能对照 `__mro__` 解释为什么子类同名方法会遮蔽父类。
- 能说明子类覆盖 `__init__` 时为何必须调用 `super().__init__(...)`，并写出正确的初始化代码（参数对齐的两种风格）。

- 能识别"子类覆盖 __init__ 忘了调 super"这一典型坑，并知道如何规避。
