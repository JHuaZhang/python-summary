## 1. 介绍

### 1.1 什么是单下划线约定

在 Python 中，当你看到一个变量名、方法名或属性名以单下划线 `_` 开头时（如 `_internal_data`、`_helper()`、`_count`），这是一个向其他开发者传达的信号：这个名字是"内部使用的"，不应该在类的外部或模块的外部直接访问。这就是 Python 的"软私有"（soft private）约定。

之所以叫"软私有"，是因为它和 Java/C++ 中的 `private` 关键字有本质区别：Python 解释器不会对单下划线开头的名字做任何访问拦截。你完全可以在类外写 `obj._internal_data`，解释器不会报错，也不会警告。它纯粹是一种命名约定——靠开发者之间的默契来维护，而不是靠编译器或运行时来强制。

这种设计体现了 Python 社区著名的哲学："We are all consenting adults"（我们都是自愿的成年人）。Python 认为程序员应该对自己的代码负责，不需要语言层面把你"保护"起来。如果你真的需要访问一个带下划线的内部属性，Python 信任你有充分的理由，不会拦着你。

单下划线约定在 Python 中有几个不同的使用场景：

- **类内部的私有属性/方法**：用 `_name` 表示"这是实现细节，外部不应依赖"。
- **模块内部的私有对象**：用 `_name` 表示"这是模块内部用的，不要 `from module import *` 导入"。
- **占位变量**：单个 `_` 用作"我不关心这个值"的临时变量。
- **避免关键字冲突**：在名字尾部加单下划线 `name_` 来避开 Python 关键字（如 `class_`、`type_`）。

本篇主要聚焦于第一种——作为"软私有"约定的单下划线前缀，同时覆盖其余几种用法。

### 1.2 基本语法与最小用法

单下划线约定没有"语法"可言——它就是普通的标识符命名。任何以 `_` 开头的合法标识符，都被社区约定为"内部"：

```python
class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner          # 公开属性：外部可自由访问
        self._balance = balance     # 软私有属性：约定不在外部直接访问

    def deposit(self, amount):
        """公开方法：外部调用"""
        self._balance += amount

    def _validate_amount(self, amount):
        """软私有方法：内部校验逻辑，约定不外部调用"""
        if amount <= 0:
            raise ValueError("金额必须为正数")

    def withdraw(self, amount):
        self._validate_amount(amount)   # 内部调用软私有方法
        self._balance -= amount


acc = BankAccount("张三", 1000)
acc.deposit(500)

# 公开属性，正常访问
print(acc.owner)        # 输出：张三

# 软私有属性——解释器不拦截，能访问但不推荐
print(acc._balance)     # 输出：1500

# 软私有方法——同样能调用，但违反约定
acc._validate_amount(-1)  # 抛出 ValueError
```

上面这个例子展示了单下划线约定的核心：`_balance` 和 `_validate_amount` 带下划线，表示"内部使用"，但 Python 不阻止你从外部访问它们。带下划线只是告诉读代码的人："这不是面向你的 API，别依赖它，它随时可能改变。"

**与公开属性的区别仅在"约定"层面**

从解释器的角度看，`self._balance` 和 `self.balance` 没有任何本质差别——它们都是普通的实例属性，存储在实例的 `__dict__` 中，访问规则完全一样。唯一的区别在于人类读者的理解：看到 `_balance` 就知道"这是内部的"。

```python
class Demo:
    def __init__(self):
        self.public = 1
        self._private = 2

d = Demo()
print(d.__dict__)   # 输出：{'public': 1, '_private': 2}
# 两者都在同一个 __dict__ 里，没有任何特殊标记
```

### 1.3 单下划线的四种角色速览

在深入之前，先用一个表格快速区分单下划线在 Python 中的四种不同角色，避免混淆：

| 用法 | 形式 | 含义 | 典型场景 |
|------|------|------|----------|
| 前缀单下划线 | `_name` | 软私有约定，"内部用" | 类/模块内部实现 |
| 尾部单下划线 | `name_` | 避开关键字冲突 | 变量名与关键字重名 |
| 单个下划线 | `_` | 不关心的占位变量 | 解包时忽略某些值 |
| 特殊方法/魔术属性 | `__name__`（双下划线包围） | Python 协议方法 | `__init__`、`__len__` 等 |

本篇聚焦第一行（前缀单下划线）和第二行（尾部单下划线），第三行简要讲解，第四行属于双下划线范畴不在本篇展开。

## 2. 核心内容

### 2.1 前缀单下划线 `_name` 作为类的软私有属性

**作用与场景**

在面向对象设计中，一个类通常会暴露一部分"公开 API"（外部可以调用的属性和方法），同时保留一部分"实现细节"（内部辅助方法、内部状态变量）。公开 API 是类的契约，改动要谨慎；实现细节则可以随时重构，外部不应依赖。单下划线前缀就是用来标记后者的。

典型场景包括：

- **内部状态变量**：类的某个属性只是为了让内部方法协作而存在，不是对外接口的一部分。
- **内部辅助方法**：被公开方法调用的私有工具方法，拆分出来是为了代码清晰而非对外暴露。
- **缓存/临时数据**：一些为了性能优化的缓存值，外部不需要知道。
- **基类的内部钩子**：基类希望子类"可以"覆写但"不必须"的内部方法。

**签名与规则**

- 命名：`_` + 合法标识符，如 `_internal_state`、`_compute_hash()`。
- 访问：外部**能**访问（解释器不拦截），但**约定不**访问。
- 子类：子类同样可以访问父类的 `_name`（与双下划线 mangling 不同，详见第 4 章）。
- 文档工具：`help()`、`pydoc`、Sphinx 等**通常会**省略 `_` 开头的成员（可配置）。

**demo：类的内部状态与辅助方法**

```python
class DataPipeline:
    """数据处理管道：对外只暴露 run()，内部细节用 _ 前缀标记。"""

    def __init__(self, source):
        self.source = source
        self._cache = {}          # 内部缓存：外部不应直接读写
        self._step_count = 0      # 内部计数器：用于日志，非公开 API

    def run(self, record):
        """公开 API：处理一条记录。"""
        self._step_count += 1
        key = self._make_key(record)     # 调用内部方法
        if key in self._cache:
            return self._cache[key]
        result = self._transform(record) # 调用内部方法
        self._cache[key] = result
        return result

    def _make_key(self, record):
        """内部方法：为记录生成缓存键。实现可能随时变。"""
        return (record["category"], record["id"])

    def _transform(self, record):
        """内部方法：实际的数据转换逻辑。"""
        return {k: str(v).upper() for k, v in record.items()}

    @property
    def processed_count(self):
        """公开只读属性：已处理条数（通过公开接口暴露）。"""
        return self._step_count


pipeline = DataPipeline(source="db")
pipeline.run({"category": "A", "id": 1, "name": "alice"})
pipeline.run({"category": "A", "id": 2, "name": "bob"})

# 公开 API：正常使用
print(pipeline.processed_count)   # 输出：2

# 软私有：能访问但违反约定——_cache 的结构是实现细节
print(pipeline._cache)            # 输出：{('A', 1): {...}, ('A', 2): {...}}
print(pipeline._step_count)       # 输出：2
```

**运行结果说明**

`processed_count` 是通过 `@property` 暴露的公开只读属性，内部读取 `_step_count`。这种模式非常常见：内部用 `_step_count` 存储，对外提供一个受控的公开接口（`processed_count`）。这样外部代码只能"读"不能"写"，且如果将来内部计数逻辑改了（比如换成多进程累加），公开接口不变，外部代码不受影响。

而 `pipeline._cache` 虽然能访问到，但它的数据结构是内部实现细节——今天用 `dict`，明天可能换成 `functools.lru_cache` 或外部 Redis。外部代码如果依赖 `_cache` 的具体结构，一旦内部重构就会崩。这正是单下划线约定要传达的："别依赖这个，它会变。"

**help() 与文档工具的行为**

```python
help(DataPipeline)
```

在输出中，你会看到 `run`、`processed_count` 这些公开成员，但 `_make_key`、`_transform`、`_cache`、`_step_count` 这些下划线成员通常不会出现在 `help()` 的公开文档里（具体取决于工具配置，但默认行为如此）。这是单下划线约定的一个实际效果：文档工具自动帮你区分"公开 API"和"内部实现"。

### 2.2 前缀单下划线 `_name` 作为模块级私有

**作用与场景**

单下划线约定不仅用于类内部，也广泛用于模块级别。一个 `.py` 文件通常既有"对外导出的函数/类"，也有"本模块内部用的辅助函数/常量"。用 `_` 前缀标记后者，就告诉模块的使用者："这些不是我的公开 API，别 import。"

这在 `from module import *` 时有实际意义——解释器默认不会导入以 `_` 开头的名字。这是单下划线约定少数有"运行时效果"的地方（详见第 4 章原理）。

**demo：模块内部辅助函数**

假设有一个 `string_utils.py` 模块：

```python
# string_utils.py

# ---- 公开 API ----
def slugify(text):
    """将文本转为 URL 友好的 slug。"""
    return _compact(_normalize(text))

def word_count(text):
    """统计单词数。"""
    return len(text.split())

# ---- 内部辅助（模块私有）----
def _normalize(text):
    """内部：统一转为小写并去重音符号（实现可能变）。"""
    return text.lower().replace("é", "e").replace("ñ", "n")

def _compact(text):
    """内部：空格转连字符、去标点。"""
    import re
    return re.sub(r"[^a-z0-9]+", "-", text).strip("-")

_DEFAULT_MAX_LEN = 80   # 内部常量
```

**在另一个文件中使用**

```python
# main.py
from string_utils import slugify, word_count

print(slugify("Héllo World!"))   # 输出：hello-world
print(word_count("one two three"))  # 输出：3
```

**星号导入的行为**

```python
# bad_import.py
from string_utils import *

print(slugify("Hello World"))    # 输出：hello-world  —— 公开函数，被导入
print(word_count("a b c"))       # 输出：3            —— 公开函数，被导入

# _normalize 和 _compact 不会被星号导入
print(_normalize)                # NameError: name '_normalize' is not defined
```

**运行结果说明**

`from string_utils import *` 只导入不以 `_` 开头的名字。`slugify`、`word_count` 被导入，而 `_normalize`、`_compact`、`_DEFAULT_MAX_LEN` 被自动跳过。这就是模块作者用 `_` 前缀标记内部函数的实际收益：即使用户用了"粗暴"的星号导入，也不会把内部辅助函数污染到他的命名空间里。

当然，用户如果显式写 `from string_utils import _normalize`，解释器是不拦的——单下划线只是约定，显式导入是用户明确知道自己要什么。

### 2.3 `__all__` 与星号导入的关系

**作用**

`__all__` 是一个模块级列表，显式声明"本模块的公开名字有哪些"。它和单下划线都能控制 `from module import *` 的行为，但机制不同：

- **没有 `__all__` 时**：`from module import *` 导入所有不以 `_` 开头的名字（即 `_` 前缀被自动过滤）。
- **有 `__all__` 时**：`from module import *` 只导入 `__all__` 列表里的名字，完全不看下划线前缀。

也就是说，`__all__` 是"白名单"，优先级高于下划线约定。即使一个名字以 `_` 开头，只要它列在 `__all__` 里，星号导入也会把它带入。

**demo：`__all__` 覆盖下划线过滤**

```python
# utils.py
__all__ = ["public_func", "_internal_func"]   # 显式声明公开 API

def public_func():
    return "I am public"

def _internal_func():
    return "I am prefixed with _"

def _another_internal():
    return "Not in __all__"
```

```python
# caller.py
from utils import *

print(public_func())       # 输出：I am public
print(_internal_func())    # 输出：I am prefixed with _   —— 在 __all__ 里，被导入了

print(_another_internal()) # NameError：不在 __all__ 里，未被导入
```

**规则总结表**

| 模块定义 | 名字以 `_` 开头 | 在 `__all__` 中 | `from m import *` 导入？ |
|----------|----------------|-----------------|------------------------|
| 无 `__all__` | 是 | — | 否 |
| 无 `__all__` | 否 | — | 是 |
| 有 `__all__` | 是 | 是 | 是 |
| 有 `__all__` | 是 | 否 | 否 |
| 有 `__all__` | 否 | 是 | 是 |
| 有 `__all__` | 否 | 否 | 否 |

**实践建议**

- 小模块、内部项目：靠 `_` 前缀过滤就够了，不必写 `__all__`。
- 对外发布的库：建议定义 `__all__`，显式控制公开 API，避免星号导入意外带入内部名字（尤其当模块从别处 import 了东西时，没有 `__all__` 可能连 import 进来的名字都被星号导出）。

### 2.4 尾部单下划线 `name_` 避开关键字冲突

**作用与场景**

有时你想要的变量名恰好是 Python 关键字（`class`、`type`、`def`、`return`、`import`、`lambda`、`global` 等），直接用会导致语法错误。Python 约定在这种情况给名字尾部加一个下划线，既保留可读性，又避开冲突。

这和前缀单下划线的含义不同：尾部下划线不是为了"私有"，而是纯粹的命名空间回避手段。

**常见场景**

- 函数参数与关键字冲突：`def register(class_=None, type_=None)`。
- 属性名与关键字冲突：ORM 模型字段、数据库列名映射。
- 变量名与内置函数冲突时（如 `type`、`id`、`list`），也可用尾部下划线，但更常见的是换一个名字（如 `obj_type`）。

**demo：参数名与关键字冲突**

```python
def create_entity(name, type_, class_):
    """type_ 和 class_ 避开 Python 关键字 type 和 class。"""
    return {"name": name, "type": type_, "class": class_}


entity = create_entity("Alice", type_="user", class_="premium")
print(entity)
# 输出：{'name': 'Alice', 'type': 'user', 'class': 'premium'}
```

```python
# ORM 场景：模型字段名与关键字冲突
class CourseModel:
    def __init__(self, name, class_, type_):
        self.name = name
        self.class_ = class_     # 数据库列名可能是 "class"
        self.type_ = type_       # 数据库列名可能是 "type"

    def to_dict(self):
        # 导出时把尾部下划线去掉，恢复原始键名
        return {"name": self.name, "class": self.class_, "type": self.type_}


course = CourseModel("Python 入门", class_="A", type_="online")
print(course.to_dict())
# 输出：{'name': 'Python 入门', 'class': 'A', 'type': 'online'}
```

**运行结果说明**

`class_` 和 `type_` 在 Python 代码中作为合法标识符使用，避免了与关键字 `class`、`type` 的冲突。当需要对外（如数据库、JSON、API 接口）输出原始键名时，在转换层去掉尾部下划线即可。这是 Web 框架、ORM、序列化库中非常常见的做法。

**不要滥用尾部下划线**

如果名字只是和内置函数（非关键字）重名，如 `list`、`dict`、`id`，通常优先换一个更具描述性的名字（`item_list`、`record_id`），而不是 `list_`、`id_`。尾部下划线主要留给真正无法避开的**关键字**冲突。

### 2.5 单个下划线 `_` 作为占位变量

**作用与场景**

一个单独的下划线 `_`（不成对、不与前缀后缀搭配）在 Python 中常被用作"占位变量"，表示"这个值我不用，但语法上需要一个名字"。这是一种约定俗成的写法，解释器对单个 `_` 也没有特殊处理（它就是一个普通变量名）。

**典型场景**

- **解包时忽略某些值**：`a, _, b = (1, 2, 3)` 表示中间的值不要。
- **循环中不需要循环变量**：`for _ in range(5)` 表示只循环 5 次，不用循环变量。
- **国际化（i18n）**：在gettext 模块中，`_()` 是翻译函数的约定别名（`_("text")`），这是另一种完全不同的用法。

**demo：解包占位**

```python
# 元组解包，只需要第一个和最后一个值
record = ("Alice", 30, "工程师", "北京", 13800138000)
name, _, _, city, phone = record

print(name)    # 输出：Alice
print(city)    # 输出：北京
print(phone)   # 输出：13800138000
# 中间的 30 和 "工程师" 被丢弃（绑定到 _，但不使用）
```

```python
# 连续多个占位：可以用 *_ 忽略中间所有值
name, *_, phone = record
print(name)    # 输出：Alice
print(phone)   # 输出：13800138000
```

**demo：循环占位**

```python
# 只想重复执行 N 次，不关心循环变量
for _ in range(3):
    print("刷一条日志")
# 输出：
# 刷一条日志
# 刷一条日志
# 刷一条日志
```

```python
# 生成 5 个随机数的列表，不需要索引
import random
samples = [random.random() for _ in range(5)]
print(len(samples))   # 输出：5
```

**运行结果说明**

`_` 在这里只是一个"被丢弃的变量名"。它在技术上仍然是一个正常的变量，会绑定到某个值，但约定上表示"我不会用它"。这让代码读起来更清晰：`for _ in range(3)` 一眼就知道"只是循环 3 次"，而 `for i in range(3)` 则暗示 `i` 会在循环体内被用到。

**注意：`_` 在交互式解释器中的特殊含义**

在 Python 交互式 shell（REPL）中，单个 `_` 是一个特殊变量，自动保存上一次表达式的结果：

```python
>>> 2 + 3
5
>>> _
5
>>> _ * 2
10
>>> _
10
```

这和"占位变量"是不同的语境——REPL 的 `_` 是解释器自动维护的，脚本文件中不存在这个行为。

### 2.6 IDE / linter / 文档工具对单下划线的识别

单下划线约定虽然是"软"的，但主流工具链都识别它，会在静态分析层面给出提示或过滤。这是单下划线在工程实践中真正发挥作用的地方。

**IDE 行为（以 PyCharm / VS Code 为例）**

- **自动补全**：输入 `obj.` 后，IDE 会把公开成员排在前面，`_` 开头的成员排在后面或折叠隐藏，需要手动展开才会显示。
- **未使用警告**：如果你在类外访问 `obj._internal`，部分 lint 规则会给出"访问受保护成员"的提示（如 Pylint 的 `protected-access` 规则）。
- **重构支持**：IDE 的"重命名"功能通常会对 `_` 开头的成员给出"这是内部成员，重命名可能影响子类"的提示。

**Pylint 的 `protected-access` 规则**

```python
class Service:
    def __init__(self):
        self._config = {"timeout": 30}


svc = Service()
print(svc._config)   # Pylint: W0212 - Access to a protected member _config of a client class
```

Pylint 会对 `svc._config` 这行报警告 `W0212`，提示"访问了受保护成员"。但这只是警告，不是错误——你可以通过注释 `# pylint: disable=protected-access` 抑制，或在配置中调整规则。这正体现了单下划线"约定但不强制"的性质。

**文档工具行为**

- **`pydoc`/`help()`**：默认不显示 `_` 开头的成员。
- **Sphinx（autodoc）**：默认不生成 `_` 开头成员的文档，需配置 `:private-members:` 才会包含。
- **pdoc**：默认隐藏 `_` 开头成员。

```python
# Sphinx 配置示例：在 conf.py 或指令中启用私有成员文档
# .. autoclass:: MyClass
#    :private-members:
```

这种工具链的统一行为，使得即使单下划线没有运行时强制力，它在工程协作中仍然有实际的约束效果——文档、补全、lint 都会帮你"提醒"这是内部成员。

### 2.7 单下划线 vs 双下划线：行为速览

Python 还有一种"双下划线前缀"（dunder prefix，如 `__name`），它和单下划线经常被混淆，但机制完全不同。这里做速览对比，详细的双下划线 name mangling 见本系列第 10 篇。

| 对比项 | 单下划线 `_name` | 双下划线 `__name` |
|--------|------------------|-------------------|
| 是否强制 | 否，纯约定 | 是，触发 name mangling |
| 运行时拦截 | 无 | 无（但仍可访问改写后的名字） |
| 名字改写 | 不改写 | 编译期改写为 `_ClassName__name` |
| 外部访问 | `obj._name` 直接可访问 | `obj.__name` 报 AttributeError（需 `obj._ClassName__name`） |
| 星号导入过滤 | 是（无 `__all__` 时） | 否（双下划线不以单 `_` 开头，不受此规则影响） |
| 子类访问父类 | 直接可访问 | 受 mangling 影响，需注意名字改写 |
| 主要目的 | 传达"内部用" | 避免子类同名属性意外覆盖 |

**demo：直观对比**

```python
class Parent:
    def __init__(self):
        self._soft_private = "单下划线：软私有"
        self.__hard_private = "双下划线：触发 mangling"


p = Parent()

# 单下划线：直接访问
print(p._soft_private)     # 输出：单下划线：软私有

# 双下划线：直接访问报错
try:
    print(p.__hard_private)
except AttributeError as e:
    print(e)               # 输出：'Parent' object has no attribute '__hard_private'

# 双下划线：需用改写后的名字访问
print(p._Parent__hard_private)   # 输出：双下划线：触发 mangling

# 看 __dict__ 里实际存的名字
print(p.__dict__)
# 输出：{'_soft_private': '单下划线：软私有', '_Parent__hard_private': '双下划线：触发 mangling'}
```

**关键区别点**

- `_soft_private` 在 `__dict__` 里原样存储，外部直接能访问。
- `__hard_private` 在 `__dict__` 里被改写为 `_Parent__hard_private`，外部用原名 `__hard_private` 访问不到（但能通过改写后的名字"绕过"，所以双下划线也不是真正的强制私有）。
- 单下划线没有任何名字改写，访问 `_x` 和访问 `x` 在运行时层面完全一样。

**何时用单下划线，何时用双下划线**

绝大多数情况用单下划线就够了。双下划线 name mangling 主要用于"防止子类无意中覆盖父类的属性名"——这在设计可被广泛继承的基类时偶尔有用，但在普通业务代码中很少需要，且会带来调试困难（改写后的名字不直观）。Python 社区的共识是：默认用单下划线，只在确有避免属性名冲突的需求时才考虑双下划线。

### 2.8 在子类中访问父类的单下划线成员

**作用与场景**

单下划线约定"不在类外访问"，但"子类算类内还是类外"是一个常见的困惑点。Python 的惯例是：子类可以访问父类的 `_name` 成员，这属于"类内部协作"的范畴。这也是单下划线和双下划线的一个重要差异——双下划线的 mangling 会让子类访问父类私有属性变得绕弯。

**demo：子类使用父类的单下划线方法**

```python
class BaseUploader:
    def upload(self, path):
        data = self._read_file(path)       # 调用内部方法
        self._send(data)                    # 调用内部方法
        return True

    def _read_file(self, path):
        """内部方法：读取文件内容。子类可覆写。"""
        with open(path, "rb") as f:
            return f.read()

    def _send(self, data):
        """内部方法：发送数据到服务端。子类可覆写。"""
        raise NotImplementedError("子类需实现 _send")


class S3Uploader(BaseUploader):
    def _send(self, data):
        """覆写父类的内部方法：改为上传到 S3。"""
        print(f"上传 {len(data)} 字节到 S3")
        # 实际调用 boto3 等
        return True


class LocalDiskUploader(BaseUploader):
    def _send(self, data):
        """覆写父类的内部方法：改为写入本地磁盘。"""
        print(f"写入 {len(data)} 字节到本地磁盘")
        return True


# 子类通过覆写 _send 改变行为，upload() 的流程不变
s3 = S3Uploader()
s3._send(b"hello")   # 输出：上传 5 字节到 S3
```

**运行结果说明**

这里 `_read_file` 和 `_send` 用单下划线标记，表示"这是 BaseUploader 的内部钩子方法"。子类 `S3Uploader`、`LocalDiskUploader` 通过覆写 `_send` 来定制具体上传方式，而父类的 `upload()` 编排流程保持不变。这是"模板方法模式"的一种体现，单下划线在这里恰好传达了"这些方法是给子类协作用的，不是给外部调用方用的"。

如果这里改成双下划线 `__send`，子类覆写时会被 mangling 成不同的名字（`_S3Uploader__send` vs `_BaseUploader__send`），父类的 `upload()` 调用 `self.__send()` 实际调用的是 `_BaseUploader__send`，子类的覆写就不生效了——这正是双下划线在某些场景下"过度保护"导致的问题。

### 2.9 使用 `_` 前缀的"契约"含义

**约定即契约**

给一个属性加 `_` 前缀，相当于你在和代码的使用者签一份非正式契约：

- **你承诺**：这个名字是实现细节，我保留随时修改它的权利（改名、删除、改语义），且不事先通知。
- **使用者承诺**：我不会在外部代码中依赖这个名字；如果非要访问，后果自负，升级时出了问题不怪作者。

这份契约没有法律效力（解释器不仲裁），但在团队协作和库的版本演进中非常有用。理解了这份契约，就能解释为什么有时候看到别人的 `_` 属性自己也想用——因为加 `_` 是在明确"这不是稳定接口"。

**demo：版本演进中的 `_` 属性**

```python
# v1.0：内部用 _items 列表存储
class Stack:
    def __init__(self):
        self._items = []

    def push(self, x):
        self._items.append(x)

    def pop(self):
        return self._items.pop()


# v2.0：内部改用 deque 优化性能（_items 被删除）
from collections import deque

class Stack:
    def __init__(self):
        self._items = deque()   # 内部结构变了

    def push(self, x):
        self._items.append(x)

    def pop(self):
        return self._items.popleft()   # deque 用 popleft
```

如果有外部代码写了 `stack._items[0]` 来"偷看"栈顶，在 v1.0 能跑（list 支持索引），在 v2.0 会报错（deque 不支持索引访问）或行为变化。`_` 前缀提前警告了："别这么用。" 如果外部只用公开 API（`push`/`pop`），从 v1 升级到 v2 毫无影响。

这就是单下划线约定在版本演进中的价值：它划清了"稳定接口"和"可变实现"的边界。

**test 中访问 `_` 属性是可接受的**

在单元测试中，直接访问 `_` 属性是常见且可接受的做法——测试本来就该深入实现细节。Pylint 通常配置为在测试文件中不报 `protected-access` 警告。

```python
# test_stack.py
def test_stack_internal_state():
    s = Stack()
    s.push(1)
    s.push(2)
    # 测试中直接检查内部状态是合理的
    assert len(s._items) == 2   # 测试代码可以访问 _ 前缀成员
```

### 2.10 尾部单下划线的其他细微用法

除了避关键字冲突，尾部单下划线偶尔还有几种用法，虽然不如前两种常见，但值得了解：

**在生成器/循环中区分同名变量**

有时你在循环里需要用到一个和外部变量同名的临时变量，又不想覆盖外部的值，可以给内部的加尾部下划线：

```python
name = "全局名字"

for name_ in ["Alice", "Bob", "Charlie"]:
    print(name_)
# 循环结束后 name 仍然是 "全局名字"
print(name)      # 输出：全局名字
```

不过这种做法可读性一般，更推荐直接换一个有意义的名字（如 `person_name`）。尾部下划线主要还是留给避关键字冲突的场景。

**与内置名短暂遮蔽时**

当某个局部变量短暂遮蔽了内置函数名，又想保留原名语义时，也有人用尾部下划线：

```python
def process(items, id_=None):
    # 参数 id_ 避免遮蔽内置 id()
    if id_ is not None:
        return id(id_)   # 这里要用内置 id()
    return [id(x) for x in items]
```

但如前所述，更推荐改成 `item_id` 这类描述性名字。尾部下划线应作为"实在避不开关键字时"的兜底手段，而非首选。

## 3. 最佳实践

### 3.1 何时该加 `_`，何时不该

**推荐原则：用于"实现细节"，不用于"这很难用"**

单下划线的正确用途是标记"实现细节"——那些为了内部协作而存在、随时可能改变、外部不应依赖的东西。它不应该被用来"隐藏"本应公开的功能，也不应该过度使用导致每个属性都带下划线。

判断标准：

- 问自己："外部代码会用这个属性/方法吗？" 会 → 公开，不加 `_`。不会 → 加 `_`。
- 问自己："我下个版本可能删掉或改掉这个吗？" 可能 → 加 `_`。绝不可能，它是稳定契约的一部分 → 不加 `_`。

**推荐写法 vs 不推荐写法**

```python
# 推荐：只有真正的实现细节加 _，公开 API 不加
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius            # 公开：用户需要读温度
        self._kelvin_cache = None         # 内部：缓存，实现细节

    @property
    def kelvin(self):
        if self._kelvin_cache is None:
            self._kelvin_cache = self.celsius + 273.15   # 内部计算
        return self._kelvin_cache
```

```python
# 不推荐：过度使用 _，把用户需要的东西也藏起来
class Temperature:
    def __init__(self, celsius):
        self._celsius = celsius          # 用户需要读温度却加 _，徒增访问成本
        self._kelvin_cache = None

    def _get_celsius(self):              # 简单读取却包一层私有方法，没必要
        return self._celsius
```

过度使用 `_` 会让用户不得不写 `temp._celsius` 来访问一个本该公开的值，增加心智负担，也违背了"We are all consenting adults"的信任精神。

### 3.2 不要在类外无谓地访问 `_` 成员

**推荐：通过公开 API 间接使用**

```python
# 推荐：只使用公开 API
queue = TaskQueue()
queue.add(task)
queue.process()
print(queue.size)        # 公开属性
```

**不推荐：直接掏内部状态**

```python
# 不推荐：直接访问 _ 前缀成员
queue = TaskQueue()
queue._tasks.append(task)        # 绕过 add() 的校验逻辑，直接操作内部列表
print(queue._task_count)         # 用内部计数器而非公开 size
```

直接访问 `_` 成员的问题在于：

1. **绕过校验**：公开方法 `add()` 可能做了参数校验、去重、日志记录，你直接 `_tasks.append` 全绕过了。
2. **耦合实现细节**：`_tasks` 今天是 list，明天可能改成 deque 或 set，你的代码会崩。
3. **版本升级风险**：作者明确说了这是内部成员，随时可能删，你用了就是自找麻烦。

**例外情况**

- **测试代码**：可以访问 `_` 成员来断言内部状态。
- **调试排查**：临时 `print(obj._internal)` 来定位问题，无可厚非。
- **第三方库的 monkey patch**：有时不得不改库的内部行为，但要做好版本升级时会坏的觉悟。
- **与标准库/知名库协作**：某些库的 `_` 成员长期稳定，社区约定可以访问（但这种情况下更建议提 issue 让作者暴露公开接口）。

### 3.3 子类覆写父类 `_` 方法要谨慎

**推荐：明确父类是否允许覆写**

```python
class BaseHandler:
    def handle(self, request):
        data = self._parse(request)      # 父类设计为可覆写的钩子
        return self._respond(data)

    def _parse(self, request):
        """子类可覆写：解析请求。"""
        return request.body

    def _respond(self, data):
        """子类可覆写：生成响应。"""
        return {"data": data}
```

当一个基类把某些方法用 `_` 标记时，它通常意味着"这些是内部协作钩子，子类可以覆写"。但不是所有 `_` 方法都应该被覆写——有些纯粹是父类自己的工具方法，覆写会破坏父类的内部逻辑。

**区分方法**：看父类的文档/注释。如果父类文档说"子类可覆写 `_xxx`"，那就可以覆写；如果没有说明，默认不覆写，只调公开接口。如果一定要改行为，优先用组合而非继承。

### 3.4 模块私有与 `__all__` 的搭配

**推荐：对外发布的库同时用 `_` 前缀和 `__all__`**

```python
# mypackage/core.py
__all__ = ["PublicClass", "public_func"]

class PublicClass:
    """公开 API。"""
    pass

def public_func():
    """公开 API。"""
    pass

def _helper():
    """内部辅助：即便漏写 __all__ 也被 _ 过滤。"""
    pass
```

双重保险：`__all__` 显式声明公开 API，`_` 前缀兜底过滤内部名字。即使将来有人重构时忘了更新 `__all__`，新增的 `_` 函数也不会被星号导入意外带出。

**不推荐：只靠 `__all__` 而不加 `_`**

```python
# 只靠 __all__，内部函数还是没加 _
__all__ = ["public_func"]

def public_func():
    pass

def helper():        # 内部函数却没加 _，星号导入虽不导入，但显式 import 仍可
    pass
```

这种情况下虽然 `from m import *` 不会带入 `helper`（因为不在 `__all__`），但 `helper` 没有任何"内部"标记，别的开发者看到它时不会意识到这是私有的。`_` 前缀的视觉信号是 `__all__` 无法替代的。

### 3.5 命名要清晰，`_` 不能替代好名字

**推荐：`_` 前缀加清晰的名字**

```python
class Payment:
    def __init__(self):
        self._pending_transactions = []     # 清晰：待处理交易
        self._retry_count = 0               # 清晰：重试次数
```

**不推荐：`_` 前缀加模糊名字**

```python
class Payment:
    def __init__(self):
        self._data = []        # _data 是什么？待处理交易？历史记录？
        self._tmp = 0          # _tmp 是什么？重试次数？临时变量？
```

`_` 前缀只是标记"内部"，但内部不等于可以乱起名。内部成员同样会被同事（和未来的自己）读到，名字要能让读者一眼明白它的用途。`_data`、`_tmp`、`_x` 这类名字在内部也是坏味道。

### 3.6 Python 的"consenting adults"哲学：不要试图强制私有

**推荐：接受约定，用单下划线表达意图**

Python 的设计哲学认为，强制私有化（如 Java 的 `private`）往往带来更多麻烦：测试困难、元编程受限、继承不够灵活。Python 选择信任开发者，用 `_` 前缀表达"这是内部的"，靠文档和约定来传达，而不是用编译器来锁死。

**不推荐：用 `__` 双下划线来"假装强制私有"**

```python
# 不推荐：普通业务类用 __ 试图强制私有
class User:
    def __init__(self, name):
        self.__name = name      # 试图"强制私有"
```

这种写法带来的问题：

- 测试时访问要写 `user._User__name`，极不直观。
- 子类想协作访问父类数据时被 mangling 挡住。
- 调试时 `__dict__` 里看到 `_User__name`，增加困惑。
- 并没有真正阻止访问（仍可绕过），只是制造了障碍。

普通业务代码用单下划线 `_name` 足矣。双下划线留给"确需避免子类属性名冲突"的特定场景（如框架基类设计）。

### 3.7 测试中访问 `_` 成员的取舍

**推荐：测试可以访问，但优先测公开行为**

```python
# 优先：通过公开行为断言
def test_stack_push_pop():
    s = Stack()
    s.push(1)
    assert s.pop() == 1
    assert s.size == 0
```

```python
# 次选：当公开行为不足以验证时，访问内部状态
def test_stack_internal_after_push():
    s = Stack()
    s.push(1)
    s.push(2)
    # 内部结构是 deque/list，检查长度
    assert len(s._items) == 2
```

优先通过公开 API 来测试（黑盒测试），因为公开 API 是稳定契约，测它最有意义。只有当公开行为无法覆盖某些边界（如"内部缓存是否生效"），才退而访问 `_` 成员做白盒断言。这样测试不会过度耦合实现细节，重构时不易碎。

### 3.8 对外 API 文档中不要暴露 `_` 成员

**推荐：文档只描述公开 API**

```python
class FileProcessor:
    """文件处理器。

    公开方法：
        process(path): 处理指定路径的文件。
        result: 获取处理结果（只读属性）。
    """

    def __init__(self):
        self._buffer = []          # 不出现在文档里
        self._encoding = "utf-8"   # 不出现在文档里

    def process(self, path):
        """处理文件。"""
        ...

    @property
    def result(self):
        """处理结果。"""
        ...
```

`_` 前缀的成员天然应被文档工具隐藏，你的 docstring 和 README 也应只描述公开 API。把 `_buffer`、`_encoding` 写进用户文档，等于告诉用户"你可以用这些"，与 `_` 的约定自相矛盾。

## 4. 原理

### 4.1 单下划线没有运行时机制：`_x` 与 `x` 本质相同

**核心事实：解释器对单下划线不做任何特殊处理**

这是理解单下划线约定的最关键一点：Python 解释器在运行时层面，对以 `_` 开头的属性名和普通属性名一视同仁。`self._balance = 100` 和 `self.balance = 100` 在解释器看来执行的是完全相同的字节码——都是往实例的 `__dict__` 里写一个键值对。`obj._balance` 和 `obj.balance` 的读取也一样，都是普通的属性查找。

**验证：属性查找完全一致**

```python
class Demo:
    def __init__(self):
        self.public = 1
        self._private = 2


d = Demo()

# 两者存储位置相同：都在实例 __dict__
print(d.__dict__)
# 输出：{'public': 1, '_private': 2}

# getattr/setattr 对两者行为一致
print(getattr(d, "public"))     # 输出：1
print(getattr(d, "_private"))   # 输出：2
print(hasattr(d, "public"))     # 输出：True
print(hasattr(d, "_private"))   # 输出：True

setattr(d, "_private", 99)
print(d._private)               # 输出：99
```

**字节码层面也没有差异**

用 `dis` 模块反汇编可以看到，访问 `obj._x` 和 `obj.x` 生成的字节码结构完全相同：

```python
import dis

def read_public(obj):
    return obj.x

def read_private(obj):
    return obj._x

print("=== read_public 字节码 ===")
dis.dis(read_public)
# 输出（核心部分）：
#   LOAD_GLOBAL    obj
#   LOAD_ATTR      x
#   RETURN_VALUE

print("=== read_private 字节码 ===")
dis.dis(read_private)
# 输出（核心部分）：
#   LOAD_GLOBAL    obj
#   LOAD_ATTR      _x
#   RETURN_VALUE
```

两条字节码唯一的区别就是 `LOAD_ATTR` 指令所带的属性名字符串不同（`x` vs `_x`）。解释器执行的指令序列完全一样，没有任何"检查下划线"的额外步骤。这从底层证明了：单下划线约定没有任何运行时机制支撑，它纯粹是命名层面的约定。

**属性查找的完整流程（与下划线无关）**

当你写 `obj._x` 时，Python 的属性查找流程是：

1. 先在 `type(obj).__dict__` 及其基类的 `__dict__` 里找 `_x`（找数据描述符）。
2. 再在 `obj.__dict__` 里找 `_x`。
3. 再在 `type(obj).__dict__` 里找非数据描述符。
4. 都找不到则触发 `__getattr__` 或抛 `AttributeError`。

这个流程对 `_x` 和 `x` 完全一致——没有任何"如果名字以 `_` 开头就走特殊分支"的逻辑。属性名只是字符串 key，下划线只是字符串的一个字符而已。

**结论**

单下划线约定的"软"字就体现在这里：它没有运行时机制，不改变字节码，不改变属性查找流程，不改变存储方式。`_x` 和 `x` 的唯一区别是"人类读者的理解不同"。这种设计是有意为之的——Python 把"什么是内部"的判断交给开发者，而不是交给解释器。

### 4.2 `from module import *` 的下划线过滤机制

**这是单下划线唯一有运行时效果的地方**

虽然单下划线在类属性层面没有任何运行时机制，但在模块导入层面，`from module import *` 确实有一条与下划线前缀相关的规则。这是 Python 语言规范明确规定的少数"下划线有实际效果"的场景。

**规则（Python 语言规范）**

当你写 `from module import *` 时，解释器的导入逻辑是：

1. **如果模块定义了 `__all__` 列表**：只导入 `__all__` 中列出的名字。无论这些名字是否以 `_` 开头，都导入；没列在 `__all__` 里的，不导入。
2. **如果模块没有定义 `__all__`**：导入模块命名空间中所有不以 `_` 开头的名字。这里的"模块命名空间"包括模块本身定义的函数/类/变量，也包括该模块从别处 import 进来的名字。

也就是说，`import *` 在没有 `__all__` 时，会用"以 `_` 开头"作为过滤条件，跳过下划线开头的名字。

**实现细节：import 系统读取模块 `__dict__`**

CPython 的 import 机制在执行 `from module import *` 时，大致等价于以下 Python 伪代码：

```python
# 伪代码：from module import * 的内部逻辑
def star_import(module):
    if hasattr(module, "__all__"):
        names_to_import = module.__all__
    else:
        # 没有定义 __all__：取所有不以 _ 开头的公开名字
        names_to_import = [
            name for name in module.__dict__
            if not name.startswith("_")
        ]

    for name in names_to_import:
        globals()[name] = getattr(module, name)
```

关键点：

- 过滤依据是 `name.startswith("_")`——只要以下划线开头就跳过，包括单下划线 `_x`、双下划线 `__x`、双下划线包围 `__x__`（不过 `__all__`、`__name__` 等模块级 dunder 本来也不该被星号导入）。
- 这个过滤只在"没有 `__all__`"时生效；有 `__all__` 时完全以 `__all__` 为准，下划线过滤不再起作用。
- 过滤的是"模块命名空间里的名字"，包括模块自己 import 进来的东西。这就是为什么对外库建议用 `__all__`——否则你 `import os` 进来，用户 `from your_module import *` 就会意外得到 `os`。

**验证：`__all__` 与下划线过滤的优先级**

```python
# module_a.py
def public():
    return "public"

def _private():
    return "private"

__all__ = ["public", "_private"]   # 显式把 _private 也列入
```

```python
# caller.py
from module_a import *

print(public())      # 输出：public
print(_private())    # 输出：private   —— 有 __all__，下划线过滤失效
```

即便 `_private` 以下划线开头，因为它在 `__all__` 里，星号导入依然把它带入了。这证明 `__all__` 白名单的优先级高于下划线过滤。

**反过来：没有 `__all__` 时下划线过滤生效**

```python
# module_b.py
def public():
    return "public"

def _private():
    return "private"

def __dunder__():
    return "dunder"
# 没有 __all__
```

```python
from module_b import *

print(public())        # 输出：public
print(_private())      # NameError: _private 未导入
print(__dunder__())    # NameError: __dunder__ 未导入
```

`_private` 和 `__dunder__` 都以下划线开头，被星号导入跳过。

**为什么 Python 要设计这个过滤规则**

这条规则存在的目的，正是配合单下划线约定：模块作者用 `_` 标记内部名字，星号导入自动跳过它们，即便用户用了"粗暴"的 `import *`，也不会把内部辅助函数污染到用户命名空间。这是 Python 把"约定"和"机制"结合得最好的一处——约定负责标记，机制负责过滤，两者协同。

但注意：这条规则只管 `import *`，不管显式导入。`from module_b import _private` 是完全合法的，解释器不拦。单下划线始终保持"软"的性质——它引导而非强制。

### 4.3 与双下划线 name mangling 的本质区别

**单下划线不改名，双下划线编译期改名**

这是两种约定最核心的机制差异。单下划线前缀（`_name`）在编译期和运行时都不改名字，`_name` 在 `__dict__` 里就是 `_name`。而双下划线前缀（`__name`，注意不是 dunder `__name__`）会在编译期触发 name mangling（名字改写），被改写成 `_ClassName__name` 存入 `__dict__`。

**name mangling 的改写规则**

当一个以双下划线开头、不以双下划线结尾的名字（即 `__name` 而非 `__name__`）出现在类体内时，Python 编译器会把它改写为 `_ClassName__name`，其中 `ClassName` 是当前类的名字。这个改写发生在编译期——在字节码生成阶段就把属性名替换掉了。

```python
class MyClass:
    def __init__(self):
        self.__value = 42       # 编译期改写为 self._MyClass__value = 42

obj = MyClass()
print(obj.__dict__)
# 输出：{'_MyClass__value': 42}
# 注意：实际存储的键是 _MyClass__value，不是 __value
```

**对比：单下划线不改名**

```python
class MyClass:
    def __init__(self):
        self._value = 42        # 不改写，存为 _value

obj = MyClass()
print(obj.__dict__)
# 输出：{'_value': 42}
```

单下划线的 `_value` 原样存储，没有 mangling。

**字节码对比**

```python
import dis

class Single:
    def __init__(self):
        self._x = 1

class Double:
    def __init__(self):
        self.__x = 1

print("=== Single._x 字节码 ===")
dis.dis(Single.__init__)
# 输出核心：
#   LOAD_CONST   1
#   LOAD_FAST    self
#   STORE_ATTR   _x       ← 属性名原样

print("=== Double.__x 字节码 ===")
dis.dis(Double.__init__)
# 输出核心：
#   LOAD_CONST   1
#   LOAD_FAST    self
#   STORE_ATTR   _Double__x     ← 编译期已改写为 _Double__x
```

关键区别在 `STORE_ATTR` 指令所带的属性名字符串：

- 单下划线：`STORE_ATTR _x`——编译器看到的还是 `_x`。
- 双下划线：`STORE_ATTR _Double__x`——编译器在生成字节码时已经把 `__x` 改写成了 `_Double__x`。

这说明 name mangling 是**编译期**行为，不是运行时行为。到运行时，`Double.__init__` 执行的就是正常的 `STORE_ATTR _Double__x`，和普通属性赋值无异。mangling 的"魔法"在编译阶段就完成了。

**mangling 的实际效果：外部访问原名会失败**

```python
obj = Double()
print(obj._Double__x)   # 输出：1   —— 用改写后的名字能访问
print(obj.__x)          # AttributeError: 'Double' object has no attribute '__x'
```

因为 `__dict__` 里存的是 `_Double__x`，用原名 `__x` 去找自然找不到。这就是双下划线"看起来强制私有"的原因——不是真的拦了你，只是名字被改了，你用原名找不到。

但用改写后的名字 `_Double__x` 依然能直接访问。所以双下划线也不是真正的强制私有，只是"改了名字让你不容易意外撞上"。这也符合 Python 的一致哲学：不真正禁止访问，只是制造障碍减少误用。

**mangling 的目的：避免子类属性名冲突**

name mangling 的设计初衷不是为了"私有化"，而是为了避免子类和父类的同名属性意外冲突。来看一个经典场景：

```python
class Base:
    def __init__(self):
        self.__value = "base"     # 改写为 _Base__value

class Derived(Base):
    def __init__(self):
        super().__init__()
        self.__value = "derived"  # 改写为 _Derived__value，不会覆盖父类的

d = Derived()
print(d.__dict__)
# 输出：{'_Base__value': 'base', '_Derived__value': 'derived'}
# 父类和子类各自的 __value 互不干扰
```

如果这里用单下划线 `_value`，子类的赋值会覆盖父类的：

```python
class Base:
    def __init__(self):
        self._value = "base"

class Derived(Base):
    def __init__(self):
        super().__init__()
        self._value = "derived"   # 覆盖了父类的 _value

d = Derived()
print(d.__dict__)
# 输出：{'_value': 'derived'}   —— 只有一个 _value
```

这就是双下划线 mangling 的真正用途：当你设计一个可能被广泛继承的基类，且希望基类的某些属性不被子类同名属性意外覆盖时，用 `__name` 让它变成 `_Base__name`，子类的 `__name` 变成 `_Derived__name`，两者共存不冲突。

**总结对比表**

| 维度 | 单下划线 `_name` | 双下划线 `__name` |
|------|------------------|-------------------|
| 编译期行为 | 不改名 | 改写为 `_ClassName__name` |
| 运行时存储 | 原名 `_name` | 改写后 `_ClassName__name` |
| 字节码 `STORE_ATTR` | 属性名为 `_name` | 属性名为 `_ClassName__name` |
| 外部访问原名 | 可访问 | AttributeError（找不到原名） |
| 外部访问改写名 | — | 可访问 `_ClassName__name` |
| `import *` 过滤 | 过滤（以 `_` 开头） | 不过滤（改写后以 `_C` 开头，不以 `__` 开头）* |
| 设计目的 | 标记"内部用" | 避免子类属性名冲突 |
| 强制程度 | 无 | 改名但可绕过 |

*注：`from module import *` 过滤的是以 `_` 开头的名字。双下划线 `__name` 在模块级别（不在类体内）不会被 mangling，所以仍以 `__` 开头，会被 `import *` 过滤。mangling 只发生在类体内。这里说的"不过滤"是指类体内的双下划线属性经 mangling 后在 `__dict__` 里以 `_ClassName__name` 形式存在，不再以 `__` 开头；但模块级的变量 `__name`（不在类内）仍以 `__` 开头会被过滤。这个细节容易混淆，需要分清"类内属性"和"模块级变量"的语境。

**核心结论**

- 单下划线：编译期不改名，运行时不拦截，纯粹是约定。`_x` 和 `x` 在解释器层面没有本质区别。
- 双下划线：编译期改名（mangling），运行时不拦截但原名访问不到。`__x` 在解释器层面变成了 `_ClassName__x`，有实际的机制差异。
- 两者都"不真正强制"——双下划线只是改了名字让你用原名找不到，但用改写后的名字仍能访问。
- 普通代码用单下划线足够；双下划线留给特定需求（避免子类属性冲突）。

### 4.4 文档工具识别 `_` 前缀的原理

**为何 `help()`、`pydoc`、Sphinx 默认隐藏 `_` 成员**

这些工具并非"被解释器告知"哪些是私有——它们只是自己在遍历类/模块的成员时，主动跳过了以 `_` 开头的名字。工具层面对单下划线的识别，是工具开发者遵循了 Python 社区约定的结果，不是语言层面的强制。

**`pydoc` 的过滤逻辑（示意）**

`pydoc` 在生成文档时，大致会做这样的过滤：

```python
# 伪代码：pydoc 收集成员时的过滤
def doc_members(cls):
    members = []
    for name in dir(cls):
        if name.startswith("_"):
            # 跳过下划线开头（除非是 __dunder__ 且工具配置要显示）
            continue
        members.append((name, getattr(cls, name)))
    return members
```

同样的逻辑也适用于 `help()`：它底层调用 `pydoc`，所以行为一致。当你 `help(SomeClass)` 时，看到的成员列表是 `pydoc` 过滤后的结果，`_` 开头的默认不显示。

**Sphinx autodoc 的 `:private-members:` 选项**

Sphinx 的 `autodoc` 扩展默认也不文档化 `_` 开头的成员，但提供了 `:private-members:` 选项让你显式包含：

```rst
.. autoclass:: MyClass
   :members:
   :private-members:
```

加了 `:private-members:` 后，`_internal_method` 这类成员也会出现在生成的文档里。这进一步说明工具的过滤是可配置的——它遵循约定，但允许你覆盖默认行为。

**lint 工具的 `protected-access` 规则**

Pylint 等工具的 `protected-access` 规则也是"工具层面遵循约定"的体现。它的检测逻辑大致是：如果在一个不属于"类自身/子类"的语境中访问了 `obj._name`，就报警告。这个规则完全是 Pylint 自己实现的静态分析，不是解释器提供的功能。

```python
# Pylint 检测逻辑示意（伪代码）
def check_protected_access(node):
    # 如果访问 obj._name，且 obj 不是 self/cls，报警告
    if (node.attr.startswith("_")
            and not node.attr.startswith("__")
            and not is_self_or_cls(node.expr)):
        warn("W0212", "access to protected member")
```

这类 lint 规则是独立的静态分析，和解释器运行时无关。它之所以能工作，是因为"单下划线=内部"是一个被广泛认可的社区约定，lint 工具据此做检查。如果某天社区约定改了（比如改成用 `@private` 装饰器标记），lint 规则也会相应调整——它跟随约定，而非定义约定。

### 4.5 单下划线约定与 Python 数据模型的关系

**Python 没有"访问控制"数据模型**

Python 的数据模型（data model）中，类和实例的属性访问由 `__getattribute__`、`__getattr__`、`__setattr__` 提供底层支持，但这些方法对属性名字符串没有任何特殊处理——它们只是按名字做字典查找。Python 没有像 C++ 那样的 `public/private/protected` 访问控制修饰符，也没有在数据模型层面为"私有"概念预留任何位置。

这意味着单下划线约定完全游离于数据模型之外：

- `__getattribute__` 不检查下划线。
- `__setattr__` 不检查下划线。
- 描述符协议不区分下划线。
- `property` 不区分下划线。

**双下划线是数据模型层面的吗**

严格说，name mangling 也不算"数据模型"——它发生在编译期（AST 到字节码阶段），而数据模型（`__getattribute__` 等）是运行时的。mangling 在字节码生成时就把名字改了，到运行时 `__getattribute__` 看到的只是普通的 `_ClassName__name` 字符串，和其他属性查找没区别。

所以 Python 的属性访问控制，从数据模型到运行时再到编译期，真正"有机制"的只有 name mangling 一处（且只是改名而不拦截）。单下划线则完全在机制之外，纯靠社区约定和工具识别来生效。

**这和"We are all consenting adults"一致**

Python 之父 Guido van Rossum 多次表达过：Python 不需要强制访问控制，因为"我们都是自愿的成年人"。如果你故意要访问一个标记为内部的属性，Python 信任你知道自己在做什么。这种哲学反映在数据模型上，就是没有任何"私有"机制——单下划线是约定的信号，不是强制的锁。

### 4.6 `__all__` 的运作原理与导入系统的协作

**`__all__` 是一个普通模块变量**

`__all__` 在本质上就是一个普通的模块级列表变量，没有任何语言层面的"特殊类型"。它之所以能影响 `from module import *` 的行为，是因为 import 机制在执行星号导入时，会主动去查模块的 `__all__` 属性。

```python
# __all__ 就是一个 list，可以随意查看和修改
# module_a.py
__all__ = ["func_a", "FuncB"]

def func_a(): pass
class FuncB: pass
def _internal(): pass
```

```python
import module_a
print(module_a.__all__)   # 输出：['func_a', 'FuncB']
print(type(module_a.__all__))   # 输出：<class 'list'>
```

`__all__` 就是一个 list 对象，你也可以运行时修改它（虽然基本没人这么做）。

**import * 的完整决策流程**

当解释器执行 `from module import *` 时，决策流程如下：

1. 导入目标模块（如果尚未导入）。
2. 检查模块是否有 `__all__` 属性。
   - 有：取 `__all__` 的值作为"待导入名字列表"。
   - 没有：取模块 `__dict__` 中所有不以 `_` 开头的名字。
3. 对列表中的每个名字，用 `getattr(module, name)` 取到对象。
4. 把 `(name, object)` 绑定到当前命名空间（`globals()`）。

关键在第 2 步：`__all__` 是"显式白名单"，覆盖下划线过滤；没有 `__all__` 则退化为"下划线过滤"。两者的优先级是 `__all__` > 下划线过滤。

**为什么 `__all__` 设计成 list 而非 set/tuple**

`__all__` 约定为 list 主要是为了文档可读性——列表有明确的顺序，读 `__all__ = ["A", "B", "C"]` 能直观看到公开 API 的清单。技术上 tuple 也能用（import 机制只是遍历它），但社区约定用 list。有些 lint 工具会检查 `__all__` 必须是 list 且名字按字母排序。

**`__all__` 不影响显式导入**

```python
# 假设 module_a 的 __all__ = ["func_a"]
from module_a import func_b   # 即使 func_b 不在 __all__ 里，也能显式导入
```

`__all__` 只影响 `import *`，不影响 `from module import name` 的显式导入。这再次体现了 Python 的哲学：约定和机制负责"默认行为"，显式操作则尊重用户的明确意图。

### 4.7 占位变量 `_` 在交互环境的特殊实现

**脚本中 `_` 是普通变量**

在一个 `.py` 脚本文件里，单个 `_` 就是一个普通变量名，没有任何特殊行为。它会被赋值、可以被读取、可以被覆盖，和 `x`、`tmp` 没有本质区别。

```python
# script.py
_ = 10
print(_)   # 输出：10

for _ in range(3):
    pass
print(_)   # 输出：2   —— 循环结束后 _ 的值是 2（最后一次的循环变量）
```

**交互式 shell 中 `_` 是 sys.displayhook 维护的**

在 Python 交互式解释器（REPL）中，`_` 是一个特殊变量，自动绑定到上一次表达式的求值结果。这个行为由 `sys.displayhook` 实现：

```python
# REPL 行为
>>> 1 + 1
2
>>> _
2
>>> "hello"
'hello'
>>> _
'hello'
```

`sys.displayhook` 的默认实现大致如下：

```python
# 伪代码：sys.displayhook 的默认逻辑
def displayhook(value):
    if value is None:
        return
    builtins._ = value          # 把结果存到 builtins._
    repr_text = repr(value)
    print(repr_text)            # 打印 repr
```

`_` 特殊行为的本质是：REPL 每次求值一个表达式后，`sys.displayhook` 把结果存到 `builtins._`。这样下一次你输入 `_` 就能取到上次的结果。这个机制只存在于交互式环境，脚本文件中没有 `sys.displayhook` 的自动调用，所以 `_` 就是普通变量。

**gettext 的 `_()` 是另一回事**

国际化库 gettext 约定用 `_()` 作为翻译函数的别名：

```python
import gettext
_ = gettext.gettext

print(_("Hello, world!"))   # 如果有中文翻译，输出中文
```

这里的 `_` 是一个函数引用，和"占位变量"完全无关。之所以用单个 `_`，纯粹是为了短——国际化文本里 `_()` 会大量出现，短名字让代码不那么啰嗦。这种用法在 Django、Flask 等 Web 框架的国际化代码里非常常见。

## 5. 总结

### 5.1 本文内容要点

- **单下划线前缀 `_name` 是 Python 的"软私有"约定**：标记"内部使用"，但解释器不强制，外部仍可直接访问。它是开发者之间的命名约定，而非访问控制机制。
- **类内部用 `_name` 标记实现细节**：内部状态、辅助方法、缓存等，外部不应依赖，随时可变。公开 API 不加 `_`，通过 `@property` 等受控暴露。
- **模块级用 `_name` 标记内部辅助函数**：`from module import *` 默认不导入以 `_` 开头的名字，这是单下划线唯一有运行时效果的场景。
- **`__all__` 是显式白名单**，优先级高于下划线过滤。有 `__all__` 时，星号导入只导入 `__all__` 列表中的名字（无论是否带 `_`）；无 `__all__` 时退化为下划线过滤。
- **尾部单下划线 `name_` 用于避开关键字冲突**：如 `class_`、`type_`，不是"私有"标记，纯粹是命名回避手段。
- **单个下划线 `_` 用作占位变量**：解包忽略、循环占位等语境；在交互式 shell 中由 `sys.displayhook` 维护为"上次结果"。
- **工具链识别 `_` 前缀**：`help()`/`pydoc`/Sphinx 默认隐藏，Pylint 的 `protected-access` 报警告，IDE 补全折叠——这些是工具遵循约定，非语言强制。
- **单下划线 vs 双下划线**：单下划线不改名、不拦截，纯约定；双下划线触发 name mangling（编译期改写为 `_ClassName__name`），原名访问不到但改写名可访问，主要用于避免子类属性冲突。
- **Python 的 consenting adults 哲学**：不做真正的强制访问控制，信任开发者，用约定和文档传达"什么是内部"，用工具辅助提醒，而非用编译器锁死。

### 5.2 读完本文你应能掌握

- 能正确判断何时给属性/方法加单下划线前缀，何时保持公开，并说明"这是实现细节"与"这是稳定 API"的区分依据。
- 能解释为什么 `obj._x` 和 `obj.x` 在解释器层面没有本质区别（属性查找、字节码、`__dict__` 存储均一致），单下划线纯粹是命名约定。
- 能说明 `from module import *` 在有/无 `__all__` 时分别如何过滤名字（有 `__all__` 用白名单，无 `__all__` 用下划线过滤），并知道 `__all__` 优先级高于下划线。
- 能区分单下划线（不改名、不拦截）与双下划线（编译期 name mangling 改写为 `_ClassName__name`）的本质机制差异，并知道两者各自的适用场景。
- 能在代码中正确使用尾部下划线 `name_` 避开关键字冲突，以及单个 `_` 作为占位变量，并说明它们与前缀单下划线含义的不同。
- 能在团队协作和库的版本演进中，利用单下划线约定划定"稳定接口"与"可变实现"的边界，让外部代码只依赖公开 API，内部重构不影响调用方。
- 能在 Pylint `protected-access` 警告、IDE 补全行为、文档工具隐藏等场景中，判断是否需要抑制/配置，还是应该改为使用公开 API。
- 能阅读 `dis` 反汇编输出，确认单下划线属性访问与普通属性访问的字节码一致（只是 `LOAD_ATTR`/`STORE_ATTR` 的属性名字符串不同），从底层验证"单下划线无运行时机制"。
