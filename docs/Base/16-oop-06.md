## 1. 介绍

### 1.1 什么是 classmethod

在 Python 的面向对象编程中，类体内定义的函数默认是"实例方法"——它的第一个参数被自动绑定为调用该方法的实例（习惯上命名为 `self`）。但很多时候，我们需要一种"操作类本身、而非操作某个实例"的方法：它要读写类属性、统计本类创建过多少实例、或者作为"替代构造器"从别的数据形态构造出本类的对象。这就是 `classmethod`（类方法）的用途。

`classmethod` 是一个内置装饰器。把它放在一个函数定义上方，这个函数就不再是普通实例方法，而变成"类方法"。类方法最显著的特征是：**它的第一个参数指向类本身，而不是实例**，习惯上命名为 `cls`。

```python
class User:
    count = 0  # 类属性

    @classmethod
    def show_count(cls):
        # cls 是 User 这个类（不是某个实例）
        print(f"当前类：{cls.__name__}，已创建 {cls.count} 个实例")
```

无论你用 `User.show_count()`（通过类调用）还是 `user.show_count()`（通过实例调用），传入的 `cls` 都是 `User` 类本身。这一点和实例方法完全不同——实例方法通过实例调用时 `self` 是该实例，通过类调用时则根本不会自动绑定（需手动传 `self`）。

**一句话区分三种方法**：

| 方法类型 | 装饰器 | 第一参数 | 绑定对象 |
|---------|--------|---------|---------|
| 实例方法 | （无） | `self` | 实例 |
| 类方法 | `@classmethod` | `cls` | 类 |
| 静态方法 | `@staticmethod` | 无自动绑定 | 不绑定（普通函数挂在类命名空间） |

类方法处在"实例方法"和"静态方法"之间：它像静态方法一样不依赖某个具体实例，但又能像实例方法一样拿到"调用者"——只不过这个调用者是**类**。

### 1.2 基本语法与最小用法

类方法的最小写法只需两步：在函数上方写 `@classmethod`，把第一个参数命名为 `cls`（名字只是约定，但强烈建议遵守，Python 会把类自动传给第一个位置参数，无论你叫它什么）。

```python
class Printer:
    prefix = "[INFO]"

    @classmethod
    def banner(cls, message):
        # cls.prefix 访问的是类属性
        return f"{cls.prefix} {message}"

# 通过类调用（最常见）
print(Printer.banner("服务已启动"))
# 输出：[INFO] 服务已启动

# 通过实例调用也可以，cls 仍是类
p = Printer()
print(p.banner("通过实例调用"))
# 输出：[INFO] 通过实例调用
```

这段代码体现了类方法的三条基本规则：

1. **`cls` 指向类**：无论是 `Printer.banner(...)` 还是 `p.banner(...)`，`cls` 都是 `Printer`，不是 `p`。
2. **能访问类属性**：`cls.prefix` 等价于 `Printer.prefix`，在类方法里通过 `cls.` 前缀操作类级状态。
3. **调用方式灵活**：类调用 `ClassName.method()` 是主推写法；实例调用 `obj.method()` 也合法，但语义上不如类调用清晰。

`@classmethod` 不是必须紧贴函数名上方——它和 `@staticmethod`、`@property` 等装饰器可以叠加，但叠加顺序要符合语义（例如 `@classmethod` 与 `@property` 叠加可造出"类属性 property"，这是较进阶的用法，后文会涉及）。最基本的用法就是单一 `@classmethod` 装饰一个普通函数。

## 2. 核心内容

### 2.1 第一个参数 cls：指向类而非实例

类方法与实例方法最本质的差异就落在第一参数上。实例方法的第一个参数 `self` 在调用时被绑定为**调用该方法的实例对象**；类方法的第一个参数 `cls` 则被绑定为**调用该方法的类对象**。这个差异决定了两者能访问什么、适合做什么。

```python
class Counter:
    total = 0  # 类属性：所有实例共享

    def __init__(self):
        Counter.total += 1      # 每创建一个实例，类属性 +1
        self.id = Counter.total  # 实例属性：自己的编号

    @classmethod
    def report(cls):
        # cls 是类，能访问类属性 cls.total
        print(f"[{cls.__name__}] 已创建 {cls.total} 个实例")
        # 这里没有 self，访问不到某个具体实例的 id

    def show_self(self):
        # self 是实例，能访问实例属性 self.id
        print(f"我是第 {self.id} 个实例")

c1 = Counter()
c2 = Counter()
Counter.report()
# 输出：[Counter] 已创建 2 个实例
c1.show_self()
# 输出：我是第 1 个实例
```

从这个例子可以直观看到：`report` 里拿到的 `cls` 是 `Counter`，能读 `cls.total`；但它没有 `self`，所以读不到 `c1.id` 这种实例属性。反过来，`show_self` 里有 `self`，能读实例属性；但它若想访问类属性也可以（通过 `Counter.total` 或 `self.total` 间接读，但通常类属性由类方法来管理更清晰）。

**`cls` 是类本身，不是字符串名字**。`cls.__name__` 才是类名字符串，`cls` 是那个类对象，可以用来实例化（`obj = cls(...)`）、访问类属性（`cls.attr`）、调用其它类方法（`cls.other_method()`），甚至传给别的函数当参数。

**类方法里能否访问实例属性**：不能直接访问。类方法不接收 `self`，没有具体实例可以 `self.xxx`。如果你的逻辑确实需要某个实例的数据，那它应该是实例方法，不是类方法。类方法只适合操作"整类共享"的状态。

### 2.2 两种调用方式：ClassName.method() 与 obj.method()

类方法有两种合法调用方式，且两种方式下 `cls` 的取值规则略有不同，这是初学者容易混淆的地方。

**通过类调用**：`ClassName.method(args)`。这是最常见、最推荐的写法，`cls` 就是 `ClassName`。

**通过实例调用**：`obj.method(args)`。这也合法，`cls` 默认取 `type(obj)`（即实例所属的类）。关键在于：**即使你通过一个子类实例调用父类里定义的类方法，`cls` 也会是子类**，而不是定义该方法的父类。这条规则是多态工厂能成立的基础，将在 2.5 和原理章详述。

```python
class Shape:
    @classmethod
    def make(cls, kind):
        # cls 是实际调用的类
        print(f"在 {cls.__name__} 上调用 make，kind={kind}")

class Circle(Shape):
    pass

# 通过类调用
Shape.make("default")
# 输出：在 Shape 上调用 make，kind=default

# 通过子类调用：cls 是子类 Circle
Circle.make("big")
# 输出：在 Circle 上调用 make，kind=big

# 通过实例调用：cls 仍是实例的类
c = Circle()
c.make("from_instance")
# 输出：在 Circle 上调用 make，kind=from_instance
```

注意 `Circle.make("big")` 这一行：`make` 定义在父类 `Shape` 里，但用子类 `Circle` 调用时，`cls` 是 `Circle`。这就是"类方法被子类继承，且 `cls` 指向实际调用的子类"的体现。

**为什么不推荐用实例调用类方法**：功能上没问题，但语义上模糊——读代码的人看到 `c.make(...)` 会以为这依赖实例 `c` 的某些状态，实际上 `c` 只是被用来推断类。写 `Circle.make(...)` 或 `type(c).make(...)` 意图更明确。唯一例外是在父类的实例方法内部调用本类类方法时，用 `self.make(...)` 比写死类名更利于子类多态（后文会展开）。

### 2.3 操作类级状态：类属性、计数器

类方法最常见的工程用途之一是管理类级状态——即写在类体里、所有实例共享的类属性。典型场景：实例计数器、全局开关、缓存。

把类属性的读写集中到类方法里，有两个好处：第一，调用方不需要知道"这个属性叫什么名字"，只需调方法；第二，将来要给计数逻辑加锁、加日志、改实现，只改一处。

```python
class User:
    _count = 0          # 类属性：已创建的实例数
    _all_ids = []       # 类属性：所有实例 id

    def __init__(self, name):
        self.name = name
        # 通过类方法登记，而不是在 __init__ 里直接改类属性
        User._register(self)

    @classmethod
    def _register(cls, instance):
        cls._count += 1
        instance.uid = cls._count          # 给实例打上编号
        cls._all_ids.append(instance.uid)

    @classmethod
    def count(cls):
        return cls._count

    @classmethod
    def all_ids(cls):
        return list(cls._all_ids)

u1 = User("张三")
u2 = User("李四")
u3 = User("王五")

print(User.count())
# 输出：3
print(User.all_ids())
# 输出：[1, 2, 3]
```

这里 `_register`、`count`、`all_ids` 都是类方法，共同维护 `_count` 和 `_all_ids` 这两个类属性。外部调用方只接触 `User.count()` 这样的接口，至于数据存在哪个类属性里、用什么数据结构，是类的内部实现细节。

**为什么用 `_` 前缀**：`_count`、`_all_ids` 用下划线开头表示"内部使用，外部请用类方法访问而非直接碰这些属性"。这是 Python 社区的约定（单下划线 = 受保护的内部成员）。

**类方法里修改类属性 vs 实例方法里修改类属性**：两者都能改，但语义不同。实例方法里写 `cls_name.attr = x` 或 `self.__class__.attr = x` 也能改类属性，但这把"管理类级状态"的逻辑散落到了各处；统一收口到类方法里更清晰，也便于子类重写类方法来改变计数策略。

### 2.4 最典型用途：替代构造器工厂方法 from_xxx

Python 一个类只能有一个 `__init__` 作为主构造器。但很多时候我们希望从不同数据形态构造对象：从字典、从 JSON 字符串、从数据库行、从另一个对象转换……每种都给出一个清晰的"工厂方法"，比让 `__init__` 通过一堆 flag 参数勉强应付要好得多。类方法天生适合做这件事——它能拿到 `cls`，用 `cls(...)` 创建本类实例，且 `cls` 在子类调用时自动指向子类，工厂可以被继承。

社区约定这类工厂方法命名为 `from_xxx`：`from_dict`、`from_json`、`from_string`、`from_tuple` 等。Python 标准库就有大量先例：`dict.fromkeys(iterable, value)` 从可迭代对象构造字典、`datetime.fromisoformat(s)` 从 ISO 格式字符串构造日期、`int.from_bytes(b, byteorder)` 从字节构造整数。

**标准库示例**：

```python
# dict.fromkeys：用一组 key 构造字典，所有 key 共享同一个默认 value
d = dict.fromkeys(["a", "b", "c"], 0)
print(d)
# 输出：{'a': 0, 'b': 0, 'c': 0}

from datetime import datetime

# datetime.fromisoformat：从 ISO 8601 字符串构造
dt = datetime.fromisoformat("2026-07-23T14:30:00")
print(dt)
# 输出：2026-07-23 14:30:00
```

这两个方法的共同点：它们都返回一个本类的新实例，且是类方法（不是静态方法），因为内部要用 `cls(...)` 来实例化——这样子类调用 `SubClass.fromisoformat(...)` 时得到的是子类实例。

**自定义工厂：User.from_dict**

下面用 `User.from_dict` 演示一个贴近真实业务的替代构造器：从 API 返回的字典构造 `User` 实例，并做字段校验和默认值填充。

```python
class User:
    def __init__(self, name, age, email=None):
        self.name = name
        self.age = age
        self.email = email

    @classmethod
    def from_dict(cls, data):
        # cls(...) 会调用 __init__
        name = data["name"]
        age = int(data.get("age", 0))
        email = data.get("email")
        return cls(name, age, email)

    @classmethod
    def from_api_json(cls, json_str):
        import json
        data = json.loads(json_str)
        # 复用 from_dict，避免逻辑重复
        return cls.from_dict(data)

    def __repr__(self):
        return f"User(name={self.name!r}, age={self.age}, email={self.email!r})"

# 主构造器：直接 new
u1 = User("张三", 30)
print(u1)
# 输出：User(name='张三', age=30, email=None)

# 替代构造器：从字典构造
u2 = User.from_dict({"name": "李四", "age": 25, "email": "li@example.com"})
print(u2)
# 输出：User(name='李四', age=25, email='li@example.com')

# 从 JSON 字符串构造（复用 from_dict）
u3 = User.from_api_json('{"name": "王五", "age": 28}')
print(u3)
# 输出：User(name='王五', age=28, email=None)
```

`from_api_json` 内部调用 `cls.from_dict(data)` 而不是 `User.from_dict(data)`，这一点很重要：如果将来有个 `AdminUser(User)` 子类，`AdminUser.from_api_json(...)` 会得到 `AdminUser` 实例（因为 `cls` 是 `AdminUser`），而不是被写死的 `User`。这就是 `cls` 的多态价值。

**为什么工厂方法定义成 `@classmethod` 而不是 `@staticmethod`**：静态方法拿不到 `cls`，只能写死 `User(...)`，子类调用时得到的永远是 `User` 实例，丢失了多态。类方法用 `cls(...)` 则自动适配子类。这是类方法相对于静态方法在工厂场景下的决定性优势。

**多个替代构造器的组织建议**：一个类可以有好几个 `from_xxx`，每个对应一种输入来源。不要试图让 `__init__` 通过 `if source == 'dict': ... elif source == 'json': ...` 来包揽一切——`__init__` 应只负责"从最基本的字段组装对象"，各种"从别的形态转换"交给 `from_xxx` 工厂。

### 2.5 子类继承与多态工厂：cls 指向实际子类

类方法能被子类继承，这是它区别于静态方法的另一关键特性。更关键的是：子类调用继承来的类方法时，`cls` 指向子类而非父类。这使得"父类定义工厂、子类自动复用工厂且产物是子类实例"成为可能——这就是多态工厂。

```python
class Animal:
    def __init__(self, name):
        self.name = name

    @classmethod
    def create(cls, name):
        # cls(...) 在子类调用时实例化的是子类
        return cls(name)

    def speak(self):
        return f"{self.name} 发出声音"

class Dog(Animal):
    def speak(self):
        return f"{self.name} 汪汪叫"

class Cat(Animal):
    def speak(self):
        return f"{self.name} 喵喵叫"

# 父类工厂造父类实例
a = Animal.create("某动物")
print(a.speak())
# 输出：某动物 发出声音

# 子类用继承来的工厂造子类实例
d = Dog.create("旺财")
print(d.speak())
# 输出：旺财 汪汪叫

c = Cat.create("咪咪")
print(c.speak())
# 输出：咪咪 喵喵叫

print(type(d).__name__, type(c).__name__)
# 输出：Dog Cat
```

`Dog.create` 并没有在 `Dog` 里定义，它是从 `Animal` 继承来的。但调用 `Dog.create("旺财")` 时，`cls` 是 `Dog`，所以 `cls("旺财")` 造出的是 `Dog` 实例。如果 `create` 是静态方法、内部写死 `Animal(name)`，那 `Dog.create(...)` 造出的会是 `Animal` 实例，`speak()` 也不会调用 `Dog` 版本——多态就断了。

**用工厂方法做"根据字符串选择子类"的注册分发**：这是多态工厂的典型落地场景——你有一组子类，根据配置或输入的字符串挑一个来实例化。

```python
class Animal:
    _registry = {}  # 类属性：名字 -> 子类

    def __init__(self, name):
        self.name = name

    @classmethod
    def register_subclass(cls, key):
        # 装饰器：把子类按 key 登记到父类的 _registry
        def deco(subcls):
            cls._registry[key] = subcls
            return subcls
        return deco

    @classmethod
    def create_by_kind(cls, kind, name):
        # 多态工厂：根据 kind 找到对应子类，再用 cls(...) 实例化
        # 注意这里用 _registry[kind] 而不是 cls(...)，因为目标类是查表得到的
        target = cls._registry.get(kind, cls)
        return target(name)

    def speak(self):
        return f"{self.name} 发出声音"

@Animal.register_subclass("dog")
class Dog(Animal):
    def speak(self):
        return f"{self.name} 汪汪叫"

@Animal.register_subclass("cat")
class Cat(Animal):
    def speak(self):
        return f"{self.name} 喵喵叫"

# 根据外部字符串选择子类
for kind, name in [("dog", "旺财"), ("cat", "咪咪"), ("bird", "小鸟")]:
    pet = Animal.create_by_kind(kind, name)
    print(f"{kind:4} -> {type(pet).__name__:7} | {pet.speak()}")
# 输出：
# dog  -> Dog     | 旺财 汪汪叫
# cat  -> Cat     | 咪咪 喵喵叫
# bird -> Animal  | 小鸟 发出声音
```

这里出现了两类 `cls` 用法：`register_subclass` 用 `cls._registry` 做注册表（子类若调用会注册到子类的 `_registry`，但通常我们在父类上调用）；`create_by_kind` 用查表结果 `target(name)` 实例化。注意 `create_by_kind` 里实例化用的是 `target`（查表得到的类），不是 `cls`——因为我们的目的就是"根据 kind 选一个具体的子类",`cls` 只是入口。

**多态工厂相对直接 if/else 的好处**：新增一种动物只需 `@Animal.register_subclass("pig")` 注册一个 `Pig` 类，不用改 `create_by_kind` 里的分派逻辑。这遵循了开闭原则——对扩展开放，对修改封闭。

### 2.6 cls 的更多用法：实例化、调用其它类方法、作为参数传递

`cls` 既然是类对象，凡是对类能做的事都能对 `cls` 做。除了最常用的 `cls(...)` 实例化和 `cls.attr` 访问类属性，还有几类常见操作。

**调用其它类方法**：类方法内部可以用 `cls.other_method()` 调用同类另一个类方法，且同样具备多态——如果子类重写了 `other_method`，`cls.other_method()` 会调用子类版本。

```python
class Config:
    @classmethod
    def defaults(cls):
        return {"timeout": 30, "retries": 3}

    @classmethod
    def load(cls, overrides=None):
        # 复用 defaults()，子类重写 defaults() 则此处自动用子类版本
        cfg = cls.defaults()
        if overrides:
            cfg.update(overrides)
        return cfg

class StrictConfig(Config):
    @classmethod
    def defaults(cls):
        return {"timeout": 5, "retries": 1}

print(Config.load({"timeout": 60}))
# 输出：{'timeout': 60, 'retries': 3}

print(StrictConfig.load({"timeout": 60}))
# 输出：{'timeout': 60, 'retries': 1}
```

`StrictConfig.load` 继承自 `Config`，内部 `cls.defaults()` 因为 `cls` 是 `StrictConfig` 而调用了重写后的 `defaults`，拿到 `retries=1`。这就是类方法之间通过 `cls` 互相调用带来的多态联动——在实例方法里用 `self.other()` 调用别的实例方法也是同样的道理。

**把 cls 当参数传递**：`cls` 是个普通对象，可以传给别的函数或注册到某个映射里。

```python
class Handler:
    @classmethod
    def register(cls):
        # 把自己（类）登记到某个全局表里
        _HANDLERS[cls.__name__] = cls

_HANDLERS = {}

class LoginHandler(Handler):
    @classmethod
    def handle(cls, req):
        return f"登录处理：{req}"

LoginHandler.register()
print(_HANDLERS)
# 输出：{'LoginHandler': <class '...LoginHandler'>}
print(_HANDLERS["LoginHandler"].handle("请求体"))
# 输出：登录处理：请求体
```

**用 cls 做类型判断**：`isinstance(obj, cls)` 在类方法里也合法，当你想检查某个对象是不是"本类或子类"的实例时有用。

### 2.7 classmethod 与实例方法、静态方法的区别

把三种方法放在一起对照，能更清晰地理解每种方法该用在哪。

```python
class Temperature:
    absolute_zero = -273.15  # 类属性

    def __init__(self, celsius):
        self.celsius = celsius

    # 实例方法：操作某个具体温度对象
    def to_fahrenheit(self):
        return self.celsius * 9 / 5 + 32

    # 类方法：操作类本身，这里用类属性做边界校验
    @classmethod
    def safe_create(cls, celsius):
        if celsius < cls.absolute_zero:
            raise ValueError(f"温度不能低于绝对零度 {cls.absolute_zero}")
        return cls(celsius)

    # 静态方法：和类有关但不依赖类状态也不依赖实例状态
    @staticmethod
    def kelvin_to_celsius(k):
        return k - 273.15

# 实例方法必须通过实例调
t = Temperature(25)
print(t.to_fahrenheit())
# 输出：77.0

# 类方法通过类调（也可实例调，不推荐）
ok = Temperature.safe_create(20)
print(ok.celsius)
# 输出：20

try:
    Temperature.safe_create(-300)
except ValueError as e:
    print(e)
# 输出：温度不能低于绝对零度 -273.15

# 静态方法：就是个挂在类命名空间里的普通函数
print(Temperature.kelvin_to_celsius(300))
# 输出：26.85
```

**判断该用哪种方法的决策表**：

| 问题 | 答案是 yes 用 |
|------|--------------|
| 需要访问/修改某个具体实例的数据？ | 实例方法（`self`） |
| 需要访问/修改类级状态，或作为工厂 `cls(...)` 造本类对象？ | 类方法（`@classmethod`、`cls`） |
| 既不需要实例状态也不需要类状态，只是逻辑上属于这个类？ | 静态方法（`@staticmethod`） |

**一条经验法则**：当你犹豫"这个方法要不要用 `@staticmethod`"时，先问自己"它需要 `cls` 吗"——如果将来可能想要多态（子类调用时行为不同），用 `@classmethod` 总是更安全的选择。静态方法没法多态，因为它拿不到 `cls`。

### 2.8 类方法作为 setter 改类属性

类方法不只能读类属性，也能写。把类属性的修改封装在类方法里，可以在修改时做校验、日志、联动更新。

```python
class AppConfig:
    _debug = False      # 类属性
    _max_conn = 10      # 类属性

    @classmethod
    def get_debug(cls):
        return cls._debug

    @classmethod
    def set_debug(cls, value):
        if not isinstance(value, bool):
            raise TypeError("debug 必须是 bool")
        old = cls._debug
        cls._debug = value
        print(f"debug: {old} -> {value}")  # 联动日志

    @classmethod
    def set_max_conn(cls, value):
        if value <= 0:
            raise ValueError("max_conn 必须为正")
        cls._max_conn = value

AppConfig.set_debug(True)
# 输出：debug: False -> True
print(AppConfig.get_debug())
# 输出：True

try:
    AppConfig.set_max_conn(0)
except ValueError as e:
    print(e)
# 输出：max_conn 必须为正
```

这种"用类方法给类属性当 setter"的模式，等于在类级别复刻了实例属性的 getter/setter 封装。如果属性较多且希望更优雅，可以结合 `@classmethod` + `@property`（见 2.9）。

### 2.9 进阶：classmethod 与 property 叠加（类属性 property）

普通 `@property` 是给**实例属性**做访问控制。如果想在类级别做同样的事——访问 `ClassName.attr` 时触发自定义 getter、赋值时触发校验——需要把 `@property` 和 `@classmethod` 叠加。写法略绕：要把 `@property` 装在一个 `@classmethod` 返回的内层对象外。

社区惯用写法（一个 `classproperty` 装饰器）：

```python
class classproperty:
    """简易类属性 property 装饰器"""
    def __init__(self, fget):
        self.fget = fget

    def __get__(self, obj, owner=None):
        # owner 是访问该属性时所在的类
        return self.fget(owner)

class Circle:
    pi = 3.14159
    _all_radii = []

    @classmethod
    def add_radius(cls, r):
        cls._all_radii.append(r)

    @classproperty
    def max_radius(cls):
        return max(cls._all_radii) if cls._all_radii else 0

Circle.add_radius(3)
Circle.add_radius(7)
print(Circle.max_radius)
# 输出：7
```

**注意**：这不是内置功能，是自实现的描述符。且这种 `classproperty` 默认只支持读，不支持 `@x.setter`（写需要再实现 `__set__`，但描述符在类级别赋值的行为和实例级别不同，常见的写法是只读）。Python 3.9 之前没有官方的"类属性 property"，3.11 也仍需自行实现。日常用类方法（`get_xxx`/`set_xxx`）作为替代更稳妥，仅在追求"像属性一样访问 `Cls.attr`"的 API 美感时才上 `classproperty`。

### 2.10 classmethod 与抽象方法结合（abc）

在抽象基类（`abc.ABC`）里，`@classmethod` 可以和 `@abstractmethod` 叠加，强制子类实现某个类方法。

```python
from abc import ABC, abstractmethod

class Storage(ABC):
    @classmethod
    @abstractmethod
    def from_config(cls, config):
        """子类必须实现：从配置对象构造一个存储实例"""
        ...

class FileStorage(Storage):
    @classmethod
    def from_config(cls, config):
        return cls(config["path"])

    def __init__(self, path):
        self.path = path

s = FileStorage.from_config({"path": "/tmp/data"})
print(s.path)
# 输出：/tmp/data
```

**装饰器顺序**：`@classmethod` 在外、`@abstractmethod` 在内。顺序反了会导致抽象方法检测失效。这也是 `@classmethod` 与其它装饰器叠加时的通用规则：`@classmethod` 通常放最外层，保证拿到的是"被它处理过的类方法对象"。

### 2.11 调用父类类方法：super() 与 cls

在类方法内部调用父类的类方法，用 `super()`，但 `super()` 的第一个参数要传 `cls`（当前类），而不是像实例方法里那样省略。这是因为类方法里没有 `self`，`super()` 需要明确告诉它"从哪个类的父类开始找"以及"绑定到哪个类"。

```python
class Base:
    @classmethod
    def greet(cls):
        return f"Base.greet on {cls.__name__}"

class Mid(Base):
    @classmethod
    def greet(cls):
        # 调用父类类方法，把 cls 传下去
        parent = super().greet()
        return f"Mid.greet before -> {parent} -> Mid.greet after"

class Leaf(Mid):
    pass

print(Base.greet())
# 输出：Base.greet on Base
print(Mid.greet())
# 输出：Mid.greet before -> Base.greet on Mid -> Mid.greet after
print(Leaf.greet())
# 输出：Mid.greet before -> Base.greet on Leaf -> Mid.greet after
```

注意 `Leaf.greet()` 的输出：`Leaf` 自己没重写 `greet`，调用的是继承的 `Mid.greet`，而 `Mid.greet` 里的 `super().greet()` 走到 `Base.greet`，此时 `cls` 仍然是 `Leaf`（输出 "Base.greet on Leaf"）。`super()` 改变的是"方法查找的起点"，不改变 `cls` 的绑定——`cls` 始终是最初发起调用的那个类。这是 `super()` 与 `cls` 协作的关键点。

在 Python 3 里，类方法内 `super()` 可以不写参数（`super()` 零参形式），解释器会通过 `__class__` 单元自动推断当前类。但显式写 `super(MyClass, cls)` 在某些元编程场景更可控。日常写零参 `super()` 即可。

## 3. 最佳实践

**类方法的命名约定**

工厂方法统一用 `from_xxx` 前缀（`from_dict`、`from_json`、`from_string`），读起来一眼就知道是"从某种形态构造本类"。访问类属性的方法用 `get_xxx`/`set_xxx` 或直接 `xxx` 作为类方法名。内部辅助类方法用 `_` 前缀（如 `_register`）。保持整套类的命名风格一致，比纠结具体名字更重要。

**优先用类调用而非实例调用**

```python
# 推荐
Counter.create("x")
User.from_dict(data)

# 不推荐（除非在实例方法内部利用多态）
counter.create("x")   # c 看起来像参与了调用，实际只用到了 type(c)
user.from_dict(data)
```

实例调用类方法功能上没错，但读代码时容易让人误以为方法依赖该实例的状态。除非你在父类实例方法内部调本类类方法、且希望子类多态，否则直接写类名调用。

**在实例方法内部谨慎使用 cls 替代类名**

实例方法内部如果要调用类方法，有两种写法：

```python
class Item:
    @classmethod
    def compute_tax(cls, price):
        return price * 0.1

    def total_with_tax(self):
        # 写法一：用 type(self)
        return self.price + type(self).compute_tax(self.price)
        # 写法二：直接写类名
        # return self.price + Item.compute_tax(self.price)
```

写法一（`type(self).compute_tax(...)`）利于子类多态：若 `LuxuryItem(Item)` 重写了 `compute_tax`，`type(self)` 是 `LuxuryItem`，会调用子类版本。写法二写死了 `Item`，丧失多态。**当你希望子类能覆盖行为时用 `type(self)`；当你明确要调用本类、不允许子类覆盖时写死类名**。不过更地道的做法是在实例方法里直接 `self.compute_tax(self.price)`——因为类方法也能通过 `self` 调用，`cls` 会被绑定为 `type(self)`，效果和 `type(self).compute_tax(...)` 一样且更简洁。

**别用类方法去访问实例属性**

```python
# 错误：类方法里想用 self
@classmethod
def get_name(cls):
    return cls.self.name  # AttributeError，cls 没有 self
```

类方法没有 `self`，访问不到实例属性。如果你的方法逻辑需要实例数据，它就应该是实例方法。把"需要实例"的逻辑硬塞进类方法，往往是因为想把它当工厂但又想顺手读点东西——拆成两个方法更干净：工厂方法只负责构造，构造完用实例方法去读。

**类属性的可变默认值陷阱**

```python
class Bad:
    items = []  # 所有实例共享同一个 list！

    @classmethod
    def add(cls, x):
        cls.items.append(x)  # 改的是类属性，影响所有实例
```

这在类方法里尤其危险，因为 `cls.items.append(x)` 看起来像"只改了类"，但如果子类也有自己的 `items`，`cls.items` 指向哪个 list 取决于 `cls` 是谁。如果想让每个子类有独立容器，需在子类里重新定义 `items = []`，或在类方法里用 `cls.__dict__` 检查并惰性初始化：

```python
class Good:
    @classmethod
    def items(cls):
        # 每个子类首次访问时在自己身上建一个独立 list
        key = "_items"
        if key not in cls.__dict__:
            setattr(cls, key, [])
        return getattr(cls, key)

    @classmethod
    def add(cls, x):
        cls.items().append(x)

class SubA(Good): pass
class SubB(Good): pass

SubA.add(1)
SubB.add(2)
print(SubA.items(), SubB.items())
# 输出：[1] [2]
```

**静态方法 vs 类方法的最终选择**

很多人在"这方法不依赖实例"时会无脑用 `@staticmethod`。更稳妥的默认是 `@classmethod`：它多了 `cls`，即使现在不用，将来想多态或改工厂时不用改签名。只有当方法"和这个类的类型本身无关、只是借类命名空间放个工具函数"时才用 `@staticmethod`（如 `Temperature.kelvin_to_celsius`）。记住：静态方法不可多态，类方法可多态。

## 4. 原理

### 4.1 classmethod 是描述符

要理解 `@classmethod` 为何"调用时自动把类绑给 `cls`"，需要先回到 Python 的属性访问机制。在 Python 中，类方法（`classmethod` 对象）本质上是一个**描述符（descriptor）**——实现了 `__get__` 方法的对象。当你写 `obj.method` 或 `Cls.method` 时，Python 不是简单地从字典里取值，而是会检查取到的对象是不是描述符，若是则调用它的 `__get__` 来生成最终绑定结果。

`@classmethod` 装饰一个函数后，得到的不是一个普通函数，而是一个 `classmethod` 类型的对象，它内部保存了原始函数。这个 `classmethod` 对象实现了描述符协议，其 `__get__` 的行为大致等价于：

```python
# 概念性伪代码，非真实源码
class classmethod:
    def __init__(self, fget):
        self.fget = fget

    def __get__(self, obj, cls=None):
        # cls 是属性访问时所在的类
        if cls is None:
            cls = type(obj)
        # 用 functools.partial 把类预填为第一个参数
        import functools
        return functools.partial(self.fget, cls)
```

也就是说，访问 `Cls.method` 或 `obj.method` 时，Python 调用 `classmethod.__get__(obj, cls)`，它返回一个已经把 `cls` 预填好的可调用对象——你再传参数调用它，实际等效于 `原始函数(cls, 你的参数...)`。这就是"`cls` 被自动绑定"的真相：不是函数本身有什么特殊，而是描述符在属性访问时帮你做了一次 `partial`。

**验证 classmethod 是描述符**：

```python
class C:
    @classmethod
    def m(cls):
        return cls

# 访问 C.m 触发 __get__，返回的是绑定后的可调用对象（非原始函数）
bound = C.m
print(type(bound).__name__)
# 输出：method  （在 CPython 中是 method 类型的绑定方法对象）

# 它已经预填了 cls，调用时不传 cls 即可
print(bound() is C)
# 输出：True

# classmethod 对象本身实现了 __get__
print(hasattr(type(C).__dict__["m"], "__get__"))
# 输出：True
```

### 4.2 __get__ 绑定时把类（而非实例）预填为第一参数 cls

对比一下普通函数（实例方法）和 `classmethod` 作为描述符的差异，就能看清"为什么 `self` 绑实例、`cls` 绑类"。

普通函数本身也是描述符——`function.__get__(obj, cls)` 在 `obj` 非 None 时返回一个绑定方法，把 `obj` 预填为第一个参数（即 `self`）。这就是实例方法 `self` 自动绑定的机制。

`classmethod` 的描述符行为与之对应但相反：它的 `__get__` **总是把 `cls`（类）预填为第一参数**，而不是 `obj`（实例）。

```python
class C:
    def instance_m(self):
        return self

    @classmethod
    def class_m(cls):
        return cls

c = C()

# 实例方法：function.__get__(c, C) 把 c 预填为 self
bound_self = c.instance_m
print(bound_self() is c)
# 输出：True

# 类方法：classmethod.__get__(c, C) 把 C 预填为 cls（注意不是 c）
bound_cls = c.class_m
print(bound_cls() is C)
# 输出：True
print(bound_cls() is c)
# 输出：False
```

关键就在 `classmethod.__get__` 的实现：它放弃了传入的 `obj`，只取 `cls` 作为预填参数。所以无论你通过实例还是类访问，预填的都是"类"。

**那 `cls` 的具体值从哪来**？`__get__` 的第二个参数 `cls` 是 Python 属性访问机制根据"访问发生的位置"提供的。当你写 `ClassName.method`，`cls` 就是 `ClassName`；当你写 `obj.method`，Python 先得到 `type(obj)` 作为 `cls` 再调 `__get__`。这就是为什么 2.2 里通过 `c.class_m()` 调用，`cls` 仍是 `type(c)` 而不是 `c`。

### 4.3 为何通过实例调用 cls 仍是类

把 4.2 的机制套到具体调用路径上，就完全解释了"通过实例调用类方法，`cls` 仍是类"这一现象。

```python
class Animal:
    @classmethod
    def who(cls):
        return cls

class Dog(Animal):
    pass

d = Dog()

# 路径一：Dog.who() -> 属性访问 Dog.who -> __get__(None, Dog) -> 预填 cls=Dog
print(Dog.who() is Dog)
# 输出：True

# 路径二：d.who() -> 属性访问 d.who -> __get__(d, type(d)=Dog) -> 预填 cls=Dog（丢弃 d）
print(d.who() is Dog)
# 输出：True
```

两条路径 `cls` 都是 `Dog`。路径二里 `__get__` 收到了实例 `d`，但 `classmethod` 的实现**忽略实例、只取类**，所以最终预填的还是 `Dog`。这与实例方法截然不同——实例方法的 `function.__get__(d, Dog)` 会预填 `d` 为 `self`。

这也解释了为什么"实例调用类方法"语义上有点误导：看起来是 `d` 在调，实际上 `d` 在这一步只贡献了它的类型，自身状态完全不参与。所以规范里推荐用 `ClassName.method()` 调用类方法——既然实例的状态根本不用，就不该用实例去调。

### 4.4 cls 在继承中指向实际子类的机制

2.5 里我们看到 `Dog.create(...)` 调用继承自 `Animal` 的类方法，`cls` 却是 `Dog`。这一条的底层机制是属性查找与 `__get__` 的 `cls` 取值规则。

当 Python 执行 `Dog.create("旺财")`：

1. 在 `Dog` 类的 `__mro__`（方法解析顺序）里查找 `create` 属性。`Dog` 自己没有，沿 MRO 找到父类 `Animal` 的 `create`——它是个 `classmethod` 对象。
2. 因为属性访问发生在 `Dog` 上（通过 `Dog.create`），Python 调用 `classmethod.__get__(None, Dog)`——注意第二个参数是**发起访问的类 `Dog`**，不是定义方法的 `Animal`。
3. `__get__` 用 `Dog` 预填 `cls`，返回绑定后的可调用对象。
4. 调用该对象（传入 `"旺财"`），等价于 `Animal.create(Dog, "旺财")`，`cls` 便是 `Dog`。

**验证：即便方法定义在父类，cls 来自发起访问的类**：

```python
class Animal:
    @classmethod
    def create(cls, name):
        return cls(name)

class Dog(Animal):
    pass

# create 定义在 Animal，但通过 Dog 访问，cls 是 Dog
d = Dog.create("旺财")
print(type(d) is Dog)
# 输出：True
print(d.__class__.__name__)
# 输出：Dog
```

这里最关键的点：`classmethod.__get__` 的 `cls` 参数由"属性访问发生的类"决定，**不是由"方法定义在哪个类"决定**。这是 Python 属性查找机制的一部分——`__get__` 的 owner 参数永远是发起访问的那个类。

再回到 2.5 多态工厂的例子：`Animal.create` 内部 `cls(name)` 造出的就是 `cls` 指向的类（`Dog`），所以 `Dog.create(...)` 得到 `Dog` 实例。如果 `create` 是静态方法，它内部只能写死 `Animal(name)`，那多态就断了——`cls` 的价值正在于此。

### 4.5 从 obj.__class__ 取类：实例调用时的类推断

通过实例调用类方法时，`classmethod.__get__` 收到的 `cls` 是 Python 根据 `obj` 推断出来的——具体取的是 `type(obj)`，在绝大多数情况下等价于 `obj.__class__`。

```python
class Base:
    @classmethod
    def reveal(cls):
        print(f"cls = {cls.__name__}")

class Sub(Base):
    pass

s = Sub()

# 通过实例调用：cls 来自 type(s)
s.reveal()
# 输出：cls = Sub

# 直接对比
print(type(s) is Sub, s.__class__ is Sub)
# 输出：True True
```

`type(obj)` 与 `obj.__class__` 通常一致，但在少数元编程场景会不同（例如用了 `__class__` 赋值或某些 C 加速类型）。CPython 的 `classmethod` 描述符在通过实例访问时用的是 `type(obj)`，等价于从实例的"真实类型"取类。这正是"子类实例调用父类定义的类方法、`cls` 仍是子类"的最后一块拼图：`type(子类实例)` = 子类。

**多态工厂完整追踪**：再看一眼 `Animal.create` 在子类上的整条链。

```python
class Animal:
    @classmethod
    def create(cls, name):
        # cls 是实际调用方类
        obj = cls(name)
        print(f"  create: cls={cls.__name__}, 造出 {type(obj).__name__}")
        return obj

class Dog(Animal):
    def __init__(self, name):
        self.name = name
        print(f"  Dog.__init__({name})")

# 通过 Dog.create：cls=Dog
Dog.create("旺财")
# 输出：
#   Dog.__init__(旺财)
#   create: cls=Dog, 造出 Dog

# 通过 Dog 实例调用：cls 仍来自 type(dog)=Dog
dog = Dog("旺财")
dog.create("另一只")
# 输出：
#   Dog.__init__(另一只)
#   create: cls=Dog, 造出 Dog
```

两种调用路径 `cls` 都是 `Dog`，验证了"从 `type(obj)` 取类"在实例调用场景下稳定指向真实子类。

### 4.6 function 描述符与 classmethod 描述符的对比

把两者并排放，差异一目了然：

| 维度 | function（实例方法） | classmethod |
|------|---------------------|-------------|
| 是否描述符 | 是，实现 `__get__` | 是，实现 `__get__` |
| `__get__(obj, cls)` 预填谁 | `obj`（实例） | `cls`（类） |
| `obj` 为 None 时（ClassName.method） | 返回未绑定函数，需手动传 self | 仍预填 `cls`，可直接调 |
| 绑定后第一参数 | `self`（实例） | `cls`（类） |
| 通过实例调用时绑定源 | 该实例本身 | `type(obj)` |
| 多态依赖 | `obj` 的实际类决定调哪个方法版本 | 发起访问的类决定 `cls` 与方法版本 |

最直观的对照代码：

```python
class C:
    def inst(self):
        return self, type(self).__name__

    @classmethod
    def klass(cls):
        return cls, cls.__name__

c = C()

# 实例方法：绑定 self=c
print(c.inst())
# 输出：(<C object>, 'C')

# 类方法：绑定 cls=C（忽略 c）
print(c.klass())
# 输出：(<class 'C'>, 'C')

# 通过类调用：
# 实例方法不预填，必须手动传 c
print(C.inst(c))
# 输出：(<C object>, 'C')

# 类方法已预填 cls=C
print(C.klass())
# 输出：(<class 'C'>, 'C')
```

注意 `C.inst()` 不传参会报错——普通函数通过类访问时 `function.__get__(None, C)` 返回的是未绑定函数（Python 3 里就是个普通函数），必须手动传 `self`。而 `C.klass()` 能直接调——`classmethod.__get__(None, C)` 总是预填 `cls`。这正是"类方法适合通过类调用、实例方法不适合"的底层原因。

### 4.7 classmethod 内部实现要点

CPython 里 `classmethod` 是一个 C 实现的类型（`PyClassMethod_Type`），其 `__get__` 逻辑大致是：

1. 取 `cls` 参数（若为 None 则取 `type(obj)`）。
2. 把内部保存的函数（`classmethod.__func__`）与 `cls` 绑定，生成一个 `method` 对象（绑定方法）。
3. 返回该 `method` 对象。

可以通过 `__func__` 看到底层原始函数：

```python
class C:
    @classmethod
    def m(cls, x):
        return cls, x

# classmethod 对象保存在类的 __dict__，__func__ 是原始函数
cm = type(C).__dict__["m"]
print(cm.__func__ is C.__dict__["m"].__func__)
# 输出：True
print(cm.__func__(C, 10))
# 输出：(<class 'C'>, 10)
```

`__func__` 是没有绑定的原始函数，手动传 `cls` 调用就是它的本来面目。`@classmethod` 做的唯一事情就是包了一层描述符，让属性访问时自动把"类"塞进第一参数。所有的"魔法"都来自这一层 `__get__`。

**classmethod 可以手动构造**（虽然极少这么做）：

```python
def raw(cls, x):
    return cls, x

class D:
    m = classmethod(raw)

print(D.m(5))
# 输出：(<class 'D'>, 5)
```

`classmethod(raw)` 等价于在 `raw` 上加 `@classmethod`。这种写法在元编程（动态给类装配方法）时偶尔用到，比如根据配置给某类挂上不同的类方法。

### 4.8 装饰器叠加时的顺序原理

当 `@classmethod` 与 `@abstractmethod` 叠加，为什么要 `@classmethod` 在外、`@abstractmethod` 在内？

```python
# 正确顺序
class C(ABC):
    @classmethod        # 外层：最后执行，把整件事变成 classmethod 对象
    @abstractmethod     # 内层：先执行，标记函数为抽象
    def m(cls): ...
```

执行顺序是"自下而上"装饰：先 `abstractmethod(m)` 得到一个标记了 `__isabstractmethod__ = True` 的函数对象，再 `classmethod(...)` 把它包成类方法描述符。`abc` 机制在类创建后会扫描类字典，检查每个属性是否带 `__isabstractmethod__`——`classmethod` 对象会代理这个属性（`classmethod.__get__` 返回的绑定方法会把 `__isabstractmethod__` 透出来），所以 `abc` 能识别出"这个类方法还是抽象的"，从而阻止类被实例化直至子类实现它。

如果反过来写 `@abstractmethod` 在外、`@classmethod` 在内，那最外层是 `abstractmethod` 作用在"一个 classmethod 对象"上，`abc` 的标记逻辑就乱了，识别失败。所以记住：**`@classmethod` 放最外层**，让其它装饰器先作用在裸函数上，最后再被 `classmethod` 包成描述符。

---

## 5. 总结

**本文内容要点**：

- `@classmethod` 是内置装饰器，把函数变成类方法；第一参数 `cls` 指向类本身（不是实例），命名只是约定但应遵守。
- 两种调用方式：`ClassName.method()`（推荐）与 `obj.method()`（合法），两种方式下 `cls` 都是类；通过实例调用时 `cls` 来自 `type(obj)`。
- 类方法适合操作类级状态——类属性、实例计数器、全局配置；把类属性的读写收口到类方法里便于校验和扩展。
- 最典型用途是替代构造器工厂方法 `from_xxx`（标准库先例：`dict.fromkeys`、`datetime.fromisoformat`）；工厂用 `cls(...)` 造实例而非写死类名，使得子类调用即得子类实例。
- 类方法被子类继承且 `cls` 指向实际子类，这是多态工厂（`Animal.create` 子类复用）和注册分发（按 kind 查表选子类）能成立的基础。
- 与实例方法（`self`、操作实例）、静态方法（无绑定、不可多态）的对比与选型决策：需要类状态或多态用 `@classmethod`，需要实例状态用实例方法，两者都不需要才用 `@staticmethod`。
- 进阶用法：类方法间通过 `cls.other()` 多态联动、`super().method()` 调父类类方法、与 `@abstractmethod` 叠加强制子类实现、自实现 `classproperty` 做类属性 property。
- 底层原理：`classmethod` 是描述符，`__get__(obj, cls)` 总是把类（而非实例）预填为第一参数；`cls` 的具体值由"发起属性访问的类"决定，实例访问时取 `type(obj)`；这是"通过实例调用 cls 仍是类"与"子类调用 cls 是子类"的根源。普通 `function` 描述符与之对照，把 `obj` 预填为 `self`——两种描述符的差异决定了实例方法与类方法的全部行为差别。

**读完本文你应能掌握**：

- 能说明 `@classmethod` 的作用、`cls` 与 `self` 的本质区别，并能正确判断一个方法该用实例方法、类方法还是静态方法。
- 能写出 `from_dict`/`from_json` 等替代构造器工厂方法，并解释为什么用 `cls(...)` 而非写死类名能让子类多态受益。
- 能用类方法管理类级状态（计数器、注册表、配置开关），并避免可变类属性默认值的共享陷阱。
- 能设计基于类方法的多态工厂与子类注册分发，新增子类时不改分派逻辑。
- 能从描述符角度解释"`cls` 为何总是类、子类调用时为何 `cls` 是子类、通过实例调用为何 `cls` 仍是类"，并能对照普通函数描述符说明 `self` 与 `cls` 绑定机制的差异。
