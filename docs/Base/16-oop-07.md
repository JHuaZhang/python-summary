## 1. 介绍

### 1.1 什么是静态方法

在 Python 的面向对象体系里，定义在类里的函数默认是「实例方法」——它的第一个参数 `self` 会被解释器自动填成调用该方法的实例对象。这种"自动填第一参数"的机制很贴心，但并不是所有写在类里的函数都需要访问实例或类本身。

有些函数只是「逻辑上归属于这个类」，却并不依赖任何实例状态、也不依赖类状态。比如一个温度换算工具类里的 `c_to_f(celsius)`，它只接收一个摄氏度数值、返回华氏度数值，换算公式和类的实例、和类本身都没有任何关系。把它放在类外面写成普通函数也完全可以，但放在类里能更好地组织代码结构——调用方一看 `TemperatureConverter.c_to_f(100)` 就知道这是一个温度换算工具。

`staticmethod`（静态方法）就是为这类函数准备的。它用 `@staticmethod` 装饰器标记，被标记后，这个函数**不再自动接收 `self` 或 `cls` 作为第一参数**，它的参数列表就是普通函数的参数列表。无论你用 `ClassName.method(...)` 调用，还是用 `obj.method(...)` 调用，解释器都**不会**偷偷把类或实例塞进参数里——你传什么参数，函数就收到什么参数。

一句话定义：**静态方法是写在类命名空间里的普通函数，它与实例方法、类方法的关键区别在于调用时不接受任何隐式第一参数。**

### 1.2 基本语法与最小用法

定义静态方法只需在普通函数上方加一行 `@staticmethod`：

```python
class MathUtils:
    @staticmethod
    def add(a, b):
        return a + b
```

注意 `add` 的参数是 `a, b`，没有 `self`、也没有 `cls`。调用时也按普通函数的方式传参：

```python
# 通过类名调用（最常见）
print(MathUtils.add(3, 5))
# 输出：8

# 通过实例调用也可以，但同样不会传入实例
util = MathUtils()
print(util.add(3, 5))
# 输出：8
```

两种调用方式结果完全一样。`util.add(3, 5)` 看起来像是实例方法调用，但因为 `add` 是静态方法，`util` 这个实例并不会被传进去——`add` 收到的就只有 `3` 和 `5`。这是静态方法最需要记住的一点：**调用形式不能改变参数接收情况，静态方法永远只拿到你显式传进去的那些参数。**

下面这个例子更直白地展示了"没有隐式参数"这件事：

```python
class Demo:
    @staticmethod
    def show_args(*args):
        print("收到参数：", args)

Demo.show_args(1, 2, 3)
# 输出：收到参数： (1, 2, 3)

d = Demo()
d.show_args(1, 2, 3)
# 输出：收到参数： (1, 2, 3)

# 对比实例方法：实例会被自动塞进 self
class Demo2:
    def show_args(self, *args):
        print("self =", self, " 其余参数：", args)

d2 = Demo2()
d2.show_args(1, 2, 3)
# 输出：self = <Demo2 object at 0x...>  其余参数： (1, 2, 3)
```

可以看到，`Demo.show_args` 不论用类还是实例调用，`args` 里都只有 `(1, 2, 3)`；而 `Demo2.show_args` 通过实例调用时，`self` 被自动填成了那个实例对象。这就是静态方法与实例方法在「第一参数」上的根本差异。

## 2. 核心内容

### 2.1 @staticmethod 装饰器的基本用法

`@staticmethod` 是一个内置装饰器，作用是把一个普通函数「标记」为静态方法。它的语法形式是：

```python
class ClassName:
    @staticmethod
    def method_name(params):
        # 函数体，与普通函数完全一致
        ...
```

被装饰后的函数在类体内不被当作实例方法处理。装饰器本身不改变函数的逻辑、参数、返回值——它只是改变了「这个函数被访问时，解释器如何对待它」。具体来说，普通的函数对象在类里会被当作实例方法（会自动绑定 `self`），而被 `@staticmethod` 包裹后，它变成了一个 `staticmethod` 对象，访问时不会被绑定。

来看一个完整的工具类示例，体会静态方法的典型写法：

```python
class TemperatureConverter:
    """温度换算工具：各种温标之间的换算公式都是纯数学运算，不依赖任何状态。"""

    @staticmethod
    def c_to_f(celsius):
        """摄氏度 -> 华氏度"""
        return celsius * 9 / 5 + 32

    @staticmethod
    def f_to_c(fahrenheit):
        """华氏度 -> 摄氏度"""
        return (fahrenheit - 32) * 5 / 9

    @staticmethod
    def c_to_k(celsius):
        """摄氏度 -> 开尔文"""
        return celsius + 273.15


# 所有换算都可以直接用类名调用，无需实例化
print(TemperatureConverter.c_to_f(100))
# 输出：212.0

print(TemperatureConverter.f_to_c(212))
# 输出：100.0

print(TemperatureConverter.c_to_k(0))
# 输出：273.15
```

这个例子体现了静态方法的两大典型特征：

1. **无需实例化**。`TemperatureConverter` 没有被实例化过，直接 `TemperatureConverter.c_to_f(100)` 就能用。因为这些方法根本不需要实例状态，自然不用先造一个实例。
2. **纯工具函数**。`c_to_f` 内部只用了传入的参数 `celsius` 和数学常数，没有访问 `self.xxx`，也没有访问 `cls.xxx`。它和写在类外面的 `def c_to_f(celsius): ...` 在行为上完全等价。

**为什么要把这类函数放进类里**

既然静态方法和普通函数行为一致，为什么不直接写成模块级函数？原因主要在代码组织：

- **命名空间归类**。`TemperatureConverter.c_to_f` 比 `c_to_f` 更能表达"这是温度换算"。多个工具函数放进同一个工具类，调用方用 `TemperatureConverter.` 前缀就能看到该领域所有相关函数，IDE 自动补全也更友好。
- **避免模块级命名污染**。一个模块里如果散落几十个 `c_to_f`、`miles_to_km`、`kg_to_lb`，会显得凌乱；收进 `UnitConverter` 类里就整洁得多。
- **便于继承与多态**。静态方法可以被 subclass 覆盖（通过类名访问时会按继承链查找），这一点普通模块函数做不到。例如 `class FastConverter(TemperatureConverter)` 可以重写 `c_to_f` 用查表实现，调用方代码 `TemperatureConverter.c_to_f(...)` 改成 `FastConverter.c_to_f(...)` 就能切换实现。

**调用方式的两种写法**

```python
# 写法一：类名调用（推荐，表达"这是工具方法"）
TemperatureConverter.c_to_f(100)

# 写法二：实例调用（合法，但容易误导读者以为它用了实例状态）
conv = TemperatureConverter()
conv.c_to_f(100)
```

两种写法结果一致。但除非你有特别的理由（比如接口要求所有方法都通过实例访问），否则静态方法**优先用类名调用**——这样代码读者一眼就知道这个方法不依赖实例，不会产生"它是不是在用 self 的某个属性"的误解。

### 2.2 静态方法内部不能使用 self 或 cls

静态方法的第一参数既不是实例也不是类，所以函数体内**不能**出现 `self` 或 `cls` 这样的名字（除非你把它们当成普通参数名，但那会非常误导）。如果你在静态方法里尝试访问实例属性，会直接失败：

```python
class Counter:
    def __init__(self):
        self.count = 0

    @staticmethod
    def describe():
        # 这里没有 self，访问不到 self.count
        return "这是一个计数器"


c = Counter()
c.count = 5
print(c.describe())
# 输出：这是一个计数器
```

`describe` 返回的是一个固定字符串，它根本不知道 `c.count` 是 5 还是别的什么。如果你希望 `describe` 能读到实例的 `count`，就不能用 `@staticmethod`，而要写成实例方法：

```python
class Counter:
    def __init__(self):
        self.count = 0

    def describe(self):
        return f"当前计数：{self.count}"


c = Counter()
c.count = 5
print(c.describe())
# 输出：当前计数：5
```

**判断该用静态方法还是实例方法的一个简单准则**：方法内部需不需要用 `self.xxx` 访问实例数据？需要 → 实例方法；不需要 → 再看是否需要 `cls` 访问/修改类数据，都不需要 → 静态方法。

### 2.3 静态方法与实例方法、类方法同处一类

实际工程里，一个类往往同时包含三种方法：实例方法（操作实例状态）、类方法（操作类状态）、静态方法（纯工具）。把它们放在一起对比，能更清楚地看到各自的角色与参数差异。

```python
class Logger:
    # 类属性：所有实例共享的配置
    _level = "INFO"

    def __init__(self, name):
        self.name = name  # 实例属性：每个 logger 实例自己的名字

    # 实例方法：用到 self，操作实例状态
    def log(self, message):
        print(f"[{Logger._level}] {self.name}: {message}")

    # 类方法：用到 cls，操作类状态
    @classmethod
    def set_level(cls, level):
        cls._level = level

    # 静态方法：既不用 self 也不用 cls，纯工具
    @staticmethod
    def format_timestamp(ts):
        """把时间戳格式化成可读字符串，与任何 logger 实例/类配置无关。"""
        import time
        return time.strftime("%Y-%m-%d %H:%M:%S", time.localtime(ts))


# 静态方法直接用类名调用，不需要实例
print(Logger.format_timestamp(1700000000))
# 输出：2023-11-15 06:13:20

# 类方法操作的是类级别的配置
Logger.set_level("DEBUG")
# 实例方法需要实例，且会用到的实例/类状态
app_logger = Logger("app")
app_logger.log("服务已启动")
# 输出：[DEBUG] app: 服务已启动
```

这个 `Logger` 类把三种方法的分工展示得很清楚：

| 方法类型 | 装饰器 | 第一参数 | 能访问什么 | 典型用途 |
|---------|--------|---------|-----------|---------|
| 实例方法 | 无 | `self`（实例） | 实例属性 + 类属性 | 操作单个对象的状态 |
| 类方法 | `@classmethod` | `cls`（类） | 类属性（不能直接访问实例属性） | 操作类级配置、替代构造 |
| 静态方法 | `@staticmethod` | 无 | 只能访问自己参数与全局变量 | 与类相关的纯工具函数 |

`format_timestamp` 是静态方法的典型——它只是个时间格式化的小工具，放进 `Logger` 类是因为它「服务于日志这个领域」（日志常用时间戳格式化），但它和具体某个 logger 实例、和 `_level` 这个类配置都无关。如果你把它写成模块级函数 `def format_timestamp(ts):` 也完全正确，放进类里纯粹是为了代码组织。

### 2.4 静态方法可以被继承和覆盖

静态方法是类的属性，会被 subclass 继承。子类可以覆盖父类的静态方法，之后通过子类名调用时，执行的就是子类的版本：

```python
class BaseValidator:
    @staticmethod
    def is_valid(value):
        """基类规则：非空即合法"""
        return value is not None and value != ""


class StrictValidator(BaseValidator):
    @staticmethod
    def is_valid(value):
        """子类规则：必须是长度 >= 3 的非空字符串"""
        return isinstance(value, str) and len(value) >= 3


print(BaseValidator.is_valid(""))
# 输出：False

print(StrictValidator.is_valid(""))
# 输出：False

print(StrictValidator.is_valid("ab"))
# 输出：False

print(StrictValidator.is_valid("abc"))
# 输出：True
```

这里有个容易踩的坑：静态方法虽然能被覆盖，但它是**按类名静态绑定的**，而不是像实例方法那样在运行时根据对象的实际类型动态查找。也就是说，如果你在子类实例上调用一个父类没被覆盖的静态方法，它就是父类的版本；如果在子类里覆盖了，通过子类名或子类实例调用就是子类版本。这与实例方法的多态行为不完全一样——实例方法通过 `self` 调用时会走 MRO 动态查找，而静态方法不接收 `self`，所以不存在"基于实际对象类型"的动态分发。

看下面这个对比：

```python
class Animal:
    @staticmethod
    def legs():
        return 4

    def speak(self):
        # 实例方法：自我调用走 self 的 MRO
        return f"我有 {self.legs()} 条腿"


class Spider(Animal):
    @staticmethod
    def legs():
        return 8


a = Animal()
print(a.speak())
# 输出：我有 4 条腿

s = Spider()
print(s.speak())
# 输出：我有 8 条腿
```

`s.speak()` 输出 8，是因为 `speak` 里通过 `self.legs()` 调用，`self` 是 `Spider` 实例，`self.legs()` 走 `Spider` 的版本。这里实例方法 `speak` 借助 `self` 实现了多态，而静态方法 `legs` 自身只是被覆盖了。

**一个细节**：在 `Animal.speak` 内部调用静态方法用的是 `self.legs()` 而非 `Animal.legs()`。这是因为写 `Animal.legs()` 会写死父类，子类覆盖就失效了；写 `self.legs()` 则会根据实际对象类型查找，能命中子类覆盖。可以说静态方法本身不参与动态分发，但当它通过 `self` 被访问时，是否能命中子类版本，取决于 `self` 的类型 —— 这是属性查找的功劳，不是静态方法自己的机制（这一点在第 4 章原理部分会细讲）。

### 2.5 静态方法作为替代构造的辅助

类方法 `@classmethod` 经常被用来做「替代构造」（factory），比如 `from_string`、`from_dict`。静态方法虽然不能直接读 `cls`，但常常作为这些工厂方法的「计算助手」——把解析、换算的纯逻辑抽成静态方法，让工厂方法只负责调度：

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    @classmethod
    def from_string(cls, s):
        """从 'x,y' 字符串构造 Point"""
        x, y = cls._parse(s)  # 调用静态方法做解析
        return cls(x, y)

    @staticmethod
    def _parse(s):
        """纯解析逻辑：把 '3,4' 拆成 (3, 4)"""
        parts = s.split(",")
        return int(parts[0]), int(parts[1])


p = Point.from_string("3,4")
print(p.x, p.y)
# 输出：3 4
```

这里 `from_string` 用 `cls` 创建实例（这是类方法的活），而真正解析字符串的 `_parse` 是纯计算，不碰 `cls`，所以做成静态方法。这种"类方法做工厂、静态方法做计算"的搭配在标准库和第三方库里非常常见。

把纯计算逻辑抽成静态方法有一个好处：它**可以脱离类单独测试**。测试 `_parse` 时不需要造 `Point` 实例，直接 `Point._parse("3,4")` 就能验证。这比把解析逻辑塞在 `from_string` 内部更易测、更易复用。

### 2.6 静态方法调用时不会触发绑定

这一点是静态方法最直观的「行为差异」，值得单独强调。普通函数在类里通过实例访问时，会变成一个「绑定方法」（bound method），它会自动把实例预填到 `self`：

```python
class Foo:
    def normal(self, x):
        return x * 2


f = Foo()
bound = f.normal  # 这是一个绑定方法对象
print(bound)
# 输出：<bound method Foo.normal of <Foo object at 0x...>>
print(bound(10))
# 输出：20   # 只传了 10，self 被自动填成 f
```

而静态方法通过实例访问时，拿到的是**原始函数**，不是绑定方法：

```python
class Foo:
    @staticmethod
    def static(x):
        return x * 2


f = Foo()
func = f.static
print(func)
# 输出：<function Foo.static at 0x...>   # 注意是 function，不是 bound method
print(func(10))
# 输出：20   # 必须显式传 10
```

`f.static` 返回的是一个普通 `function` 对象（不是 `bound method`），调用它时必须显式提供全部参数。这就是静态方法"调用时不传隐式参数"的直观体现：因为你拿到的压根就不是绑定过的方法，而是赤裸的函数。

如果你尝试像实例方法那样少传一个参数，会报参数缺失错误：

```python
class Foo:
    @staticmethod
    def needs_two(a, b):
        return a + b


f = Foo()
# 试图少传一个参数（期望像实例方法那样自动补 self）—— 不行
print(f.needs_two(1))
# 报错：TypeError: needs_two() missing 1 required positional argument: 'b'
```

报错信息"missing 1 required positional argument: 'b'"明确说明：`f` 没有被自动塞进去，`needs_two` 真的只收到了一个参数 `1`。

## 3. 最佳实践

### 3.1 什么时候该用静态方法

**推荐：与类领域相关、但不需要实例或类状态的纯工具函数。**

判断清单（按顺序排查）：

1. 方法内部需要访问 `self.xxx`（实例属性）吗？需要 → 实例方法。
2. 方法内部需要访问/修改 `cls.xxx`（类属性）、或者需要用 `cls` 来创建实例吗？需要 → 类方法。
3. 两样都不需要，但函数逻辑上和这个类关系密切（同一领域、配套工具）？→ 静态方法。
4. 连「和这个类关系密切」都谈不上？→ 写成模块级普通函数，别硬塞进类里。

举几个适合做静态方法的例子：

- `StringValidator.is_valid_email(s)`：邮箱格式校验，纯字符串处理。
- `MathUtils.gcd(a, b)`：最大公约数，纯数学。
- `TemperatureConverter.c_to_f(c)`：温度换算，纯公式。
- `Logger.format_timestamp(ts)`：时间戳格式化，纯格式化。
- `GeoUtils.haversine(lat1, lon1, lat2, lon2)`：球面距离，纯数学。

这些函数放在类里是因为它们都属于某个明确的领域（字符串校验、数学、温度、日志、地理），放一起方便查找和 IDE 补全；但它们本身和实例、类状态毫无瓜葛，做成静态方法最恰当。

**不推荐：为了"显得面向对象"而把一堆无关函数塞进一个类并标成静态方法。**

如果你发现一个类里全是静态方法、没有实例方法、没有类属性，那这个类其实退化成了一个命名空间。此时要么拆成多个职责更清晰的工具类，要么干脆把这些函数放到模块顶层——Python 的模块本身就是命名空间，不一定非要用类来装。

### 3.2 静态方法内部不要去"手动"获取类或实例

有时有人为了在静态方法里拿到类，会写出这种 hack：

```python
class Bad:
    _config = {"timeout": 30}

    @staticmethod
    def get_timeout():
        return Bad._config["timeout"]   # 硬编码类名去访问类属性
```

这能跑通，但有隐患：

- **继承时失效**。子类 `class Better(Bad): _config = {"timeout": 60}` 覆盖了 `_config`，但 `Better.get_timeout()` 还是返回 30，因为静态方法里硬编码了 `Bad`。
- **逻辑上荒谬**。既然你要读类属性，说明这个方法和类状态有关——那它就该是类方法，用 `cls` 而不是硬编码 `Bad`。

正确写法：

```python
class Good:
    _config = {"timeout": 30}

    @classmethod
    def get_timeout(cls):
        return cls._config["timeout"]   # 通过 cls，继承时正确分发


class Better(Good):
    _config = {"timeout": 60}


print(Good.get_timeout())
# 输出：30
print(Better.get_timeout())
# 输出：60   # 子类覆盖生效
```

**准则：静态方法内部不应直接引用类名去访问类级数据。一旦你这么做了，多半说明它本应是类方法。** 静态方法的正确用法是「只用自己的参数算东西」，不碰类的状态。

### 3.3 静态方法命名与标记的约定

- 静态方法既然是工具函数，用**动词或动宾短语**命名，表达"做什么"：`is_valid`、`c_to_f`、`format_timestamp`。不要用名词命名（名词更像属性）。
- 纯内部使用的静态方法用下划线前缀：`_parse`、`_normalize`，表示"这是给本类其他方法用的私有工具"。
- 静态方法通常不访问实例属性，所以不要在静态方法名里带 `self_` 之类的暗示。
- 如果一个静态方法其实是某个公开 API 的实现细节，把它放成 `_` 开头的私有静态方法，再让公开的实例方法/类方法去调它，比直接把细节暴露在公开接口里更好。

### 3.4 不要用静态方法"伪装"实例方法

有时候新手会把本应是实例方法的方法误写成静态方法，然后在外部调用时手动把实例传进去：

```python
class Bad:
    def __init__(self, value):
        self.value = value

    @staticmethod
    def display(obj):
        print(obj.value)


b = Bad(42)
Bad.display(b)
# 输出：42
```

虽然能跑，但这完全违背了 Python 的方法机制——明明可以让它做实例方法自动收 `self`，却偏要手动传 `obj`，既啰嗦又容易传错（`Bad.display("not an instance")` 会运行到 `obj.value` 才崩）。正确写法就是去掉 `@staticmethod`，把 `obj` 换成 `self`：

```python
class Good:
    def __init__(self, value):
        self.value = value

    def display(self):
        print(self.value)


g = Good(42)
g.display()
# 输出：42
```

**简记：方法需要实例数据就老老实实写成实例方法，别用静态方法 + 手动传实例这种别扭写法。**

### 3.5 静态方法与函数式工具的兼容性

因为静态方法本质上就是普通函数，它能很好地与 Python 的函数式工具（`map`、`filter`、`sorted` 的 `key` 等）配合：

```python
class StringUtils:
    @staticmethod
    def normalize(s):
        return s.strip().lower()


words = ["  Hello", "WORLD ", "  PyTHON "]
# 把静态方法当普通函数传给 map
normalized = list(map(StringUtils.normalize, words))
print(normalized)
# 输出：['hello', 'world', 'python']

# 当 sorted 的 key
data = ["Banana", "apple", "Cherry"]
print(sorted(data, key=StringUtils.normalize))
# 输出：['apple', 'Banana', 'Cherry']
```

注意这里 `StringUtils.normalize` 作为函数对象直接被传递（`map` 和 `sorted` 调用它时按普通函数传参）。如果它是个实例方法，就得先造实例或用 `lambda` 包一层；静态方法没这麻烦。这也是静态方法"和普通函数一致"的一个实用体现。

### 3.6 用 @staticmethod 明确表达意图

在团队协作中，`@staticmethod` 还有一个无形的价值：它**向读代码的人声明意图**——"这个方法我故意写成静态的，它不碰实例也不碰类"。这种声明比注释更可靠，因为它被解释器强制执行：你一旦在静态方法里写了 `self.xxx`，运行时会立刻报错 `NameError: name 'self' is not defined`（因为 `self` 压根没被定义为参数）。

反过来，如果一个方法写成静态方法后，过几个月你发现总忍不住想在它里面读类属性，这个"想读"的冲动本身就是一个信号——它在告诉你：这个方法不该是静态的，该升级成类方法了。把 `@staticmethod` 改成 `@classmethod`，把第一参数从某个业务参数改成 `cls`，问题就理顺了。

## 4. 原理

### 4.1 函数也是描述符：普通方法为何会自动绑定 self

要理解静态方法的原理，得先理解普通实例方法为什么会"自动填 self"。这背后的关键事实是：**Python 的函数对象本身就是描述符（descriptor）**。

描述符是实现了 `__get__`（以及可选 `__set__`/`__delete__`）协议的对象。当你通过实例访问一个描述符时，Python 会调用它的 `__get__(instance, owner)`，把访问"转换"成别的结果。普通函数实现了 `__get__`，它的 `__get__` 做的事情是：**返回一个绑定方法对象，把 `instance` 预填到第一参数 `self` 上。**

用代码看这个过程最直观：

```python
class C:
    def method(self, x):
        return x


# 1) 直接通过类访问：拿到原始函数（此时 __get__ 被以 instance=None 调用，返回函数本身）
print(C.method)
# 输出：<function C.method at 0x...>

# 2) 通过实例访问：__get__ 被以 instance=obj 调用，返回绑定方法
obj = C()
print(obj.method)
# 输出：<bound method C.method of <C object at 0x...>>
```

`C.method`（类访问）和 `obj.method`（实例访问）返回的不是同一个东西——前者是函数，后者是绑定方法。绑定方法内部记录了"要调用的原始函数"和"被绑定的实例"两个信息，当你调用它时，它会把那个实例自动加到参数列表最前面：

```python
obj = C()
bound = obj.method
# bound(10) 等价于 C.method(obj, 10)
print(bound(10))
# 输出：10
```

这就是普通方法"自动传 self"的全部真相：**函数的 `__get__` 在被实例访问时，返回的是一个帮你预填了 `self` 的绑定方法**。这个机制对任何"在类体里写的普通函数"都默认生效，所以默认情况下类里的函数都是实例方法。

### 4.2 staticmethod 是一个描述符，但它的 __get__ 不做绑定

`@staticmethod` 做的事情，本质上是把普通函数对象换成了一个 `staticmethod` 对象。这个 `staticmethod` 对象也是一个描述符——但它实现了与普通函数**不同**的 `__get__`：

> **staticmethod 的 `__get__` 直接返回原始函数，不做任何绑定。**

也就是说，无论你是通过类访问还是通过实例访问一个静态方法，`__get__` 返回的都是那个原始的 `function` 对象，而不是绑定方法。既然拿到的是没绑过的函数，调用时自然不会有人帮你预填 `self` 或 `cls`——你必须显式传全所有参数。

用代码验证这一点：

```python
class C:
    @staticmethod
    def static_method(x):
        return x


# 类访问：__get__ 返回原始函数
print(C.static_method)
# 输出：<function C.static_method at 0x...>

# 实例访问：__get__ 同样返回原始函数（注意不是 bound method！）
obj = C()
print(obj.static_method)
# 输出：<function C.static_method at 0x...>

# 对比绑定方法：实例访问普通函数返回 bound method
class D:
    def normal(self, x):
        return x


d = D()
print(d.normal)
# 输出：<bound method D.normal of <D object at 0x...>>
```

关键差异就在这里：`obj.static_method` 拿到的还是 `function`，而 `d.normal` 拿到的是 `bound method`。类型不同，调用行为就不同。

可以进一步用 `inspect` 看见两者的对象类型差异：

```python
import inspect

print(type(C.static_method))          # <class 'function'>
print(type(C.__dict__["static_method"]))  # <class 'staticmethod'>  ← 存在类字典里的是 staticmethod 对象
print(type(D.normal))                  # <class 'function'>
print(type(D.__dict__["normal"]))      # <class 'function'>        ← 存在类字典里的是原始函数
```

这里有个细节值得注意：**存在类字典 `C.__dict__["static_method"]` 里的是 `staticmethod` 对象**（装饰后产生的包装对象），而 `C.static_method`（属性访问后）拿到的是 `staticmethod.__get__` 返回的原始函数。属性访问会触发描述符协议，把 `staticmethod` 对象"解包"回原始函数。`D.__dict__["normal"]` 存的就是函数本身，因为普通函数没有被任何装饰器包裹。

这也解释了为什么 `staticmethod` 被叫做"装饰器但其实是描述符"——它对函数的包裹不是为了改变函数行为，而是为了改变函数被访问时的 `__get__` 逻辑，让它在实例访问时也不绑定。

### 4.3 三角对比：function / classmethod / staticmethod 的描述符行为

把三种"放在类里的可调用物"放在一起对比描述符行为，是最清晰的记忆方式。

**普通函数（默认变成实例方法）**

- 类字典里存的是：`function` 对象。
- `__get__(None, cls)`（类访问）：返回函数本身，不绑定。
- `__get__(instance, cls)`（实例访问）：返回 `bound method`，把 `instance` 绑定到第一参数。
- 结果：通过实例调用时 `self` 被自动填入。

```python
class A:
    def m(self, x):
        return x


a = A()
print(type(A.__dict__["m"]))   # <class 'function'>
print(A.m)                     # <function A.m ...>        ← 类访问：函数
print(a.m)                     # <bound method A.m of ...> ← 实例访问：绑定方法
print(a.m(1))                  # 1   ← a 被自动填进 self
```

**classmethod**

- 类字典里存的是：`classmethod` 对象（包裹了原始函数）。
- `__get__(instance, cls)`：返回 `bound method`，但绑定的是**类** `cls`，不是实例。
- 特别地，无论 `instance` 是 `None` 还是某个实例，`classmethod.__get__` 都用 `cls`（也就是 `owner`）来绑定。所以类访问和实例访问都会把 `cls` 绑定到第一参数。
- 结果：调用时 `cls` 被自动填入，无论是 `Cls.m()` 还是 `obj.m()`。

```python
class B:
    @classmethod
    def m(cls, x):
        return (cls, x)


b = B()
print(type(B.__dict__["m"]))   # <class 'classmethod'>
print(B.m)                     # <bound method B.m of <class B>>
print(b.m)                     # <bound method B.m of <class B>>   ← 实例访问也绑定类，不是 b
print(B.m(1))                  # (<class 'B'>, 1)   ← cls 自动填成 B
print(b.m(1))                  # (<class 'B'>, 1)   ← 同样填成 B，不是 b
```

**staticmethod**

- 类字典里存的是：`staticmethod` 对象（包裹了原始函数）。
- `__get__(instance, cls)`：**直接返回原始函数**，不做任何绑定。
- 结果：无论类访问还是实例访问，拿到的都是赤裸函数，调用时不会自动填任何参数。

```python
class S:
    @staticmethod
    def m(x):
        return x


s = S()
print(type(S.__dict__["m"]))   # <class 'staticmethod'>
print(S.m)                     # <function S.m ...>      ← 类访问：原始函数
print(s.m)                     # <function S.m ...>      ← 实例访问：还是原始函数
print(S.m(1))                  # 1   ← 没有任何隐式参数
print(s.m(1))                  # 1   ← 同样没有任何隐式参数
```

**一张对比表**

| | 类字典存储 | 类访问 `Cls.m` | 实例访问 `obj.m` | 调用时的隐式第一参数 |
|---|---|---|---|---|
| 普通函数 | `function` | 原始 `function` | `bound method`（绑定 `obj`） | `self = obj`（实例访问时） |
| `@classmethod` | `classmethod` 对象 | `bound method`（绑定 `cls`） | `bound method`（绑定 `cls`） | `cls = Cls`（始终） |
| `@staticmethod` | `staticmethod` 对象 | 原始 `function` | 原始 `function` | 无 |

这张表是整个"为什么静态方法不传 self/cls"的核心答案。三者都是描述符，但 `__get__` 的实现策略不同：普通函数偏向"帮实例绑定"，classmethod 偏向"帮类绑定"，staticmethod 偏向"什么都不绑定"。

### 4.4 为什么静态方法不需要实例或类作为上下文

从设计意图看，静态方法就是为了支持「不需要实例或类上下文」这类函数而存在的。普通函数的 `__get__` 会偷偷把实例预填进去，这对需要 `self` 的实例方法很方便，但对纯工具函数就是麻烦——它压根不需要 `self`，少传一个参数反而会让调用者困惑。`staticmethod` 的存在就是为了"关掉"这个自动绑定行为。

从实现看，`staticmethod` 之所以能做到不绑定，是因为它的 `__get__` 选择**忽略传入的 `instance` 和 `owner`**，直接返回原始函数。把这种"忽略上下文"的语义和类方法对比：

- `classmethod.__get__(instance, owner)` 把 `owner`（类）拿来绑到第一参数——它要类作为上下文。
- `staticmethod.__get__(instance, owner)` 直接丢掉 `instance` 和 `owner`，返回裸函数——它不要任何上下文。

也就是说，`staticmethod` 拿到了上下文信息（`instance` 和 `owner` 都通过 `__get__` 的参数传进来了），但它**刻意不用**。这恰好对应了它的语义：这个函数和当前位置的对象/类没有关系，请把它当普通函数对待。

这也能解释一个常见疑问："为什么 `obj.static_method()` 不传 `obj`？明明是通过 `obj` 调用的呀。" —— 因为在属性访问那一瞬间，`obj` 被交给了 `staticmethod.__get__`，但 `__get__` 把它扔了，返回了不带 `obj` 的原始函数。接下来 `()` 调用针对的是那个原始函数，`obj` 早已不在场。`obj` 的唯一作用是"触发了属性访问"，但没进入最终的函数调用。

### 4.5 调用时无隐式第一参数的完整链路

把一次 `obj.static_method(arg)` 调用的全过程拆开，能彻底看清"为什么没有隐式参数"：

1. `obj.static_method` 触发属性查找。
2. Python 在 `type(obj)` 的 MRO 里找到 `static_method`，发现它存在类字典里是个 `staticmethod` 对象。
3. 因为 `staticmethod` 实现了 `__get__`，Python 把它当作描述符，调用 `staticmethod.__get__(obj, type(obj))`。
4. `staticmethod.__get__` 的实现忽略 `obj` 和 `type(obj)`，直接返回被包裹的原始函数 `function`。
5. 所以 `obj.static_method` 这个表达式的值就是那个原始函数。
6. 接着 `(arg)` 是对原始函数的调用。原始函数的签名是 `def static_method(x): ...`（只有一个参数 `x`），所以调用时只接收 `arg`，没有任何额外的隐式参数。

对比 `obj.normal_method(arg)`：

1. `obj.normal_method` 触发属性查找。
2. 找到 `normal_method` 是个普通 `function`，`function` 也实现了 `__get__`，也是描述符。
3. Python 调用 `function.__get__(obj, type(obj))`。
4. `function.__get__` 看到 `obj is not None`，返回一个绑定方法对象，把 `obj` 存进去作为 `self`。
5. `obj.normal_method` 的值是绑定方法。
6. `(arg)` 调用绑定方法。绑定方法的调用逻辑是：把存的 `obj` 作为第一参数，加上你传的 `arg`，一起传给原始函数。所以实际调用是 `normal_method(obj, arg)`，`self` 被自动填成 `obj`。

两段链路的差异就发生在第 4 步：普通函数的 `__get__` 把 `obj` 做成了绑定方法，而 `staticmethod` 的 `__get__` 把 `obj` 丢了。这一步决定了后面调用时是否有隐式参数。

**通过类调用 `Cls.static_method(arg)` 的链路**

1. `Cls.static_method` 触发属性查找。
2. 找到 `staticmethod` 对象。
3. Python 调用 `staticmethod.__get__(None, Cls)`（注意 `instance` 是 `None`）。
4. `staticmethod.__get__` 仍然忽略这两个参数，返回原始函数。
5. `(arg)` 调用原始函数，只接收 `arg`。

对比 `Cls.normal_method(arg)`：`function.__get__(None, Cls)` 看到 `instance is None`，**也会返回原始函数**（不绑定）。所以 `Cls.normal_method(arg)` 实际上需要你手动传 self：`Cls.normal_method(obj, arg)`。这就是为什么"通过类调用实例方法时必须手动传 self"——因为类访问时函数的 `__get__` 不做绑定。

这一点引出一个有趣的事实：**普通函数和静态方法在"类访问"时表现一样**（都返回原始函数），只有"实例访问"时才分道扬镳——普通函数绑定实例，静态方法依然不绑定。换句话说，`staticmethod` 相对于普通函数的额外作用，体现在"实例访问时不绑定"这一件事上。

### 4.6 从 CPython 实现看 staticmethod 的极简

在 CPython 源码里，`staticmethod` 的 C 实现非常短。它的 `__get__` 大致等价于：

```python
class staticmethod:
    def __init__(self, f):
        self.__func__ = f

    def __get__(self, instance, owner=None):
        return self.__func__   # 直接返回原始函数，无视 instance / owner
```

对比 `classmethod` 的等价实现（简化版）：

```python
class classmethod:
    def __init__(self, f):
        self.__func__ = f

    def __get__(self, instance, owner=None):
        if owner is None:
            owner = type(instance) if instance is not None else object
        # 返回一个绑定到 owner（类）的绑定方法
        return self.__func__.__get__(owner, type(owner))
```

`classmethod.__get__` 至少要计算 `owner`，还要借用函数自身的 `__get__` 构造一个绑定方法（绑的是 `owner`，也就是类）。而 `staticmethod.__get__` 啥都不算，直接 `return self.__func__`。从源码体量上就能看出静态方法的"轻"——它只是一个"不要绑定"的标记。

`staticmethod` 对象本身只持有被包裹的原始函数（在 `__func__` 属性里）。你可以直接访问这个原始函数：

```python
class C:
    @staticmethod
    def m(x):
        return x


# 静态方法对象存在类字典里，内部的原始函数可以通过 __func__ 访问
sm = C.__dict__["m"]
print(type(sm))            # <class 'staticmethod'>
print(sm.__func__)         # <function C.m at 0x...>
print(sm.__func__(42))     # 42   ← 直接调用原始函数
```

这种极简结构也意味着 `staticmethod` 几乎没有额外开销——访问它就是一次 `__get__` 调用返回函数，调用函数本身和普通函数调用一样快。不用担心"用静态方法会不会比普通函数慢"——属性访问时那一次 `__get__` 调用开销可以忽略不计。

### 4.7 一个常见的认知陷阱：静态方法"住在类里"但不等于类方法

有人会混淆"静态方法定义在类里"和"静态方法属于类"，从而误以为静态方法能像类方法那样访问类属性。其实「定义在类里」只是命名空间的归属，不等于「能访问类状态」。类属性之所以能在实例方法里被访问，是因为实例方法有 `self`，而 `self.xxx` 的查找会回退到类（属性查找机制 MRO 的事）；类方法能访问类属性，是因为它有 `cls`。静态方法两个都没有，所以它不能"自然地"触达任何类级数据——除非你硬编码类名去引用（但那是反模式，见 3.2）。

回头看那个 `Logger` 例子：`format_timestamp` 是静态方法，它完全不知道 `Logger._level` 是什么，也不该知道。如果哪天它需要根据日志等级来决定时间戳精度（比如 DEBUG 级带毫秒、INFO 级不带），那它就不再"与类状态无关"了——这时候应该把它改成实例方法或类方法，让它能拿到 `_level`。`staticmethod` 的这种"隔绝状态"既是它的限制，也是它的价值：它强制你把"纯计算"和"有状态"的代码分开，带来更清晰的职责边界。

### 4.8 静态方法的继承查找与覆盖机制

前面 2.4 提到静态方法可以被继承和覆盖，这里从原理上解释它是怎么查找的。

当你写 `Child.static_method(...)`：

1. Python 在 `Child.__dict__` 里找 `static_method`。
2. 找到了（子类覆盖了）→ 是个 `staticmethod` 对象 → `__get__(None, Child)` 返回子类版本的原始函数。
3. 没找到 → 沿 MRO 往上找，在 `Parent.__dict__` 里找到 → 返回父类版本的原始函数。

这个查找过程和普通属性查找一模一样，没有什么特别的。`staticmethod` 只影响"找到之后怎么处理"（即 `__get__` 的行为），不影响"怎么找到"。

当你写 `child_instance.static_method(...)` 并且 `Child` 没有覆盖时：

1. Python 在 `type(child_instance).__dict__`（即 `Child.__dict__`）里找，没找到。
2. 沿 MRO 找到 `Parent.__dict__["static_method"]`，是个 `staticmethod` 对象。
3. 调用 `staticmethod.__get__(child_instance, Child)`，仍然返回原始函数，忽略实例。
4. 调用原始函数，没有隐式参数。

注意第 3 步：即便有 `child_instance`，`staticmethod.__get__` 也照样忽略它。所以"通过子类实例调用父类的静态方法"和"通过父类名调用"结果完全一样——都不会把任何实例/类塞进去。

这也再次说明：静态方法不参与"基于实际对象类型的运行时多态分发"，它只是普通的属性查找。它之所以能在子类里"被覆盖"，是因为子类在自己的 `__dict__` 里塞了一个新的 `staticmethod` 对象，属性查找时优先命中子类版本。这是属性查找的功劳，和实例方法那种靠 `self` 触发的动态分发是两套机制。

## 5. 总结

### 5.1 本文内容要点

- **static 方法的定位**：`@staticmethod` 标记的函数是写在类命名空间里的普通函数，它不接收 `self`、不接收 `cls`，调用时不被自动绑定任何隐式第一参数。它与类相关，但不依赖实例或类状态。
- **基本语法**：在普通函数上方加 `@staticmethod`，参数列表与普通函数一致。`ClassName.method(...)` 与 `obj.method(...)` 两种调用等价，都只传显式参数。
- **典型用途**：与类领域相关、但不需要实例或类状态的纯工具函数，如 `TemperatureConverter.c_to_f`、`Logger.format_timestamp`、`StringUtils.normalize`、`MathUtils.gcd`。它们无需实例化即可通过类名调用。
- **三种方法对比**：实例方法（无装饰器，第一参数 `self`，访问实例状态）、类方法（`@classmethod`，第一参数 `cls`，访问类状态、做替代构造）、静态方法（`@staticmethod`，无隐式参数，纯工具）。
- **继承与覆盖**：静态方法可被子类覆盖，通过子类名或实例访问时按 MRO 查找命中子类版本；但静态方法自身不参与基于实际对象类型的运行时多态分发，覆盖生效靠的是属性查找。
- **原理核心**：普通函数是描述符，其实例访问时 `__get__` 返回绑定方法（预填 `self`）；`classmethod` 的 `__get__` 返回绑定到 `cls` 的绑定方法；`staticmethod` 的 `__get__` 直接返回原始函数、忽略 `instance` 与 `owner`，不做任何绑定。正是这第三种 `__get__` 让静态方法在调用时没有隐式第一参数。
- **最佳实践要点**：需要 `self` 用实例方法、需要 `cls` 用类方法、都不需要且与类领域相关才用静态方法；静态方法内部不要硬编码类名访问类属性（该改成类方法）；不要用静态方法 + 手动传实例来伪装实例方法；静态方法可作为类方法工厂的纯计算助手，便于单独测试、与函数式工具兼容。

### 5.2 读完本文你应能掌握

- 能说明 `@staticmethod` 的语法形式与最小用法，正确写出无 `self`/`cls` 的静态方法并通过类名调用。
- 能判断一个方法该用实例方法、类方法还是静态方法：依据"是否需要 `self` 访问实例状态""是否需要 `cls` 访问类状态或创建实例"两个问题排查。
- 能解释为什么静态方法通过实例调用时 `self` 不会被自动填入——从描述符 `__get__` 返回原始函数、不做绑定这一步讲清。
- 能说清普通函数、`@classmethod`、`@staticmethod` 三者作为描述符的 `__get__` 行为差异，并给出"类访问/实例访问返回什么、调用时隐式参数是什么"的三角对比。
- 能指出静态方法的典型应用场景（纯工具函数、类方法工厂的计算助手）并说明为什么要放进类里（命名空间归类、便于继承覆盖、与函数式工具兼容）。
- 能识别并避免常见反模式：在静态方法里硬编码类名访问类属性、用静态方法伪装实例方法、把无关函数硬塞进工具类。
- 能区分"静态方法被覆盖"与"实例方法多态分发"两种机制：前者靠属性查找命中子类版本，后者靠 `self` 在运行时走 MRO。

### 5.3 一句话回顾

> 静态方法是用 `@staticmethod` 标记、存放在类命名空间里的普通函数；它的描述符 `__get__` 忽略调用上下文、直接返回原始函数，因此无论类名调用还是实例调用都不会预填 `self` 或 `cls`，适合做与类领域相关但不依赖任何状态的纯工具函数。
