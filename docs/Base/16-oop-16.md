## 1. 介绍

### 1.1 什么是多继承

多继承是指一个子类可以同时拥有两个或两个以上基类的继承形式。在 Python 中，声明多继承的语法非常直接——在类定义的括号里列出多个基类，用逗号分隔：

```python
class A:
    def hello(self):
        print("A.hello")

class B:
    def world(self):
        print("B.world")

# C 同时继承 A 和 B，因此同时拥有 hello 和 world 两个方法
class C(A, B):
    pass

c = C()
c.hello()   # 来自 A
c.world()   # 来自 B
# 输出：
# A.hello
# B.world
```

C 同时获得了 A 的 `hello` 和 B 的 `world`，这就是多继承最直观的价值——**能力组合**。一个类不需要把所有功能塞进单一的继承链，而是可以从多个来源分别"借"能力。

多继承在很多面向对象语言里并不存在或受限：Java 类只能单继承（接口可多实现）、Ruby 故意只支持单继承并用 Mixin 模块弥补。Python 选择直接支持多继承，这使得它在表达"一个对象同时具备多种正交能力"时非常灵活，但也因此引入了一类经典难题——当多个基类之间存在共同祖先时，方法解析顺序和基类初始化的重复执行就成了必须正视的问题。

### 1.2 多继承的基本语法与 `__bases__`

多继承的最小语法就是 `class 子类(基类1, 基类2, ...):`。基类的顺序不是任意的装饰，它直接决定了方法解析的优先级——这一点会在第 4 章原理部分深入展开，这里先建立感性认识。

```python
class Base:
    def show(self):
        print("Base.show")

class LoggerMixin:
    def show(self):
        print("LoggerMixin.show（带日志能力）")

class Service(LoggerMixin, Base):
    """先继承 LoggerMixin 再继承 Base，show 会优先用 LoggerMixin 的版本"""
    pass

s = Service()
s.show()
# 输出：
# LoggerMixin.show（带日志能力）

# __bases__ 可以查看一个类的直接基类
print(Service.__bases__)
# 输出：
# (<class '...LoggerMixin'>, <class '...Base'>)
```

`Service.__bases__` 是一个元组，记录了直接基类及其顺序。这个顺序就是书写顺序 `(LoggerMixin, Base)`，它与方法查找顺序（MRO）密切相关但不完全等同——MRO 还要经过 C3 线性化算法处理（详见第 4 章）。

**单继承是多继承的特例**

当只写一个基类时，多继承退化为单继承，所有规则依然适用。理解了多继承的机制，单继承自然就清楚了。因此本篇把单继承视为多继承的退化情形来统一处理，不再单独说明。

### 1.3 从单继承到多继承：为什么需要多继承

真实的业务对象往往同时具备多种"正交"的能力。以一个需要同时具备"可日志记录"和"可序列化为 JSON"的用户对象为例：

- 若只能单继承，要么把日志逻辑塞进 `User` 的父类，要么把 JSON 逻辑塞进去，但这两种能力彼此独立，强行捏合会让父类职责臃肿。
- 多继承允许把每种能力拆成独立的小类（Mixin），按需组合进主类，每个 Mixin 只关心自己的那一维。

```python
import json

class LogMixin:
    def log(self, msg):
        print(f"[LOG] {self.__class__.__name__}: {msg}")

class JsonMixin:
    def to_json(self):
        return json.dumps(self.__dict__, ensure_ascii=False)

class User(LogMixin, JsonMixin):
    def __init__(self, name, age):
        self.name = name
        self.age = age

u = User("张三", 28)
u.log("用户创建")        # 来自 LogMixin
print(u.to_json())       # 来自 JsonMixin
# 输出：
# [LOG] User: 用户创建
# {"name": "张三", "age": 28}
```

`User` 本身只定义业务字段，日志和序列化能力分别来自两个 Mixin，互不干扰、可独立演进。这种"小功能混入主类"的模式是多继承最常见也最健康的用法，后文会专章讨论。

## 2. 核心内容

### 2.1 方法解析顺序（MRO）与 `__mro__`

多继承带来的第一个实际问题就是：当多个基类都定义了同名方法时，子类调用 `obj.method()` 究竟执行哪一个？这由**方法解析顺序**（Method Resolution Order，MRO）决定。Python 给每个类计算好一条线性的方法查找链，存放在 `__mro__` 属性里。

```python
class A:
    def greet(self):
        print("A.greet")

class B(A):
    def greet(self):
        print("B.greet")

class C(A):
    def greet(self):
        print("C.greet")

class D(B, C):
    pass

# __mro__ 是一个元组，按查找顺序排列
for cls in D.__mro__:
    print(cls.__name__)
# 输出：
# D
# B
# C
# A
# object

d = D()
d.greet()
# 输出：
# B.greet
```

`D.__mro__` 为 `[D, B, C, A, object]`：查找 `greet` 时从 D 开始，D 没有就找 B，B 有就停止，因此执行 `B.greet`。注意 B 和 C 都继承自 A，但 A 在 MRO 里只出现一次且排在 B、C 之后——这正是 C3 线性化的功劳，它把菱形结构"压平"成一条无重复的线性链，避免对 A 的重复访问。

**`__mro__` 不可随意更改**

`__mro__` 在类创建时由 C3 算法计算并固化为一个元组，运行期不可修改。这意味着基类列表的书写顺序在类定义那一刻就锁定了方法查找行为。用 `mro()` 方法也可以拿到列表形式：

```python
print([cls.__name__ for cls in D.mro()])
# 输出：
# ['D', 'B', 'C', 'A', 'object']
```

**MRO 无法一致时直接报错**

并非任意基类组合都能算出合法的 C3 顺序。如果基类列表的顺序蕴含矛盾（例如先声明 `B` 在 `C` 前，但 `C` 的某条约束又要求 `C` 在 `B` 前），Python 在类创建时会直接抛 `TypeError`，拒绝创建该类。这是 C3 的一个重要保护机制——它宁可报错也不接受无意义的继承图。

```python
class X: pass
class Y: pass
class Z(X, Y): pass   # Z 的存在要求 X 先于 Y
# 下面这行会抛错：W 要求 Y 先于 X，与 Z 的约束冲突
# class W(Y, X, Z): pass
# TypeError: Cannot create a consistent method resolution
# order (MRO) for bases Y, X, Z
```

（上面的 `class W` 在解释器中会抛 `TypeError` 而非打印输出，注释仅作说明。）

### 2.2 菱形（钻石）继承问题

当继承图出现"A 被 B、C 共同继承，D 又同时继承 B、C"时，结构形如菱形/钻石，这就是经典的菱形继承问题：

```
        A
       / \
      B   C
       \ /
        D
```

菱形的麻烦在于：A 处于共享祖先位置，如果不加处理，A 的方法（尤其是 `__init__`）很可能在构造 D 时被调用多次，或者反过来因为查找路径不经过 A 而漏初始化。这是多继承被诟病"复杂"的根源。

**先看一个"不协作"导致 A 被多次初始化的反例**

下面这个例子故意让 B、C 各自直接调用 `A.__init__`（而非用 super 协作），观察 A 的初始化次数：

```python
class A:
    def __init__(self):
        print("A.__init__ 被调用")
        self.a_value = 1

class B(A):
    def __init__(self):
        print("B.__init__ 被调用")
        A.__init__(self)   # 直接显式调用 A 的初始化
        self.b_value = 2

class C(A):
    def __init__(self):
        print("C.__init__ 被调用")
        A.__init__(self)   # 同样直接显式调用 A 的初始化
        self.c_value = 3

class D(B, C):
    def __init__(self):
        print("D.__init__ 被调用")
        B.__init__(self)   # 显式调用 B
        C.__init__(self)   # 显式调用 C，而 C 内部又会调用 A.__init__

d = D()
print("a_value =", d.a_value)
# 输出：
# D.__init__ 被调用
# B.__init__ 被调用
# A.__init__ 被调用
# C.__init__ 被调用
# A.__init__ 被调用
# a_value = 1
```

`A.__init__ 被调用` 出现了两次——一次经 B、一次经 C。如果 A 的 `__init__` 里有副作用（打开文件、申请资源、计数器自增），重复执行就会导致资源泄漏或状态错误。这就是菱形继承最典型的病灶。

**用协作式 super 修复：A 只被调用一次**

把每个类的 `__init__` 改成调用 `super().__init__()`，让调用沿 MRO 链传递，A 就只会被访问一次：

```python
class A:
    def __init__(self):
        print("A.__init__ 被调用")
        self.a_value = 1

class B(A):
    def __init__(self):
        print("B.__init__ 被调用")
        super().__init__()      # 不直接写 A.__init__，而是沿 MRO 往下传
        self.b_value = 2

class C(A):
    def __init__(self):
        print("C.__init__ 被调用")
        super().__init__()      # 沿 MRO 往下传
        self.c_value = 3

class D(B, C):
    def __init__(self):
        print("D.__init__ 被调用")
        super().__init__()      # 一个 super 就能把整条 MRO 走完
        self.d_value = 4

d = D()
print("a_value =", d.a_value, "| b_value =", d.b_value,
      "| c_value =", d.c_value, "| d_value =", d.d_value)
# 输出：
# D.__init__ 被调用
# B.__init__ 被调用
# C.__init__ 被调用
# A.__init__ 被调用
# a_value = 1 | b_value = 2 | c_value = 3 | d_value = 4
```

这一次 `A.__init__` 只出现一次，且 B、C、A 的初始化都被完整执行，四个属性齐全。关键在于：`super()` 不是"调用父类"，而是"调用 MRO 中的下一个类"——对于 D 而言，MRO 是 `[D, B, C, A, object]`，`D.super()` 指向 B，`B.super()` 指向 C（而非 B 的直接父类 A！），`C.super()` 指向 A，于是整条链顺序走完，A 自然只被访问一次。这是理解 Python 多继承的核心要点，第 4 章会展开算法细节。

### 2.3 `super()` 的真正语义：MRO 上的下一个类

很多初学者把 `super()` 理解为"调用父类的方法"，这种理解在单继承下勉强够用，但在多继承下是**错误**的。`super()` 实际上调用的是**当前实例的 MRO 链中、当前类之后的那个类**的对应方法。

```python
class Base:
    def who(self):
        return "Base"

class Mid(Base):
    def who(self):
        return "Mid -> " + super().who()

class Side(Base):
    def who(self):
        return "Side -> " + super().who()

class Final(Mid, Side):
    def who(self):
        return "Final -> " + super().who()

f = Final()
print(Final.__mro__)
print(f.who())
# 输出：
# (<class '...Final'>, <class '...Mid'>, <class '...Side'>, <class '...Base'>, <class 'object'>)
# Final -> Mid -> Side -> Base
```

注意 `Mid.who` 里的 `super().who()` 调用的不是 `Base.who`，而是 `Side.who`！这正是 MRO 的奇妙之处：`Final` 的 MRO 把 `Side` 排在了 `Mid` 之后、`Base` 之前，所以 `Mid` 里的 `super()` 跳到了 `Side` 而非 `Base`。如果你把 `super()` 当成"调父类"，这段行为完全无法理解；用"MRO 上的下一个类"来解读则一目了然。

**`super()` 的两种调用形式**

```python
class Parent:
    def __init__(self, value):
        self.value = value

class Child(Parent):
    def __init__(self, value, extra):
        # 形式一：Python 3 零参数 super()，隐式使用当前类和当前方法的第一参数
        super().__init__(value)
        # 形式二：显式写明，Python 2 也支持，等价于上面的写法
        # super(Child, self).__init__(value)
        self.extra = extra
```

Python 3 推荐零参数形式 `super().__init__(...)`，简洁且由解释器自动填入正确的类与实例。显式形式 `super(Child, self)` 在需要动态指定类（如某些元编程场景）时仍有用。

### 2.4 带参数的协作式 `__init__`

前面演示的 `super().__init__()` 都是无参的，但真实场景里不同基类的 `__init__` 往往需要不同参数。多继承下，协作式 super 如何把各自的参数传到位？这是一道经典难题。

**问题：参数对不齐**

```python
class A:
    def __init__(self, a):
        self.a = a

class B(A):
    def __init__(self, a, b):
        super().__init__(a)
        self.b = b

class C(A):
    def __init__(self, a, c):
        super().__init__(a)
        self.c = c

class D(B, C):
    def __init__(self, a, b, c):
        pass
        # B 要 (a,b)，C 要 (a,c)，参数签名不一致，super().__init__() 怎么传？
```

`D.__init__` 里的 `super().__init__(...)` 没法只传一组参数同时满足 B 和 C 的签名。解决这类问题有两种常见思路。

**思路一：统一签名，用 kwargs 传递**

让所有协作的 `__init__` 接受可变关键字参数 `**kwargs`，把不属于自己处理的参数继续沿 MRO 往下传：

```python
class A:
    def __init__(self, a=None, **kwargs):
        print(f"A 收到 a={a}")
        self.a = a

class B(A):
    def __init__(self, b=None, **kwargs):
        print(f"B 收到 b={b}")
        super().__init__(**kwargs)   # 把剩余参数（包括 a）继续传
        self.b = b

class C(A):
    def __init__(self, c=None, **kwargs):
        print(f"C 收到 c={c}")
        super().__init__(**kwargs)   # 把剩余参数（包括 a）继续传
        self.c = c

class D(B, C):
    def __init__(self, a=None, b=None, c=None):
        print(f"D 收到 a={a} b={b} c={c}")
        super().__init__(a=a, b=b, c=c)   # 全部打包成 kwargs 交给 MRO 链
        self.d = "D-self"

d = D(a=1, b=2, c=3)
print("d.a =", d.a, "| d.b =", d.b, "| d.c =", d.c, "| d.d =", d.d)
# 输出：
# D 收到 a=1 b=2 c=3
# B 收到 b=2
# C 收到 c=3
# A 收到 a=1
# d.a = 1 | d.b = 2 | d.c = 3 | d.d = D-self
```

每个类从 kwargs 里"摘走"自己关心的参数，其余通过 `super().__init__(**kwargs)` 往下传，直到最后一个类把残余参数消费掉。这种方式要求每个类都遵守"只取己所需、其余往下传"的协作约定，签名虽不统一但通过 kwargs 解耦。

**思路二：显式分派（不推荐，仅作对比）**

也可以在 `D.__init__` 里分别显式调用 B 和 C，但这又回到了非协作模式，A 会被多次初始化，且需要手动避免重复——本质上放弃了 super 的协作机制，一般只在无法统一协作时作为权宜之计，不作为常规做法。

### 2.5 普通方法在菱形结构中的协作

`__init__` 只是菱形问题的典型代表，普通方法同样需要协作。下面是一个 `save` 方法沿 MRO 协作传递的例子，每个类贡献一段逻辑：

```python
class BaseModel:
    def save(self):
        print("BaseModel: 写入数据库")

class TimestampMixin:
    def save(self):
        print("TimestampMixin: 记录更新时间")
        super().save()      # 继续沿 MRO 传递

class ValidateMixin:
    def save(self):
        print("ValidateMixin: 校验字段")
        super().save()      # 继续沿 MRO 传递

class Article(TimestampMixin, ValidateMixin, BaseModel):
    def save(self):
        print("Article: 准备保存")
        super().save()      # 交给 Mixin 链
        print("Article: 保存完成")

Article().save()
# 输出：
# Article: 准备保存
# TimestampMixin: 记录更新时间
# ValidateMixin: 校验字段
# BaseModel: 写入数据库
# Article: 保存完成
```

`Article` 的 MRO 是 `[Article, TimestampMixin, ValidateMixin, BaseModel, object]`，`save` 沿这条链一路传下去，每个 Mixin 都有机会插入自己的逻辑，最后由 `BaseModel` 兜底。这就是 Mixin 模式的精髓——功能像"插件"一样叠加在基类之上，且顺序由基类列表书写顺序决定（这里仅为演示顺序控制，实际业务里通常应先校验后保存，可调整 Mixin 顺序）。

### 2.6 Mixin 模式详解

Mixin（混入）是 Python 多继承最成熟、最受推荐的使用方式。它的核心思想是：把一个**小而专注的能力**封装成一个类，再通过多继承混入主类，主类组合多个 Mixin 即可获得多种正交能力。

**Mixin 的特征**

- 单一职责：一个 Mixin 只提供一维能力（如日志、序列化、比较、打印），不定义业务实体。
- 不独立实例化：Mixin 通常不单独使用，而是混入其他类。它本身往往没有完整的 `__init__` 或业务字段。
- 通过 super 协作：Mixin 的方法尽量用 `super()` 与链上其他类协作，保证能融入菱形调用链。

**示例：组合多个实用 Mixin**

```python
import json
from datetime import datetime

class LogMixin:
    """为任何对象添加日志能力"""
    def log(self, msg, level="INFO"):
        ts = datetime.now().strftime("%H:%M:%S")
        print(f"[{ts}] {level} {self.__class__.__name__}: {msg}")

class JsonMixin:
    """为对象添加 to_json 能力"""
    def to_json(self):
        return json.dumps(self.__dict__, ensure_ascii=False, sort_keys=True)

class ReprMixin:
    """为对象添加友好的 __repr__"""
    def __repr__(self):
        items = ", ".join(f"{k}={v!r}" for k, v in self.__dict__.items())
        return f"{self.__class__.__name__}({items})"

# 主类只关心业务字段，三种能力全都"混"进来
class Product(LogMixin, JsonMixin, ReprMixin):
    def __init__(self, name, price):
        self.name = name
        self.price = price

p = Product("机械键盘", 599.0)
p.log("商品上架")
print(p.to_json())
print(p)
# 输出：
# [HH:MM:SS] INFO Product: 商品上架
# {"name": "机械键盘", "price": 599.0}
# Product(name='机械键盘', price=599.0)
```

`Product` 类体里没有一行日志、序列化、repr 的代码，却同时拥有这三种能力——全部来自三个 Mixin。每个 Mixin 都可以独立复用到任何有 `__dict__` 的类上，彼此正交、互不干扰。

**ComparableMixin：实现比较协议**

手写 Mixin 有助于理解多继承如何配合协议方法。下面这个 Mixin 只要求子类实现 `_cmp_key`，就给对象加上大小比较能力：

```python
class ComparableMixin:
    """只要求子类实现 _cmp_key，即可获得全套大小比较"""
    def _cmp_key(self):
        raise NotImplementedError

    def __eq__(self, other):
        if not isinstance(other, ComparableMixin):
            return NotImplemented
        return self._cmp_key() == other._cmp_key()

    def __lt__(self, other):
        return self._cmp_key() < other._cmp_key()

class Student(ComparableMixin):
    def __init__(self, name, score):
        self.name = name
        self.score = score

    def _cmp_key(self):
        return self.score   # 按分数比较

a = Student("甲", 88)
b = Student("乙", 92)
print(a < b, a == Student("丙", 88), b > a)
# 输出：
# True True True
```

`ComparableMixin` 定义了 `__eq__` 和 `__lt__`，主类只需实现 `_cmp_key` 提供比较依据即可获得比较能力。现代 Python 更推荐用 `functools.total_ordering` 装饰器达到同样目的，但手写 Mixin 把"协议方法 + 协作"展示得更清楚。

### 2.7 多继承的复杂性风险

多继承并非全是好处，它带来的复杂性需要警惕。

**同名方法歧义**

当多个基类定义了同名方法但语义不同时，MRO 只会选中一个，另一个被静默遮蔽，容易产生难以察觉的 bug：

```python
class Drawable:
    def render(self):
        print("Drawable: 绘制图形")

class Reportable:
    def render(self):
        print("Reportable: 渲染报表为 PDF")

class Dashboard(Drawable, Reportable):
    """意图同时具备画图和出报表能力，但 render 同名被遮蔽"""
    pass

Dashboard().render()
# 输出：
# Drawable: 绘制图形
```

`Reportable.render` 被完全遮蔽，调用方根本感知不到。两个基类的 `render` 一个画图、一个出报表，本应取不同方法名（`draw` 与 `export_pdf`），强行同名反而丢失能力。多继承放大了命名冲突的影响——单继承下同名方法最多覆盖一层，多继承下则是整条 MRO 上所有同名方法相互竞争。

**状态组合困难**

多个基类各自维护状态（`__init__` 里的字段）时，如何安全地组合这些状态是真实的难题——上一节的"带参数协作式 init"已经展示了参数对齐的繁琐。当基类数量增多、字段交叉依赖时，协作式 init 的 kwargs 传递很容易写错，且难以静态检查。漏传一个参数，远端基类就拿不到需要的值，而报错往往要等到运行时才暴露。

**继承树过深**

多继承叠加多层 Mixin 后，MRO 会变得很长，调试一个方法调用需要沿整条 MRO 查找，可读性下降。一旦某层 Mixin 忘记调用 `super()`，链条就在那里中断，后续基类的方法被静默跳过，排查困难。这种"链式协作"的健壮性完全依赖于每一环都遵守约定，任何一环违约都会破坏整体行为。

### 2.8 何时用多继承，何时避免

多继承的适用与不适用场景应当有明确判断。

**适合多继承的场景**

- Mixin 复用：能力小而正交，混入主类即可使用（日志、序列化、比较、缓存等）。这是多继承的主流健康用法。
- 协议组合：需要同时满足多个协议（如同时可迭代、可比较、可哈希），用 Mixin 实现各协议比单继承更灵活。
- 框架扩展点：框架定义了若干可插拔 Mixin，业务按需混入，无需重写框架基类。

**应当避免多继承的场景**

- 多个基类各自有大量状态字段且彼此耦合：状态组合复杂性远超收益，这种情况下**组合优于继承**——把每个能力做成独立对象，主对象持有这些对象并委托调用。
- 多个基类是完整的业务实体而非小能力：继承多个"大父类"会让子类职责混乱，违背单一职责。
- 团队对 MRO 与 super 协作不熟悉：多继承的协作规则一旦被破坏（某个基类不调 super），bug 表现隐蔽。不熟悉的团队宜先单继承 + 组合，待机制熟悉后再引入 Mixin。

**组合优于继承的原则**

当能力之间需要复杂的状态交互时，"持有"比"继承"更稳健：

```python
# 不推荐：多继承叠加多个有状态基类，状态组合难维护
class UserWithCache(CacheBase, DbBase, AuthBase):
    ...

# 推荐：组合，每个能力是独立对象，职责清晰、可独立测试
class UserService:
    def __init__(self, cache, db, auth):
        self.cache = cache    # 持有，而非继承
        self.db = db
        self.auth = auth

    def get_user(self, uid):
        cached = self.cache.get(uid)
        if cached:
            return cached
        user = self.db.load(uid)
        self.cache.set(uid, user)
        return user
```

组合让每个能力的生命周期、测试、替换都独立可控，避免了多继承下 init 协作和 MRO 串联的复杂性。Mixin 用于"无状态或轻状态的横切能力"，组合用于"有状态的业务模块"——二者分工明确，比一刀切地用多继承健康得多。

### 2.9 基类顺序的重要性

基类列表的书写顺序直接影响 MRO，从而影响方法调用结果。这是一个需要在设计时就认真考虑的决策，不是随意排列。

**最左优先原则**

在 C3 能保证一致性的前提下，基类列表从左到右体现了"更优先/更具体"的意图。对于 Mixin，常见约定是**把 Mixin 写在主基类之前**：

```python
class Service(LogMixin, JsonMixin, BaseRepository):
    ...
```

这样 Mixin 的方法会先于 `BaseRepository` 被找到，可以覆盖或前置包装基类行为。如果把 `BaseRepository` 写在最左，Mixin 的同名方法会被基类遮蔽，混入就失去意义。

**换序即换行为**

下面这个例子直观展示基类顺序对结果的影响：

```python
class A:
    def who(self):
        return "A"

class B:
    def who(self):
        return "B"

class AB(A, B):
    pass

class BA(B, A):
    pass

print(AB().who(), "|", [c.__name__ for c in AB.__mro__])
print(BA().who(), "|", [c.__name__ for c in BA.__mro__])
# 输出：
# A | ['AB', 'A', 'B', 'object']
# B | ['BA', 'B', 'A', 'object']
```

`AB` 与 `BA` 的区别仅是基类顺序，`who` 的结果就由 A 变成 B。多继承下"顺序即优先级"，设计类层次时务必想清楚谁该排前。

**`super().__init__` 与 `super()` 在普通方法里的协作要点**

- 任何参与协作链的类，只要定义了与链上同名的方法，就应在该方法内调用 `super().方法()`，否则链条在此中断。
- `super()` 的目标由实例的 MRO 决定，与直接父类无必然关系。
- 不要假设 `super()` 一定调到"逻辑上的父类"——它调的是 MRO 下一个。

## 3. 最佳实践

### 3.1 用 Mixin 而非"大父类"做多继承

多继承的健康用法是混入小能力，不是叠加大实体。判断标准很简单：每个基类是否只提供一维能力、能否独立复用。

**推荐写法**

```python
class CacheMixin:
    """只管缓存读写，不管业务"""
    def get_cached(self, key):
        ...

class UserRepo(BaseRepo, CacheMixin):
    """主类继承单一业务基类，额外混入缓存能力"""
    ...
```

**不推荐写法**

```python
class UserRepo(UserLogic, CacheLogic, AuthLogic, NotifyLogic):
    """四个全是带状态的业务逻辑类，状态组合难以维护"""
    ...
```

前者主类只继承一个业务基类，其余是轻量 Mixin；后者把四个有状态逻辑类并列继承，init 协作和字段 ownership 都会失控。

### 3.2 所有参与协作的类都调 super

菱形协作链的健壮性依赖于"每一环都调 super"。只要有一层忘记，后续基类的方法就被静默跳过。

**推荐写法**

```python
class A:
    def do(self):
        print("A.do")

class B(A):
    def do(self):
        print("B.do")
        super().do()        # 一定要传下去

class C(A):
    def do(self):
        print("C.do")
        super().do()        # 一定要传下去

class D(B, C):
    def do(self):
        print("D.do")
        super().do()

D().do()
# 输出：
# D.do
# B.do
# C.do
# A.do
```

**不推荐写法**

```python
class C(A):
    def do(self):
        print("C.do")
        # 漏掉 super().do()，链条在此中断，A.do 永远不会被执行
```

漏掉一个 `super().do()`，`A.do` 就被跳过——这正是菱形协作的脆弱之处，也是"每个参与类都调 super"这条约定的价值所在。

### 3.3 统一协作方法的签名

协作链上同名方法的签名应保持兼容，否则 `super()` 传递参数时会出错。最实用的做法是统一接受 `**kwargs`，每层只摘取自己需要的参数。

**推荐写法**

```python
class Base:
    def configure(self, **kwargs):
        self.tag = kwargs.pop("tag", "default")

class MixA(Base):
    def configure(self, **kwargs):
        self.a_flag = kwargs.pop("a_flag", False)
        super().configure(**kwargs)   # 剩余参数往下传

class MixB(Base):
    def configure(self, **kwargs):
        self.b_level = kwargs.pop("b_level", 0)
        super().configure(**kwargs)

class Obj(MixA, MixB):
    def configure(self, **kwargs):
        super().configure(**kwargs)

o = Obj()
o.configure(tag="x", a_flag=True, b_level=3)
print(o.tag, o.a_flag, o.b_level)
# 输出：
# x True 3
```

每层用 `kwargs.pop` 取走自己的参数，剩余通过 `super().configure(**kwargs)` 下传。这样即便未来新增 Mixin，也只需在自己的 `configure` 里 pop 新参数，不影响既有链路。

**不推荐写法**

```python
class MixA(Base):
    def configure(self, a_flag):          # 固定参数，与 Base.configure(**kwargs) 不兼容
        self.a_flag = a_flag
        # super().configure() 无法把其他参数传下去
```

固定位置参数会让链上其他类的参数无从传递，协作链崩溃。多继承协作方法签名一律以 `**kwargs` 兜底为佳。

### 3.4 给基类定义顺序一个明确约定

团队层面应约定基类列表的排列规则，避免随意书写导致 MRO 不可预期。常见约定：

- **Mixin 在前，主基类在后**：`class X(LogMixin, CacheMixin, Base)`。保证 Mixin 优先覆盖、前置包装。
- **更具体的能力在前，更通用的在后**：具体业务 Mixin 排前，基础设施类排后。
- **只有一个"实体基类"**：主类应只有一个"真正的父类"承载业务，其余都是 Mixin。多于一个实体基类通常意味着设计有问题。

在 code review 时把基类顺序当作一个检查项，能有效减少 MRO 相关的隐微 bug。

### 3.5 用 `__mro__` 辅助调试

当方法调用结果与预期不符时，第一时间打印 `__mro__` 看实际查找顺序，往往能立刻定位问题：

```python
class A:
    def run(self): print("A.run")
class B(A):
    def run(self): print("B.run"); super().run()
class C(A):
    def run(self): print("C.run")    # 故意不调 super
class D(B, C):
    pass

print([c.__name__ for c in D.__mro__])
D().run()
# 输出：
# ['D', 'B', 'C', 'A', 'object']
# B.run
# C.run
```

看 MRO 是 `[D, B, C, A]`，`B.run` 调 super 跳到 `C.run`，但 `C.run` 没调 super 于是链条中断，`A.run` 不执行。MRO 一打印，断点位置一目了然——这是排查多继承问题的第一步。

### 3.6 避免在 Mixin 里定义重 `__init__`

Mixin 应尽量无状态或只持有与本能力直接相关的轻状态。如果一个 Mixin 需要复杂的 `__init__`（大量字段、外部依赖），说明它已经不再是"小能力"，更适合做成独立对象用组合持有。

**推荐写法**

```python
class PrintMixin:
    """无状态，只依赖 self.__dict__"""
    def pretty(self):
        return ", ".join(f"{k}={v}" for k, v in self.__dict__.items())
```

**不推荐写法**

```python
class DbMixin:
    def __init__(self, dsn, pool_size, timeout):
        self.conn = connect(dsn, pool_size, timeout)  # 重状态，应改为组合
```

`DbMixin` 这种带连接池、超时的重状态"伪 Mixin"做成 Mixin 会污染协作 init，应独立成 `Database` 对象由主类持有。

## 4. 原理

本章是理解 Python 多继承的关键。我们要讲清楚三件事：菱形结构为什么会引发 A 的重复访问与漏初始化、C3 线性化如何把菱形压平成一条无重复的 MRO、协作式 super 如何沿这条 MRO 传递使 A 的方法只执行一次、以及基类列表顺序如何通过 C3 影响最终 MRO。

### 4.1 菱形结构与"重复访问"的根源

菱形继承的本质是**共享祖先**：D 的两条继承路径（D→B→A 与 D→C→A）最终都会汇聚到 A。在没有线性化机制的朴素模型里，对 A 的访问会沿两条路径各走一次，造成重复。

**朴素的深度优先遍历及其问题**

旧式类（Python 2 的经典类，不继承 object）采用的就是朴素的深度优先、从左至右遍历：对 `D(B, C)`，先深度遍历 B 的祖先链 `D→B→A`，再深度遍历 C 的祖先链 `D→C→A`。但 A 已经在第一条链中出现过，于是结果就是 `D B A C`——A 排在 C 之前，C 的方法反而晚于 A 被查找，这破坏了"子类先于父类"的基本约束，也会导致 A 被重复访问。

**新式类的 C3 线性化**

新式类（Python 3 所有类均为新式，默认继承 object）改用 C3 线性化算法。C3 的核心目标有三：

1. 单调性：子类先于父类。
2. 基类列表顺序保持：写 `class D(B, C)` 则 B 先于 C。
3. 无重复：每个类在 MRO 中只出现一次。

这三条合起来，就能把菱形结构压平成一条满足所有约束的线性序列。

### 4.2 C3 线性化算法详解

C3 算法的输入是一个类的基类列表 `(B1, B2, ..., Bn)`，输出是一条线性序列 L[C]。算法用"合并"（merge）操作把多条已计算的子 MRO 合成一条。

**记号与定义**

- `L[C]` 表示类 C 的线性化（MRO）。
- `C + [B1, B2, ..., Bn]` 表示 C 的线性化由 C 本身打头，后接其基类列表。
- `merge(L[B1], L[B2], ..., L[Bn], [B1, B2, ..., Bn])` 是核心合并操作。

**线性化公式**

```
L[C] = C + merge(L[B1], L[B2], ..., L[Bn], [B1, B2, ..., Bn])
```

其中 `C +` 表示把 C 放在结果最前；`merge` 负责把后续部分按规则拼出来。

**merge 的规则**

`merge` 接收若干个列表，对每个列表取其**头部**（第一个元素），判断该头部是否在其它列表的**尾部**（除第一个外的其余部分）中出现：

- 若某列表的头部不在任何其它列表的尾部出现，则它是"好头部"，把它从所有列表头部移除并追加到结果。
- 若所有列表的当前头部都出现在某个列表的尾部，则无法选出好头部，合并失败，抛 `TypeError`（MRO 不一致）。
- 重复上述过程，直到所有列表为空。

**用菱形 D(B, C), B(A), C(A), A(object) 走一遍 C3**

设继承图：`A(object)`，`B(A)`，`C(A)`，`D(B, C)`。逐个计算线性化。

第一步，计算叶子类的线性化：

```
L[object] = [object]
L[A] = A + merge(L[object], [object]) = [A, object]
```

第二步，计算 B 和 C：

```
L[B] = B + merge(L[A], [A]) = B + merge([A, object], [A])
    取 A：A 在第二个列表的头部，取走，得 [A, object]
    = [B, A, object]

L[C] = C + merge(L[A], [A]) = [C, A, object]
```

第三步，计算 D：

```
L[D] = D + merge(L[B], L[C], [B, C])
     = D + merge([B, A, object], [C, A, object], [B, C])
```

按 merge 规则一步步选头部：

- 看 `[B, A, object]` 的头 B：B 是否出现在其它列表的尾部？第二个列表 `[C, A, object]` 的尾部是 `[A, object]`，没有 B；第三个列表 `[B, C]` 的尾部是 `[C]`，没有 B。B 是好头部，取走 B。
  - 结果暂为 `[D, B]`，merge 剩 `[A, object]`、`[C, A, object]`、`[C]`。
- 看 `[A, object]` 的头 A：A 是否出现在其它列表尾部？第二个列表 `[C, A, object]` 的尾部是 `[A, object]`，**包含 A**！所以 A 不是好头部，跳过。
- 看 `[C, A, object]` 的头 C：C 是否出现在其它列表尾部？第一个列表尾部 `[object]` 没有 C；第三个列表 `[C]` 的尾部是空，没有 C。C 是好头部，取走 C。
  - 结果暂为 `[D, B, C]`，merge 剩 `[A, object]`、`[A, object]`、`[]`。
- 看 `[A, object]` 的头 A：现在其它非空列表也是 `[A, object]`，尾部都是 `[object]`，没有 A。A 是好头部，取走 A。
  - 结果暂为 `[D, B, C, A]`，merge 剩 `[object]`、`[object]`、`[]`。
- 取 object，结果为 `[D, B, C, A, object]`。

最终：

```
L[D] = [D, B, C, A, object]
```

这正是 `D.__mro__` 的实际值。可以看到 A 只出现一次，且排在 B、C 之后——C3 通过 merge 规则把"先沿 B 深度到 A"的朴素路径修正为"先走完同级基类 C 再上到 A"，避免了 A 的提前重复访问。

**MRO 不一致时的失败**

如果把前例的 `Z(X, Y)` 与 `W(Y, X, Z)` 放在一起：`Z` 要求 X 在 Y 前，`W` 的基类列表又要求 Y 在 X 前，两条约束冲突，merge 在某一步找不到好头部，于是抛 `TypeError: Cannot create a consistent method resolution order`。C3 宁可报错也不给出自相矛盾的顺序，这是它对多继承安全性的根本保障。

### 4.3 协作式 super 沿 MRO 传递的机制

理解了 MRO，super 的行为就清楚了。`super()` 返回一个**代理对象**，该对象的方法调用会跳到"实例 MRO 中、当前类之后"的那个类的方法上。

**super 的两个隐藏参数**

零参数 `super()` 在方法内部被调用时，解释器自动填入两个值：

- `__class__`：当前方法所属的类（编译期确定，不是 `self.__class__`）。
- `self`：当前方法的第一个参数（实例）。

`super().__init__()` 等价于 `super(__class__, self).__init__()`。关键是它用 `self.__class__.__mro__` 来确定查找链，而起点是 `__class__` 在这条 MRO 中的位置——从该位置的**下一个**类开始查找。

**为什么 B.super() 跳到 C 而不是 A**

以菱形 D(B, C) 为例，`self.__class__` 是 D，`self.__class__.__mro__` 是 `[D, B, C, A, object]`。在 `B.__init__` 里调 `super().__init__()`：

- `__class__` 是 B（方法定义在 B 里）。
- 在 MRO `[D, B, C, A, object]` 中找到 B 的位置是索引 1。
- 从索引 2 开始查找 `__init__`，索引 2 是 C。

于是 `B.super().__init__()` 跳到 `C.__init__`，而不是 B 的直接父类 A。这正是"MRO 上的下一个类"而非"直接父类"的体现。

**完整调用链**

D 的 `__init__` 被调用时，沿 MRO 的传递过程如下：

```
D.__init__  (MRO 起点 D)
  -> super().__init__()  跳到 B
B.__init__
  -> super().__init__()  跳到 C
C.__init__
  -> super().__init__()  跳到 A
A.__init__
  -> super().__init__()  跳到 object
object.__init__  (通常无操作)
```

A 在整条链中只出现一次，因此 `A.__init__` 只执行一次。这就是"协作式 super 使基类方法只执行一次"的底层机制——它不是某种特殊去重，而是 MRO 本身把 A 压成单一节点、super 严格沿此单一节点链传递的自然结果。

**不协作时的两种病态**

若链上某类不用 super 而直接调 `A.__init__(self)`（如 2.2 的反例），调用链就脱离了 MRO，A 被从多条显式路径各访问一次，出现重复初始化。若某类既不调 super 也不显式调父类，链条在此中断，后续基类（包括 A）被漏初始化。两种病态都源于"不沿 MRO 协作"。

### 4.4 基类列表顺序如何通过 C3 影响结果

C3 的 merge 输入包含"基类列表 `[B1, ..., Bn]`"本身，因此书写顺序直接影响 merge 的选头过程，从而影响最终 MRO。

**对比 `D(B, C)` 与 `D(C, B)`**

- `D(B, C)` 的 merge 优先选 B（B 在列表头部且不在其它尾部），得 `[D, B, C, A, object]`。
- `D(C, B)` 的 merge 优先选 C，得 `[D, C, B, A, object]`。

两者都是合法 C3 顺序，但 B 与 C 的先后对调。于是 `super()` 链的传递顺序、同名方法的选中结果都会随之改变。这就是"基类顺序即优先级"的算法根源——C3 在保证约束的前提下，忠实地保留了书写顺序的优先级意图。

**为什么顺序冲突会报错**

当 `Z(X, Y)` 设定了"X 先于 Y"的约束，而 `W(Y, X, Z)` 又把 Y 排在 X 前，merge 在处理 W 时会同时面对"X 先于 Y"（来自 Z 的 MRO 尾部约束）和"Y 先于 X"（来自 W 的基类列表）两条矛盾，任何头部都无法成为好头部，merge 失败抛错。这种"宁可报错也不接受矛盾顺序"的设计，是多继承安全的最后一道防线。

### 4.5 旧式类深度优先 vs 新式类 C3 广度混合

Python 2 的旧式类（不继承 object）采用朴素深度优先：对 `D(B, C)`、`B(A)`、`C(A)`，遍历得 `D B A C`，A 排在 C 前面，导致 C 的方法可能被 A 遮蔽、A 被重复访问。Python 3 全部为新式类（默认继承 object），一律采用 C3，结果为 `D B C A object`，A 被正确地排到 B、C 之后且只出现一次。

这一变更从算法层面根治了旧式菱形的问题。Python 3 开发者无需再为旧式/新式的差异分心，但理解这段历史有助于读懂早期多继承资料里"深度优先"与"广度优先"的讨论——所谓"C3 广度混合"，指的就是 merge 在同级基类之间横向选取（先走完 B、C 同级再上到 A），而非一味纵深到底。

## 5. 总结

### 5.1 本文内容要点

- 多继承允许一个子类同时继承多个基类，语法 `class C(A, B):`，价值在于能力组合。
- 方法解析顺序（MRO）由 C3 线性化算法计算，存放于 `__mro__`，决定同名方法选中谁。
- 菱形继承是共享祖先的结构（D 经 B、C 共同继承 A），朴素访问会让 A 被多次初始化或漏初始化。
- `super()` 的真正语义是"调 MRO 上的下一个类"，而非"调父类"；它依赖实例 `__class__.__mro__` 与当前类在其中的位置。
- 协作式 super 沿 MRO 单链传递，使共享祖先 A 的方法只执行一次；任一层不协作则会重复或中断。
- 带参数的协作 init 用 `**kwargs` 逐层摘取、剩余下传的方式解耦签名。
- Mixin 模式是多继承的健康用法：小而正交的能力混入主类，主类只继承一个实体基类。
- 多继承的复杂性风险包括同名方法遮蔽、状态组合困难、协作链断裂；有状态业务模块宜用组合而非继承。
- 基类列表书写顺序经 C3 直接影响 MRO，是"顺序即优先级"的设计决策；顺序矛盾时 C3 报错保护。
- C3 算法通过 merge 在同级基类间横向选取，把菱形压平为无重复线性链，取代了旧式类的朴素深度优先。

### 5.2 读完应能掌握

- 能画出 `D(B, C), B(A), C(A)` 的菱形结构，并用 `__mro__` 验证其线性化为 `[D, B, C, A, object]`。
- 能用协作式 `super().__init__()` 编写菱形继承，使 A 的初始化只执行一次，并能解释 B.super() 为何跳到 C。
- 能识别"不协作"代码导致的 A 多次初始化或漏初始化，并改写为协作式。
- 能用 `**kwargs` 编写带不同参数的协作式 init，使各基类各取所需、剩余下传。
- 能设计 LogMixin、JsonMixin 等横切能力并正确混入主类，避免有状态的"伪 Mixin"。
- 能判断何时用多继承（Mixin 复用）、何时用组合（有状态业务模块），并说明理由。
- 能用 C3 merge 规则手工推导简单菱形的 MRO，并能解释基类顺序改变时 MRO 如何随之变化。
- 能用 `__mro__` 打印实际查找顺序来排查协作链断裂、方法遮蔽等多继承问题。
