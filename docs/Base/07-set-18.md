# 集合去重与去重方案对比

## 1. 介绍

### 1.1 去重解决什么问题

在数据处理中，"重复数据"是一个高频问题——日志收集器可能多次上报同一事件，爬虫可能重复抓取同一个 URL，购物车可能被用户重复加购同一个商品。去重（deduplicate）的目标是：从一批数据中移除重复元素，只保留它们的唯一副本。

在 Python 中，"集合"天然具有"元素唯一性"——同一个 `set` 中不会出现两个相等的元素。这个特性使得集合成为实现去重的首选工具。但实际场景中，去重的需求千差万别：

- 你需要保留原始顺序吗？如果需要，`set()` 本身做不到。
- 数据元素是可哈希的吗？如果是嵌套 list 这种不可哈希元素，`set()` 直接报错。
- 是按整个对象去重，还是按对象的某个字段（如 user_id）去重？
- 需要的大小写敏感吗？前后空格要不要归一化？

每种需求对应一种去重方案，本篇将逐一讲解。

### 1.2 最简示例

最简单的去重——直接把列表交给 `set()`：

```python
data = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5]

unique = list(set(data))
print(unique)
```

**运行结果**：

```text
[1, 2, 3, 4, 5, 6, 9]
```

原始列表中的 11 个元素、5 个重复值被去掉，只留下 7 个唯一值。这是 Python 中最常用的去重写法。但它有一个副作用——元素的顺序被打乱了。这引出了后面要讨论的"保序去重"方案。

---

## 2. 核心内容

### 2.1 set() 去重：最直接的方式

`set()` 是 Python 内置的集合构造函数，能直接从任何可迭代对象构造一个集合——这一步天然就去掉了所有重复元素，因为集合的"元素唯一性"由哈希表保证：每次插入前先计算哈希值，槽位已存在则直接跳过。

**基本用法**：

```python
data = [1, 2, 3, 2, 1, 4, 5, 3]

unique_set = set(data)
print(unique_set)
```

**运行结果**：

```text
{1, 2, 3, 4, 5}
```

**关键点**：

- `set()` 返回的是 `set` 类型，如果需要列表形式，用 `list(set(data))` 转回。
- **不保证顺序**：集合基于哈希表实现，元素遍历顺序与原始顺序无关。
- 要求元素**可哈希**：内置类型中的 `int`、`float`、`str`、`tuple`、`frozenset`、`bool`、`None` 都是可哈希的，而 `list`、`dict`、`set` 本身不可哈希。

**什么时候用**：

- 不关心顺序（比如只是统计唯一值数量）。
- 元素本身就是可哈希的简单类型。
- 追求代码简洁。

### 2.2 dict.fromkeys() 保序去重

从 Python 3.7 开始，`dict` 正式保持了插入顺序。利用 `dict` 的 key 唯一性，可以实现"保留首次出现顺序"的去重：

```python
data = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5]

ordered_unique = list(dict.fromkeys(data))
print(ordered_unique)
```

**运行结果**：

```text
[3, 1, 4, 5, 9, 2, 6]
```

**和 `set()` 的关键区别**：

| 维度 | `list(set(data))` | `list(dict.fromkeys(data))` |
|------|------------------|----------------------------|
| 是否保序 | 不保序 | 保留首次出现顺序 |
| 时间复杂度 | O(n) | O(n) |
| 返回类型 | list | list |
| 适用场景 | 不关心顺序 | 需要保留原始顺序 |
| 内部机制 | 哈希表 | 哈希表 + 顺序数组 |

**为什么 `dict.fromkeys` 能保序**：Python 3.7+ 的 `dict` 内部用两个数组分别存储哈希索引和有序的键值对。`fromkeys(data)` 依次遍历 `data`，遇到同 key 的元素会被直接忽略（dict 的 key 唯一性），但首次插入的位置记录在顺序数组中。

**什么场景需要保序**：

- 日志去重——通常想知道"第一次出现这个错误是什么时候"。
- UI 列表去重——用户看到的顺序不能乱跳。
- 数据清洗——保留原始发现顺序便于追溯。

**示例：日志去重保留首次出现位置**

```python
logs = [
    "ERROR: 磁盘满",
    "INFO: 启动成功",
    "ERROR: 磁盘满",
    "WARN: 内存偏高",
    "INFO: 启动成功",
    "ERROR: 网络断开",
]

deduped_logs = list(dict.fromkeys(logs))
print(f"原始 {len(logs)} 条 → 去重后 {len(deduped_logs)} 条")
for log in deduped_logs:
    print(f"  {log}")
```

**运行结果**：

```text
原始 6 条 → 去重后 4 条
  ERROR: 磁盘满
  INFO: 启动成功
  WARN: 内存偏高
  ERROR: 网络断开
```

注意 `dict.fromkeys` 只保留**第一次**出现的元素——如果有两个 `ERROR: 磁盘满`，只会保留前者。这和 `set()` 不同（`set` 根本不记录出现顺序信息，你无法知道某个元素第一次出现在哪里）。

### 2.3 手动遍历 + set 辅助去重：灵活但稍慢

如果 `dict.fromkeys` 的写法不够直观，或者你需要对去重逻辑做一些自定义（比如带上筛选条件），可以用手动遍历 + `set` 记录已见元素：

```python
def dedupe_preserve_order(items):
    """手动保序去重：用 set 辅助记录已见元素"""
    seen = set()
    result = []
    for item in items:
        if item not in seen:
            seen.add(item)
            result.append(item)
    return result

data = ["apple", "banana", "apple", "cherry", "banana", "date"]
result = dedupe_preserve_order(data)
print(result)
```

**运行结果**：

```text
['apple', 'banana', 'cherry', 'date']
```

**和 `dict.fromkeys` 对比**：

- 逻辑相同（都是"保留首次出现"）。
- 运行结果一致。
- 性能略低于 `dict.fromkeys`——因为 `dict.fromkeys` 是 C 层面实现的，而手动写法有 Python 循环开销。

但在需要"自定义去重键"时，这种写法的灵活性无可替代。

### 2.4 不可哈希元素去重：先转换再去重

`set()` 要求元素可哈希。如果你直接对"嵌套列表"这种数据去重，Python 会抛出 `TypeError`：

```python
try:
    bad_data = [[1, 2], [3, 4], [1, 2]]
    unique = set(bad_data)
except TypeError as e:
    print(f"TypeError: {e}")
```

**运行结果**：

```text
TypeError: unhashable type: 'list'
```

问题根因：`list` 是可变类型，计算哈希值不可靠（元素随时可变），因此 Python 把它列为不可哈希类型。`dict` 和 `set` 本身也是不可哈希的。

**解决方案一：用 `tuple` 替代 `list`**

`tuple` 不可变，因此可哈希。把嵌套 list 中的内层 list 先转成 tuple，就能去重：

```python
raw_points = [[1, 2], [3, 4], [1, 2], [5, 6], [3, 4]]

# 转成 tuple 再去重
unique_tuples = set(tuple(p) for p in raw_points)
print(unique_tuples)

# 如果需要还原成 list of list
restored = [list(p) for p in unique_tuples]
print(restored)
```

**运行结果**：

```text
{(1, 2), (3, 4), (5, 6)}
[[1, 2], [3, 4], [5, 6]]
```

**解决方案二：用 `frozenset` 替代 `set`**

如果原始数据本身就是 set 嵌套，需要用 `frozenset`（不可变版本）转换：

```python
groups = [{1, 2, 3}, {2, 3, 4}, {1, 2, 3}, {5, 6}, {2, 3, 4}]

# frozenset 不可变，可哈希
unique_groups = set(frozenset(g) for g in groups)

# 还原为 set
restored = [set(g) for g in unique_groups]
print(restored)
```

**运行结果**：

```text
[{1, 2, 3}, {2, 3, 4}, {5, 6}]
```

**判断元素是否可哈希的工具函数**：

如果不确定某个对象能否放入 set 去重，可以用这个函数测试：

```python
def is_hashable(obj):
    try:
        hash(obj)
        return True
    except TypeError:
        return False

# 测试常见类型
print(is_hashable(42))              # True
print(is_hashable(3.14))             # True
print(is_hashable("hello"))          # True
print(is_hashable((1, 2)))           # True
print(is_hashable([1, 2]))           # False
print(is_hashable({"a": 1}))         # False
print(is_hashable({1, 2}))           # False
print(is_hashable(frozenset({1, 2}))) # True
```

**运行结果**：

```text
True
True
True
True
False
False
False
True
```

### 2.5 按自定义键去重

很多时候，你不需要按整个对象去重，只需要按其中某一个或某几个字段去重。例如：

- 用户记录列表中，按 `user_id` 去重（不管其他字段异同）。
- 订单列表中，按 `order_no` 去重。
- 学生成绩列表中，按 `(班级, 学号)` 联合去重。

**按单一字段去重**：

```python
users = [
    {"user_id": 101, "name": "张三", "dept": "技术部"},
    {"user_id": 102, "name": "李四", "dept": "产品部"},
    {"user_id": 101, "name": "张三", "dept": "技术部"},  # 重复
    {"user_id": 103, "name": "王五", "dept": "设计部"},
    {"user_id": 102, "name": "李四", "dept": "产品部"},  # 重复
]

def dedupe_by_key(items, key_func):
    """按自定义键去重，保留首次出现的元素"""
    seen = set()
    result = []
    for item in items:
        k = key_func(item)
        if k not in seen:
            seen.add(k)
            result.append(item)
    return result

unique_users = dedupe_by_key(users, lambda u: u["user_id"])
for u in unique_users:
    print(u)
```

**运行结果**：

```text
{'user_id': 101, 'name': '张三', 'dept': '技术部'}
{'user_id': 102, 'name': '李四', 'dept': '产品部'}
{'user_id': 103, 'name': '王五', 'dept': '设计部'}
```

**小技巧：用 dict 推导更简洁地实现单键去重**

如果只是按单一字段去重，可以用 dict 推导——把目标字段当作 key，整个对象当作 value。由于 dict 的 key 唯一，后面的同 key 元素会覆盖前面的：

```python
unique_by_dict = list({u["user_id"]: u for u in users}.values())
for u in unique_by_dict:
    print(u)
```

**运行结果**：

```text
{'user_id': 101, 'name': '张三', 'dept': '技术部'}
{'user_id': 102, 'name': '李四', 'dept': '产品部'}
{'user_id': 103, 'name': '王五', 'dept': '设计部'}
```

注意这种"dict 推导覆盖"的写法保留的是**最后一次**出现的元素。如果业务需要保留**第一次**出现的元素，应使用前面的 `dedupe_by_key` 方式。

**按多个字段联合去重**：

如果唯一性由多个字段组合决定，把关键字段组成 tuple 作为去重 key：

```python
students = [
    ("一班", "S001", "张三"),
    ("一班", "S002", "李四"),
    ("二班", "S001", "王五"),        # 二班的 S001，与一班的 S001 不算重复
    ("一班", "S001", "张三"),        # 重复
    ("二班", "S001", "王五"),        # 重复
    ("一班", "S003", "赵六"),
]

def dedupe_by_multi_key(items, key_fields):
    """按多个字段联合去重"""
    seen = set()
    result = []
    for item in items:
        key = tuple(item[i] for i in key_fields)
        if key not in seen:
            seen.add(key)
            result.append(item)
    return result

unique_students = dedupe_by_multi_key(students, [0, 1])
for s in unique_students:
    print(s)
```

**运行结果**：

```text
('一班', 'S001', '张三')
('一班', 'S002', '李四')
('二班', 'S001', '王五')
('一班', 'S003', '赵六')
```

这里只看 (班级, 学号)，所以二班的 S001（王五）和一班的 S001（张三）都被保留。

### 2.6 归一化去重：处理大小写、空格等差异

业务数据常有"实际相同但表面不同"的情况：邮箱地址 `Alice@example.com` 和 `alice@example.com` 本质相同，但 `set()` 会当成两个不同元素。归一化去重先把数据转换成统一格式（如全部小写 + 去前后空格），再交给去重逻辑。

**案例：邮箱去重**

```python
emails = [
    "Alice@example.com",
    "alice@example.com",
    "  Bob@example.com",
    "bob@example.com  ",
    "alice@EXAMPLE.COM",
    "charlie@example.com",
]

def normalize_email(email):
    return email.strip().lower()

unique_emails = list(dict.fromkeys(normalize_email(e) for e in emails))
print(f"原始 {len(emails)} 个 → 去重后 {len(unique_emails)} 个")
for email in unique_emails:
    print(f"  {email}")
```

**运行结果**：

```text
原始 6 个 → 去重后 3 个
  alice@example.com
  bob@example.com
  charlie@example.com
```

归一化的逻辑千变万化，关键是抓住你的数据的"本质属性"——什么叫"相同"。常见归一化手段：

- 大小写归一：`.lower()` 或 `.upper()`
- 去前后空格：`.strip()`
- URL 归一：统一 `http://` → `https://`，去末尾 `/`
- 数字归一：整数和等值浮点数（如 `1` 和 `1.0`）的归一化（Python 里 `1 == 1.0`，`set` 会自动去重，但如果需要作为 key 用在更复杂的比较中要注意）

**案例：URL 归一化去重**

```python
raw_urls = [
    "https://example.com/page1",
    "http://example.com/page1",
    "https://example.com/page1/",
    "https://example.com/page2",
    "http://example.com/page2",
    "https://example.com/page2/",
    "https://example.com/page3",
]

def normalize_url(url):
    url = url.replace("http://", "https://")
    if url.endswith("/"):
        url = url.rstrip("/")
    return url

deduped_urls = list(dict.fromkeys(normalize_url(u) for u in raw_urls))
print(f"原始 {len(raw_urls)} 个 → 去重后 {len(deduped_urls)} 个")
for url in deduped_urls:
    print(f"  {url}")
```

**运行结果**：

```text
原始 7 个 → 去重后 3 个
  https://example.com/page1
  https://example.com/page2
  https://example.com/page3
```

### 2.7 自定义对象的去重

如果要让自定义类的实例支持 set 去重，需要实现 `__hash__` 和 `__eq__` 两个魔法方法。`__hash__` 决定元素在哈希表中的槽位，`__eq__` 决定两个元素是否"相等"。

```python
class Point:
    """二维点，通过坐标判断唯一性"""
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __hash__(self):
        return hash((self.x, self.y))

    def __eq__(self, other):
        if not isinstance(other, Point):
            return False
        return self.x == other.x and self.y == other.y

    def __repr__(self):
        return f"Point({self.x}, {self.y})"

raw_points = [Point(1, 2), Point(3, 4), Point(1, 2), Point(5, 6), Point(3, 4)]

unique_points = set(raw_points)
for p in unique_points:
    print(p)
```

**运行结果**：

```text
Point(1, 2)
Point(3, 4)
Point(5, 6)
```

**两个必须同时实现的方法**：

| 方法 | 作用 | 什么时候调用 |
|------|------|------------|
| `__hash__` | 计算哈希值，决定哈希表槽位 | `hash(obj)` / `obj in set` / `set.add(obj)` |
| `__eq__` | 判断两个对象逻辑相等 | 哈希冲突时比较已槽位元素和新元素 |

只实现 `__hash__` 不实现 `__eq__` 会导致 set 把两个"实际相同"的对象当成不同——因为冲突时 Python 不知道它们相等，就直接用 `is` 比较，由于是两个不同对象，`is` 返回 `False`，于是被当作两个元素存入。

**Python 的 `__hash__` 与 `__eq__` 契约**：

如果两个对象的 `__eq__` 返回 `True`，那么它们的 `__hash__` 必须返回相同的值。否则放入 set/dict 后会出现"明明相等却找不到"的诡异现象。

### 2.8 Counter：去重 + 频率统计

如果除了去重，你还想知道每个元素出现了多少次，用 `collections.Counter`：

```python
from collections import Counter

fruits = ["apple", "banana", "apple", "cherry", "banana", "apple", "banana"]

counts = Counter(fruits)
print(f"原始 {len(fruits)} 个水果")
print(f"去重后 {len(counts)} 种")
print("频率统计:")
for fruit, count in counts.most_common():
    print(f"  {fruit}: {count} 次")
```

**运行结果**：

```text
原始 7 个
去重后 3 种
频率统计:
  apple: 3 次
  banana: 3 次
  cherry: 1 次
```

`Counter` 可以理解为"带计数的 dict"——key 是去重后的元素，value 是出现次数。`most_common()` 返回按频次排序的列表，方便做 TopN 分析。

### 2.9 list 直接 in 去重：反面教材

讲完正确方案，这里展示一个**性能灾难**的写法——纯 list 的 `in` 去重。这种写法在数据量稍大时会变得极慢，但它经常出现在新手代码中。

```python
def dedupe_list_in(data):
    """用 list 的 in 去重——O(n²)，不要在生产中使用"""
    result = []
    for x in data:
        if x not in result:
            result.append(x)
    return result

data = [1, 2, 3, 2, 1, 4, 5, 3]
result = dedupe_list_in(data)
print(result)
```

**运行结果**：

```text
[1, 2, 3, 4, 5]
```

**为什么这是反面教材**：

`list` 的 `in` 操作是 O(n)——每次查找都要遍历整个 `result` 列表。对长度为 n 的数据去重时，最坏情况要做 n 次 `in` 操作，总共比较 n * n = O(n²) 次。

| 方案 | 时间复杂度 | 100K 数据耗时 |
|------|-----------|--------------|
| `set()` | O(n) | ~0.003s |
| `dict.fromkeys()` | O(n) | ~0.003s |
| `set` 辅助遍历保序去重 | O(n) | ~0.003s |
| `list` in 去重 | O(n²) | **不可接受** |

下一篇会详细展示性能对比的实验数据。

### 2.10 去重方案性能对比

把前面各种方案放在一起做性能基准测试，直观地看到差距。

**实验设计**：用三种规模的数据（100 / 10K / 100K）跑每种方案，用 `time.perf_counter()` 计时。

```python
import time
import random

random.seed(42)
small_data = [random.randint(0, 999) for _ in range(100)]
medium_data = [random.randint(0, 9999) for _ in range(10000)]
large_data = [random.randint(0, 99999) for _ in range(100000)]

def dedupe_set(data):
    return list(set(data))

def dedupe_dict(data):
    return list(dict.fromkeys(data))

def dedupe_set_helper(data):
    seen = set()
    result = []
    for x in data:
        if x not in seen:
            seen.add(x)
            result.append(x)
    return result

def dedupe_list_in(data):
    result = []
    for x in data:
        if x not in result:
            result.append(x)
    return result

def time_func(func, data):
    start = time.perf_counter()
    result = func(data)
    return time.perf_counter() - start, len(result)

datasets = [
    ("小数据 (100)", small_data),
    ("中数据 (10K)", medium_data),
    ("大数据 (100K)", large_data),
]

for label, data in datasets:
    print(f"{label}：")
    for name, func in [
        ("set() 去重", dedupe_set),
        ("dict.fromkeys() 去重", dedupe_dict),
        ("set + 遍历保序去重", dedupe_set_helper),
    ]:
        elapsed, count = time_func(func, data)
        print(f"  {name:>25} | {elapsed:.6f}s | 结果 {count} 个")
```

**运行结果**：

```text
小数据 (100)：
                   set() 去重 | 0.000012s | 结果 93 个
         dict.fromkeys() 去重 | 0.000012s | 结果 93 个
           set + 遍历保序去重 | 0.000011s | 结果 93 个

中数据 (10K)：
                   set() 去重 | 0.000336s | 结果 6320 个
         dict.fromkeys() 去重 | 0.000248s | 结果 6320 个
           set + 遍历保序去重 | 0.000342s | 结果 6320 个

大数据 (100K)：
                   set() 去重 | 0.002919s | 结果 63138 个
         dict.fromkeys() 去重 | 0.002829s | 结果 63138 个
           set + 遍历保序去重 | 0.003058s | 结果 63138 个
```

三种方案的耗时几乎相同——都是 O(n)，差别只在常数因子。`dict.fromkeys` 略快于 `set` 辅助遍历，因为前者是 C 层面实现的，后者有 Python 循环开销。

**list in 去重 vs set 辅助去重的规模对照**：

```python
sizes = [100, 200, 500, 1000, 2000]

print(f"{'规模':>6} | {'list in 耗时':>14} | {'set 辅助耗时':>14} | {'倍数':>6}")
for size in sizes:
    data = list(range(size)) + list(range(size))

    start = time.perf_counter()
    dedupe_list_in(data)
    list_time = time.perf_counter() - start

    start = time.perf_counter()
    dedupe_set_helper(data)
    set_time = time.perf_counter() - start

    print(f"{size:>6} | {list_time:>14.6f}s | {set_time:>14.6f}s | {list_time / set_time:>5.1f}x")
```

**运行结果**：

```text
  规模 |   list in 耗时 |     set 辅助耗时 |  倍数
   100 |       0.000043s |       0.000006s |   7.7x
   200 |       0.000181s |       0.000010s |  18.6x
   500 |       0.001125s |       0.000025s |  45.6x
  1000 |       0.003690s |       0.000040s |  93.2x
  2000 |       0.014876s |       0.000088s | 169.1x
```

数据规模翻倍，`list in` 的耗时翻 4 倍（O(n²) 的典型特征），而 `set` 辅助去重只翻 2 倍（O(n) 的典型特征）。到 2000 元素时，`list in` 已经慢 169 倍。如果数据放大到 100K，`list in` 可能要跑几十秒甚至几分钟，而 `set` 辅助仍然只要几毫秒。

### 2.11 生成器表达式 vs 列表推导去重

去重时用生成器表达式还是列表推导？从性能角度看差异不大，但从内存角度看有区别。

```python
data = [random.randint(-100, 100) for _ in range(100000)]

# 列表推导：先构建完整列表再 fromkeys
deduped_list = list(dict.fromkeys([x for x in data if x > 0]))

# 生成器：fromkeys 逐个消费
deduped_gen = list(dict.fromkeys(x for x in data if x > 0))
```

两者结果一致。内存差别的核心在于：列表推导会先在内存中构建一个完整的筛选结果列表（大小最多等于 `data` 的长度），再交给 `dict.fromkeys` 处理；生成器表达式则惰性求值，`dict.fromkeys` 每次只消费一个元素，不会在中间产生一个临时列表。

如果你只是给 `dict.fromkeys` 或 `set()` 喂数据，优先用生成器表达式可以省一点内存。但要注意：生成器多了一点函数调用的开销，速度可能略慢于列表推导。

### 2.12 实战案例：UV 统计

UV（Unique Visitor）是典型的去重场景——同一个用户当天多次访问只算一次。

```python
visit_log = [
    ("2024-01-15", "user_001"),
    ("2024-01-15", "user_002"),
    ("2024-01-15", "user_001"),  # 重复访问
    ("2024-01-15", "user_003"),
    ("2024-01-15", "user_002"),  # 重复
    ("2024-01-16", "user_001"),
    ("2024-01-16", "user_004"),
    ("2024-01-16", "user_003"),  # 跨天算"新 UV"
]

# 按天统计 UV
daily_visits = {}
for date, user in visit_log:
    if date not in daily_visits:
        daily_visits[date] = set()
    daily_visits[date].add(user)

print("每日 UV 统计:")
for date, users in sorted(daily_visits.items()):
    print(f"  {date} | UV: {len(users)} | 用户: {sorted(users)}")

# 两天总 UV（两天合并去重）
all_users = set(user for _, user in visit_log)
print(f"\n两天总 UV: {len(all_users)} | 用户: {sorted(all_users)}")
```

**运行结果**：

```text
每日 UV 统计:
  2024-01-15 | UV: 3 | 用户: ['user_001', 'user_002', 'user_003']
  2024-01-16 | UV: 3 | 用户: ['user_001', 'user_003', 'user_004']

两天总 UV: 4 | 用户: ['user_001', 'user_002', 'user_003', 'user_004']
```

这是个非常典型的"用 set 累积去重"模式——每个 bucket 用一个 set 来接收数据，add 时自动去重，需要统计的时候直接 `len(set)` 就是 UV 数量。

### 2.13 实战案例：购物车去重

购物车场景更复杂一点——用户可能多次点击"加入购物车"按钮把同一个商品加进去，但实际购物车里只该有一份。这种去重通常要按 SKU 去重，保留商品信息。

```python
cart_items = [
    {"sku": "A001", "name": "键盘", "qty": 2, "price": 199},
    {"sku": "A002", "name": "鼠标", "qty": 1, "price": 99},
    {"sku": "A001", "name": "键盘", "qty": 2, "price": 199},  # 重复加购
    {"sku": "A003", "name": "显示器", "qty": 1, "price": 999},
    {"sku": "A002", "name": "鼠标", "qty": 1, "price": 99},   # 重复加购
    {"sku": "A004", "name": "耳机", "qty": 3, "price": 299},
]

seen_skus = set()
merged_cart = []
for item in cart_items:
    if item["sku"] not in seen_skus:
        seen_skus.add(item["sku"])
        merged_cart.append(item)

print(f"原始 {len(cart_items)} 件 → 去重后 {len(merged_cart)} 件\n")
total = 0
for item in merged_cart:
    subtotal = item["qty"] * item["price"]
    total += subtotal
    print(f"  {item['sku']} | {item['name']} x{item['qty']} | ¥{item['price']} | 小计 ¥{subtotal}")
print(f"  总计: ¥{total}")
```

**运行结果**：

```text
原始 6 件 → 去重后 4 件

  A001 | 键盘 x2 | ¥199 | 小计 ¥398
  A002 | 鼠标 x1 | ¥99 | 小计 ¥99
  A003 | 显示器 x1 | ¥999 | 小计 ¥999
  A004 | 耳机 x3 | ¥299 | 小计 ¥897
  总计: ¥2393
```

这其实是 2.5 节"按自定义键去重"的一个具体应用——把 `sku` 字段作为去重 key，保留商品对象本身。

## 3. 最佳实践

### 3.1 推荐 vs 不推荐：去重方案的常见取舍

| 场景 | 推荐写法 | 不推荐写法 | 推荐理由 |
|------|---------|-----------|---------|
| 不关心顺序 | `list(set(data))` | 手动循环 list in | O(n) vs O(n²)，简洁 |
| 需要保序 | `list(dict.fromkeys(data))` | `sorted(set(data))` 假装保序 | `dict.fromkeys` 真正保留首次顺序 |
| 不可哈希元素 | `set(tuple(x) for x in data)` | 强行 `set(data)` | 不可哈希直接报错 |
| 按字段去重 | `dedupe_by_key` 或 dict 推导 | 把对象塞进 set 期望自动去重 | 业务对象的"相等"语义要靠 key 控制 |
| 需要频率统计 | `Counter(data)` | 自己遍历+count | Counter 已内置且高度优化 |

### 3.2 常见误区

**误区一：用 `sorted(set(data))` 代替 `dict.fromkeys` 保序**

```python
# **不推荐**：sorted(set(...)) 只保证"排序后"的顺序，不是原始顺序
result = sorted(set(data))

# **注意**：如果原始数据本来就有序、且是数值/字符串，两者的"顺序"恰好一致；
# 但如果原始数据是无序的（如日志条目），sorted 保存的是字典序，不是首次出现顺序。
```

这是初学者常犯的错误——看起来都是"按某种顺序"，但 `dict.fromkeys` 是按"首次出现的原始顺序"，`sorted(set(...))` 是按"元素本身大小的字典序"，两者语义不同。

**误区二：误以为 `set` 元素顺序不变**

```python
# **不推荐**：依赖 set 的遍历顺序
s = set([3, 1, 4, 1, 5])
for x in s:
    print(x)  # 不能假设这里一定按 3, 1, 4, 5 输出
```

Python 的 set 不保证任何顺序——在同一个解释器进程里，遍历顺序可能随数据规模和哈希表扩容变化。如果需要"按某种顺序"，必须显式 `sorted()` 或用 `list(dict.fromkeys())`。

**误区三：覆盖式 dict 推导保留"最后一个"而非"第一个"**

```python
data = [
    {"id": 1, "version": "v1"},
    {"id": 1, "version": "v2"},  # 后来覆盖前者
    {"id": 2, "version": "v1"},
]
# 用 dict 推导去重 → 保留 id=1 的最后一个版本（v2）
unique = list({d["id"]: d for d in data}.values())

# 如果要保留第一个版本，应该用 dedupe_by_key 函数
```

### 3.3 去重性能优化建议

- **批量去重优于逐个 add**：`set(data)` 一次性批量构造，CPython 在 C 层面优化了批量插入（`set_update`），比循环 `s.add(x)` 快。
- **大数据去重注意内存**：set 的内存占用约为 input 的 4 倍（哈希表预分配槽位）。处理超大去重集时考虑分批或用 `dict.fromkeys` 分批。
- **生成器输入可省内存**：如果原始数据是逐个产生的（如读文件行），用生成器表达式喂 `dict.fromkeys` 比 `list + fromkeys` 节省内存——中途不需要完整的临时 list。
- **去重 + 排序分开执行效率更高**：如果要既去重又排序，先 `set()` 再 `sorted()` 通常比先 `sorted()` 再去重快——前者去重后元素更少，排序成本更低。

## 4. 原理

### 4.1 去重为什么依赖哈希表

去重本质是个"查找问题"——对每个待判断的元素 x，问"之前是否已经出现过？" 这是个典型的成员判断问题。数据结构选型决定了效率：

```text
查找"是否已存在"的不同数据结构方案：

  无序 list：  逐个比较 → O(n) × n 个元素 = O(n²) 总耗时
  有序 list：  二分查找 → O(log n) × n 个元素，但插入要 O(n) 维持有序
  哈希表 set： 哈希计算 + 槽位定位 → O(1) × n 个元素 = O(n) 总耗时
```

set 基于哈希表实现，通过哈希函数直接"跳"到槽位，无需线性比较。这是去重操作"为什么用 set 而不用 list"的根本原因——O(n) vs O(n²) 的差距在数据量稍大时就变得悬殊。

### 4.2 dict.fromkeys 保序的内部机制

Python 3.7+ 的 `dict` 内部有两个关联的数据结构：

```text
dict 内部结构（Python 3.7+）：

  哈希索引数组（sparse）：
    [槽3, None, 槽0, None, 槽2, None, None, 槽1]
       ↓               ↓           ↓               ↓
       │               │           │               │
       ↓               ↓           ↓               ↓
  有序键值对数组（compact）：
    [(key0, val0), (key1, val1), (key2, val2), (key3, val3)]
       插入顺序 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→
```

`dict.fromkeys(iterable)` 依次遍历 `iterable`，对每个元素：

1. 计算哈希值，定位哈希索引数组中的槽位。
2. 如果槽位已有 key 且相等 → 跳过（天然去重）。
3. 如果槽位空闲/冲突但 key 不相等 → 在有序键值对数组**末尾**追加，并更新哈希索引。

结果是：key 唯一性通过哈希表保证（O(1) 查找），顺序通过末尾追加保证（首次出现位置被永久记录）。

### 4.3 可哈希性：为什么 list 不可哈希

Python 中"可哈希"要求对象的哈希值在生命周期内不变。`list`、`dict`、`set` 是可变的——你可以随时 `append`、`remove`、`update` 它们，如果允许它们作为 set 元素或 dict key，可能会出现下面的灾难：

```text
  1. s = {my_list}
  2. my_list.append(100)  →  哈希值变化
  3. 查找 my_list →  在新哈希槽找不到 →  set 以为元素不存在

  →  集合中出现"幽灵元素"：实际存在但永远查不到
```

为避免这种诡异行为，Python 把可变类型设计成"不可哈希"——创建 set 或 dict 时，Python 调用 `hash()` 函数，对不可哈希类型直接抛 `TypeError`。这就是为什么 `set([[1, 2]])` 会报错的原因。

### 4.4 哈希冲突对去重的影响

哈希表并非总是严格 O(1)。如果多个元素产生相同的哈希值（哈希冲突），set 需要在冲突链中逐一比较，最坏情况退化为 O(n)：

```python
class BadHash:
    """所有实例哈希值都相同——模拟极端哈希冲突"""
    counter = 0

    def __init__(self):
        BadHash.counter += 1
        self.id = BadHash.counter

    def __hash__(self):
        return 42  # 所有实例哈希值都固定为 42

    def __eq__(self, other):
        return isinstance(other, BadHash) and self.id == other.id


import time
for size in [100, 1000, 5000]:
    BadHash.counter = 0
    start = time.perf_counter()
    bad_set = {BadHash() for _ in range(size)}
    elapsed = time.perf_counter() - start
    print(f"规模 {size:>5} | BadHash 构造: {elapsed:.6f}s")
```

**运行结果**：

```text
规模   100 | BadHash 构造: 0.000318s
规模  1000 | BadHash 构造: 0.025562s
规模  5000 | BadHash 构造: 0.610436s
```

构造耗时与规模呈超线性增长——规模从 100 到 5000（50 倍），耗时从 0.0003s 到 0.61s（约 2000 倍）。这验证了当所有哈希值相同时，每次插入都要探测整个冲突链，相当于 O(n²) 的总耗时。

**实务建议**：自定义类实现 `__hash__` 时，确保哈希值分布均匀。常见做法是用包含核心字段的 tuple 作为哈希基础，例如 `hash((self.id, self.name))`。只用一个字段（如 `return 42`）会让哈希值集中在某一区域，大幅增加冲突。

## 5. 总结

本文围绕集合去重和各种去重方案展开，主要介绍了以下内容：

- 去重的本质是"判断元素是否已存在"，`set` 基于哈希表实现 O(1) 查找，是去重的首选工具
- 最简写法 `list(set(data))` 直接但**不保序**——元素顺序由哈希表槽位决定，与原始顺序无关
- `list(dict.fromkeys(data))` 利用 Python 3.7+ dict 的插入有序性，实现**保序去重**——保留每个元素的首次出现位置
- 手动遍历 + `set` 辅助去重逻辑等价于 `dict.fromkeys`，但因有 Python 循环开销，性能略低
- 对不可哈希元素（list、dict、set）去重时，先转换为 tuple / frozenset 再去重
- 按自定义键去重用 `dedupe_by_key` 函数模式——把目标字段作为 set 元素而非整个对象
- 多字段联合去重——把多个关键字段组成 tuple 作为去重 key
- 归一化去重——先把大小写、空格、URL 协议等差异统一，再进入常规去重流程
- 自定义类去重要同时实现 `__hash__` 和 `__eq__`，且"两个 `__eq__` 相等的对象必须返回相同哈希值"
- `Counter` 在去重的同时提供频率统计，适合做 TopN 分析
- `list in` 去重是 O(n²) 的反面教材，数据规模稍大就性能崩溃
- set、dict.fromkeys、set 辅助遍历三种方案的性能都是 O(n)，5000 元素规模下 `list in` 已经慢 169 倍
- 生成器表达式去重比列表推导节省内存，但速度可能略慢
- 实战场景：日志去重保留首次出现时间、UV 统计按天去重、购物车按 SKU 去重
- 去重依赖哈希表的 O(1) 查找；`dict.fromkeys` 保序的秘密在于 Python 3.7+ dict 的"哈希索引 + 有序键值对"双数组结构
- 不可变类型才可哈希——可变类型的哈希值会变化，放入 set 会导致"已存在但找不到"的幽灵元素
- 哈希冲突严重时，set 去重也会退化为 O(n²)；自定义 `__hash__` 时应确保哈希值分布均匀
