# zfill 方法

## 1. 介绍

### 1.1 知识点定义

`str.zfill(width)` 是字符串的**零填充方法**：把原串整体右移，在左侧不断补 ASCII 字符 `'0'`，直到整个字符串长度达到 `width`，然后返回这个新字符串。

名字拆开看就懂了一半：`z` 是 zero（零），`fill` 是填充——"用零填充"。它解决的是一个非常具体的排版问题：**把宽度不一的字符串变成等宽**。序号 `1`、`12`、`123` 排在一列里参差不齐；时间 `8:5:3` 读起来别扭；流水号 `42` 和 `1024` 对不齐；从 `image1.png` 到 `image10.png` 的文件名排序混乱。凡是"希望数字部分对齐、空缺处用 0 占位"的地方，都是它的主场。

它的签名只有一个参数：

| 维度 | 说明 |
|------|------|
| 所属 | `str` 的内置实例方法 |
| 语法 | `s.zfill(width)` |
| 参数 | `width`：目标总长度，必须能通过 `__index__` 协议转成整数 |
| 返回值 | 补零后的新字符串 |
| 填充字符 | 固定为 ASCII `'0'`，不可指定 |
| 填充方向 | 只在左侧补，右侧分毫不动 |
| 截断行为 | **从不截断**——原串已经够长就原样返回 |
| 符号处理 | 首字符是 `+` 或 `-` 时，补的 0 插在符号**之后** |

在展开细节之前，先把两条最容易踩错的铁律摆在台面上：

- **它只补不砍**。`"12345".zfill(3)` 的结果是 `'12345'`，不是 `'123'`。`width` 是"至少达到"的目标，不是"规整到"的裁剪尺寸。
- **它会认符号**。`"-42".zfill(6)` 得到 `'-00042'` 而不是 `'000-42'`。这是它区别于 `rjust(width, '0')` 的看家本领，也是这个老方法至今仍被需要的原因。

两条铁律各自都能跑出一串反直觉的结果，本篇第 2 章会逐一验证。

### 1.2 最简示例

先看一个最小可运行的样子。三段代码分别覆盖三种典型走向——正常补零、超长不砍、带符号：

```python
print(repr("42".zfill(5)))       # 长度不足, 左侧补零
print(repr("12345".zfill(3)))    # 长度已够, 原样返回
print(repr("-42".zfill(6)))      # 带符号, 0 补在符号之后
```

运行结果：

```text
'00042'
'12345'
'-00042'
```

第一行的 `'42'` 只有 2 个字符，补 3 个 `0` 凑满 5 位。第二行的 `'12345'` 已经有 5 个字符，比 `width=3` 还长，`zfill` 不砍任何东西。第三行最能体现它的性格：`'-42'` 的首字符是负号，于是 3 个 `0` 全部插在负号右边，得到 `'-00042'`——负号稳稳定在最左端，就像它本来就该在那里。

**这个符号行为不是所有填充方法都有的**，接下来的内容基本都围绕它展开。

### 1.3 字符串对齐填充工具体系中的定位

Python 里能把字符串"撑到固定宽度"的手段有三路，`zfill` 是其中最专一的一路：

```text
字符串填充与对齐方法
│
├── 补零专用 —— zfill(width)              ← 本篇聚焦
│     └── 唯一会识别 +/- 前缀的填充方法
│
├── 自定义填充字符 —— ljust / rjust / center
│     ├── rjust(width, fillchar): 右对齐, 左侧补
│     ├── ljust(width, fillchar): 左对齐, 右侧补
│     └── center(width, fillchar): 居中, 两侧补
│
└── 格式化语法 —— f-string / str.format
      ├── 面向数值: 支持精度、符号标志、千分位
      └── 面向字符串: 用 0> / <0 等对齐选项
```

三路工具的定位可以这样区分：

- **`zfill` 管"补零"这一件事**。填充字符写死是 `'0'`，换来的是唯一懂符号前缀的能力。
- **`ljust` / `rjust` / `center` 管"填充字符自定义"**。想用 `*`、`-`、空格填空都行，代价是不理解 `+` / `-`，符号会被当成普通字符推到右边。
- **f-string / `format` 管"数值格式化"**。它是唯一能同时处理精度、千分位、小数点对齐的，但它的对齐语法作用于格式化后的整体，对"传入的原始字符串"并没有符号识别能力。

一个方法宁可只做一件小事也要把符号处理正确，是因为**数值字符串的符号位置在工程里经常是有语义的**——`-00042` 表示负数 42，`000-42` 表示一段谁也不认识的乱码。选型时的判断依据就在这句话里。

## 2. 核心内容

### 2.1 基本行为

#### 2.1.1 签名与参数语义

`zfill` 只收一个位置参数 `width`，语义是"目标总长度"：

```python
cases = [
    ("42", 5),      # 短数字补零
    ("0", 3),       # 单个 0 也要补到 3 位
    ("7", 2),       # 只补一位
    ("3.14", 8),    # 小数点不参与特殊处理
    ("", 5),        # 空串: 全部用 0 填满
]
for text, width in cases:
    result = text.zfill(width)
    print(f"{text!r:>8}.zfill({width}) = {result!r:>12}  (len={len(result)})")
```

运行结果：

```text
    '42'.zfill(5) =      '00042'  (len=5)
     '0'.zfill(3) =        '000'  (len=3)
     '7'.zfill(2) =         '07'  (len=2)
  '3.14'.zfill(8) =   '00003.14'  (len=8)
      ''.zfill(5) =      '00000'  (len=5)
```

三件事值得注意。**第一，补的是"最少数量"**——`width=5` 时补到 5 位就停，不会多补。**第二，小数点、字母、空格都只是普通字符**，`'3.14'` 里的 `.` 不享有任何特殊地位，所以 `'3.14'.zfill(8)` 是把 0 补在整个串的左边，而不是补在小数点前面。**第三，空串会被填满**——`''.zfill(5)` 得到 5 个 `0`，因为空串长度 0，需要补 5 个。

如果只是想在右侧补齐，那不是 `zfill` 的职责，用 `ljust`——`'42'.ljust(5, '0')` 得到 `'42000'`，语义完全不同。

#### 2.1.2 width 小于等于长度：原样返回，绝不截断

`width` 是"至少达到"而非"规整到"，所以原串已经够长时它什么也不做：

```python
for text, width in [("123", 3), ("12345", 3), ("hello", 2), ("42", 1)]:
    result = text.zfill(width)
    print(f"{text!r:>9}.zfill({width}) = {result!r:>9}  (长度 {len(text)} >= {width})")
```

运行结果：

```text
    '123'.zfill(3) =     '123'  (长度 3 >= 3)
  '12345'.zfill(3) =   '12345'  (长度 5 >= 3)
  'hello'.zfill(2) =   'hello'  (长度 5 >= 2)
     '42'.zfill(1) =      '42'  (长度 2 >= 1)
```

四行输出全部原样返回，长度一个都没变。把 `zfill` 当"定宽裁剪"用的人会在这里翻车：他想把任意长度的输入统一成 3 位，结果长输入原封不动地漏了过去。**需要截断必须自己写切片**，比如 `text.zfill(3)[-3:]`——先补足再取最后 3 位，才是"规整到固定宽度"的完整语义。

这个行为也解释了为什么边界判断是 `>=` 而不是 `>`：长度正好等于 `width` 时没有可补的位置，自然也走原样返回这条路。

#### 2.1.3 返回新串：原串不变，忘记接收等于白忙

字符串不可变，补零的结果必然是一个新字符串，**原串从头到尾保持原样**：

```python
serial = "7"
serial.zfill(4)                      # 反面教材: 结果被丢弃
print(f"调用后 serial = {serial!r}")

serial = serial.zfill(4)             # 正确: 用变量接住返回值
print(f"接收后 serial = {serial!r}")
```

运行结果：

```text
调用后 serial = '7'
接收后 serial = '0007'
```

第一行的 `serial.zfill(4)` 确实执行了、确实造出了 `'0007'`——但这个新串无人接收，当场蒸发，`serial` 依旧是 `'7'`。**"我明明补零了，写进文件还是没补"这类 bug，第一嫌疑人永远是忘记接收返回值**。字符串的所有转换类方法都有这个坑，`zfill` 也不例外。

#### 2.1.4 对象细节：无需补零时返回原对象

同样是"调用后什么也没变"，底层却有两种不同的处理方式：

```python
text = "abc"
print(f"text.zfill(5) is text: {text.zfill(5) is text}   (需要补零)")
print(f"text.zfill(3) is text: {text.zfill(3) is text}   (长度相等)")
print(f"text.zfill(1) is text: {text.zfill(1) is text}   (宽度更小)")
```

运行结果：

```text
text.zfill(5) is text: False   (需要补零)
text.zfill(3) is text: True   (长度相等)
text.zfill(1) is text: True   (宽度更小)
```

只要**真的补了零，就一定新建对象**（第一行 `False`）；只要**无需补零，就直接把原对象还给你**（后两行 `True`）。这个细节的实践含义是：**不能用 `is` 判断"这串是不是被补过零"**。`text.zfill(5) is text` 为假只说明新建了对象，不代表内容变了——如果 `text` 本来就长 5 位，内容完全一样却依然返回新对象。比较内容用 `==`，判断"有没有被改动"也只能靠比较前后内容。

### 2.2 填充内容：永远是 ASCII '0'

#### 2.2.1 不校验内容是否为数字

方法名里的 `fill` 才是关键——它只负责"填"，不负责判断"该不该填"：

```python
for text, width in [("hello", 8), ("0x1f", 6), ("abc", 6), ("--", 4), ("3.14", 8)]:
    print(f"{text!r:>8}.zfill({width}) = {text.zfill(width)!r}")
```

运行结果：

```text
 'hello'.zfill(8) = '000hello'
  '0x1f'.zfill(6) = '000x1f'
   'abc'.zfill(6) = '000abc'
    '--'.zfill(4) = '-00-'
  '3.14'.zfill(8) = '00003.14'
```

`'hello'` 不是数字，照样被补；`'0x1f'` 是十六进制字面量，`zfill` 不认识 `0x` 前缀，把它当普通文本补在最左侧。**它没有任何"数字校验"逻辑**——这是设计上的克制，也是使用上的责任：可以补零不代表补出来的东西有语义。

`'--'.zfill(4)` 的结果 `'-00-'` 更值得玩味：首字符是 `-`，于是补的 2 个 `0` 插到了它后面，可第二个 `-` 却被当成了普通字符。这类"看起来像数字其实不是"的输入是零填充最危险的地带。

#### 2.2.2 长度按码点计算，与显示宽度无关

`width` 比的是 `len(s)`，也就是**码点个数**，而不是终端里占多少列：

```python
for text in ["一二三", "café", "👍"]:
    result = text.zfill(5)
    print(f"{text!r}.zfill(5) = {result!r}  (len({text!r})={len(text)})")
```

运行结果：

```text
'一二三'.zfill(5) = '00一二三'  (len('一二三')=3)
'café'.zfill(5) = '0café'  (len('café')=4)
'👍'.zfill(5) = '0000👍'  (len('👍')=1)
```

`'一二三'` 的码点数是 3，所以补 2 个 `0`；但在等宽终端里它显示为 6 列宽，补完反而变成了 8 列，**比目标"宽度"宽出一倍**。`'👍'` 更极端：1 个码点、补 4 个 `0`，视觉上却是 2 列 + 4 列。

结论很明确：**`zfill` 是"码点计数"的对齐工具，不是"视觉列宽"的对齐工具**。要做表格列对齐、中日韩混排对齐，得用能计算显示宽度的第三方库（如 `wcwidth`），`zfill` 在这里帮不上忙。

#### 2.2.3 只补左侧，不补右侧

填充方向是写死的：只在左边补。右侧补齐是 `ljust` 的活：

```python
print(repr("42".zfill(5)))          # 左补: 数字靠右
print(repr("42".ljust(5, "0")))     # 右补: 数字靠左
print(repr("42".rjust(5, "0")))     # 左补, 但不懂符号
```

运行结果：

```text
'00042'
'42000'
'00042'
```

`zfill(5)` 和 `rjust(5, '0')` 在**无符号**的情况下结果完全相同（都是 `'00042'`），但 `ljust(5, '0')` 是另一个语义——`'42000'`，数值直接被改变了数量级。**绝对不要用 `ljust` 补零**：它补出来的不是"对齐后的 42"，而是"四万二千"。

### 2.3 符号前缀处理：zfill 的看家本领

#### 2.3.1 零插在符号之后

这是 `zfill` 存在的核心理由。当首字符是 `+` 或 `-` 时，补的 `0` 会被插到符号**后面**，而不是整个串的前面：

```python
for text, width in [("-42", 6), ("+42", 6), ("-3.14", 8), ("+3.14", 8)]:
    print(f"{text!r:>8}.zfill({width}) = {text.zfill(width)!r}")
```

运行结果：

```text
   '-42'.zfill(6) = '-00042'
   '+42'.zfill(6) = '+00042'
 '-3.14'.zfill(8) = '-0003.14'
 '+3.14'.zfill(8) = '+0003.14'
```

对比一下带符号与不带符号的三种情况，能更清楚地看到"数字主体位数一致"这个设计意图：

```python
for text in ["42", "+42", "-42"]:
    print(f"{text!r:>6}.zfill(6) = {text.zfill(6)!r}")
```

运行结果：

```text
  '42'.zfill(6) = '000042'
 '+42'.zfill(6) = '+00042'
 '-42'.zfill(6) = '-00042'
```

三者补出来的数字主体都是 4 位（`000042` 的数位部分、`+00042` 与 `-00042` 除去符号后的部分）。**这正是"对齐"的本意**：一列有正有负的数值，符号各占一格，数字部分位数一致，小数点自然对齐，肉眼扫一列就能比大小。如果按 `rjust` 的做法把 0 补在符号前面得到 `'000-42'`，这一列就彻底废了。

即使只有一个孤零零的符号字符，规则照样生效：

```python
print(repr("-".zfill(3)))
print(repr("+".zfill(3)))
```

运行结果：

```text
'-00'
'+00'
```

#### 2.3.2 判定只看首字符，不做语法解析

`zfill` 的符号识别非常朴素——**只看第 0 个字符是不是 `+` 或 `-`**，之后的内容一概不分析：

```python
cases = ["-42", "--42", "+-42", "-+42", "- 42", " -42"]
for text in cases:
    print(f"{text!r:>8}.zfill(6) = {text.zfill(6)!r}")
```

运行结果：

```text
   '-42'.zfill(6) = '-00042'
  '--42'.zfill(6) = '-00-42'
  '+-42'.zfill(6) = '+00-42'
  '-+42'.zfill(6) = '-00+42'
  '- 42'.zfill(6) = '-00 42'
  ' -42'.zfill(6) = '00 -42'
```

六行输出把规则暴露得很彻底：

- `'--42'`：首字符是 `-`，触发符号规则，0 插到它后面，第二个 `-` 沦为普通字符。**这里没有任何"符号合法性校验"**，`'-00-42'` 不是什么数的表示。
- `'-+42'`：同理，`+` 被当成普通字符，得到 `'-00+42'`。
- `'- 42'`：符号后面跟空格，规则照样触发。
- `' -42'`：**首字符是空格**，不满足条件，于是 `0` 直接补在了最左边，得到 `'00 -42'`——负号被推到了第 3 位。这是外部数据里最常见的一种翻车方式。

所以使用前务必确认输入是"干净的、符号在最左"的形态。如果数据里混着前后空格，先 `strip()` 再 `zfill()`：

```python
raw = " -42"
print(repr(raw.strip().zfill(6)))
```

运行结果：

```text
'-00042'
```

#### 2.3.3 只认 ASCII 的 + 与 -

符号判定用的是 ASCII 的 `'+'`（U+002B）和 `'-'`（U+002D）。外观极像的 Unicode 减号 U+2212 MINUS SIGN 不在其列：

```python
minus_sign = "\u2212"                # U+2212, 外观与 ASCII 减号几乎一致
text = minus_sign + "42"
print(f"原串 {text!r} (U+2212).zfill(6) = {text.zfill(6)!r}")
```

运行结果：

```text
原串 '−42' (U+2212).zfill(6) = '000−42'
```

结果里 `0` 被补到了最前面，U+2212 被当成普通字符往右推。**这两个字符在终端里几乎无法用肉眼区分**，但行为天差地别。从网页、PDF、Excel 复制出来的数据经常带 U+2212，处理前先做一次归一化：

```python
text = "\u221242"                    # 从外部复制来的 "-42"
normalized = text.replace("\u2212", "-")
print(repr(normalized.zfill(6)))
```

运行结果：

```text
'-00042'
```

#### 2.3.4 与内容语义无关：符号只管首位

符号处理是纯位置规则，不关心字符串表示的到底是什么数：

```python
text = "-1.5e-3"
print(repr(text.zfill(10)))
```

运行结果：

```text
'-0001.5e-3'
```

只有最前面的 `-` 享受"0 插在其后"的待遇，指数部分的 `-` 是普通字符，参与长度计算但不参与判定。理解这一点就不会对结果感到意外：**`zfill` 眼里没有"数"，只有"一串字符 + 首字符可能是符号"**。

### 2.4 与 rjust 和 f-string 的对照

#### 2.4.1 zfill vs rjust(width, '0')：符号位置分岔

两者在无符号输入上完全等价，分歧只出现在有符号时：

```python
for text, width in [("42", 5), ("-42", 6), ("+42", 6), ("-3.14", 8)]:
    padded_zfill = text.zfill(width)
    padded_rjust = text.rjust(width, "0")
    same = "是" if padded_zfill == padded_rjust else "否"
    print(f"{text!r:>8} | zfill={padded_zfill!r:>10} | rjust={padded_rjust!r:>10} | {same}")
```

运行结果：

```text
    '42' | zfill=   '00042' | rjust=   '00042' | 是
   '-42' | zfill=  '-00042' | rjust=  '000-42' | 否
   '+42' | zfill=  '+00042' | rjust=  '000+42' | 否
 '-3.14' | zfill='-0003.14' | rjust='000-3.14' | 否
```

`rjust` 把补的字符一律放在最左边，**符号被当成普通字符推到右边**，结果 `'000-42'` 在数值上毫无意义。一句话总结这条分界线：**只要输入可能带符号，就用 `zfill`；确认没有符号，两者随便选。**

#### 2.4.2 zfill vs f-string 数值格式化

如果手上是真正的数值类型（`int` / `float`）而不是字符串，f-string 通常是更合适的工具——它不必先转字符串，还支持符号标志与精度：

```python
for value in [42, -42, 0, 7]:
    print(f"{value:>4} -> '05d'={format(value, '05d')!r}  '+06d'={format(value, '+06d')!r}")
```

运行结果：

```text
  42 -> '05d'='00042'  '+06d'='+00042'
 -42 -> '05d'='-0042'  '+06d'='-00042'
   0 -> '05d'='00000'  '+06d'='+00000'
   7 -> '05d'='00007'  '+06d'='+00007'
```

格式说明 `'05d'` 里的 `0` 是"补零标志"，`5` 是总宽度；f-string 对数值**天然知道符号的位置**，所以 `format(-42, '05d')` 得到 `'-0042'`，与 `str(-42).zfill(5)` 的结果完全一致。而 `'+06d'` 里的 `+` 是"总是显示符号"标志，`zfill` 做不到这一点——**它只能保住已经存在的符号，无法凭空造出一个 `+`**。

对字符串用格式说明时，`0>` 只表示"用 0 右对齐"，**不具备符号识别能力**：

```python
text = "-42"
print(f"format(text, '0>6') = {format(text, '0>6')!r}")
```

运行结果：

```text
format(text, '0>6') = '000-42'
```

结果与 `rjust(6, '0')` 一致，而不是 `zfill(6)` 的 `'-00042'`。**这就是"字符串的补齐"不能用格式说明替代 `zfill` 的原因**。

#### 2.4.3 三方对照表

| 维度 | `zfill(width)` | `rjust(width, '0')` | f-string / `format` |
|------|---------------|---------------------|---------------------|
| 输入类型 | 字符串 | 字符串 | 任意类型 |
| 填充字符 | 固定 `'0'` | 任意单字符 | 由格式说明决定 |
| 符号识别 | **有**，0 插在符号后 | 无，符号被推右 | 对数值有；对字符串无 |
| 凭空加 `+` 号 | 不支持 | 不支持 | 支持（`+` 标志） |
| 小数点对齐 | 不支持 | 不支持 | 支持（配合精度） |
| 千分位分隔 | 不支持 | 不支持 | 支持（`,` 选项） |
| 典型场景 | 补零且可能带符号的字符串 | 无符号的纯右对齐 | 数值格式化 |

选型判断可以浓缩成两句：**数据已经是字符串且可能带符号，用 `zfill`；数据是数值，用 f-string。**

### 2.5 参数纪律与报错

#### 2.5.1 width 必须走 __index__ 协议

`width` 不是"能 `int()` 转换就行"，而是必须实现 `__index__` 协议：

```python
for width in [3, True]:
    print(f"'42'.zfill({width!r}) = {'42'.zfill(width)!r}")
for width in [3.0, "3", None]:
    try:
        "42".zfill(width)
    except TypeError as e:
        print(f"'42'.zfill({width!r}) -> TypeError: {e}")
```

运行结果：

```text
'42'.zfill(3) = '042'
'42'.zfill(True) = '42'
'42'.zfill(3.0) -> TypeError: 'float' object cannot be interpreted as an integer
'42'.zfill('3') -> TypeError: 'str' object cannot be interpreted as an integer
'42'.zfill(None) -> TypeError: 'NoneType' object cannot be interpreted as an integer
```

报错信息高度统一：`cannot be interpreted as an integer`。**`'3'` 这样的数字字符串也不行**——这正是"用 `__index__` 而不是 `int()`"的体现，避免出现"字符串 `'3'` 悄悄变成 3"这种隐式转换。`True` 是 `bool`，而 `bool` 是 `int` 的子类，所以 `zfill(True)` 把宽度当成 1；`'42'` 长度已经是 2，于是原样返回。

自定义对象只要实现 `__index__` 就能作为宽度：

```python
class Width:
    def __init__(self, value):
        self.value = value
    def __index__(self):
        return self.value

print(repr("42".zfill(Width(5))))
```

运行结果：

```text
'00042'
```

#### 2.5.2 参数个数纪律

必须恰好传 1 个参数，多传少传都会被拒绝：

```python
for args in [(), (5, 6)]:
    try:
        "42".zfill(*args)
    except TypeError as e:
        print(f"zfill{args} -> TypeError: {e}")
```

运行结果：

```text
zfill() -> TypeError: str.zfill() takes exactly one argument (0 given)
zfill(5, 6) -> TypeError: str.zfill() takes exactly one argument (2 given)
```

报错信息把"exactly one"写得很直白。**不要试图给 `zfill` 再传一个填充字符**——想指定填充字符,要用 `rjust`。

#### 2.5.3 负数 width

负数宽度不会被当成错误，而是按"无需补充"处理：

```python
for width in [-3, -100]:
    print(f"'42'.zfill({width}) = {'42'.zfill(width)!r}")
```

运行结果：

```text
'42'.zfill(-3) = '42'
'42'.zfill(-100) = '42'
```

任何负数都小于字符串长度，于是统一走"原样返回"分支。**不会抛异常，也不会有任何提示**——如果你的宽度是从配置或用户输入算出来的，负值会被静默吞掉，值得加一道校验。

#### 2.5.4 int 没有 zfill

`zfill` 是 `str` 的方法，整数身上没有：

```python
try:
    (42).zfill(5)
except AttributeError as e:
    print(f"(42).zfill(5) -> AttributeError: {e}")
print(f"正确写法: str(42).zfill(5) = {str(42).zfill(5)!r}")
```

运行结果：

```text
(42).zfill(5) -> AttributeError: 'int' object has no attribute 'zfill'
正确写法: str(42).zfill(5) = '00042'
```

注意报错类型是 `AttributeError`（属性不存在）而不是 `TypeError`，这个区别在写 `except` 时有用。**必须先 `str()` 转换**，或者改用 f-string 直接格式化数值。

## 3. 最佳实践

### 3.1 推荐 vs 不推荐：数字补零与字符串补零分开

最核心的一条实践原则：**先看数据是什么类型，再决定用哪套工具**。

```python
# 不推荐: 数值先转字符串再补零, 白白多一步
value = 42
padded = str(value).zfill(6)

# 推荐: 数值直接用 f-string, 支持符号标志, 无需转换
padded = f"{value:06d}"

# 不推荐: 字符串带符号却用 rjust, 符号位置被破坏
delta = "-42"
broken = delta.rjust(6, "0")        # '000-42' —— 语义丢失

# 推荐: 字符串带符号用 zfill, 符号被正确保护
fixed = delta.zfill(6)              # '-00042'
```

原因在于两者的能力边界不同：f-string 面向数值，能处理精度、千分位、符号标志这些"数值相关"的需求；`zfill` 面向字符串，能处理"首字符可能是符号"这种"文本相关"的需求。**混用不会报错，但会得到语义错误的结果。**

另有一条容易被忽略的建议：**能用 f-string 就用 f-string，除非数据本来就是字符串**。因为 `str(value).zfill(n)` 多做了一次类型转换，而 `f"{value:0{n}d}"` 一步到位。

### 3.2 定宽编号模板

生成定宽编号是最常见的用法。它的价值不只是好看，而是**让字符串排序的结果等于数值排序的结果**：

```python
order_ids = [1, 12, 123, 1234]
plain = sorted(str(i) for i in order_ids)
padded = sorted(str(i).zfill(4) for i in order_ids)
print(f"直接按字符串排序(错): {plain}")
print(f"zfill 后排序(对):     {padded}")
```

运行结果：

```text
直接按字符串排序(错): ['1', '12', '123', '1234']
zfill 后排序(对):     ['0001', '0012', '0123', '1234']
```

这份数据恰好"看起来是对的"，因为数字位数递增。换一组更狡猾的数据，问题立刻现形：

```python
order_ids = [1, 2, 10, 100]
print(sorted(str(i) for i in order_ids))
print(sorted(str(i).zfill(4) for i in order_ids))
```

运行结果：

```text
['1', '10', '100', '2']
['0001', '0002', '0010', '0100']
```

第一行里 `'10'` 排在了 `'2'` 前面——**字典序逐字符比较，第一位 `'1'` 小于 `'2'`，后面就不看了**。补零之后每一位的权重固定，字典序与数值序才真正一致。这是编号系统、分页文件名、日志分片名里必须补零的根本原因。

编号模板：

```python
def make_order_id(number: int, width: int = 6) -> str:
    return f"ORD-{str(number).zfill(width)}"

for number in [1, 12, 1234]:
    print(make_order_id(number))
```

运行结果：

```text
ORD-000001
ORD-000012
ORD-001234
```

### 3.3 时间字段模板

时间是最经典的两段式补零场景：

```python
samples = [(8, 5, 3), (12, 30, 59), (23, 0, 0)]
for hour, minute, second in samples:
    stamp = f"{str(hour).zfill(2)}:{str(minute).zfill(2)}:{str(second).zfill(2)}"
    print(stamp)
```

运行结果：

```text
08:05:03
12:30:59
23:00:00
```

这里的宽度固定为 2，并且**数值范围天然被约束在 0~59 / 0~23**，所以补零之后长度一定正确，不需要额外的截断保护。这是 `zfill` 用起来最省心的场景。

不过也要清楚：**如果时间已经是 `datetime` 对象，用 `strftime('%H:%M:%S')` 更直接**。`zfill` 适合的是"手头只有一堆拆开的整数"的情形。

### 3.4 金额与符号场景

金额场景能同时暴露 `zfill` 的长处与短板：

```python
amounts = ["-50", "-100", "+250", "999", "-3.5"]
for amount in amounts:
    print(f"${amount.zfill(9)}")
```

运行结果：

```text
$-00000050
$-00000100
$+00000250
$000000999
$-000003.5
```

长处是**符号被稳稳地固定在符号位**：前四行的正负号都在 `$` 之后的第一格，一列扫下来整齐。短板在第五行——`'-3.5'` 的数字长度和其他项不同，小数点完全对不齐。**`zfill` 保证的是总长度一致，不是小数点对齐。**

如果要做报表级别的金额对齐，用 f-string 的精度控制：

```python
amounts = ["-50", "-100", "+250", "999", "-3.5"]
for amount in amounts:
    print(f"${float(amount):>+10.2f}")
```

运行结果：

```text
$    -50.00
$   -100.00
$   +250.00
$   +999.00
$     -3.50
```

小数点、小数点后两位、正负号全部对齐。**结论：金额这类"数值语义强"的场景优先 f-string；`zfill` 只适合"金额已经被格式化成字符串、只需要补零对齐符号位"的窄场景。**

### 3.5 可排序文件名模板

文件系统按字典序排列文件名，所以 `image1.png`、`image10.png`、`image2.png` 的顺序是反直觉的：

```python
raw = ["image1.png", "image10.png", "image2.png", "image100.png"]
print(f"原始名字排序(错): {sorted(raw)}")

def pad_number(name: str) -> str:
    stem, _, ext = name.rpartition(".")
    prefix = stem.rstrip("0123456789")
    number = stem[len(prefix):]
    return f"{prefix}{number.zfill(4)}.{ext}"

print(f"补齐后排序(对):   {sorted(pad_number(n) for n in raw)}")
```

运行结果：

```text
原始名字排序(错): ['image1.png', 'image10.png', 'image100.png', 'image2.png']
补齐后排序(对):   ['image0001.png', 'image0002.png', 'image0010.png', 'image0100.png']
```

模板把文件名拆成"非数字前缀 + 数字 + 扩展名"三段，只对数字部分补零。这样既保住了原有命名风格，又让字典序与数值序一致。**注意 `rstrip("0123456789")` 用的是字符集合语义**——它从右侧连续剥掉所有数字字符，正好把数字部分整段分离出来。

### 3.6 常见错误模式及修正

**错误一：以为会截断**

```python
# 不推荐: 期望把任意长度规整成 3 位, 长输入会漏过去
result = text.zfill(3)

# 推荐: 先补足再取右侧固定位数, 这才是"规整到固定宽度"
result = text.zfill(3)[-3:]
```

**错误二：忘记接收返回值**

```python
# 不推荐: 结果被丢弃, text 毫无变化
text.zfill(6)

# 推荐: 用变量接住
text = text.zfill(6)
```

**错误三：带符号的字符串用 rjust**

```python
delta = "-42"

# 不推荐: '000-42', 符号位置被破坏
broken = delta.rjust(6, "0")

# 推荐: '-00042', 符号受保护
fixed = delta.zfill(6)
```

**错误四：外部数据没清洗就补零**

```python
raw = " -42"                          # 带前导空格

# 不推荐: '00 -42', 符号被推到第 3 位
broken = raw.zfill(6)

# 推荐: 先去空白再补零
fixed = raw.strip().zfill(6)          # '-00042'
```

**错误五：整数直接调 zfill**

```python
number = 42

# 不推荐: AttributeError, int 没有这个方法
# number.zfill(5)

# 推荐: 数值用 f-string
padded = f"{number:05d}"

# 也可以: 显式转成字符串
padded = str(number).zfill(5)
```

**错误六：用 is 判断补零结果**

```python
text = "abc"

# 不推荐: 内容相同时 is 也可能为 True, 判断不可靠
if text.zfill(3) is not text:
    ...

# 推荐: 比较内容
if text.zfill(3) == text:
    ...
```

**错误七：Unicode 减号未归一化**

```python
raw = "\u221242"                      # 从网页复制来的数字

# 不推荐: '000−42', 符号未被识别
broken = raw.zfill(6)

# 推荐: 先归一化再补零
fixed = raw.replace("\u2212", "-").zfill(6)
```

### 3.7 方法选择决策速查表

| 你的需求 | 推荐做法 | 关键理由 |
|---------|---------|---------|
| 字符串补零，可能带 `+` / `-` | `s.zfill(width)` | 唯一能保护符号位置的填充方法 |
| 字符串补零，确认无符号 | `s.rjust(width, '0')` | 与 `zfill` 等价，语义更直白 |
| 字符串补其他字符 | `s.rjust(width, ch)` / `ljust` / `center` | `zfill` 填充字符写死是 `'0'` |
| 整数补零 | `f"{value:0{width}d}"` | 不必先转字符串，支持符号标志 |
| 浮点数补零并小数点对齐 | `f"{value:{width}.{prec}f}"` | `zfill` 只能按总长度补，管不了小数位 |
| 数值加千分位 | `f"{value:,}"` | 只有格式化语法支持 |
| 任意长度规整到固定宽度 | `s.zfill(w)[-w:]` | `zfill` 只补不砍，截断要自己做 |
| 视觉列宽对齐（中文混排） | 计算显示宽度 | `zfill` 按码点计数，与显示宽度无关 |

## 4. 原理

### 4.1 纯 Python 等价实现：先补零，再处理首字符

`zfill` 由 CPython 在 C 层实现，逻辑本身非常短。把它翻译成等价的 Python 代码，规则就一目了然：

```python
def my_zfill(text: str, width: int) -> str:
    if len(text) >= width:
        return text                       # 无需补零, 原样返回
    fill = width - len(text)              # 需要补几个 0
    if text[:1] in ("+", "-"):            # 只看首字符是不是符号
        return text[0] + "0" * fill + text[1:]
    return "0" * fill + text
```

这段实现只有 4 个决策点，恰好对应前面观察到的全部行为：

1. `len(text) >= width` → 原样返回，解释了"只补不砍"和宽度相等时的原对象返回。
2. `fill = width - len(text)` → 补最少数量，不多补。
3. `text[:1] in ("+", "-")` → 只检查首字符，且只认这两个 ASCII 字符，解释了 `'--42'`、`' -42'`、U+2212 的全部行为。
4. 符号分支里 `text[0] + "0" * fill + text[1:]` → 把符号摘出来放在最前，解释了"0 插在符号之后"。

把这段实现与内置 `zfill` 在大量输入上逐一比对，可以确认它与 CPython 行为完全一致：

```python
samples = ["", "0", "42", "-42", "+42", "-", "+", "--42", "+-42", " -42", "- 42",
           "\u221242", "3.14", "hello", "一二三", "👍", "0x1f", "--", "-0", "-42.5e+3"]
widths = [-5, 0, 1, 2, 3, 5, 6, 8, 10, 12]

mismatches = 0
for text in samples:
    for width in widths:
        if my_zfill(text, width) != text.zfill(width):
            mismatches += 1

print(f"用例数: {len(samples) * len(widths)}, 不一致: {mismatches}")
```

运行结果：

```text
用例数: 200, 不一致: 0
```

200 组用例零分歧——**`zfill` 的全部秘密就是"长度判断 + 首字符判断"这两件事**，没有任何隐藏的数值解析逻辑。

### 4.2 为什么只填 '0' 且不做数字校验

这看起来是个"能力不足"的设计，其实是有意为之。

**填充字符写死为 `'0'`，是为了让 `zfill` 在 C 层只处理一种情况。** 通用的填充需要接收任意填充字符、判断它的长度（必须是单个字符）、处理多字节情况，而 `zfill` 只需要填一个固定的单字节字符，实现可以极短、极快。需要自定义填充字符的场景，`rjust` / `ljust` / `center` 已经覆盖；如果 `zfill` 也能传填充字符，它就变成 `rjust` 的副本，失去存在价值。

**不做数字校验，是因为校验会带来无法回答的边界问题。** 假设 `zfill` 真的检查了"内容是不是数字"，那么 `'3.14'` 算不算数字？`'0x1f'` 算不算？`'1_000'` 算不算？`'--'` 算不算？每一个判断都需要一套规则，而任何一套规则都会挡住一部分用户本来就想要的用法——比如给十六进制的 `'1f'` 补零到 8 位，这是完全合理的需求。**"不判断"反而是最通用、最不容易出错的选择**：想校验的人自己校验，`zfill` 只做纯粹的文本操作。

这也解释了一个更普遍的原则：**字符串方法的职责边界通常划在"字符"这一层，而不是"语义"这一层**。方法名里的 `fill` 而不是 `format_number`，已经在提示这一点。

### 4.3 与 format 的关系：两套独立实现

`zfill` 和 f-string 的补零看起来在做同一件事，实际是两条互不相干的代码路径：

| 维度 | `str.zfill` | 数值格式说明 `05d` |
|------|------------|-------------------|
| 作用对象 | 字符串本身 | 数值（先转成十进制文本） |
| 符号位置 | 靠"移动首字符"实现 | 由格式化器在生成文本时就摆好 |
| 能否产生 `+` | 不能，只能保住已有的 | 能，`+` 标志会主动加上 |
| 是否懂小数点 | 不懂 | 配合精度能对齐 |
| 对字符串的作用 | 正常补零并保护符号 | `0>` 只做右对齐，不认符号 |

关键差异是**"符号是在生成文本时产生，还是在已有文本里挪位置"**。数值格式化是从数值出发生成文本，符号是生成过程的一部分，所以它能凭空加上 `+`；`zfill` 是在已有文本上操作，只能保住已经存在的符号，无法造出不存在的字符。

这决定了两者的适用范围：**要"生成"一个带符号的定宽数字，用格式化；要"对齐"一个已经是字符串的带符号数字，用 `zfill`。**

### 4.4 性能：与 rjust 同量级，优于格式化语法

如果只看"补零到 8 位"这件事，各方案的耗时（Python 3.12，每次调用平均微秒数）：

| 方案 | 平均耗时（微秒/次） | 相对开销 |
|------|-------------------|---------|
| `'42'.zfill(8)` | 0.055 | 基准 |
| `'42'.rjust(8, '0')` | 0.052 | 基本持平 |
| `format('42', '0>8')` | 0.086 | 约 1.6 倍 |
| `f'{42:08d}'` | 0.100 | 约 1.8 倍 |

`zfill` 与 `rjust` 性能几乎一致——**选择哪个纯粹看语义，不必为性能纠结**。格式化语法慢一些，是因为它要走完整的格式说明解析流程；但它换来的是精度、千分位、符号标志这些 `zfill` 不具备的能力，这笔开销通常是值得的。

需要强调的是：**这个量级的差异（不到 0.05 微秒）在绝大多数程序里都无关紧要**。只有在真正热点路径上批量处理千万级字符串时，这个数字才有意义。日常选型请以语义正确为准。

## 5. 总结

本文围绕 `str.zfill` 方法展开，主要介绍了以下内容：

- **基本语义**：`zfill(width)` 在左侧补 ASCII `'0'` 直到总长度达到 `width`，只补不砍，`width <= len(s)` 时原样返回原对象。
- **填充内容固定**：填充字符写死为 `'0'`，不可指定；不校验内容是否为数字，按码点计数长度，与终端显示宽度无关。
- **符号前缀处理是核心特性**：首字符为 `+` 或 `-` 时补的 0 插在符号之后；判定只看首字符、不做语法解析、只认 ASCII 符号，U+2212 等 Unicode 减号会被当成普通字符。
- **与相邻工具的边界**：`rjust(width, '0')` 在无符号时等价、有符号时会把符号推到右边；f-string 的数值格式说明能对齐并主动添加符号，但对字符串的 `0>` 只做右对齐。
- **参数纪律**：`width` 必须实现 `__index__` 协议，参数个数必须恰好 1 个，负数宽度按"无需补充"静默处理，`int` 上没有这个方法。
- **最佳实践**：数值用 f-string、字符串补零用 `zfill`；定宽编号、时间字段、带符号金额、可排序文件名四类场景的模板；七类常见错误模式及其修正；一张方法选择速查表。
- **原理**：`zfill` 的全部逻辑就是"长度判断 + 首字符判断"，纯 Python 四行即可复现并与内置实现完全一致；填充字符与不校验内容都是有意为之的克制设计；性能与 `rjust` 持平。
