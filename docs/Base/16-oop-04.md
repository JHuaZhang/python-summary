## 1. 介绍

### 1.1 什么是类属性与实例属性

在 Python 面向对象编程中，"属性"是挂在对象上的数据。但属性并不是铁板一块——它分为两种来源截然不同的类别：**类属性**与**实例属性**。理解两者的区别，是写好任何一个类的前提，也是排查"为什么两个实例的数据会互相串""为什么改了一个全变了"这类诡异 bug 的关键。

**类属性**：定义在类体中、但在任何方法之外（不写在 `__init__` 等实例方法里）的变量。它归属于类这个对象本身，存储在类的 `__dict__` 中。由于所有实例都由这个类创建，所以类属性被该类的所有实例共享——你可以把它理解成"全班同学共用的黑板"，任何人都能看到，内容只有一块。

**实例属性**：通常在 `__init__` 方法里通过 `self.attr = value` 定义，归属于具体的某个实例对象，存储在该实例自己的 `__dict__` 中。每个实例的实例属性互相独立——就像"每个同学自己的笔记本"，你在自己本子上写的内容，不会出现在别人的本子上。

这两者的核心差异可以用一句话概括：**类属性一份大家共享，实例属性每人一份互不干扰**。但这句话背后隐藏着大量细节：访问时 Python 怎么决定读哪一份？赋值时又写到哪一份？可变类属性为什么会"串台"？类属性适合用来做什么？这些都将在后面展开。

先看一个最小示例，直观感受两者的位置与可见性：

```python
class Dog:
    # 类属性：写在类体、方法之外
    species = "Canis lupus familiaris"  # 所有狗共享的"物种"

    def __init__(self, name):
        # 实例属性：写在 __init__ 里，通过 self 绑定到具体实例
        self.name = name  # 每只狗各自的名字


dog_a = Dog("旺财")
dog_b = Dog("大黄")

# 类属性：所有实例都能访问，读的是同一份
print(dog_a.species)   # 实例也能访问类属性
print(dog_b.species)   # 两只狗看到的内容完全一样
print(Dog.species)     # 也可以直接通过类访问

# 实例属性：各实例各自一份，互不影响
print(dog_a.name)      # 旺财
print(dog_b.name)      # 大黄
# 输出：
# Canis lupus familiaris
# Canis lupus familiaris
# Canis lupus familiaris
# 旺财
# 大黄
```

上面的 `species` 是类属性，`name` 是实例属性。注意一个关键现象：`dog_a.species` 这种"实例访问类属性"的写法是合法的——这正是后面要讲的属性查找机制在起作用。

### 1.2 基础语法与最小用法

类属性的语法定义非常简单：**在类体中、方法之外直接赋值**即可。实例属性的语法定义则是：**在方法内通过 `self.attr = value` 赋值**（最常见于 `__init__`）。

```python
class Config:
    # ① 类属性：直接在类体中赋值
    version = "1.0.0"          # 常量型类属性，全局共享
    timeout = 30               # 默认配置型类属性
    max_retry = 3              # 所有实例共用的重试上限

    def __init__(self, env):
        # ② 实例属性：在 __init__ 中通过 self 赋值
        self.env = env         # 每个实例各自的运行环境
        self.status = "idle"   # 每个实例各自的状态

    def run(self):
        # 方法内也可以读类属性，直接用 self 或类名都行
        print(f"[{self.env}] v{self.version}, 超时{self.timeout}s")
        self.status = "running"  # 改的是实例属性
```

读写规则速览（先建立直觉，细节在第 2 章和第 4 章展开）：

| 操作 | 写法 | 实际影响对象 |
|------|------|-------------|
| 读类属性 | `ClassName.attr` / `obj.attr`（若实例未遮蔽） | 类 `__dict__` |
| 改类属性 | `ClassName.attr = x` | 类 `__dict__`，所有实例受影响 |
| 读实例属性 | `obj.attr` | 实例 `__dict__`（找不到才去类找） |
| 写实例属性 | `obj.attr = x` | 实例 `__dict__`，不影响类与其他实例 |

注意最后一行：**通过实例 `obj.attr = x` 赋值，永远不会修改类属性**，它只会在该实例的 `__dict__` 里新建/覆盖一个同名属性，"遮蔽"掉类属性。这是初学者最容易踩的坑之一，后面会反复演示。

## 2. 核心内容

### 2.1 类属性的存储位置与共享本质

类属性之所以"被所有实例共享"，根本原因在于它的存储位置。Python 中每个类对象自身也有一个 `__dict__`，类属性就放在这里；每个实例对象也有自己的 `__dict__`，实例属性放在这里。两者是**两个不同的字典**，物理上分开存储。

```python
class Counter:
    total = 0  # 类属性

    def __init__(self):
        self.value = 0  # 实例属性


c1 = Counter()
c2 = Counter()

# 类的 __dict__ 里有 total，没有 value
print("total" in Counter.__dict__)   # True
print("value" in Counter.__dict__)   # False

# 每个实例的 __dict__ 里有 value，没有 total
print(c1.__dict__)   # {'value': 0}
print(c2.__dict__)   # {'value': 0}
print("total" in c1.__dict__)        # False —— 实例 __dict__ 里没有 total
# 输出：
# True
# False
# {'value': 0}
# {'value': 0}
# False
```

从输出可以清楚看到：`total` 只存在于 `Counter.__dict__`，`c1` 和 `c2` 的 `__dict__` 里都没有它。那为什么 `c1.total` 还能读到？因为访问 `c1.total` 时，Python 先在 `c1.__dict__` 里找，没找到，就自动"往上"去 `Counter.__dict__` 里找——这就是共享的本质：**实例自己没有，但能借到类的那一份**。

既然只有一份，那么通过类名修改它，所有实例再读时自然都会看到新值：

```python
class Counter:
    total = 0


c1 = Counter()
c2 = Counter()

print(c1.total, c2.total)   # 0 0
Counter.total = 100         # 通过类名改类属性
print(c1.total, c2.total)   # 100 100 —— 所有实例看到的都变了
# 输出：
# 0 0
# 100 100
```

**共享意味着一处修改、全员可见**。这一点既是有用特性的来源（如统计计数器、全局配置），也是危险陷阱的来源（如可变类属性的"串台"，见 2.5）。

### 2.2 实例属性的独立性与 per-instance 存储

实例属性写在 `__init__` 里，每次创建实例时都会执行一次 `__init__`，所以每个实例都会获得自己的一份副本，存入各自的 `__dict__`。这意味着修改一个实例的实例属性，对其他实例毫无影响。

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount  # 只改当前实例的 balance


a1 = Account("张三", 100)
a2 = Account("李四", 200)

a1.deposit(50)  # 张三存 50
print(a1.balance)   # 150 —— 只影响 a1
print(a2.balance)   # 200 —— a2 不受影响
print(a1.__dict__, a2.__dict__, sep="\n")
# 输出：
# 150
# 200
# {'owner': '张三', 'balance': 150}
# {'owner': '李四', 'balance': 200}
```

两个实例的 `__dict__` 是完全独立的字典，互不牵连。这就是"每人一份笔记本"的物理体现。

### 2.3 访问顺序：先实例 __dict__ 再类 __dict__

当写下 `obj.attr` 去读取时，Python 并不是"随便找一个有的地方"，而是遵循严格的查找顺序：**先在实例自己的 `__dict__` 里找；找不到，再去类（及其基类）的 `__dict__` 里找**。这个顺序和 Python 作用域的 LEGB 规则（Local → Enclosing → Global → Built-in）可以类比：都是从近到远、先自身再外层。

```python
class User:
    role = "guest"   # 类属性：默认角色

    def __init__(self, name, role=None):
        self.name = name
        if role is not None:
            self.role = role  # 在实例 __dict__ 里也放一个同名 role


u1 = User("访客甲")          # 不传 role，实例 __dict__ 里没有 role
u2 = User("管理员乙", "admin")  # 传了 role，实例 __dict__ 里有 role

print(u1.role)   # guest  —— 实例没有，去类里借
print(u2.role)   # admin  —— 实例自己有，优先用自己的
print(User.role) # guest  —— 直接看类
# 输出：
# guest
# admin
# guest
```

关键现象：`u1` 和 `u2` 都能访问 `.role`，但读到的值不同。因为 `u2` 的实例 `__dict__` 里有 `role='admin'`，查找时第一步就命中，不再去类里找；`u1` 的实例 `__dict__` 里没有 `role`，查找落空后才"向上"借到类的 `'guest'`。

**访问顺序对照表**：

| 读取 `obj.attr` 的步骤 | 查找位置 | 命中则返回 | 未命中则 |
|----------------------|---------|-----------|---------|
| 第 1 步 | 实例 `obj.__dict__` | 实例属性值 | 进入第 2 步 |
| 第 2 步 | 类 `type(obj).__dict__` 及基类 MRO | 类属性值 | 进入第 3 步 |
| 第 3 步 | 调用 `__getattr__`（若定义了）或抛 `AttributeError` | 自定义结果 | 报错 |

这个"先实例后类"的顺序是后面所有现象（遮蔽、共享、陷阱）的统一解释，务必记牢。

### 2.4 遮蔽：实例赋值同名属性不修改类属性

理解了访问顺序，就能解释一个最容易让人困惑的行为：**通过实例 `obj.attr = x` 赋值，不会修改类属性**。因为赋值走的是 `__setattr__`，它默认把数据写进实例自己的 `__dict__`，根本不碰类的 `__dict__`。如果实例 `__dict__` 里原本没有这个键，赋值后就新建一个；如果有，就覆盖。总之，类的那一份原封不动。

这就产生"遮蔽"（shadowing）效果：实例 `__dict__` 里多了一个和类属性同名的键，以后该实例再读 `obj.attr` 时，第 1 步就命中实例自己的值，永远读不到类属性了——就像"自己的笔记本盖住了黑板上的字"。

```python
class Printer:
    mode = "draft"   # 类属性：默认打印模式

    def __init__(self, name):
        self.name = name


p1 = Printer("打印机A")
p2 = Printer("打印机B")

# 初始状态：两个实例都能读到类的 mode
print(p1.mode, p2.mode, Printer.mode)   # draft draft draft

# 通过实例 p1 给同名属性赋值
p1.mode = "final"   # 这不是改类属性，而是在 p1.__dict__ 新建 mode

# 结果：p1 被遮蔽，p2 和类不受影响
print(p1.mode)        # final  —— p1 自己有了，读自己的
print(p2.mode)        # draft  —— p2 没有自己那份，仍读类
print(Printer.mode)   # draft  —— 类属性根本没动
print("p1.__dict__:", p1.__dict__)
print("p2.__dict__:", p2.__dict__)
# 输出：
# draft draft draft
# final
# draft
# draft
# p1.__dict__: {'name': '打印机A', 'mode': 'final'}
# p2.__dict__: {'name': '打印机B'}
```

从 `__dict__` 可以直观看到：`p1` 多了一个 `mode` 键，`p2` 没有；类的 `mode` 自始至终都是 `'draft'`。

**如果想"撤销"遮蔽，恢复读取类属性**，只需用 `del` 删除实例自己的那份：

```python
del p1.mode       # 删掉实例 __dict__ 里的 mode
print(p1.mode)    # draft —— 又回到读类属性了
# 输出：
# draft
```

**常见误区**

很多初学者想"用一个实例去改类的共享属性"，于是写 `p1.mode = "final"`，以为这样所有实例都会变成 `final`——结果只有 `p1` 变了，其他实例纹丝不动。正确做法是用类名赋值：`Printer.mode = "final"`，这样改的是类的 `__dict__`，所有未被遮蔽的实例都会看到新值。

### 2.5 可变类属性的共享陷阱

前面讲的都是不可变对象（数字、字符串）作为类属性，遮蔽就遮蔽了，不会出大乱子。但当类属性是**可变对象**（列表、字典、集合等）时，一个隐蔽的陷阱就出现了：所有实例"共享"的其实是**同一个对象的引用**。任何一个实例对这个可变对象做原地修改（如 `list.append`、`dict[k]=v`），改的都是那唯一一份，于是所有实例都会看到变化——哪怕你本意只是想给某个实例自己加一条数据。

```python
class Team:
    members = []   # 可变类属性：列表

    def __init__(self, name):
        self.name = name

    def add_member(self, member):
        self.members.append(member)   # 原地修改，改的是共享的那份


t1 = Team("一组")
t2 = Team("二组")

t1.add_member("张三")   # 本意：给一组的成员列表加人
print(t1.members)   # ['张三']
print(t2.members)   # ['张三'] —— 二组也出现了张三！
print(Team.members) # ['张三'] —— 类的那份也被改了
print(t1.members is t2.members)  # True —— 两个实例引用的是同一个列表对象
# 输出：
# ['张三']
# ['张三']
# ['张三']
# True
```

`is` 判断为 `True` 说明 `t1.members` 和 `t2.members` 根本是同一个对象。这就是"串台"的本质：可变类属性只有一份，原地修改影响所有引用者。

出错的原因在于 `self.members.append(...)` 这一行——它做的是**原地修改**，而不是赋值。原地修改不会触发 `__setattr__`，不会在实例 `__dict__` 新建 `members`，它直接作用在从类里"借"来的那个共享列表上。所以"借来 → 改 → 还回去还是那一份"，全员可见。

**正确写法：把可变默认值放到实例属性里**

如果希望每个实例拥有各自独立的列表，应该在 `__init__` 里为每个实例新建一个列表：

```python
class Team:
    def __init__(self, name):
        self.name = name
        self.members = []   # 每个实例各自一份，互不干扰

    def add_member(self, member):
        self.members.append(member)


t1 = Team("一组")
t2 = Team("二组")
t1.add_member("张三")
print(t1.members)   # ['张三']
print(t2.members)   # [] —— 二组干净
print(t1.members is t2.members)  # False —— 不同对象
# 输出：
# ['张三']
# []
# False
```

这条规则和"函数默认参数不要用可变对象"是同一个道理：可变默认值被共享，会引发意想不到的跨调用/跨实例污染。记忆口诀：**可变默认值，永远放到 `__init__` 里新建**。

### 2.6 类属性的典型用途

既然类属性有"一份共享"的特性，它天然适合那些"全局性"的数据。常见的合法用途有几类：

**① 计数器：统计创建了多少个实例**

```python
class Connection:
    count = 0   # 类属性：记录已创建的连接数

    def __init__(self, host):
        self.host = host
        Connection.count += 1   # 通过类名改类属性，确保改的是共享那份

    def close(self):
        Connection.count -= 1


c1 = Connection("10.0.0.1")
c2 = Connection("10.0.0.2")
c3 = Connection("10.0.0.3")
print(Connection.count)   # 3 —— 所有实例共享同一个计数器
# 输出：
# 3
```

注意这里用的是 `Connection.count += 1` 而非 `self.count += 1`。如果写成 `self.count += 1`，由于 `+=` 对不可变对象等价于"读后赋值"，赋值会走 `__setattr__` 写到实例 `__dict__`，结果每个实例都会有自己的 `count`，计数器就失效了（见 3.2 的详细分析）。

**② 常量：放一些不会变的类级常量**

```python
class MathUtils:
    PI = 3.141592653589793
    E = 2.718281828459045

    def circle_area(self, r):
        return self.PI * r * r   # 读类常量


m = MathUtils()
print(m.circle_area(2))        # 用实例访问类常量
print(MathUtils.PI)            # 也可通过类直接访问
# 输出：
# 12.566370614359172
# 3.141592653589793
```

**③ 默认配置：所有实例共用的默认参数**

```python
class HttpClient:
    timeout = 30        # 类属性：默认超时
    max_retry = 3       # 类属性：默认重试次数
    base_url = ""       # 类属性：默认基础地址

    def __init__(self, base_url=None):
        if base_url is not None:
            self.base_url = base_url   # 实例可遮蔽，用自定义值

    def request(self, path):
        print(f"请求 {self.base_url}{path}, 超时{self.timeout}s, 重试{self.max_retry}次")


client_default = HttpClient()
client_default.request("/api/users")
# 输出：请求 /api/users, 超时30s, 重试3次

client_custom = HttpClient("https://example.com")
client_custom.timeout = 60   # 实例级遮蔽，只改自己的超时
client_custom.request("/api/users")
# 输出：请求 https://example.com/api/users, 超时60s, 重试3次
# 输出：
# 请求 /api/users, 超时30s, 重试3次
# 请求 https://example.com/api/users, 超时60s, 重试3次
```

这里演示了类属性作为默认值、实例属性作为可覆盖值的经典组合：类属性提供"开箱即用的默认行为"，实例属性提供"按需定制"的能力，访问顺序保证了"有定制用定制，没定制用默认"。

**④ 类型标识：表示所有实例共有的类别信息**

```python
class Animal:
    kingdom = "Animalia"   # 所有动物共有的"界"
    species = None         # 由子类覆盖

    def info(self):
        print(f"界: {self.kingdom}, 种: {self.species}")


class Cat(Animal):
    species = "Felis catus"


class Dog(Animal):
    species = "Canis lupus familiaris"


Cat().info()
Dog().info()
# 输出：
# 界: Animalia, 种: Felis catus
# 界: Animalia, 种: Canis lupus familiaris
```

子类通过覆盖类属性 `species` 来表达"本子类的所有实例都属于某某种"，这是面向对象中"类级元数据"的典型用法。

### 2.7 通过类名 vs 通过实例操作类属性

改类属性只有一种可靠方式：**通过类名赋值** `ClassName.attr = x`。通过实例赋值 `obj.attr = x` 不会改类属性，只会遮蔽。这一节用对照实验把两者彻底讲清。

```python
class Sensor:
    unit = "℃"   # 类属性：所有传感器默认单位

    def __init__(self, value):
        self.value = value


s1 = Sensor(36)
s2 = Sensor(28)

# 【操作 A】通过类名改类属性
Sensor.unit = "°F"
print(s1.unit, s2.unit, Sensor.unit)
# 全员变化，因为改的是共享那份
# 输出：°F °F °F

# 【操作 B】通过实例赋值同名属性
s1.unit = "K"   # 只在 s1.__dict__ 新建 unit，遮蔽类属性
print(s1.unit, s2.unit, Sensor.unit)
# s1 读自己的，s2 和类仍是上一步的值
# 输出：K °F °F

# 【操作 C】再通过类名改类属性
Sensor.unit = "℃"
print(s1.unit, s2.unit, Sensor.unit)
# 注意：s1 已被遮蔽，仍读自己的 K；s2 未遮蔽，跟随类变化
# 输出：K ℃ ℃
# 输出：
# °F °F °F
# K °F °F
# K ℃ ℃
```

最后一步最重要：一旦某个实例被遮蔽，它就和类属性"脱钩"了，之后类属性再怎么变，该实例都读自己的固定值。这一点在调试时极具迷惑性——"为什么别人都变了就它没变"，多半是因为它早先被实例赋值遮蔽过。

**访问与修改对照速查表**

| 操作 | 写法 | 改了谁的 `__dict__` | 对其他实例的影响 |
|------|------|---------------------|------------------|
| 读 | `obj.attr` | 不改 | — |
| 读 | `ClassName.attr` | 不改 | — |
| 改类属性 | `ClassName.attr = x` | 类 | 所有未遮蔽实例都变 |
| 新建实例属性（遮蔽） | `obj.attr = x` | 实例 | 仅该实例 |
| 删除实例属性（撤销遮蔽） | `del obj.attr` | 实例（删键） | 该实例重新读类 |
| 原地改可变类属性 | `obj.list_attr.append(x)` | 类（对象本身） | 所有实例都变 |

## 3. 最佳实践

### 3.1 可变默认值不要放类属性

这是第一位的铁律。只要一个属性的默认值是可变对象（list、dict、set、甚至自定义对象），就**不要**写成类属性，而要在 `__init__` 里为每个实例新建。

**不推荐**

```python
class Order:
    items = []   # 危险：所有实例共享同一个列表

    def add(self, item):
        self.items.append(item)
```

**推荐**

```python
class Order:
    def __init__(self):
        self.items = []   # 每个实例各自一份

    def add(self, item):
        self.items.append(item)
```

原因已在 2.5 详述：可变类属性只有一份，原地修改会污染所有实例。把可变对象放进 `__init__`，每次创建实例都执行一次 `self.items = []`，保证每份独立。

### 3.2 计数器/累加器必须通过类名修改

当用类属性做"统计创建实例数"这类计数器时，修改语句一定要写 `ClassName.count += 1`，不要写 `self.count += 1`。

原因在于 `+=` 对不可变对象（如 int）展开后是 `self.count = self.count + 1`：先读（此时 `self.count` 若实例没有，会借到类的值，比如 0），再赋值（赋值走 `__setattr__`，写到实例 `__dict__`）。于是第一个实例第一次执行后，实例 `__dict__` 里就有了 `count=1`，从此和类的 `count` 脱钩——计数器在类层面永远是 0，各实例各算各的。

**不推荐**

```python
class BadCounter:
    count = 0

    def __init__(self):
        self.count += 1   # 错：会在实例 __dict__ 新建 count


for _ in range(5):
    BadCounter()
print(BadCounter.count)   # 0 —— 类计数器根本没动
# 输出：0
```

**推荐**

```python
class GoodCounter:
    count = 0

    def __init__(self):
        GoodCounter.count += 1   # 对：明确改类属性


for _ in range(5):
    GoodCounter()
print(GoodCounter.count)   # 5
# 输出：5
```

### 3.3 优先用实例属性存"每份数据"，用类属性存"共享元数据"

**不推荐**

```python
class User:
    name = ""   # 把本应每位用户各自有的数据写成类属性
    age = 0
```

**推荐**

```python
class User:
    default_role = "guest"   # 共享的默认值，适合类属性

    def __init__(self, name, age):
        self.name = name     # 每位用户各自的数据，用实例属性
        self.age = age
```

判断标准很简单：**这个数据是"每个人都不同"还是"大家都一样"？** 每个人都不同的数据（姓名、年龄、余额）必须用实例属性；大家都一样的元数据/默认值/常量（默认角色、版本号、超时配置）适合用类属性。混用会导致两类问题：本应独立的数据互相串，或本应共享的数据被各实例遮蔽后无法统一更新。

### 3.4 读类属性时优先用类名，读实例属性时用 self

在方法内部读取类属性，既可以用 `self.attr`（依赖查找机制），也可以用 `ClassName.attr`（直接取类那份）。两者在"实例未被遮蔽"时结果一致，但语义清晰度不同。

**推荐**

```python
class Config:
    timeout = 30

    def show(self):
        print(Config.timeout)   # 明确"我要读的是类那份"
```

用 `ClassName.attr` 能让意图更清晰：读者一看就知道这是在访问类级常量，而不是某个可能被遮蔽的实例属性。尤其在大型代码里，`self.timeout` 可能被某处实例赋值遮蔽过，用 `self` 读取会得到不确定的结果；用 `Config.timeout` 则始终读到类的那一份，行为可预测。

当然，如果就是想享受"实例可覆盖默认值"的机制，则用 `self.attr` 是正确的，这正是 2.6 ③ 的用法。关键是有意识地区分两种写法，不要随手都用 `self`。

### 3.5 不要用类属性做"实例间通信"

有人发现类属性能被所有实例看到，就把它当成"实例间传递消息"的通道——在实例 A 里改类属性，在实例 B 里读。这种做法可维护性极差：谁改的、何时改的、改之前是什么值，全无保障；一旦有实例遮蔽了同名属性，通信链路就断了。

**不推荐**

```python
class Worker:
    shared_state = {}   # 当作全局通信板


w1 = Worker()
w2 = Worker()
w1.shared_state["key"] = "value"   # 想让 w2 看到
# 能工作，但脆弱、难追踪
```

如果有跨实例共享状态的需求，更合适的做法是：用专门的模块级变量、用单例模式、或显式传入一个共享对象。类属性做通信板只适合非常小的脚本，不适合严肃项目。

## 4. 原理

### 4.1 属性查找的 __getattribute__ 机制

前面反复说"先查实例 `__dict__` 再查类"，这背后的实际执行者是特殊方法 `__getattribute__`。每次写 `obj.attr` 读取时，Python 都会调用 `type(obj).__getattribute__(obj, 'attr')`（如果没自定义，就用 object 默认的实现）。默认实现的查找流程可以概括为以下几步：

1. **先查实例 `__dict__`**：在 `obj.__dict__` 里找 `'attr'`。命中则返回对应值（如果值同时定义了 `__get__`，如描述符，还要走描述符协议，见 4.4）。
2. **再查类及基类的 `__dict__`**：按 MRO（方法解析顺序）遍历 `type(obj)` 及其基类的 `__dict__`。命中则返回（同样可能涉及描述符协议）。
3. **都未命中，尝试 `__getattr__`**：如果类定义了 `__getattr__` 方法，调用它做兜底处理；可以返回一个值，也可以主动抛 `AttributeError`。
4. **都没有，抛 `AttributeError`**。

注意 `__getattr__` 和 `__getattribute__` 的区别：`__getattribute__` 是**每次访问都调用**的"前门"，默认实现已经把"先实例后类"的逻辑写死了；`__getattr__` 是**只有正常查找落空才调用**的"兜底后门"，适合实现"动态生成属性"这类高级需求。不建议重写 `__getattribute__`，它影响每一次属性访问，稍有疏忽就会引发无限递归或性能问题。

```python
class Demo:
    class_attr = "我是类属性"

    def __init__(self):
        self.instance_attr = "我是实例属性"

    def __getattr__(self, name):
        print(f"  [__getattr__ 被调用，请求属性: {name}]")
        return f"<默认值:{name}>"


d = Demo()
print(d.instance_attr)   # 第 1 步命中实例 __dict__
print(d.class_attr)      # 第 1 步落空，第 2 步命中类 __dict__
print(d.not_exist)       # 第 1、2 步都落空，第 3 步调用 __getattr__
# 输出：
# 我是实例属性
# 我是类属性
#   [__getattr__ 被调用，请求属性: not_exist]
# <默认值:not_exist>
```

从输出可以看到：只有访问不存在的属性时，`__getattr__` 才会被调用。对于存在的实例属性和类属性，默认的 `__getattribute__` 直接在头两步就返回了，不会触发兜底。

MRO（Method Resolution Order，方法解析顺序）决定了第 2 步"查类及基类"时的遍历顺序。对于单继承，就是"子类 → 父类 → 父类的父类 …"；对于多继承，Python 3 使用 C3 线性化算法计算一个确定的顺序，可以用 `ClassName.__mro__` 查看：

```python
class A:
    x = "A"


class B(A):
    x = "B"


class C(A):
    x = "C"


class D(B, C):
    pass


d = D()
print(D.__mro__)
print(d.x)   # 按 MRO 找：D 没有 → B 有 'B'，命中
# 输出：
# (<class '...D'>, <class '...B'>, <class '...C'>, <class '...A'>, <class 'object'>)
# B
```

MRO 保证了在多重继承下，属性查找仍有唯一确定的顺序，不会出现歧义。

### 4.2 赋值走 __setattr__，默认只写实例 __dict__

读属性有 `__getattribute__`，写属性（`obj.attr = x`）则有 `__setattr__`。默认的 `object.__setattr__` 实现了一个关键规则：**把数据写进实例的 `__dict__`，不碰类的 `__dict__`**。这就是为什么"通过实例赋值永远不会修改类属性"。

```python
class Widget:
    color = "red"   # 类属性

    def __init__(self, name):
        self.name = name


w = Widget("按钮")
w.color = "blue"   # 走 __setattr__，写进 w.__dict__，不碰 Widget.__dict__

print(w.__dict__.get("color"))    # blue —— 实例有了自己的 color
print(Widget.__dict__["color"])   # red  —— 类属性原封不动
# 输出：
# blue
# red
```

赋值时并不做"先查后写"——不会因为实例 `__dict__` 里没有 `color`、类里有 `color`，就"贴心地"去改类的那个。`__setattr__` 只认一个目标：**当前实例的 `__dict__`**。这种"读找得到、写只写自己"的不对称设计，是有意为之的：它让实例可以有自己的定制值而不影响其他实例，同时也埋下了"误以为实例赋值能改共享属性"的陷阱。

`+=`、`-=` 这类增量赋值对不可变对象（int、str 等）等价于"读取 + 赋值"两步。以 `self.count += 1` 为例：先执行读取 `self.count`（可能借到类的值），得到结果 `旧值 + 1`，再执行赋值 `self.count = 结果`（走 `__setattr__` 写实例 `__dict__`）。所以一旦执行过一次，实例就拥有了独立的 `count`，和类的 `count` 脱钩。这就解释了 3.2 中"计数器必须用类名"的原因。

对可变对象（list、dict），`self.list_attr.append(x)` 走的是另一条路：`append` 是方法调用，不是赋值。`self.list_attr` 读取时若实例没有，就借到类的那个共享列表对象，然后在这个对象上原地修改——既没走 `__setattr__`，也没在实例 `__dict__` 新建任何键，改的就是类的那唯一一份。这就是 2.5 陷阱的根源。

### 4.3 可变类属性共享同一对象的引用本质

Python 中"共享"的本质是"多个名字绑定到同一个对象"。对于类属性 `Team.members = []`，这个列表对象在类定义执行时创建一次，存入 `Team.__dict__['members']`。当实例 `t1` 访问 `t1.members` 时，查找机制借到的是**同一个对象的引用**——`t1.members` 这个名字和 `Team.members` 这个名字指向内存里同一个列表。

```python
class Team:
    members = []


t1 = Team()
t2 = Team()

# 三个名字指向同一个列表对象
print(Team.members is t1.members)   # True
print(Team.members is t2.members)   # True
print(t1.members is t2.members)     # True

# 唯一一份列表的 id
print(id(Team.members), id(t1.members), id(t2.members))
# 输出（id 每次运行不同，但三者相等）：
# True
# True
# True
# 4301234560 4301234560 4301234560
```

`is` 比较的是对象身份（内存地址），三者全为 `True`，证明它们是同一个对象。`id()` 返回的内存地址也完全相同。所以 `t1.members.append("张三")` 修改的是这个唯一对象，`t2.members` 自然也能看到"张三"。

这与不可变类属性（如 `total = 0`）的"共享"有微妙差别。不可变对象没有原地修改操作——`0` 不能被"原地加 1"变成 `1`，任何改变都意味着创建新对象并重新绑定。所以对不可变类属性，你无法像 `append` 那样"悄悄改掉共享那份"，只能通过 `ClassName.attr = x` 显式地让类的名字指向新对象（此时所有未遮蔽的实例再读取，会借到这个新对象）。而对可变类属性，原地修改不改变名字的绑定，只改变对象内部内容，所以连"显式改类"这一步都省了——后果就是改了大家都看得到。

一句话总结：**不可变类属性的共享是"名字共享、读时借值"；可变类属性的共享是"对象共享、改时同体"**，后者的危险性远高于前者。

### 4.4 描述符协议对查找的介入（进阶）

在第 4.1 节的查找流程里提到"如果值定义了 `__get__`，还要走描述符协议"。这一节简要说明描述符如何介入类属性的查找，属于进阶内容，理解了能彻底看清属性访问的全貌。

描述符（descriptor）是一个实现了 `__get__`（和可选的 `__set__`、`__delete__`）方法的类，其实例作为**另一个类的类属性**存在。函数（`function`）本身就是描述符——这就是方法能自动绑定 `self` 的原因。`property` 也是描述符，它把 `__get__`/`__set__` 转发到 getter/setter。

描述符分为两类：
- **数据描述符**：同时实现 `__get__` 和 `__set__`（如 `property` 的完整形式）。它在查找时**优先于实例 `__dict__`**。
- **非数据描述符**：只实现 `__get__`（如普通函数）。它在查找时**晚于实例 `__dict__`**——如果实例 `__dict__` 有同名键，非数据描述符会被遮蔽，不会被调用。

因此完整的查找顺序（含描述符）是：

1. 数据描述符（在类及基类 `__dict__` 中，且定义了 `__set__`）。
2. 实例 `__dict__`。
3. 非数据描述符或普通类属性（在类及基类 `__dict__` 中）。
4. `__getattr__` 兜底。

```python
class TypedField:
    """一个简单的数据描述符：类型校验字段。"""
    def __init__(self, name, expected_type):
        self.name = name
        self.expected_type = expected_type

    def __get__(self, instance, owner):
        if instance is None:
            return self
        return instance.__dict__.get(self.name)

    def __set__(self, instance, value):
        if not isinstance(value, self.expected_type):
            raise TypeError(f"{self.name} 必须是 {self.expected_type.__name__}")
        instance.__dict__[self.name] = value


class Person:
    age = TypedField("age", int)   # 类属性是数据描述符

    def __init__(self, age):
        self.age = age   # 触发描述符 __set__，而非简单写实例 __dict__


p = Person(20)
print(p.age)   # 触发描述符 __get__
try:
    p.age = "二十"   # 触发 __set__，类型不符抛错
except TypeError as e:
    print(e)
# 输出：
# 20
# age 必须是 int
```

这里 `Person.age` 是一个数据描述符，它拦截了对 `p.age` 的读写：读走 `__get__`，写走 `__set__`。即使是"通过实例赋值"，也不会简单地把值塞进实例 `__dict__`，而是交给描述符的 `__set__` 处理（描述符自己决定最终存哪——这里它存在实例 `__dict__` 里，但用的是内部名 `self.name`）。这就是为什么说"通过实例赋值默认只写实例 `__dict__`"——前提是没有数据描述符拦截；一旦有数据描述符，`__setattr__` 会优先调用描述符的 `__set__`。

对于普通类属性（非描述符，如 `total = 0`、`members = []`），查找遵循 4.1 的简化流程：先实例 `__dict__`，后类 `__dict__`，没有描述符介入。本篇前面讲的所有例子都属于这一类。

## 5. 总结

### 5.1 本文内容要点

- **类属性**定义在类体、方法之外，存于类的 `__dict__`，被所有实例共享；**实例属性**通常在 `__init__` 中通过 `self` 定义，存于各实例自己的 `__dict__`，互相独立。
- 读取 `obj.attr` 时，`__getattribute__` 按"先实例 `__dict__` → 后类及基类 `__dict__`（按 MRO）→ `__getattr__` 兜底 → 否则 `AttributeError`"的顺序查找。
- 赋值 `obj.attr = x` 走 `__setattr__`，默认只写实例 `__dict__`，不碰类的 `__dict__`；因此通过实例给同名属性赋值，只会在实例 `__dict__` 新建/覆盖一个键，"遮蔽"类属性，而不会修改类属性。
- 修改类属性的正确方式是 `ClassName.attr = x`，这会改变所有未遮蔽实例读取到的值；已被遮蔽的实例不受影响，仍读自己的那份。
- 可变类属性（list、dict 等）被所有实例共享的是"同一个对象的引用"，任何实例对其做原地修改（`append`、`dict[k]=v`）都会影响所有实例——这是高频陷阱，可变默认值必须放到 `__init__` 里为每个实例新建。
- 类属性的典型合法用途：实例计数器（通过类名 `+=`）、类级常量、默认配置、类型标识元数据；不适合放"每 instance 各异的数据"或做"实例间通信板"。
- 在有数据描述符（如 `property`）介入时，查找顺序会有调整：数据描述符优先于实例 `__dict__`，非数据描述符（如普通函数）晚于实例 `__dict__`。

### 5.2 读完应能掌握

- 能区分类属性与实例属性的存储位置（类 `__dict__` vs 实例 `__dict__`），并说出"共享"与"独立"的物理原因。
- 能复述属性查找的完整顺序（实例 `__dict__` → 类及基类 `__dict__` 按 MRO → `__getattr__`），并解释为什么实例能访问类属性、为什么实例的同名属性会"遮蔽"类属性。
- 能说明 `obj.attr = x` 走 `__setattr__` 默认写实例 `__dict__`、不修改类属性的原因，并能用 `ClassName.attr = x` 正确地修改共享类属性。
- 能诊断并修复"可变类属性串台"bug，把可变默认值迁移到 `__init__` 中 per-instance 新建。
- 能正确实现"统计实例数"的类属性计数器，解释为什么必须用 `ClassName.count += 1` 而非 `self.count += 1`。
- 能根据"每份数据都不同"还是"大家都一样"这一标准，判断属性应写成实例属性还是类属性，并能用类属性表达常量、默认配置、类型元数据。
- 能说出 `__getattribute__` 与 `__getattr__` 的区别，以及数据描述符与非数据描述符在查找顺序中的位置。
