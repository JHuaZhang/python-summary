## 1. 介绍

### 1.1 什么是实例方法

在面向对象编程中，一个类往往既承载数据（属性），也承载行为（方法）。**实例方法**就是定义在类体内部、用来操作"某个具体实例"的函数。它和普通函数最关键的区别在于：它的第一个参数永远接收"调用它的那个实例"，习惯上写作 `self`。

可以这样理解：类是一张图纸，实例是根据图纸造出来的具体产品；实例方法则是"附在产品上的操作手册"，每件产品各自拿着一本手册，但手册内容（方法代码）只有一份，存放在图纸（类）那里。当你对某件产品发出指令（调用方法）时，手册会自动知道"现在该操作的是这件产品"，这就是 `self` 的来源。

```python
class Stack:
    """一个极简的栈，用来体会实例方法的基本形态。"""

    def __init__(self):
        self._items = []          # 实例属性，存放栈内元素

    def push(self, value):        # 第一个参数 self 是调用该方法的实例
        self._items.append(value) # 通过 self 操作"这个"实例的数据

    def pop(self):
        return self._items.pop()

s = Stack()
s.push(10)                        # 等价于 Stack.push(s, 10)
s.push(20)
print(s.pop())                    # 通过实例调用，self 自动绑定到 s
# 输出：20
```

上面这个 `Stack` 类就是实例方法最典型的写法：`push` 和 `pop` 都是定义在类体里的普通 `def`，第一个形参 `self` 指向调用它们的那个 `Stack` 实例。`s.push(10)` 这一行，Python 会在背后把它翻译成 `Stack.push(s, 10)`——把实例 `s` 作为 `self` 传进去，再把 `10` 作为 `value` 传进去。也就是说，`self` 并不是什么关键字，只是一个约定俗成的形参名，它由"调用机制"负责填充，不需要你手动写。

实例方法在 Python 面向对象体系里是出现频率最高的成员：绝大多数业务逻辑、数据加工、状态变更、协议方法（`__str__`、`__len__`、`__eq__` 等）都以实例方法的形式存在。理解了 `self` 的绑定机制、三种调用方式、方法与函数的区分，就等于握住了 OOP 的钥匙。

### 1.2 基本语法与最小用法

实例方法的基本形式很朴素，就是写在类体里的 `def`：

```text
class 类名:
    def 方法名(self, 形参1, 形参2, ...):
        方法体
        return 返回值
```

几个要点先记在心里：

- 第一个形参名几乎总是写 `self`，但 Python 并不强制叫这个名字，它只是一个社区约定；写成 `this`、`me` 也能跑，只是不要那样做。
- 调用时，通过 `实例.方法名(实参...)` 的方式调用，`self` 由解释器自动填入，你只要传"后面的"参数。
- 方法体内部通过 `self.属性名` 访问/修改实例属性，通过 `self.其他方法名()` 调用同一实例的其它方法。
- 实例方法本质上是"存在类身上的函数"，实例本身并不保存方法的副本——这一点会在原理章详细展开。

下面是一个最完整的最小用法，覆盖定义、调用、访问属性、调用其他方法四个动作：

```python
class Counter:
    def __init__(self, start=0):
        self.count = start        # 在实例方法里初始化实例属性

    def inc(self, step=1):
        self.count += step        # 通过 self 修改实例属性
        self._log("inc")          # 在方法里调用本实例的另一个方法
        return self.count

    def _log(self, action):
        # 也是实例方法，通过 self 访问实例属性
        print(f"[Counter#{id(self):x}] {action} -> {self.count}")

c = Counter(5)
print(c.inc(2))                   # 通过实例调用，self 自动绑定到 c
# 输出：
# [Counter#...] inc -> 7
# 7
```

这里的 `_log` 虽然命名以单下划线开头表示"内部使用"，但它本质上和 `inc` 一样是实例方法，只是社区约定不把它当公开 API。`c.inc(2)` 把 `c` 绑定为 `self`，`inc` 内部的 `self._log("inc")` 又会把同一个 `c` 作为 `self` 传给 `_log`，所以两个方法操作的是同一个实例的状态。这种"方法之间通过 `self` 互相调用"是面向对象里把逻辑拆分到多个方法的基础。

## 2. 核心内容

### 2.1 self 参数：指向调用实例

`self` 是实例方法的灵魂。它不是 Python 的关键字，只是一个普通形参，之所以在每个方法里都写它，是因为 Python 的方法调用机制规定：**通过实例调用方法时，实例本身会被作为第一个位置参数传入**。这个参数名社区统一写作 `self`，遵守这个约定即可。

**为什么要这么设计？** 因为方法代码只有一份，存在类身上；当多个实例都调用同一个方法时，解释器必须有一个机制告诉方法"现在该操作哪一个实例"。把实例作为第一个参数显式传进去，就是最直接的做法。对比 Java/C++ 里隐式的 `this`，Python 选择了显式——`self` 明明白白出现在形参列表里，方法体内每一次访问实例状态都要写 `self.xxx`，一眼就能看出哪些是实例成员、哪些是局部变量。

```python
class Light:
    def __init__(self):
        self.on = False

    def toggle(self):
        # self 指向"当前正在操作的"那个 Light 实例
        self.on = not self.on
        return self.on

a = Light()
b = Light()
print(a.toggle(), b.toggle())      # 两个实例各自独立
# 输出：True True
print(a.on, b.on)                  # 状态分别存储在各自的实例里
# 输出：True True
a.toggle()                         # 只翻 a，不影响 b
print(a.on, b.on)
# 输出：False True
```

可以看到，`toggle` 方法代码只有一份，但 `a.toggle()` 时 `self` 是 `a`，`b.toggle()` 时 `self` 是 `b`；方法体里 `self.on` 这一句到底改的是谁的 `on`，完全由调用时绑定的 `self` 决定。这就是实例方法能"对每个实例独立工作"的根本原因。

**self 名字不强制，但不要改**

Python 解释器只认"第一个位置参数"，不认名字，所以下面这种写法技术上能跑：

```python
class Bad:
    def greet(this, name):         # 形参名写成 this，能与 Java 对应
        return f"hi {name} from {id(this):x}"

b = Bad()
print(b.greet("Tom"))
# 输出：hi Tom from <某个十六进制 id>
```

但这是反模式，不要在真实代码里写。社区约定 `self` 是有意义的：任何 Python 开发者看到 `self` 都知道它指代实例，改成 `this` 会增加阅读负担，也会被 linter（如 pep8、flake8）警告。记住：`self` 不是关键字，但是规范。

### 2.2 obj.method(args) 与 ClassName.method(obj, args) 的等价性

这是理解实例方法最重要的一步：通过实例调用方法，和通过类调用方法、手动传入实例，二者完全等价。

```python
class Greeter:
    def __init__(self, name):
        self.name = name

    def hello(self, target):
        return f"{self.name} says hello to {target}"

g = Greeter("Alice")

# 方式一：通过实例调用，self 自动绑定
print(g.hello("Bob"))
# 输出：Alice says hello to Bob

# 方式二：通过类调用，手动把 g 作为第一个参数传进去
print(Greeter.hello(g, "Bob"))
# 输出：Alice says hello to Bob
```

两种写法得到完全一样的结果。区别只在于：

- `g.hello("Bob")`：解释器看到 `实例.方法` 这种访问，会自动把 `g` 绑定为 `self`，你只需要传 `self` 之后的参数。
- `Greeter.hello(g, "Bob")`：通过类名访问方法，得到的是未绑定的原始函数，不会自动填充 `self`，你必须显式把 `g` 作为第一个位置参数传进去。

这个等价关系不是为了炫技，它在很多真实场景里都有用：当你手头只有一个实例引用、但需要通过类名显式定位方法时（比如在子类里绕过重写调用父类方法 `Super.method(self, ...)`，或在做元编程、monkey patch、unittest.mock 时），就需要用类名形式。

**一个更直观的堆栈对比**

```python
class Stack:
    def __init__(self):
        self._items = []

    def push(self, value):
        self._items.append(value)
        return len(self._items)

    def pop(self):
        if not self._items:
            raise IndexError("pop from empty stack")
        return self._items.pop()

s = Stack()

# 方式一：实例.方法(实参)
s.push(1)
s.push(2)
print(s.pop())
# 输出：2

# 方式二：类.方法(实例, 实参)
Stack.push(s, 3)
Stack.push(s, 4)
print(Stack.pop(s))
# 输出：4
```

这段代码把 `s.push(1)` 与 `Stack.push(s, 1)` 并排放在一起，你能清楚看到：两种写法的"参数数量差 1"，差的那个就是 `self`。第一种写法时 `self` 由绑定机制悄悄塞进去；第二种写法时 `self` 由你手动塞进去。除此之外，执行流程完全一致。

**容易踩坑：忘了手动传 self**

```python
# 错误演示：通过类调用却忘了传实例
# Greeter.hello("Bob")   # TypeError: hello() missing 1 required positional argument: 'target'
```

当你写 `Greeter.hello("Bob")` 时，`"Bob"` 被填进了 `self`，于是 `target` 缺失，Python 抛出 `TypeError`。这个错误信息对新手很有迷惑性——"missing required argument 'target'"，但真正的根源是没传 `self`。记住：**通过类调用实例方法，第一个参数必须是实例**。

### 2.3 三种调用方式对比

实例方法有三种调用方式，理解它们的差异对排查问题、做元编程都很有帮助。

```python
class Widget:
    def __init__(self, label):
        self.label = label

    def render(self, ctx):
        return f"<{self.label}> in {ctx}"

w = Widget("btn")
ctx = "page"

# 方式一：通过实例调用（最常用，self 自动绑定）
r1 = w.render(ctx)
print(r1)
# 输出：<btn> in page

# 方式二：通过类调用，手动传实例（self 显式）
r2 = Widget.render(w, ctx)
print(r2)
# 输出：<btn> in page

# 方式三：拿到方法对象后，手动传实例调用
func = Widget.render       # 这是类里的原始函数（未绑定）
r3 = func(w, ctx)
print(r3)
# 输出：<btn> in page
```

三种方式的结果一模一样，但内部走的路径不同：

| 调用方式 | 写法 | self 来源 | 用途 |
|---|---|---|---|
| 实例调用 | `w.render(ctx)` | 绑定机制自动填充 | 日常 99% 的情况 |
| 类调用 | `Widget.render(w, ctx)` | 手动作为第一个参数 | 显式定位方法、父类调用、mock |
| 函数对象调用 | `Widget.render.__get__(w, Widget)(ctx)` 或直接 `func(w, ctx)` | 手动作为第一个参数 | 元编程、描述符演示 |

第三种方式中，`Widget.render` 取出来的是类命名空间里的原始函数（一个 `function` 对象），它没有自动绑定 `self`，所以你必须手动把 `w` 作为第一个参数传进去。这与"实例调用时绑定机制返回一个 bound method"是两回事——下文会详述。

**用场景来区分**

```python
# 场景：在子类里显式调用父类被重写的方法
class Base:
    def __init__(self):
        self.tag = "base"

    def info(self):
        return f"Base<{self.tag}>"


class Derived(Base):
    def __init__(self):
        super().__init__()         # 这里 super().__init__() 其实就是 Base.__init__(self)
        self.tag = "derived"

    def info(self):
        # 显式通过类名调用父类方法，把 self 传进去
        parent = Base.info(self)
        return parent + f" -> Derived<{self.tag}>"


d = Derived()
print(d.info())
# 输出：Base<derived> -> Derived<derived>
```

这里 `Base.info(self)` 就是"类调用方式"的典型用法：子类 `info` 重写了父类 `info`，但你仍然想复用父类逻辑，于是用 `Base.info(self)` 绕过重写，直接定位到父类的方法，并显式把 `self` 传进去。`super().info()` 做的也是这件事，只是在多继承下更智能。

### 2.4 在方法里访问实例属性与类属性

实例方法通过 `self` 可以访问两种属性：实例自己的属性（存在实例的 `__dict__` 里），以及类属性（存在类的 `__dict__` 里，所有实例共享）。

```python
class Account:
    # 类属性：所有实例共享这一份
    bank_code = "BANK-0001"

    def __init__(self, owner, balance=0):
        # 实例属性：每个实例各自一份
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        # 通过 self 修改实例属性
        self.balance += amount
        return self.balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("余额不足")
        self.balance -= amount
        return self.balance

    def describe(self):
        # self.bank_code 会先找实例 __dict__，找不到再找类 __dict__
        return f"{self.owner} @ {self.bank_code}, balance={self.balance}"


a = Account("Alice", 100)
b = Account("Bob", 50)
print(a.describe(), b.describe())
# 输出：Alice @ BANK-0001, balance=100 Bob @ BANK-0001, balance=50

a.deposit(30)
print(a.balance, b.balance)        # a 的修改不影响 b
# 输出：130 50

Account.bank_code = "BANK-0002"    # 修改类属性，影响所有实例
print(a.describe(), b.describe())
# 输出：Alice @ BANK-0002, balance=130 Bob @ BANK-0002, balance=50
```

几个关键点：

- `self.owner`、`self.balance` 这种是实例属性，每个实例独立持有；对 `a` 的修改完全不影响 `b`。
- `self.bank_code` 表面上是通过 `self` 访问的，但因为实例 `__dict__` 里没有 `bank_code`，Python 会沿着 `type(self).__mro__` 向上查找到类的 `__dict__`，最终拿到的是类属性。所以 `self.bank_code` 看起来像实例属性，其实是共享的类属性。
- 当你写 `Account.bank_code = "BANK-0002"`，所有实例通过 `self.bank_code` 读到的值都变了——这正是"类属性是共享的"的体现。

**修改类属性：小心被实例属性遮蔽**

```python
class Config:
    level = "INFO"                 # 类属性，作为默认日志级别

    def __init__(self, name):
        self.name = name

    def set_level(self, level):
        # 如果写成 self.level = level，会在实例上创建 level 实例属性，
        # 之后 self.level 读到的是实例属性，不再读到类属性！
        self.level = level         # 这样写就遮蔽了类属性

    def show(self):
        return f"{self.name}: {self.level}"


c1 = Config("c1")
c2 = Config("c2")
c1.set_level("DEBUG")
print(c1.show(), c2.show())
# 输出：c1: DEBUG c2: INFO
```

这里 `c1` 调用 `set_level("DEBUG")` 后，`c1.__dict__` 里多了一个 `level` 实例属性，`c1.show()` 里 `self.level` 先从实例 `__dict__` 找到 `"DEBUG"` 就返回了，根本不会再去找类属性。这就是"实例属性会遮蔽同名类属性"的现象。如果你想要"修改一处影响所有实例"的效果，就要写 `Config.level = level`（通过类名修改类属性），而不是 `self.level = level`（这会在实例上新建一份）。

**在实例方法里读取与修改类属性的正确写法**

```python
class Counter:
    total = 0                      # 类属性：统计所有实例被创建过多少次

    def __init__(self):
        # 推荐通过类名修改类属性（避免在实例上意外新建属性）
        Counter.total += 1
        self.id = Counter.total    # 用类属性给实例编号

    @classmethod
    def reset(cls):
        # 修改类属性更地道的做法是用 classmethod（见专门章节）
        cls.total = 0


print(Counter.total)               # 0
a = Counter()
b = Counter()
print(a.id, b.id, Counter.total)   # 1 2 2
Counter.reset()
print(Counter.total)               # 0
```

这里 `Counter.total += 1` 在 `__init__` 里通过类名修改类属性是正确写法；如果误写成 `self.total += 1`，第一次调用时 `self.total` 会先去类里读到 `0`，自增后写成 `self.total = 1`——结果实例上多了一个 `total` 实例属性，类属性 `Counter.total` 依然是 `0`，统计就完全失效了。这是实例方法里操作类属性最容易踩的坑之一。

### 2.5 在方法里调用其他方法：self.other()

实例方法之间通过 `self.方法名()` 互相调用，是把复杂逻辑拆分到多个方法的基础。`self` 会指向同一个实例，所以被调用的方法操作的状态与调用方一致。

```python
class Order:
    def __init__(self, items):
        self.items = list(items)   # [(name, price, qty), ...]

    def subtotal(self):
        # 被 total() 调用的"内部"方法
        return sum(price * qty for _, price, qty in self.items)

    def discount(self):
        # 满减规则：小计 >= 200 减 30
        if self.subtotal() >= 200: # 在方法里调用本实例的另一个方法
            return 30
        return 0

    def total(self):
        # 入口方法：组合 subtotal 和 discount
        st = self.subtotal()
        return st - self.discount()


order = Order([("book", 60, 2), ("pen", 10, 5)])
print(order.subtotal(), order.discount(), order.total())
# 输出：170 0 170

big = Order([("laptop", 1000, 1)])
print(big.subtotal(), big.discount(), big.total())
# 输出：1000 30 970
```

`total()` 内部调用 `self.subtotal()` 和 `self.discount()`，`self` 指向 `order`（或 `big`），于是被调用的方法也会读到同一个 `self.items`，运算逻辑可以顺畅拼接。这种"实例方法调实例方法"的模式，把业务拆成多个小方法后再组合，是面向对象设计的常规手法。

**重写时的调用链：self 会触发动态分派**

```python
class Shape:
    def area(self):
        return 0

    def describe(self):
        # 通过 self.area() 调用，会按 self 的真实类型分派
        return f"{type(self).__name__} area={self.area():.2f}"


class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        return 3.14 * self.r * self.r


c = Circle(2)
print(c.describe())
# 输出：Circle area=12.56
```

这里 `Shape.describe` 里写的 `self.area()` 并不会固定调用 `Shape.area`，而是按 `self` 的实际类型去查找——`c` 是 `Circle`，所以 `self.area()` 调用的是 `Circle.area`。这是 Python（以及绝大多数 OO 语言）的**动态分派**机制：通过 `self.方法名()` 调用永远按实例的真实类型查找方法，即使调用代码写在父类里也会正确走到子类的实现。这个机制是"模板方法模式"和"多态"能工作的前提。

### 2.6 方法对象 vs 函数对象

这是很多人混淆的一点：**类体里写的是普通函数，通过实例访问时会变成"方法对象"**。

```python
class Counter:
    def inc(self):
        return "inc"
```

我们来观察 `Counter.inc` 和 `Counter().inc` 是不是同一个对象：

```python
print(type(Counter.inc))           # 类身上取出来的是一个普通函数
# 输出：<class 'function'>

c = Counter()
print(type(c.inc))                 # 实例身上取出来的是一个"绑定方法对象"
# 输出：<class 'method'>

print(Counter.inc is c.inc)        # 两个对象不一样
# 输出：False
```

`Counter.inc` 取出的是你在类体里写的那份原始 `function` 对象；而 `c.inc` 是在访问时临时生成的"绑定方法"（`method`）对象，它内部记录了"哪个函数 + 哪个实例（self）"，所以调用时不需要你再传 `self`。

**方法对象的内部结构**

绑定方法对象有两个关键属性：

```python
class Counter:
    def __init__(self):
        self.n = 0

    def inc(self):
        self.n += 1
        return self.n


c = Counter()
m = c.inc
print(m.__func__ is Counter.inc)   # __func__ 就是底层那个原始函数
# 输出：True
print(m.__self__ is c)             # __self__ 就是绑定的实例
# 输出：True
```

一个绑定方法对象本质上是 `(函数, 实例)` 的组合包装。当你调用 `m()`，它等价于 `m.__func__(m.__self__)`。知道这两个属性在做 mock、调试、反射时很有用——比如你拿到一个方法对象，想知道它具体绑定在哪个实例上，打印 `m.__self__` 就能看出来。

**函数对象的属性 vs 绑定方法的属性**

```python
class Counter:
    pass

def inc(self):
    return 42

Counter.inc = inc                  # 给类动态挂一个函数

c = Counter()
print(type(Counter.inc))           # 你挂上去的是什么，类里就是什么
# 输出：<class 'function'>
print(type(c.inc))                 # 但通过实例访问，会被绑定成方法
# 输出：<class 'method'>
print(c.inc())
# 输出：42
```

这个小实验很好地说明了：**判别"是不是方法"的依据不是你写了什么，而是你访问的方式**。同一个 `function` 对象，通过类访问时是函数，通过实例访问时变成绑定方法。是不是"绑定"取决于访问路径，而不是定义形式。

### 2.7 实例方法本质属于类，不在实例 __dict__

一个常被忽略的事实：**实例方法并不存在于实例的 `__dict__` 里，而是存在于类的 `__dict__` 里**。实例身上只有它的数据属性，方法代码全部分享自类。

```python
class User:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"hi, I'm {self.name}"


u = User("Tom")
print(u.__dict__)
# 输出：{'name': 'Tom'}

print("greet" in User.__dict__)    # 方法在类的命名空间里
# 输出：True
print("greet" in u.__dict__)       # 方法不在实例的 __dict__ 里
# 输出：False
```

`u.__dict__` 里只有 `name`，连 `greet` 的影子都看不到。这印证了开头那个比喻：方法代码是"存在图纸上的操作手册"，每件实例持有的只是自己的数据（`name`），调用方法时，Python 先在 `u.__dict__` 里找 `greet`，找不到，去类 `User.__dict__` 里找，找到，绑定后执行。

这样做的好处是显然的：一万个 `User` 实例也只共享一份方法代码，不会每个实例都复制一份函数对象。这也是为什么"实例方法本质属于类"——它们只是通过实例对外呈现为"这个对象能做的事"。

**类里有，实例没有：属性查找路径**

```python
class User:
    role = "guest"                 # 类属性

    def __init__(self, name):
        self.name = name           # 实例属性

    def greet(self):
        return f"{self.role}: {self.name}"
```

当你在方法里写 `self.role` 或在实例外部写 `u.role`，查找顺序是：

1. 先看 `instance.__dict__`（实例自己的命名空间）。
2. 找不到，沿 `type(instance).__mro__` 依次查看每个类的 `__dict__`。
3. 最终都找不到，抛 `AttributeError`（除非定义了 `__getattr__`）。

```python
u = User("Tom")
print(u.__dict__)              # {'name': 'Tom'} —— 只有实例属性
print(User.__dict__["role"])   # "guest" —— 类属性在类里
# 注意：User.__dict__ 是一个 mappingproxy，不是普通 dict
print(type(User.__dict__))
# 输出：<class 'mappingproxy'>
```

`User.__dict__` 是 `mappingproxy`——一个不可变视图，意在防止你在运行时随意修改类的命名空间（虽然你仍可以通过 `setattr` 或者写 `User.role = ...` 来改）。注意它的不变形是"视图不可变"，底层的类命名空间本身还是可以通过赋值改动的。

## 3. 最佳实践

### 3.1 self 名字不要改

形参名虽然 Python 不强制叫 `self`，但几乎所有 Python 代码、标准库、文档、IDE 提示都默认它是 `self`。改成 `this`、`me` 不仅会被 linter 警告，还会让其他开发者困惑，破坏可读性。

**推荐**

```python
def transfer(self, to, amount):
    self.balance -= amount
    to.balance += amount
```

**不推荐**

```python
def transfer(this, to, amount):       # 形参名乱写
    this.balance -= amount
    to.balance += amount
```

原因：`self` 是社区约定，等同于"这是一个实例方法、第一个参数是当前实例"的信号；改名字等于丢掉了这个隐性约定，协作和维护成本都会上升。

### 3.2 通过实例访问 vs 通过类访问：用途要分清

- **日常调用**：一律写 `obj.method(args)`，让绑定机制自动填 `self`，代码最简洁、最符合直觉。
- **父类调用 / 绕过重写**：写 `SuperClass.method(self, args)`，显式定位父类实现，常见于 `__init__` 和被重写方法的复用。
- **元编程 / mock / 测试反射**：用 `ClassName.method` 拿到原始函数，必要时手动传实例，或借助描述符手动触发绑定。

**推荐**

```python
class Base:
    def hook(self):
        return "base"


class Sub(Base):
    def hook(self):
        # 复用父类逻辑再做扩展
        parent = Base.hook(self)
        return parent + " +sub"
```

**不推荐**

```python
class Sub(Base):
    def hook(self):
        # 不要为了"省事"用实例去访问父类方法：
        # 这样会触发动态分派，调到的是 Sub.hook 自己，递归死循环
        parent = self.hook()            # 这不是父类调用，是调用自己！
        return parent + " +sub"
```

原因：`self.hook()` 走的是动态分派，按 `self` 的真实类型查找，在 `Sub.hook` 里写 `self.hook()` 等于自己调自己，无限递归直到栈溢出。要绕过重写必须用类名形式 `Base.hook(self)`。

### 3.3 不要过度依赖实例属性遮蔽类属性

类属性与实例属性同名时，实例属性会遮蔽类属性（属性查找先实例后类）。这种"隐式覆盖"很容易在多人协作里造成难以排查的 bug。

**推荐**

```python
class Config:
    level = "INFO"           # 类属性 = 默认配置

    def __init__(self, name):
        self.name = name

    def set_level(self, level):
        # 通过类名修改类属性，确保影响所有实例
        Config.level = level
```

**不推荐**

```python
class Config:
    level = "INFO"

    def set_level(self, level):
        self.level = level   # 会在某个实例上偷偷新建一个 level，
                              # 下次有人改 Config.level，这个实例不受影响
```

原因：`self.level = level` 创建了一个实例属性，之后 `self.level` 永远读到实例上的那份，类属性 `Config.level` 的修改对它无效。如果别的代码以为"修改类属性就会影响全部实例"，就会踩到不一致。要么明确分清"这是实例级配置"（在 `__init__` 里就初始化实例属性），要么用类名修改类属性，不要在方法里隐式遮蔽。

### 3.4 拆分方法时优先用 self.method()，少用全局函数

把业务逻辑拆成多个实例方法时，方法之间应通过 `self.method()` 调用，而不是把逻辑散落成模块级自由函数再让方法去调它。这样状态和逻辑都聚合在类里，便于继承、重写和测试。

**推荐**

```python
class Invoice:
    def __init__(self, items):
        self.items = items

    def subtotal(self):
        return sum(item.total() for item in self.items)

    def tax(self):
        return self.subtotal() * 0.1     # 同类内部调用

    def total(self):
        return self.subtotal() + self.tax()
```

**不推荐**

```python
def _tax(subtotal):
    return subtotal * 0.1                # 散落的自由函数，税率逻辑游离于类外

class Invoice:
    def total(self):
        st = sum(item.total() for item in self.items)
        return st + _tax(st)
```

原因：`_tax` 写在模块里，税率成为"全局规则"，无法被子类按需重写；而把 `tax` 写成实例方法后，子类只需要重写 `tax` 就能改变税率，`total` 完全不用改。这正是 `self.method()` 拆分方式带来的扩展性。

### 3.5 实例方法里慎用可变默认值与全局可变状态

实例方法常常维护实例的状态，使用可变默认参数或全局可变状态会破坏"状态隔离在实例里"的承诺。

**不推荐**

```python
class Cart:
    def __init__(self):
        self.items = []

    def add(self, item, basket=[]):       # 可变默认参数！
        basket.append(item)
        self.items = basket
```

原因：可变默认参数在函数定义时被求值一次，多次调用共享同一个 list，跨实例之间会互相污染——这是 Python 经典坑，实例方法里同样要避免。

**推荐**

```python
class Cart:
    def __init__(self):
        self.items = []

    def add(self, item, basket=None):
        if basket is None:
            basket = []
        basket.append(item)
        self.items = basket
```

### 3.6 判断"方法 vs 属性"的方法

`callable` 和 `inspect` 能帮你区分"这个对象是方法还是普通属性"，在写框架、ORM、序列化器时很有用。

```python
import inspect

class Demo:
    val = 10

    def f(self):
        return 20

d = Demo()

print(callable(d.val), callable(d.f))            # False True
print(inspect.isfunction(Demo.f), inspect.ismethod(d.f))   # True True
```

当你要把对象字段序列化成 JSON 时，需要对"`val` 这类数据属性"和"`f` 这类方法"区别对待，`inspect.ismethod` 是判定"实例身上的绑定方法"的标准手段。

### 3.7 私有方法命名用单下划线而非双下划线

表示"内部方法"用前缀单下划线 `_method`；只有遇到真正的命名冲突（如子类不小心覆盖父类同名方法）才考虑双下划线 `__method` 触发名称重整。绝大多数情况下单下划线就够了。

**推荐**

```python
class Service:
    def run(self):
        self._prepare()
        self._execute()

    def _prepare(self):           # 单下划线表示内部方法
        ...

    def _execute(self):
        ...
```

单下划线只是约定，外部仍然能访问，但..."买了票的可以坐，没买票的别进"，社区心照不宣。双下划线会触发名称重整，对反射、调试、mock 都增加难度，除非必要不滥用。

## 4. 原理

### 4.1 方法在类 __dict__ 中是普通 function

先看一个自然的事实：当你在类体里写 `def inc(self): ...` 时，`inc` 就是一个普通的 `function` 对象。Python 并没有为"类体里的函数"创建一种独立的类型，它就是 `function`。

```python
class Counter:
    def inc(self):
        return 1


print(type(Counter.inc))
# 输出：<class 'function'>
print(Counter.inc.__name__)
# 输出：inc
print(Counter.inc.__qualname__)   # __qualname__ 比 __name__ 更精确
# 输出：Counter.inc
```

`Counter.inc` 的类型是 `function`，和你写在模块顶层的函数没区别。`__qualname__` 带上类前缀 `Counter.inc`，是它"出生在类体里"留下的唯一指纹；除此之外它与普通函数完全一样，既能赋值给变量、也能单独调用，只是需要手动传 `self`。

```python
class Counter:
    def inc(self):
        return self.n + 1


c = type("C", (), {"n": 5})()
# 直接通过类拿到原始函数，把 c 作为 self 手动传进去
print(Counter.inc(c))             # 6
# 输出：6
```

这个例子说明：实例方法没有任何"魔法类型"——它就是个函数，需要 `self` 的时候由绑定机制（或你手动）填进去。

### 4.2 function 实现了 __get__ 描述符协议

那为什么 `c.inc` 和 `Counter.inc` 表现不一样？秘密在于：**`function` 类型实现了描述符协议 `__get__`**。当你通过实例访问类属性时，如果属性是一个带 `__get__` 的对象，Python 就会调用 `__get__(instance, owner)` 把它"翻译"成另一个对象；裸访问（`Class.method`）也会触发 `__get__(None, owner)`，但对函数而言它会返回它自己。

我们可以用一个简化的"假函数"来复现这个机制：

```python
class MyDescriptor:
    """一个极简的"可绑定"描述符，用来类比 function 的行为。"""
    def __init__(self, func):
        self.func = func

    def __get__(self, instance, owner):
        print(f"  __get__ 被调用: instance={instance!r}, owner={owner.__name__}")
        if instance is None:
            print("  -> 通过类访问，返回自身（类似未绑定的函数）")
            return self
        print("  -> 通过实例访问，返回一个绑定版本")
        def bound(*args, **kwargs):
            return self.func(instance, *args, **kwargs)
        return bound

    def __call__(self, *args, **kwargs):
        # 通过类访问时返回自身，调用它就当作"未绑定函数"用
        return self.func(*args, **kwargs)


class Holder:
    @MyDescriptor
    def echo(self, x):
        return f"[{id(self):x}] echo({x})"


# 通过类访问：instance=None，MyDescriptor.__get__ 返回自身
print("=== 通过类访问 ===")
f = Holder.echo
# 输出：
#   __get__ 被调用: instance=None, owner=Holder
#   -> 通过类访问，返回自身（类似未绑定的函数）
h = Holder()
print("=== 通过实例访问 ===")
m = h.echo
# 输出：
#   __get__ 被调用: instance=<Holder object at 0x...>, owner=Holder
#   -> 通过实例访问，返回一个绑定版本
print(m(42))                       # 不需要手动传 self
# 输出：[<id>] echo(42)
```

这个简化模型就是 `function` 的真实行为：**通过实例访问触发 `__get__` 返回绑定对象；通过类访问 `__get__(None, owner)` 返回自身（未绑定）**。`function` 实现的版本返回的不是手写闭包，而是 C 层的 `method` 对象（即 `bound method`），但概念上完全对应。

### 4.3 绑定机制：通过实例访问返回 bound method，通过类访问返回原始 function

让我们用真实代码观测这条规则：

```python
class Counter:
    def inc(self):
        return 1


c = Counter()

# 通过类访问：function.__get__(None, Counter) 返回自身
print(type(Counter.inc))
# 输出：<class 'function'>

# 通过实例访问：function.__get__(c, Counter) 返回 bound method
print(type(c.inc))
# 输出：<class 'method'>

# 验证 bound method 的内部结构
m = c.inc
print(m.__func__ is Counter.inc)   # True：底层函数就是类里那份
# 输出：True
print(m.__self__ is c)             # True：绑定到实例 c
# 输出：True
```

一个 bound method 可以理解为一个"`(func, self)` 的预绑定包装"。调用 `m()` 时，CPython 会内部执行 `func(self, *args, **kwargs)`。这种设计让 `obj.method(args)` 写起来像"对象天生知道自己在调什么"，但底层依然是"把对象作为第一个参数传给类里的函数"。

**手动触发描述符协议**

你可以用 `__get__` 手工模拟"通过实例访问"的过程，看到完全一样的结果：

```python
class Counter:
    def inc(self):
        return 1


c = Counter()

# 手动调用描述符 __get__
bound = Counter.inc.__get__(c, Counter)
print(type(bound))                 # 与 c.inc 等价
# 输出：<class 'method'>
print(bound is c.inc)              # 内容等价（注意同一次访问会创建新对象）
# 输出：False（每次访问都新建一个 method 对象，但语义等价）
print(bound.__func__ is c.inc.__func__)
# 输出：True
```

每次 `c.inc` 这种访问，CPython 都会即时调用 `function.__get__` 创建一个全新的 `method` 对象——它们之间 `is` 比较为 `False`，但语义完全等价。这也是为什么"不要用 `is` 比较方法对象"——同一个实例两次拿到的方法对象不是同一个对象，但调用的底层函数和绑定的实例是同一个。如果需要比较，请比较 `__func__` 和 `__self__`。

### 4.4 两种访问路径的细化差别

| 访问方式 | 触发 `__get__` | 返回对象 | 调用时 self 来源 |
|---|---|---|---|
| `ClassName.method` | 是，但 `instance=None` | 原始 `function` | 手动作为第一个参数 |
| `instance.method`   | 是，`instance=实例` | `method`（bound） | 由 `method` 自动填入 |
| `instance.method.__func__` | 不再触发 | 原始 `function` | 手动作为第一个参数 |

```python
class Counter:
    def inc(self):
        return id(self)


c = Counter()

# 方式一：实例访问 -> bound method
print(c.inc() == id(c))            # True，self 由 bound method 自动填入
# 输出：True

# 方式二：类访问 -> 原始函数
print(Counter.inc(c) == id(c))     # True，self 手动传入
# 输出：True

# 方式三：从 bound method 拆出底层函数再调用
print(c.inc.__func__(c) == id(c))  # True，self 手动传入
# 输出：True
```

三种方式最终都把 `c` 作为 `self` 传给底层那个 `function`，差别只在"谁来填 self"。

### 4.5 LOAD_METHOD / CALL_METHOD 字节码优化

绑定机制本来有一个性能问题：每次 `obj.method(args)` 都要新建一个 `method` 对象（包装 `func + self`），用完即弃，GC 压力大。为了消除这种临时对象的分配，CPython 3.7 引入了 `LOAD_METHOD` / `CALL_METHOD` 字节码优化。

**普通调用路径（无优化）**

在没有优化的世界里，`obj.method(arg)` 的字节码大致是：

```text
LOAD_FAST   obj        # 把 obj 压栈
LOAD_ATTR   method     # 这一步会触发 __get__，返回一个 bound method 对象压栈
LOAD_FAST   arg        # 把 arg 压栈
CALL_FUNCTION 2        # 调用那个 bound method 对象
POP_TOP
```

`LOAD_ATTR method` 会创建一个临时 `method` 对象，调用完立刻丢掉——这是开销所在。

**优化路径：LOAD_METHOD / CALL_METHOD**

CPython 3.7 之后改用了两个新字节码：

```text
LOAD_METHOD  method   # 尝试"直接拿到底层函数 + 绑定的 self"，不创建方法对象
LOAD_FAST    arg
CALL_METHOD  2        # 等价于直接 func(self, arg)
```

`LOAD_METHOD` 会先沿属性查找链找到类里的 `function`，如果它发现这个函数是实现 `__get__` 的常规 function，并且实例确实有这一个方法，就**回填一组 `(func, self)` 而不是构造一个 bound method 对象**。`CALL_METHOD` 直接对这组 `(func, self)` 完成调用，整个过程**完全不创建临时 method 对象**。

我们可以用 `dis` 直接观测这种优化：

```python
import dis


class Stack:
    def __init__(self):
        self._items = []

    def push(self, value):
        self._items.append(value)
        return len(self._items)


s = Stack()

# 反汇编"实例调用方法"
print("=== s.push(1) 的字节码 ===")
dis.dis(lambda: s.push(1))
```

你会看到类似下面的输出：

```text
=== s.push(1) 的字节码 ===
  1           0 LOAD_GLOBAL              0 (s)
              2 LOAD_METHOD              2 (push)
              4 LOAD_CONST               1 (1)
              6 CALL_METHOD              1
              8 POP_TOP
             10 RETURN_VALUE
```

果然是 `LOAD_METHOD` + `CALL_METHOD`，**没有出现 `LOAD_ATTR` 创建 method 对象的步骤**。这意味着大量调用 `obj.method()` 时，CPython 不会为每次调用分配一个临时的 method 对象。

**优化哪些不成立**

`LOAD_METHOD` 是一个"乐观"优化，某些情况下会回退到普通路径：

- 不存在该方法、或查找链遇到数据描述符、`__slots__` 描述符、property 等都会让优化不成立。
- 优化只是省了 method 对象的分配，不改变语义：返回值、`self` 绑定、异常都和普通路径完全一致。

```python
# 这种用法不会被优化：因为 c.inc 必须被真正取出用于传参
g = c.inc   # 这一步会创建方法对象（不是 LOAD_METHOD 的目标场景）
g()
```

但如果只是 `c.inc()` 这种直接调用的形式，就走上优化路径，避免了不必要的临时对象。

**对实际编码的影响**

理解 `LOAD_METHOD/CALL_METHOD` 后，你在写高频代码时可以心里有底：

- `obj.method(args)` 这种直接调用是优化过的，能放心写；
- 中间变量持有方法对象 `g = obj.method; g(); g(); ...` 不会反复"创建新方法对象"，因为只赋值一次；
- 但每次写 `obj.method` 这种纯访问表达式都会触发 `function.__get__`，生成一个全新的 `method` 对象——如果你想频繁调用，推荐 `g = obj.method` 先持有一次再复用，避免反复创建。

```python
# 推荐：把方法对象 hoist 出来，高频调用
g = s.push
for i in range(1_000_000):
    g(i)
```

```python
# 高频写 s.push 直接调用其实也很快（有 LOAD_METHOD 优化），
# 但如果你把它作为参数传给别的函数（map(s.push, range(...))），
# 那种"先拿到方法对象再调用"的形式需要慎重，会反复创建方法对象
```

### 4.6 描述符模型小结

实例方法的整套机制，本质上是"function 是一个非数据描述符，它的 `__get__` 在不同访问路径下返回不同对象"。把它放进描述符家族里看：

- **数据描述符**：同时实现 `__get__` 和 `__set__`（如 `property`、`classmethod`、自定义描述符），查找优先级高于实例 `__dict__`。
- **非数据描述符**：只实现 `__get__`（如 `function`、`staticmethod`），查找优先级低于实例 `__dict__`，可以被同名实例属性遮蔽。

```python
class Counter:
    def inc(self):
        return 1


c = Counter()
# 在实例身上放一个同名的普通属性，会遮蔽方法（非数据描述符优先级低）
c.inc = "shadowed"
print(c.inc)
# 输出：shadowed
```

`function` 作为非数据描述符可以被实例属性遮蔽——这也提醒我们：**不要在实例上随便塞和方法同名的属性**，否则方法会被"挡住"调不到。相比之下，`property` 这类数据描述符优先级高，即使你在实例 `__dict__` 里塞了同名属性也读不到，会被 `property` 接管。

## 5. 总结

### 5.1 本文内容要点

- **实例方法定义在类体**：第一个形参 `self` 指向调用实例，社区约定形参名不可改。
- **两种等价调用**：`obj.method(args)` 等价 `ClassName.method(obj, args)`，差别只在 `self` 由谁填充。
- **三种调用方式**：实例调用（自动绑定）、类调用（手动传 self）、拿到函数对象直接调用（手动传 self）——结果一致，语义有别。
- **访问实例属性与类属性**：`self.xxx` 先找实例 `__dict__`，再沿 `type(self).__mro__` 找到类属性；实例属性会遮蔽同名类属性，修改类属性要走类名或 `classmethod`。
- **方法调用另一方法**：`self.other()` 走动态分派按实例真实类型查找，是模板方法和多态的前提；在子类里调用父类实现要写 `SuperClass.method(self, ...)` 绕过重写。
- **方法 vs 函数**：类里是普通 `function`，通过实例访问触发 `__get__` 返回 `method`（绑定方法），通过类访问返回原始 `function`（未绑定）；绑定方法由 `__func__` 和 `__self__` 组成。
- **方法在类里不在实例里**：实例 `__dict__` 只有数据属性，方法代码存在类 `__dict__` 里被所有实例共享，找不到时会沿 MRO 向上查。
- **描述符协议**：`function` 是非数据描述符，`__get__(None, owner)` 返回自身，`__get__(instance, owner)` 返回 bound method。
- **LOAD_METHOD / CALL_METHOD 优化**：CPython 3.7 起对 `obj.method(args)` 直接调用做了优化，回填 `(func, self)` 而不构造临时 method 对象，减少 GC 压力；不影响语义，但提示你高频调用时把方法对象 hoist 出来再复用。
- **最佳实践要点**：`self` 名字不改；日常用实例调用，绕过重写用类调用；不要在实例上随意放与方法/类属性同名的属性；私有方法用单下划线；不要用可变默认参数或全局可变状态污染实例状态。

### 5.2 读完应能掌握

- 能用清晰的术语解释 `self` 是什么、为什么形参要写 `self`、`obj.method(args)` 与 `ClassName.method(obj, args)` 为什么等价。
- 能写出包含实例属性 + 类属性 + 多个互相调用方法的类，并说明 `self.xxx` 在哪一步找到的是实例属性、哪一步找到的是类属性。
- 能分清 `Counter.inc`（function）与 `c.inc`（bound method）在类型、`__func__`、`__self__` 上的差异，并能用 `type()` 和 `inspect.ismethod` 验证。
- 能用 `Stack.push(s, 1)` 这种类调用形式绕过重写调用父类方法，并解释为什么不能在子类方法里写 `self.method()` 调用父类实现（会动态分派到自己）。
- 能描述 `function.__get__` 在两种访问路径下的行为差异，并能用 `Counter.inc.__get__(c, Counter)` 手动触发描述符协议复现绑定结果。
- 能在字节码层面说明 `LOAD_METHOD`/`CALL_METHOD` 优化的作用，知道在什么场景下该把方法对象 hoist 出来避免重复创建。
- 能识别"实例属性遮蔽类属性""可变默认参数""双下划线滥用"这些常见反模式，并写出对应的推荐写法。

### 5.3 延伸阅读方向

- **classmethod 与 staticmethod**：同样是定义在类体里，但 `classmethod` 的 `self` 由类填充，`staticmethod` 干脆没有 `self`，对应不同的绑定策略——见后续专门章节。
- **描述符协议全貌**：`__get__` / `__set__` / `__delete__`，数据描述符 vs 非数据描述符的优先级——是 property、slots、字段验证器的基础。
- **super 的真实机制**：`super()` 并不是"调用父类"，而是按 MRO 顺序在类身上构造一个"代理"，组合 `__class__.__mro__` 与 `self` 做方法查找。
- **`__getattribute__` 与属性查找链**：所有"通过实例访问属性"的入口都经过 `__getattribute__`，理解它能彻底说清描述符、`__dict__`、MRO 之间的协作顺序。
- **dunder 方法与隐式调用**：`len(x)`、`x + y`、`str(x)` 等都是隐式触发实例方法 `__len__`/`__add__`/`__str__`，它们的绑定与分派与普通实例方法完全一致，只是入口由语法糖接管。
