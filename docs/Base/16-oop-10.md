## 1. 介绍

### 1.1 什么是名称重整

在 Python 的面向对象编程中，"私有"是一个经常被讨论但又容易误解的话题。与 Java、C++ 这类语言不同，Python 并没有真正意义上的 `private` 关键字来强制禁止外部访问某个属性。Python 信奉"我们都是自愿的成年人"这一哲学——你看到的属性，理论上都可以访问。但这并不意味着 Python 完全没有提供任何机制来帮助开发者做访问隔离，**名称重整（name mangling）** 就是其中一种针对类内部属性命名的编译期改写机制。

名称重整的具体含义是：当你在类体内定义一个以**两个及以上下划线开头**、且**不以两个及以上下划线结尾**的属性名时（例如 `__value`），Python 编译器会在编译阶段把这个名字自动改写为 `_ClassName__value` 的形式——即在原名字前面加上一个下划线和所属类名。这个改写过程对开发者是透明的：你在代码里写的依然是 `self.__value`，但解释器实际存储和查找的名字是 `self._ClassName__value`。

需要注意的是，名称重整只是一种"改名隔离"机制，而非真正的访问控制。它最早被引入 Python 的主要目的是**避免子类在不知情的情况下无意覆盖父类中的同名属性**，尤其是在多重继承和大型类继承体系中，这个问题尤为突出。通过把 `__value` 改写成带类名前缀的名字，不同类中各自的 `__value` 在底层存储时会拥有不同的真实名字，从而互不冲突。

理解名称重整需要把握几个关键边界：

- `__value`（双下划线开头、不以双下划线结尾）—— 触发名称重整，改写为 `_ClassName__value`。
- `__value__`（首尾都是双下划线）—— 这是 Python 的魔术方法/dunder 方法命名约定（如 `__init__`、`__str__`），**不触发**名称重整。
- `_value`（仅单下划线开头）—— 这是"软私有"约定，**不触发**名称重整，外部仍可直接访问，只是约定上表示"内部使用"。

下面先看一个最直观的例子，感受名称重整带来的效果。

### 1.2 基本语法与最小用法

名称重整不需要任何特殊语法来触发，它完全由属性名的书写形式决定。只要你在类体内写了一个符合"双下划线开头、不以双下划线结尾"规则的名字，重整就会自动发生。

```python
class Base:
    def __init__(self):
        self.__value = 100  # 写的是 __value，实际存储为 _Base__value

    def show(self):
        # 类体内部引用 self.__value 也会被一致地改写
        return self.__value


b = Base()
print(b.show())  # 输出：100

# 在类外部用 __value 访问会失败，因为真实名字不是 __value
try:
    print(b.__value)
except AttributeError as e:
    print(e)  # 输出：'Base' object has no attribute '__value'

# 但可以用改写后的真实名字手动访问——所以并非真正私有
print(b._Base__value)  # 输出：100
```

上面这个例子展示了名称重整最核心的三件事：

1. 类体内定义 `self.__value` 后，实际存储的名字是 `_Base__value`，类体内部通过 `self.__value` 引用时也会被一致改写，所以 `show()` 方法能正常返回值。
2. 类外部直接 `b.__value` 会报 `AttributeError`，因为 `b` 的实例字典里根本没有 `__value` 这个键，只有 `_Base__value`。
3. 但只要你写 `b._Base__value`，就能正常访问到这个值——改写后的名字是一个确定的、可预测的字符串，没有任何强制访问屏障。

这就是名称重整的本质：它改了名字，但没有锁住访问。下面我们逐一展开它的规则、场景与原理。

## 2. 核心内容

### 2.1 触发规则与改写形式

名称重整的触发条件完全由标识符的"下划线形态"决定，理解规则要抓住"开头"和"结尾"两侧的约束。

**触发条件（同时满足才改写）**：

- 标识符以**两个及以上**下划线开头：`__x`、`__data`、`___x`（三个也属于"两个以上"）都会被纳入考察。
- 标识符**不以**两个及以上下划线结尾：即 `__x__`、`__init__` 这种首尾双下划线的 dunder 名字不触发改写。

满足这两个条件后，改写规则是：在原名字前面拼接**一个下划线**加上**当前所在类的名字**。

| 原名字（在类 `MyClass` 内） | 是否触发改写 | 改写后的真实名字 |
|---|---|---|
| `__value` | 是 | `_MyClass__value` |
| `__data_list` | 是 | `_MyClass__data_list` |
| `__value__` | 否（首尾双下划线，dunder） | `__value__`（不变） |
| `_value` | 否（仅单下划线开头） | `_value`（不变） |
| `value` | 否（无下划线） | `value`（不变） |
| `___value` | 是（三个下划线开头，不以两个以上结尾） | `_MyClass___value` |

来看一个对照演示，用 `dir()` 和实例的 `__dict__` 直接观察改写后的真实名字。

```python
class Demo:
    def __init__(self):
        self.__private = 1     # 触发改写 -> _Demo__private
        self._soft = 2         # 不触发改写
        self.public = 3        # 不触发改写
        self.__dunder__ = 4    # 不触发改写（首尾双下划线）


d = Demo()

# 查看实例字典，可以看到真实存储的键名
print(d.__dict__)
# 输出：{'_Demo__private': 1, '_soft': 2, 'public': 3, '__dunder__': 4}

# 用 dir 过滤出带 Demo 的名字
print([name for name in dir(d) if 'Demo' in name])
# 输出：['_Demo__private']
```

从 `__dict__` 的输出可以清楚看到：`self.__private` 在实例字典里的键就是 `_Demo__private`，而非 `__private`；而 `_soft`、`public`、`__dunder__` 都保持原样。这就是名称重整在存储层面的直接体现。

**改写中的类名来源**

改写时拼接的"类名"是定义该标识符的**类**的名字，与实例的实际类型无关，也与继承关系无关。也就是说，如果属性在 `Base` 类体内被定义，那么无论后续 `Sub(Base)` 还是 `SubSub(Sub)`，这个属性的真实名字永远是 `_Base__value`，不会变成 `_Sub__value`。这条规则在原理解析章会详细展开，这里先记住一个结论：**改写发生在编译期，依据的是定义所在的类，而非运行时的类型**。

### 2.2 类体内部引用的一致改写

名称重整不只作用于属性定义，对类体内任何对 `__name` 形式的引用——包括读取、赋值、方法调用——都会做一致的改写。这保证了类体内部代码可以始终用 `self.__value` 这样的简写来访问自己的属性，而不会因为底层名字被改写而出现"定义找得到、引用找不到"的割裂。

```python
class Counter:
    def __init__(self, start=0):
        self.__count = start          # 定义：改写为 _Counter__count

    def increment(self):
        self.__count += 1             # 引用：同样改写为 _Counter__count

    def reset(self, value):
        self.__count = value          # 赋值：同样改写

    @property
    def current(self):
        return self.__count           # 读取：同样改写


c = Counter(10)
c.increment()
c.increment()
c.reset(50)
print(c.current)  # 输出：50

# 外部看不到 __count，只能看到改写后的名字
print(c.__dict__)  # 输出：{'_Counter__count': 50}
```

这个例子说明，无论你在类体内对 `self.__count` 做定义、读取、累加还是重新赋值，所有引用都被一致地映射到 `_Counter__count`。开发者不需要关心底层名字，`self.__count` 在整个 `Counter` 类体内始终指向同一个被改写后的属性。

**类体内引用改写的边界**

需要注意的是，改写只发生在"类体内"且"以 `__` 开头的标识符"上。如果类体内你通过一个动态字符串去访问属性，比如 `getattr(self, '__count')`，这个名字不会被改写——因为它只是一个普通的字符串值，不是源码中的标识符。这是初学者容易踩的坑。

```python
class Trap:
    def __init__(self):
        self.__value = 42  # _Trap__value

    def get_via_attr(self):
        # getattr 的参数是运行时字符串，不会做 name mangling
        return getattr(self, '__value')  # 这里试图访问 __value，而非 _Trap__value


t = Trap()
try:
    print(t.get_via_attr())
except AttributeError as e:
    print(e)  # 输出：'Trap' object has no attribute '__value'
```

如上，`getattr(self, '__value')` 在运行时去找名为 `__value` 的属性，而实例字典里只有 `_Trap__value`，所以会抛 `AttributeError`。如果你确实想用 `getattr` 在类体内部访问被改写的属性，要么写 `getattr(self, '_Trap__value')`，要么在类体内用 `self.__value`（会被编译器改写）。

### 2.3 类外部访问的行为差异

名称重整最直观的外部表现就是：直接用 `obj.__value` 在类外部访问会失败，但这并非因为访问被"禁止"，而是因为根本不存在名为 `__value` 的属性。理解这一点至关重要——它和真正的访问控制有本质区别。

```python
class Account:
    def __init__(self, owner, balance):
        self.owner = owner          # 公开属性
        self.__balance = balance    # 改写为 _Account__balance

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount  # 类体内引用，一致改写

    def get_balance(self):
        return self.__balance  # 类体内引用，一致改写


acc = Account('Alice', 1000)
print(acc.owner)  # 输出：Alice

# 直接用 __balance 访问 -> 失败（不存在该名字）
try:
    print(acc.__balance)
except AttributeError as e:
    print(e)  # 输出：'Account' object has no attribute '__balance'

# 用改写后的真实名字 -> 可以访问，甚至修改
print(acc._Account__balance)  # 输出：1000
acc._Account__balance = -999  # 直接绕过 deposit 的校验
print(acc.get_balance())      # 输出：-999
```

上面这个 `Account` 例子很好地说明了名称重整"并非真私有"：`deposit` 方法原本对 `amount > 0` 做了校验，但外部一行 `acc._Account__balance = -999` 就绕过了这层校验。名称重整没有提供任何运行时屏障，它只是改了名字而已。

**为什么仍被认为有价值**

即便不是真私有，名称重整在实际工程中仍有价值，主要体现在"避免无意覆盖"而非"防止恶意访问"。它的潜台词是：如果你要访问一个 `_ClassName__value` 名字，你必须显式写出类名——这本身就是一种"我明确知道我在干什么"的信号，比直接 `obj.__value` 要显眼得多。对于合理的代码审查，这类访问很容易被识别和质疑。

### 2.4 避免子类覆盖：核心使用场景

名称重整被引入 Python 的主要动机，就是解决子类与父类各自拥有同名"私有"属性时的冲突问题。在没有名称重整的世界里，如果 `Base` 有一个 `__value`、`Sub` 也有一个 `__value`，二者在底层是同一个名字 `__value`，子类的赋值会覆盖父类的值，导致难以排查的 bug。有了名称重整，`Base` 的 `__value` 变成 `_Base__value`，`Sub` 的 `__value` 变成 `_Sub__value`，两者在实例字典里各占一个键，互不干扰。

```python
class Base:
    def __init__(self):
        self.__value = 'base'

    def base_value(self):
        return self.__value  # 类体内引用，改写为 _Base__value


class Sub(Base):
    def __init__(self):
        super().__init__()
        self.__value = 'sub'  # 改写为 _Sub__value，不会覆盖父类的 _Base__value

    def sub_value(self):
        return self.__value  # 类体内引用，改写为 _Sub__value


s = Sub()
print(s.base_value())  # 输出：base
print(s.sub_value())   # 输出：sub

# 看实例字典：两个值共存
print(s.__dict__)
# 输出：{'_Base__value': 'base', '_Sub__value': 'sub'}
```

这个例子是理解名称重整价值的钥匙。`Sub` 的 `__init__` 里先调用 `super().__init__()`，父类把 `'base'` 存到 `_Base__value`；随后子类把 `'sub'` 存到 `_Sub__value`。两个值在同一个实例字典里和平共处。`base_value()` 方法是父类定义的，它内部的 `self.__value` 在编译期就被绑定为 `_Base__value`，所以即使运行时 `self` 是 `Sub` 实例，它读到的依然是父类那个 `'base'`。同理，`sub_value()` 读到的是子类的 `'sub'`。

如果不用双下划线而用单下划线或普通名字，结果就完全不同。

```python
class BaseSingle:
    def __init__(self):
        self._value = 'base'   # 不触发改写

    def base_value(self):
        return self._value


class SubSingle(BaseSingle):
    def __init__(self):
        super().__init__()
        self._value = 'sub'  # 不触发改写，直接覆盖父类的 _value

    def sub_value(self):
        return self._value


ss = SubSingle()
print(ss.base_value())  # 输出：sub（父类方法读到被子类覆盖后的值）
print(ss.sub_value())   # 输出：sub
print(ss.__dict__)      # 输出：{'_value': 'sub'}  只有一个键
```

对比两个例子的 `__dict__` 输出，差别一目了然：单下划线场景下只有一个 `_value` 键，子类的赋值把父类的值覆盖了，导致 `base_value()` 这个本应返回 `'base'` 的方法也返回了 `'sub'`。这就是"子类无意覆盖父类同名属性"的典型问题，而双下划线名称重整正是为解决它而生。

**多重继承场景的价值**

在多重继承或深层继承体系中，不同基类可能各自定义了同名的 `__attr`。如果没有名称重整，MRO（方法解析顺序）末端的某个类一旦赋值 `self.__attr`，就会抹掉其他类设的值。有了名称重整，每个基类的 `__attr` 都带各自的类名前缀，互不冲突。

```python
class Logger:
    def __init__(self):
        self.__buffer = []  # _Logger__buffer

    def log(self, msg):
        self.__buffer.append(msg)

    def logs(self):
        return list(self.__buffer)


class Cache:
    def __init__(self):
        self.__buffer = {}  # _Cache__buffer，与 Logger 的互不冲突

    def put(self, key, val):
        self.__buffer[key] = val

    def cached(self):
        return dict(self.__buffer)


class Service(Logger, Cache):
    def __init__(self):
        Logger.__init__(self)
        Cache.__init__(self)


svc = Service()
svc.log('启动成功')
svc.put('user', 'Alice')

print(svc.logs())   # 输出：['启动成功']
print(svc.cached()) # 输出：{'user': 'Alice'}
print(svc.__dict__)
# 输出：{'_Logger__buffer': ['启动成功'], '_Cache__buffer': {'user': 'Alice'}}
```

`Logger` 用列表做日志缓冲，`Cache` 用字典做缓存，两者各自用了 `__buffer` 这个名字。如果没有名称重整，`Service` 实例字典里只会有一个 `__buffer`，后初始化的那个会覆盖前者，导致日志功能或缓存功能之一失效。有了名称重整，`_Logger__buffer` 和 `_Cache__buffer` 各自独立，两个功能都能正常工作。这是一个非常有说服力的真实场景。

### 2.5 魔术方法不被改写

Python 的魔术方法（dunder 方法）采用首尾双下划线的命名形式，如 `__init__`、`__str__`、`__repr__`、`__len__` 等。由于它们**以双下划线结尾**，不满足名称重整的触发条件（要求"不以两个及以上下划线结尾"），因此不会被改写。这一点至关重要，因为魔术方法是 Python 与解释器之间的协议接口，改写会破坏协议调用机制。

```python
class Item:
    def __init__(self, name, price):
        self.name = name
        self.__price = price  # _Item__price，触发改写

    # __str__ 是 dunder 方法，不触发改写
    def __str__(self):
        return f'{self.name}: {self.__price}'

    # __repr__ 同理不触发改写
    def __repr__(self):
        return f'Item({self.name!r}, {self.__price!r})'


it = Item('杯子', 29.9)
print(it)        # 输出：杯子: 29.9    （调用未被改写的 __str__）
print(repr(it))  # 输出：Item('杯子', 29.9)
print(str(it))   # 输出：杯子: 29.9

# 验证 __str__ 这个名字本身没被改写
print([name for name in dir(it) if 'str' in name.lower()])
# 输出：['__str__']  而非 _Item__str__
```

如果 `__str__` 被改写成 `_Item__str__`，那么 `print(it)` 就无法触发 `__str__`，因为解释器寻找的是 `__str__` 这个确切的名字。Python 的协议机制依赖 dunder 名字的稳定性，所以"首尾双下划线"这条边界线非常关键——它既是魔术方法的命名约定，也是名称重整的"免死金牌"。

**自定义 dunder 属性也不改写**

虽然不推荐，但如果你自己定义一个非标准的 dunder 属性（如 `__my_thing__`），它同样不会被改写，因为它满足"以双下划线结尾"。

```python
class Weird:
    def __init__(self):
        self.__custom__ = '不改写'  # 首尾双下划线，不改写


w = Weird()
print(w.__dict__)  # 输出：{'__custom__': '不改写'}
print(w.__custom__)  # 输出：不改写  （外部也能直接访问）
```

这说明名称重整的判定完全基于"下划线形态"这一字面规则，与名字是否属于"标准魔术方法"无关。社区约定俗成地只对标准协议方法使用 `__x__` 形式，自定义属性不要用这种形式，以免既丧失了改写保护，又容易被误认为魔术方法。

### 2.6 单下划线 _value 与双下划线 __value 的取舍

Python 中表示"内部使用"的属性有两种约定：单下划线 `_value`（软私有）和双下划线 `__value`（触发名称重整）。它们各有适用场景，理解差异才能正确选用。

**单下划线 `_value`**

- 不触发任何改写，外部可直接访问：`obj._value`。
- 仅作为**约定**，表示"这是实现细节，不应被外部依赖，但我不会阻止你访问"。
- 适用于绝大多数"内部属性"场景：模块内部函数、类的内部辅助属性、不希望出现在 `from module import *` 中的名字。
- 是 Python 社区最主流的"私有"表达方式，标准库大量使用。

**双下划线 `__value`**

- 触发名称重整，外部直接 `obj.__value` 会失败（但 `obj._ClassName__value` 可访问）。
- 主要价值在于**避免子类无意覆盖**，而非访问控制。
- 适用于：设计的类预期会被广泛继承、子类行为不可控、且父类确实需要保护某些内部状态不被子类同名属性覆盖的场景。
- 不适用于：单文件、不被继承的类、或希望子类自由扩展的属性——这种场景用单下划线即可，过度使用双下划线反而增加调试难度。

来看一个对比场景，帮助你体会何时该用哪个。

```python
class BaseProtected:
    def __init__(self):
        # _config 仅作为"内部使用"的约定，子类可以覆盖、外部可以访问
        self._config = {'timeout': 30}

        # __state 用于关键内部状态，不希望被子类同名属性意外覆盖
        self.__state = 'IDLE'


class SubProtected(BaseProtected):
    def __init__(self):
        super().__init__()
        # 子类也有个 _config，会覆盖父类的——如果这是有意的，没问题
        self._config = {'timeout': 60, 'retry': 3}

        # 子类也有 __state，但不会覆盖父类，因为各自改写为不同名字
        self.__state = 'RUNNING'

    def report(self):
        # 注意：这里访问的 __state 会被改写为 _SubProtected__state
        return f'sub state={self.__state}'


sp = SubProtected()
print(sp._config)  # 输出：{'timeout': 60, 'retry': 3}
print(sp.report())  # 输出：sub state=RUNNING
print(sp.__dict__)
# 输出：{'_config': {'timeout': 60, 'retry': 3},
#       '_BaseProtected__state': 'IDLE',
#       '_SubProtected__state': 'RUNNING'}
```

在这个例子里，`_config` 被有意覆盖是设计的一部分（子类提供自己的配置），所以用单下划线；而 `__state` 是父类维护的关键状态，不希望被子类干扰，所以用双下划线，两个状态值在实例字典里共存。

**选择建议**

- 默认用单下划线 `_value`，它足以表达"内部使用"的意图，且不引入改写的复杂性。
- 仅当你设计的类会被他人继承、且父类需要保护某些内部状态不被子类同名属性意外覆盖时，才考虑用双下划线 `__value`。
- 永远不要用双下划线来实现"真正的私有"——它做不到，还会让调试和子类化变得更困难。

### 2.7 用 inspect 观察改写后的名字

在调试或探索第三方库时，经常需要确认某个被改写的属性的真实名字。Python 标准库的 `inspect` 模块，以及内置的 `dir()`、`__dict__`，都能帮我们看到改写后的名字。

```python
import inspect


class Connection:
    def __init__(self):
        self.__host = 'localhost'  # _Connection__host
        self.__port = 3306         # _Connection__port
        self.__connected = False   # _Connection__connected

    def connect(self):
        self.__connected = True


conn = Connection()
conn.connect()

# 方法一：用 dir() 列出所有成员，过滤出带类名前缀的
mangled = [n for n in dir(conn) if n.startswith('_Connection__')]
print(mangled)
# 输出：['_Connection__connected', '_Connection__host', '_Connection__port']

# 方法二：直接看实例字典
print(conn.__dict__)
# 输出：{'_Connection__host': 'localhost', '_Connection__port': 3306, '_Connection__connected': True}

# 方法三：用 inspect.getmembers 获取所有成员（含值）
members = inspect.getmembers(conn)
mangled_members = [(n, v) for n, v in members if n.startswith('_Connection__')]
print(mangled_members)
# 输出：[('_Connection__connected', True), ('_Connection__host', 'localhost'), ('_Connection__port', 3306)]
```

`inspect.getmembers` 返回的成员列表中，被改写的属性以 `_Connection__` 开头，可以直接识别。这在阅读不熟悉的代码库、尤其是需要在类外部手动访问某个"私有"属性做调试时非常有用。

**改写名字的可预测性**

由于改写规则是确定的（`_ClassName__attrname`），你完全可以不借助 `inspect` 就推算出真实名字。但要注意一点：如果类名本身以下划线开头（如 `_Internal`），改写后的名字会是 `__Internal__value`（一个下划线 + `_Internal` + `__value`），形态略特殊。多数情况下类名不会以下划线开头，无需深究这种边界。

### 2.8 名称重整与方法的关系

名称重整不仅作用于实例属性，同样作用于类体内定义的方法名。如果在一个类里定义了 `__do_something` 这样的方法，它的真实名字也会被改写。但这与魔术方法 `__call__`、`__getitem__` 等的协议调用机制无关——协议方法不会被改写，只有非协议的双下划线方法才会被改写。

```python
class Processor:
    def __init__(self, data):
        self.__data = data  # _Processor__data

    def run(self):
        # 类体内调用 __prepare 和 __finalize，一致改写
        prepared = self.__prepare()
        result = self.__process(prepared)
        self.__finalize()
        return result

    def __prepare(self):   # _Processor__prepare
        return [x * 2 for x in self.__data]

    def __process(self, items):  # _Processor__process
        return sum(items)

    def __finalize(self):  # _Processor__finalize
        self.__data = []


p = Processor([1, 2, 3])
print(p.run())  # 输出：12

# 外部直接调用 __prepare 会失败
try:
    p.__prepare()
except AttributeError as e:
    print(e)  # 输出：'Processor' object has no attribute '__prepare'

# 但可以手动调用改写后的名字
print(p._Processor__prepare())
# 注意：此时 __data 已被 __finalize 清空，所以输出：[]
# 输出：[]
```

注意这个例子最后的输出：`p.run()` 执行时，`__prepare` 返回 `[2, 4, 6]`，`__process` 求和得 `12`，然后 `__finalize` 把 `__data` 清空。所以 `run()` 返回 `12`。之后在外部手动调用 `p._Processor__prepare()`，因为 `__data` 已经是空列表，所以返回 `[]`。这个细节说明：改写后的方法名指向同一个真实方法，调用它和在类体内调用 `self.__prepare()` 效果完全一致。

## 3. 最佳实践

### 3.1 默认用单下划线，仅在需要时才用双下划线

Python 社区的普遍共识是：单下划线 `_value` 是表达"内部使用"的首选方式，双下划线 `__value` 只在确有需要时才使用。过度使用双下划线会带来调试困难——当你或同事在类外部用 `obj.__x` 访问失败时，往往需要额外查 `__dict__` 才能找到真实名字，增加了认知负担。

**推荐写法**

```python
class UserService:
    def __init__(self):
        self._db = None       # 单下划线：内部使用，子类可访问/覆盖
        self._cache = {}      # 单下划线：内部实现细节

    def get_user(self, uid):
        if uid in self._cache:
            return self._cache[uid]
        user = self._db.query(uid)
        self._cache[uid] = user
        return user
```

**不推荐写法**

```python
class UserService:
    def __init__(self):
        self.__db = None      # 过度使用，未被继承就没有必要
        self.__cache = {}     # 过度使用，增加调试难度
```

如果一个类不会被继承、或子类完全由你控制，用单下划线就够了。双下划线的价值只在"子类不可控、且需要保护父类内部状态"时才真正体现。

### 3.2 不要依赖双下划线做安全隔离

由于 `obj._ClassName__value` 可以直接访问甚至修改被改写的属性，双下划线无法提供真正的安全隔离。如果你的属性确实需要保护（如余额、权限标记），应该通过方法做校验，而非指望名字改写挡住外部访问。

**推荐写法（用方法做校验）**

```python
class Wallet:
    def __init__(self, balance=0):
        self.__balance = balance  # 改写为 _Wallet__balance，仅作隔离

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError('取款金额必须为正')
        if amount > self.__balance:
            raise ValueError('余额不足')
        self.__balance -= amount
        return self.__balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError('存款金额必须为正')
        self.__balance += amount
        return self.__balance
```

这里 `__balance` 用双下划线只是表示"内部状态"，真正的业务保护由 `withdraw`/`deposit` 的校验逻辑提供。即便有人写 `wallet._Wallet__balance = -1e9`，那是他主动绕过校验，责任在调用方；而如果连校验方法都没有，只靠双下划线"挡"一下，那才是设计缺陷。

### 3.3 子类中不要手动写改写后的名字

有时你会在子类中需要访问父类的被改写属性，正确做法是通过父类提供的方法访问，而非在子类里写 `self._Base__value`。手动写改写后的名字会让代码与父类的命名强耦合，一旦父类改名或重构，子类代码就会失效。

**推荐写法（用方法访问）**

```python
class Base:
    def __init__(self):
        self.__value = 100

    def get_value(self):  # 父类提供访问接口
        return self.__value


class Sub(Base):
    def __init__(self):
        super().__init__()

    def double_value(self):
        return self.get_value() * 2  # 通过方法访问，而非 self._Base__value


s = Sub()
print(s.double_value())  # 输出：200
```

**不推荐写法**

```python
class Sub(Base):
    def double_value(self):
        return self._Base__value * 2  # 手动写改写名字，强耦合
```

### 3.4 避免对需要被子类覆盖的属性用双下划线

如果你设计的属性是"希望子类提供自己的实现"的扩展点，用双下划线会让子类难以覆盖——子类里写的 `self.__value` 会被改写成 `_Sub__value`，和父类的 `_Base__value` 是两个不同的属性，子类不会"覆盖"父类，而是"共存"。这通常不是扩展点想要的行为。

**推荐写法（扩展点用单下划线或公开名）**

```python
class Base:
    def __init__(self):
        self._handler = self._default_handler  # 扩展点，子类可覆盖

    def _default_handler(self, data):
        return data

    def process(self, data):
        return self._handler(data)


class Sub(Base):
    def __init__(self):
        super().__init__()
        self._handler = self._custom_handler  # 覆盖父类扩展点

    def _custom_handler(self, data):
        return data.upper()


print(Sub().process('hello'))  # 输出：HELLO
print(Base().process('hello'))  # 输出：hello
```

这里 `_handler` 用单下划线，子类可以直接覆盖父类的值，`process` 方法调用时自然走到子类的处理器。如果用双下划线，父类的 `__handler` 和子类的 `__handler` 会共存，`process` 方法在父类内引用的 `self.__handler` 始终指向 `_Base__handler`，子类无法介入。

### 3.5 属性名不要以双下划线结尾的自定义形式

如前所述，`__x__` 形式不触发改写。如果你本意是想用名称重整保护一个属性，却误用了 `__x__` 形式，结果既没得到改写保护，又会让读者误以为是魔术方法。

**不推荐写法**

```python
class Bad:
    def __init__(self):
        self.__internal__ = 42  # 不触发改写，外部可直接访问，还像魔术方法


b = Bad()
print(b.__internal__)  # 输出：42  （没得到保护）
```

**推荐写法**

```python
class Good:
    def __init__(self):
        self.__internal = 42  # 触发改写为 _Good__internal


g = Good()
try:
    print(g.__internal)
except AttributeError as e:
    print(e)  # 输出：'Good' object has no attribute '__internal'
```

### 3.6 调试时善用 __dict__ 与 dir 确认真实名字

当你在调试中遇到 `AttributeError: 'X' object has no attribute '__y'` 时，第一反应应该是查 `obj.__dict__` 或 `dir(obj)`，确认改写后的真实名字。避免盲目猜测。

```python
class DebugTarget:
    def __init__(self):
        self.__secret = '真实的秘密'


dt = DebugTarget()

# 遇到 AttributeError 时
try:
    print(dt.__secret)
except AttributeError:
    print('真实名字:', list(dt.__dict__.keys()))
    # 输出：真实名字: ['_DebugTarget__secret']
```

养成这个习惯后，名称重整带来的"访问失败困惑"就能迅速化解。

## 4. 原理

### 4.1 改写发生在编译期

名称重整最根本的机制特征是：它发生在**编译期**，由 Python 编译器在把源码编译成字节码之前对标识符做文本层面的改写，而非运行时的动态行为。这意味着改写的结果在代码运行前就已经确定，不依赖运行时的任何状态。

具体来说，当 Python 编译器在编译一个类的类体（class body）时，它会扫描类体中所有以双下划线开头、不以双下划线结尾的标识符，并把这些标识符替换为 `_ClassName__原名字` 的形式。这个 `ClassName` 就是当前正在编译的类的名字。改写后的标识符随后被正常编译成字节码，对运行时而言，它就是一个普通的属性名。

```python
import dis


class Exam:
    def __init__(self):
        self.__value = 1  # 编译期改写为 self._Exam__value


# 反汇编 __init__ 的字节码，可以看到 LOAD_ATTR/STORE_ATTR 操作的名字是 _Exam__value
print([instr for instr in dis.get_instructions(Exam.__init__) if 'value' in instr.argrepr])
# 输出：[Instruction(opname='STORE_ATTR', opcode=95, arg=3, argval='_Exam__value',
#        argrepr='_Exam__value', offset=4, starts_line=3, is_jump_target=False, cache_offset=0)]
```

从 `dis` 的输出可以看到，`self.__value = 1` 这条源码编译后的字节码里，`STORE_ATTR` 操作的目标属性名就是 `_Exam__value`，而非源码里写的 `__value`。这直接证明了改写发生在编译期——字节码里已经看不到 `__value` 这个名字了。

**为什么是编译期而非运行时**

把改写放在编译期有几个好处：一是零运行时开销，改写只做一次，之后执行字节码时就是普通的属性访问；二是行为可预测，开发者看到源码就能推算出真实名字；三是与 Python 的动态特性解耦，不需要运行时维护额外的名字映射表。

### 4.2 改写规则与边界详解

名称重整的判定规则严格基于标识符的下划线形态，可以用一个清晰的判定流程来描述。

**判定流程**：

1. 取标识符 `name`。
2. 检查 `name` 是否以**两个及以上下划线**开头：即 `name[:2] == '__'`。若否，不改写。
3. 检查 `name` 是否以**两个及以上下划线**结尾：即 `name[-2:] == '__'`。若是，不改写（这是 dunder 方法）。
4. 同时满足"以 `__` 开头"且"不以 `__` 结尾"，则改写为 `_ClassName + name`。

注意第 3 步的措辞：Python 官方文档的描述是"name ends with at least two underscores"（以至少两个下划线结尾）。这意味着 `__value_`（开头双下划线、结尾单下划线）仍然会被改写，因为它不以"两个及以上下划线"结尾。

```python
class EdgeCase:
    def __init__(self):
        self.__a = 1     # 改写 _EdgeCase__a
        self.__b_ = 2    # 以双下划线开头、单下划线结尾 -> 仍改写 _EdgeCase__b_
        self.__c__ = 3   # 首尾双下划线 -> 不改写
        self._d = 4      # 单下划线开头 -> 不改写
        self.e = 5       # 无下划线 -> 不改写


ec = EdgeCase()
print(ec.__dict__)
# 输出：{'_EdgeCase__a': 1, '_EdgeCase__b_': 2, '__c__': 3, '_d': 4, 'e': 5}
```

观察 `__dict__`：`__b_` 被改写为 `_EdgeCase__b_`（因为它不以两个下划线结尾），`__c__` 未被改写，`_d` 和 `e` 也未改写。这与判定流程完全吻合。

**改写后名字的构造**

改写后的名字 = `_` + `ClassName` + 原名字。注意：

- 前缀只有一个下划线，不是两个。
- `ClassName` 是定义所在类的名字，不包含模块名、不包含父类名。
- 原名字（含开头的双下划线）整体拼接在 `ClassName` 之后，所以 `__value` 改写为 `_ClassName__value`（`__` 来自原名字）。

### 4.3 为何能避免子类覆盖

名称重整能避免子类覆盖父类同名属性的根本原因，在于改写后的名字"携带了定义所在的类名"，使得父子类各自的 `__value` 改写后变成不同字符串，在实例字典里占据不同键位。

具体来看：

- 父类 `Base` 内的 `self.__value = x` 被改写为 `self._Base__value = x`。
- 子类 `Sub` 内的 `self.__value = y` 被改写为 `self._Sub__value = y`。

这两个键 `_Base__value` 和 `_Sub__value` 是不同的字符串，Python 的字典按键存储，不同的键互不影响。所以即便同一个实例的 `__dict__` 里同时存在这两个键，它们也各自独立，赋值一个不会影响另一个。

```python
class Base:
    def __init__(self):
        self.__value = 'base'  # _Base__value


class Sub(Base):
    def __init__(self):
        super().__init__()
        self.__value = 'sub'   # _Sub__value


s = Sub()
# 两个键共存，互不覆盖
assert '_Base__value' in s.__dict__
assert '_Sub__value' in s.__dict__
assert s.__dict__['_Base__value'] == 'base'
assert s.__dict__['_Sub__value'] == 'sub'
print('共存验证通过：', s.__dict__)
# 输出：共存验证通过： {'_Base__value': 'base', '_Sub__value': 'sub'}
```

**父类方法引用 self.__value 的行为**

关键还在于父类定义的方法内部对 `self.__value` 的引用，也在父类编译时被改写为 `_Base__value`。这意味着：即使 `self` 运行时是 `Sub` 实例，父类方法读到的依然是 `_Base__value` 这个键，而非子类的 `_Sub__value`。这就保证了父类的"私有"逻辑不会被子类干扰。

```python
class Base:
    def __init__(self):
        self.__value = 'base'

    def whoami(self):
        # 这里的 self.__value 在 Base 编译时改写为 _Base__value
        return f'Base sees: {self.__value}'


class Sub(Base):
    def __init__(self):
        super().__init__()
        self.__value = 'sub'  # _Sub__value

    def whoami_sub(self):
        # 这里的 self.__value 在 Sub 编译时改写为 _Sub__value
        return f'Sub sees: {self.__value}'


s = Sub()
print(s.whoami())     # 输出：Base sees: base
print(s.whoami_sub()) # 输出：Sub sees: sub
```

`s.whoami()` 调用的是父类 `Base` 定义的 `whoami` 方法，方法体内的 `self.__value` 在编译期就被绑定为 `_Base__value`，所以读到 `'base'`；`s.whoami_sub()` 是子类定义的方法，其 `self.__value` 绑定为 `_Sub__value`，读到 `'sub'`。两个方法各看各的"私有"属性，互不串扰。

**没有名称重整会怎样**

对照一下没有名称重整（用单下划线或普通名）的情况，就能看出重整的关键作用。

```python
class BaseNoMangle:
    def __init__(self):
        self._value = 'base'  # 不改写

    def whoami(self):
        return f'Base sees: {self._value}'


class SubNoMangle(BaseNoMangle):
    def __init__(self):
        super().__init__()
        self._value = 'sub'  # 不改写，直接覆盖父类的 _value


s2 = SubNoMangle()
print(s2.whoami())  # 输出：Base sees: sub  <- 父类方法读到的是被覆盖后的值
```

这里父类的 `whoami` 读到 `'sub'` 而非 `'base'`，因为 `_value` 没有被改写，子类的赋值覆盖了同一个键。这就是名称重整要解决的核心问题。

### 4.4 为何不算真正的私有

名称重整经常被误称为"私有属性机制"，但它并不提供真正的访问控制。它不算真正私有的原因有三层。

**第一层：改写后的名字是可预测、可访问的。**

改写规则是公开且确定的：`_ClassName__attrname`。任何人只要知道类名和属性名，就能算出真实名字并直接访问。Python 不会对这种访问做任何拦截。

```python
class Secret:
    def __init__(self):
        self.__password = 's3cret'  # _Secret__password


st = Secret()
# 改写后名字可直接访问
print(st._Secret__password)  # 输出：s3cret
# 甚至可以直接修改
st._Secret__password = 'hacked'
print(st._Secret__password)  # 输出：hacked
```

**第二层：dir 和 __dict__ 会暴露改写后的名字。**

实例的 `__dict__` 和 `dir()` 会列出所有属性，包括改写后的。没有任何机制把这些名字隐藏起来。

```python
print([n for n in dir(st) if 'password' in n.lower()])
# 输出：['_Secret__password']
print(st.__dict__)
# 输出：{'_Secret__password': 'hacked'}
```

**第三层：没有运行时访问权限检查。**

不同于 Java 的 `private` 会在编译期检查访问权限、在运行时也可能做反射限制，Python 完全不做这类检查。任何代码在任何位置都可以访问任何对象的任何属性，只要名字写对。这是 Python 动态语言本性决定的。

所以名称重整的本质是"改名隔离"而非"访问禁止"。它的价值在于避免无意覆盖、让有意访问者显式表达意图，而非阻止访问。

### 4.5 self.__value 在类体内引用的改写一致性

前面多次提到"类体内引用也会被一致改写"，这一节我们深入看这个一致性是如何保证的，以及它为什么重要。

名称重整对"定义"和"引用"是一视同仁的：只要标识符在某个类的类体内出现，且符合改写条件，无论是出现在赋值左侧（定义/赋值）还是表达式右侧（读取）或方法调用中，都会被改写。这个改写依据的是标识符所在的**词法作用域**——即源码上它写在哪个类的类体里，而非运行时 `self` 的类型。

```python
class Lexical:
    def __init__(self):
        self.__data = [1, 2, 3]  # 改写 _Lexical__data

    def read(self):
        # 引用 self.__data，在 Lexical 类体内 -> 改写为 _Lexical__data
        return self.__data

    def append(self, item):
        # 引用 self.__data，在 Lexical 类体内 -> 改写为 _Lexical__data
        self.__data.append(item)
        return self.__data


class Child(Lexical):
    def read_child(self):
        # 引用 self.__data，在 Child 类体内 -> 改写为 _Child__data
        # 注意：这不是父类的 _Lexical__data
        return self.__data


c = Child()
# Child.__init__ 没有定义，调用父类 Lexical.__init__，创建的是 _Lexical__data
c.append(4)
print(c.read())       # 输出：[1, 2, 3, 4]    （走 _Lexical__data）

# read_child 试图读 _Child__data，但从未被创建
try:
    print(c.read_child())
except AttributeError as e:
    print(e)  # 输出：'Child' object has no attribute '_Child__data'

print(c.__dict__)  # 输出：{'_Lexical__data': [1, 2, 3, 4]}
```

这个例子非常关键。`Child` 没有定义自己的 `__init__`，所以实例化时调用父类 `Lexical.__init__`，创建的是 `_Lexical__data`。但 `Child.read_child` 方法在 `Child` 类体内引用 `self.__data`，编译期被改写为 `_Child__data`——这与父类的 `_Lexical__data` 是两个不同的名字，所以 `read_child` 找不到对应的属性，抛出 `AttributeError`。

**一致性的意义**

这种"定义和引用都改写、且依据词法类"的机制，带来了一致性：在同一个类体内，`self.__value` 无论出现在定义、读取还是调用处，都指向同一个被改写后的名字 `_ThisClass__value`。开发者不需要区分"这个 `self.__value` 是定义还是引用"——它们全部一致地映射到同一个底层名字。这种一致性让类体内的代码逻辑保持自洽：你在 `__init__` 里存的 `__value`，在你这个类的其他方法里用 `self.__value` 一定能读到。

代价是：子类中引用 `self.__value` 不会读到父类的值，它指向子类自己的 `_Child__value`。这是名称重整"避免覆盖"的另一面——父子类各自独立，互不串扰。如果你确实需要子类访问父类的被改写属性，要么父类提供公开/受保护的方法（推荐），要么子类手动写 `self._Parent__value`（不推荐，强耦合）。

### 4.6 改写与继承、MRO 的关系

名称重整与继承体系、方法解析顺序（MRO）之间有几个值得注意的交互点。

**改写不沿继承传递**

父类的 `__value` 改写为 `_Base__value`，子类不会"继承"这个改写规则。子类里写 `self.__value` 时，依据的是子类的名字，改写为 `_Sub__value`。改写是"每个类各自做"的，不沿 MRO 传递。

**父类方法在子类实例上调用时，仍用父类的改写名字**

父类 `Base` 定义的方法 `whoami` 里引用 `self.__value`，这个引用在 `Base` 编译时被改写为 `_Base__value`。当子类实例调用 `whoami` 时，方法体里的字节码已经是 `LOAD_ATTR _Base__value`，不会因为 `self` 是 `Sub` 实例就变成 `_Sub__value`。这就是为什么父类方法在子类实例上仍能正确读到父类的"私有"属性。

**多重继承下各基类的 __attr 互不冲突**

前面 2.4 节的 `Logger`/`Cache` 例子已经展示过：多个基类各自有 `__buffer`，改写后分别是 `_Logger__buffer` 和 `_Cache__buffer`，互不冲突。这是名称重整在多重继承中的最大价值——它让各基类的内部状态保持独立，不因组合而互相覆盖。

**MRO 不影响改写名字的确定**

MRO 决定的是"方法从哪个类取"，而改写名字在编译期就确定了。即：父类方法体内的 `self.__attr` 永远是 `_Parent__attr`，无论该方法最终通过怎样的 MRO 路径被调用。MRO 影响"调用哪个类的方法"，不影响"方法内的属性改写名字"。

### 4.7 改写与模块、全局作用域的边界

名称重整只在**类体**内生效。模块级别的全局变量、函数内的局部变量，即使名字以双下划线开头，也不会被改写——因为它们不在任何类的类体里。

```python
__module_var = '我不在类体里，不会被改写'


def func():
    __local = '我也不会被改写'
    return __local


print(__module_var)  # 输出：我不在类体里，不会被改写
print(func())        # 输出：我也不会被改写
```

只有当 `__name` 形式的标识符出现在某个类的类体内时，改写才会发生。这是初学者容易混淆的点——看到双下划线就以为会被改写，实际上脱离类体就没有改写。

```python
class OnlyHere:
    __class_attr = '我在类体里，会被改写'  # _OnlyHere__class_attr

    def show(self):
        return OnlyHere.__class_attr  # 类体内引用，一致改写


print([n for n in dir(OnlyHere) if 'class_attr' in n])
# 输出：['_OnlyHere__class_attr']
```

注意这里 `__class_attr` 是类属性（定义在类体但不在方法内），同样会被改写为 `_OnlyHere__class_attr`。改写不区分实例属性还是类属性，只看"是否在类体内且符合命名规则"。

### 4.8 名称重整与属性描述符、property 的交互

当双下划线属性名遇上描述符（descriptor）或 `property` 时，改写依然基于命名规则发生，但需要注意描述符的查找链与改写后名字的关系。

```python
class Temperature:
    def __init__(self, celsius):
        self.__celsius = celsius  # _Temperature__celsius

    @property
    def celsius(self):
        return self.__celsius  # 类体内引用，改写为 _Temperature__celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError('低于绝对零度')
        self.__celsius = value  # 改写为 _Temperature__celsius


t = Temperature(25)
print(t.celsius)  # 输出：25
t.celsius = 30
print(t.celsius)  # 输出：30

try:
    t.celsius = -300
except ValueError as e:
    print(e)  # 输出：低于绝对零度

# 被 property 包装的是 celsius（不改写），底层存储是 _Temperature__celsius
print(t.__dict__)  # 输出：{'_Temperature__celsius': 30}
```

这里 `celsius` 是 property 对象，名字不以双下划线开头，不触发改写，作为公开访问接口；而 `__celsius` 是底层存储，被改写为 `_Temperature__celsius`。property 的 getter/setter 内部引用 `self.__celsius`，在类体内一致改写，所以能正确访问底层值。这是一个常见的"用 property 保护双下划线属性"的实践模式。

## 5. 总结

### 5.1 本文内容要点

- **名称重整的定义**：以两个及以上下划线开头、不以两个及以上下划线结尾的属性名（如 `__value`），在类体内会被 Python 编译器自动改写为 `_ClassName__value` 的形式。
- **触发规则与边界**：`__value` 改写、`__value__`（dunder）不改写、`_value`（单下划线）不改写；改写后的名字是 `_ClassName + 原名字`。
- **类体内部引用一致性**：类体内对 `self.__value` 的定义、读取、赋值、调用都会被一致改写，依据的是词法所在的类，而非运行时 `self` 的类型。
- **类外部访问**：`obj.__value` 会失败（真实名字不是 `__value`），但 `obj._ClassName__value` 可直接访问，所以并非真正私有。
- **避免子类覆盖**：父类 `__value` 改写为 `_Base__value`，子类 `__value` 改写为 `_Sub__value`，二者在实例字典里共存互不冲突，这是名称重整的核心价值。
- **魔术方法不改写**：`__init__`、`__str__` 等 dunder 方法因首尾双下划线不触发改写，保证了协议调用机制的稳定。
- **单下划线与双下划线的取舍**：默认用单下划线做"软私有"，仅在需要避免子类覆盖时才用双下划线；不要用双下划线做安全隔离。
- **inspect 观察**：用 `dir()`、`__dict__`、`inspect.getmembers` 可看到改写后的真实名字。
- **原理**：改写发生在编译期，由编译器对类体内符合规则的标识符做文本替换，改写后的名字进入字节码；运行时零额外开销，行为可预测。

### 5.2 读完应能掌握

- 能说明 `__value`、`__value__`、`_value` 三者在名称重整上的区别及各自适用场景。
- 能写出 Base 与 Sub 各有 `__value` 共存不冲突的 demo，并用 `__dict__` 验证两个改写后的名字。
- 能解释为何 `obj.__value` 在类外失败、而 `obj._ClassName__value` 能访问，并说明"不是真私有"的原因。
- 能用 `dis` 或 `__dict__` 观察编译期改写后的真实名字，并在调试中据此解决 `AttributeError`。
- 能在工程中正确选用单下划线或双下划线，避免过度使用双下划线或误用 `__x__` 形式。
- 能用 `property` 配合双下划线属性，既保证内部存储的改名隔离，又提供受校验的公开访问接口。
- 能解释 `self.__value` 在父类方法与子类方法中分别引用不同底层名字（`_Base__value` vs `_Sub__value`）的原理，避免在子类中误读父类私有属性。
